# Verification

Owner: A6 (independent verification and OT safety). A6 writes this document independently of the implementing agents and actively attempts to disprove their claims.

Status: **Phase 0 draft (2026-10-23).** No lab IED exists; every slice result can reach `simulated` at most. A1 accepted the criteria below as the Phase 0 baseline on 2026-10-23. Numeric thresholds marked *(proposed)* stay proposed until the owning agent confirms or replaces them with evidence in Phase 1. No product code exists, so nothing below has been verified against an implementation. Executed so far: experiment E-01, the recording simulator self-test, the A3 E1 reproduction with extra probes (all `simulated`), and the A2 register corpus review (`desk`).

## Rules

- A test result is reported only with reproducible output committed under `tests/`.
- Every result states its evidence class: `hardware`, `simulated` (simulator, emulator, loopback), `fixture` (recorded real or sanitized real output), or `desk` (document analysis only, nothing executed). These map onto the capability classes in [device-capabilities.md](device-capabilities.md); a `simulated` or `fixture` result never supports a `hardware-verified` claim.
- A critical unresolved safety or security failure blocks milestone acceptance regardless of other progress.
- Claims by implementing agents are inputs to verification, not evidence.
- **Oracle independence.** A6 tests must not import the implementation's parsers, normalizers, or schema helpers to compute expected results. Expected values come from the raw fixture, the OEM document, or a hand-built ground-truth file committed next to the fixture. A test that compares the implementation with itself is not verification.
- **Negative tests are mandatory.** Every criterion that says "only", "never", or "no" has at least one test that tries to make the forbidden thing happen.
- Recalled vendor facts in this document (for example SEL command behaviour) are marked *recalled*. They are leads for A2 to confirm against an OEM manual, not evidence.

## First vertical slice acceptance criteria

Target (brief, Phase 2): collect native SER records from a representative lab IED and securely forward them to an upstream Syslog collector, with local asset identification and evidence preservation.

**Constraint confirmed by the project owner (via A1, 2026-10-23): there is no lab IED and there are no real device outputs.** The slice is therefore verified against OEM documentation and a device simulator only. The highest evidence class any slice result can reach is `simulated`. Each criterion below states what a passing simulator run proves, and what remains unproven until hardware exists. A milestone report that drops the second column misstates the result.

Ground-truth sources named below:

- **GT-DOC:** the OEM manual section cited by A2 in the approved command register or capability matrix (document title, revision, section, page).
- **GT-EX:** a documentation example (sample command output printed in an OEM manual), transcribed into a fixture by A6 with a `SOURCE.md` naming the page. These are `documented-example` fixtures, not device output (see "Device simulator plan").
- **GT-HAND:** a hand-written expected-results file A6 derives from GT-EX without running project code.
- **GT-REC:** the recording simulator's byte log ([tests/safety/recording_simulator/](../tests/safety/recording_simulator/)).
- **GT-RX:** an independent upstream receiver that is not project code (for example a stock rsyslog or syslog-ng instance), whose received-message log is the ground truth for forwarding.

## Monitoring goals acceptance criteria (ADR-0008)

New ground-truth sources, in addition to GT-DOC, GT-EX, GT-HAND, GT-REC and GT-RX above:

- **GT-INJ:** a labelled schedule written by A6 from a fixed seed before the implementation exists: an event series or a configuration-change series, each injected departure or change listed with its time, kind and the alarm it must raise. The schedule is committed before the test first runs against the product. Synthetic, so it supports `simulated` claims only.
- **GT-PCAP:** a capture whose labels (address, port, protocol, version, direction) A6 wrote with an independent decoder (tshark or Zeek), never with the product. A public or lab capture, with a `SOURCE.md`.
- **GT-MIB:** a recording SNMP agent that A6 builds from the vendor MIB and manual: the values it serves, and a log of every PDU it received (the SNMP counterpart of GT-REC).
- **GT-ADV:** a hand-built applicability truth table: asset identities and their evidence sources, crossed with test advisories, each cell the class it must get. Test advisories are marked `test-only` and never enter a shipped advisory set (R9 constraint, P10).

### R4.8 observation period and measures

These semantics are fixed now so that the R4.8 brief designs to them; A1 may change them only by amending this section before the tests are written.

- **Event-type key.** An event's type is, for SER, the element name and its state as printed (for example `51P1P` `Asserted`); for Syslog, the sender's facility, severity and the message ID or, without one, the message text with digits replaced (the template). The R4.8 contract must name the key exactly; A6's tests use that definition, and a key that changes after the tests are written is a contract change.
- **Clock.** Rate and time-of-day rules use the platform's receive time. A time-of-day rule may use the device's wall-clock time only when the event's offset is known (V-S3), and the alarm says which clock it used.
- **Observation period.** It starts at the first event stored for the asset after the baseline is enabled, and ends when both a minimum duration (14 days *(proposed)*) and a minimum event count (200 events *(proposed)*) are reached. Only time with successful collection counts: an interval in which the asset's collection failed (any V-S12 failure) extends the period by its length, and the baseline records its coverage. During the period no departure alarm is raised, and health shows the progress (days and events so far, out of the minimum). Collection and V-S12 health alarms are unaffected.
- **The baseline.** At the end of the period it is recorded once, versioned and hashed in the audit chain, listing every event type learnt with its counts, its hours of occurrence and any periodic pattern found. It never changes silently: re-learning is an explicit, audited action that records the old and the new baseline. The baseline becomes active only after an operator acknowledges it, and the acknowledgement is recorded in the audit chain (A1 ruling on #144, 2026-10-26). An event type learnt during a compromise is therefore seen by a person before it becomes normal. Until the acknowledgement, no departure alarm is raised, and health shows the baseline as awaiting acknowledgement.
- **Departure rules**, each with its parameters shown in the alarm:
  1. **New type:** an event type not in the baseline, alarmed on its first occurrence.
  2. **Repeats:** the same type more than N times in a window W, when the baseline's maximum for that window was below N.
  3. **Rate:** an event type's count in a time bucket above the baseline's bound for that bucket. The rule and bound are named in the brief (for example the maximum seen times a factor), never learnt silently.
  4. **Time:** an event type at an hour in which the baseline never saw it.
  5. **Absence:** a type that the baseline found periodic (a regular interval with stated tolerance) does not occur within its interval plus tolerance.
- **Measures**, reported on every run:
  - **Recall per departure kind** on a GT-INJ series that contains at least 3 injected departures of each kind: the number alarmed over the number injected. The target is 100%.
  - **False positives** on a held-out benign series from the same generator (a different seed), as long as the observation period. The measure is departure alarms per asset-day. The bound is 0 on synthetic series *(proposed)*; the bound for real data is set once a real history exists.
  - **Precision** on the injected series: alarms that match an injected departure over all departure alarms.
  - **Latency:** the time from the event that broke the baseline to the alarm. The target is within one collection cycle.
  - A synthetic false-positive rate says nothing about a real device and is reported as `simulated`.

### R9 classes and what `confirmed` needs

- **`applicable-by-version`:** the asset's product and version fall inside the advisory's affected range. Any identity source may produce it; the finding names the source (`device-read`, `passive`, `operator`) and lists every other precondition of the advisory that was not read.
- **`confirmed`:** all three of these hold, and nothing less:
  1. The product and version were read from the device itself through a registered read path (for example `ID`, `CFG.TXT` or SNMPv3), with the evidence ID and time.
  2. Every further precondition the advisory names is evidenced: an affected option fitted, a setting enabled, an interface or service enabled. Evidence is a device-read value, or, for a precondition that a service is reachable on the network, a passive observation of the device's own traffic (R6.7) that cites its packets.
  3. The evidence is current: no later read contradicts it, and no configuration change has been retrieved since.

  `confirmed` means the advisory's stated conditions hold on this device. It never means that exploitation was tested or is possible (P10), and nothing is ever probed to reach it (R9.4).
- **`mitigated`:** the advisory or the vendor names a mitigation, and the mitigation is evidenced by a device-read setting or by a recorded network control. A control entered by an operator is labelled `operator-attested`.
- **`not-applicable`:** a device-read identity outside the affected range, or a product the advisory does not name. An operator-entered identity outside the range gives `not-applicable (operator)`, which is reported as weaker evidence.

## Proposed architecture-critical risks (A6 input to the Phase 0 exit gate)

A1 consolidates the five risks the gate requires. A6 proposes these, ranked by consequence:

1. **Read-only collection has device side effects** (C-01, C-02, C-12). Consequence: a monitoring feature changes device state, trips a SCADA alarm, or locks out an engineer. Owner: A2.
2. **The platform holds a path into IEDs** (C-07, C-08, C-12, B-04, B-05). Stored credentials, a spoofable device identity, and hostile device output each give an attacker leverage. Owner: A3.
3. **No primary device evidence** (C-10, B-01). Every interoperability claim in the first slice is currently unprovable beyond `simulated`. Owner: A2 with the project owner.
4. **Delivery guarantees are weaker than the requirements assume** (C-04, E-01, B-03). Owner: A4 and A5.
5. **Timestamp and ordering fidelity across vendors** (C-05, C-06, Q3). Owner: A4 with A2.

## Independent validation methods (from the brief, section 7)

- Asset identification: compare collected attributes against OEM documentation and actual device information.
- Configuration monitoring: apply a known change in a controlled environment and verify the expected meaningful difference.
- SER collection: reconcile original device events with collected and forwarded events (timestamps, order, duplicates, missing data).
- Secure access: demonstrate permitted operation, unauthorized access denial, session expiration, and revocation.
- IDS: labeled benign and malicious traffic; measure false positives, detection effectiveness, and latency.
- Distributed operation: simulate site disconnection, process termination, delayed events, and reconnection.
- OT safety: verify passive functions generate no control/write commands and approved reads stay within tested limits.

- **Evidence class:** `desk`, `simulated`. Which case is real needs H-12.
- **Disproves:** that `SHO P 1` alone can detect a Spanish port.

### F-001 — 2026-10-23 — E-01: TLS syslog write success does not imply delivery

- **Tested:** whether a forwarder can treat error-free writes to an RFC 5425 (syslog over TLS, octet-counted) collector as delivered.
- **How:** loopback TLS collector reads 50 frames, stops reading while the forwarder writes 100 more, then resets the connection as a crashed collector would. Five trials. Script: [tests/integration/experiments/syslog_tls_delivery_gap.py](../tests/integration/experiments/syslog_tls_delivery_gap.py).
- **Result:** 5 of 5 trials: forwarder recorded 150 successful writes, collector received 50, 100 frames lost with no error at write time. The first error surfaced only on a later write (`ConnectionResetError`).
- **Evidence:** [tests/integration/experiments/results/E-01-2026-10-23.json](../tests/integration/experiments/results/E-01-2026-10-23.json). Class `simulated` (Python 3.13.17, OpenSSL 3.0.13, Linux loopback). The size of the loss window depends on socket buffer sizes, which on real hosts can reach megabytes.
- **Disproves:** the implicit assumption that RFC 5425 forwarding alone satisfies R4.7 "retransmission" and V-S6. Raised as C-04 and B-03.
