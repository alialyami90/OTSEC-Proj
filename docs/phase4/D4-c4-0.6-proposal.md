## 1. What 0.6 changes, and nothing else

- **The identifier** becomes `otsec.event/0.6`, and `self` in `contracts/event/validate.go` moves to minor 6. As in 0.4 and 0.5, `Identifier` is one constant, so every event the node writes is stamped 0.6.
- **C4-0.6-1** adds the health type `detector.observation-refused` (§2.1).
- **C4-0.6-2** adds the health type `detector.baseline-refused` (§2.2).
- **C4-0.6-3** states that a `network-observation` or `collection.run` event of a later C4 minor is refused at judging, not at decoding (§3.1).
- **Beside it, C13's text** declares the stored observation strict (§3.2). That changes what a reader does, not what any writer emits, so C13 stays at minor 0.3 (C13 note, §4: "C13 text ... before the next C13 minor").

**Unchanged:** every envelope field, every closed set, `event.Decode`, every other health type and its details, `sensor.counters` (C4-0.4-1 to C4-0.5-3), and C6. In particular, no field or flag of a `network-observation`, `collection.run`, SER or Syslog envelope changes. That is the statement C4 (b)'s guard asks of any C4 minor approved before (b) merges (C4 note, §2 (b), "Why C4 0.4 and 0.5 sit below the floor"). It is `desk`.

## 2. The two health types

Both types are platform events (`origin: platform`, `kind: telemetry-health`). The node writes both on the health stream through `sensorHealth`. Both are open-set additions to `Health.Type`, which "later minors may add" (`event.go`). Each also gets its own detail check in `Event.validate`, beside `checkSensorCounters`, so a malformed event is refused at commit like a malformed `sensor.counters`.

**Rules for both types:**

- **New in 0.6.** An event of either type stamped 0.5 or earlier is refused (`forbidden`, `health.type`: "new in otsec.event/0.6"), as `sensor.counters` is below 0.3. No build writes either type before 0.6. If one did, its events would then be unreadable as well as unshared (D5's note, §7).
- **Closed at the event's own minor, open for a later one.** For an event stamped at or below the reader's minor, a detail key, `reason.<r>` name or `cause` value that this section does not define is refused (`enum`, "not a detail of `<type>` in `<schema>`"). For an event stamped above the reader's minor, it is accepted, and the forms of the keys this section defines are still checked. This follows `checkSensorCounters`'s `later` branch.
- **Values.** A "count" below is a decimal from 1 to 2^64 − 1 with no leading zero (`^[1-9][0-9]{0,19}$`, then parsed as a `uint64`), the same form as `runs_folded` (C4-0.5-1). `0`, a leading zero, a sign and a value above 2^64 − 1 are refused (`enum`).
- **No record text.** Every value is a count, a node-held name, a time the node wrote, a hash, or a parsed identifier. So no value can carry record or document text, and none can contain the bytes `"collection.run"`, which is the filter `newSessions` uses on the health stream (§4).

### 2.1 C4-0.6-1. `detector.observation-refused`

This event carries the durable counts of stored observations that the network detector refused to judge, by reason, since `since`. It is D5's design, option B of section 2.4: written before the detector checkpoint whose interval refused a record.

| Detail | Required | Form |
| --- | --- | --- |
| `stream` | yes | the observation stream it counts, a C4 stream token (`Stream.Valid`) |
| `since` | yes | when these counts began, RFC 3339 as `time.RFC3339Nano` parses it, as in `intake.drop-counted` (`countDetails`). Otherwise refused (`time-format`) |
| `through` | yes | a count: the `Through` of the checkpoint that this event precedes |
| `count` | yes | a count: the sum of every `reason.<r>` in the event |
| `reason.<r>` | at least one | a count: the records refused for reason `<r>` since `since`. Present only when above 0 |
| `first_seq.<r>`, `last_seq.<r>` | exactly when `reason.<r>` is | counts: the lowest and highest seq refused for `<r>` since `since` |

- **The closed set of `<r>`:** `later-minor`, `malformed`, `detector-refused`. These are D5's three reasons, section 2.1.
- **Relations checked** (each refused as `enum` and naming its detail):
  - `count` equals the sum of the `reason.*` values, and that sum fits in a `uint64`;
  - for each `<r>`, `first_seq.<r>` ≤ `last_seq.<r>` ≤ `through`.

  Each holds by D5's construction: `Detector.Observe` takes a refused record's seq into `Through`, and a counted refusal has a seq above the restored event's `through`. So a failure here is a writer defect. It shows as a refused commit, which D5's design already handles as an owed event: the checkpoint waits, then the alarm `network-refused-counts-unwritten`.
- **Not checked:** that `last_seq.<r>` − `first_seq.<r>` + 1 ≥ `reason.<r>`. D5's section 8 names the build-change cases in which a count can be wrong without being flagged. Refusing such an event would turn a miscount into an unwritten one. Whether the counts are true rests on the writer and on D5's T5 and T6.
- At most 13 details. D5's T10 pins the rendered size against a default Syslog target's 2,048 octets.

### 2.2 C4-0.6-2. `detector.baseline-refused`

This event records that the approved network baseline was refused and the detector is off. It is D5's section 3.1: written once per down stretch.

| Detail | Required | Form |
| --- | --- | --- |
| `hash` | yes | `sha256:` and 64 lowercase hex digits: the refused document's `netobs.Digest` |
| `schema` | yes | `unreadable`, or a string that `version.Parse` reads with the name `netbaseline` |
| `cause` | yes | the closed set `later-minor`, `not-canonical`, `malformed` (D5's section 3.1) |

- **A relation, checked:** `cause: later-minor` with `schema: unreadable` is refused (`enum`), because a later minor is known only from a stamp that parsed.
- **Not checked by C4:** whether the stamp is above `baselineSelf`. `contracts/event` does not import `contracts/netobs`, since `netobs` imports `event`. That the cause is right is `NewDetector`'s classification (D4's) and D5's T8.
- `schema`'s form is the contract check behind D5's rule that a value from a refused document is shown "only when it parses". A value that does not parse cannot be committed in this event.

### 2.3 The writer's rules (D5's, checked by D5's tests)

- **Built when written.** A counts event or a baseline event that is owed, because its write failed or the ceiling or its budget holds it, is kept as counts or as the alarm's state. It is built and stamped when it is written, and never kept as built bytes across a restart. That is the condition under which C4 0.4 and every later minor need no floor: no pending C4 event outlives the process that built it (`docs/release.md` §7.2, the C4 0.4 row). D5's note already describes it this way: the flag and the range live in memory, and the baseline event is "tried again at each tick step". E6-16 tests it.
- The budgets (4 an hour for the counts event, the pool for the baseline event), the cadence, the start's scan and the `since` and `through` rules are D5's note, unchanged.

## 3. What a 0.6 reader refuses on the network path

### 3.1 C4-0.6-3. A later C4 minor's `network-observation` and `collection.run`

This is the text of C4's (b) as approved, in contract form.

- **`event.Decode` is unchanged.** It reads a later 0.x minor forward with `strictjson.Forward` and then validates it. SER, Syslog, `sensor.counters`, `netobs.alert` and every other health event keep their forward read, as do the two new types.
- **The check.** One exported function in `contracts/netobs` takes an event and returns nil or the refusal below. The proposed name is `CheckEventMinor(*event.Event) error`. Under it is an unexported helper that takes the event's `schema` and a reader's C4 minor as arguments. The exported function passes C4's own minor, read from `event.Identifier`, and never C13's `self`.
- **Its callers:**
  - `ObservationFromEvent` (D4): after its `kind` check, and before `DecodeStored`.
  - `observationOf` (D5): on the path where `event.Decode` returns an error and a non-nil event. A later-minor stamp is refused ahead of the `Validate` error. An error with no event (duplicate key, case variant) stays a decode error.
  - `runSessionOf` (D5), on both decode paths, in this order:
    1. `health.type == collection.run`. Any other type is no session, whatever its stamp.
    2. The stamp check.
    3. The `after_seq` test and the session's fields, as on `main`.

    A refusal is an error, so `newSessions` marks the entry `bad`.
- **The refusal.** A `*netobs.Error` with `Code: CodeSchema` and `Field: "schema"`, for which `errors.Is(err, netobs.ErrLaterMinor)` holds. A schema the check cannot read (empty, unparseable, another name, another major) is refused as `CodeSchema` without `ErrLaterMinor`. This fails closed, and no product path reaches it, since `event.Decode` already refuses each of those.
- **The `Field` split** (D4's F1 on #766). `ObservationFromEvent` prefixes each `Field` that `DecodeStored` returns with `netobs.`, so the C13 stamp reads `netobs.schema` and the C4 stamp `schema`. A later-minor refusal of either kind is returned alone, never inside an `errors.Join`. That way the error the node matches with `errors.Is(ErrLaterMinor)` is the one whose `Field` it reads. `DecodeStored`'s own whole-body `Field`, `netobs` (its `CodeRange` and `CodeDecode` errors), stays `netobs` and is not doubled (§8 item 2).

### 3.2 C13's text beside it (no C13 minor)

This is the text of C13's (b) as approved, condition 2.

- **The stored observation is strict.** `DecodeStored` refuses a stored observation whose `schema` is a later C13 minor than the reader's `self`. The refusal is in `validateStored`, after `storedSchema`, on the stored observation's path only. It is `CodeSchema` with `ErrLaterMinor`. `DecodeStored`'s first decode stays `strictjson.Forward`, so a later record is refused as `schema` whether or not it carries an unknown key.
- **What it supersedes.** CH-35's "forward for a later one" no longer applies to the stored observation. It still applies to alerts (bridge items 3 and 4) and to baselines, where `DecodeBaseline` is unchanged and `IsCanonical` already refuses.

## 4. Earlier readers and rollback

| | Reads a 0.6 `detector.*` event | Reads any other 0.6 event |
| --- | --- | --- |
| C4 0.3 to 0.5 code | Yes. `Health.Type` is open, and these readers have no detail rule for either type, so the event passes `Validate` read forward. No product reader on those builds acts on it: `eventFeed.takeHealth` returns at `default` for a type it does not route, `lastDropCounts` pins `intake.drop-counted`, and `newSessions` skips a record without `"collection.run"` | Yes, read forward. Nothing is dropped, because 0.6 adds no envelope key or flag value (§1). So a 0.5 build's forward read of a 0.6 `network-observation` or `collection.run` judges what the 0.6 build would judge. This is `desk`, the same per-minor reading as for 0.4 and 0.5 (C4 note §1.4) |
| C4 0.6 code | Yes, with §2 checked | Yes. Network events of 0.6 or earlier are judged, and later ones are refused (§3) |

- **No reader floor from 0.6's types.** Every earlier reader accepts every 0.6 event (E6-4), and no earlier build reads a `detector.*` event at all.
- **Receivers first** (C6, `contracts/syslog/doc.go`, "Versions"). Every forwarded event's `ev` becomes `otsec.event/0.6` at once, as with 0.4 and 0.5. `Render` renders the new details as `hd` parameters, and C6 does not change.
- **The C4 0.4 condition holds** if the writer rule of §2.3 holds: no pending C4 event outlives the process that built it. A 0.5 build therefore reads every stored 0.6 event, and refuses only a pending one.
- **What a rollback from the 0.6 build to a 0.5 build costs.** None of it is a misjudgement:
  - while rolled back, refusals are back to `main`'s in-memory `observations_refused`, with no alarm and no counts event, and a later C4 or C13 record is read forward again. No such record exists unless a build above 0.6 or above C13 0.3 ran, and the floor of §5 keeps a node that ran one out of this rollback;
  - when the node is moved forward again, its start finds the newest counts event's `through` below the restored checkpoint, and reads that as "no refusal in between". The older build's refusals are then counted nowhere, and status shows the counts as exact. That is a build change between an event and a later checkpoint. D5's note conditions exactness on its absence (section 2.4, "Recommendation: B"; section 8). This proposal restates the limit and adds no mechanism (§7).

### Order

- **One merge carries the refusals and the alarm.** D1's 7011347039 puts (b) in "the same change and C4 minor" as the types, after D5's alarmed refusal, and D5's node code writes types that only the 0.6 validator defines. ## 7. Limits

- The validator checks the form of both events, not their truth. That the counts are exact rests on D5's design and tests, within the limits of D5's section 8.
- A rollback below 0.6 and a move forward again leave the older build's refusals uncounted, while status shows the counts as exact (§4). The OS log's `observations_refused` lines of that build are the only trace. This proposal names the limit and does not close it.
- The reading that 0.4, 0.5 and 0.6 leave the two network envelopes unchanged is `desk`, and no test checks it (C4 note §1.4).
- Every residual of the two notes stands:
  - a hand install below the floor;
  - AP-10, owed before the first release;
  - the event baseline's forward read of SER, Syslog and health envelopes;
  - a node-defined `collection.run` detail key;
  - a refused record that is never judged again.
