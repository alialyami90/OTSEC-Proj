## 1. What 0.6 changes, and nothing else

- **The identifier** becomes `otsec.event/0.6`, and `self` in `contracts/event/validate.go` moves to minor 6. As in 0.4 and 0.5, `Identifier` is one constant, so every event the node writes is stamped 0.6.
- **C4-0.6-1** adds the health type `detector.observation-refused` (§2.1).
- **C4-0.6-2** adds the health type `detector.baseline-refused` (§2.2).
- **C4-0.6-3** states that a `network-observation` or `collection.run` event of a later C4 minor is refused at judging, not at decoding (§3.1).
- **Beside it, C13's text** declares the stored observation strict (§3.2). That changes what a reader does, not what any writer emits, so C13 stays at minor 0.3 (C13 note, §4: "C13 text ... before the next C13 minor"). `contracts/netobs` also exports the reader's own C13 identifier as `SelfIdentifier()` (`self.String()`), which the counts event's `netobs` detail carries (§2.1). `netobs.Identifier` is the 0.1 channel's identifier and does not track `self`, so it cannot serve.

**Unchanged:** every envelope field, every closed set, `event.Decode`, every other health type and its details, `sensor.counters` (C4-0.4-1 to C4-0.5-3), and C6. In particular, no field or flag of a `network-observation`, `collection.run`, SER or Syslog envelope changes. That is the statement C4 (b)'s guard asks of any C4 minor approved before (b) merges (C4 note, §2 (b), "Why C4 0.4 and 0.5 sit below the floor"). For 0.6, "no field" is tested once the code lands, by E6-4 (c)'s head leg; "no flag" stays `desk`, since no strict decode sees an added value of an open set; for 0.4 and 0.5 both stay `desk` (§7).

## 2. The two health types

Both types are platform events (`origin: platform`, `kind: telemetry-health`). The node writes both on the health stream through `sensorHealth`. Both are open-set additions to `Health.Type`, which "later minors may add" (`event.go`). Each also gets its own detail check in `Event.validate`, beside `checkSensorCounters`, so a malformed event is refused at commit like a malformed `sensor.counters`.

**Rules for both types:**

- **New in 0.6.** An event of either type stamped 0.5 or earlier is refused (`forbidden`, `health.type`: "new in otsec.event/0.6"), as `sensor.counters` is below 0.3. No build writes either type before 0.6. A type written before C4 defines it would be an unshared representation (D5's note, §7), and under this gating its events would then also be refused by a 0.6 reader.
- **Closed at the event's own minor, open for a later one.** For an event stamped at or below the reader's minor, a detail key, `reason.<r>` name or `cause` value that this section does not define is refused (`enum`, "not a detail of `<type>` in `<schema>`"). For an event stamped above the reader's minor, it is accepted, and the forms of the keys this section defines are still checked. This follows `checkSensorCounters`'s `later` branch.
- **Relations are checked over present, well-formed keys only**, as `checkSensorCounters` does. A missing key is refused as `missing` and a malformed one under its own code, and a relation that names either is not checked, so each refusal has one code. For example, an event with no `count` is refused as `missing` only.
- **Values.** A "count" below is a decimal from 1 to 2^64 − 1 with no leading zero (`^[1-9][0-9]{0,19}$`, then parsed as a `uint64`), the same form as `runs_folded` (C4-0.5-1). `0`, a leading zero, a sign and a value above 2^64 − 1 are refused (`enum`).
- **No record text.** Every value is a count, a node-held name, a time the node wrote, a hash, or a parsed identifier, so no value can carry record or document text. A value can contain the bytes `"collection.run"` (`stream` is a C4 stream token, and `Stream.Valid` accepts `collection.run`; D6's N4), so `newSessions`'s byte filter passes such an event on. That does no harm: once `event.Decode` succeeds, `runSessionOf` checks the type first on every build, and §3.1 keeps that check first on that path.

### 2.1 C4-0.6-1. `detector.observation-refused`

This event carries the durable counts of stored observations that the network detector refused to judge, by reason, since `since`. It is D5's design, option B of section 2.4: written when the counts have changed since the last counts event, or a start has set or widened `unsure` (§4, "The durable mark"), before the detector checkpoint that follows (D5's section 5). An event owed for `unsure` is written at the first checkpoint whose `Through` is at or above U, and no checkpoint is stored before it, as for any owed event (D1's 7054968770 ruling 1). It is not written at every checkpoint: after a crash between an event and its checkpoint, the replay refuses records at or below the old event's `through` again without counting them, and an event written then would carry a `last_seq` above its own `through` (D5's 7053649155, on §8 item 3).

| Detail | Required | Form |
| --- | --- | --- |
| `stream` | yes | the observation stream it counts, a C4 stream token (`Stream.Valid`) |
| `since` | yes | when these counts began, RFC 3339 as `time.RFC3339Nano` parses it, as in `intake.drop-counted` (`countDetails`). Otherwise refused (`time-format`) |
| `through` | yes | a count: the `Through` of the checkpoint that this event precedes |
| `netobs` | yes | the writer's C13 identifier, `netobs.SelfIdentifier()` at the write: a string that `version.Parse` reads with the name `netobs`. Otherwise refused (`enum`) |
| `unsure` | no | the seq range whose refusals the counts may hold wrongly, as two counts `<a>-<b>` joined by one `-`, with `<a>` ≤ `<b>` ≤ `through`. Present exactly while the counts include such a range (§4, "The durable mark"). Otherwise refused (`enum`) |
| `count` | yes | a count: the sum of every `reason.<r>` in the event |
| `reason.<r>` | at least one | a count: the records refused for reason `<r>` since `since`. Present only when above 0 |
| `first_seq.<r>`, `last_seq.<r>` | exactly when `reason.<r>` is | counts: the lowest and highest seq refused for `<r>` since `since` |

- **The closed set of `<r>`:** `later-minor`, `malformed`, `detector-refused`. These are D5's three reasons, section 2.1.
- **`netobs`** lets the start name a change of C13 minor at the same C4 minor as the cause of a mark (§4, "What the start marks"). C13 0.3 came without a C4 minor (D4-102), so the event's C4 `schema` alone would miss such a change. It names the cause only and does not set the mark (D1's 7054268705, ruling 1). It goes in at 0.6 because the detail set is closed at the event's own minor, and a key added later would need another C4 minor. `contracts/event` checks only the form: it does not import `contracts/netobs`, since `netobs` imports `event`.
- **Relations checked** (each refused as `enum` and naming its detail):
  - `count` equals the sum of the `reason.*` values, and that sum fits in a `uint64` (it does not wrap);
  - for each `<r>`, `first_seq.<r>` ≤ `last_seq.<r>` ≤ `through`, compared as numbers;
  - in `unsure`, `<a>` ≤ `<b>` ≤ `through`, compared as numbers.

  Each holds by D5's construction, provided the writer follows the write rule above: `Detector.Observe` takes a refused record's seq into `Through`, and a counted refusal has a seq above the restored event's `through`. So a failure here is a writer defect. It shows as a refused commit, which D5's design already handles as an owed event: the checkpoint waits, then the alarm `network-refused-counts-unwritten`. Each relation has a case in E6-1 that kills its mutant (D1's 7011692095 item 3; ruling 6).
- **A later minor's `reason.<r>`.** On an event stamped above the reader's minor, an unknown `reason.<r>` is accepted, summed into `count`, and paired with its `first_seq.<r>` and `last_seq.<r>`. So every later minor keeps `count` as the sum of all `reason.*` keys, and keeps each reason's seq pair. A later minor that needs otherwise needs a new type.
- **A later minor's doubt.** Every later minor keeps all of the counts' doubt in `unsure`, as one range of this form, so a 0.6 reader of a later minor's event, which accepts unknown keys (E6-3), misses none of it. A later minor that needs another form needs a new type (D3's N9).
- **Not checked:** that `last_seq.<r>` − `first_seq.<r>` + 1 ≥ `reason.<r>`. D5's section 8 names the build-change cases in which a count can be wrong; §4 marks those with U > T. Refusing such an event would turn a miscount into an unwritten one. Whether the counts are true rests on the writer and on D5's T5 and T6.
- **`unsure`'s `<b>` ≤ `through`** holds because the range is T + 1 to U, from an event that the running build found at its start (§4), and its first counts event is written at a checkpoint whose `Through` is at or above U: an event owed for the range alone waits for such a checkpoint (above), and a counted refusal has a seq above U (D5's seq rule, section 2.4), so a quiet replay gives exactly U. A range that is carried forward keeps its bounds, and `through` only grows.
- **Its size.** At the event's own minor the closed set allows at most 15 details (six keys and three per reason). That is a consequence of the closed set, not a check, so a later minor's event with more keys is not refused for its count. D5's T10 pins the rendered size against a default Syslog target's 2,048 octets. D6's probe rendered the 14-detail form of `a0733336` (with `netobs`, without `unsure`), with the node ID at 63 characters and the seq and every count at 2^64 − 1, in 1,108 octets at C4 0.3, 0.4 and 0.5, within T10's three quarters, 1,536 (`desk`, probe, 7054258521). D6's later probe rendered the 15-detail form, with `unsure` at both ends 2^64 − 1 and `since` with nanoseconds and a `+14:00` offset, in 1,146 octets on a `tls` `best-effort` target of 2,048 octets with the summary kept; it decodes at C4 0.3, 0.4 and 0.5 and re-encodes to equal JSON (`desk`, probe, 7054960340). D5's T10 pins it in code.

### 2.2 C4-0.6-2. `detector.baseline-refused`

This event records that the approved network baseline was refused and the detector is off. It is D5's section 3.1: written once per down stretch.

| Detail | Required | Form |
| --- | --- | --- |
| `hash` | yes | `sha256:` and 64 lowercase hex digits: the refused document's `netobs.Digest` |
| `schema` | yes | `unreadable`, or a string that `version.Parse` reads with the name `netbaseline` |
| `cause` | yes | the closed set `later-minor`, `not-canonical`, `malformed` (D5's section 3.1) |

- **A relation, checked:** `cause: later-minor` with `schema: unreadable` is refused (`enum`), because a later minor is known only from a stamp that parsed.
- **Not checked by C4:** whether the stamp is above `baselineSelf`. That the cause is right is `NewDetector`'s classification (D4's) and D5's T8.
- `schema`'s form is the contract check behind D5's rule that a value from a refused document is shown "only when it parses". A value that does not parse cannot be committed in this event.

### 2.3 The writer's rules (D5's, checked by D5's tests)

- **Built when written.** A counts event or a baseline event that is owed, because its write failed or the ceiling or its budget holds it, is kept as counts or as the alarm's state, in memory only. It is built and stamped when it is written, and never kept as built bytes. Nothing is owed across a restart: the owed state lives in memory, and a restart drops it (D5's section 2.4, its stated limit). An event owed for `unsure` is owed again by the next start, which finds U > T again because no checkpoint passed it (§4). That is the condition under which C4 0.4 and every later minor need no floor: no pending C4 event outlives the process that built it (`docs/release.md` §7.2, the C4 0.4 row). E6-16 tests it in two legs.
- The budgets (4 an hour for the counts event, the pool for the baseline event), the cadence, the start's scan and the `since` and `through` rules are D5's note, unchanged, with §2.1's write rule.

## 3. What a 0.6 reader refuses on the network path

### 3.1 C4-0.6-3. A later C4 minor's `network-observation` and `collection.run`

This is the text of C4's (b) as approved, in contract form.

- **`event.Decode` is unchanged.** It reads a later 0.x minor forward with `strictjson.Forward` and then validates it. SER, Syslog, `sensor.counters`, `netobs.alert` and every other health event keep their forward read, as do the two new types. When `Validate` fails, it returns the decoded event together with the error. That covers a later minor, `""`, a string that does not parse and another name, which it reads forward, and another major, which it reads strictly only when its minor is at or below `self`'s, since it compares only the name and the minor with `self` (`got.Name == self.Name && got.Minor <= self.Minor`, as `DecodeStored` does): `otsec.event/1.0` is read strictly and `otsec.event/1.7` forward (D6's probes at `420c98cd`, 7053855789 and 7054258521; D6's N18).
- **The check.** One exported function in `contracts/netobs` takes an event and returns nil or the refusal below. The proposed name is `CheckEventMinor(*event.Event) error`. Under it is an unexported helper that takes the event's `schema` and a reader's C4 minor as arguments. The exported function passes C4's own minor, read from `event.Identifier`, and never C13's `self`.
- **Its callers:**
  - `ObservationFromEvent` (D4): after its `kind` check, and before `DecodeStored`.
  - `observationOf` (D5): on the path where `event.Decode` returns an error and a non-nil event. A later-minor stamp is refused ahead of the `Validate` error. Any other stamp returns the `Validate` error, as on `main`. An error with no event (duplicate key, case variant) stays a decode error.
  - `runSessionOf` (D5), in this order:
    - **When `event.Decode` returns no error:**
      1. `health.type == collection.run`. Any other type is no session, as on `main`.
      2. The stamp check. A later stamp is refused.
      3. The `after_seq` test and the session's fields, as on `main`.
    - **When `event.Decode` returns an error:**
      1. With no event, or with an event whose type is not `collection.run`, the error is returned, as on `main`. There is no "type first" short cut on this path: a later minor that moves or renames `health` fails `Validate`, and its record still contains `"collection.run"`, so it must stay `bad` (D3's B2).
      2. A `collection.run` with a later stamp is refused.
      3. A `collection.run` whose stamp is not later returns its `Validate` error before the `after_seq` test, as on `main`.

    A refusal or an error makes `newSessions` mark the entry `bad`. So on the error path every entry that is `bad` on `main` is still `bad`, and the only change is which error it carries. The other change from `main` is on the no-error path: a later-minor `collection.run` that decodes is `bad`, where `main` builds a session from it. No change from `main` remains for a record that is not a `collection.run` but contains the bytes `"collection.run"` (D5's N1, moot under D1's ruling 2).
- **The refusal.** A `*netobs.Error` with `Code: CodeSchema` and `Field: "schema"`, for which `errors.Is(err, netobs.ErrLaterMinor)` holds. A schema the check cannot read (empty, unparseable, another name, another major) is refused as `CodeSchema` without `ErrLaterMinor`. This fails closed. Which error reaches the node depends on the path:
  - **The envelope path.** For an envelope whose C4 stamp the check cannot read, `observationOf` returns the `Validate` error that `event.Decode` returned ("Any other stamp returns the `Validate` error", above), so the check's own `CodeSchema` refusal does not reach the node there. The record is `malformed` because a `Validate` error is returned (D6's probe: `otsec.event/1.0` gives `*event.Error` codes `schema`, `forbidden`, `forbidden`, and no `*netobs.Error`, 7054258521). E6-13's fourth leg is that case.
  - **The body path.** For a current-C4 envelope whose body is stamped with another C13 major, or with a stamp that does not parse, the first error is a `*netobs.Error` with `CodeSchema` from `storedSchema`, without `ErrLaterMinor` (D6's probe, 7054258521). There the node's rule decides: it classifies a refusal as `later-minor` by `errors.Is(err, netobs.ErrLaterMinor)` and never by `Code == CodeSchema`, so the record is `malformed`. E6-13's fifth leg tests that rule.
- **A refused observation is nil.** When `DecodeStored` or `ObservationFromEvent` returns an error for which `errors.Is(err, ErrLaterMinor)` holds, the observation it returns is nil, so no later caller (the learner, the link) can use a body whose later keys the forward read dropped (D3's N2). On `main`, `DecodeStored` returns `&o` beside `validateStored`'s error and `ObservationFromEvent` returns `o, err`; for a later-minor refusal both return nil. E6-6 and E6-12 assert it.
- **The `Field` split** (D4's F1 on #766). `ObservationFromEvent` prefixes each `Field` that `DecodeStored` returns with `netobs.`, so the C13 stamp reads `netobs.schema` and the C4 stamp `schema`. A later-minor refusal of either kind is returned alone, never inside an `errors.Join`. That way the error the node matches with `errors.Is(ErrLaterMinor)` is the one whose `Field` it reads. `DecodeStored`'s own whole-body `Field`, `netobs` (its `CodeRange` and `CodeDecode` errors), stays `netobs` and is not doubled (§8 item 2).

**The node's handling of a refused `collection.run`** (D1's ruling 1; D5's option (b) in 7053649155). It is not counted in `detector.observation-refused`, which counts observation-stream records only: its `through` is an observation-stream seq, and a session's health-stream seq would break §2.1's relations (D3's B1). Instead:

- **Its own alarm, `network-session-refused`**, raised once per node process run, at the first `collection.run` refused under `ErrLaterMinor`. It is a separate alarm and not a fourth reason of `network-observation-refused`, so that `observations_refused_by` and the counts event stay counts of observations. Its name and text are as D5 confirmed them (7054038547, with "health-stream seq", since the observation alarm's seqs are observation-stream seqs), with D3's N8 clause: "a `collection.run` was written by a later build (a C4 minor above this build's `event.Identifier`), so this build refused it at judging: its session was not handed to the detector, which may then report that run's flows as unexplained, and `own-session-unseen` does not check that run. It is counted in status (`runs_session_missing`), in memory only. First at health-stream seq `<n>`. Remedy: move this node forward to a build that reads it; records already passed are not judged again." Like D5's other refusal alarms it is the node's own, so C5 does not change.
- **Its count** is the in-memory `runs_session_missing` (`intakeRecords.missing`), as for every `bad` entry on `main`, and the detector's `session-missing`. The counts event does not take sessions.
- **A durable session count** is D5's open item, which D1 records in D4-121. That meets the C4 note's condition 1 for `collection.run` ("or D1 records it as an open item").

### 3.2 C13's text beside it (no C13 minor)

This is the text of C13's (b) as approved, condition 2.

- **The stored observation is strict.** `DecodeStored` refuses a stored observation whose `schema` is a later C13 minor than the reader's `self`. The refusal is in `validateStored`, after `storedSchema`, on the stored observation's path only. It is `CodeSchema` with `ErrLaterMinor`, and the observation returned is nil (§3.1). `DecodeStored`'s first decode stays `strictjson.Forward`, so a later record whose forward decode succeeds is refused as `schema` whether or not it carries an unknown key. One whose forward decode fails (a known key with another JSON type) is refused as `decode` first (§7).
- **What it supersedes.** CH-35's "forward for a later one" no longer applies to the stored observation. It still applies to alerts (bridge items 3 and 4) and to baselines, where `DecodeBaseline` is unchanged and `IsCanonical` already refuses.

## 4. Earlier readers and rollback

| | Reads a 0.6 `detector.*` event | Reads any other 0.6 event |
| --- | --- | --- |
| C4 0.3 to 0.5 code | Yes. `Health.Type` is open, and these readers have no detail rule for either type, so the event passes `Validate` read forward and re-encodes with no key lost (D6's probes at 0.3, 0.4 and 0.5: the 13-detail form in 7053855789, the 14-detail form, with `netobs`, in 7054258521, and the 15-detail form, with `unsure`, in 7054960340; E6-4's counts fixture carries it). Several readers read it, and none acts on it: `eventFeed.takeHealth` returns at its `asset_id` lookup, which neither type carries; `lastDropCounts` pins `intake.drop-counted`; `runSessionOf` returns no session for any other type once `Decode` succeeds; and the forwarder's `Render` renders it | Yes, read forward. Nothing is dropped, because 0.6 adds no envelope key or flag value (§1). So a 0.5 build's forward read of a 0.6 `network-observation` or `collection.run` judges what the 0.6 build would judge. For an added envelope key, E6-4 (c)'s head leg tests this for 0.6 once the code lands; for an added value of an open set it stays `desk` (§1) |
| C4 0.6 code | Yes, with §2 checked | Yes. Network events of 0.6 or earlier are judged, and later ones are refused (§3) |

- **No reader floor from 0.6's types.** Every earlier reader accepts every 0.6 event (E6-4), and no earlier build acts on a `detector.*` event.
- **Receivers first** (C6, `contracts/syslog/doc.go`, "Versions"). Every forwarded event's `ev` becomes `otsec.event/0.6` at once, as with 0.4 and 0.5. `Render` renders the new details as `hd` parameters, and C6 does not change.
- **The C4 0.4 condition holds** if the writer rule of §2.3 holds: no pending C4 event outlives the process that built it. A 0.5 build therefore reads every stored 0.6 event, and refuses only a pending one.
- **What the start marks as not exact** (D1's ruling 4 (a), narrowed by D1's 7054268705 ruling 1; D5 owes the tests and the code, in its D4-120 item 3.1 change). At start, D5's scan finds the newest counts event, with its `through` U, and the detector restores its checkpoint, with its `Through` T. The start marks the counts as not exact (`observations_refused_exact: false`) only when **U > T**. The replay then judges T + 1 to U again, and D5's seq rule holds over that range only if the replay refuses the same records the event counted (D5's note §8). `observations_refused_unsure` is the range T + 1 to U, in `unsure`'s form `<a>-<b>` (§2.1).
  - **The cause.** U > T means a crash or a failed checkpoint came between the event and its checkpoint (D5's note §2.4, "A replay does not count twice"). The build may also have changed. The start cannot tell the two apart, so it marks both. A crash on the same build is marked although D5's seq rule keeps its count exact: D5's T5 (c) then asserts the mark. That errs toward caution (P5).
  - **What the writer's minors do.** They only name the cause in the status text: "a build change" when the event's envelope `schema` is not `event.Identifier` or its `netobs` detail is not `netobs.SelfIdentifier()`, and "a crash or a build change" when both are equal. They do not set the mark.
  - **Not "a lower bound".** With U > T and a forward build, the count can be too high (D5's note §8), so status says "not exact", not "a lower bound".
  - **U ≤ T leaves the counts exact** when the newest counts event carries no `unsure` (D6's N21), within D5's limits, whatever the minors. Nothing the event counted is replayed, and no refusal lies in (U, T], because a counted refusal makes the counts change and the checkpoint waits for the counts event (D5's note §5), outside the checkpoint stored past `RefusedCountsWait`, whose limit D5's note §2.4 states. So an ordinary upgrade across a C4 or C13 minor after a clean stop is not marked, and nothing shows an empty range: with U = T there is no mark and no `observations_refused_unsure`.
  - **With no restored checkpoint**, the counts begin again (`since` = now, `through` = 0; D5's note §2.4, "A start whose checkpoint did not restore"), so the earlier event's counts are in no count and nothing is marked. D5 confirmed this reading (7054807248).

  D5's tests, each with its control: U > T at equal minors is marked, cause "a crash or a build change"; U > T with each minor changed is marked, cause "a build change"; U = T and U < T, each with each minor changed, are not marked.
- **The durable mark** (D1's 7054268705 ruling 2, option (i); D6's B2, D3's N7). The mark is not kept only in memory and in the status file, where the next counts event and the next start would lose it:
  - **Set** (D1's 7054968770 ruling 1, option (i); D5's B2, D3's B4, D6's B3). The start that finds U > T makes a counts event owed, as a counted refusal does, with the counts unchanged and `unsure` set to the range. The checkpoint waits for it under D5's note §2.4 hold ("no checkpoint passes an unwritten count"): the event is written at the first checkpoint whose `Through` is at or above U, carrying that `Through`, and no checkpoint is stored before it. From then on every counts event the process writes carries `unsure` (§2.1). The status shows the mark at once, before the event is written. No key is added.
  - **No checkpoint between T and U narrows or drops the range.** While the event is owed, a checkpoint attempted between T and U is not stored, so the stored checkpoint stays at T and a crash or a stop before the write leaves U > T with the full range T + 1 to U (D6's B3). The one exception is the forced checkpoint below.
  - **Carried forward.** At every start, when the newest counts event carries `unsure`, the start keeps the mark and the range, whether U > T or not, and every counts event the process writes carries it again. A start that only carries a range owes no event, since the newest event already holds it. The status names such a range as carried from an earlier start. A start or a counts write therefore never shows the counts as exact while they include the range, outside the forced checkpoint below. A crash or a clean stop before the owed event is written leaves the older event as the newest and the stored checkpoint at T, with U > T still, so the next start marks the range again and owes the event again.
  - **Two ranges.** When a start finds U > T while it also carries a range, the carried range widens to the lower of the two starts and the higher of the two ends, which is U, since a carried `<b>` is at most its event's `through`, U. A widening makes a counts event owed, as a set does; a new range inside the carried one changes nothing and owes none. One range keeps the detail at one key; the widened range can hold seqs that were not in doubt, which errs toward caution.
  - **Only this range goes into `unsure`** (D6's N21). D5's note §2.4 also shows a range in status past `RefusedCountsWait`, the refusals counted in memory and not yet in an event. That range is not put in `unsure`: once its event is written, its refusals are counted in it and are not in doubt. When both are live, status's `observations_refused_unsure` shows one range from the lower start to the higher end, `observations_refused_exact` is false, and the status text names both causes.
  - **The forced checkpoint** (D3's B4). An event owed for the range is held by the same budget and ceiling as any counts event, so past `RefusedCountsWait` D5's note §2.4 stores the checkpoint without it, as its sibling limit for counts, and raises `network-refused-counts-unwritten`. For an event owed for the range alone, its text reads "the mark that the counts of refused observations may be wrong for seqs `<a>-<b>` was not written to the health stream within `RefusedCountsWait` (`<cause>`), so the detector's checkpoint was stored without it. Status shows the counts as not exact until it is written. A restart before then shows them as exact, or as not exact only above the stored checkpoint, and this alarm is then the only record of that range." When the event is owed for counts and for the range, the counts form is raised with the wider range. This text is D5's to confirm in its code change. A restart before the write then loses the range, or the part of it at or below the forced checkpoint (§7).
  - **Stop.** The range stops being carried exactly when the counts no longer include it: when the counts begin again under D5's note §2.4 (the newest event not found within the scan or pruned, or a checkpoint that did not restore), with a new `since`. The first counts event under the new `since` carries no `unsure`, and the status shows exact counts again. Nothing else clears it: not a counts write, a restart, an upgrade or a clean stop. The carried range is unchanged, except as widened under "Two ranges", until `since` begins again (D7's N7).
  - **Tests (E6-18, D5's).** Listed in §6.
- **What the start cannot detect** (D1's ruling 4 (c)). Nothing on the store names the build: no code reads `debug.ReadBuildInfo` or a revision, the detector checkpoint carries only its C13 stamp, which 0.5 and 0.6 builds share, and the status file carries `go_version`. So:
  - a build change at the same C4 and C13 minors is marked when U > T, the only case where it matters, and goes unmarked only when U ≤ T, where the counts are exact (above);
  - a rollback from 0.6 to a build below 0.6 and a move forward again (0.6, then 0.5, then 0.6 or a later build) is not seen. A build below 0.6 writes no counts event, so the newest one was written by the first 0.6 run, and the start shows the counts as exact, or as not exact only for a range it carried before, while the rolled-back build's refusals are counted nowhere.

  No heuristic is used for the second: D5's scan of health records for a lower stamp is not adopted (ruling 4 (c)). D4-121 records the case as a risk bounded by AP-10 on the update path (D1's 7054268705 ruling 5).
- **What a rollback from the 0.6 build to a 0.5 build costs.** None of it is a misjudgement:
  - **It can only be a hand install.** Every release carries (b) and the counts writer (D4-120 items 2.2 and 2.6), and AP-10's floor refuses an older build through the update path (D1's ruling 3; D3's B3 (b)). A hand install bypasses AP-10 (`docs/release.md` §7.4) and is a release outside the rollback set (`docs/release.md` §7.3). So a build without the counts writer reaches a node only by a hand install (D7's N6).
  - While rolled back, refusals are back to `main`'s in-memory `observations_refused`, with no alarm and no counts event. A record of a minor that changed the `network-observation` or `collection.run` envelope would be read forward again and misjudged, but no such record exists: a 0.5 build reads every 0.6 record forward with nothing dropped (above), and the floor of §5 keeps a node that ran a build above it out of this rollback.
  - **No trace of the rolled-back build's refusals remains.** `observations_refused` lives in that process's memory and in the status file, which the next build overwrites. Nothing about a refusal reaches the OS log: a build below 0.6 raises no alarm for one (D5's note §1; `docs/release.md` §7.1), and the OS log's other entries on `main`, the store's mode changes (`Status`) and the node's start line (`RunFrom`), do not name refusals. When the node is moved forward again, the start does not see the rolled-back stretch (above).

## 7. Limits

- The validator checks the form of both events, not their truth. That the counts are exact rests on D5's design and tests, within the limits of D5's section 8.
- **What the start marks** (§4): only U > T, as not exact, with the range T + 1 to U, made durable by a counts event the start owes, and carried in every later counts event until the counts begin again.
- **The forced checkpoint drops the mark on a restart** (§4, "The forced checkpoint"; D3's B4). When the event owed for the range is held past `RefusedCountsWait`, the checkpoint is stored without it, as in D5's note §2.4 for counts, and `network-refused-counts-unwritten` names the range in the OS log. A restart before the event is written then shows the counts as exact, or as not exact only above the forced checkpoint, and the alarm is the only record of the range. It is the same class as D5's stated limit for counts (D5's note §2.4 and §8). A same-build crash with U > T is marked although its count is exact. A build change at the same C4 and C13 minors is marked when U > T and unmarked only when U ≤ T, where the counts are exact.
- **The build change the start cannot see** (§4): a rollback below 0.6 with a move forward again. Status then shows the counts as exact, or as not exact only for a range carried from before. It can only follow a hand install, which bypasses AP-10 (`docs/release.md` §7.4): AP-10's floor refuses an older build through the update path only, and every release carries (b) and the counts writer. No trace of the rolled-back build's refusals remains: `observations_refused` is in memory and in the status file, which the next build overwrites, and nothing about a refusal reached the OS log. D4-121 records it as a risk bounded by AP-10 on the update path.
- **A refused `collection.run` is counted in memory only** (`runs_session_missing`), and alarmed once per process run. A durable count is D5's open item in D4-121 (§3.1).
- **A later minor can be refused as `malformed`, not `later-minor`.** A later minor that changes a known key's JSON type fails `strictjson.Forward` (`CodeDecode`, at `netobs` or in `event.Decode`), and a later C4 `kind` fails `ObservationFromEvent`'s `kind` check first. Either is refused and counted as `malformed`, so its alarm lacks the "move this node forward" remedy. It still fails closed.
- The reading that 0.4 and 0.5 leave the two network envelopes unchanged is `desk` (C4 note §1.4). For 0.6, E6-4 (c)'s head leg tests it for envelope keys once the code lands; for added values of an open set it stays `desk`.
- Every residual of the two notes stands:
  - a hand install below the floor;
  - AP-10, owed before the first release;
  - the event baseline's forward read of SER, Syslog and health envelopes;
  - a node-defined `collection.run` detail key;
  - a refused record that is never judged again.
