## 0. The two facts that shape it

- **A network baseline belongs to a sensor, not an asset.** There is one per sensor, on the stream `netbaseline/<sensor>` (#532 §8). Every 0.9 baseline kind is keyed by `asset_id`: the C7 body, the collector's enrolment check and C8's chain check. Kind `network` needs a sensor key instead.
- **The person adds the authorized writers.** The note (§2.3) has the person add writers to the frozen draft in the admin client, and the writers are never learned. So the document the person approves is not the one the node recorded. And `MaxRequestBytes` is 8 KiB, so a site's whole writer list may not fit inside the signed request. (D3's review of the drafts, change 1.)

## 1. C7 0.10 (`otsec.authz/0.10`)

**The kind.** `BaselineNetwork BaselineKind = "network"`.

**`NodeBaselineAckBody` gains two optional fields:**

```go
SensorID    string `json:"sensor_id,omitempty"`    // kind network only
DraftDigest string `json:"draft_digest,omitempty"` // kind network only
```

**`Validate`:**
- **For kinds `configuration` and `event`,** the rules are unchanged: `asset_id` is required, and both new fields are absent.
- **For kind `network`,** all of these must hold:
  - `asset_id` is absent;
  - `sensor_id` is a lowercase UUID;
  - `draft_digest` and `baseline_digest` both match `sha256:<64 hex>`.

  The two digests are equal when the person added no writers.
- **Kind `network` needs a payload stamped 0.10 or later.** It is refused on an earlier one, as `configKindsSince` gates the 0.6 kinds. A 0.9 collector refuses it as an unknown kind value, which fails closed.

**What the signature binds.** `baseline_digest` is the digest of the **accepted document**: the frozen draft with the person's `authorized_writers` filled in, encoded canonically as the note's §1 requires. `draft_digest` is the digest of the frozen draft it was built from. Both are signed, so the person attests to the draft as well as to what they added.

**How the accepted document reaches the node.**
1. The admin client shows the accepted document and writes its exact bytes to the node's admin folder (the file name is D5's, beside `clear-suspension.json`). The file is unsigned, and has no effect without a signature that names its hash (HR-14: the client computes the digest over the bytes it shows).
2. The client sends the signed request. The collector verifies it and numbers its decision.
3. The node adopts the document only when all of the following hold. Otherwise it writes `config.baseline_acknowledged` with outcome `denied` and takes nothing.
   - The collector has accepted the request.
   - `sensor_id` is the sensor in the node's `network_sensor` section.
   - `draft_digest` is the latest `baseline.network` the node recorded for that sensor (§2.1).
   - The file's SHA-256 equals `baseline_digest`, and the file is at most `MaxBaselineBytes`. When the two digests are equal, the node already holds the bytes and needs no file.
   - The file, with `authorized_writers` emptied, is byte for byte the draft. So a person can add writers and change nothing else.

   The node then stores the file as a `baseline.network` record, as accepted, and the detector uses it.

**The collector.**
- The asset check in `pipeline.go` applies to `asset_id`, so for kind `network` there is nothing to check. The collector doesn't know the node's sensors, and the node makes the check after acceptance, as above.
- Signature, permission for the kind, nonce and numbering are unchanged.
- The answer still gives nothing away to a prober: no target is named for an unsigned request, as today.

**Permission.** A key allowed `node.baseline_ack` may now acknowledge a network baseline, and with it the authorized writers. That gives one person both the configuration and the network acknowledgements. A separate kind, say `node.network_baseline_ack`, would let an owner split the two roles. Since `AdminKey.Kinds` already fails closed for new kinds, the cost would be one request kind and a separate path through the collector. **Question 1 for D1:** one kind, or two? I lean to one, because both are security-role acknowledgements of a baseline, and the owner has asked for no split.

**Schema and goldens.** `schema/admin-request.json` (`$id` 0.10) gains the two fields, conditioned on `kind`. The admin-signed goldens are restamped 0.10, and one network-ack golden is added.

## 2. C8 0.12 (`otsec.audit/0.12`)

All of these records are written by the node. **A target can now be a sensor.** `Target` gains `sensor_id` (a lowercase UUID). On the records in this section with kind `network`, the target is `sensor_id`, and `asset_id` is absent. Every other record is unchanged, and its target stays an asset.

### 2.1 `config.baseline_recorded` and `config.baseline_acknowledged` for kind `network`

- **`config.baseline_recorded`** (kind `network`) is written once the learner's frozen draft is stored as `baseline.network`. It carries:
  - `baseline_digest`: the draft;
  - `baseline_version`: n + 1;
  - `previous_digest`: the network baseline recorded before it, if there was one.
- **`config.baseline_acknowledged`** (kind `network`) carries:
  - the existing fields `decision_seq`, `payload_sha256`, `kind` and `baseline_digest` (the accepted document);
  - a new field, `draft_digest`;
  - `previous_digest`: the network baseline acknowledged before it, if there was one.

  These come from the signed body, as for the other kinds. `denied` is written when the node refuses to adopt the document (§1).
- **Chain check** (`VerifyChain`, as 0.8 does for event baselines):
  - a succeeded acknowledgement's `draft_digest` must equal the latest `config.baseline_recorded` of kind `network` for that sensor, as far as the view shows;
  - acknowledgements are tracked per (sensor, kind), so `previous_digest` follows the succession.

### 2.2 `store.retention_moved` (#532 §3)

This is written **before** the retention consumer's cursor commits. If the write fails, the cursor stays where it was, so the node fails closed. The target is the sensor. A new object, `retention`, holds the move and is allowed on this action only:

| Field | What it is |
| --- | --- |
| `stream` | the alert stream, `network-alert/<sensor>` |
| `from_seq`, `to_seq` | the cursor before and after; `to_seq` ≥ `from_seq` |
| `retention_s` | the configured retention |
| `wall_utc` | the wall time used |
| `cutoff_utc` | the cutoff applied |
| `previous_cutoff_utc` | the cutoff of the move before it, or of the persisted one after a start |
| `bound` | `wall`, `monotonic` or `start`: which limit set the cutoff (#532 §3) |

**Chain check.** Within one stream, in chain order:
- each move's `from_seq` equals the previous move's `to_seq`;
- its `previous_cutoff_utc` equals the previous move's `cutoff_utc`;
- `cutoff_utc` is not earlier than `previous_cutoff_utc`;
- `cutoff_utc` is not later than `wall_utc` less `retention_s`.

A view that starts mid-chain accepts its first move as given, as `activeFor` does today. A forward clock step then shows as a move with `bound: monotonic`, next to the step's `clock.change`.

### 2.3 `config.learner_retired` (#532 §8)

This is written **before** the learner leaves the consumer set. If the write fails, the learner stays in the set: it keeps holding back pruning, and status shows it. The target is the sensor. The `config` object carries:
- `kind`: `network`;
- `baseline_version`: the learning run's version;
- `cursor_seq`: the learner's last confirmed seq on the observation stream;
- `reason_code`: `acknowledged` or `stopped`.

With `acknowledged`, it also carries `baseline_digest`, which names the acknowledgement.

**Chain check.**
- An `acknowledged` retirement follows a succeeded `config.baseline_acknowledged` of kind `network` for the same sensor, with the same `baseline_digest`.
- A learning run is retired at most once, by sensor and `baseline_version`.

### 2.4 Gates and readers

- **Gates.** The three uses of kind `network`, `store.retention_moved`, `config.learner_retired`, `Target.sensor_id` and `draft_digest` all need a record stamped 0.12 or later. `actionSince` and the config validators refuse them on an earlier record.
- **Readers.** An older reader maps an unknown action to `unrecognized`, as today. The node writes none of these until its readers and the chain verifier are at 0.12. Readers are upgraded before writers (#532 §7).
- **Schema.** `schema/record.json` (`$id` 0.12) gains the two actions, `retention`, `Target.sensor_id`, `draft_digest`, and kind `network` in the `kind` enum.

## 3. Tests

These are written with D6's contract tests.

**`contracts/authz`:**
- A network acknowledgement passes with `sensor_id` and both digests.
- A network acknowledgement is refused in each of these cases:
  - it has an `asset_id`;
  - it has no `sensor_id`, or an uppercase one;
  - a digest is malformed;
  - it is stamped 0.9.
- A configuration or event acknowledgement with `sensor_id` or `draft_digest` is refused.
- The 0.9 goldens still verify.

**`contracts/audit`:**
- A valid record of each new action and kind passes.
- Each record is refused when stamped 0.11.
- A `retention` object on any other action is refused.
- A network record with `asset_id` is refused.
- `VerifyChain` breaks on each of these:
  - an acknowledgement whose draft is not the latest recorded;
  - a gap or overlap between two retention moves;
  - a cutoff that goes backwards, or is later than the wall time less the retention;
  - a retirement with no matching acknowledgement;
  - a second retirement of one run.

**Collector:**
- A network acknowledgement is accepted without an asset check, and numbered.
- A 0.9-stamped one is refused.

**Node** (in the node PR):
- An accepted document whose file hash differs is denied.
- An accepted document whose `draft_digest` is not the latest draft is denied.
- An accepted document that differs from the draft outside `authorized_writers` is denied.
- An accepted document for another sensor is denied.
- A file in the admin folder that no signature names is never read as a baseline.
- The retention move: the audit write comes first, and a failure keeps the cursor.
- The learner's retirement: the audit write comes first, and a failure keeps the learner in the consumer set.
