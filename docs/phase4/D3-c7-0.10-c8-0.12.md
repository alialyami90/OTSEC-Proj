## 0. The two facts that shape it

- **A network baseline belongs to a sensor, not an asset.** There is one per sensor, on the stream `netbaseline/<sensor>` (#532 §8). Every 0.9 baseline kind is keyed by `asset_id`: the C7 body, the collector's enrolment check and C8's chain check. Kind `network` needs a sensor key instead.
- **The person adds the authorized writers.** The note (§2.3) has the person add writers to the frozen draft in the admin client, and the writers are never learned. So the document the person approves is not the one the node recorded. And `MaxRequestBytes` is 8 KiB, so a site's whole writer list may not fit inside the signed request. (D3's review of the drafts, change 1.)

## 1. C7 0.10 (`otsec.authz/0.10`)

**A new admin-signed kind, `node.network_baseline_ack`** (D1, for D4-68). Through `authorized_writers`, a network acknowledgement grants which hosts may write to relays without an alert. That is a different grant from accepting a configuration or event baseline, so it has its own kind (P4, least privilege).

- **Granting it.** `AdminKey.Kinds` fails closed, so a key signs the new kind only when its list names it. A key pinned without a list, or with a list that names only `node.baseline_ack`, is refused with `AdminCheckAuthority`, and so is the reverse. D1 also asks for an audit record of the grant. Today a key's kinds are pinned in the collector's configuration out of band, and nothing in the chain records them. D1 ruled that recording the grant at first use is enough, with an ordering rule (§1.1, §2.4).
- **Gate.** `kindSince` puts it at minor 10. A request stamped earlier can't ask for it, and a 0.9 collector refuses it as an unknown kind. Both fail closed.
- **The baseline kind.** `BaselineNetwork BaselineKind = "network"`, used by C8 (§2) and by the node. `node.baseline_ack` doesn't take it: `NodeBaselineAckBody.Validate` keeps accepting `configuration` and `event` only, so a network baseline can be acknowledged only through the new kind.

### 1.1 The grant, recorded at first use (D1, §4 Q2)

**`AdminAccepted` gains `keys_digest`** (since 0.10). It is set on every accepted reply to an admin-signed request stamped 0.10 or later. The digest is `sha256:` followed by the SHA-256 of the collector's pinned administrator keys, one line per key, sorted by key ID. Each line holds the key ID, the principal, the status and the sorted kinds, separated by spaces, with the kinds joined by commas. A key pinned without a list is written with the 0.5 default kinds it actually has. **`AdminAccepted` also gains `keys`**: the same list as objects, so the node can record it. Its size is bounded by the number of pinned keys, which the collector already limits.

**The ordering rule.** When a reply's `keys_digest` differs from the last one the node recorded, the node first writes `policy.apply` naming the new digest and the keys (§2.4). Only after that write may it apply the reply's decision. If the write fails, the decision isn't applied, and the request is answered as on any audit failure (fail closed). A grant of `node.network_baseline_ack` therefore always appears in the chain before the first acknowledgement it allows. The node takes the digest and the keys only from the collector's authenticated reply, never from its own disk or configuration (D6).

### 1.2 The body

```go
// NodeNetworkBaselineAckBody (since 0.10) accepts one sensor's network
// baseline, with the authorized writers the person added (C13 §8).
type NodeNetworkBaselineAckBody struct {
	SensorID       string `json:"sensor_id"`       // lowercase UUID, the node's network_sensor
	DraftDigest    string `json:"draft_digest"`    // the frozen draft the node recorded
	BaselineDigest string `json:"baseline_digest"` // the accepted document
}
```

`Validate` requires a lowercase UUID and two digests of the form `sha256:<64 hex>`. The two digests are equal when the person added no writers.

**What the signature binds.** `baseline_digest` is the digest of the **accepted document**: the frozen draft with the person's `authorized_writers` filled in, encoded canonically as the note's §1 requires. `draft_digest` is the frozen draft it was built from. Both are signed, so the person attests to the draft as well as to what they added.

**How the accepted document reaches the node.**
1. The admin client shows the accepted document and writes its exact bytes to the node's admin folder, as `network-baseline-<sensor_id>.json` (D5), beside `clear-suspension.json`. The file is unsigned and has no effect without a signature that names its hash. The client computes the digest over the bytes it shows (HR-14).
2. The client sends the signed request. The collector verifies it and numbers its decision.
3. The node adopts the document only when all of the following hold. Otherwise it writes `config.baseline_acknowledged` with outcome `denied` and takes nothing.
   - The collector has accepted the request.
   - `sensor_id` is the sensor in the node's `network_sensor` section.
   - `draft_digest` is the latest `baseline.network` the node recorded for that sensor (§2.1).
   - The file's SHA-256 equals `baseline_digest`, and the file is at most `MaxBaselineBytes`. The node reads the file once, and hashes, compares and stores those same bytes (D6, T3). When the two digests are equal, the node already holds the bytes and ignores any file in the folder.
   - The file is canonical (D4). Decoded strictly as the baseline document and encoded again in C13 §8's canonical encoding, it gives the same bytes. It also passes the document's own checks, so each writer is a (client, server, class) entry with class `write` or `control`. A document re-encoded with other whitespace or key order fails here and is denied, even though its hash is the one signed.
   - The file, decoded, with `authorized_writers` set to `[]` and encoded canonically again, is byte for byte the draft. A person can therefore add writers and change nothing else.

   The node then stores the file as a `baseline.network` record, as accepted, and the detector uses it. If the configuration ceiling refuses the store (#532 §8), the acknowledgement is written as `denied` with a storage reason, and `network-baseline-no-room` is raised (D5).

**The collector.**
- It has no asset to check for this kind. The collector doesn't know the node's sensors, and the node checks the sensor after acceptance, as above.
- Signature, the kind's permission, the nonce and the numbering are as for every admin kind.
- The answer gives nothing away to a prober: no target is named for an unsigned request, as today.

**Schema and goldens.** `schema/admin-request.json` (`$id` 0.10) gains the kind and its body. The admin-signed goldens are restamped 0.10, and one network-ack golden is added.

## 2. C8 0.12 (`otsec.audit/0.12`)

All of these records are written by the node. **A target can now be a sensor.** `Target` gains `sensor_id` (a lowercase UUID). On the records in this section with kind `network`, the target is `sensor_id`, and `asset_id` is absent. Every other record is unchanged, and its target stays an asset.

### 2.1 `config.baseline_recorded` and `config.baseline_acknowledged` for kind `network`

- **`config.baseline_recorded`** (kind `network`) is written once the learner's frozen draft is stored as `baseline.network`. It carries:
  - `baseline_digest`: the draft;
  - `baseline_version`: n + 1;
  - `previous_digest`: the network baseline recorded before it, if there was one.
- **Only the draft has a `config.baseline_recorded`** (D4). The accepted document's record is the acknowledgement that names its digest, so two `baseline.network` documents per learning run, the draft and the accepted one, are normal.
- **`config.baseline_acknowledged`** (kind `network`) carries:
  - the existing fields `decision_seq`, `payload_sha256`, `kind` and `baseline_digest` (the accepted document);
  - a new field, `draft_digest`;
  - `previous_digest`: the network baseline acknowledged before it, if there was one.

  These come from the signed body, as for the other kinds. `denied` is written when the node refuses to adopt the document (§1).
- **Chain check** (`VerifyChain`, as 0.8 does for event baselines):
  - a succeeded acknowledgement's `draft_digest` must equal the latest `config.baseline_recorded` of kind `network` for that sensor, as far as the view shows;
  - acknowledgements are tracked per (sensor, kind), so `previous_digest` follows the succession.

### 2.2 `store.retention_moved` (#532 §3)

This is written **before** the retention consumer's cursor commits. If the write fails, the cursor stays where it was, so the node fails closed. The target is the sensor.

**The first record is written when the consumer is created** (D5). It has `bound: created`, `from_seq` = `to_seq` = the consumer's starting cursor, and no `previous_cutoff_utc`. Its `cutoff_utc` is the commit time of the oldest stored alert, or wall time less the retention when the stream is empty. Nothing is pruned at creation, so a clock stepped before the consumer's first run can't prune anything. Every later move is bounded from a recorded cutoff. A consumer created again later, after a forward target is removed, starts again with another `created` record.

**After that, a move is written only when it advances** (D6, T1). At each hourly tick the node computes the cutoff, as #532 §3 describes. It makes and records a move only when the new cutoff is later than the previous recorded one and the move passes at least one alert (`to_seq` > `from_seq`). Otherwise it writes nothing and persists nothing. That covers every tick while a backward clock step stalls the cutoff. "The previous move" in #532 §3's monotonic bound is therefore the previous recorded move. A new object, `retention`, holds the move and is allowed on this action only:

| Field | What it is |
| --- | --- |
| `stream` | the alert stream, `network-alert/<sensor>` |
| `from_seq`, `to_seq` | the cursor before and after; `to_seq` > `from_seq`, except on `created`, where they are equal |
| `retention_s` | the configured retention |
| `wall_utc` | the wall time used |
| `cutoff_utc` | the cutoff applied |
| `previous_cutoff_utc` | the cutoff of the recorded move before it; absent on `created` |
| `bound` | `created`, or which limit set the cutoff: `wall`, `monotonic`, or `start` (the one-hour limit after a node start, #532 §3) |

**Chain check.** Each `created` record starts a new chain for its stream (D6). A consumer created again after a forward target is removed starts at a `from_seq` ahead of the last move, because the target consumed alerts in between. Within a chain, in chain order:
- each move's `from_seq` equals the previous record's `to_seq`;
- its `previous_cutoff_utc` equals the previous record's `cutoff_utc`;
- its `cutoff_utc` is later than `previous_cutoff_utc`;
- its `cutoff_utc` is not later than `wall_utc` less `retention_s`.

The wall bound applies to moves only, not to `created` (D6). A `created` cutoff is the oldest stored alert's commit time, which can be younger than the retention. Because no move is written while the cutoff is stalled, an honest move always satisfies the last two rules.

A view that starts mid-chain accepts its first move as given, as `activeFor` does today. A forward clock step then shows as a move with `bound: monotonic`, next to the step's `clock.change`.

**What the chain can't prove** (D6, T2). The record carries no monotonic time, so `VerifyChain` can't detect an early prune under a forward step, and `bound` is the node's own word. A passing chain shows that the moves are contiguous and never go backwards. It does not prove the monotonic bound. The evidence for the bound is #532 §6's node test, the forward step with its `clock.change` record.

### 2.3 `config.learner_retired` (#532 §8)

This is written **before** the learner leaves the consumer set. If the write fails, the learner stays in the set: it keeps holding back pruning, and status shows it. The target is the sensor. The `config` object carries:
- `kind`: `network`;
- `baseline_version`: the learning run's version;
- `cursor_seq`: the learner's last confirmed seq on the observation stream;
- `reason_code`: `acknowledged` or `stopped`.

With `acknowledged`, it also carries `baseline_digest`, which names the acknowledgement.

**Chain check.**
- An `acknowledged` retirement follows a succeeded `config.baseline_acknowledged` of kind `network` for the same sensor, with the same `baseline_digest`.
- A learning run is retired at most once, by sensor and `baseline_version`.

### 2.4 `policy.apply` for the administrator keys (D1, §1.1)

This is written by the node with `reason_code` `admin_keys`, before it applies any decision from a reply whose `keys_digest` is new. A new object, `admin_keys`, is allowed on that reason only:
- `digest`: the reply's `keys_digest`;
- `previous_digest`: absent the first time;
- `keys`: a list of key ID, principal, status and kinds, one entry per pinned key.

**The acceptance carries its digest** (D6). C8's `Admin` (the `verified` block on an allowed `collector.request`) gains `keys_digest` since 0.12. It is set from the reply's `keys_digest`, and it is required on an allowed admin `collector.request` stamped 0.12 or later, so `Validate` refuses a 0.12 acceptance without it (D6). The chain then shows which key set each decision was made under.

**Chain check.** These are the rules:
- An accepted admin decision stamped 0.12 or later is applied (a `config.*` or other record naming its `decision_seq`) only after a `policy.apply` with `admin_keys` whose `digest` equals its acceptance's `verified.keys_digest`, and that record is the latest `admin_keys` record before the decision.
- The verified key's kind is in that record's list for the key.
- Each record's `previous_digest` is the digest of the one before it.

A view that starts mid-chain accepts its first record as given.

### 2.5 Gates and readers

- **Gates.** The three uses of kind `network`, `store.retention_moved`, `config.learner_retired`, `Target.sensor_id`, `draft_digest`, `admin_keys` and `verified.keys_digest` all need a record stamped 0.12 or later. `actionSince` and the config validators refuse them on an earlier record.
- **Readers.** An older reader maps an unknown action to `unrecognized`, as today. The node writes none of these until its readers and the chain verifier are at 0.12. Readers are upgraded before writers (#532 §7).
- **Schema.** `schema/record.json` (`$id` 0.12) gains the two actions, `retention`, `admin_keys`, `verified.keys_digest`, `Target.sensor_id`, `draft_digest`, and kind `network` in the `kind` enum. In C7, `schema/collector-reply.json` (`$id` 0.10) gains `admin.keys_digest` and `admin.keys`.

## 3. Tests

These are written with D6's contract tests.

**`contracts/authz`:**
- A `node.network_baseline_ack` passes with `sensor_id` and both digests, and with the two digests equal.
- It is refused in each of these cases:
  - `sensor_id` is absent or uppercase;
  - `draft_digest` or `baseline_digest` is absent, or malformed (D6, T5);
  - an unknown field is present, such as `asset_id`;
  - it is stamped 0.9.
- A key that holds only `node.baseline_ack` is refused for the new kind with `AdminCheckAuthority`, and a key that holds only the new kind is refused for `node.baseline_ack` (D1). A key pinned without a list is refused for the new kind.
- `node.baseline_ack` with kind `network` is refused.
- The 0.9 goldens still verify.

**`contracts/audit`:**
- A valid record of each new action and kind passes.
- Each record is refused when stamped 0.11.
- A `retention` object on any other action is refused.
- `sensor_id` on any action other than the network records is refused (D6, T4).
- A network record with both `asset_id` and `sensor_id`, or with neither, is refused.
- An allowed admin `collector.request` stamped 0.12 without `verified.keys_digest` is refused (D6).
- A retention record with `to_seq` = `from_seq` is refused unless its `bound` is `created`. A `created` record with `previous_cutoff_utc` is refused.
- Goldens (D6): a `created` record whose cutoff is the commit time of an alert younger than the retention verifies, and two chains in one stream, each begun by its own `created`, verify.
- `VerifyChain` breaks on each of these:
  - an acknowledgement whose draft is not the latest recorded;
  - a gap or overlap between two retention moves;
  - a move with no `created` record before it, in a view that holds the stream's start;
  - a move whose `from_seq` doesn't follow the latest `created` record's chain;
  - a cutoff that doesn't advance, or is later than the wall time less the retention;
  - a retirement with no matching acknowledgement;
  - a second retirement of one run;
  - an admin decision applied before a `policy.apply` with its keys digest, or under a key whose kinds in that record don't include the verified kind.
  - a decision whose `verified.keys_digest` differs from the latest `admin_keys` record before it (D6).

**Collector:**
- The new kind is accepted without an asset check, and numbered.
- Every accepted admin reply stamped 0.10 carries `keys_digest` and `keys`. The digest changes when a key's kinds, status or principal change, and stays the same when only their order in the configuration changes.
- A 0.9-stamped request for it is refused.

**Node** (in the node PR):
- An accepted document whose file hash differs is denied.
- An accepted document whose `draft_digest` is not the latest draft is denied.
- An accepted document that differs from the draft outside `authorized_writers` is denied.
- An accepted document that is not canonical is denied, though its hash is the signed one: the draft with writers added, re-encoded with other whitespace or key order (a golden, D6 T3, D4). So is a document whose writer has a class other than `write` or `control`.
- An accepted document for another sensor is denied.
- A file in the admin folder that no signature names is never read as a baseline. When the two digests are equal, a file present in the folder is ignored (D6, T5).
- The file is swapped between the hash check and the store: the stored record holds the checked bytes (D6, T3).
- The retention consumer's creation writes its `created` record and prunes nothing, with the clock stepped forward past the retention before the first tick (D5).
- The retention move: the audit write comes first, and a failure keeps the cursor.
- An adoption refused by the configuration ceiling is written as `denied` with a storage reason, and raises `network-baseline-no-room` (D5).
- A backward clock step (D6, T1), on the test clock:
  1. A move is taken.
  2. The wall clock steps back by more than an hour.
  3. The hourly tick runs. No record is written, and `VerifyChain` passes.
  4. The clock advances until wall time less the retention passes the old cutoff. The next move chains to the record before the step.
- The learner's retirement: the audit write comes first, and a failure keeps the learner in the consumer set.
- The grant (D1, D6): change a key's kinds and send one network acknowledgement. The `policy.apply` with the new digest comes before `config.baseline_acknowledged`. With the `policy.apply` write forced to fail, the acknowledgement is not adopted. A digest written into the node's own files or configuration is never recorded or used. Only the one in the collector's reply counts (D6).
