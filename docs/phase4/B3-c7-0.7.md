# C7 0.7: a run request may name a register run (P4-A3, D4-13)

Owner: B3. Date: 2026-10-28. Status: **proposal, for review.** No code is changed by this note. B1 approves C7 0.7 after its consumers review it:
- B2, for IED compatibility (C2 0.6, the adapter's run mode);
- B5, for the node's request side;
- B6, independently, for the refusal tests below.

Every result here is `desk`. No device is behind any of it.

## Why

#331 (C2 0.6) makes a register run, `sel.config.read_all`, invocable under its own ID. The collector cannot take it yet. `RunBody.ValidateAgainst` knows operations only, so a request that names a run is refused as `unknown_operation`. That is fail-closed, and a test pins it (#332). Three further things would break the first time the refusal is lifted:

1. `decideRun` takes `op, _ := m.Operation(body.OperationID)` and then reads `op.AccessLevel` for the credential check. For a run `op` is nil, so a request with a credential would panic.
2. `Pipeline.invocation` copies `PipelineConfig.Limits` into the invocation. The default deadline is 120 s, and the run's own deadline is 300 s. The adapter takes the tighter of the two (`session.limits` in `modules/ied/sel751/run.go`, #331), so the run would always time out.
3. The collector's test profile does not name `sel.config.read_all`, so C2's `CheckAgainst` would refuse it.

## Proposal

### 1. The wire: no new field

`RunBody.operation_id` may name a register operation or a register run. Nothing else in `RunBody` changes.

- **Why not a `run_id` field.** C3 puts operation and run IDs in one namespace (`checkCommon` refuses a duplicate entry ID; `Run`'s documentation says so), so one string cannot be both and is never ambiguous. A second field would add a second way to say the same thing, and the node would have to know which IDs are runs. It has only the register revision today (`Config.RegisterVersion`), and B5's schedule entry already holds one `operation` string.
- **Why a minor bump anyway.** C7's readers accept any minor of the same major (`version.ID.Accepts`), and this adds no field, so a 0.6 collector reads a 0.7 request and refuses the run ID as `unknown_operation`. That is a clean refusal, and the node must treat it as "this collector cannot run it", not as a fault. The bump is for the other direction and for the record: the 0.7 collector takes a run ID only from a request stamped 0.7 or later, and refuses one stamped earlier as `unknown_operation`, which is what a 0.6 collector would say. No honest node sends one.

### 2. What the collector checks for a run (`RunBody.ValidateAgainst`, step 6 of `decideRun`)

All of these come before the floor, the interval, the claim and any credential, so a refusal spends none of them:

| Request | Refusal | Check |
| --- | --- | --- |
| `operation_id` is in neither the operations nor the runs | `unknown_operation` | as now |
| names a run, and `params` is not empty | `bad_params` | a run is literal; it takes no parameters (`RegisterLookup.Invocable` says the same in C2 0.6) |
| names a run, and a step does not render (a deny rule matches the step's line, or it does not classify as its own operation) | `not_invocable` | `Matcher.RenderRun` fails as a whole, and nothing is sent. This is the "step the policy denies" case |
| names a run, and a step is not read-only or not in the operate phase | `not_invocable` | repeats C3's package validation for the matcher the collector holds, so a package that was somehow activated with such a step still cannot run |
| names a run whose highest step needs level 0 | `not_invocable` | the adapter's run mode always authenticates, so a run is a Level 1 session. A run of Level 0 steps is not one this build can send |
| names a run, and `credential_ref` is empty | `credential_mismatch` | a run is above level 0, as for any other operation (C7-A2-5) |
| names a run, and the request is stamped before 0.7 | `unknown_operation` | see section 1 |
| the principal is not a schedule | `principal` | unchanged: step 1 |

The run's access level is the highest of its steps' levels, as `RegisterLookup.Invocable` returns it, and not a constant. With C3 0.3's rules (steps are operate-phase, at most level 1) it is `"1"` for every run that passes the rows above. A new exported method, `RunBody.AccessLevel(m *register.Matcher) (string, error)`, returns it for both an operation and a run, so `decideRun` does not read `op.AccessLevel` from a possibly nil operation. A nil operation or run cannot reach the credential path, because `ValidateAgainst` has already refused it.

### 3. Limits (`Pipeline.invocation`)

For a run, the invocation's `StepTimeoutMS`, `DeadlineMS` and `MaxResponseBytes` are `Limits.ForRun(m, id)`, from the signed register. The connect timeout, retries and minimum interval stay as they are. The adapter still holds each step to its own register limits and to these, whichever is tighter.

- **Open question for B1:** the register's signed run limits replace `PipelineConfig.Limits` for a run, and an operator cannot tighten them in the collector's configuration. I propose this because the run's bounds are already capped by C3 at C2's ceilings, and a collector that quietly shortened them would make every run fail with a timeout that no register change could fix. An operator who needs a shorter run ships a register revision. If B1 prefers a ceiling in the configuration, the cost is a second knob and a way for a run to be configured into permanent failure.
- `execute` bounds the whole run by `Limits.DeadlineMS + 10 s`, so after `ForRun` that is 310 s for `sel.config.read_all`.
- The result frame of a maximal run (524,288 received bytes, their records, and at most `MaxOutcomeRecords` audit records) must fit `collectorwire.MaxOutcomeBytes` (8 MiB). The implementation PR adds that test, with a maximal fixture.

### 4. Audit and the stores

- `device.op` names the run's ID as `operation_id` (the result's `operation_id`). Its `bytes_sent_digest` already covers every operate-phase line the transcript holds.
- The failed-auth floor, the suspensions and the minimum interval treat a run as one session. #332 pins this for every failure code a run can end with: a confirmed login with no QUI sets the floor from the session's end, a QUI clears it, and the codes suspend what they suspend for a single operation.
- No new audit action and no new refusal code.

### 5. What the node does

The node's request side changes in one way: it stamps `authz.ContractID`, so it sends `otsec.authz/0.7`. A schedule entry's `operation` may then name `sel.config.read_all`. `ConfigReadOperation` already treats that ID as configuration collection. The node does not check the ID against the register today and need not (the collector does).

**Ask of B5:** confirm that no deadline on the node's run request is shorter than a run plus 10 s, because the collector may now take 310 s to answer. I found none in `platform/node/schedule.go` or `collectorclient`.

### 6. Hosted adapters

A run is hosted only if the family's adapter does. `SEL751Runner` calls `sel751.Run`, which refuses a run it has no reader for (`refused.not_invocable`, before any connection). That refusal comes after the secret is open, which `ValidateAgainst` cannot know. The collector binary carries the register's shipped revision and the adapter in one release, so I propose a test and not a runtime check: every run in the shipped SEL-751 register is in `sel751`'s run table. If B1 wants a runtime check, `Runner` gets a second method, `Hosts(operationID) bool`, and `decideRun` refuses with `not_invocable` before the credential.

## What stays the same

- Only a schedule causes device I/O. A person never does.
- The request carries no line, no limits and no secret. The lines come from the verified register, and every line still passes `Matcher.Permit` at egress.
- The collector stays fail-closed until the implementation PR: the current refusal (`unknown_operation`) holds on `main`.

## Tests (B6 to review and extend)

In the implementation PR:

- `ValidateAgainst`: every row in the table in section 2, each refused before a credential is acquired (the test counts `Creds.Acquire` calls, which is zero) and before the floor and interval are touched.
- `decideRun`: an accepted run request builds a plan whose `Use.AccessLevel` is `"1"`, whose limits are the run's (300 s, 524,288 bytes), and which reaches the runner.
- A request stamped 0.6 that names a run is refused.
- A mutant that applies `PipelineConfig.Limits` to a run is killed by a test that runs a 200 s fixture.
- Maximal outcome frame under `MaxOutcomeBytes`.
- Every shipped run is hosted.

B6, as the independent check: a run ID with parameters, or with a step the policy denies, is refused before any credential is read.

## Not decided here

- A person-initiated run (an engineer reading the configuration on demand). That is the "engineering operation" path (R2), with its own role, session and audit, and no part of this change.
- Level 2 steps in a run. C3 0.3 refuses them, and C7 does not add them.
