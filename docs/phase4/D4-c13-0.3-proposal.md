## 1. Reader and rollback rules for the whole change

These extend CH-35 and CH-36. They state nothing new about how a minor is read.

### 1.1 Channel and store

- **The channel stays strict** (CH-36). A 0.3 sensor's hello is refused by a 0.2 node as `hello`, because ALPN carries the major only (§2 of 0.2).
  - No value on the channel is `null`; a record carrying one is refused as `form`. A sensor-hello or tick carrying one closes the connection (`hello`, `tick`). (D1's ruling on #732, P4-4-NULL; no minor change.)
  - A 0.3 node knows 0.2 on the channel, as CH-36 allows for a later minor, so it can drain a 0.2 sensor's buffered runs. Their records are stored at 0.2, the minor of the run's hello (CH-36).
- **One rule: an observation stored below 0.3 is not judged by CH-51** (D1's ruling 6). That covers an observation stored before the upgrade and a 0.2 run drained after it alike. Such a record carries no counts by construction, and the profiles of runs from before the upgrade are not held, so no comparison could hold.
  - **So an upgrade raises no `own-session-mismatch`** for 0.2 records, in retention or drained.
  - **A peer cannot pick a lower minor to escape the rule.** The minor of a stored record is the channel minor the node accepted (CH-36), and a 0.3 sensor offers only 0.3. Only a sensor host held by the attacker could offer 0.2, and that branch is outside this rule (AP-36; design §5 item 7).
  - **The limit, stated in item 4's gate report** (D1's ruling 6): flows stored below 0.3 are judged by the base rules only. A tied flow among them is skipped by every base rule except `node-address-spoofed` (design §0), so it stays hidden as HR-24 states. **Nothing in 0.3 bounds how long a 0.2 sensor runs behind a 0.3 node** (D3's B1): the upgrade order fixes a sequence, not a duration. The alarm below makes the state visible for as long as it lasts.
- **The node shows that the rule is off** (D3's B1 and D6's N5, option (i); round 2's mechanism 8):
  - **`network-own-session-unjudged`,** a node alarm, is raised while the node accepts a run whose minor is below 0.3 from its sensor, and cleared when that sensor's next accepted run is 0.3. It covers both cases: a 0.2 sensor in the window that the upgrade order creates on purpose, and a sensor rolled back. It writes no health event and is shown in status and the OS log, as `network-detector-not-restored` is, so §1.10's 45 an hour does not change.
  - **`detector_tied_below_minor`,** a run total of the node's detector shown in status, counts the tied flows that CH-51 skipped because their stored minor is below 0.3, drained or live. A tied flow in retention at the first start after the upgrade is counted too.
  - Neither is a §1.10 value. D5 adds both to its note's lists in the code brief, as for §1.2's `network-alert-unreadable`. No C7 or C8 change: no admin action and no audited record is added (D3's review).
  - *Test:* N-14's leg (3). *Control:* a node that skips the flows silently, which raises no alarm and counts 0.
- **Upgrade order: node first, then sensor. Rollback order: sensor first, then node.**
  - In that order the link stays up. While the sensor is still 0.2, its records are stored at 0.2 and fall under the rule above.
  - In the wrong order, the link is down (`hello`) until the node catches up, and the records wait in the sensor's buffer (CH-20).
  - D7's record of what rolls back together lists the pair and the order, and the rollback floor of §1.2.
- **The store reads forward** (`DecodeStored`, `strictjson.Forward` in `contracts/netobs/observation.go`). So a 0.2 node reads a 0.3 stored `flow` `end` with the new fields ignored, and a 0.3 node reads a 0.2 stored record strictly, with the fields absent.
- **Absent, `0` and `false` stay distinct through the node's tie path** (D5's B4). `Link.record` (`platform/sensorlink/link.go`) ties a held record by `json.Unmarshal` into `netobs.Observation` and `json.Marshal` back, and every tied flow passes through it. So every field of CH-52 to CH-55 is, in the Go type, a pointer or an equivalent that keeps absent, `0` and `false` apart through that re-encode. With a plain `uint64` and no `omitempty`, an absent count would be stored as 0 and read as a complete zero (a miss); with `omitempty`, a true 0 would be stored as absent (an alert on every clean own run). *Test:* N-8's leg (2), through `Link.record`. *Control:* the same field as a non-pointer `uint64`.

### 1.2 Stored alerts and the detector's checkpoint after a rollback

- **What `main` does, read from the code.** At a restore, `alertsAfter` (`platform/node/netdetector.go`) decodes every alert after the checkpoint's `last_alert_seq` with `AlertFromEvent`. Any error fails the restore. The node then raises `network-detector-not-restored` and starts its detector from the oldest retained observation (the restore path in the same file). `AlertFromEvent` has no other caller outside tests. The forwarder sends the C4 `netobs.alert` event as it sends any health event, and never parses `rule`.
- **The design's sentence was wrong for `main`,** and this commit corrects it in design §7.1 item 1. It said that a rolled-back node "refuses those stored alerts on read, counts each under the refusal count, and loses none from the store". On `main`, nothing counts a refused stored alert, and one unreadable alert after `last_alert_seq` fails the whole restore.
- **Required: skip, count, alarm** (D1's ruling 2, a requirement of the brief "The approved contracts in code"; D1 records it when it approves 0.3). In `alertsAfter`, a stored alert that `event.Decode` or `AlertFromEvent` cannot read (D5's N1: `alertsAfter` returns on an `event.Decode` error before `AlertFromEvent` is reached, so both are named):
  - **is skipped,** and the restore goes on with the alerts it can read. The alert stays in the store, which is append-only, so a later upgrade reads it again;
  - **is counted** under `detector_alerts_unreadable`, a run total of the node's detector, shown in status;
  - **raises `network-alert-unreadable`**, with the count in its text. It is raised at the restore that skipped one, and cleared at the next restore that skips none. It writes no health event, and is shown in status and the OS log only, as `network-detector-not-restored` is (D5's N1). So `D5-sensor-node.md` §1.9 item 5's pool list and §1.10's 45 an hour stay as they are.
  - **What the skip costs:** the restore holds back only the alerts it read (D4-74). If the replay raises a skipped alert's condition again, it is stored a second time. That is a duplicate, and it fails loud, never silent.
  - D5 adds the count and the alarm to its note's lists in the code brief. They are not §1.10 values.
- **What a node rolled back from 0.3 to 0.2 does:**
  - Its detector checkpoint is `otsec.netcheckpoint/0.3`, a later minor. The 0.2 node must read it as CH-35's bridge build does (D5 §1.15 item 1): recognise any `otsec.netcheckpoint/0.x` detector document, raise `network-detector-not-restored` for a minor it cannot read, start from the oldest retained observation, and remove the document once its own first checkpoint commits.
  - It raises the retained observations' alerts again, as CH-35 states for the 0.1 rollback.
  - It judges no tied flow by CH-51, so HR-24 is again "hidden whole" for as long as the rollback lasts.
  - **The `own-session-mismatch` alerts stay in the store,** which is append-only. A later upgrade reads them again.
- **Requirement on the 0.2 code** (D1's ruling 2; not yet built, brief "The approved contracts in code"): the 0.2 detector's checkpoint reader keeps bridge items 1 and 2 of CH-35 for a later minor. **Without it,** a rollback from 0.3 gets the silent restart that CH-35 describes for 0.1: `main`'s exact match on `CheckpointIdentifier` in `detectorCheckpoints` skips the 0.3 document, and the node gives no alarm, stores duplicate alerts and leaves an orphaned document.
- **The 0.2 code also keeps CH-35's bridge item 5 for a later minor** (D5's N2 on this PR, under round 2's mechanism 8): it ties a held record of a later minor by patching the raw JSON, never through `Link.record`'s re-encode into its own type. Under the stated rollback order the sensor goes first, so the 0.3 node's intake hold (`netcheckpoint.intake`) can still hold raw 0.3 bodies when the node rolls back. Re-encoded into 0.2's type, such a body would keep `schema` at 0.3 and lose CH-52 to CH-55's fields for good, and a later upgrade would judge it with the counts missing. *Test:* N-13's leg (4). *Control:* a 0.2 tie that re-encodes, which stores a 0.3 record without its counts.
- **The rollback floor** (D3's N3). A 0.3 node may be rolled back only to a 0.2 build that carries all three requirements above: the bridge reader of CH-35 items 1 and 2 for a later minor, bridge item 5 for a later minor, and skip, count and alarm in `alertsAfter`. A rollback to the 0.2 code now on `main` gets a restore failed whole by one `own-session-mismatch` alert, or the silent restart above. D7's record of what rolls back together names that build as the floor.
- **A 0.2 checkpoint with a 0.3 alert after it.** A node rolled back to 0.2 may also hold a 0.2 checkpoint, written before the upgrade, with `own-session-mismatch` alerts after its `last_alert_seq`. Skip, count, alarm applies there, so that checkpoint still restores.
- **The upgrade direction** (D5's B2). **A 0.3 node reads the 0.2 detector checkpoint it finds at the upgrade,** strictly and with no alarm, as CH-35 has 0.2 read 0.1 ("Read"). Its restore then goes on as for its own checkpoint, and a session open at that checkpoint is judged as the node-restart rule below states. *Test:* N-13's leg (3). *Control:* an exact match on the 0.3 identifier, which skips the 0.2 document and restarts silently.
- **0.3 code always writes `otsec.netcheckpoint/0.3`** (D5's B2, pinned). It never writes 0.2, even while it holds no state that 0.2 cannot read, so that one identifier is never written by two binaries. The learner's half takes the same identifier (0.1 §8), and its form does not change.
- **A session whose records began before the detector's first observation is judged unjudged** (D5's B3, option (b); round 2's mechanism 9; round 3's rule from D5's B5). The detector checkpoint keeps its form and holds no running sums, so C5 does not change (P8), and no checkpoint field is added.
  - **F** is the first observation seq this detector took since its process started: the restored checkpoint's `through` + 1, or, at a first start, after pruning, or when the checkpoint did not restore (`network-detector-not-restored`), the oldest retained observation's seq.
  - **The rule.** A session handed over by `Session(s, afterSeq)` (`modules/detection/netdetect/own.go`) whose `afterSeq` is below F is judged with every comparison that reads an `end` count listed as `unjudged … :incomplete` (CH-51), never against the partial sum. For a re-pointed open-flow entry, the earliest `afterSeq` among the invocations that held the entry is compared.
  - **What it covers:** a node restart with a session open at the checkpoint; a checkpoint that did not restore, or none, with a session whose earlier records were pruned or lie before F; and a session whose tied ID was evicted past `MaxTiedSessions` (256; `TiedEvicted`, `contracts/netobs/checkpoint.go`) before the checkpoint. The rule keys on the session, not on membership of the checkpoint's own-session state, so an evicted or unrestored ID changes nothing.
  - It fails toward alerting: the cost is one alert for each tied session whose records began before F.
  - *Test:* N-17, three legs. *Control:* a detector that judges the partial sum, which raises nothing on a run whose excess was before F.

### 1.3 Sizes

- **A `flow` `end`** gains at most 278 octets (recounted in round 2): seven numeric keys, each with a 19-digit value, the most that the range 0 to 2^63 − 1 stated for each count in CH-52 to CH-55 allows (`orig_payload` 34, `resp_payload` 34, `orig_pkts` 31, `resp_pkts` 31, `rexmit_inconsistent` 41, `to_device_overlap_octets` 46, `password_lines` 36: 253), plus `"incomplete":true` (17), plus eight commas (8). That counts all eight keys, although `password_lines` and `incomplete` never sit on one record (CH-55), so a record that the node accepts gains at most 260.
  - This is far below `MaxNetobsBytes` (24 KiB), and a `flow` record is not the worst stored body.
  - The worst-body pin (CH-35, R-1 to R-6) is rerun with the new fields on every `end` (N-12).
- **An alert's `observation`** stays within `ExplainMax` (256). The longest head the grammar admits (CH-51) is 177 octets, so `": "` and at least 77 octets of free text always fit; the free text is cut to fit and the head never is. The longest head one judgement writes is 95 octets (Telnet). A summary's union of Telnet hits writes at most 120, and one that mixes Telnet and SNMPv3 hits can reach 177, which still fits (CH-51).
- **No new member enters `counters`, so none enters `sensor.counters`** (CH-53). `overlap_table_full` is in the new `frame_stage` object, and the agent's two new counts are in `agent` (CH-43). The heartbeat grows by at most 57 octets for `frame_stage` and 82 for the two agent counts. Heartbeats are never stored. So C4 0.4 and the health events' caps do not change.

### 1.4 A Telnet result without `session.telnet`

C2 0.10 (D2's proposal, #671) refuses a Telnet result without `session.telnet`, so such a result comes only from a 0.9 collector. The run's profile is then held but partial: it has no `refusals`, `command_octets_received`, `read_to_eof` or `rexmit_octets`. That is not design §3.2's case of no profile held, in which the base rules judge a tied flow as if untied. For a flow tied to such a run (D4's N2 on #671, 6862377718), the detector:
- lists `M6b:no-profile` under `unjudged` (CH-51), as for `rexmit_octets` `unknown` (design §3.1), so the flow alerts;
- judges M1 and M5 as usual;
- judges M3 to the relay with the 194-octet tolerance of design §5 item 3 (no `refusals`);
- leaves M3 from the relay unjudged, since `read_to_eof` is not known. That is design §5 item 4's residual, which raises no alert, so it is in neither list of the head (CH-51).

Both this rule and the untied reading fail closed. This one keeps M1, M3 to the relay and M5. *Test:* N-15.

## 2. CH-51. The rule `own-session-mismatch`

- **The token.** `own-session-mismatch` joins `Rules` (`contracts/netobs/alert.go`), which is a closed set. The new token is the reason this change is a minor.
- **The rule runs before any baseline is acknowledged.** It is in `BaselineFree`, like the other own-session rules (D4-68 ruling 10), because a tied flow skips every base rule (design §0).
- **Parameters: none** (D1's ruling 5). The rule's bounds come from each run's profile, and the text states the excess over them.
  - **Only M4 uses a setting.** Its bound adds 2*g*, where *g* is `tie_grace_s`, the baseline parameter that `own-session-outside-record` and `own-session-unseen` show. It also adds `max_skew_ms`, which is fixed at 2,000 ms in CH-22 and is not a setting.
  - **M4 is not judged for Telnet** (design §3), so `tie_grace_s` would describe only SNMPv3's M4 alerts. The excess that M4 states is computed with it already.
  - Neither value is in `coverage.settings`, which holds `sa_reply_timeout_ms`, `max_pending_dnp3` and `flow_idle_s` (`contracts/netobs/citation.go`), and from 0.2 `prp_window_ms` (CH-28).
- **The fixed head of `observation`: two lists** (D6's B1, option (a); round 2's mechanism 1). One list names what the flow exceeded, the other what could not be judged and failed closed, so no reason is left unattached:

  ```
  observation := head [ ": " free-text ]       the whole string matches this production
  head        := part ( " " part )*            at least one part; parts in the order below, each at most once
  part        := comparisons | unjudged | reasons | "no-profile"
  comparisons := "comparison" ( " " C )+       C in M1 M2 M3 M4 M5 M6a M6b, each at most once, in that order
  unjudged    := "unjudged" ( " " U )+         U in M2:incomplete M3:incomplete M5:incomplete M6a:incomplete
                                                    M6b:incomplete M6b:no-profile, each at most once, in that order
  reasons     := "reason" ( " " R )+           R in prp-table-full prp-mismatched, each at most once, in that order
  ```

  - **`comparison`** names only the comparisons the flow exceeded.
  - **`unjudged`** names each comparison that was not judged and fails closed, with its cause. The causes, and the program that sees each, are CH-53's table; `M6b:no-profile` is the collector's side (`rexmit_octets` `unknown`, or a 0.9 result, §1.4). **A comparison left out by design is in neither list,** because it raises no alert: M4 for Telnet, M3 from the relay without `read_to_eof` or with a restart or an `idle` cut in its stretch, and M6b on a stretch where a PRP count rose (design §4, §5 items 4 to 6). M1 and M4 are judged on what was seen and never listed as unjudged (D6's N15): every route by which either cannot be judged (a lost `end`, an `incomplete` record, a session that began before the detector's first observation) also lists M3, M5, M6a and M6b for Telnet, or M2 and M3 for SNMPv3, so the flow alerts anyway; and M1 and M4 alert only on more, so judging what was seen raises nothing false.
  - **`reason`** keeps only the states that changed a bound the flow was judged against: R is written when R rose in the flow's stretch (design §4) and the flow was judged on a comparison whose bound R changes, which is SNMPv3's M2 or M3 (the doubled bound). A Telnet flow therefore never carries a reason.
  - **`no-profile`** alone is the one fixed phrase for a tied flow with no profile held (design §3.2), which the base rules judge as if untied.
  - **A judgement never lists one comparison in both `comparison` and `unjudged`.** The grammar allows it, because a summary's head is a union (below).
  - **Examples:** `comparison M3 M6b: …`; `unjudged M6b:no-profile`; `unjudged M5:incomplete M6b:incomplete: …`; `comparison M5 unjudged M6b:incomplete`; `comparison M2 reason prp-table-full: …`; `no-profile: …`. D6's pair of B1 is now told apart: two placed password lines on a run whose `rexmit_octets` is `unknown` write `comparison M5 unjudged M6b:no-profile`, and an unplaced slot with a complete overlap count and no excess writes `unjudged M5:incomplete`. (A record with `incomplete` carries no `password_lines`, CH-55, so it writes `unjudged M5:incomplete M6b:incomplete`.)
  - **`Alert.Validate` refuses** an `own-session-mismatch` alert whose whole `observation` does not match the production (D6's N1): the head, then either the string's end or `": "` and free text. So `comparison M3 M3`, `comparison M6b M3`, `comparison M3x`, a cause not in U's set, `reason` before `unjudged`, and a missing head are refused, although each starts with a valid head.
  - **The free text is cut to fit `ExplainMax`, and the head is never cut** (D6's N2). The detector cuts the free text, at a UTF-8 boundary, so that the whole `observation` is at most 256 octets. The longest head the grammar admits is 177 octets (all seven comparisons, all six unjudged items, both reasons and `no-profile`), so a head always fits with `": "` and 77 octets of free text. One judgement writes at most 95 (`comparison M1 unjudged M3:incomplete M5:incomplete M6a:incomplete M6b:incomplete M6b:no-profile`), and a summary's union of Telnet hits at most 120 (Telnet: `comparison M1 M3 M5 M6a M6b unjudged M3:incomplete M5:incomplete M6a:incomplete M6b:incomplete M6b:no-profile no-profile`). A window of one asset that mixes Telnet and SNMPv3 hits can reach the grammar's 177, which still fits. On `main`, an alert whose `Health()` fails is not built (`commitAlerts`), so without the cut an alert stating several excesses with two IPv6 endpoints would be lost. *Test:* N-3. *Control:* a detector that writes every excess in full, whose alert is then not built.
  - **A summary's head is the union of the heads of the window's hits** (D6's N8, fixed): each part is the union of that part over the hits, in the fixed order. The free text is the latest hit's, cut to fit. So a spoofed judgement followed in one window by a designed fail-closed hit keeps both heads' items. Design §3.2's "a later hit overwrites a window's `Observation`" now holds for the free text only. **The union includes the head of the window's stored `Observation`** (D6's N12): the detector takes it from the `DetectorWindow` held in its checkpoint (`contracts/netobs/checkpoint.go`), never from a set kept in memory only, so the union survives a restore with the checkpoint's form unchanged (§11). *Test:* N-2's leg (3), with a variant whose window is restored between its two hits. *Control:* a summary that keeps the latest head, which drops the earlier hit's `comparison`; for the variant, a union kept in memory only.
  - Every other rule's text is unchanged.
- **The text states only the excess, never the run's own totals** (design §3.2; §7 below). It says what was seen and never says "spoofed" (D4-68 ruling 10).
- **What an earlier reader does:** a 0.2 `Alert.Validate` fails it as `form` ("is not a rule"). §1.2 gives the consequence. A C6 or upstream reader gets the token as text in the forwarded health event and parses no `Rules`. C4 does not change.
- **When a tied flow is judged with its `end` lost** (D6's B2 and D5's N1 on #677; round 2's mechanism 3). Each tied key that the hold's open table drops at a new sensor run, and each held flow that the hold marks `EndLost` (a new run or degraded coverage; `giveWay` in `platform/sensorlink/hold.go`), is judged then, with every comparison that reads an `end` count listed under `unjudged` with the cause `incomplete`: `M3 M5 M6a M6b` for Telnet, `M2 M3` for SNMPv3. M1 and M4 are judged on what was seen. A tied key whose open-flow entry expires with no `end` (design §3.2's second path) is judged the same way. The node is the only program that sees this cause (CH-53's table). *Test:* N-16. *Control:* a detector that judges only on an `end`, which never judges such a flow.
- **What a rollback costs:** §1.2.
- **Test:** N-1, N-2, N-3, N-13, N-16.

## 3. CH-52. Payload and packets per direction on a `flow` `end`

- **Fields.** On every `flow` `end` whose `l4` is `tcp` or `udp`, a 0.3 channel record carries:
  - `orig_payload` and `resp_payload`, the payload octets each end sent;
  - `orig_pkts` and `resp_pkts`, the packets each end sent.

  Each is a decimal integer from 0 to 2^63 − 1. In the Go type the fields are optional, and keep absent and 0 apart through the tie path (§1.1, D5's B4). They are required in a 0.3 channel record, and may be absent in a stored record of any minor (CH-35's pattern). They are never on a `start`, and never on a layer-2 or other `l4` record.
- **`orig` is the record's `ip.src` end, and `resp` its `ip.dst` end.** `src` is as C13 defines it: for `client-server`, the end that sent the SYN; for `direction: none` and `midstream`, the sender of the first frame (CH-49).
  - **The link agent maps the engine's ends to the record's.** Zeek's "originator" can differ from C13's `src`. Its heuristic flips a connection's direction (the `^` in `history`, `base/protocols/conn/main.zeek` at `v9.0.1`). Where Zeek's originator is the record's `dst`, the agent swaps each `orig_`/`resp_` pair.
  - **A reader never takes `orig` to mean "to the device".** The detector finds the direction to the device by the run's endpoint, the device's address and port (design §3).
- **`orig_payload` and `resp_payload`** (design §7.1 item 2 (a); the engine computes them already, design §2):
  - **TCP:** the sequence span each end sent. That is Zeek's `orig_bytes` and `resp_bytes` (`c$orig$size`, `TCP_Endpoint::Size()`): without the SYN and the FIN octet, unwrapped over 64 bits, from the first sequence number seen on a midstream join.
  - **UDP:** the sum of the payload lengths each end sent (`UDPSessionAdapter.cc`).
  - **What does not count:** retransmissions, keep-alives (`snd.nxt` − 1, at most one octet), zero-window probes, the PRP RCT, VLAN tags and padding.
  - **What inflates it:** a segment far ahead in sequence, and an ACK beyond the data sent. Both are noisy and hide nothing (design §7.1).
  - **Holes:** a hole inside the span is counted, so loss cannot make the span smaller than what was sent. Zeek's `missed_bytes` shows the holes and is not carried.
- **`orig_pkts` and `resp_pkts`:** Zeek's `orig_pkts` and `resp_pkts` from its conn-size analyzer, counted after the PRP discard, which the frame stage makes before the engine (SL-3; E-D4-02). Whether a fragmented datagram counts once, after reassembly, is a stage 2 check (design §2). Until it is measured, the detector judges SNMPv3 datagrams on these fields only as the design's §3 M2 states.
- **Deltas.** Each `end` carries the counts since the previous `end` of the same connection, and a checker sums `end` records by key, as for `packets` and `bytes` (0.1 §4.3).
  - **For UDP, and for the packet counts, the sum is the total.**
  - **For TCP's payload fields the sum can exceed what was sent, at the start of each later portion** (D6's N3). After an `idle` cut or a sensor restart the engine opens a new connection and starts its span at the first segment it sees (the partial-connection branch of `init_endpoint`, `InitStartSeq(first_seg_seq - 1)`, Zeek `v9.0.1`). If that segment is a retransmission or a keep-alive (`snd.nxt` − 1), the two portions' spans overlap by up to that segment's length. It never makes the sum smaller, so it gives noise and never a miss. The detector's allowance is design §4's: to the relay, the run's longest approved line + 2 for each `idle` cut or restart in the stretch; from the relay, a flow with either in its stretch is not judged. *Test:* N-6's leg (4) and an own-run cell (design §6.6). *Control:* a bound without the per-cut allowance, which alerts on the own run whose later portion starts with a retransmission.
- **Checks the node makes:** each value lies in its range. On a TCP `end` with `syn_only: true`, both payload fields are 0, because a syn-only flow carries no payload (0.1 §4.3). The node makes no check that ties these counts to `packets` or `bytes`. Those count frames after the discard with link-layer octets, and the two are not equal in general (design §4, the RCT and fragments).
- **What an earlier reader does:** §1.1.
- **What a rollback costs:** the detector loses M2 and M3 with the rule (§1.2). The stored fields stay.
- **Test:** N-4, N-5, N-6 (legs (1), (3) and (4)), N-12, and N-16 and N-17, which judge the sums of these counts with an `end` missing or across a node restart.

## 4. CH-53. The overlap count, `incomplete`, and the frame stage's and agent's counts

These are design §3.3, adopted by D1 (6854297364, and the conditions of D3 and D6 on `7f9e9953`), as contract text, with round 2's mechanisms 2 and 4 to 7. The frame stage computes them and the link agent joins them (D3's SL-3 change, #677, which follows this clause).

- **`to_device_overlap_octets`** (named by its direction, D6's N4; `orig_overlap_octets` at `e7ec8ecd`) is on a TCP `flow` `end` that a frame-stage record joined. Its value is the sum, over the record's portion, of each segment's payload octets that lie at or below the highest sequence end seen in that direction before the segment. It is a decimal integer from 0 to 2^63 − 1. It counts the direction from the node's address to the listed endpoint, **whichever end is the record's `src`.** A portion that starts with the relay's frame (after an `idle` cut or a sensor restart) is `midstream` with the relay as `src` (CH-49), and its `orig_payload` is then the relay's octets; the overlap count still counts the node's direction, as its name says.
  - **A segment that starts exactly at the highest end adds nothing.** One that starts one octet below it adds one.
  - **The only exclusion:** a one-octet segment that starts at the highest end − 1 (a keep-alive). Every other short segment counts.
  - **Sequence numbers are unwrapped to 64 bits** from the first one seen.
  - **Payload length** is the IPv4 total length less its header, options included, or the IPv6 payload length less any extension headers, less the TCP data offset.
  - **It is a delta since the previous `end` of the connection,** as in CH-52. The frame stage keeps the entry across an `idle` cut, so the highest end carries over and the portions' counts do not overlap.
  - **The direction from the device is not counted.**
- **`incomplete`**, present only as `true`, on a TCP `flow` `end`. It means only that the overlap count for that record, and with it `password_lines` (CH-55), cannot be read as complete. It says nothing about the flow's other fields.
- **The agent marks every TCP `end` that no record joined** (D6's B2, option (b); round 2's mechanism 2). It sets `incomplete: true` on each such `end`, whatever its endpoints. The agent does not read the frame stage's lists. So a TCP `end` carries either a joined record's fields or `incomplete: true` with no count; no TCP `end` carries neither. A tied flow to an endpoint not on the lists therefore alerts with `unjudged M5:incomplete M6b:incomplete`. That fails closed, and the operator lists the endpoint. `no-profile` is the collector's side only (CH-51). The cost is 17 octets on every TCP `end` the frame stage does not track (§1.3).
- **Each cause of a missing or partial count, and the program that sees it:**

  | Cause | Seen by | What it gives |
  | --- | --- | --- |
  | The frame stage refused the entry, its table full | Frame stage (counts `overlap_table_full`); agent (no record joins) | `incomplete` on the `end`, by the agent |
  | No entry: the handshake was not seen whole (a midstream join, a sensor restart, one-direction capture, a lost handshake frame), or the flow is not from a listed node address to a listed endpoint | Agent (no record joins) | `incomplete`, by the agent |
  | A header in the flow was malformed (lengths inconsistent with each other or with the frame) | Frame stage | `incomplete` in its record |
  | An IP fragment on a tracked flow (D6's B3) | Frame stage | `incomplete` in its record |

  | A record that matched no `end` and left the buffer (mechanism 5) | Agent (counts `overlap_unjoined`) | `incomplete` on the `end` whose span held it, if one came |
  | Two records inside one engine `end`'s span: an entry freed or begun inside one engine flow (design §3.3, D6's B1 on #664), or a record written after a close and before the agent reads that close's `end` ("An `end`'s span") | Agent | `incomplete` on that `end` |

- **IP fragments** (D6's B3). The frame stage does not reassemble. A fragment on a tracked flow marks that flow's record `incomplete`: an IPv4 frame with MF set or a non-zero fragment offset, or an IPv6 frame with a Fragment header. A fragment whose TCP ports the frame stage can read marks its own entry. A fragment whose ports it cannot read (a later fragment, or a first one too short to hold them) marks every tracked entry between its two IP addresses, in either direction. **Its scope** (D6's N13): for IPv4, only a fragment of protocol 6, since the protocol is part of IPv4's reassembly key (RFC 791), so no fragment of another protocol can complete a TCP segment; for IPv6, every fragment between the two addresses, since a later fragment's Next Header is ignored by the receiver (RFC 8200 §4.5) and cannot limit the rule. So a fragmented IPv6 SNMPv3 datagram between the node and a device that also holds a tracked Telnet flow marks that flow: noise, which fails closed, and which anyone on the segment can raise at will (design §4). Without this, a substitute injected as a first fragment holding only the TCP header and a second holding the N octets would count 0 at the frame stage while the relay and the engine reassemble it, and in the ACK-first order nothing would alert. The same rule covers overlapping fragments, where the relay's reassembly and the engine's could differ. Own runs should not meet it, because Windows sets DF on TCP; that is inference, and a stage 2 own-run cell checks it (design §6.6). Reassembly in the frame stage was the alternative, and it is not taken: it would put more code in the program that parses hostile frames. *Test:* N-10's fragment legs. *Control:* a frame stage that reads a first fragment's lengths as the segment's, which counts 0 and lets the substitution pass; for the address rule's leg, a frame stage that marks only fragments whose ports it reads.
- **Bad TCP checksums** (D6's N7). The frame stage reads no payload byte (§10), so it cannot verify a TCP checksum. A segment that the relay discards for its checksum still counts in the overlap. So anyone on the segment who sees the sequence numbers can raise `comparison M6b` on own runs at will, with no effect on the device. That is noise, never a miss, and it is stated as a known false-positive source an attacker can cause (design §4). A stage 2 cell measures it.
- **Which flows are tracked.** The frame stage creates an entry only for a TCP flow that meets all three of these:
  - its source is one of the node's addresses;
  - its destination is a listed collector endpoint, a relay's address and Telnet port;
  - the frame stage saw the handshake complete: the node's SYN, the relay's SYN-ACK, and an ACK of that ISN + 1.

  **The half-open entry** (D6's N18 on #677; D1's ruling on N18, D3's choice (i) in 6880609659). At the node's first SYN on a key that meets the first two conditions, the frame stage makes a half-open entry in the same table, holding the first SYN's receive time. A retransmitted SYN does not replace it (Zeek's `start` is the time of the packet that created the connection: `IPBasedAnalyzer::NewConn`, `src/packet_analysis/protocol/ip/IPBasedAnalyzer.cc`, SHA-256 `24e6b81f…24ea`, passes `run_state::processing_start_time`). The entry becomes tracked when the handshake completes. It counts against `MaxOverlapFlows`, is refused at the bound and counted under `overlap_table_full`, never evicts an entry, and is freed with no record if the handshake does not complete within `MaxConnectTimeoutMS` of frame time. A handshake carries no payload, so nothing is counted before the entry is tracked. *Test:* SL-T25 (j)'s case with one SYN retransmitted (#677): the record joins. *Control:* a frame stage that keeps the last SYN's time. The flood is below ("A SYN flood can fill the table").

  **Two rules of the engine's that the half-open entry does not follow, labelled designed noise** (D6's N23 on #673; `desk`, Zeek 9.0.1 in the pinned tarball). "A retransmitted SYN" means one with the same ISN.
  - **A SYN with another ISN** on a connection still in its handshake is a reuse for the engine (`TCPSessionAdapter::IsReuse`, `src/packet_analysis/protocol/tcp/TCPSessionAdapter.cc`, `4ee34a68…2419c`, weird `SYN_seq_jump`), so its connection starts at that SYN's time.
  - **A SYN retransmitted after `tcp_attempt_delay`** (`5 secs &redef`, `scripts/base/init-bare.zeek`, `05e96067…c4c675`) with nothing from the relay meets a connection that `TCPSessionAdapter::AttemptTimer` has removed, and opens a new one at its own time. So an own dial whose relay does not answer for 5 s, after two lost SYNs or at its session limit (`unknown`, C2 0.10), gets an engine start later than the entry's.
  - In both, the record's start matches no `end`, which reads `incomplete` and alerts: noise that fails closed, never a miss. A stage 2 own-run cell measures it (design §6.6). SL-3 names the value of `tcp_attempt_delay` the script sets (D3, #677).

  **A SYN on a key whose entry is tracked or kept** (D6's B7 on #673; D1's ruling 6881410545, item 3, option (a)). The SYN neither ends, frees nor replaces that entry, and it writes no record.
  - A kept entry holds the SYN's time, as a half-open entry would. It goes on flagging payload toward the device ("A late frame" below), and it is replaced only when a handshake completes on its key ("A handshake on the key"). The replacing entry takes the held SYN's time as its start.
  - *Why* (`desk`, Zeek 9.0.1 in the pinned tarball): the engine can keep such a SYN in the old connection.
    - After an RST whose sequence is less than `TOO_LARGE_SEQ_DELTA` (1,048,576) ahead, `ConnectionClosed` defers the close while data is pending (`close_deferred`), before it sets `did_close` (`TCPSessionAdapter.cc`, `4ee34a68…2419c`).
    - `IsClosed()` is `orig->did_close || resp->did_close` (`TCPSessionAdapter.h`, `8a78d84a…d9a2f`), so it stays false, and `IsReuse` returns false for a SYN whose sequence is the endpoint's `StartSeq()`.
    - A frame stage that replaced the entry at that SYN would count none of the payload the old connection then takes. The old `end` would join the earlier record and read complete: a miss.
  - Where the engine does split at the SYN, an `end` that no record joined, or two records in one span, reads `incomplete` (the causes table).
  - **A SYN repeated after `tcp_attempt_delay`, or with another ISN, on a tracked or kept entry** (D1's correction of item 2, for SL-T25 (j) on #677). The entry still neither ends, frees nor is replaced, and writes no record; a kept entry keeps the first SYN's time, as a half-open entry does.
    - On a tracked entry, a SYN with another ISN is a reuse for the engine (`IsReuse`, weird `active_connection_reuse`), which ends the old connection and opens one at that SYN. The entry's record, at its portion's end, has the old start: the old `end` has no record and reads `incomplete`, and so does the new connection's. A same-ISN SYN stays in the old connection, and nothing changes. `tcp_attempt_delay` does not apply once the relay has answered.
    - On a kept entry, the engine's connection opened at the first SYN is removed after `tcp_attempt_delay` with nothing from the relay, and a SYN with another ISN is a reuse (`SYN_seq_jump`). Either way the engine's next connection starts at the later SYN, not at the held time. A handshake that then completes replaces the entry with the held first SYN's time, so its record matches no `end`, which reads `incomplete`.
    - Both are noise that fails closed, never a miss, as for the half-open entry ("Two rules of the engine's" above).
  - *Test:* N-10's SYN legs. *Control:* a frame stage that replaces the entry at any SYN, or ends a live entry at one, which reads the count complete.

  **Both lists are sensor configuration,** set at commissioning and kept in a configuration file the frame stage reads at its start. CH-32's `file <path> sha256:<hex>` line covers "every configuration file any of the four reads at start", so the lists are in `config_digest` through that file's line. CH-32's closed lines do not change: its `setting <name> <decimal>` list of eight scalars cannot hold a list of addresses, and none is added. A change in either list therefore shows as `sensor-coverage-mismatch`, with CH-32's limit that the digest is the sensor's own word (AP-36).
- **How a reader takes the two fields.** The overlap count is complete only when `to_device_overlap_octets` is present and `incomplete` is absent.
  - **A count with `incomplete: true`** is a partial count. No reader takes it as complete.
  - **A missing count never reads as zero.** A tied Telnet flow without a complete count on any portion lists `M6b:incomplete` under `unjudged` (CH-51), and alerts. A record with `incomplete` carries no `password_lines` (CH-55), so it also lists `M5:incomplete`: the head is `unjudged M5:incomplete M6b:incomplete`.
  - **The node refuses** `incomplete: false`, and either field on a UDP record, on any `start`, or on a non-IP record.
- **The record's start is the portion's start** (D4's N1 on #677). The frame-stage record carries the kernel's receive timestamp of the portion's first frame: for the first portion the first SYN's, never a retransmitted SYN's, which the frame stage holds in the half-open entry (D6's N18 on #677; "Which flows are tracked"); after an `idle` cut, the first frame after the cut, which is the frame whose time opens the engine's next connection. A record that carried the flow's first time on every portion would join no `end` after the first `idle` cut, and every own run held past `flow_idle_s` would alert.
  - **Precision: microseconds, matched exactly** (D6's N14). The engine's pipe is a classic pcap stream in microseconds (SL-3), and the record carries the start as the value the frame stage wrote into that frame's pipe record. Zeek holds a packet's time as `struct timeval` (`pkt_timeval ts` in `src/iosource/Packet.h`, `time = ts.tv_sec + ts.tv_usec / 1e6` in `Packet.cc`), and `dispatch_packet` (`src/RunState.cc`, SHA-256 `6da21a51…76984`) starts the connection at that time. The agent rounds the engine's double (about 0.24 µs of resolution at today's epoch, so an error under 0.12 µs) to the microsecond, which recovers the written value exactly. There is no nanosecond branch.
- **The order of a record and its `end`** (D4's N2 on #677, D5's N2 there; round 2's mechanism 7). SL-3 states the sensor's side:
  - the frame stage writes a portion's record before it forwards the frame that closes the portion (for an `idle` cut, the first frame, on any flow, whose time passes the cut, because the engine's clock advances on any frame; D3's N4), or the end of input. So before it forwards each frame, the frame stage checks its entries' idle times against that frame's time;
  - it writes a counters record before each overlap record, and at least once per `SensorTickInterval`;
  - **`idle` cuts are taken on frame time, as the engine's are, and on no other clock** (D6's B5 (b) on #677; D1's corrected ruling there, (b3), 6880789325). The frame stage cuts a tracked entry's portion at the first frame, on any flow, whose time is at or after the entry's last frame time, on its key in either direction, plus `flow_idle_s` (D3's N4). The engine's inactivity timer runs on the same frame times, which both programs take from the same kernel timestamps, so for the frames both programs take, read in time order, the two cuts fall at the same frame, and no monotonic or wall clock enters the join. **Where they can differ** (D6's N24 on #677 and N22 on #673), each giving an `end` with no record or two records in one span, so `incomplete`: noise, never a miss.
    - A frame that only the frame stage takes: a segment with a bad TCP checksum, which the engine drops before `TCPSessionAdapter::Process` (`TCPAnalyzer::DeliverPacket`, `src/packet_analysis/protocol/tcp/TCP.cc`, `585e70b6…38400`, at the default `ignore_checksums` of F), and the frame stage cannot check ("Bad TCP checksums" above); or a frame lost to `drops_decoder`. The engine's last time does not move, so it can cut first. Anyone who sees the flow can cause this.
    - A key's frames read out of time order, as a TAP's two outputs on two capture interfaces can be. Both programs take the time of the last frame read on the key (below), and the engine's timer, armed at the earlier bound, can fire later than the bound by up to the reorder. Through a quiet spell no frame comes, so neither program cuts until the first frame after it: the record and the engine's `end: idle` are written then, and the `end` joins the record as at any other cut. That delay is W-7's amended bound and its stated limit (CH-57);
  - **A frame at exactly the bound cuts the flow, in both programs** (D1 on `records-auditor`'s cross-audit, 6880955572 on #673, item 4; `desk`, Zeek 9.0.1 read in the pinned tarball and not run):
    - `Session::InactivityTimer` (`src/session/Session.cc`, SHA-256 `220661ab…13cfc`) removes the connection when `last_time + inactivity_timeout <= t`. `t` is the network time that `TimerMgr::DoAdvance` (`src/Timer.cc`, `a4f6a176…609015`) passes to every timer whose time is at or before it (`timer->Time() <= new_t`), and `dispatch_packet` advances to the frame's time before it processes the frame.
    - For a tracked flow the timeout is `tcp_inactivity_timeout`: `TCP_Endpoint::SetState` (`src/analyzer/protocol/tcp/TCP_Endpoint.cc`, `6a935b5b…bf2a7`) switches to it from the handshake's `udp_inactivity_timeout` (`TCPAnalyzer::MakeSessionAdapter`, `src/packet_analysis/protocol/tcp/TCP.cc`, `585e70b6…38400`) when the handshake ends, and a tracked entry exists only after a completed handshake ("Which flows are tracked").
    - The timer is set at `last_time + timeout` (`Session::SetInactivityTimeout`). One that fires before the bound re-arms itself at `last_time + inactivity_timeout`, and `DoAdvance` takes a re-armed timer that is already due in the same advance. So, under the timer cap, with the key's frames read in time order, the connection is cut at the first frame whose time is at or after the last frame's time plus `inactivity_timeout`, before that frame is processed.
    - **`last_time` is the time of the last frame read on the key, not the largest** (D6's N22 on #673). `TCPSessionAdapter::Process` sets it to each packet's own time (`Conn()->SetLastTime(run_state::current_timestamp)`, `TCPSessionAdapter.cc`, `4ee34a68…2419c`). The frame stage's last frame time is the same: the time of the last frame read on the key, in either direction. Out of time order, a timer armed earlier can fire after the bound, and the two cuts can differ within the reorder ("Where they can differ" above).
    - **The frame stage matches it.** It cuts when `last + flow_idle_s <= t`, computed as the engine computes it: in IEEE 754 double, each time taken as `ts.tv_sec + static_cast<double>(ts.tv_usec) / 1e6` from the microseconds it writes into the pipe (`Packet::Init`, `src/iosource/Packet.cc`, `b94512b5…395ee`; "Precision" above). For times between 2^30 s and 2^31 s (2004 to 2038) and a whole `flow_idle_s`, `last + flow_idle_s` is exact and lies on the same 2^-22 s grid as `t`, so the double test equals an integer test in microseconds (D6's check of 200,000 times at each of three values, 6881392461); the double computation is kept so that the rule holds without that range.
    - **Requirements on the project's script,** built by the brief that changes it: it sets `tcp_inactivity_timeout` to `flow_idle_s`, and it defines no `connection_timing_out` hook that can return false, which would stop the engine's cut (`InactivityTimer`) while the frame stage cuts.
    - *Test:* N-18 (4). *Control:* the off-by-one mutant, a frame stage that cuts only when `last + flow_idle_s < t`.
  - the agent drains the frame stage's pipe, until a read would block, before it handles each engine line.

- **How a pending record leaves the agent's buffer** (D3's N1, second half; D5's B1 on #677; round 2's mechanism 5). A record leaves:
  - when an engine `end` of its key arrives whose span holds the record's start. It joins that `end` when it matches by key and start (above); otherwise it leaves unjoined, and that `end` is `incomplete`;
    - **An `end`'s span** (D6's B6 on #677; D1's ruling 6881410545, item 1, option (b)). For a TCP `end` whose cause is `fin` or `rst`, the span runs from the `end`'s start until the agent reads that `end`: the `end` takes every pending record of its key whose start is at or after its own. For every other `end`, the span is the `end`'s own times, from its start to its last frame time (0.1 §4.1). The rule is the agent's alone, with no engine change, and SL-3 states it with this clause (D3, #677).
    - *Why* (`desk`, Zeek 9.0.1 in the pinned tarball). `TCPSessionAdapter::Process` moves a connection's last time only while one side has not closed (`if ( ! orig->did_close || ! resp->did_close )`, `TCPSessionAdapter.cc`, `4ee34a68…2419c`). Until `ConnDeleteTimer`, a segment without SYN still goes to that connection. So after FINs both ways, an `end` ends at the second FIN, whatever came after it. Read as its own times, the late record of "A late frame" below would fall outside it, join nothing, and the `end` would read complete: a miss. After an RST only the reset side's `did_close` is set, so later frames still move the last time; `rst` takes the same rule so that the two closes read alike.
    - *What it costs:* noise on closed connections only. A record of the same key that the frame stage writes after the close and before the agent reads the `end` falls into that `end`, for example a new connection on the key that completes and ends within the delay bound. Both that `end` and the engine's next `end` of the key then read `incomplete`.
  - or when it has waited longer than 2 × `flow_idle_s` plus the engine's delay bound, measured on frame time. The engine's delay bound is the larger of `tcp_close_delay` and `tcp_reset_delay` as the project's script sets them (5 s each by default at `v9.0.1`); SL-3 states the values the script sets.
  - **A step in frame time counts toward the wait only up to `flow_idle_s`** (D6's B5 (a) on #677; D1's ruling there, (a1)). The wait is the sum of the steps in frame time the agent reads on the frame stage's pipe after the record, each step counted at most `flow_idle_s`. Frame time is the latest frame receive time a counters record carries (SL-3).
    - *Why.* The engine's `end`s advance only with frames, so a wall-clock bound would expire records whose `end` is still due. Frame time alone fails the same way across a quiet spell: at the first frame after it, frame time jumps by the whole spell, the agent reads the jump before the engine has the frame, and a record whose `end` the engine writes at that same frame would leave first (D6's B5 (a), its case). Capped, the jump adds at most `flow_idle_s`, so a record that had waited less than the delay bound has, after the jump, waited less than `flow_idle_s` plus the delay bound, which is below the leave age of 2 × `flow_idle_s` plus the delay bound, and it is still pending when its `end` comes.
    - *What it costs.* A record that never joins still leaves: after at most three spells, or after steady frames. Three spells reach the leave age only while the delay bound is below `flow_idle_s` (3 × `flow_idle_s` > 2 × `flow_idle_s` + the delay bound; D6's N25 on #673): true at 5 s with the lowest `flow_idle_s`, 10. If the script's values break that condition, a record that never joins needs more spells, which only delays its leaving. A longer wait only alerts, never misses: a record kept too long can only leave unjoined later, with its `end` `incomplete`.
    - (a2), the wait on the engine's clock through a new engine line, is not taken (D1's ruling): it would change what the engine writes, and the leave rule does not need it.

A SYN alone never does. That is design §6.4 item 5's boundary case with a SYN, which gives `comparison M1` or `incomplete`.

    - **The margin (ii) does not cover two cases** (D3's N6 on #673; D6's N23 on #677). The frame stage frees the entry before it forwards the frame, and at the default the engine may process the frame before the delete timer fires, so late payload in that frame lands in the old connection uncounted: a miss. ## 5. CH-54. `rexmit_inconsistent`

- **The field.** A count on every TCP `flow` `end`, a decimal integer from 0 to 2^63 − 1, required in a 0.3 channel record. It counts the engine's `rexmit_inconsistency` events on the connection, as a delta since the previous `end`.
- **Why it has no direction** (D1's ruling 1). Design §3.1 says the project's script "would count the event per direction". Zeek's event cannot support that. Its signature at `v9.0.1` is `rexmit_inconsistency(c: connection, t1: string, t2: string, tcp_flags: string)` (`src/event.bif`). `TCP_Reassembler::Overlap` knows `IsOrig()` but does not pass it (`TCP_Reassembler.cc`). So the script cannot attribute an event to a direction from the event alone, and the count covers both directions.
  - **The cost of this is noise, never a miss.** An inconsistent retransmission from the relay also gives `comparison M6a`, and the alert's text says the direction was not known.
  - **How often a relay's retransmissions differ in content is `unknown`.** It is a stage 2 own-run cell, labelled as a known false-positive source until measured. If the noise it adds is not zero, item 4's gate report names it (D1's ruling 1).
- **The handler.** The project's handler counts the event and discards `t1` and `t2`. They are never logged, stored or forwarded, and `policy/protocols/conn/weirds.zeek` is never loaded (D1's ruling 1, 6854205907; design §3.1, stage 3's three checks).
- **What an earlier reader does:** §1.1.
- **What a rollback costs:** M6a goes with the rule.
- **Test:** N-4, N-11.

## 6. CH-55. `password_lines`, M5's input, and `login.attempts`

Point 3 is settled as **(B)**, with D6's conditions (B-i) to (B-iii) (D1's ruling 6879608207; all three reviewers chose (B)). (A), emitting the `insecure` observation at the portion's end, is not taken: besides R6.4's latency on a held session, it could lose the login frames it cites from the ring (`ring_bytes` may be 0, CH-32), it would need a new bounded wait table with no natural bound, and it would move every Telnet login's observation, not only own runs' (D3, D5, D6).

- **The field (B-ii).** `password_lines`, a decimal integer from 0 to 2^63 − 1, on a TCP `flow` `end`. It is the number of password lines the client sent in the record's portion. A password line is the client's line in a credential slot that follows a password prompt (0.1 §3.2's Telnet slot).
  - Prompts the server sent and the client did not answer are not counted. After a wrong password a SEL-751 prompts up to three times, and the adapter sends nothing more (S22 p. 7.33).
  - A server's echo is not a client line.
  - **It follows CH-52:** a delta since the previous `end` of the connection, summed by key; optional in the Go type, keeping absent and 0 apart (§1.1); never on a `start`, a UDP or a non-IP record.
  - **It is carried only on the flows that CH-53 tracks,** because the frame stage is the program that places the slots. It travels in SL-3's overlap record and uses its join (D3 adds it on #677). It is never required: its absence has a meaning (below).
- **It says whether it is exact (B-i).** `password_lines` is present only when the frame stage placed every credential slot in the portion and the record is not `incomplete`. It is absent when any frame of the portion carried a `slot-not-placed` redaction on the client's side (0.1 §3.2: for example a password sent before its prompt, or a login at an unknown prompt), or when the record carries `incomplete` (CH-53), or when no record joined. **The node refuses** `password_lines` beside `incomplete: true`.
  - **On a tied Telnet flow, an absent count on any portion means M5 was not judged.** The flow lists `M5:incomplete` under `unjudged` (CH-51) and alerts. An absent count never reads as 0.
  - This closes the case D6 and D3 found in (B) as first worded: `slot` on the `insecure` record describes only the login at its emission, so a later login whose slot could not be placed would otherwise give a short count read as exact, a miss for p ≤ 4 (design §5 item 3).
- **M5 reads only `password_lines` (B-iii).** M5 compares the sum of `password_lines` over the tied flow's portions with the run's (`credential_sent` ? 1 : 0) (design §3). It never reads `insecure.login.attempts`.
- **`login.attempts` keeps its 0.1 meaning** ("the number of attempts", at the key's first occurrence in the flow, 0.1 §4.2). Its type, range and emission do not change. The meaning that the first draft of this clause proposed (password lines, D2's note 4 on #664) now belongs to `password_lines`.
- **The frame stage places the slots on tracked flows,** as it does for redaction. With `ring_bytes` 0 it still places them on tracked flows, for this count. That reads only what the redaction already reads (§10). *Test:* N-6's leg (8). *Control:* a frame stage that places no slot when the ring is off (D6's N11).
- **A password line counts once, however many frames carry it** (D6's N10). Redaction marks every copy of a frame; the count is taken once per line on the client's stream after reassembly, where 0.1 §3.2 places the slots, never per frame. So a password segment retransmitted after the sensor saw it, or duplicated while the PRP table is full, adds nothing. *Test:* N-6's leg (7). *Control:* a count of frames that carry a `credential` redaction, which gives 2.
- **What an earlier reader does:** §1.1. No 0.2 rule reads `attempts`. On `main`, no code outside the contract reads or writes it (a search of `modules/`, `platform/`, `cmd/` and the engine script).
- **What a rollback costs:** M5 goes with the rule.
- **Test:** N-4 (placement), N-6's legs (2), (5) and (6) (rig), and design §6.4's M5 rows. The two cases from D6's (B) conditions:

## 7. Who reads `orig_payload`, and the password's length (D3's N1)

- **Who reads it.** It follows the path of every stored observation:
  - the sensor host, which writes it and also sees the frames;
  - the channel, under TLS (0.2 §2);
  - the node's intake and its `network-observation` class, kept under that class's retention and never forwarded upstream (0.1 §1);
  - the detector;
  - anyone who reads the node's store, a stolen node or disk included.

  An alert never carries it: the alert states the excess only (CH-51; design §3.2).
- **The residual.** On an own Telnet run, `orig_payload` less the approved commands' lengths, less 3 × `refusals` (C2 0.10), gives the password's length plus the 2 octets of CR LF.
  - **The same readers already learn that length** from the `credential` redaction of any cited login frame. The marker's length equals the secret's on purpose (0.1 §3.2, D4-67).
  - **Where a login frame is not cited,** because the `insecure` key is not a first sight, `orig_payload` is a second route to the same fact for the same readers. It adds no new reader.
  - **What the length gives:** it narrows a search of the password space to one length. It reveals no character.

### 15.2 `sa`

- **Why a value and not an absent meaning.** "Not known" is a real state (D2 on #735): a request whose 129 the sensor missed, one completed early by a reused sequence number or a full pending table, and every request pending at `sensor-stop` (0.1 §4.3). If absence were that state, a sensor that drops the key on every DNP3 record would silence `dnp3_no_sa` and `sa-failed` and nothing would show it. With the value, a dropped key is refused as `missing` and counted under `sensor-record-refused`.
- **The values** are `challenged`, `aggressive`, `failed`, `none` and `unknown`. 0.1 §4.3's text "and `sa` absent otherwise" reads "and `unknown` otherwise". `sa` and `objects_unread` are in the key a function is emitted under, so an `unknown` after a `none` for the same code and objects in one flow is emitted again. `sa_error_from` stays present only with `failed`.
- **How the sensor derives each value from the script's rows** (D4-117 item 3.1; D2's B1 and B2; D6's point 3):

  | Value | When |
  | --- | --- |
  | `challenged` | a g120v1 row from the outstation for the request |
  | `aggressive` | g120v3 with g120v9 in the request's object rows |
  | `failed` | a g120v7 row for the request, with its sender in `sa_error_from` |
  | `none`, a code with a reply | `done: response`, no group 120 in the request or the response, `objects_unread: false`, and no DNP3 analyzer violation in the response direction between the request's header row and its `done` row |
  | `none`, a code with no reply (6, 8, 10, 12) | `done: timeout`, no group 120 in the request (no g120v3 or g120v9), `objects_unread: false`, and no 131 before `sa_reply_timeout_ms`, **unless** the coverage statement shows the response direction unseen (next row). The alert fires on silence that was observed (D6's point 3, which D1 took) |
  | `unknown` | `done: timeout` on a code with a reply; `done: replaced`; a no-reply code whose response direction the coverage statement shows unseen: at the timeout, `coverage.degraded` is not empty, or the outstation's end is not covered by the statement in force (its VID not in `vlans_seen`, untagged not seen when untagged, or on PRP its LAN not in `lans_seen`), the test `Detector.covers` applies; `objects_unread: true` with no group 120 in the headers that were read; a response with a DNP3 analyzer violation before its `done` row and no group 120 read; **and any combination no row above names** (D6's N1), for example a request with g120v3 and no g120v9, `done: response`, and no challenge or error |

  The table is total: a request that matches no row for `challenged`, `aggressive`, `failed` or `none` is `unknown`, never one of those four. `unknown` must not be the cheap benign answer (D4-117 item 3.1): it is never written where a row above gives `none`.
- **Stated costs.** A missed 131 on a no-reply code gives a false `none` and a false `dnp3_no_sa`; that fails loud, and the citation shows no 131 was seen (D6's point 3). A SPAN placement that sees one direction, without a degraded coverage statement, also reads `none` on a no-reply code: loud, not silent.
- **How the node reads `unknown`, fail-closed.** It never sets `dnp3_no_sa` (that would be a false V-M6 flag) and never raises `sa-failed` (no error was seen). It sets a new node flag, **`dnp3_sa_unknown: true`, exactly on a DNP3 `function` whose class is in `NoSAClasses` (`write`, `control`, `session-setup`) and whose `sa` is present as `unknown`** (D3's N2, D6's point 4). A stored DNP3 record with `sa` absent and no flag still decodes, as it does today, and readers show it as "SA not determined"; the same record with the flag is refused (`conflict`).
- **Where it is shown** (D3's N1, D5's side). Wherever "DNP3 without SA" is shown or counted, in V-M6 and in the R9 view, a function with `dnp3_sa_unknown` goes on the not-shown-protected side, under one heading, "without SA, or SA not determined", with the split shown. It is never a separate bucket that a summary can leave out. V-M6 (D6's `docs/verification.md`) scores a request that GT labels as without SA and the sensor reports as `unknown` as a miss in the recall of "DNP3 without SA" and as no false flag, with `unknown` in its own column, so `unknown` cannot raise V-M6's score.
- **How `unknown` is reached without a compromised sensor** (D3's N1): dropping or delaying the outstation's replies, flooding the pending table, reusing sequence numbers, or a placement that sees one direction. The causes stay visible by name in the heartbeat (`dnp3_seq_reused`, `dnp3_pending_overflows`) and in `coverage.degraded` (`dnp3-pending-overflow`). `dnp3_seq_reused` also counts a master's ordinary retry, which reuses the sequence number with an identical fragment (IEEE 1815's retransmission, D2's note), so the R9 view shows it as a count, never as a fault.
- **Limit, stated:** an `sa-failed` whose g120v7 arrived after `sa_reply_timeout_ms` is lost as `unknown`, 0.1's rule ("not paired again"), unchanged. A device on the path can cause this by delaying the error past the timeout (D3's N1). No new mechanism.

### 15.3 `objects_unread`

- **The case.** An unknown group or qualifier, or a malformed range, leaves the rest of a DNP3 request unread. DNP3 object headers carry no per-object length (the qualifier and range set the size), so nothing after the first unreadable header can be read (D2's point 3). The qualifier that matters most is 0x5B (free format, a count and a size prefix), which group 120 uses.
- **Form** (D3's B1, broad option; D4-117 item 3.2): `"objects_unread": true|false`, **required on every DNP3 `function`**, with `objects` holding the headers read before the first one that could not be (sorted, at most 16, as now). Refused on Modbus. **The sensor writes `false` only on positive evidence that the engine read the object headers to the end of the request, and `true` otherwise.** Until the method below is measured with its GT-PCAP case and control, it writes `true` on every request.
- **The emission key** (D6's point 2). The key a function record is emitted under is the flow, code, `sub`, objects, `objects_unread`, `unit` and `sa` (0.1 §4.2 with `objects_unread` added). Without it, a clean `2 [g50v1]` early on a flow and a later `2 [g50v1]` with unread headers share a key whenever their `sa` matches, which an attacker can arrange (`unknown` for both, by reusing the sequence number), and the second is never emitted.
- **How the node reads `true`, fail-closed:** the class is the most restrictive row of `fc-classes/1` for the code, the same rule as an absent `sub` (0.1 §4.3). Function 2 with `objects_unread: true` classes as `write`, never `time-sync` or `session-setup`, so `unauthorized-write` and `dnp3_no_sa` judge it. Function 1 stays `read` (its most restrictive row), so there is no fail-open (D2's point 3). The learner does not learn the record's (code, objects); `new-function` judges it as a function not in the baseline. An unreadable request can make noise but cannot pass as a known read or a time sync. `sa: none` beside `true` is refused (`conflict`, 15.2), only when the key is present: a stored record without the key reads as `true` for its class, and a stored `sa: none` without the key still decodes (D6's N3).
- **The signal the script uses** (D4-117 item 3.2; D6's point 2; HR-25). In Zeek 9.0.1's DNP3 analyzer, a binpac exception sets `skip`, and parsing of the flow stops in both directions (`D4-hr23-design.md` §1 item 6 and §2.3, `desk`). The candidate signal for `true` is **the DNP3 analyzer's violation on the flow** (`analyzer_violation_info`, as `zeek-patch/viol.zeek` logs it), in the request's direction, after the request's application-header row and before its `done` row. `false` is written only when the request's `done` row arrives with no such violation, **and** the GT-PCAP case below has shown that each unreadable form raises the violation, with its control. That an unknown group or qualifier raises the violation is `inference` (D6's), not read in the source. Because parsing stops, a request with unread headers is often the last one parsed on its flow and ends in `timeout`. **On UDP** (`D4-hr23-design.md` §2.3, "A stop that (A) does not remove" and "(B')"): stock Zeek raises the violation for a datagram that reaches the analyzer through `Analyzer::NextPacket`, but none for a flow's first datagram, which the PIA replays straight to `DNP3_UDP_Analyzer::DeliverPacket`; only (B')'s patched `catch` raises it there, under C2. So the signal on UDP needs C2 for a request that is its flow's first datagram; without C2 such a request gives no violation, and `false` would be wrong, so the case below includes it.
- **Limit:** until the method is measured, no DNP3 record carries `sa: none`. It is stated once, in 15.10.
- **The noise the limit brings** (D3's N1 on `e9375d06`). Until the method is measured every DNP3 function 2 carries `objects_unread: true` and classes as `write`, including time sync (g50v1, g50v3) and IIN clear (g80v1). So `unauthorized-write` (`unauthorizedWrite` in `rules.go`, which reads `writeClass`) fires on every time sync and IIN clear from a master that is not authorized for `write`. The only way to quiet it is to add (client, server, `write`) to `authorized_writers`, which also authorizes every DNP3 write from that master. **`authorized_writers` is not widened to quiet this noise**: the alert is the cost of the limit, it is shown as such, and it ends when the method is measured. 15.6 states the same cost for Modbus.
- **GT-PCAP case owed** (D6's point 2, D2's point 3, D6's N5 on `e9375d06`; ids from D1): an unknown group; an undefined variation of a known group (for example g50v99); a reserved qualifier; a range past the fragment; and a 0x5B header whose size prefix runs past the fragment; each with its control (the same request readable). And a clean `2 [g50v1]`, then a `2 [g50v1]` with an unreadable header, then a later request, all on one flow. The later request is labelled with HR-25's expected result, not excluded. On UDP, an unreadable request as its flow's first datagram, under C2 and under the stock build (the stock build is expected to raise no violation, so `true` stays there). That each unreadable form raises the analyzer violation is still `inference`: if Zeek's binpac consumes an unknown object with `&restofdata` instead of throwing, no violation is raised, `false` would be written wrongly, and only this case shows it. So `false` is never written before this case passes for every form; if a form raises no violation, `true` stays on every request and D4 brings the options to D1 before item 4's gate (15.10).
- **Not chosen:** emitting such a request as `undecoded` instead of `function`, which D2 raised on #735. It would hide a write or an operate from `unauthorized-write`, which fails open.

### 15.4 `l2.vlan`, stacked tags and `ethertype`

- **VID 0** (D2's point 4, D6's point 1, D4-117 item 3.3). In IEEE 802.1Q, VID 0 is the null VID: the tag carries priority only, and the bridge port assigns the frame to its PVID, as for an untagged frame. IEC 61850-8-1 GOOSE and 9-2 SV are often sent with VID 0 and priority 4. The decoder requires the key and sets `L2.VLAN` to nil when it is 0, so every reader and the stored form stay as they are (absent means untagged). This fixes the fail-open D6 measured at `bca57ee2` (`TestOwnConfig`'s untagged case with `ptr(0)` raises no `node-address-spoofed`).
- **`ethertype` is the type after every tag** (D3's B2, D4-117 item 3.3): after each 802.1Q (`0x8100`) or 802.1ad (`0x88a8`) tag, in any order, up to four tags (five or more, and `0x9100`, below), and after an HSR tag (`0x892f`, IEC 62439-3, whose 6-octet header comes before the inner type). That inner type decides whether `ip` is required. A PRP RCT is a trailer and moves nothing. HSR rings are not in the first protocol set: the frame stage skips the HSR tag so that IP behind it is read, and it discards no HSR duplicate (not built, as PRP's discard is not).
- **A stacked frame: which VID `l2.vlan` holds, and where the stacking is recorded** (D3's B2, D2; D4-117 item 3.3; **accepted by D1, 6955432193 item 1, D4-118 item 4**).
  - `l2.vlan` holds **the outermost tag's VID** (0 mapped to nil as above). That is the tag the switch at the observation point forwards on, and the segment the frame was seen on.
  - **The stacking is recorded in `l2.inner_vlans`**: the VIDs of the tags after the outer one, in wire order, each 0 to 4094 (0 kept here, since it is evidence), 1 to 3 entries. Present exactly when the frame carried more than one 802.1Q or 802.1ad tag; refused (`conflict`) as `[]`. An HSR tag is not a VLAN tag and is not listed. The R9 view shows a flow with `inner_vlans` as "stacked tags".
  - **An inner VID may only add a finding** (D3's B1 on `e9375d06`, D4-118 item 4). The inner VIDs are chosen by the sender, and that is how double tagging hops VLANs. So no reader of `inner_vlans` ever makes a frame count as covered, as on one of the node's segments, or as authorized, when the outer VID alone would not. **Coverage and the VLAN sets read the outer VID only:** `Detector.covers` and `Detector.see`, `coverage.vlans_seen` and `untagged_seen`, the node's VLAN sets (`newOwnConfig`), and the learner's address entries. An inner VID enters none of them.
  - **The spoofing check reads both** (D1's item 1), in this fail-closed form (D6's B1): `nodeAddressSpoofed` raises `node-address-spoofed` for a flow start from a node address whose source MAC is not the node's when **the outer VID or any inner VID** is on one of the node's segments. An outer VID that is nil (untagged, or 0 mapped to nil) matches the untagged segment, and on a stacked frame its inner VIDs are matched as well. **An inner VID of 0 is read as the untagged segment** (the fail-closed reading, D6's B1): on a frame with an inner 0 the check matches the untagged segment as well as the outer VID and the other inner VIDs. Adding inner VIDs can only make the check true where it was false, never the reverse. `explainNodeAddressSpoofed` names the outer VID and the inner VIDs, and which one matched.
  - **The other VLAN rules.** No other rule reads a VID to judge in this change; the learner and coverage read the outer VID as above. A rule that reads stacked tags for another finding is a new mechanism, settled first (D4-99), and is not proposed here.
  - **Absent `inner_vlans` narrows the spoofing check**, so a producer that leaves it out on a stacked frame fails open for that check. The QinQ GT-PCAP case (below, 15.9) is the evidence that the frame stage writes it, and its expectation is labelled so: "producer writes `inner_vlans`; without it, `node-address-spoofed` on an inner-VID frame is a miss" (D6's B1).
  - **Five or more tags: refused** (D3's N2 and B1, D6's N6 and B1; **ruled by D1, 6993015611, option (c)**). The frame stage reads at most four tags (the outer one and three inner). On a fifth, `inner_vlans` holds three VIDs and `ethertype` is the fifth tag's TPID (`0x8100` or `0x88a8`). The agent writes Zeek's records for the frame as for any frame, with the `ip` Zeek gives (whether Zeek 9.0.1 decodes IP behind five tags is not checked; the GT case measures it, 15.9), and by 15.1's `ip` rule (channel-only) the node refuses each as `conflict`, raising `sensor-record-refused` once for each new reason in a node run and counting it after, as the MPLS and PPPoE case below. The agent never drops `ip` to write a layer 2 record: no rule judges an observation without `ip` (`(*Detector).Observe` skips it, and `(*Learner).Observe` counts it only under `Undecoded`), so that form would let the sender, who chooses the tag count, turn a loud refusal into a silent stored record. **Cost, stated:** every rule is blind to the flow's records and their stored rows are lost; the refusal, its count under `conflict` and the alarm are what shows the flow. A GT-PCAP case with five tags is owed (15.9).
  - **TPID `0x9100`** (D2's N1 on `e10469ae`). `0x9100`, the pre-standard QinQ TPID, **is not a tag** for the frame stage: it is never counted in `inner_vlans` and no VID is read from it. `ethertype` is `0x9100`. Zeek's Ethernet analyzer may hand `0x9100` to its VLAN analyzer and give an `ip` (D2's recollection, not checked at 9.0.1). If Zeek gives such a record, it is refused as `conflict`, loud, and is listed with MPLS and PPPoE under "Visibility limits" below; if it gives none, the flow is silent to every rule (15.9 measures which). That is the same rule as five tags. A switch forwards a `0x9100` frame as IP only when configured for that TPID (D2).
  - **Coverage of the two refused cases** (D2's N2 on `04880a6f`). A frame with five or more tags, and a frame whose type after its tags is `0x9100`, count in coverage like any other frame, by the outer VID: `untagged_seen` when no tag comes before (or the outer VID is 0), its outer VID in `vlans_seen` otherwise. The sensor saw that segment; under 802.1Q such a frame sits on the port's PVID or on the outer VID. Refusing the frame's records, if Zeek gives any, does not remove it from coverage: the coverage statement is the frame stage's, and is carried on every observation the sensor writes, so a later accepted observation carries it to the node. Leaving it out would under-report coverage with no alarm: `Detector.covers` false silences `own-session-unseen` and turns a DNP3 `none` into `unknown` (15.2). Test in 15.9.
  - **Floor:** `inner_vlans` joins the rollback floor's tokens (15.8).
- **VID 0 in coverage** (D6's N4 on `e9375d06`). A frame whose outer VID is 0 counts as untagged: it sets `untagged_seen`, and 0 never enters `vlans_seen` (which C13 checks as 1 to 4094). Otherwise a sensor that listed 0 would have every coverage record refused, and one that did not count it as untagged would leave the untagged segment uncovered, which 15.6 then counts as blindness on a GOOSE or SV segment.
- **Visibility limits, stated** (D2's point 4, D6's point 6). What a SPAN or mirror port shows depends on the switch: the same frame may appear untagged, priority-tagged or tagged with the PVID, so a VID observed at the sensor is the mirror's view, not necessarily the sender's. Zeek also decodes IP behind other link types, such as MPLS and PPPoE (D6's recollection, not checked at 9.0.1). Unless the frame stage gives the inner type, such a flow has an `ethertype` of `0x8847` or `0x8864` with an `ip` and is refused as `conflict`: loud (`sensor-record-refused`), but its content is lost to every rule. The same holds for a frame tagged with `0x9100`, and for a frame with five or more tags (above), if Zeek gives a record for it; if Zeek gives none, the flow is silent to every rule, not refused (to be measured, 15.9).
- **GT-PCAP cases owed** (D6's list; ids from D1): untagged, VID 0, QinQ IPv4 TCP (labelled as above), and five tags IPv4 TCP (to be measured: if Zeek gives records, they carry `ip`, three `inner_vlans` and `ethertype` the fifth TPID, each refused as `conflict`), each with its expected record and coverage (15.9).

### 15.5 SNMPv3

- **`engine_id` accepts `""`** (D2's B3, D4-117 item 3.4). RFC 3414 §4 (discovery) sends a Request with a zero-length `msgAuthoritativeEngineID`, and §3.1 step 5 accepts it. C13 0.2's `engineIDForm` (5 to 32 octets) refuses the first message of every SNMPv3 session and probe. This is a C13 0.2 bug, fixed in the code change.
- **`usm_parsed`, a required boolean** (D2's B4, D6's point 11, D4-117 item 3.4). `engine_id`, `user`, `boots` and `time` are fields of one `UsmSecurityParameters` SEQUENCE (RFC 3414 §2.4), in clear at every security level, so they stand or fall together. With `usm_parsed: true` all four are required, `boots` and `time` each from 0 to 2147483647 (RFC 3414's `INTEGER (0..2147483647)`; 2147483647 boots is the latched state, §2.2.2, which is stored and shown). With `false` all four are absent and refused (`conflict`) if present. `level` comes from `msgFlags`, outside USM, and stays required.
- **The stored path** (D3's B2 on `e9375d06`). In a stored record an absent `usm_parsed` reads as `true`: every SNMPv3 record stored today carries `engine_id` and `user`. The requirement of the four fields with `true` and the bound of 2147483647 on `boots` and `time` are channel-only, so a stored record accepted today (with `boots` or `time` absent, or above the bound) is still accepted. The refusal of the four with `usm_parsed: false` runs on both paths, since it needs the new key, which no stored record carries today.
- **What the script must log to fill `engine_id` and `user`** (D4-117 item 3.4). In `log_snmp`, when `h$v3?$user_security_parameters`, two new fields beside the lengths it logs now:
  - `v3_usm_engine_id`: `bytestring_to_hexstr(AuthoritativeEngineID)`, the lowercase hex of every octet, `""` for zero length;
  - `v3_usm_user_name`: `bytestring_to_hexstr(UserName)`, so that the log carries every byte with no escaping to undo. The agent makes C13's `Text` from the bytes (`NewText`).

  The existing `v3_usm_engine_id_len` and `v3_usm_user_name_len` stay, and the agent checks that each hex field is twice its length; a mismatch writes no `encrypted` object. **Until the script logs both, the agent writes no `encrypted` object for SNMPv3** (D6's point 11): a filler such as `"0000000000"` would pass the form and store fabricated evidence. An SNMP flow without `encrypted` reads as "encryption not determined", never as encrypted. The user name is an identifier, not a secret, and is treated as hostile `Text` (D3); GT-PCAP holds test names only (D2).
- **An engine ID of 1 to 4 or over 32 octets** (D2's B3 second half; **accepted by D1, 6955432193 item 2, D4-118 item 4**). Refusing such a record loses the flow to every rule (its addresses, `unknown-pair`, `new-service`), which an attacker can choose, the same objection D6 made to the `lan` byte check. So:
  - C13 accepts `engine_id` of **0 to 32 octets**. RFC 3411's SIZE(5..32) describes a configured engine, not the wire field (D2's own reading), so 1 to 4 octets are stored as read, as evidence.
  - An engine ID over 32 octets cannot be written in C13's form without cutting it. The agent writes **`usm_parsed: false`** for that message, so the record, its flow and its `level` are accepted and judged. `usm_parsed` then means "the USM block was parsed and its engine ID is at most 32 octets"; the cost is that such an engine ID is not stored.
  - **No alert in this change** (D1's item 2). An alert on a malformed engine ID would be a new rule (C12 and the rule set), a new mechanism settled first (D4-99); none is proposed.
  - **Floor:** engine IDs of 1 to 4 octets join `engine_id: ""` among the floor's tokens (15.8).
- **Not an asset identity.** Whether the engine ID survives a firmware upgrade is unverified (D2's `C2-snmp-family.md`, S29, `documented-untested`), so nothing on the node keys asset identity on `engine_id` alone.

### 15.6 The optional keys' conditions, the Modbus sub-function and blindness

- **`insecure.login` re-emitted when a login appears** (D3's N3). A Telnet or FTP flow's first sight usually comes before its login, so without a second record `login` would be absent on most flows and D4-67's evidence that a secret went in clear would be lost. **Accepted by D1** (6955432193 item 4, D4-118 item 4): the flow's record is emitted once more when its first login is placed (`slot` becomes `placed` or `not-placed`), with `login`; `login`'s presence is in the key that record is emitted under. At most one extra record per flow. Absent `login` reads "no login seen when recorded".
- **`user` only with `slot: placed`** (D3's N4). When the slot could not be placed (an unknown prompt, a login joined midstream, a password sent before its prompt), the sensor cannot know which typed text was a user name. SEL Level 1 (`ACC`, then the password; HR-1, HR-8) has no user name at all, so a wrong prompt table would store the password as `user`, a stored `Text` that no redaction covers. `user` with any other `slot` is refused (`conflict`) on the channel only; a stored record carrying it is accepted as today (D3's B2 on `e9375d06`).
- **TLS and SNI** (D3's N5): as 15.1 states.
- **The Modbus sub-function** (D6's point 5; D4-117 item 3.6). **Open item, owner D4, before P4-4-DE:** the script reads the sub-function of codes 8 and 43, with measured cases (D6's list: 8/0 then 8/4 on one flow, a code 8 too short for its sub-function, and 43/14). Until then, the absent `sub` fails closed but costs more than noise: every 43/14 device-ID poll (a common inventory read) classes as `write` and every 8/0 as `control`, each raising `unauthorized-write` on every connection; the only way to quiet them is to authorize the poller for class `write` in `authorized_writers`, keyed by (client, server, class), which also authorizes Modbus 5, 6, 15 and 16 from it; and every code 8 on a flow shares one emission key, so an 8/4 (force listen-only) after an 8/0 gives no record. An absent `sub` also claims "too short" (0.1 §4.3), which is false while the script never reads it. So P4-4-DE does not wire Modbus before this item closes. By the Modbus Application Protocol (v1.1b3 §6.8, §6.21; `desk`, D2), 8's sub-functions include 0x0001 and 0x0004, and only 43's MEI 0x0E is a read. Which Zeek 9.0.1 event carries the sub-function is not read (D2 recalls `modbus_diagnostics_request` and `modbus_encap_interface_transport_request`, unchecked).
- **Blindness is counted** (D6's point 8; D4-117 item 3.7). Required coverage keys catch a sensor that forgets them, not one that reports itself blind (`"degraded":["interface-bound"]`, or `vlans_seen: []` with `untagged_seen: false`). Such a record becomes `d.cov` for the next judgement, and `judge` (`own.go`) drops each due session whose `covers` is false with `continue`. In the code change, the detector counts each session so dropped, and the node shows the count in status beside `PendingFull` (D5 reviews the status side).

### 15.7 `drops_driver`

**Required in every 0.2 and 0.3 heartbeat, with no condition on W-5** (D6's point 10; D4-117 item 3.5; **accepted by D1, 6955432193 item 3, D4-118 item 4**). Under option (b) the socket holder reads `tp_drops` from `PACKET_STATISTICS`, which 0.2's `drops_driver` row says it "may read ... under its call filter (SL-3)" (0.2's counter table, assumption A1). Whether that read works under the filter is the open item below, measured by 0.2's W-3; W-5 covers the first pipe and `drops_holder`, not this read, and no W-row decides C13. A sensor that cannot read the counter cannot send a valid heartbeat, and the node refuses every heartbeat as `missing`, which is loud. The first text's fallback to CH-27's form is withdrawn, so the row's contract test can be written now.

**Open item, owner D4, before P4-4-DE** (D1's item 3; 15.10): whether **the socket holder** can read the driver's drop count under its SL-3 call filter is undetermined. The reader is the holder, not the agent: under SL-3 they are separate programs, and the holder owns the socket (0.2's `drops_driver` row; D6's N3 on `e10469ae`). D4 measures it, with the pass condition and control in 15.10. If it cannot be read, D4 brings the options back to D1 before any sensor is wired; no sensor sends a heartbeat with a made-up `drops_driver`.

### 15.8 In place, and the rollback floor

- **Amended in place, no new minor** (D4-117 item 3.8), on D3's conditions in 6952389925:
  - (a) this is the last in-place change to 0.2 and 0.3: **from the first sensor build (P4-4-DE), any change to a key being required or optional, or to a closed set, is a new minor;**
  - (b) D7 adds the floor to `docs/release.md` §7.1 at the merge commit of the code change: a build below it would refuse stored records carrying the tokens below through `DecodeStored`, and the replay (`observeTo` in `platform/node/netdetector.go`) turns a refused stored observation into `nil`, counts it under `Refused` and judges nothing on it, so a rollback below the floor stops judging every retained record that carries a token, with only a count to show it (D6's point 7);
  - (c) the same change updates every producer of 0.2 or 0.3 records that the tests use: fixtures, `sensor_rig` and the GT-PCAP expectations, so no producer of the old form survives to mask the change.
- **Why in place** (D3, D6's point 7). No sensor exists, so no 0.2 or 0.3 record has been produced by one, and the channel is unwired (`channelIdentifiers` holds only 0.2 and 0.3; nothing in `cmd/` calls `sensorlink`). A new minor would leave the fail-open absences readable on 0.2 and 0.3, and would not be safer for rollback: `strictjson.Forward` would drop `objects_unread` and `dnp3_sa_unknown` without a word. At mixed versions, a new sensor and a node below the change fail closed and visibly (each refusal counts under `sensor-record-refused`). The real cost is that "0.2" names two forms a hello cannot tell apart, harmless only while no producer of the old form exists (D3).
- **The floor's tokens** (D4-117 item 3.8): `sa: unknown`, `objects_unread`, `dnp3_sa_unknown`, `usm_parsed`, `engine_id: ""`, `inner_vlans` (15.4) and engine IDs of 1 to 4 octets (15.5); the last two settled by D1's 6955432193 items 1 and 2 (D3's N3). `vlan: 0` is not a token: it is never stored (15.4).
- **What changes on the channel:** the required keys of 15.1; `sa: unknown` and the node's `dnp3_sa_unknown`; `objects_unread` and `usm_parsed`; `engine_id`'s form; `boots` and `time`'s bound; `l2.vlan` gains 0, mapped to nil; `inner_vlans`; the conflict checks on `sa: none` with `objects_unread: true`, on `login.why`, on `login.user`, on `ip` against `ethertype` and on the four USM fields.
- **What changes in the stored path:** only what reading a stored record written after the change needs. `DecodeStored` accepts the floor's tokens and keeps reading absent as this section states. **It still refuses nothing it accepts today**, because every new check on keys a stored record can carry today is channel-only (Scope; D3's B2), an absent `usm_parsed` reads as `true` (15.5), and the `sa: none` conflict needs `objects_unread` present (15.3). The stored-path checks that remain are those on the new keys and values themselves, which today's strict decode refuses already: `objects_unread: true` with `sa: none`, `usm_parsed: false` with a USM field, `inner_vlans: []`, and `dnp3_sa_unknown` on a record it does not belong to.
- **Sizes.** `unknown` is shorter than `challenged`, so the longest `sa` is unchanged. `"objects_unread":false` adds 23 octets with its comma to every DNP3 `function`; `"usm_parsed":true` adds 18 to an SNMPv3 record; `"inner_vlans":[4094,4094,4094]` adds at most 31; `"vlan":0` adds 9 on the channel and nothing stored. The coverage keys made required stay bounded by `MaxCoverageBytes` (2 KiB). In the stored form, `dnp3_sa_unknown` is 5 octets longer than `dnp3_no_sa` (D6's point 7). **D6's recount** of `TestWorstStored02Fits` and `TestWorstStored03Fits`, with the channel record's, is due before the code change merges.

### 15.10 Open items and the limit (D4-118 item 4)
