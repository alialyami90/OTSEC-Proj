## 1. Reader and rollback rules for the whole change

These extend CH-35 and CH-36. They state nothing new about how a minor is read.

### 1.1 Channel and store

- **The channel stays strict** (CH-36). A 0.3 sensor's hello is refused by a 0.2 node as `hello`, because ALPN carries the major only (§2 of 0.2).
  - A 0.3 node knows 0.2 on the channel, as CH-36 allows for a later minor, so it can drain a 0.2 sensor's buffered runs. Their records are stored at 0.2, the minor of the run's hello (CH-36).
- **One rule: an observation stored below 0.3 is not judged by CH-51** (D1's ruling 6). That covers an observation stored before the upgrade and a 0.2 run drained after it alike. Such a record carries no counts by construction, and the profiles of runs from before the upgrade are not held, so no comparison could hold.
  - **So an upgrade raises no `own-session-mismatch`** for 0.2 records, in retention or drained.
  - **A peer cannot pick a lower minor to escape the rule.** The minor of a stored record is the channel minor the node accepted (CH-36), and a 0.3 sensor offers only 0.3. Only a sensor host held by the attacker could offer 0.2, and that branch is outside this rule (AP-36; design §5 item 7).
  - **The limit, stated in item 4's gate report** (D1's ruling 6): flows stored below 0.3 are judged by the base rules only. A tied flow among them is skipped by every base rule except `node-address-spoofed` (design §0), so it stays hidden as HR-24 states. **Nothing in 0.3 bounds how long a 0.2 sensor runs behind a 0.3 node** (D3's B1): the upgrade order fixes a sequence, not a duration. The alarm below makes the state visible for as long as it lasts.
- **The node shows that the rule is off** (D3's B1 and D6's N5, option (i); round 2's mechanism 8):
  - **`network-own-session-unjudged`,** a node alarm, is raised while the node accepts a run whose minor is below 0.3 from its sensor, and cleared when that sensor's next accepted run is 0.3. It covers both cases: a 0.2 sensor in the window that the upgrade order creates on purpose, and a sensor rolled back. It writes no health event and is shown in status and the OS log, as `network-detector-not-restored` is, so §1.10's 45 an hour does not change.
  - **`detector_tied_below_minor`,** a run total of the node's detector shown in status, counts the tied flows that CH-51 skipped because their stored minor is below 0.3, drained or live. A tied flow in retention at the first start after the upgrade is counted too.
  - Neither is a §1.10 value. D5 adds both to its note's lists in the code brief, as for §1.2's `network-alert-unreadable`. No C7 or C8 change: no admin action and no audited record is added (D3's review).
  - *Test:* N-14's leg (3). *Control:* a node that skips the flows silently, which raises no alarm and counts 0.
- **Upgrade order: node first, then sensor. Rollback order: sensor first, then node.**
  - In that order the link stays up. While the sensor is still 0.2, its records are stored at 0.2 and fall under the rule above.
  - In the wrong order, the link is down (`hello`) until the node catches up, and the records wait in the sensor's buffer (CH-20).
  - D7's record of what rolls back together lists the pair and the order, and the rollback floor of §1.2.
- **The store reads forward** (`DecodeStored`, `strictjson.Forward` in `contracts/netobs/observation.go`). So a 0.2 node reads a 0.3 stored `flow` `end` with the new fields ignored, and a 0.3 node reads a 0.2 stored record strictly, with the fields absent.
- **Absent, `0` and `false` stay distinct through the node's tie path** (D5's B4). `Link.record` (`platform/sensorlink/link.go`) ties a held record by `json.Unmarshal` into `netobs.Observation` and `json.Marshal` back, and every tied flow passes through it. So every field of CH-52 to CH-55 is, in the Go type, a pointer or an equivalent that keeps absent, `0` and `false` apart through that re-encode. With a plain `uint64` and no `omitempty`, an absent count would be stored as 0 and read as a complete zero (a miss); with `omitempty`, a true 0 would be stored as absent (an alert on every clean own run). *Test:* N-8's leg (2), through `Link.record`. *Control:* the same field as a non-pointer `uint64`.

### 1.2 Stored alerts and the detector's checkpoint after a rollback

- **What `main` does, read from the code.** At a restore, `alertsAfter` (`platform/node/netdetector.go`) decodes every alert after the checkpoint's `last_alert_seq` with `AlertFromEvent`. Any error fails the restore. The node then raises `network-detector-not-restored` and starts its detector from the oldest retained observation (the restore path in the same file). `AlertFromEvent` has no other caller outside tests. The forwarder sends the C4 `netobs.alert` event as it sends any health event, and never parses `rule`.
- **The design's sentence was wrong for `main`,** and this commit corrects it in design §7.1 item 1. It said that a rolled-back node "refuses those stored alerts on read, counts each under the refusal count, and loses none from the store". On `main`, nothing counts a refused stored alert, and one unreadable alert after `last_alert_seq` fails the whole restore.
- **Required: skip, count, alarm** (D1's ruling 2, a requirement of the brief "The approved contracts in code"; D1 records it when it approves 0.3). In `alertsAfter`, a stored alert that `event.Decode` or `AlertFromEvent` cannot read (D5's N1: `alertsAfter` returns on an `event.Decode` error before `AlertFromEvent` is reached, so both are named):
  - **is skipped,** and the restore goes on with the alerts it can read. The alert stays in the store, which is append-only, so a later upgrade reads it again;
  - **is counted** under `detector_alerts_unreadable`, a run total of the node's detector, shown in status;
  - **raises `network-alert-unreadable`**, with the count in its text. It is raised at the restore that skipped one, and cleared at the next restore that skips none. It writes no health event, and is shown in status and the OS log only, as `network-detector-not-restored` is (D5's N1). So `D5-sensor-node.md` §1.9 item 5's pool list and §1.10's 45 an hour stay as they are.
  - **What the skip costs:** the restore holds back only the alerts it read (D4-74). If the replay raises a skipped alert's condition again, it is stored a second time. That is a duplicate, and it fails loud, never silent.
  - D5 adds the count and the alarm to its note's lists in the code brief. They are not §1.10 values.
- **What a node rolled back from 0.3 to 0.2 does:**
  - Its detector checkpoint is `otsec.netcheckpoint/0.3`, a later minor. The 0.2 node must read it as CH-35's bridge build does (D5 §1.15 item 1): recognise any `otsec.netcheckpoint/0.x` detector document, raise `network-detector-not-restored` for a minor it cannot read, start from the oldest retained observation, and remove the document once its own first checkpoint commits.
  - It raises the retained observations' alerts again, as CH-35 states for the 0.1 rollback.
  - It judges no tied flow by CH-51, so HR-24 is again "hidden whole" for as long as the rollback lasts.
  - **The `own-session-mismatch` alerts stay in the store,** which is append-only. A later upgrade reads them again.
- **Requirement on the 0.2 code** (D1's ruling 2; not yet built, brief "The approved contracts in code"): the 0.2 detector's checkpoint reader keeps bridge items 1 and 2 of CH-35 for a later minor. **Without it,** a rollback from 0.3 gets the silent restart that CH-35 describes for 0.1: `main`'s exact match on `CheckpointIdentifier` in `detectorCheckpoints` skips the 0.3 document, and the node gives no alarm, stores duplicate alerts and leaves an orphaned document.
- **The 0.2 code also keeps CH-35's bridge item 5 for a later minor** (D5's N2 on this PR, under round 2's mechanism 8): it ties a held record of a later minor by patching the raw JSON, never through `Link.record`'s re-encode into its own type. Under the stated rollback order the sensor goes first, so the 0.3 node's intake hold (`netcheckpoint.intake`) can still hold raw 0.3 bodies when the node rolls back. Re-encoded into 0.2's type, such a body would keep `schema` at 0.3 and lose CH-52 to CH-55's fields for good, and a later upgrade would judge it with the counts missing. *Test:* N-13's leg (4). *Control:* a 0.2 tie that re-encodes, which stores a 0.3 record without its counts.
- **The rollback floor** (D3's N3). A 0.3 node may be rolled back only to a 0.2 build that carries all three requirements above: the bridge reader of CH-35 items 1 and 2 for a later minor, bridge item 5 for a later minor, and skip, count and alarm in `alertsAfter`. A rollback to the 0.2 code now on `main` gets a restore failed whole by one `own-session-mismatch` alert, or the silent restart above. D7's record of what rolls back together names that build as the floor.
- **A 0.2 checkpoint with a 0.3 alert after it.** A node rolled back to 0.2 may also hold a 0.2 checkpoint, written before the upgrade, with `own-session-mismatch` alerts after its `last_alert_seq`. Skip, count, alarm applies there, so that checkpoint still restores.
- **The upgrade direction** (D5's B2). **A 0.3 node reads the 0.2 detector checkpoint it finds at the upgrade,** strictly and with no alarm, as CH-35 has 0.2 read 0.1 ("Read"). Its restore then goes on as for its own checkpoint, and a session open at that checkpoint is judged as the node-restart rule below states. *Test:* N-13's leg (3). *Control:* an exact match on the 0.3 identifier, which skips the 0.2 document and restarts silently.
- **0.3 code always writes `otsec.netcheckpoint/0.3`** (D5's B2, pinned). It never writes 0.2, even while it holds no state that 0.2 cannot read, so that one identifier is never written by two binaries. The learner's half takes the same identifier (0.1 §8), and its form does not change.
- **A session open across a node restart is judged unjudged** (D5's B3, option (b); round 2's mechanism 9). The detector checkpoint keeps its form and holds no running sums, so C5 does not change (P8). At a restore, the detector holds no deltas from tied records at or before the checkpoint's `through`. So a tied session that is pending at the checkpoint (tied and not yet judged, 0.1 §8) is judged at its end with every comparison that reads an `end` count listed as `unjudged … :incomplete` (CH-51), never against the partial sum. It fails toward alerting: the cost is one alert for each tied session open across a node start. *Test:* N-17. *Control:* a detector that judges the partial sum, which raises nothing on a run whose excess was in the part before `through`.

### 1.3 Sizes

- **A `flow` `end`** gains at most 278 octets (recounted in round 2): seven numeric keys, each with a 19-digit value, the most that the range 0 to 2^63 − 1 stated for each count in CH-52 to CH-55 allows (`orig_payload` 34, `resp_payload` 34, `orig_pkts` 31, `resp_pkts` 31, `rexmit_inconsistent` 41, `to_device_overlap_octets` 46, `password_lines` 36: 253), plus `"incomplete":true` (17), plus eight commas (8). That counts all eight keys, although `password_lines` and `incomplete` never sit on one record (CH-55), so a record that the node accepts gains at most 260.
  - This is far below `MaxNetobsBytes` (24 KiB), and a `flow` record is not the worst stored body.
  - The worst-body pin (CH-35, R-1 to R-6) is rerun with the new fields on every `end` (N-12).
- **An alert's `observation`** stays within `ExplainMax` (256). The longest head the grammar admits (CH-51) is 177 octets, so `": "` and at least 77 octets of free text always fit; the free text is cut to fit and the head never is. The longest head one judgement writes is 95 octets (Telnet). A summary's union of Telnet hits writes at most 120, and one that mixes Telnet and SNMPv3 hits can reach 177, which still fits (CH-51).
- **No new member enters `counters`, so none enters `sensor.counters`** (CH-53). `overlap_table_full` is in the new `frame_stage` object, and the agent's two new counts are in `agent` (CH-43). The heartbeat grows by at most 57 octets for `frame_stage` and 82 for the two agent counts. Heartbeats are never stored. So C4 0.4 and the health events' caps do not change.

### 1.4 A Telnet result without `session.telnet`

C2 0.10 (D2's proposal, #671) refuses a Telnet result without `session.telnet`, so such a result comes only from a 0.9 collector. The run's profile is then held but partial: it has no `refusals`, `command_octets_received`, `read_to_eof` or `rexmit_octets`. That is not design §3.2's case of no profile held, in which the base rules judge a tied flow as if untied. For a flow tied to such a run (D4's N2 on #671, 6862377718), the detector:
- lists `M6b:no-profile` under `unjudged` (CH-51), as for `rexmit_octets` `unknown` (design §3.1), so the flow alerts;
- judges M1 and M5 as usual;
- judges M3 to the relay with the 194-octet tolerance of design §5 item 3 (no `refusals`);
- leaves M3 from the relay unjudged, since `read_to_eof` is not known. That is design §5 item 4's residual, which raises no alert, so it is in neither list of the head (CH-51).

Both this rule and the untied reading fail closed. This one keeps M1, M3 to the relay and M5. *Test:* N-15.

## 2. CH-51. The rule `own-session-mismatch`

- **The token.** `own-session-mismatch` joins `Rules` (`contracts/netobs/alert.go`), which is a closed set. The new token is the reason this change is a minor.
- **The rule runs before any baseline is acknowledged.** It is in `BaselineFree`, like the other own-session rules (D4-68 ruling 10), because a tied flow skips every base rule (design §0).
- **Parameters: none** (D1's ruling 5). The rule's bounds come from each run's profile, and the text states the excess over them.
  - **Only M4 uses a setting.** Its bound adds 2*g*, where *g* is `tie_grace_s`, the baseline parameter that `own-session-outside-record` and `own-session-unseen` show. It also adds `max_skew_ms`, which is fixed at 2,000 ms in CH-22 and is not a setting.
  - **M4 is not judged for Telnet** (design §3), so `tie_grace_s` would describe only SNMPv3's M4 alerts. The excess that M4 states is computed with it already.
  - Neither value is in `coverage.settings`, which holds `sa_reply_timeout_ms`, `max_pending_dnp3` and `flow_idle_s` (`contracts/netobs/citation.go`), and from 0.2 `prp_window_ms` (CH-28).
- **The fixed head of `observation`: two lists** (D6's B1, option (a); round 2's mechanism 1). One list names what the flow exceeded, the other what could not be judged and failed closed, so no reason is left unattached:

  ```
  observation := head [ ": " free-text ]       the whole string matches this production
  head        := part ( " " part )*            at least one part; parts in the order below, each at most once
  part        := comparisons | unjudged | reasons | "no-profile"
  comparisons := "comparison" ( " " C )+       C in M1 M2 M3 M4 M5 M6a M6b, each at most once, in that order
  unjudged    := "unjudged" ( " " U )+         U in M2:incomplete M3:incomplete M5:incomplete M6a:incomplete
                                                    M6b:incomplete M6b:no-profile, each at most once, in that order
  reasons     := "reason" ( " " R )+           R in prp-table-full prp-mismatched, each at most once, in that order
  ```

  - **`comparison`** names only the comparisons the flow exceeded.
  - **`unjudged`** names each comparison that was not judged and fails closed, with its cause. The causes, and the program that sees each, are CH-53's table; `M6b:no-profile` is the collector's side (`rexmit_octets` `unknown`, or a 0.9 result, §1.4). **A comparison left out by design is in neither list,** because it raises no alert: M4 for Telnet, M3 from the relay without `read_to_eof` or with a restart or an `idle` cut in its stretch, and M6b on a stretch where a PRP count rose (design §4, §5 items 4 to 6). M1 and M4 read starts and times, not `end` counts, so they are judged on what was seen and never listed as unjudged.
  - **`reason`** keeps only the states that changed a bound the flow was judged against: R is written when R rose in the flow's stretch (design §4) and the flow was judged on a comparison whose bound R changes, which is SNMPv3's M2 or M3 (the doubled bound). A Telnet flow therefore never carries a reason.
  - **`no-profile`** alone is the one fixed phrase for a tied flow with no profile held (design §3.2), which the base rules judge as if untied.
  - **A judgement never lists one comparison in both `comparison` and `unjudged`.** The grammar allows it, because a summary's head is a union (below).
  - **Examples:** `comparison M3 M6b: …`; `unjudged M6b:no-profile`; `unjudged M5:incomplete M6b:incomplete: …`; `comparison M5 unjudged M6b:incomplete`; `comparison M2 reason prp-table-full: …`; `no-profile: …`. D6's pair of B1 is now told apart: two placed password lines on a run whose `rexmit_octets` is `unknown` write `comparison M5 unjudged M6b:no-profile`, and an unplaced slot with a complete overlap count and no excess writes `unjudged M5:incomplete`. (A record with `incomplete` carries no `password_lines`, CH-55, so it writes `unjudged M5:incomplete M6b:incomplete`.)
  - **`Alert.Validate` refuses** an `own-session-mismatch` alert whose whole `observation` does not match the production (D6's N1): the head, then either the string's end or `": "` and free text. So `comparison M3 M3`, `comparison M6b M3`, `comparison M3x`, a cause not in U's set, `reason` before `unjudged`, and a missing head are refused, although each starts with a valid head.
  - **The free text is cut to fit `ExplainMax`, and the head is never cut** (D6's N2). The detector cuts the free text, at a UTF-8 boundary, so that the whole `observation` is at most 256 octets. The longest head the grammar admits is 177 octets (all seven comparisons, all six unjudged items, both reasons and `no-profile`), so a head always fits with `": "` and 77 octets of free text. One judgement writes at most 95 (`comparison M1 unjudged M3:incomplete M5:incomplete M6a:incomplete M6b:incomplete M6b:no-profile`), and a summary's union of Telnet hits at most 120 (Telnet: `comparison M1 M3 M5 M6a M6b unjudged M3:incomplete M5:incomplete M6a:incomplete M6b:incomplete M6b:no-profile no-profile`). A window of one asset that mixes Telnet and SNMPv3 hits can reach the grammar's 177, which still fits. On `main`, an alert whose `Health()` fails is not built (`commitAlerts`), so without the cut an alert stating several excesses with two IPv6 endpoints would be lost. *Test:* N-3. *Control:* a detector that writes every excess in full, whose alert is then not built.
  - **A summary's head is the union of the heads of the window's hits** (D6's N8, fixed): each part is the union of that part over the hits, in the fixed order. The free text is the latest hit's, cut to fit. So a spoofed judgement followed in one window by a designed fail-closed hit keeps both heads' items. Design §3.2's "a later hit overwrites a window's `Observation`" now holds for the free text only. *Test:* N-2's leg (3). *Control:* a summary that keeps the latest head, which drops the earlier hit's `comparison`.
  - Every other rule's text is unchanged.
- **The text states only the excess, never the run's own totals** (design §3.2; §7 below). It says what was seen and never says "spoofed" (D4-68 ruling 10).
- **What an earlier reader does:** a 0.2 `Alert.Validate` fails it as `form` ("is not a rule"). §1.2 gives the consequence. A C6 or upstream reader gets the token as text in the forwarded health event and parses no `Rules`. C4 does not change.
- **When a tied flow is judged with its `end` lost** (D6's B2 and D5's N1 on #677; round 2's mechanism 3). Each tied key that the hold's open table drops at a new sensor run, and each held flow that the hold marks `EndLost` (a new run or degraded coverage; `giveWay` in `platform/sensorlink/hold.go`), is judged then, with every comparison that reads an `end` count listed under `unjudged` with the cause `incomplete`: `M3 M5 M6a M6b` for Telnet, `M2 M3` for SNMPv3. M1 and M4 are judged on what was seen. A tied key whose open-flow entry expires with no `end` (design §3.2's second path) is judged the same way. The node is the only program that sees this cause (CH-53's table). *Test:* N-16. *Control:* a detector that judges only on an `end`, which never judges such a flow.
- **What a rollback costs:** §1.2.
- **Test:** N-1, N-2, N-3, N-13, N-16.

## 3. CH-52. Payload and packets per direction on a `flow` `end`

- **Fields.** On every `flow` `end` whose `l4` is `tcp` or `udp`, a 0.3 channel record carries:
  - `orig_payload` and `resp_payload`, the payload octets each end sent;
  - `orig_pkts` and `resp_pkts`, the packets each end sent.

  Each is a decimal integer from 0 to 2^63 − 1. In the Go type the fields are optional, and keep absent and 0 apart through the tie path (§1.1, D5's B4). They are required in a 0.3 channel record, and may be absent in a stored record of any minor (CH-35's pattern). They are never on a `start`, and never on a layer-2 or other `l4` record.
- **`orig` is the record's `ip.src` end, and `resp` its `ip.dst` end.** `src` is as C13 defines it: for `client-server`, the end that sent the SYN; for `direction: none` and `midstream`, the sender of the first frame (CH-49).
  - **The link agent maps the engine's ends to the record's.** Zeek's "originator" can differ from C13's `src`. Its heuristic flips a connection's direction (the `^` in `history`, `base/protocols/conn/main.zeek` at `v9.0.1`). Where Zeek's originator is the record's `dst`, the agent swaps each `orig_`/`resp_` pair.
  - **A reader never takes `orig` to mean "to the device".** The detector finds the direction to the device by the run's endpoint, the device's address and port (design §3).
- **`orig_payload` and `resp_payload`** (design §7.1 item 2 (a); the engine computes them already, design §2):
  - **TCP:** the sequence span each end sent. That is Zeek's `orig_bytes` and `resp_bytes` (`c$orig$size`, `TCP_Endpoint::Size()`): without the SYN and the FIN octet, unwrapped over 64 bits, from the first sequence number seen on a midstream join.
  - **UDP:** the sum of the payload lengths each end sent (`UDPSessionAdapter.cc`).
  - **What does not count:** retransmissions, keep-alives (`snd.nxt` − 1, at most one octet), zero-window probes, the PRP RCT, VLAN tags and padding.
  - **What inflates it:** a segment far ahead in sequence, and an ACK beyond the data sent. Both are noisy and hide nothing (design §7.1).
  - **Holes:** a hole inside the span is counted, so loss cannot make the span smaller than what was sent. Zeek's `missed_bytes` shows the holes and is not carried.
- **`orig_pkts` and `resp_pkts`:** Zeek's `orig_pkts` and `resp_pkts` from its conn-size analyzer, counted after the PRP discard, which the frame stage makes before the engine (SL-3; E-D4-02). Whether a fragmented datagram counts once, after reassembly, is a stage 2 check (design §2). Until it is measured, the detector judges SNMPv3 datagrams on these fields only as the design's §3 M2 states.
- **Deltas.** Each `end` carries the counts since the previous `end` of the same connection, and a checker sums `end` records by key, as for `packets` and `bytes` (0.1 §4.3).
  - **For UDP, and for the packet counts, the sum is the total.**
  - **For TCP's payload fields the sum can exceed what was sent, at the start of each later portion** (D6's N3). After an `idle` cut or a sensor restart the engine opens a new connection and starts its span at the first segment it sees (the partial-connection branch of `init_endpoint`, `InitStartSeq(first_seg_seq - 1)`, Zeek `v9.0.1`). If that segment is a retransmission or a keep-alive (`snd.nxt` − 1), the two portions' spans overlap by up to that segment's length. It never makes the sum smaller, so it gives noise and never a miss. The detector's allowance is design §4's: to the relay, the run's longest approved line + 2 for each `idle` cut or restart in the stretch; from the relay, a flow with either in its stretch is not judged. *Test:* N-6's leg (4) and an own-run cell (design §6.6). *Control:* a bound without the per-cut allowance, which alerts on the own run whose later portion starts with a retransmission.
- **Checks the node makes:** each value lies in its range. On a TCP `end` with `syn_only: true`, both payload fields are 0, because a syn-only flow carries no payload (0.1 §4.3). The node makes no check that ties these counts to `packets` or `bytes`. Those count frames after the discard with link-layer octets, and the two are not equal in general (design §4, the RCT and fragments).
- **What an earlier reader does:** §1.1.
- **What a rollback costs:** the detector loses M2 and M3 with the rule (§1.2). The stored fields stay.
- **Test:** N-4, N-5, N-6 (legs (1), (3) and (4)), N-12, and N-16 and N-17, which judge the sums of these counts with an `end` missing or across a node restart.

## 4. CH-53. The overlap count, `incomplete`, and the frame stage's and agent's counts

These are design §3.3, adopted by D1 (6854297364, and the conditions of D3 and D6 on `7f9e9953`), as contract text, with round 2's mechanisms 2 and 4 to 7. The frame stage computes them and the link agent joins them (D3's SL-3 change, #677, which follows this clause).

- **`to_device_overlap_octets`** (named by its direction, D6's N4; `orig_overlap_octets` at `e7ec8ecd`) is on a TCP `flow` `end` that a frame-stage record joined. Its value is the sum, over the record's portion, of each segment's payload octets that lie at or below the highest sequence end seen in that direction before the segment. It is a decimal integer from 0 to 2^63 − 1. It counts the direction from the node's address to the listed endpoint, **whichever end is the record's `src`.** A portion that starts with the relay's frame (after an `idle` cut or a sensor restart) is `midstream` with the relay as `src` (CH-49), and its `orig_payload` is then the relay's octets; the overlap count still counts the node's direction, as its name says.
  - **A segment that starts exactly at the highest end adds nothing.** One that starts one octet below it adds one.
  - **The only exclusion:** a one-octet segment that starts at the highest end − 1 (a keep-alive). Every other short segment counts.
  - **Sequence numbers are unwrapped to 64 bits** from the first one seen.
  - **Payload length** is the IPv4 total length less its header, options included, or the IPv6 payload length less any extension headers, less the TCP data offset.
  - **It is a delta since the previous `end` of the connection,** as in CH-52. The frame stage keeps the entry across an `idle` cut, so the highest end carries over and the portions' counts do not overlap.
  - **The direction from the device is not counted.**
- **`incomplete`**, present only as `true`, on a TCP `flow` `end`. It means only that the overlap count for that record, and with it `password_lines` (CH-55), cannot be read as complete. It says nothing about the flow's other fields.
- **The agent marks every TCP `end` that no record joined** (D6's B2, option (b); round 2's mechanism 2). It sets `incomplete: true` on each such `end`, whatever its endpoints. The agent does not read the frame stage's lists. So a TCP `end` carries either a joined record's fields or `incomplete: true` with no count; no TCP `end` carries neither. A tied flow to an endpoint not on the lists therefore alerts with `unjudged M5:incomplete M6b:incomplete`. That fails closed, and the operator lists the endpoint. `no-profile` is the collector's side only (CH-51). The cost is 17 octets on every TCP `end` the frame stage does not track (§1.3).
- **Each cause of a missing or partial count, and the program that sees it:**

  | Cause | Seen by | What it gives |
  | --- | --- | --- |
  | The frame stage refused the entry, its table full | Frame stage (counts `overlap_table_full`); agent (no record joins) | `incomplete` on the `end`, by the agent |
  | No entry: the handshake was not seen whole (a midstream join, a sensor restart, one-direction capture, a lost handshake frame), or the flow is not from a listed node address to a listed endpoint | Agent (no record joins) | `incomplete`, by the agent |
  | A header in the flow was malformed (lengths inconsistent with each other or with the frame) | Frame stage | `incomplete` in its record |
  | An IP fragment on a tracked flow (D6's B3) | Frame stage | `incomplete` in its record |
  | The agent refused the record at `MaxOverlapJoinPending` (mechanism 4) | Agent (counts `overlap_join_refused`) | `incomplete` on the `end` it would have joined |
  | A record that matched no `end` and left the buffer (mechanism 5) | Agent (counts `overlap_unjoined`) | `incomplete` on the `end` whose span held it, if one came |
  | Two records inside one engine `end`'s span: an entry freed or begun inside one engine flow (design §3.3, D6's B1 on #664) | Agent | `incomplete` on that `end` |
  | A run portion with a `start` and no `end` (an unclean sensor stop, a lost `end`, the open table dropped at a new run, `EndLost`) | Node only | `unjudged … :incomplete` (CH-51, mechanism 3) |
  | A tied session open across a node restart | Node only | `unjudged … :incomplete` (§1.2, mechanism 9) |
  | The record's minor is below 0.3 | Node only | Not judged; `network-own-session-unjudged` and `detector_tied_below_minor` (§1.1, mechanism 8) |
  | `rexmit_octets` `unknown`, or a 0.9 result | Collector | `unjudged M6b:no-profile` (CH-51, §1.4) |

- **IP fragments** (D6's B3). The frame stage does not reassemble. A fragment on a tracked flow marks that flow's record `incomplete`: an IPv4 frame with MF set or a non-zero fragment offset, or an IPv6 frame with a Fragment header. A fragment whose TCP ports the frame stage can read marks its own entry. A fragment whose ports it cannot read (a later fragment, or a first one too short to hold them) marks every tracked entry between its two IP addresses, in either direction. Without this, a substitute injected as a first fragment holding only the TCP header and a second holding the N octets would count 0 at the frame stage while the relay and the engine reassemble it, and in the ACK-first order nothing would alert. The same rule covers overlapping fragments, where the relay's reassembly and the engine's could differ. Own runs should not meet it, because Windows sets DF on TCP; that is inference, and a stage 2 own-run cell checks it (design §6.6). Reassembly in the frame stage was the alternative, and it is not taken: it would put more code in the program that parses hostile frames. *Test:* N-10's fragment leg. *Control:* a frame stage that reads a first fragment's lengths as the segment's, which counts 0 and lets the substitution pass.
- **Bad TCP checksums** (D6's N7). The frame stage reads no payload byte (§10), so it cannot verify a TCP checksum. A segment that the relay discards for its checksum still counts in the overlap. So anyone on the segment who sees the sequence numbers can raise `comparison M6b` on own runs at will, with no effect on the device. That is noise, never a miss, and it is stated as a known false-positive source an attacker can cause (design §4). A stage 2 cell measures it.
- **Which flows are tracked.** The frame stage creates an entry only for a TCP flow that meets all three of these:
  - its source is one of the node's addresses;
  - its destination is a listed collector endpoint, a relay's address and Telnet port;
  - the frame stage saw the handshake complete: the node's SYN, the relay's SYN-ACK, and an ACK of that ISN + 1.

  **Both lists are sensor configuration,** set at commissioning and kept in a configuration file the frame stage reads at its start. CH-32's `file <path> sha256:<hex>` line covers "every configuration file any of the four reads at start", so the lists are in `config_digest` through that file's line. CH-32's closed lines do not change: its `setting <name> <decimal>` list of eight scalars cannot hold a list of addresses, and none is added. A change in either list therefore shows as `sensor-coverage-mismatch`, with CH-32's limit that the digest is the sensor's own word (AP-36).
- **How a reader takes the two fields.** The overlap count is complete only when `to_device_overlap_octets` is present and `incomplete` is absent.
  - **A count with `incomplete: true`** is a partial count. No reader takes it as complete.
  - **A missing count never reads as zero.** A tied Telnet flow without a complete count on any portion lists `M6b:incomplete` under `unjudged` (CH-51), and alerts. A record with `incomplete` carries no `password_lines` (CH-55), so it also lists `M5:incomplete`: the head is `unjudged M5:incomplete M6b:incomplete`.
  - **The node refuses** `incomplete: false`, and either field on a UDP record, on any `start`, or on a non-IP record.
- **The record's start is the portion's start** (D4's N1 on #677). The frame-stage record carries the kernel's receive timestamp of the portion's first frame: for the first portion the SYN's, which the frame stage holds from before the entry exists; after an `idle` cut, the first frame after the cut, which is the frame whose time opens the engine's next connection. A record that carried the flow's first time on every portion would join no `end` after the first `idle` cut, and every own run held past `flow_idle_s` would alert.
  - **Precision.** The record carries the start at the precision of the engine's pipe, which SL-3 names: the value the frame stage wrote into that frame's pipe record. The agent rounds the engine's time (a double, about 0.24 µs of resolution at today's epoch) to that precision before it compares. At microsecond precision the rounding recovers the written value exactly, since the double's error is under half a microsecond (desk reasoning). At nanosecond precision it does not, and the match needs a stated tolerance of at least 0.5 µs. Stage 2 pins the rule, exact or with its tolerance, in SL-3's text and the rig's cases (§8).
- **The order of a record and its `end`** (D4's N2 on #677, D5's N2 there; round 2's mechanism 7). SL-3 states the sensor's side:
  - the frame stage writes a portion's record before it forwards the frame that closes the portion (for an `idle` cut, the first frame past it), or the end of input;
  - it writes a counters record before each overlap record, and at least once per `SensorTickInterval`;
  - `idle` cuts are taken on frame time, as the engine's are;
  - the agent drains the frame stage's pipe, until a read would block, before it handles each engine line.

  So an `end` never waits for its record: the record is read before the engine can write the `end`. An `end` with no joined record after the drain is marked `incomplete` at once (mechanism 2). **No bound on held `end`s is needed,** because the agent holds none (D6's B2, "under both options", third item).
- **How a pending record leaves the agent's buffer** (D3's N1, second half; D5's B1 on #677; round 2's mechanism 5). A record leaves:
  - when an engine `end` of its key arrives whose span holds the record's start. It joins that `end` when it matches by key and start (above); otherwise it leaves unjoined, and that `end` is `incomplete`;
  - or when it has waited longer than 2 × `flow_idle_s` plus the engine's delay bound, measured on frame time. The engine's delay bound is the larger of `tcp_close_delay` and `tcp_reset_delay` as the project's script sets them (5 s each by default at `v9.0.1`); SL-3 states the values the script sets. Frame time is used because the engine's `end`s advance only with frames, so a wall-clock bound would expire records whose `end` is still due.

  Each record that leaves unjoined is counted under `overlap_unjoined` in the agent's object (CH-43). Without this rule a slow leak of records that never join would reach `MaxOverlapJoinPending` with no attacker at all.
- **The counts, and where they sit** (D5's B1, option (i); round 2's mechanisms 4 and 6). None is a member of `counters`, so none is mapped to `sensor.counters`, and C4 0.4 stays closed and unchanged:
  - **`overlap_table_full`,** in a new heartbeat object `"frame_stage": { "overlap_table_full": <uint64> }`, from the frame stage. It counts the entries the frame stage refused because its table held `MaxOverlapFlows` entries. A new entry is refused and never evicts a live one.
  - **`overlap_join_refused`** and **`overlap_unjoined`,** two new keys of the `agent` object (CH-43).
  - Each is required in a 0.3 heartbeat, with every key present, and is a run total that never decreases (`Follows`). The node shows the latest values in status. The alerts they cause (`unjudged … :incomplete`) make the exhaustion visible per flow.
  - *Test:* N-9. *Control:* a heartbeat decoder that accepts `frame_stage` or either agent key absent, and a node that writes `diff.overlap_table_full`, which C4 0.4's closed set refuses.
- **`MaxOverlapFlows` = 4,096 entries,** a fixed sensor bound for §12 of 0.2, about 80 octets each. An entry is freed:
  - when its flow ends (`fin` both ways, or `rst`);
  - after 2 × `flow_idle_s` with no frame;
  - after `MaxConnectTimeoutMS` (30 s) if its flow has carried no payload.

  An `idle` cut writes the record and keeps the entry (design §3.3). So `MaxOverlapFlows` bounds the frame stage's table only. It does not bound how many records the stage writes, since one entry writes a record at each portion's end.
- **`MaxOverlapJoinPending` = 8,192 records,** the most the link agent holds read and not yet joined to an engine `end` (SL-3, "How the agent reads it", in D3's #677). It is twice `MaxOverlapFlows`: one record pending for each entry, plus one for an entry freed and made again on the same key while its old record still waits for the engine's `end`. That value is reasoned, not measured. The records are fixed-size, so the buffer is bounded in octets as well. **At the bound the agent refuses the newest record and counts it under `overlap_join_refused`** (D3's N1, backed by D5; round 2's mechanism 4). The stream does not end, so no run restarts and no other flow loses capture. The `end` that the refused record would have joined has no record and reads `incomplete` (mechanism 2). A count is never dropped unseen. It is a sensor bound for §12 of 0.2, beside `MaxOverlapFlows`, and not a §1.10 value. Whether 8,192 is ever reached by own runs is a stage 2 cell. *Test:* SL-T25 (c) on #677 for the agent; N-8's leg (3) for the node's reading. *Control:* an agent that ends the stream at the bound, which restarts the run.
- **What it reads:** the TCP `seq`, the IP and TCP lengths and data offset, the IP fragment fields, the flags and the direction. It reads no payload byte (§10).
- **What an earlier reader does:** §1.1. A 0.2 node never meets the heartbeat's new keys, because the channel is strict.
- **What a rollback costs:** M6b goes with the rule (§1.2).
- **Test:** N-6 (leg (3)), N-7, N-8, N-9, N-10, N-14, and N-16 and N-17 for the two causes only the node sees.

## 5. CH-54. `rexmit_inconsistent`

- **The field.** A count on every TCP `flow` `end`, a decimal integer from 0 to 2^63 − 1, required in a 0.3 channel record. It counts the engine's `rexmit_inconsistency` events on the connection, as a delta since the previous `end`.
- **Why it has no direction** (D1's ruling 1). Design §3.1 says the project's script "would count the event per direction". Zeek's event cannot support that. Its signature at `v9.0.1` is `rexmit_inconsistency(c: connection, t1: string, t2: string, tcp_flags: string)` (`src/event.bif`). `TCP_Reassembler::Overlap` knows `IsOrig()` but does not pass it (`TCP_Reassembler.cc`). So the script cannot attribute an event to a direction from the event alone, and the count covers both directions.
  - **The cost of this is noise, never a miss.** An inconsistent retransmission from the relay also gives `comparison M6a`, and the alert's text says the direction was not known.
  - **How often a relay's retransmissions differ in content is `unknown`.** It is a stage 2 own-run cell, labelled as a known false-positive source until measured. If the noise it adds is not zero, item 4's gate report names it (D1's ruling 1).
- **The handler.** The project's handler counts the event and discards `t1` and `t2`. They are never logged, stored or forwarded, and `policy/protocols/conn/weirds.zeek` is never loaded (D1's ruling 1, 6854205907; design §3.1, stage 3's three checks).
- **What an earlier reader does:** §1.1.
- **What a rollback costs:** M6a goes with the rule.
- **Test:** N-4, N-11.

## 6. CH-55. `password_lines`, M5's input, and `login.attempts`

Point 3 is settled as **(B)**, with D6's conditions (B-i) to (B-iii) (D1's ruling 6879608207; all three reviewers chose (B)). (A), emitting the `insecure` observation at the portion's end, is not taken: besides R6.4's latency on a held session, it could lose the login frames it cites from the ring (`ring_bytes` may be 0, CH-32), it would need a new bounded wait table with no natural bound, and it would move every Telnet login's observation, not only own runs' (D3, D5, D6).

- **The field (B-ii).** `password_lines`, a decimal integer from 0 to 2^63 − 1, on a TCP `flow` `end`. It is the number of password lines the client sent in the record's portion. A password line is the client's line in a credential slot that follows a password prompt (0.1 §3.2's Telnet slot).
  - Prompts the server sent and the client did not answer are not counted. After a wrong password a SEL-751 prompts up to three times, and the adapter sends nothing more (S22 p. 7.33).
  - A server's echo is not a client line.
  - **It follows CH-52:** a delta since the previous `end` of the connection, summed by key; optional in the Go type, keeping absent and 0 apart (§1.1); never on a `start`, a UDP or a non-IP record.
  - **It is carried only on the flows that CH-53 tracks,** because the frame stage is the program that places the slots. It travels in SL-3's overlap record and uses its join (D3 adds it on #677). It is never required: its absence has a meaning (below).
- **It says whether it is exact (B-i).** `password_lines` is present only when the frame stage placed every credential slot in the portion and the record is not `incomplete`. It is absent when any frame of the portion carried a `slot-not-placed` redaction on the client's side (0.1 §3.2: for example a password sent before its prompt, or a login at an unknown prompt), or when the record carries `incomplete` (CH-53), or when no record joined. **The node refuses** `password_lines` beside `incomplete: true`.
  - **On a tied Telnet flow, an absent count on any portion means M5 was not judged.** The flow lists `M5:incomplete` under `unjudged` (CH-51) and alerts. An absent count never reads as 0.
  - This closes the case D6 and D3 found in (B) as first worded: `slot` on the `insecure` record describes only the login at its emission, so a later login whose slot could not be placed would otherwise give a short count read as exact, a miss for p ≤ 4 (design §5 item 3).
- **M5 reads only `password_lines` (B-iii).** M5 compares the sum of `password_lines` over the tied flow's portions with the run's (`credential_sent` ? 1 : 0) (design §3). It never reads `insecure.login.attempts`.
- **`login.attempts` keeps its 0.1 meaning** ("the number of attempts", at the key's first occurrence in the flow, 0.1 §4.2). Its type, range and emission do not change. The meaning that the first draft of this clause proposed (password lines, D2's note 4 on #664) now belongs to `password_lines`.
- **The frame stage places the slots on every frame of a tracked flow,** as it does for redaction. With `ring_bytes` 0 it still places them on tracked flows, for this count. That reads only what the redaction already reads (§10).
- **What an earlier reader does:** §1.1. No 0.2 rule reads `attempts`. On `main`, no code outside the contract reads or writes it (a search of `modules/`, `platform/`, `cmd/` and the engine script).
- **What a rollback costs:** M5 goes with the rule.
- **Test:** N-4 (placement), N-6's legs (2), (5) and (6) (rig), and design §6.4's M5 rows. The two cases from D6's (B) conditions:
  - a second login after the `insecure` record was emitted: `comparison M5`. *Control:* a detector that reads `login.attempts`, which misses it;
  - a later password sent before its prompt: `unjudged M5:incomplete`. *Control:* a count present although a slot was not placed, which lets it pass.

## 7. Who reads `orig_payload`, and the password's length (D3's N1)

- **Who reads it.** It follows the path of every stored observation:
  - the sensor host, which writes it and also sees the frames;
  - the channel, under TLS (0.2 §2);
  - the node's intake and its `network-observation` class, kept under that class's retention and never forwarded upstream (0.1 §1);
  - the detector;
  - anyone who reads the node's store, a stolen node or disk included.

  An alert never carries it: the alert states the excess only (CH-51; design §3.2).
- **The residual.** On an own Telnet run, `orig_payload` less the approved commands' lengths, less 3 × `refusals` (C2 0.10), gives the password's length plus the 2 octets of CR LF.
  - **The same readers already learn that length** from the `credential` redaction of any cited login frame. The marker's length equals the secret's on purpose (0.1 §3.2, D4-67).
  - **Where a login frame is not cited,** because the `insecure` key is not a first sight, `orig_payload` is a second route to the same fact for the same readers. It adds no new reader.
  - **What the length gives:** it narrows a search of the password space to one length. It reveals no character.
- **An alert's excess.** Someone who injected a known number of octets and reads the alert's excess could work out 12 − p (design §5 item 3). That reader injected the octets, which takes the credentials HR-24 assumes the attacker holds, so it learns nothing it did not have.
- **The residual is recorded when HR-24 closes** (design §7.1). It is named here so that D3's threat-model row can cite this clause.
