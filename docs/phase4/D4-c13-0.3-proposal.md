## 1. Reader and rollback rules for the whole change

These extend CH-35 and CH-36. They state nothing new about how a minor is read.

### 1.1 Channel and store

- **The channel stays strict** (CH-36). A 0.3 sensor's hello is refused by a 0.2 node as `hello`, because ALPN carries the major only (§2 of 0.2).
  - A 0.3 node knows 0.2 on the channel, as CH-36 allows for a later minor, so it can drain a 0.2 sensor's buffered runs.
  - A 0.2 run's `flow` `end` records carry none of the new counts. CH-51's rule judges a tied flow on such a record as `reason incomplete` (CH-53).
- **Upgrade order: node first, then sensor. Rollback order: sensor first, then node.**
  - Upgrading in that order, the only cost is noise. While the sensor is still 0.2, every own run ties on a 0.2 record, and every such flow alerts `reason incomplete`. The upgrade explains those alerts.
  - In the wrong order, the link is down (`hello`) until the node catches up, and the records wait in the sensor's buffer (CH-20).
  - D7's record of what rolls back together lists the pair and the order.
- **The store reads forward** (`DecodeStored`, `strictjson.Forward` in `contracts/netobs/observation.go`). So a 0.2 node reads a 0.3 stored `flow` `end` with the new fields ignored, and a 0.3 node reads a 0.2 stored record strictly, with the fields absent.
- **A stored observation of a minor below 0.3 is not judged by CH-51.** It carries no counts by construction, and the run profiles of flows retained from before an upgrade are not held. Judging them would raise `reason incomplete` on every tied flow in retention at the first start after the upgrade. **Cost:** a tied flow captured before the upgrade stays as 0.2 left it, hidden whole (HR-24 as it stands). A 0.3 sensor writes only 0.3, and the minor of a stored record is the channel minor the node accepted (CH-36). So a peer cannot pick a lower minor to escape the rule, short of holding the sensor host (AP-36, outside this rule; design §5 item 7).

### 1.2 Stored alerts and the detector's checkpoint after a rollback

- **What `main` does, read from the code.** At a restore, `alertsAfter` (`platform/node/netdetector.go`) decodes every alert after the checkpoint's `last_alert_seq` with `AlertFromEvent`. Any error fails the restore. The node then raises `network-detector-not-restored` and starts its detector from the oldest retained observation (the restore path in the same file). `AlertFromEvent` has no other caller outside tests. The forwarder sends the C4 `netobs.alert` event as it sends any health event, and never parses `rule`.
- **The design's sentence is corrected here.** Design §7.1 item 1 says that a rolled-back node "refuses those stored alerts on read, counts each under the refusal count, and loses none from the store". On `main`, nothing counts a refused stored alert. One unreadable alert after `last_alert_seq` fails the whole restore.
- **What a node rolled back from 0.3 to 0.2 does:**
  - Its detector checkpoint is `otsec.netcheckpoint/0.3`, a later minor. The 0.2 node must read it as CH-35's bridge build does (D5 §1.15 item 1): recognise any `otsec.netcheckpoint/0.x` detector document, raise `network-detector-not-restored` for a minor it cannot read, start from the oldest retained observation, and remove the document once its own first checkpoint commits.
  - It raises the retained observations' alerts again, as CH-35 states for the 0.1 rollback.
  - It judges no tied flow by CH-51, so HR-24 is again "hidden whole" for as long as the rollback lasts.
  - **The `own-session-mismatch` alerts stay in the store,** which is append-only. A later upgrade reads them again.
- **Requirement on the 0.2 code** (not yet built, brief "The approved contracts in code"): the 0.2 detector's checkpoint reader keeps bridge items 1 and 2 of CH-35 for a later minor. **Without it,** a rollback from 0.3 gets the silent restart that CH-35 describes for 0.1: `main`'s exact match on `CheckpointIdentifier` skips the 0.3 document, and the node gives no alarm, stores duplicate alerts and leaves an orphaned document. This is point 2 for D1 (§13).
- **The checkpoint moves to `otsec.netcheckpoint/0.3`** whenever 0.3's detector writes state that 0.2 cannot read, such as a window whose `rule` is `own-session-mismatch`. The learner's half takes the same identifier (0.1 §8), and its form does not change.

### 1.3 Sizes

- **A `flow` `end`** gains at most 236 octets: seven keys with 19-digit values, `"incomplete":true`, and their commas.
  - This is far below `MaxNetobsBytes` (24 KiB), and a `flow` record is not the worst stored body.
  - The worst-body pin (CH-35, R-1 to R-6) is rerun with the new fields on every `end` (N-12).
- **An alert's `observation`** stays within `ExplainMax` (256). Its longest fixed head (CH-51) is 92 octets.
- **No new heartbeat counter enters `sensor.counters`** (CH-53). So C4 0.4 and the health events' caps do not change.

## 2. CH-51. The rule `own-session-mismatch`

- **The token.** `own-session-mismatch` joins `Rules` (`contracts/netobs/alert.go`), which is a closed set. The new token is the reason this change is a minor.
- **The rule runs before any baseline is acknowledged.** It is in `BaselineFree`, like the other own-session rules (D4-68 ruling 10), because a tied flow skips every base rule (design §0).
- **Parameters: none.** The rule's bounds come from each run's profile and are stated in the text as the excess. Its `tie_grace_s` and `max_skew_ms` terms are C13 settings already shown in coverage. Listing one setting in `params` and not the other would mislead.
- **The fixed head of `observation`.** It is the design's §3.2 phrases, pinned here:

  ```
  observation := head [ ": " free-text ]
  head        := comparisons | reasons | comparisons " " reasons
  comparisons := "comparison" ( " " C )+     C in M1 M2 M3 M4 M5 M6a M6b, each at most once, in that order
  reasons     := "reason" ( " " R )+         R in prp-table-full prp-mismatched no-profile incomplete, each at most once, in that order
  ```

  - **Examples:** `comparison M3 M6b: …`, `comparison M6b reason no-profile`, `reason incomplete: …`.
  - **`Alert.Validate` refuses** an `own-session-mismatch` alert whose `observation` does not start with a head of this form. That covers an unknown comparison or reason, a repeat, an order other than the one above, and a missing head.
  - Every other rule's text is unchanged.
- **The text states only the excess, never the run's own totals** (design §3.2; §7 below). It says what was seen and never says "spoofed" (D4-68 ruling 10).
- **What an earlier reader does:** a 0.2 `Alert.Validate` fails it as `form` ("is not a rule"). §1.2 gives the consequence. A C6 or upstream reader gets the token as text in the forwarded health event and parses no `Rules`. C4 does not change.
- **What a rollback costs:** §1.2.
- **Test:** N-1, N-2, N-3, N-13.

## 3. CH-52. Payload and packets per direction on a `flow` `end`

- **Fields.** On every `flow` `end` whose `l4` is `tcp` or `udp`, a 0.3 channel record carries:
  - `orig_payload` and `resp_payload`, the payload octets each end sent;
  - `orig_pkts` and `resp_pkts`, the packets each end sent.

  Each is a decimal integer from 0 to 2^63 − 1. In the Go type the fields are optional. They are required in a 0.3 channel record, and may be absent in a stored record of any minor (CH-35's pattern). They are never on a `start`, and never on a layer-2 or other `l4` record.
- **`orig` is the record's `ip.src` end, and `resp` its `ip.dst` end.** `src` is as C13 defines it: for `client-server`, the end that sent the SYN; for `direction: none` and `midstream`, the sender of the first frame (CH-49).
  - **The link agent maps the engine's ends to the record's.** Zeek's "originator" can differ from C13's `src`. Its heuristic flips a connection's direction (the `^` in `history`, `base/protocols/conn/main.zeek` at `v9.0.1`). Where Zeek's originator is the record's `dst`, the agent swaps each `orig_`/`resp_` pair.
  - **A reader never takes `orig` to mean "to the device".** The detector finds the direction to the device by the run's endpoint, the device's address and port (design §3).
- **`orig_payload` and `resp_payload`** (design §7.1 item 2 (a); the engine computes them already, design §2):
  - **TCP:** the sequence span each end sent. That is Zeek's `orig_bytes` and `resp_bytes` (`c$orig$size`, `TCP_Endpoint::Size()`): without the SYN and the FIN octet, unwrapped over 64 bits, from the first sequence number seen on a midstream join.
  - **UDP:** the sum of the payload lengths each end sent (`UDPSessionAdapter.cc`).
  - **What does not count:** retransmissions, keep-alives (`snd.nxt` − 1, at most one octet), zero-window probes, the PRP RCT, VLAN tags and padding.
  - **What inflates it:** a segment far ahead in sequence, and an ACK beyond the data sent. Both are noisy and hide nothing (design §7.1).
  - **Holes:** a hole inside the span is counted, so loss cannot make the span smaller than what was sent. Zeek's `missed_bytes` shows the holes and is not carried.
- **`orig_pkts` and `resp_pkts`:** Zeek's `orig_pkts` and `resp_pkts` from its conn-size analyzer, counted after the PRP discard, which the frame stage makes before the engine (SL-3; E-D4-02). Whether a fragmented datagram counts once, after reassembly, is a stage 2 check (design §2). Until it is measured, the detector judges SNMPv3 datagrams on these fields only as the design's §3 M2 states.
- **Deltas.** Each `end` carries the counts since the previous `end` of the same connection, so a checker that sums `end` records by key gets the totals, as for `packets` and `bytes` (0.1 §4.3).
- **Checks the node makes:** each value lies in its range. On a TCP `end` with `syn_only: true`, both payload fields are 0, because a syn-only flow carries no payload (0.1 §4.3). The node makes no check that ties these counts to `packets` or `bytes`. Those count frames after the discard with link-layer octets, and the two are not equal in general (design §4, the RCT and fragments).
- **What an earlier reader does:** §1.1.
- **What a rollback costs:** the detector loses M2 and M3 with the rule (§1.2). The stored fields stay.
- **Test:** N-4, N-5, N-6, N-12.

## 4. CH-53. The overlap count, `incomplete`, and `overlap_table_full`

These are design §3.3, adopted by D1 (6854297364, and the conditions of D3 and D6 on `7f9e9953`), as contract text. The frame stage computes them and the link agent joins them (D3's SL-3 change, this brief).

- **`orig_overlap_octets`** is on a TCP `flow` `end` for a flow the frame stage tracked. Its value is the sum, over the record's portion, of each segment's payload octets that lie at or below the highest sequence end seen in that direction before the segment. It counts the direction from the tracked flow's `src`, which is the node's address (below).
  - **A segment that starts exactly at the highest end adds nothing.** One that starts one octet below it adds one.
  - **The only exclusion:** a one-octet segment that starts at the highest end − 1 (a keep-alive). Every other short segment counts.
  - **Sequence numbers are unwrapped to 64 bits** from the first one seen.
  - **Payload length** is the IPv4 total length less its header, options included, or the IPv6 payload length less any extension headers, less the TCP data offset.
  - **It is a delta since the previous `end` of the connection,** as in CH-52.
  - **The direction from the device is not counted.**
- **`incomplete`**, present only as `true`, on a TCP `flow` `end`. It means only that the overlap count for that record cannot be read as complete. It says nothing about the flow's other fields. It is set when:
  - the frame stage's entry was refused;
  - the entry began after the flow's first segment (a midstream join, a refusal, or a sensor restart);
  - a run portion of the key has a `start` and no `end` (after an unclean sensor stop or a lost `end`);
  - a header in the flow was malformed;
  - the link agent could not join a count to the record;
  - a frame-stage record joined no engine flow, or an entry was freed or begun inside one engine flow's span (design §3.3, D6's B1 on #664).
- **Which flows are tracked.** The frame stage creates an entry only for a TCP flow that meets all three of these:
  - its source is one of the node's addresses;
  - its destination is a listed collector endpoint, a relay's address and Telnet port;
  - the frame stage saw the handshake complete: the node's SYN, the relay's SYN-ACK, and an ACK of that ISN + 1.

  **Both lists are sensor configuration,** set at commissioning and covered by `config_digest` as `setting` lines (CH-32). So a change in either shows as `sensor-coverage-mismatch`. A flow to an endpoint not on the list carries neither field.
- **How a reader takes the two fields.** The overlap count is complete only when `orig_overlap_octets` is present and `incomplete` is absent.
  - **A count with `incomplete: true`** is a partial count. No reader takes it as complete.
  - **A missing count never reads as zero.** A tied flow without a complete count alerts as `own-session-mismatch` with `reason incomplete`, or with `reason no-profile` when its endpoint is not listed (CH-51; design §3.3).
  - **The node refuses** `incomplete: false`, and either field on a UDP record, on any `start`, or on a non-IP record.
- **`overlap_table_full`**, a new heartbeat counter, from the frame stage. It counts the entries the frame stage refused because its table held `MaxOverlapFlows` entries. A new entry is refused and never evicts a live one.
  - It is required in a 0.3 heartbeat. It is a run total that never decreases (`Follows`).
  - **It is shown in status only, and not in `sensor.counters`.** That keeps C4 0.4 and the health event's size as they are, like the agent's counts (CH-43). The alerts it causes (`reason incomplete`) make the exhaustion visible per flow.
- **`MaxOverlapFlows` = 4,096 entries,** a fixed sensor bound for §12 of 0.2, about 80 octets each. An entry is freed:
  - when its flow ends (`fin` both ways, or `rst`);
  - after 2 × `flow_idle_s` with no frame;
  - after `MaxConnectTimeoutMS` (30 s) if its flow has carried no payload.

  An `idle` cut writes the record and keeps the entry (design §3.3).
- **What it reads:** the TCP `seq`, the IP and TCP lengths and data offset, the flags and the direction. It reads no payload byte (§10).
- **What an earlier reader does:** §1.1. A 0.2 node never meets the heartbeat counter, because the channel is strict.
- **What a rollback costs:** M6b goes with the rule (§1.2).
- **Test:** N-7, N-8, N-9, N-10, N-14.

## 5. CH-54. `rexmit_inconsistent`

- **The field.** A count on every TCP `flow` `end`, a decimal integer from 0, required in a 0.3 channel record. It counts the engine's `rexmit_inconsistency` events on the connection, as a delta since the previous `end`.
- **Why it has no direction (correction to design §3.1 and §7.1 item 2 (c)).** The design names the field `orig_rexmit_inconsistent` and says the project's script "would count the event per direction". Zeek's event cannot support that. Its signature at `v9.0.1` is `rexmit_inconsistency(c: connection, t1: string, t2: string, tcp_flags: string)` (`src/event.bif`). `TCP_Reassembler::Overlap` knows `IsOrig()` but does not pass it (`TCP_Reassembler.cc`). So the script cannot attribute an event to a direction from the event alone, and the count covers both directions.
  - **The cost of this is noise, never a miss.** An inconsistent retransmission from the relay also gives `comparison M6a`, and the alert's text says the direction was not known.
  - **How often a relay's retransmissions differ in content is `unknown`.** It is a stage 2 own-run cell, labelled as a known false-positive source until measured.
  - **Point 1 for D1** (§13) covers this.
- **The handler.** The project's handler counts the event and discards `t1` and `t2`. They are never logged, stored or forwarded, and `policy/protocols/conn/weirds.zeek` is never loaded (D1's ruling 1, 6854205907; design §3.1, stage 3's three checks).
- **What an earlier reader does:** §1.1.
- **What a rollback costs:** M6a goes with the rule.
- **Test:** N-4, N-11.

## 6. CH-55. `login.attempts`

- **The meaning (D2's note 4 on #664; design §7.1 item 3).** `attempts` is the number of password lines the client sent. A password line is the client's line in the credential slot that follows a password prompt (0.1 §3.2's Telnet slot).
  - Prompts the server sent and the client did not answer are not counted. After a wrong password a SEL-751 prompts up to three times, and the adapter sends nothing more (S22 p. 7.33).
  - A server's echo is not a client line.
  - 0.1 said only "the number of attempts". The type and the range do not change.
- **It is exact only with `slot: placed`.** With `not-placed` or `none`, the sensor could not place every slot, and the count is the lines it did place.
  - **Proposed:** the detector's M5 reads `attempts` only with `slot: placed`. On any other value, the tied Telnet flow alerts `comparison M5 reason incomplete`.
- **A gap in 0.1: when the observation is emitted.** An `insecure` observation is emitted once per key per flow, "at the key's first occurrence in that flow" (0.1 §4.2). For Telnet that is before or at the first login. So `attempts` would count at most the lines sent before the emission, and a second login later in the same flow would not be counted. M5 needs the count over the flow.
  - **(A) Emit at the end.** A Telnet `insecure` observation that carries a `login` is emitted at the flow portion's `end` (`fin`, `rst`, `idle`, `sensor-stop`), with `attempts` counted over that portion. 0.1 already waits for DNP3's `function` until its `sa` is known (0.1 §4.3), so this has a precedent. The cost is that `insecure` arrives later. No rule alerts on `insecure` with a latency bound.
  - **(B) A count on the `flow` `end`.** A new count field there, with `insecure` unchanged.
  - **I recommend (A):** it adds no field, and M5's latency matches the first judgement path (design §3.2). This is a new mechanism, so under D4-99 the options are agreed in comments before either is written into 0.3. It is point 3 for D1 (§13).
- **What an earlier reader does:** no 0.2 rule reads `attempts`. On `main`, no code outside the contract reads or writes it (a search of `modules/`, `platform/`, `cmd/` and the engine script).
- **What a rollback costs:** M5 goes with the rule.
- **Test:** N-6 (rig), with the cases in design §6.4 (M5 rows).

## 7. Who reads `orig_payload`, and the password's length (D3's N1)

- **Who reads it.** It follows the path of every stored observation:
  - the sensor host, which writes it and also sees the frames;
  - the channel, under TLS (0.2 §2);
  - the node's intake and its `network-observation` class, kept under that class's retention and never forwarded upstream (0.1 §1);
  - the detector;
  - anyone who reads the node's store, a stolen node or disk included.

  An alert never carries it: the alert states the excess only (CH-51; design §3.2).
- **The residual.** On an own Telnet run, `orig_payload` less the approved commands' lengths, less 3 × `refusals` (C2 0.10), gives the password's length plus the 2 octets of CR LF.
  - **The same readers already learn that length** from the `credential` redaction of any cited login frame. The marker's length equals the secret's on purpose (0.1 §3.2, D4-67).
  - **Where a login frame is not cited,** because the `insecure` key is not a first sight, `orig_payload` is a second route to the same fact for the same readers. It adds no new reader.
  - **What the length gives:** it narrows a search of the password space to one length. It reveals no character.
- **An alert's excess.** Someone who injected a known number of octets and reads the alert's excess could work out 12 − p (design §5 item 3). That reader injected the octets, which takes the credentials HR-24 assumes the attacker holds, so it learns nothing it did not have.
- **The residual is recorded when HR-24 closes** (design §7.1). It is named here so that D3's threat-model row can cite this clause.

## 13. Points for D1's ruling

1. **`rexmit_inconsistent` without a direction** (CH-54). Zeek 9.0.1's event carries none. Three options:
   - (a) a count over both directions, as written here, which fails toward noise;
   - (b) keep the name `orig_rexmit_inconsistent`, which would misstate the field;
   - (c) attribute the direction by a mechanism outside the event, which is a new mechanism and is not proposed.

   I recommend (a). The brief's expected interface names `orig_rexmit_inconsistent`, so this needs D1's word.
2. **The 0.2 code keeps CH-35's bridge reader for a later checkpoint minor** (§1.2). Without it, a rollback from 0.3 is silent. This adds a requirement to the brief "The approved contracts in code". It is not a new mechanism, because the bridge build already defines it.
3. **When a Telnet `insecure` with a `login` is emitted** (CH-55). This is a new mechanism, so its options, (A) or (B), are to be agreed in comments before 0.3 fixes M5's input (D4-99). Until then, CH-55's meaning stands, and M5's input is open.
4. **The new heartbeat counter `overlap_table_full`.** The brief does not list it, but design §3.3 needs it. Status only, to keep C4 0.4 unchanged.
5. **The `own-session-mismatch` alert takes no params** (CH-51). A reviewer may prefer `tie_grace_s`, as `own-session-outside-record` has.
6. **A stored observation below 0.3 is not judged by CH-51** (§1.1). This trades the noise of an upgrade for leaving flows captured before it as 0.2 left them.
