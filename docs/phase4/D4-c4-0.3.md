# C4 `otsec.event/0.3`: a kind and a field for C13 observations

D4, 2026-11-07. This is the draft for review. D1 approves it with C13 `otsec.netobs/0.1` ([D4-c13-netobs.md](D4-c13-netobs.md)) and C5 0.9 (#532) in D4-68. The reviewers are:

- D5, for the store's event path;
- D3, for the boundary;
- D6, for the contract tests.

Everything here is `desk`. The code follows approval, in `contracts/event`, with C13's package.

## Why C4 changes

C13 observations are stored as C4 events, so they use the store's event path unchanged (#532 §2, D4's answer to D5's question 1). Alerts need no C4 change: they are `telemetry-health` events of type `netobs.alert`, and `Health.Type` is an open set. Observations need two things C4 0.2 doesn't have: a kind, and a place for the observation's body.

## What changes

| Item | 0.2 | 0.3 |
| --- | --- | --- |
| `Identifier` | `otsec.event/0.2` | `otsec.event/0.3` |
| `Kind` | seven constants | adds `KindNetworkObservation = "network-observation"` |
| `Event` | | adds `Netobs json.RawMessage` (`json:"netobs,omitempty"`) |
| `schema/event.json` | | adds the `netobs` property, an object |

**The rules `Validate` adds:**

1. `netobs` is present exactly when `kind` is `network-observation`, and only on an event stamped 0.3 or later.
2. Such an event is a platform event: `origin` is `platform` and `origin_auth` is `platform`. It has no `native`, `device_time` or `collection`, and no `evidence_class`. These are the existing platform-event rules, and none of them changes.
   - The observation's evidence class is in its own body (C13 §5, `node.evidence_class`), set by the node from its configuration (D1-23).
   - Its packets are the record's C5 capture, named in the body (`node.stored_capture`), as a C10 alarm's evidence is.
3. `source.asset` is the observation's destination asset (C13 §5). When that end doesn't resolve, `source.asset` is absent and the event carries the flag `asset-unresolved`, as today.
4. `netobs` is one JSON object of at most `MaxNetobsBytes` bytes. The value is pinned in code from C13's worst stored observation, and is expected near 16 KiB, because the frame bytes are not in the body. C13's `TestWorstStoredObservationFits` also pins the whole stored record, the event plus its capture, at most 64 KiB (D5).

**What C4 does not check.** C4 checks only that `netobs` is an object within its bound. The node checks the body against C13 at intake, before it hands the record to the store. The store checks only C4's `Validate`, as for every event (C5 0.9 §2), so C5 needs no hook for events. And `contracts/event` doesn't import `contracts/netobs`. That keeps C4 free of C13, and lets C13 cite C4 event IDs without an import cycle.

## Compatibility

- **Readers.** A 0.2 reader keeps an event of an unknown kind as opaque (`Kind` is open) and ignores the unknown `netobs` field, because C4 is not strict. Nothing that reads C4 events breaks.
- **The store.** It accepts only a C4 schema this binary reads exactly (`assignSeq`), so C4 0.3 ships in the same release as the node that writes observations (#532 §2). No observation can exist before then.
- **Forwarding and C6.** Observation streams are never a forward target's stream. That is a node rule, with its test in #532 §6. So C6 never meets this kind, and C6 doesn't change.
- **Rollback.** A 0.2 binary never opens the `network` database, because its layout doesn't name it (#532 §5). So it never reads a 0.3 observation.

## Tests

The tests go in `contracts/event`, with D6's contract tests:

- A valid 0.3 observation event passes.
- Each of these is refused:
  - `netobs` on another kind;
  - `network-observation` without `netobs`;
  - `netobs` on an event stamped 0.2;
  - `netobs` that is not an object;
  - `netobs` one byte over `MaxNetobsBytes`, while `netobs` at exactly `MaxNetobsBytes` passes (D6);
  - a `network-observation` event with origin `device`, or with `native` or `evidence_class`.
- An existing 0.2 golden still validates byte for byte.
- A 0.3 observation decoded by the 0.2 code path keeps its kind and drops `netobs` without error. That is the reader rule, tested with a copy of 0.2's decoder.
- `schema/event.json` agrees with `Validate` on every golden, as `schema_test.go` checks today.
