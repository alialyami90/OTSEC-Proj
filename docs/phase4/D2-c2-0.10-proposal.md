# C2 0.10: a Telnet session's facts for HR-24's own-session profile (D2, 2026-11-13)

D2's proposal for `otsec.adapter/0.10`, under brief P4-4-HR24P (in #670, `docs/agent-handoffs.md`, "After D4-100", not yet merged). Revised the same day for `records-auditor`'s audit and D1's rulings (6861454974 on #671). It takes `docs/phase4/D4-hr24-design.md` §7.2 items 4 and 7 to contract text. D3, D4 and D6 review it, and D1 approves it in a decision entry. No contract code changes here. The code comes with the brief "The approved contracts in code".

- **Evidence class: `desk`.** Nothing here is built or run. Code is cited by function at `main` `65980515`. The manual cited is S22, the SEL-751 Instruction Manual, date code 20260910, from `reference/manuals-SEL/`; page numbers are the manual's own.
- **The collector's part (§3.3) is D3's, and it is marked awaiting D3.** C2 0.10's `rexmit_octets` is owned with D3 for the collector (D1, 6854297364 on #664). D3 is on another task, so this proposal states the text, and the PR comment for D3 asks the questions in §7.
- **What it changes:** one optional object, `session.telnet`, in a C2 result. No new code, status, phase, record kind or C1, C3, C7 or C9 change. `docs/phase4/D5-sensor-node.md` §1.10 is not touched.

0.10 adds, for a connected Telnet session:

1. `refusals` and `command_octets_received` (§7.2 item 4), which set M3's Telnet tolerances;
2. `read_to_eof`: whether the adapter read to the relay's end of stream after QUI (D6's N6, §4's "Relay output after the QUI reply" row);
3. `rexmit_octets`, or `rexmit_unknown`, which fails closed (§7.2 item 7, M6b).

## 1. The object

```json
"session": {
  "connected": true, "wake_sent": false, "language_probe": "accepted",
  "password_prompt": true, "credential_sent": true, "echo_scan": "performed",
  "access_level": "1", "quit_sent": true,
  "local_addr": "127.0.0.1:53114",
  "connected_at": "2026-11-13T20:15:02.418230115Z",
  "telnet": {
    "refusals": 2,
    "command_octets_received": 9,
    "read_to_eof": false,
    "rexmit_octets": 0
  }
}
```

and, when the collector could not read the count:

```json
  "telnet": { "refusals": 2, "command_octets_received": 9, "read_to_eof": false, "rexmit_unknown": "in-flight" }
```

`session.telnet` sits beside `session.snmp` (0.7), and is its Telnet counterpart: present exactly when the session is Telnet (no `session.snmp`) and `connected` is true. A result that never connected carries neither, as in 0.9. All four counts are numbers and a flag. None carries device bytes, so the node's profile stays numeric (D4's §3.2, D3's N1).

### 1.1 `refusals`

The number of three-octet refusals, `IAC DONT x` or `IAC WONT x`, that the transport wrote in the session. It is `telnet.Stats.Refusals` (`modules/ied/telnet`, `answer`), which counts a refusal only after its `Write` returned without error.

- **What it gives M3:** the client's only octets to the relay outside the transcript's sent data are the refusals (`telnet` package doc: "The refusals are the only other bytes it writes"). So the to-relay bound becomes the transcript's sent octets + 3 × `refusals` + 2, exactly, in place of 3 × 64 + 2 = 194 (D4's §5 item 3).
- **Its one undercount:** a refusal whose `Write` fails after putting part of its three octets on the wire is not counted. The write error ends the session (`telnet` package doc), so this happens at most once a session and costs at most 2 octets under the bound. Under-reporting gives noise, not a miss, because M3 tests for more.
- **After the half-close (§1.3):** a refusal the relay's late negotiation asks for cannot be written once the socket's write side is closed. Its `Write` fails, is not counted, and sets the transport's sticky error (`c.err`), so the next `Read` returns that error, not EOF, and `read_to_eof` is false (§1.3).

### 1.2 `command_octets_received`

The octets the transport read from the socket less the data octets its decoder produced (`Conn.Received`). On a session the decoder reached the end of without error, that is every octet received on the wire that is not delivered as data: each command's `IAC` and verb, each option byte, a subnegotiation's `IAC SB`, its contents and its `IAC SE`, and one octet for each escaped 0xFF (the leading `IAC`; `IAC IAC` is one data octet, `decode`). It is §7.2 item 4's definition, made exact to the code:

- `decode` counts each data octet in `data` (`c.received`), and every other octet it consumes is a command octet. The transport counts the octets each `nc.Read` returns. The difference is the field.
- **Where the two differ:** when `decode` stops on `telnet.ErrTooLarge` or `telnet.ErrNegotiation`, the rest of that read's buffer is counted as command octets but was not decoded. On `main` either error reaches `await` (`modules/ied/sel751/run.go`) as a plain read error. It becomes `errClosed`, and `stepFailed` gives `failed.transport_closed`; outside a reply that already ended in a prompt, that is the code. (`failed.response_too_large` comes only from the adapter's own budget, `errTooLarge`, and C2 has no negotiation code.) Either way the error is sticky, so the read that follows returns it and not EOF, and `read_to_eof` is false (§1.3). The from-relay direction is then not judged, and the overstatement widens nothing that is judged.
- **With `read_to_eof` true** the from-relay payload on the wire equals the transcript's received octets + `command_octets_received` + Σ (secret length − 10) over the redacted echoes, exactly. So D4's from-relay bound (transcript + `command_octets_received` + 2 × echoes on a SEL-751) holds with no other slack.
- It is also ≥ 3 × the number of `WILL` and `DO` received, so ≥ 3 × `refusals` (each refusal answers one; `answer`). Validate checks that (§2 rule 3).

### 1.3 `read_to_eof`

True when, after QUI was sent, the adapter's last read in the close phase returned the relay's end of stream (the peer's FIN: `io.EOF` from the socket), with the decoder in no error, so that every octet the relay sent is in the transcript or in `command_octets_received`. Otherwise false.

**EOF in place of D4's wording.** D4's M3 judges the from-relay direction when the run "sent QUI and did not end on a timeout, a response limit or the deadline". This proposal makes the relay's EOF the gate instead, and the choice is deliberate. A run that sent QUI and timed out on no step can still leave relay octets unread at close, because `await` returns on a prompt and the quiet interval, not at EOF (D6's N6). A run that timed out on an earlier step and then sent QUI reads that step's late octets in the close phase, so at EOF its transcript is complete. Only EOF says that nothing the relay sent is missing. D4's outcome conditions are then not needed for this direction, and D4 decides whether to keep them as well.

**What the adapter does on `main` (D6's N6, answered from the code and the manual):**

- `quit` sends QUI and calls `await(time.Time{}, true)`, which returns on a prompt and the quiet interval, on the step timeout, on the budget, or at the end of the connection. `run` then closes the socket (`defer s.nc.Close()`). The adapter itself never waits for EOF.
- **S22 says QUI does not end the Telnet session.** QUIT "Goes to Access Level 0" (Table 7.59, p. 7.73). "To terminate a Telnet session, use the EXIT command" (Communications Interfaces, p. 7.3), and the Telnet Server note says to "Use the QUIT command prior to closing the Telnet-to-Host session" (p. 7.16). EXIT is not in the C3 register and is not proposed.
- **So on a SEL-751 as documented, and with the adapter as on `main`, `read_to_eof` would be false on every run** (`documented-untested`, inference from S22). The adapter would see EOF only where the relay closed the connection itself, for example at `TIDLE` (1–30 min, default 15, Table 4.104, p. 4.250), and no run waits that long. D4's M3 from the relay would then be judged on no SEL-751 run, and §5 item 4 of D4's note would cover every run.

**D1 ruled for the half-close, on conditions (6861454974, ruling 1):**
- **The collector half-closes, not the adapter.** It does so only after the adapter has read QUI's reply, through a collector seam (§3.3), with `CloseWrite`: a FIN, and no data octet or command. The adapter then reads to EOF inside the close step's existing timeout, which `await` already applies. No new bound is added. What arrives is committed as the close phase's reply.
- **If the relay does not close,** the read ends as it does today, `read_to_eof` is false, and the run is otherwise unchanged.
- **A refusal asked for after the half-close** cannot be written, and the sticky error makes `read_to_eof` false (§1.1).
- **It lifts one exclusion, for this change only:** P4-4-HR24's "no change to the collector's own sessions". D1 records that when it approves C2 0.10.
- **D3, the collector's owner, and D6, for device safety, agree to it in this PR first,** or say why not (D4-99).
- **On hardware,** how the relay answers a half-close is `unknown` (D2's note 3 on D4's M4 row). It is an H-row, and D1 numbers it with the stage-2 brief.

0.10's field is the same whether the relay closes or not. Only its value differs.

### 1.4 `rexmit_octets` and `rexmit_unknown`

Exactly one of the two is present in `session.telnet`.

- **`rexmit_octets`** is the number of payload octets the collector's own socket retransmitted **to the device** over the session, as the collector's kernel counts them: on Windows, `TCP_INFO_v0.BytesRetrans` from `WSAIoctl` with `SIO_TCP_INFO`, version 0, on the session's socket (Windows 10 1703 and later, no elevation); on Linux, `tcp_info.tcpi_bytes_retrans` from `getsockopt(TCP_INFO)` (kernel 4.19 and later). The socket knows nothing of what the device retransmitted, so the field says nothing of the other direction. It is an integer from 0 to 2⁵³ − 1.
- **`rexmit_unknown`** is a closed token for why the count was not read:
  - `in-flight`: at the read, the socket had data sent and not acknowledged (`BytesInFlight` ≠ 0 on Windows; `tcpi_unacked` ≠ 0 on Linux), so later retransmissions could still happen;
  - `call-failed`: the call returned an error;
  - `unsupported`: the build or kernel predates the field (Windows 10 LTSB 2016, Linux before 4.19), or the connection the `Dial` seam gave has no socket to ask (a replay or an in-memory pipe).
- **`unknown` fails closed** (D4's §3.1): on any `rexmit_unknown`, and on a Telnet result with no `session.telnet` at all (§4), the node's M6b raises `own-session-mismatch` with `reason no-profile`. The node's own sanity bound (0 ≤ value ≤ k × sent octets, D4's §3.1) is the node's, not C2's; C2 checks only the type and range.
- **`unknown` until measured** (D4's §3.1, unchanged): whether `BytesRetrans` counts tail-loss probes and how it counts a repacketized retransmission. Linux will be measured on CI-Linux with `netem`. The Windows half is `desk` until a measurement the owner allows.

## 2. Rules (`Result.Validate`)

For a 0.10 result or later:

1. `session.telnet` is present ⇔ `session.snmp` is absent and `connected` is true. A 0.9 or earlier result that carries it fails ("`session.telnet` is new in 0.10"), as `session.snmp` does before 0.7.
2. `refusals` ≥ 0 and `command_octets_received` ≥ 0, each at most 2⁵³ − 1.
3. `command_octets_received` ≥ 3 × `refusals`.
4. `read_to_eof` true ⇒ `quit_sent` true. The code is not checked: a transport error is never EOF, because the transport's error is sticky (§1.2), and that guarantee is the adapter's, tested from outside (§8 test 7), not a rule Validate can check from the result.
5. Exactly one of `rexmit_octets` and `rexmit_unknown`. `rexmit_octets` is an integer in range; `rexmit_unknown` is one of `in-flight`, `call-failed`, `unsupported`. A later minor's token is read by an earlier reader as `unknown` too, which fails closed (§4).

`session.telnet` is strict inside: an unknown field in it is refused for a result of this package's minor or earlier, and ignored for a later one, as `DecodeResult` does today.

## 3. Who fills them

### 3.1 The transport (`modules/ied/telnet`, D2)

`Conn` gains a count of the octets read from the socket, and a method that returns it with `Stats` and `Received`. Nothing it writes changes.

### 3.2 The SEL-751 adapter (`modules/ied/sel751`, D2)

- Sets `refusals` and `command_octets_received` from the transport at `result`.
- In `quit`, after QUI's reply has been read, calls the collector's half-close seam (§3.3), then reads on in the same close step to EOF or the step's end.
- Sets `read_to_eof`: true only when that read ended on the connection's end with the decoder in no error (the socket's error is `io.EOF`).
- Calls the collector's read seam (§3.3) once, after the session's last write or read, whichever is later, and before the socket is closed, on every connected path, and copies its answer.

### 3.3 The collector's read (`modules/security/collector`, D3: **awaiting D3**)

Proposed text, for D3 to accept, change or refuse in the PR:

- `sel751.Config` gains two seams, which the collector sets beside `Dial`:
  - `HalfClose func(net.Conn) error`, the `CloseWrite` of D1's ruling 1 (§1.3). Nil, or an error, means the adapter reads on as today, and `read_to_eof` can still be true only if the relay closes;
  - `Rexmit func(net.Conn) (octets int64, unknown string)`. Nil gives `unsupported`.
  The platform code (the `SIO_TCP_INFO` call on Windows, `TCP_INFO` on Linux, through `SyscallConn`) lives in the collector, which already owns the dialer (`endpointDialer`), so no device-facing code gains a system call of its own.
- **The read rule, amended from D1's 6854297364 (taken in principle by D1, 6861454974 ruling 2, pending D3):** it is read once, on the session's own socket, after the session's last write or read, whichever is later, and it is valid only with nothing in flight. D1's earlier wording reads it "after EOF". By §1.3 a SEL-751 does not close after QUI, and with the half-close it closes only if it answers the FIN, which is `unknown`. So a rule that waited for EOF could make every run `unknown`, and M6b would alert `no-profile` on every own run. What the rule needs is that no data octet is sent, and so none retransmitted, after the read: nothing in flight at the read, and no write after it. The seam runs after the last write as well as the last read, because a session can end on a write: `await` returns on `ctx.Err()` or the deadline after a send, and `sendFailed` ends the session after a write. Refusals are written only from inside a read, so they come before the seam. After the half-close no refusal can be written (§1.1).
- **On a path where data is in flight** (a timeout, the deadline, an abort): the read gives `in-flight`, and the socket is then closed abortively (`SO_LINGER` 0), as D3's rule says, so that nothing is retransmitted after the read. An abortive close sends an RST to the relay, which ends the TCP connection. That the relay's session then stays at its level until `TIDLE`, as after a close without QUI, is `inference`: S22 p. 7.16 says it only for a close ("Otherwise, the relay remains at an elevated access level until TIDLE expires"). D6 reviews it as device behaviour.
- **Questions for D3:** (a) are the two seams the boundary you want, or should the collector patch the result after the adapter returns (I chose the seams so the result is built in one place, as in 0.9 §1.4); (b) is "after the last write or read, nothing in flight" an acceptable form of your rule; (c) on Linux CI, is `tcpi_unacked` the in-flight test you want; (d) do you agree to the half-close (D1's ruling 1).

### 3.4 SNMPv3

Not affected. UDP has no retransmission count, M6b is Telnet only (D4's §3), and an SNMPv3 result carries no `session.telnet`.

## 7. The bound D3's stage-2 risk 1 asks for (6855320671 on #664)

An on-path attacker who completes real handshakes as the node can hold frame-stage entries, but only as many as the relay accepts Telnet sessions.

- **The SEL-751's limit is 2 concurrent Telnet sessions.** S22 Table 7.5, note a (p. 7.13): "PORT 1 concurrently supports … two Telnet … sessions"; and Table N.2, "SEL-751 Capability for Different Protocols" (p. N.4): Telnet, 2 sessions. The two tables agree for Telnet. (They disagree for FTP, two against one, so the manual's counts are not all consistent.) `docs/device-capabilities.md` already records "2 concurrent Telnet sessions" (`documented-untested`). Table 7.5 note a says "PORT 1". That the limit is per relay, and not per Ethernet port, is `inference`: on dual-port models both Ethernet ports serve PORT 1 under its `NETMODE` setting, with one `TPORT`.
- **The bound per SEL-751 is therefore `unknown`.** Two sessions are documented. What the relay does with a third connection is not, and the answer changes the bound:
  - **refused or reset:** the entry is freed at once, so the attacker holds at most 2 entries per relay. While both are held, the collector's own dial meets a relay with no free session, and that run does not tie;
  - **handshake completed, then held unserved:** each such flow is an entry until `MaxConnectTimeoutMS` (30 s) frees it (D4's §3.3), so the bound is the attacker's connection rate × 30 s, not 2.
- The manual does not say which. It is a device question for an H-row beside ruling 1's, which D1 numbers with the stage-2 brief. Stage 2 should have a case for each answer.
- **An idle attacker's session ends at `TIDLE`** (1–30 min, default 15, Table 4.104, p. 4.250), unless the attacker keeps it active. A relay with `ETCPKA := Y` also probes an idle peer (`KAIDLE` 10 s by default, same table), and an on-path attacker answers those probes.

## 9. Limits and risks

- Every value here is from the adapter's own counts or the collector's kernel. A compromised collector can report anything, but the collector holds the device credentials and is already the trust root for its own runs (D3's model).
- `rexmit_octets` reports a count, not content, and adds no new reader at the site: it is a number about the platform's own socket.
- No field reveals the password's length. `refusals` and `command_octets_received` are about negotiation, and the transcript already stores the redaction marker, whose fixed length hides the secret's.
- Nothing here contacts a device. Every behaviour of the SEL-751 above is from S22 and is `documented-untested`.
