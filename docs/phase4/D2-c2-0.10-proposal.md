0.10 adds, for a connected Telnet session:

1. `refusals` and `command_octets_received` (§7.2 item 4), which set M3's Telnet tolerances;

3. `rexmit_octets`, or `rexmit_unknown`, which fails closed (§7.2 item 7, M6b).

## 1. The object

```json
"session": {
  "connected": true, "wake_sent": false, "language_probe": "accepted",
  "password_prompt": true, "credential_sent": true, "echo_scan": "performed",
  "access_level": "1", "quit_sent": true,
  "local_addr": "127.0.0.1:53114",
  "connected_at": "2026-11-13T20:15:02.418230115Z",
  "telnet": {
    "refusals": 2,
    "command_octets_received": 9,
    "read_to_eof": false,
    "rexmit_octets": 0
  }
}
```

and, when the collector could not read the count:

```json
  "telnet": { "refusals": 2, "command_octets_received": 9, "read_to_eof": false, "rexmit_unknown": "in-flight" }
```

`session.telnet` sits beside `session.snmp` (0.7) as its Telnet counterpart. It belongs to a session that is Telnet (no `session.snmp`) and connected. Its presence rule is §2 rule 1. `refusals`, `command_octets_received` and `read_to_eof` are required inside it, and an absent one is not read as 0 or false (D4's N1). Every field is a number or a flag. None carries device bytes, so the node's profile stays numeric (D4's §3.2, D3's N1).

### 1.1 `refusals`

The number of three-octet refusals, `IAC DONT x` or `IAC WONT x`, that the transport wrote in the session. It is `telnet.Stats.Refusals` (`modules/ied/telnet`, `answer`), which counts a refusal only after its `Write` returned without error.

- **What it gives M3:** the client's only octets to the relay outside the transcript's sent data are the refusals (`telnet` package doc: "The refusals are the only other bytes it writes"). So the to-relay bound becomes the transcript's sent octets + 3 × `refusals` + 2, exactly, in place of 3 × 64 + 2 = 194 (D4's §5 item 3).
- **Its one undercount:** a refusal whose `Write` fails after putting part of its three octets on the wire is not counted. The write error ends the session (`telnet` package doc), so this happens at most once a session and costs at most 2 octets under the bound. Under-reporting gives noise, not a miss, because M3 tests for more.
- **After the half-close (§1.3):** a refusal asked for by the relay's late negotiation cannot be written once the socket's write side is closed. The `Write` fails locally (EPIPE on Linux, WSAESHUTDOWN on Windows; D6), nothing goes on the wire, and the refusal is not counted. The failure sets the transport's sticky error (`c.err`), so the next `Read` returns that error, not EOF, and `read_to_eof` is false.

### 1.2 `command_octets_received`

The octets the transport read from the socket less the data octets its decoder produced (`Conn.Received`). On a session whose decoder reached the end without error, that is every octet received on the wire that is not delivered as data:
- each command's `IAC` and verb, and each option byte;
- a subnegotiation's `IAC SB`, its contents and its `IAC SE`;
- one octet for each escaped 0xFF: the leading `IAC`, since `IAC IAC` is one data octet (`decode`).

It is §7.2 item 4's definition, made exact to the code:

- `decode` counts each data octet in `data` (`c.received`), and every other octet it consumes is a command octet. The transport counts the octets each `nc.Read` returns. The difference is the field.
- **Where the two differ:** when `decode` stops on `telnet.ErrTooLarge` or `telnet.ErrNegotiation`, the rest of that read's buffer is counted as command octets but was not decoded.
  - On `main`, either error reaches `await` (`modules/ied/sel751/run.go`) as a plain read error. It becomes `errClosed`, and `stepFailed` gives `failed.transport_closed`. That is the code, unless the reply had already ended in a prompt.
  - `failed.response_too_large` comes only from the adapter's own budget (`errTooLarge`), and C2 has no negotiation code.
  - Either way the error is sticky, so the read that follows returns it and not EOF, and `read_to_eof` is false (§1.3). The from-relay direction is then not judged, so the overstatement widens nothing that is judged.
- **With `read_to_eof` true,** the from-relay payload on the wire equals, exactly: the transcript's received octets + `command_octets_received` + Σ (secret length − 10) over the redacted echoes. So D4's from-relay bound holds with no other slack. That bound is the transcript + `command_octets_received` + 2 × the echoes on a SEL-751. §8 test 7 checks the equality from outside the adapter (D4's N3).
- It is also ≥ 3 × the number of `WILL` and `DO` received, so it is ≥ 3 × `refusals`, since each refusal answers one (`answer`). Validate checks that (§2 rule 3).

### 1.3 `read_to_eof` and the close step

True when, after QUI was sent, the adapter's last read in the close phase returned the relay's end of stream (the peer's FIN: `io.EOF` from the socket), with the decoder in no error. Every octet the relay sent is then in the transcript or in `command_octets_received`. Otherwise it is false.

**EOF in place of D4's wording.** D4's M3 judges the from-relay direction when the run "sent QUI and did not end on a timeout, a response limit or the deadline". This proposal makes the relay's EOF the gate instead, on purpose, and D4 adopted it (6862377718, question 2):
- A run that sent QUI and timed out on no step can still leave relay octets unread at close, because `await` returns on a prompt and the quiet interval, not at EOF (D6's N6).
- A run that timed out on an earlier step and then sent QUI reads that step's late octets in the close phase, so at EOF its transcript is complete.
- Only EOF says that nothing the relay sent is missing.

**What the adapter does on `main` (D6's N6, answered from the code and the manual):**

- `quit` sends QUI and calls `await(time.Time{}, true)`. That returns on a prompt and the quiet interval, on the step timeout, on the budget, or at the end of the connection. `run` then closes the socket (`defer s.nc.Close()`). The adapter never waits for EOF.
- **S22 says QUI does not end the Telnet session:**
  - QUIT "Goes to Access Level 0" (Table 7.59, p. 7.73);
  - "To terminate a Telnet session, use the EXIT command" (Communications Interfaces, p. 7.3);
  - the Telnet Server note says to "Use the QUIT command prior to closing the Telnet-to-Host session" (p. 7.16).

  EXIT is not in the C3 register, and this proposal does not add it.
- **So with the adapter as on `main`, `read_to_eof` would be false on every SEL-751 run** (`documented-untested`, inference from S22). The adapter would see EOF only where the relay closed the connection itself, for example at `TIDLE` (1–30 min, default 15; Table 4.104, p. 4.250). No run waits that long.

**D1 ruled for the half-close, on conditions (6861454974, ruling 1). D3 and D6 agreed to it on #671.** As both checked, `run`'s deferred `Close` on `main` already sends a FIN at the same moment. `CloseWrite` sends that FIN and no data octet. Only the read side differs: it stays open, so relay octets that arrive after the FIN are read and acknowledged. On `main`, the closed socket answers them with an RST (D3; D6). The close step is pinned as follows (D3's and D6's B2):

1. **When the collector half-closes.** Only when `quit`'s `await` returned a prompt with no error and the transport is not dead. On any other path there is no half-close and the close is as on `main`. `read_to_eof` is then true only if that `await` itself ended at EOF.
2. **Who half-closes.** The collector, not the adapter, through the `HalfClose` seam (§3.3), with `CloseWrite`. That sends a FIN and no data octet or command.
3. **The read after it** writes nothing, and ignores prompts and the quiet interval. It ends at the first of:
   - EOF;
   - an error;
   - the response budget, with `closeAllowance` unchanged;
   - `MaxCommands`;
   - **the end `quit`'s `await` computed when QUI was sent**: QUI's send + `step_timeout_ms`, the `stepEnd` QUI's reply already shares.

   It never starts a new timer, and the invocation deadline is still not applied in the close phase. So the worst case stays one step past the deadline, as on `main`, and no new bound is added.
4. **What it reads** is part of the close phase's one reply segment, committed by `run`'s last `commit` with QUI's reply (D6's N7). `commit` and Validate read it as they read QUI's reply. A level prompt in it counts towards `access_level`, the highest level any reply showed (`dialogue.go`). The result still carries no code for it, because the adapter acts on nothing after QUI. So a relay that printed `=>` after the FIN leaves `access_level` at "1" or above, and that shows in the result. §8 test 7 pins it.
5. **If the relay neither closes nor sends,** what is sent is unchanged, but the run is longer (D3's note 4, D6's N2). The close step now runs to QUI's send + one step (15 s with `pipeline.go`'s default limits, up to 60 s at `MaxStepTimeoutMS`), where on `main` it ends after the quiet interval. Through that time:
   - `ended_at` moves later;
   - the collector holds its session and the asset's busy claim;
   - the relay holds one of its two Telnet sessions (§7), at Level 0.

   D4 says whether anything in the tie reads `ended_at` beyond C2 0.9's window. M4 is not judged for Telnet (D4's §3).
6. **A refusal asked for after the half-close** cannot be written, and the sticky error makes `read_to_eof` false (§1.1).
7. **The exclusion it lifts:** P4-4-HR24's "no change to the collector's own sessions", for this change only. D1 records that when it approves C2 0.10.
8. **On hardware,** how the relay answers a half-close is `unknown` (D2's note 3 on D4's M4 row). §9 gives the H-row.

0.10's field is the same whether the relay closes or not. Only its value differs. Against a relay that does not answer the half-close, D4's §5 item 4 covers every run until the H-row measures it (D4, 6862377718).

### 1.4 `rexmit_octets` and `rexmit_unknown`

Exactly one of the two is present in `session.telnet`. JSON `null` decodes as absent (Go's decoder leaves a pointer nil), so `"rexmit_octets": null` beside a token passes, and alone fails (D6's N3).

- **`rexmit_octets`** is the number of payload octets the collector's own socket retransmitted **to the device** over the session, as the collector's kernel counts them. It is an integer from 0 to 2⁵³ − 1. The socket knows nothing of what the device retransmitted, so the field says nothing of the other direction.
  - Windows: `TCP_INFO_v0.BytesRetrans`, from `WSAIoctl` with `SIO_TCP_INFO` version 0 on the session's socket (Windows 10 1703 and later, no elevation).
  - Linux: `tcp_info.tcpi_bytes_retrans`, from `getsockopt(TCP_INFO)` (kernel 4.19 and later).
- **Over-reporting is the direction that leads to a miss** (D4's N4). The node subtracts `rexmit_octets` from the sensor's overlap count. So every octet the collector over-counts credits an injection of the same size, and M6b misses it. Under-reporting gives noise. §8 test 8's pinned range therefore bounds the count from above as well as from below. The node's own sanity bound (0 ≤ value ≤ k × sent octets) is D4's, pinned in #673 or the detector brief. C2 checks only the type and range.
- **`rexmit_unknown`** is a closed token for why the count was not read:
  - `in-flight`: at the read, a payload octet had been written to the socket and not acknowledged, whether sent or still unsent, so it could still be sent or retransmitted (§3.3 gives each platform's test);
  - `call-failed`: the call returned an error;
  - `unsupported`: the build or kernel predates the field (Windows 10 LTSB 2016, Linux before 4.19), or the connection the `Dial` seam gave has no socket to ask (a replay or an in-memory pipe).
- **`unknown` fails closed** (D4's §3.1). On any `rexmit_unknown`, including a later minor's token (§2 rule 5), the node's M6b raises `own-session-mismatch` with `comparison M6b reason no-profile`.
- **`unknown` until measured** (D4's §3.1, with D3's notes 1 and 3):
  - whether `BytesRetrans` counts tail-loss probes, and how it counts a repacketized retransmission;
  - **keep-alive probes.** `endpointDialer` uses a zero `net.Dialer`, so Go's default TCP keep-alive (15 s) is on. With the close step now running up to one step, probes can fall inside the session. Whether a probe one octet below `snd_una` counts in `BytesRetrans`, or in `tcpi_bytes_retrans`, is `unknown`. The frame stage's keep-alive pair (#673 N-10) covers the sensor's side;
  - **written and unsent data on Windows.** `TCP_INFO_v0` has no unsent-octets field. A peer that advertises a zero window keeps a written line in the send buffer, where `BytesInFlight` reads 0, and the line may be sent and retransmitted after the read. That under-reports, which is noise and not a miss.

  Linux will be measured on CI-Linux. Windows will be measured on a GitHub-hosted Windows runner with WinDivert, after D7's inventory entry (D4-98). Until then the Windows half is `desk`.

## 2. Rules (`Result.Validate`)

1. **Presence** (D6's N5):
   - In a result of 0.10 or later, `session.telnet` present ⇒ `session.snmp` absent and `connected` true.
   - In a result whose minor is 0.10, the package's own minor, a connected session without `session.snmp` carries `session.telnet`. A later minor's result is not held to this half, so a later minor can add a third connected transport, an SSH session say, without a major. A reader that finds `session.telnet` absent on a Telnet result fails closed at the node (§4).
   - A 0.9 or earlier result that carries it fails ("`session.telnet` is new in 0.10"), as `session.snmp` does before 0.7.
2. `refusals`, `command_octets_received` and `read_to_eof` are each present. `refusals` and `command_octets_received` are integers from 0 to 2⁵³ − 1.
3. `command_octets_received` ≥ 3 × `refusals`.
4. `read_to_eof` true ⇒ `quit_sent` true. The code is not checked. A transport error is never EOF, because the transport's error is sticky (§1.2). That guarantee belongs to the adapter and is tested from outside (§8 test 7). Validate cannot check it from the result.
5. Exactly one of `rexmit_octets` and `rexmit_unknown`, where `null` is absent.
   - `rexmit_octets` is an integer in range.
   - In a result of the package's own minor, `rexmit_unknown` is one of `in-flight`, `call-failed` or `unsupported`.
   - In a later minor's result it is any token of the same form, lowercase letters and hyphens, at most 32 octets, and a reader takes it as `unknown`. That fails closed (§4).

`session.telnet` is strict inside: an unknown field in it is refused in a result of this package's minor or earlier, and ignored in a later one, as `DecodeResult` does today.

## 3. Who fills them

### 3.1 The transport (`modules/ied/telnet`, D2)

`Conn` gains a count of the octets read from the socket, and a method that returns it with `Stats` and `Received`. Nothing it writes changes.

### 3.2 The SEL-751 adapter (`modules/ied/sel751`, D2)

- Sets `refusals` and `command_octets_received` from the transport at `result`.
- In `quit`, under §1.3's condition 1, calls the collector's `HalfClose` seam, then reads as §1.3's condition 3 says: no writes, prompts ignored, ending at QUI's `stepEnd` at the latest. It is a loop of its own, not a second `await`. A second `await` would set a fresh `stepEnd`, and it would return on the prompt already held in `s.reply` (D3's B2).
- Sets `read_to_eof`: true only when the close phase's last read ended on the connection's end, with the decoder in no error and the socket's error `io.EOF`.
- Calls the collector's `Rexmit` seam once, after the session's last write or read, whichever is later, and before the socket is closed, on every connected path. On the normal path that is after the read to EOF ends (D4's N5). It copies the answer into the result.
- Closes the socket as on `main`, gracefully, on every path, `in-flight` included (D3's and D6's B1).

### 3.3 The collector's seams and read (`modules/security/collector`, D3)

D3 accepted this on #671 (6862434878), on the conditions below.

- **Two seams in `sel751.Config`,** which the collector sets beside `Dial`:
  - `HalfClose func(net.Conn) error`. It only calls `CloseWrite` on a `*net.TCPConn`, and returns an error for any other type. On nil or an error, the adapter reads on as on `main`, and `read_to_eof` can still be true only if the relay closes;
  - `Rexmit func(net.Conn) (octets int64, unknown string)`. It only reads: `getsockopt(TCP_INFO)`, or `WSAIoctl` with `SIO_TCP_INFO` version 0. It writes no option. Nil gives `unsupported`.
- **Neither seam can be reached from a monitoring permission, and neither sends a payload octet** (D3):
  - `SEL751Runner.Run` sets both from collector functions, never from a `RunPlan` field or anything a request carries;
  - both get the socket the `Dial` seam returned (`s.nc`), which `endpointDialer` already limits to the run's endpoint;
  - the platform code, through `SyscallConn`, lives in the collector, so no device-facing code gains a system call of its own.
- **The read rule**, which replaces D1's earlier "after EOF" (6854297364). D3 accepted it, and D1 took it in principle (6861454974, ruling 2):
  - The count is read once, on the session's own socket, after the session's last write or read, whichever is later. It is valid only when no payload octet written to the socket is unacknowledged, whether sent or unsent.
  - Why not "after EOF": a SEL-751 does not close after QUI (§1.3), and whether it answers the half-close is `unknown`. Waiting for EOF could make every run `unknown`, and M6b would then alert `no-profile` on every own run.
  - What the rule needs is that no payload octet is sent, and so none retransmitted, after the read. Nothing unacknowledged at the read excludes a retransmission of old payload. No write after the read excludes new payload.
  - The seam runs after the last write as well as the last read, because a session can end on a write: `await` returns on `ctx.Err()` or the deadline after a send, and `sendFailed` ends the session after a write.
  - Refusals are written only from inside a read, so they come before the seam. After the half-close no refusal can be written (§1.1).
  - The half-close FIN, the close and any later RST carry no payload.
- **Each platform's in-flight test.** The contract's test is in payload octets (D6's B1). A platform test may be stricter, which errs towards `in-flight` and so towards noise, but never looser:
  - **Linux:** `tcpi_unacked` = 0 and `tcpi_notsent_bytes` = 0 (D3's note 1; kernel 4.6 and later). `tcpi_unacked` counts segments, so an unacknowledged FIN also reads as in flight. D3 accepted that as the safe side.
  - **Windows:** `BytesInFlight` = 0. Whether an unacknowledged FIN counts in it is `unknown`. D3 is asked to say (D4's N5). If it does, an own run that reads before the relay acknowledges our FIN gets `in-flight` and alerts `no-profile`. That fails closed, and the read placed after the read to EOF makes it rare. Stage 2's own-run cells show whether that noise is zero. Unsent data is not visible on Windows (§1.4).
- **No abortive close** (D3's and D6's B1, D3 withdrawing that part of 6854286062):
  - On a path where data is in flight, the read gives `in-flight` and the socket closes as on `main`, gracefully. The token already fails closed, so whatever the socket retransmits after the read changes no value anyone judges.
  - An `SO_LINGER` 0 close would discard an unacknowledged QUI and send an RST. That would leave the relay at its level until `TIDLE` (S22 p. 7.16), and it would be a second change to the collector's sessions with no ruling behind it.
  - D4 drops the same sentence from its design §3.1 in #673.

### 3.4 SNMPv3

Not affected. UDP has no retransmission count, M6b is Telnet only (D4's §3), and an SNMPv3 result carries no `session.telnet`.

## 4. What an earlier reader does, and what a rollback costs

C2's readers accept every minor of major 0: an earlier one strictly, a later one forward (`version.Accepts`, and `DecodeResult` with `strictjson.Forward`). The readers of session facts on `main` are:
- the collector: `runaudit.go` and `runner_sel751.go`;
- the asset module: `modules/asset`, the SNMP check;
- the node: `platform/node/schedule.go` to `netintake.go`, the tie.

None of them reads anything 0.10 adds.

**The reader rule for a Telnet result without `session.telnet`** is the detector's (D4's N2, written into #673). Under rule 1 this arises only from a collector older than 0.10. The run's profile then exists but is partial, which is not design §3.2's case of no profile held. The detector:
- raises `comparison M6b reason no-profile` (design §3.1);
- judges M1 and M5 as usual, and M3 to the relay with the 194-octet tolerance (design §5 item 3);
- leaves M3 from the relay unjudged.

| Field | A 0.9 reader of a 0.10 result | A 0.10 reader of a 0.9 result | Rollback cost |
| --- | --- | --- | --- |
| `refusals` | Ignored. A 0.9 reader has no `own-session-mismatch` rule. | Absent. M3 to the relay takes the 194-octet tolerance. | See the closing row. |
| `command_octets_received` | Ignored. | Absent. The from-relay direction is not judged. | None beyond the closing row. |
| `read_to_eof` | Ignored. | Absent. The from-relay direction is not judged. | None beyond the closing row. |
| `rexmit_octets` / `rexmit_unknown` | Ignored. | Absent. M6b alerts `reason no-profile`. | See the closing row. |
| **The object as a whole** | A 0.9 node with a 0.10 collector reads every result and loses nothing, since it has no rule that reads the object. | The reader rule above: fail-closed noise, never a skip. | **The collector rolled back to 0.9 under a 0.10 node:** a `comparison M6b reason no-profile` alert for each tied Telnet flow until the collector is at 0.10 again, and the wider to-relay tolerance meanwhile. **The node rolled back to 0.9:** the fields are ignored, and the rule goes with C13 0.3 (D4's proposal). No stored data is lost, because a stored 0.10 result still decodes forward. D7's record of versions that roll back together should list C2 0.10 with C13 0.3 and the node build that reads them. |

A later token in `rexmit_unknown` (rule 5), read by 0.10, is `unknown`. So a later minor that adds a reason costs nothing.

## 7. The bound D3's stage-2 risk 1 asks for (6855320671 on #664)

An on-path attacker who completes real handshakes as the node can hold frame-stage entries, but only as many as the relay accepts Telnet sessions.

- **The SEL-751 documents 2 concurrent Telnet sessions:**
  - S22 Table 7.5, note a (p. 7.13): "PORT 1 concurrently supports … two Telnet … sessions";
  - Table N.2, "SEL-751 Capability for Different Protocols" (p. N.4): Telnet, 2 sessions.

  The two tables agree for Telnet. They disagree for FTP (two against one), so the manual's counts are not all consistent. `docs/device-capabilities.md` already records "2 concurrent Telnet sessions" (`documented-untested`).
- **Per relay is `inference`.** Table 7.5 note a says "PORT 1". On dual-port models both Ethernet ports serve PORT 1 under its `NETMODE` setting, with one `TPORT`, so the limit is taken to be per relay and not per Ethernet port.
- **The bound per SEL-751 is therefore `unknown`.** What the relay does with a third connection is not documented, and the answer changes the bound:
  - **refused or reset:** the entry is freed at once, so the attacker holds at most 2 entries per relay. While both are held, the collector's own dial meets a relay with no free session, and that run does not tie;
  - **handshake completed, then held unserved:** each such flow is an entry until `MaxConnectTimeoutMS` (30 s) frees it (D4's §3.3), so the bound is the attacker's connection rate × 30 s, not 2.
- The manual does not say which, so it is §9's second H-row. Stage 2 should have a case for each answer.
- **An idle attacker's session ends at `TIDLE`** (1–30 min, default 15; Table 4.104, p. 4.250), unless the attacker keeps it active. A relay with `ETCPKA := Y` also probes an idle peer (`KAIDLE` 10 s by default, same table), and an on-path attacker answers those probes.

## 8. Tests D6 is asked for

Tests 1 to 6 are contract tests in `tests/contract/`, written from this text. Tests 7 to 10 are integration tests, as 0.9's test 2 is in `tests/integration/sel751datef` (D6's N3). Each test has a control that can fail.

1. **Rule 1:**
   - a connected Telnet 0.10 result without `session.telnet` fails;
   - a not-connected result with it fails;
   - an SNMPv3 result with it fails;
   - a 0.9 result with it fails;
   - a connected 0.11 result without it decodes forward.
2. **Rules 2 and 3:**
   - each of `refusals`, `command_octets_received` and `read_to_eof` absent fails at 0.10 (D4's N1);
   - a negative count fails, and so does a count of 2⁵³; 2⁵³ − 1 passes;
   - `command_octets_received` = 3 × `refusals` − 1 fails, and = 3 × `refusals` passes.
3. **Rule 4:** `read_to_eof` true with `quit_sent` false fails. Its twin, with `quit_sent` true, passes.
4. **Rule 5:**
   - `rexmit_octets` and `rexmit_unknown` together fail, and so does neither;
   - a 0.10 token outside the three fails, and so does a negative or fractional count;
   - `"rexmit_octets": null` beside a token passes, and alone fails;
   - a 0.11 result with an unknown token of the stated form decodes forward, and the reader reads it as `unknown`. One that breaks the form fails.
5. **Strictness:** an unknown field inside `session.telnet` fails at 0.10 and is ignored at 0.11.
6. **Forward:** every 0.9 golden still validates under 0.10. **Backward** (a 0.10 golden read by the 0.9 code) is a new mechanism. Under D4-99 it is not written until the options in my comment on #671 are agreed.
7. **From outside the adapter,** against A6's recording simulator, which records the far side:
   - **The counts:**
     - On a run whose simulator offers options, a subnegotiation and an escaped 0xFF, `refusals` equals the refusals the simulator received.
     - On the same run, `command_octets_received` equals the octets the simulator sent less the data octets it sent.
     - On the run that reads to EOF, and with an echo of the secret so that the Σ term is not zero, the transcript's received octets + `command_octets_received` + Σ (p − 10) equal the octets the simulator sent (D4's N3). The equalities are asserted only on runs where `read_to_eof` is true.
   - **EOF:**
     - The simulator closes after the half-close: true.
     - It closes before the half-close: true.
     - It sends an RST after the half-close: false.
     - It sends relay octets over `closeAllowance`: false.
     - It sends a `DO` after the half-close: false.
     - It sends more than `MaxCommands` commands: false.
   - **The close step's end (D3's and D6's B2):**
     - The simulator answers QUI at half a step and then neither closes nor sends.
     - Pass: `read_to_eof` is false, and the close phase ends by QUI's send + one `step_timeout_ms`, within a margin pinned before the run.
     - Control: a mutant with a fresh `stepEnd` ends at 1.5 steps and fails.
   - **No half-close:** QUI gets no reply. There is no half-close, and the simulator's octet after our FIN draws an RST, as on `main`.
   - **A level prompt after the FIN:** the simulator prints `=>` after it. `access_level` shows it, and the code is unchanged (§1.3 condition 4).
   - **The passive proof:** in every case, the `DO` case included, the simulator records no octet from the client after the FIN.
   - **One leg through `SEL751Runner.Run`.** A nil `HalfClose` degrades silently to false and "not judged", which raises no alert. The control is the runner with `HalfClose` nil, which must give false.
8. **The collector's read:**
   - **On CI-Linux:** in a network namespace, drop at the receiver's ingress with nft (after the capture tap, so that a dropped segment is in the capture). Then `rexmit_octets` lies within a pinned range of the retransmitted octets counted from the capture of the same run. The range is pinned from above as well as below (D4's N4).
   - **A path with data in flight** gives `in-flight`, and the socket closes gracefully.
   - **The Windows leg** runs on a GitHub-hosted Windows runner with WinDivert, after D7's inventory entry (D4-98).
9. **The reader rule,** with D4's detector code:
   - a tied Telnet flow whose result lacks `session.telnet`, or carries any `rexmit_unknown`, alerts `comparison M6b reason no-profile`;
   - control: the rule removed, which gives no alert;
   - positive control: a tied Telnet flow with a full `session.telnet` within every bound gives no alert.
10. **No abortive close (D6's B1):**
    - On CI-Linux, in a network namespace, drop QUI's first copy at the simulator's ingress, then abort the run.
    - Pass: the simulator receives QUI once the drop ends, and no RST comes before it.
    - Control: an `SO_LINGER` 0 mutant, under which the simulator never receives QUI.

## 9. H-rows, written now for D1 to number with the stage-2 brief (D6's N1)

1. **How a SEL-751 answers the client's half-close after QUI's reply.**
   - **Question:** at a named firmware, does the relay:
     - (a) close with a FIN within the step;
     - (b) send an RST;
     - (c) send more octets first;
     - (d) hold the connection until `TIDLE` or until its keep-alive gives up?
   - **Method:** a passive capture of an ordinary collector run against a lab relay, with the owner's authorization. `main` already sends the same FIN at the same moment, so the row needs no new code to answer.
   - **Consequence:** under (b) or (d), `read_to_eof` is false on every run, and M3 from the relay is judged on no SEL-751 run. That is the miss for which option (a) of D1's ruling 1 was refused, and HR-24's closing measurement must say so. A simulator that closes on the FIN shows only that the code path works (`simulated`).
2. **What a SEL-751 does with a third concurrent Telnet connection.**
   - **Question:** is it refused, reset, or accepted and held unserved, and for how long?
   - **Method:** **a lab relay only, never a site relay,** with the owner's authorization. The test holds both of the relay's Telnet sessions, so it is not passive.
   - **Consequence:** it gives §7's bound, either 2 entries per relay or the attacker's rate × 30 s.

## 10. Limits and risks

- Every value here is from the adapter's own counts or the collector's kernel. A compromised collector can report anything, but the collector holds the device credentials and is already the trust root for its own runs (D3's model).
- **Readers who learn the password's length, p** (D3's note 2, D6's N4; the brief's "Uncertainty or safety risks"). No field gives p alone. Combined with other data, some do:
  - **To the relay:** with `refusals` exact, the sensor's `orig_payload` − (sent octets + 3 × `refusals`) = p − 10, from D4's M3 credential slot. Under 0.9 the refusals were unknown, which blurred this, except on a relay that negotiates nothing. The readers are #673 §7's, and #673 §7 records this residual.
  - **From the relay:** with `read_to_eof` true on a relay that echoes the secret, `resp_payload` − received octets − `command_octets_received` = Σ (p − 10) over the echoes. This is a second route for the same readers, and #673 §7 should name it beside the first.
  - **`rexmit_octets` alone:** when the only retransmitted segment is the credential line, `rexmit_octets` = p + 2. This needs no sensor count. It reaches the C2 result's readers: the collector, the node, and wherever the node keeps the result as sent (`collectorclient.Outcome.ResultJSON`). That set differs from the `network-observation` class #673 §7 names, and on those runs it undoes the fixed-length marker (C-A2-3).

  In each case this is the length only, and the last route needs a run with loss. On plaintext Telnet an on-path reader sees the password itself (HR-1, HR-2, HR-8). D3 adds these routes to the threat-model row #673 §7 names, when HR-24 closes.
- The half-close changes what the collector sends on no path. It changes how long a session to a relay that does not close is held (§1.3 condition 5).
- Nothing here contacts a device. Every behaviour of the SEL-751 above is from S22 and is `documented-untested`.
