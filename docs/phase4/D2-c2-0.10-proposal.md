# C2 0.10: a Telnet session's facts for HR-24's own-session profile (D2, 2026-11-13)

D2's proposal for `otsec.adapter/0.10`, under brief P4-4-HR24P (`docs/agent-handoffs.md`, "After D4-100"). It takes `docs/phase4/D4-hr24-design.md` §7.2 items 4 and 7 to contract text. D3, D4 and D6 review it, and D1 approves it in a decision entry. No contract code changes here. The code comes with the brief "The approved contracts in code".

- **Evidence class: `desk`.** Nothing here is built or run. Code is cited by function at `main` `65980515`. The manual cited is S22, the SEL-751 Instruction Manual, date code 20260910, from `reference/manuals-SEL/`; page numbers are the manual's own.
- **The collector's part (§3.3) is D3's, and it is marked awaiting D3.** C2 0.10's `rexmit_octets` is owned with D3 for the collector (D1, 6854297364 on #664). D3 is on another task, so this proposal states the text, and the PR comment for D3 asks the questions in §7.
- **What it changes:** one optional object, `session.telnet`, in a C2 result. No new code, status, phase, record kind or C1, C3, C7 or C9 change. `docs/phase4/D5-sensor-node.md` §1.10 is not touched.

0.10 adds, for a connected Telnet session:

1. `refusals` and `command_octets_received` (§7.2 item 4), which set M3's Telnet tolerances;
2. `read_to_eof`: whether the adapter read to the relay's end of stream after QUI (D6's N6, §4's "Relay output after the QUI reply" row);
3. `rexmit_octets`, or `rexmit_unknown`, which fails closed (§7.2 item 7, M6b).

## 1. The object

```json
"session": {
  "connected": true, "wake_sent": false, "language_probe": "accepted",
  "password_prompt": true, "credential_sent": true, "echo_scan": "performed",
  "access_level": "1", "quit_sent": true,
  "local_addr": "127.0.0.1:53114",
  "connected_at": "2026-11-13T20:15:02.418230115Z",
  "telnet": {
    "refusals": 2,
    "command_octets_received": 9,
    "read_to_eof": false,
    "rexmit_octets": 0
  }
}
```

and, when the collector could not read the count:

```json
  "telnet": { "refusals": 2, "command_octets_received": 9, "read_to_eof": false, "rexmit_unknown": "in-flight" }
```

`session.telnet` sits beside `session.snmp` (0.7), and is its Telnet counterpart: present exactly when the session is Telnet (no `session.snmp`) and `connected` is true. A result that never connected carries neither, as in 0.9. All four counts are numbers and a flag. None carries device bytes, so the node's profile stays numeric (D4's §3.2, D3's N1).

### 1.1 `refusals`

The number of three-octet refusals, `IAC DONT x` or `IAC WONT x`, that the transport wrote in the session. It is `telnet.Stats.Refusals` (`modules/ied/telnet`, `answer`), which counts a refusal only after its `Write` returned without error.

- **What it gives M3:** the client's only octets to the relay outside the transcript's sent data are the refusals (`telnet` package doc: "The refusals are the only other bytes it writes"). So the to-relay bound becomes the transcript's sent octets + 3 × `refusals` + 2, exactly, in place of 3 × 64 + 2 = 194 (D4's §5 item 3).
- **Its one undercount:** a refusal whose `Write` fails after putting part of its three octets on the wire is not counted. The write error ends the session (`telnet` package doc), so this happens at most once a session and costs at most 2 octets under the bound. Under-reporting gives noise, not a miss, because M3 tests for more.

### 1.2 `command_octets_received`

The octets the transport read from the socket less the data octets its decoder produced (`Conn.Received`). On a session the decoder reached the end of without error, that is every octet received on the wire that is not delivered as data: each command's `IAC` and verb, each option byte, a subnegotiation's `IAC SB`, its contents and its `IAC SE`, and one octet for each escaped 0xFF (the leading `IAC`; `IAC IAC` is one data octet, `decode`). It is §7.2 item 4's definition, made exact to the code:

- `decode` counts each data octet in `data` (`c.received`), and every other octet it consumes is a command octet. The transport counts the octets each `nc.Read` returns. The difference is the field.
- **Where the two differ:** when `decode` stops on `ErrTooLarge` or `ErrNegotiation`, the rest of that read's buffer is counted as command octets but was not decoded. Such a session ends `failed.response_too_large` or with the negotiation error, and never has `read_to_eof` (§1.3), so the from-relay direction is not judged on it, and the overstatement widens nothing that is judged.
- **With `read_to_eof` true** the from-relay payload on the wire equals the transcript's received octets + `command_octets_received` + Σ (secret length − 10) over the redacted echoes, exactly. So D4's from-relay bound (transcript + `command_octets_received` + 2 × echoes on a SEL-751) holds with no other slack.
- It is also ≥ 3 × the number of `WILL` and `DO` received, so ≥ 3 × `refusals` (each refusal answers one; `answer`). Validate checks that (§2 rule 3).

### 1.3 `read_to_eof`

True when, after QUI was sent, the adapter's last read in the close phase returned the relay's end of stream (the peer's FIN: `io.EOF` from the socket), with the decoder in no error, so that every octet the relay sent is in the transcript or in `command_octets_received`. Otherwise false.

**What the adapter does on `main` (D6's N6, answered from the code and the manual):**

- `quit` sends QUI and calls `await(time.Time{}, true)`, which returns on a prompt and the quiet interval, on the step timeout, on the budget, or at the end of the connection. `run` then closes the socket (`defer s.nc.Close()`). The adapter itself never waits for EOF.
- **S22 says QUI does not end the Telnet session.** QUIT "Goes to Access Level 0" (Table 7.59, p. 7.73). "To terminate a Telnet session, use the EXIT command" (Communications Interfaces, p. 7.3), and the Telnet Server note says to "Use the QUIT command prior to closing the Telnet-to-Host session" (p. 7.16). EXIT is not in the C3 register and is not proposed.
- **So on a SEL-751, as documented, `read_to_eof` is false on every run** (`documented-untested`, inference from S22). The adapter would see EOF only where the relay closed the connection of its own accord, for example at `TIDLE` (1–30 min, default 15, Table 4.104, p. 4.250), which no run waits for. The result: D4's M3 from the relay is not judged on any SEL-751 run, and §5 item 4 of D4's note covers every run, not only those that timed out. The to-relay direction, where a write shows, stays strict.

**One way to make it true, for D1's ruling (§6, point 1):** after QUI's reply, the adapter half-closes its socket (`CloseWrite`, a FIN, no data octet and no command), then reads to EOF, bounded by the step timeout, committing what arrives as the close phase's reply. Whether the relay answers a client's FIN with its own is `unknown` (D2's note 3 on D4's M4 row); if it does not, the read ends at the step timeout, `read_to_eof` is false, and the run is one step longer. This changes what the collector puts on the wire (a FIN one quiet interval earlier than today), which D4's note says it would not ("no change to the collector's sessions"). I recommend it, but it is the adapter's behaviour, not the contract's, so 0.10's field is the same either way.

### 1.4 `rexmit_octets` and `rexmit_unknown`

Exactly one of the two is present in `session.telnet`.

- **`rexmit_octets`** is the number of payload octets the collector's own socket retransmitted **to the device** over the session, as the collector's kernel counts them: on Windows, `TCP_INFO_v0.BytesRetrans` from `WSAIoctl` with `SIO_TCP_INFO`, version 0, on the session's socket (Windows 10 1703 and later, no elevation); on Linux, `tcp_info.tcpi_bytes_retrans` from `getsockopt(TCP_INFO)` (kernel 4.19 and later). The socket knows nothing of what the device retransmitted, so the field says nothing of the other direction. It is an integer from 0 to 2⁵³ − 1.
- **`rexmit_unknown`** is a closed token for why the count was not read:
  - `in-flight`: at the read, the socket had data sent and not acknowledged (`BytesInFlight` ≠ 0 on Windows; `tcpi_unacked` ≠ 0 on Linux), so later retransmissions could still happen;
  - `call-failed`: the call returned an error;
  - `unsupported`: the build or kernel predates the field (Windows 10 LTSB 2016, Linux before 4.19), or the connection the `Dial` seam gave has no socket to ask (a replay or an in-memory pipe).
- **`unknown` fails closed** (D4's §3.1): on any `rexmit_unknown`, and on a Telnet result with no `session.telnet` at all (§4), the node's M6b raises `own-session-mismatch` with `reason no-profile`. The node's own sanity bound (0 ≤ value ≤ k × sent octets, D4's §3.1) is the node's, not C2's; C2 checks only the type and range.
- **`unknown` until measured** (D4's §3.1, unchanged): whether `BytesRetrans` counts tail-loss probes and how it counts a repacketized retransmission. Linux is measured on CI-Linux with `netem`. The Windows half is `desk` until a measurement the owner allows.

## 2. Rules (`Result.Validate`)

For a 0.10 result or later:

1. `session.telnet` is present ⇔ `session.snmp` is absent and `connected` is true. A 0.9 or earlier result that carries it fails ("`session.telnet` is new in 0.10"), as `session.snmp` does before 0.7.
2. `refusals` ≥ 0 and `command_octets_received` ≥ 0, each at most 2⁵³ − 1.
3. `command_octets_received` ≥ 3 × `refusals`.
4. `read_to_eof` true ⇒ `quit_sent` true, and the code is not `failed.response_too_large`.
5. Exactly one of `rexmit_octets` and `rexmit_unknown`. `rexmit_octets` is an integer in range; `rexmit_unknown` is one of `in-flight`, `call-failed`, `unsupported`. A later minor's token is read by an earlier reader as `unknown` too, which fails closed (§4).

`session.telnet` is strict inside: an unknown field in it is refused for a result of this package's minor or earlier, and ignored for a later one, as `DecodeResult` does today.

## 3. Who fills them

### 3.1 The transport (`modules/ied/telnet`, D2)

`Conn` gains a count of the octets read from the socket, and a method that returns it with `Stats` and `Received`. Nothing it writes changes.

### 3.2 The SEL-751 adapter (`modules/ied/sel751`, D2)

- Sets `refusals` and `command_octets_received` from the transport at `result`.
- Sets `read_to_eof` in `quit`'s close-phase read: true only when that read ended on the connection's end with the decoder in no error (`await`'s `s.dead` branch after QUI, with the error `io.EOF`).
- Calls the collector's read seam (§3.3) once, after the session's last read and before the socket is closed, on every connected path, and copies its answer.

### 3.3 The collector's read (`modules/security/collector`, D3: **awaiting D3**)

Proposed text, for D3 to accept, change or refuse in the PR:

- `sel751.Config` gains a seam, `Rexmit func(net.Conn) (octets int64, unknown string)`, which the collector sets beside `Dial`. Nil gives `unsupported`. The platform code (the `SIO_TCP_INFO` call on Windows, `TCP_INFO` on Linux, through `SyscallConn`) lives in the collector, which already owns the dialer (`endpointDialer`), so no device-facing code gains a system call of its own.
- **The read rule, amended from D1's 6854297364:** it is read once, after the session's last read, on the session's own socket, and it is valid only with nothing in flight. D1's ruling reads it "after EOF". By §1.3, on a SEL-751 there is no EOF after QUI unless D1 adopts the half-close, so a rule that waits for EOF would make every run `unknown`, and M6b would alert `no-profile` on every own run. What the rule needs is that no data octet can be sent, and so none retransmitted, after the read: nothing in flight at the read, and no write after it. The adapter writes nothing after its last read (refusals are written only from inside a read), so "after the last read, with nothing in flight" meets that, EOF or not.
- **On a path where data is in flight** (a timeout, the deadline, an abort): the read gives `in-flight`, and the socket is then closed abortively (`SO_LINGER` 0), as D3's rule says, so that nothing is retransmitted after the read. An abortive close sends an RST to the relay. That ends the TCP connection as a FIN would; the relay's session then stays at its level until `TIDLE`, as it does today when a run ends without QUI (S22 p. 7.16). D6 reviews it as device behaviour.
- **Questions for D3:** (a) is the seam the boundary you want, or should the collector patch the result after the adapter returns (I chose the seam so the result is built in one place, as in 0.9 §1.4); (b) is "after the last read, nothing in flight" an acceptable form of your rule; (c) on Linux CI, is `tcpi_unacked` the in-flight test you want.

### 3.4 SNMPv3

Not affected. UDP has no retransmission count, M6b is Telnet only (D4's §3), and an SNMPv3 result carries no `session.telnet`.

## 4. What an earlier reader does, and what a rollback costs

C2's readers accept every minor of major 0: an earlier one strictly, a later one forward (`version.Accepts`, `DecodeResult` with `strictjson.Forward`). The readers of session facts on `main` are the collector (`runaudit.go`, `runner_sel751.go`), the asset module (`modules/asset`, the SNMP check) and the node (`platform/node/schedule.go` to `netintake.go`, the tie). None of them reads anything 0.10 adds.

| Field | A 0.9 reader of a 0.10 result | A 0.10 reader of a 0.9 result | Rollback cost |
| --- | --- | --- | --- |
| `refusals` | Ignored. It has no `own-session-mismatch` rule. | Absent. The Telnet profile has no exact to-relay tolerance. | See the closing row. |
| `command_octets_received` | Ignored. | Absent. The from-relay direction is not judged. | None beyond the row below. |

That is fail-closed noise, never a skip. | **The collector rolled back to 0.9 under a 0.10 node:** one `no-profile` alert for each tied Telnet flow until the collector is at 0.10 again. **The node rolled back to 0.9:** the fields are ignored, and the rule is gone with C13 0.3 (D4's proposal). ## 6. For D1's ruling

1. **`read_to_eof` and the half-close (§1.3).** As documented, a SEL-751 never closes after QUI, so the field is false on every run and M3 from the relay is never judged. Options: (a) accept that, and D4's §5 item 4 becomes every run; (b) the adapter half-closes after QUI's reply and reads to EOF within the step timeout. I recommend (b). It adds no command and no data octet, and it also gives D3's read its EOF.
2. **The read rule for `rexmit_octets` (§3.3).** With (a), D1's "after EOF" cannot hold on a SEL-751, and I propose "after the last read, nothing in flight". With (b), both hold where the relay answers the FIN. D3's answer comes first.

## 7. The bound D3's stage-2 risk 1 asks for (6855320671 on #664)

An on-path attacker who completes real handshakes as the node can hold frame-stage entries, but only as many as the relay accepts Telnet sessions.

- **The SEL-751's limit is 2 concurrent Telnet sessions.** S22 Table 7.5, note a (p. 7.13): "PORT 1 concurrently supports … two Telnet … sessions"; and Table N.2, "SEL-751 Capability for Different Protocols" (p. N.4): Telnet, 2 sessions. The two tables agree for Telnet. (They disagree for FTP, two against one, so the manual's counts are not all consistent.) `docs/device-capabilities.md` already records "2 concurrent Telnet sessions" (`documented-untested`). Dual Ethernet models share PORT 1 and one `TPORT`, so the limit is per relay, not per Ethernet port.
- **So the bound per SEL-751 is 2 held entries**, and while the attacker holds both, the collector's own dial meets a relay with no free session, a run that does not tie.
- **`unknown`, and it changes the bound:** what the relay does with a third connection. If its TCP stack completes the handshake and then holds the connection unserved, each such flow is an entry until `MaxConnectTimeoutMS` (30 s) frees it (D4's §3.3), and the bound becomes the attacker's connection rate × 30 s, not 2. If it refuses or resets the connection, the entry is freed at once. The manual does not say. It is a device question for an H-row, with the owner's authorization, and stage 2 should have a case for each answer.
- **An idle attacker's session ends at `TIDLE`** (1–30 min, default 15, Table 4.104, p. 4.250), unless the attacker keeps it active. A relay with `ETCPKA := Y` also probes an idle peer (`KAIDLE` 10 s by default, same table), and an on-path attacker answers those probes.

## 8. Tests D6 is asked for

Contract tests in `tests/contract/`, from this text:

1. Rule 1: a connected Telnet 0.10 result without `session.telnet` fails; a not-connected one with it fails; an SNMPv3 result with it fails; a 0.9 result with it fails.
2. Rules 2 and 3: a negative count, a count over 2⁵³ − 1, and `command_octets_received` = 3 × `refusals` − 1 each fail; = 3 × `refusals` passes.
3. Rule 4: `read_to_eof` true with `quit_sent` false fails; with `failed.response_too_large` fails.
4. Rule 5: both of `rexmit_octets` and `rexmit_unknown`, neither, a token outside the three, a negative or fractional count, each fail. A 0.11 result with an unknown token decodes forward, and the reader's profile reads it as `unknown`.
5. Strictness: an unknown field inside `session.telnet` fails at 0.10 and is ignored at 0.11.
6. Forward and back: every 0.9 golden still validates under 0.10; a 0.10 golden decodes under the 0.9 code (D6 builds the 0.9 package at its merge commit), with the object ignored.
7. **From outside the adapter** (as 0.9's test 2): against A6's recording simulator, which records the far side, `refusals` equals the refusals the simulator received, and `command_octets_received` equals the octets the simulator sent less the data octets it sent, on a run whose simulator offers options, a subnegotiation and an escaped 0xFF. A run where the simulator closes after QUI gives `read_to_eof` true; one where it does not gives false.
8. The collector's read (after D3 agrees §3.3): on CI-Linux with `netem` loss on loopback, `rexmit_octets` is within a pinned range of the retransmitted octets counted from a capture of the same run; a path with data in flight gives `in-flight` and an RST, with no data frame after the read in the capture. The Windows half stays `desk`.
9. The reader rule (with D4's detector code): a tied Telnet flow whose result lacks `session.telnet`, or carries any `rexmit_unknown`, alerts `own-session-mismatch` with `reason no-profile`; control: the rule removed, which gives no alert.

## 9. Limits and risks

- Every value here is from the adapter's own counts or the collector's kernel. A compromised collector can report anything, but the collector holds the device credentials and is already the trust root for its own runs (D3's model).
- `rexmit_octets` reports a count, not content, and adds no new reader at the site: it is a number about the platform's own socket.
- No field reveals the password's length. `refusals` and `command_octets_received` are about negotiation, and the transcript already stores the redaction marker, whose fixed length hides the secret's.
- Nothing here contacts a device. Every behaviour of the SEL-751 above is from S22 and is `documented-untested`.
