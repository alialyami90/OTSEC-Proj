# C5 0.7: the last hold codes, document series, and a bounded remover (D4-20, D4-32, D4-36)

C5, 2026-11-01. A proposal for `otsec.store/0.7`. Nothing here is built yet. Every result it promises will be `simulated`.

C5 0.7 carries three rulings:
- D4-20 rules 1 and 2: two hold codes;
- D4-20 rule 3: a remover for configuration reads that showed no difference;
- D4-32 item 2, as D4-36 defines it: the event-baseline checkpoint as a node document of the configuration class, with its own removal rule.

The store's part and the node's part are kept apart below. The store can enforce only what it can see, which is class, holds, commit order and a document's series. The node enforces what needs the audit chain.

*Revised at the reviews of C1, C2, C3 and C4 on `bd8f39e`, and of C6 on `945b6fc` (the storage named, section 4's checkpoint sentence and rollback note, and the added tests). The changes are: the closed pairing of kinds and series; the remover takes one series, and only three series can be removed at all; the event baseline's holds are stated; the finished learner's checkpoint stays until the next re-learn; and the node replays an audited removal at start.*

## 1. Hold codes (D4-20 rules 1 and 2)

- **`approved-difference`.** The snapshot and difference of a change that an approval covered. `Ref` is the `config.change_detected` record.
- **`superseded-baseline`.** A baseline record that a newer acknowledgement of the same kind replaced. `Ref` is that newer `config.baseline_acknowledged` (D4-20, B5's point 2).
- **Validation.** Both join the closed `HoldCode` set and `HoldReason.Validate`.
- **Priority.** A record wanted for two reasons is held for the first of these: `baseline`, `unapproved-difference`, `approved-difference`, `acknowledged-difference`, `restored-difference`, `superseded-baseline`. 0.7 exports the order as `HoldPriority`, so the node's fold and C6's tests use one list.
- **Event baselines too (C4).** The fold holds each asset's acknowledged baseline of each kind with `baseline`, with `Ref` its `config.baseline_acknowledged`. That is what it does on `main`, for a C9 snapshot of kind `configuration` and a C10 record of kind `event`. After a re-learn, the active event baseline is no longer the newest of its series, so its hold is what keeps it, and a detector that does not restore is rebuilt from it (D4-32). `superseded-baseline` covers both kinds. The remover cannot take a baseline of either kind anyway (section 3), so the holds are a second guard there. They remain the only guard against any later removal path.
- **Unknown codes.** The 0.6 rule stands: a reconcile that meets a code it does not know keeps that hold and raises `store-holds-reconciled`.

## 2. Document series (the validator tells the kinds apart, D4-32 item 1)

The store must tell evidence from working state, and it must find the newest record of a series without decoding every record after it. So the validator now also names the record's series, and the store keeps that name beside the record.

- **The validator.** `DocumentValidator` becomes `func(document []byte, capture *Capture) (DocumentInfo, error)`. `DocumentInfo` is `{Kind DocumentKind; Series string}`, and `Kind` is a closed set:
  - `evidence`: C9 snapshots and differences, and C10 baselines. These are what R3.5 and R3.6 keep.
  - `working-state`: the node's `otsec.eventcheckpoint/0.1`. It is not evidence and is not in the audit chain (D4-32).
- **The series, a closed pairing (C3's point 2).** The contract fixes which series belong to which kind, and `DocumentInfo.Validate` refuses any other pair:

  | Kind | Series | Document |
  | --- | --- | --- |
  | `evidence` | `config.snapshot` | a C9 snapshot, including a configuration baseline |
  | `evidence` | `config.difference` | a C9 difference |
  | `evidence` | `baseline.event` | a C10 event baseline |
  | `working-state` | `eventcheckpoint.learner` | the learner half of a checkpoint |
  | `working-state` | `eventcheckpoint.detector` | the detector half of a checkpoint |

  A configuration baseline is an acknowledged C9 snapshot, not a C10 document (C8, C2's review). It stays in `config.snapshot`, and its `baseline` hold keeps it, not the newest-of-series rule. `baseline.configuration` is never written. The validator sets `Series` from the document it has decoded, using C9's own constants (`config.KindSnapshot`, `config.KindDifference`), so the names cannot drift from C9. A C9 or C10 document never classifies as `working-state`, and a checkpoint never names an evidence series. Otherwise a checkpoint naming `baseline.event` would make the real newest baseline "not the newest of its series".

  An asset's stream is `config/<asset>`, so a series is per asset as well.
- **Storage (C6's point 1).**
  - **The format stays `otsec.platform-store/2`.** 0.7 adds to the format-2 schema in place. It does not bump the format, so a 0.6 binary still opens a 0.7 store.
  - **Two columns** on `events`: `doc_kind TEXT` and `doc_series TEXT`. Both are nullable with no default. The store sets them in the commit transaction for a configuration record, and leaves them NULL for every other class. A 0.6 insert names its own columns, so a record a 0.6 binary commits into a 0.7 store gets NULL in both.
  - **One index**, `CREATE INDEX events_by_series ON events (stream, doc_series, seq) WHERE doc_series IS NOT NULL`, for the newest-of-series query. It is partial, so on a 0.6 store it is empty when it is created, and the migration writes no index pages for existing rows.
  - **The migration at open.** The two `ALTER TABLE ... ADD COLUMN` statements and the `CREATE INDEX` run in one transaction, only when `doc_kind` is missing (checked with `pragma table_info`). A crash at open leaves all three or none, and a second open does nothing.
  - **A record with NULL in both** (committed before 0.7, or by a rolled-back binary) is refused by the remover (fail closed), and the newest-of-series check ignores it. That is safe, because no binary before 0.7 writes a checkpoint or any 0.7 series. On `main`, nothing writes configuration records yet, so no shipped store has any.
- **Why not reclassify at removal.** The newest-of-series check would then decode every later record of the stream, each up to 1.5 MiB. A column makes it one indexed query.

## 3. The remover (D4-20 rule 3, D4-32 item 2)

```go
// ConfigRemover removes unheld configuration records in bounded steps (0.7).
type ConfigRemover interface {
	RemoveConfig(ctx context.Context, stream StreamID, series string, seqs []Seq) (Removed, error)
}
```

It removes the named records with their captures in one transaction, committed at `SyncFull`. A capture is removed only when no retained record of any stream refers to it (PruneStep's rule, as for `Discard`). A seq that is no longer stored, or that is past the stream's last committed seq, is skipped, so a removal stopped partway is finished by calling it again. `Removed` reports the records and bytes removed and lists the seqs skipped, so the node sees a skip (C6).

**All or nothing.** The checks below run inside the transaction before anything is deleted. If any seq of the step is refused, the step removes nothing.

**When it runs (C6).** It runs while the database is collecting and while it is drain-only (in recovery), as pruning does, and when the configuration class is at its quota, which is when a removal matters most. It is refused, with nothing removed, when the database is not open.

**What the store refuses**, with `CodeInvalid` and nothing removed:
- a stream that is not of class `configuration`;
- a `series` outside `RemovableSeries` (C3's point 1). That set is `config.snapshot`, `eventcheckpoint.learner` and `eventcheckpoint.detector`. So differences and baselines of either kind cannot be removed through this API, whatever the node passes. D4-20 rule 3 removes only compared reads' snapshots (`config.read_compared` names `snapshot_seq`), and every stored difference is a change's difference, held by rules 1 and 2 (C2);
- an empty list, a repeated seq, seq 0, or more than `RemoveConfigStep` seqs;
- a held record, whatever its code;
- a record whose `Series` is not `series`, or that has none (pre-0.7);
- the newest record of its series in the stream, by commit order (seq). For a checkpoint, this is D4-36's "the checkpoint the node would restore": the newest committed one, chosen without decoding it. A newer checkpoint that is corrupt still makes the older one removable once the node's other conditions hold. The check is per series and per stream: a newer detector checkpoint does not make the newest learner checkpoint removable, and a newer record in another asset's stream changes nothing here. A step that names the newest and an older record is refused whole.

**`RemoveConfigStep`** is 4. A configuration record is up to 1.5 MiB, and the database's recovery reserve is that of one 1.5 MiB commit. Deleting a row writes its b-tree and freelist pages, not its overflow content, so the WAL of a step should be far below the reserve. The store test measures it (as E-A5-3 did for `Discard`), and 4 is lowered if the measurement says so.

**What the node checks before it calls** (the store cannot see these):
- **A no-difference read** (D4-20 rule 3 and its amendments). The audit chain shows the read as no difference, or as the same change, and its result is recorded. The read is not one of the two newest such reads of the asset and kind. The removal is by seq range of one asset and kind, never by time or space pressure. Each step writes a node-written `config.reads_removed` (C8 0.7), receipted before `RemoveConfig` is called, and a refusal to audit refuses the removal.
- **An audited removal that never ran (C3's point 3).** The fold moves past the reads a `config.reads_removed` names. So after a crash between that record's receipt and `RemoveConfig`, no later pass would choose those seqs again, and they would stay stored for good: no evidence is lost, but quota leaks. At start, before any new removal, the node replays the last `config.reads_removed` of each asset through `RemoveConfig`. That is idempotent, because a seq no longer stored is skipped.
- **A checkpoint** (D4-32 item 2, D4-36). A newer checkpoint of the same half and asset has committed, and the `node-eventbaseline` cursor was saved after that commit. No C8 record is written for a checkpoint removal.
- **A finished learner's last checkpoint (C4's point 3).** It is the newest of its series, so the store refuses it. Nothing newer is written to `eventcheckpoint.learner` until the next re-learn, so it stays, about 1.3 MB per asset at the widest, until that re-learn's first checkpoint supersedes it. That is bounded, and the quota floor already counts it (four checkpoint records per asset). Once the `config.baseline_recorded` of its baseline is in the chain, the node does not restore it (D4-32 item 2). This replaces the earlier sentence calling it removable then.
- **Counts.** Each removal is counted in node status and in a platform health event.

**Fault at the commit.** The audit record is written before the removal. So a crash between the two leaves the records in place and an audit that names more than was removed. Nothing is removed without a receipt. B6's case list in D4-20 covers this.

## 4. Compatibility

- **A 0.6 binary on a 0.7 store.**
  - It opens the store (same format).
  - It prunes nothing held, because the prune skips every row in the holds table whatever its code.
  - Its reconcile keeps the codes it does not know, and raises `store-holds-reconciled` for each such hold.
  - Its commits land with NULL in both new columns.
  - It has no checkpoint writer, so it writes no checkpoint. Its only reader of these streams, `locate`, compares digests and passes over a checkpoint record harmlessly (C6's point 3).
- **A 0.7 binary on a 0.6 store.** It adds the two columns and the index at open, in one transaction, with no rewrite of rows.
- **The cross-version test (C6's point 2).** C6 writes the 0.6 side on `main` before the store PR, with the newer writer stood in for by SQL using the names above. The store PR adds the 0.7 side: the migration and its idempotence, the refusal of a NULL-series record, and the newest-of-series check ignoring NULL rows.
- **The release note.** A rollback below 0.7 loses nothing that is held. What the operator sees instead:
  - one `store-holds-reconciled` alarm for each `approved-difference` or `superseded-baseline` hold, at every 0.6 start;
  - no checkpoints while rolled back, so the feeder restarts from the last 0.7 checkpoint when 0.7 returns;
  - configuration records committed while rolled back carry no series, so 0.7 can never remove them, and they count against the quota until an operator acts.

## 5. Tests

- **`contracts/store`:**
  - the new codes;
  - `HoldPriority` is a permutation of the closed `HoldCode` set, with every code exactly once, so a code added later cannot be left without a priority;
  - `DocumentInfo` over all ten kind-by-series pairs: the five in the table pass and the other five are refused. It also refuses an empty series, `baseline.configuration` and an unknown kind;
  - `RemovableSeries` is exactly the three named series;
  - `CheckRemoveConfig` refuses each argument case above and each series outside `RemovableSeries`, passes exactly `RemoveConfigStep` seqs, and refuses one more.
- **`platform/store`:**
  - every refusal on a real database, including the newest of a series, a pre-0.7 record, a `config.difference` and a `baseline.event`;
  - for each refusal (held, wrong series, NULL series, the newest), a step of four with only that one seq refused removes nothing;
  - per series and per stream, as in section 3, and a step naming the newest and an older record refused whole;
  - the class's counted bytes equal a recount from the tables after a full step, after a removal skipped and finished, and after a fault inside the transaction;
  - `Removed` lists a skipped seq, including one past the stream's last committed seq;
  - a removal with the class at its quota, and one in drain-only mode;
  - the migration at open, a crash during it, and its idempotence;
  - a removal skipped partway and finished by a second call;
  - a shared capture kept while another record refers to it. This is built from two C9 snapshots of one transcript, so the baseline's transcript survives the removal of a matching read (C2's note);
  - the WAL of the worst step measured against the reserve: four records of 1.5 MiB each with unshared captures, all removed, with the index and `auto_vacuum=INCREMENTAL` as the store opens, and the `-wal` size read after the commit and before any checkpoint, as in E-A5-3. If the step does not fit, `RemoveConfigStep` is lowered in the same PR;
  - fault injection at the commit, and the node's replay at start of an audited removal that never ran (C3's point 3).
- **`platform/node` (the node's checks):**
  - the two newest reads kept;
  - a read without its audit result refused;
  - a checkpoint removed only after the newer commit and the cursor save;
  - D4-36's case, where the newest checkpoint is committed and corrupt and the older one is still removable;
  - no C9 or C10 document classifies as `working-state`.
