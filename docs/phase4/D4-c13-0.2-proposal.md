**CH-49. Which end of a UDP flow is `src`, and which end is a service's server** (D4's N2 on #648; GT-PCAP's `dnp3-udp-*` cases, merged in #648). 0.1 states the first sender as `src` only for `midstream` (0.1 §4.1), and the server of a `service` as `ip.dst` (0.1 §4.3). Read together, a sensor that orients a `service` record like its flow would name the master as the server on a flow the outstation starts. This clause states the reading 0.1 leaves implicit. It adds no field and changes no field's meaning.

- **Input:** a UDP conversation or a layer-2 frame (`direction: none`); and a `service` observation on any flow.
- **Outcome, `src` (0.1 §4.1 as amended):** with `direction: none`, `src` (and, for layer 2, `l2.src_mac`) is the sender of the flow's first frame as the sensor saw it, as for `midstream`. This is GT-PCAP's rule (D6 plan §1) and the baseline note's (§2.2). A flow cut by `idle` and seen again is a new `start`, with its own first sender. No port, no protocol and no engine's naming of the ends decides `src`.
- **Outcome, the server of a `service` (0.1 §4.3 as amended):**
  - **Where the protocol's content shows the roles, the server is the end the content shows as the server.** For DNP3 it is the outstation: the end whose link-layer frames have DIR clear, DIR being set on a frame from the master (as `tests/integration/gt_pcap/gtlabel.py` reads it, #648). For a TCP flow with `direction: client-server` it is the SYN's receiver, as in 0.1.
  - **A `service` record's `ip` always puts the server at `dst`,** and its other end at `src`, **even where its flow's first sender was the server.** So a `service` record's `ip` may be the reverse of its own flow's `flow` records. The key (server address, `l4`, server port, `protocol`) is the same whichever flow carries it, and a sensor may emit it once on each flow (0.1 §4.2).
  - Where neither the handshake nor the content shows the roles, this clause adds nothing to 0.1.
- **Example** (GT-PCAP's `dnp3-udp-temp-port`): the master 192.0.2.14 sends its requests from udp/41017 to the outstation 192.0.2.20 at udp/20000, and the outstation sends its responses from udp/20000 to the master's udp/20000. These are two flows. The second has `src` 192.0.2.20:20000, because the outstation sent first on it. Any `service` record, on either flow, names 192.0.2.20 udp/20000 `dnp3` at `ip.dst`. A sensor that oriented the record like the second flow would name 192.0.2.14 udp/20000 as a DNP3 server, which the label fails.
- **Counted:** nothing new.
- **Meets:** no SL rule. 0.1 §4.1 and §4.3, stated; V-M6's `service` comparison.
- **Test:** U-2.

## 2. The transport (brief item 1)

**CH-1. The link is TCP, then TLS 1.3, then C13's framing.**

- **Input:** the live enrolment's address and port (SL-5, SL-9).
- **Rules:**
  - The node dials that address. TLS is 1.3 only, and both ends present a certificate.
  - Each end checks the other's key against the pin in the enrolment in force at that moment, at every handshake.
  - No session resumption, no early data and no pre-shared key. No system roots and no trust by name (SL-2, SL-12).
  - The certificate's own dates are not checked. The node enforces the enrolment's `not_after` (SL-8).
  - **ALPN** `otsec.netobs/0` is required at both ends (difference 8, ruling: the major only). With the major only, a minor mismatch fails at the hello as `hello`, with the schema saying why, and not as a TLS alert.
  - C13 sets no default port. The enrolment names it.
- **Outcome:** a handshake that fails any of these never reaches C13, and nothing is read or sent.
- **Counted:**
  - At the node, under `dial_failures`, a closed set that this proposal names for D5 to build:
    - `connect`: the TCP connect failed or timed out (D5's 5 s);
    - `handshake-timeout` (CH-4);
    - `tls`: TLS other than 1.3, no certificate, or no ALPN or another value;
    - `peer-key`: a key whose pin is not the enrolment's;
    - `expired`: a dial that would be due after `not_after`. The node does not make it, and counts it here because it is the one dial the enrolment, not the network, refuses (#628 §1.3, "Expiry").
  - `peer-key` and `expired` also write C8 `sensor.link_refused` under its cap: at most once in a stretch and once an hour for each sensor, generation and reason, its hour starting again at each succeeded `sensor.enrolled` of that sensor (C8-5; ruling 2 on #631; #644 §1.9 item 6). **A stretch ends at the next accepted hello from that sensor, and at a node start** (C8-5; D5's B5 on #634). The stretch is kept in memory, and the hour, which is durable, bounds what restarts add. The other three write nothing stored.
  - At the agent, every failed handshake counts under `handshake` in `agent.closes` (CH-43).
- **The dial limit before an address has answered** (SL-30, ruling 5 on #631). Until the node has accepted a hello from the enrolled pin at the enrolled address, it makes at most three dials to that address, then stops, with the standing alarm `sensor-dial-limit`, until an administrator acts.
  - A dial is one TCP connection attempt, whatever becomes of it: a refused connection counts. One attempt is one source port, abandoned at the node's 5 s connect timeout.
  - The count and the pair's proof are saved and synced before each dial, and belong to the address and the pin. CH-13 rows 5b and 6 save the proof.
  - **A count that cannot be trusted reads as spent** (SL-30; #644 §1.1; D4's B2 on #633). The count is kept in `sensorrun.json` under a write number, `write_no`, which the node also commits in the cursor of every open sensor database after each write of the file (CH-18), **and always in the database of the sensor being dialled** (SL-30 at #641's `467c1dd6`; D6's N5 on #641; #644 §1.1), so that the check that a file is behind never rests only on another sensor's database for a pair this sensor dials. A save SL-30 requires before a dial is complete only once that commit, in the dialled sensor's database, has returned; a dial to a sensor whose database is not open waits, as the dial condition requires (CH-4). **What "holds a write number" means** (SL-30; D3's ruling, comment 6839793110 on #641; #644 §1.1): the file's write numbers start at 1, and 0 says that no file has been written. A sensor database holds a write number when it has a cursor, and **a first cursor of 0 is a number**: it is what a database created at commissioning carries before any file is written, and a node killed after the first file write and before the commit that follows finds the file at 1 and the cursor at 0, which is current. A database **holds no write number only when it has no cursor at all.** A file whose `write_no` is below **the highest number that any sensor database holds** is **behind**; a file missing while any sensor database holds a number **above 0** is **lost**. A file behind, lost or unreadable reads as spent, unless a cursor of the live generation proves the pair (CH-18). A file missing while no database holds a number above 0 is a new node's and reads as empty, **unless a live enrolment's database is missing or has no cursor, which reads as lost** (below).
  - **A sensor database missing under a live enrolment is lost, whatever the run file holds** (SL-30, from D6's B2 on #641; #644 §1.1). The count of every pair of that sensor reads as spent, answered or not, no cursor proves a pair, and the next dial waits for an administrator's re-arm with `sensor-dial-limit` standing.
    - **So that a missing database always means a lost one,** the node creates the sensor's database, for a sensor that has none, and commits its first cursor **before it writes the succeeded `sensor.enrolled`**, and so before `sensors.json` and before any dial (SL-30; #644 §1.3 enrolment step 3). That first cursor carries the run file's current `write_no`, or 0 when no file has been written, so a database made at commissioning is current with the file. A power cut that undoes the creation's rename while the audit record survives also reads as lost; it fails closed and costs a re-arm.
    - **A database that holds no write number (no cursor) while the run file holds one reads as lost,** as an absent one does, and so does a live enrolment's database with no cursor, whatever the file holds. That covers a creation interrupted before its first commit (D3's rule 2 on #641, comment 6838033945). A cursor of 0 is not "no write number".
    - **"Spent" holds across any number of restarts until a re-arm** (same rule). When the node reads a sensor's counts as spent because its database is lost, it acts in this order: it writes `sensorrun.json` with every pair of that sensor marked spent, under a new `write_no`, and syncs it; only then does it create the database again, whose first commit carries that `write_no`. At every later start it finds the spent marks, or a file behind the database (spent), or a database lost again or holding no write number (spent). Only a re-arm's grant clears a spent mark.
  - After a first accepted hello the address has shown itself to be the sensor, and CH-38's redial rule applies.
  - The mechanism and the re-arm are the node's (#644 §1.1). The alarm's name is final in both documents (ruling 4 on #634).
- **Meets:** SL-2, SL-4, SL-8, SL-12, SL-18, SL-30.
- **Test:** M-6, and the rig's SL-T3 (`peer-key`), SL-T5 (`expired`), SL-T8 (TLS 1.2, resumption) and SL-T23 (the dial limit), with its legs (o), a run file replaced by an older copy or deleted (control: a node that trusts a readable file, which dials twice more), (p), the sensor database deleted after two dials to a pair that has not answered, with the run file kept, with it replaced by its copy from before the second dial, and with it deleted too (control: a node that reads a missing database as a new node's and takes the file as it finds it, which makes one, two and three more dials), and (q), the node restarted twice after (p)'s first case with the file put back before each start, and once killed between the database's creation and its first commit: no source port until a re-arm (controls: a node that marks nothing before it creates the database again; a node that trusts the file while the database holds no write number), and **(r), commissioning and a cursor of 0:** a `new` enrolment of a pair that has never answered, on a node with no run file, restarted before any dial: three source ports, then none; again, killed after the first dial's file write and before the cursor's commit: the next start reads the file as current and the count as one, two more source ports, then none; again, with the enrolment's record made to fail after the database's creation and the node restarted: the enrolment is not live, and once applied again, three source ports (controls: a node that reads a cursor of 0 as no write number holds the pair spent after the kill and opens no source port; a node that creates the database only at the first dial reads it as absent at the first restart and opens none). The node's tests are `TestDialLimitLostDatabase`, `TestDialLimitSpentAcrossRestarts`, `TestRunFileRolledBack` and `TestRunFileFirstWriteKill` (#644 §1.1, §1.4).

**CH-2. Framing runs in both directions, with a small cap from the node.**

- **Input:** every frame, in either direction: a 4-byte big-endian length, then one JSON document in UTF-8.
- **Outcome:**
  - A length above `MaxChannelFrame` (64 KiB) from the sensor closes the node's connection (`frame-too-large`), as 0.1 does (`FramesTooLarge`).
  - A length above `MaxNodeMessage` (1 KiB) from the node closes the agent's connection (`frame-too-large`).
  - The node's two messages are under 300 bytes, so 1 KiB holds them with room, and no more (SL-19: "small and bounded").
- **Counted:** `frame-too-large` under `link_closes`, or under `agent.closes`.
- **Meets:** SL-19, SL-20.
- **Test:** M-2.

**CH-3. One connection for each sensor.**

- **Input:** a second connection for one `sensor_id`.
- **Outcome:**
  - The node opens at most one connection for each `sensor_id`, with at most one dial in progress. Its intake refuses a second concurrent connection for the same sensor and closes it (`second-connection`, difference 7).
  - The link agent, on completing a handshake with the node's key while it holds an older connection, closes the older one (`superseded`) and keeps the newer. The node holds one key, so the newer connection is the node's current one, after a node restart for example.
- **Counted:** `second-connection` under `link_closes`; `superseded` under `agent.closes`.
- **Meets:** SL-12.
- **Test:** M-5.

**CH-4. Timeouts, at both ends.**

| Name | Value | Input and outcome | Counted |
| --- | --- | --- | --- |
| `HandshakeTimeout` | 10 s | A TLS handshake that has not completed within it is abandoned (SL-12) | `handshake-timeout` under `dial_failures`; `handshake` under `agent.closes` |
| `HelloTimeout` | 10 s | The first frame from the other end must arrive within it after the handshake: `node-hello` at the agent, `sensor-hello` at the node. Otherwise the connection closes | `node-hello-timeout` under `agent.closes`; `hello-timeout` under `link_closes` |
| `IdleTimeout` | 30 s | A direction that carries no frame for 30 s is closed by the end that receives it. The sensor sends a `tick` every `SensorTickInterval` (10 s) and the node an `ack` at least every 10 s (CH-8, CH-9), so 30 s is three missed messages | `idle` under either set |

- **The node dials only when it can send `node-hello` at once** (D4's B5 on #633; #644 §1.1's dial row): the sensor's database is open, its cursor is read and parses (CH-18), and the sensor's intake has started with its restored hold recovered (`Link.RecoverHold`), so that `taken` includes every record the hold released (CH-17). Otherwise it does not dial, and `sensor-state-unread` stands with cause `position` (CH-45), beside `sensor-store-not-open` when the database is the reason and `sensor-intake-not-started` when the intake is. *Why:* a node that dialled with its cursor unread would send no `taken`, read the counter as 0 at CH-13 row 3, save the agent's oldest run over the real cursor at row 6, and store that run's records a second time. The other conditions of a dial (the enrolment, the state, the link key, the asset address, SL-30) are the node's (#644 §1.1).
- *Test:* M-4's leg, the node's `TestNoDialWithoutPosition`: with the database open and its cursor's read made to fail, and again with the intake not started, no SYN goes to the sensor and `sensor-state-unread` stands with cause `position`. *Control:* a node that dials with the cursor unread, which saves the agent's oldest run over the real cursor and stores its records a second time.
- The node's own TCP connect timeout (5 s) and write deadline (10 s for each node message) are node-local (#628 §1.1).
- **Meets:** SL-12, SL-20.
- **Test:** M-4.

**CH-38. Redialling: the node decides from its own state** (D3 B1).

- **Applies once the address has answered as the sensor** (SL-30). Before the node's first accepted hello from the enrolled pin at the enrolled address, CH-1's limit of three dials applies instead, and nothing here grants a fourth.
- **Input:** a connection the agent closed with TLS `close_notify`.
- **Outcome:** the node redials at once only when both of these hold. Otherwise it backs off: 1 s, doubling to 60 s, ±20 % jitter, reset after a connection whose hello was accepted and which lasted 60 s (#628 §1.1).
  - It had accepted a hello on that connection, and had taken (CH-17) every `seq` up to the connection's run's `newest_seq`, as the hello and the ticks last stated it. That is what `run-complete` means, judged by the node and not by the sensor. **A close before the node has read a `sensor-hello`** (the agent's `binding` after a `renew`, for one) is never a finished run: it takes the back-off, and is counted under `link_closes` as `closed-before-hello` (CH-11; D4's note 5 on #633).
  - At least `RedialFloor` has passed since its last immediate redial to this sensor.
- **`RedialFloor` is 10 s** in both documents, by D1's ruling on round two. D3 accepts it. It is one `SensorTickInterval`. It caps the turns a sensor can force at 360 an hour.
  - With 64 runs to drain (CH-46), the current run can wait about 11 minutes behind an outage's old runs at 10 s, and about an hour if back-off applies (D6; §16).
  - Each turn costs the node a handshake, one durable save of a new run (CH-13), a cleared open-flow table, and at most one alarm per connection.
- **Counted:** `run-complete` closes, `closed-before-hello`, and immediate redials refused for the floor, in status.
- **Meets:** SL-20, SL-30; D3's §11.2 reason for keeping a link's opening and closing out of the audit chain.
- **Test:** M-7, M-11, and the rig's SL-T23.

## 3. The channel's messages

### 3.1 Closed sets and number forms

**CH-5. Each direction has a closed set of message types, and every number has one form.**

| From | Types | Stored? | Numbered (`seq`)? |
| --- | --- | --- | --- |
| Node | `node-hello`, `ack` | No | No |
| Sensor | `sensor-hello`, `tick` | No | No |
| Sensor | `heartbeat`, `observation` (0.1's records, 0.2's fields) | The observation; the heartbeat feeds the node's capped health events (CH-45) | Yes, as in 0.1 |

- **At the agent,** a frame from the node whose type is not in its set, or that carries a field not listed here, closes the connection (`type`). A known type that fails its strict decode closes it too: `node-hello` or `ack`. The agent has no code path from a node message to anything but its trim cursor (SL-19).
- **At the node,** an unknown type from the sensor is refused with `CodeType`, counted under `sensor-record-refused`, and the connection stays open, as in 0.1. An alert-shaped record is refused this way (0.1 §1, AP-34).
- **Numbers.** Each field written "decimal from 1" is 0.1's `seq` form: `^[1-9][0-9]{0,19}$`, at most 2^64 − 1. Each field written "decimal from 0" is `^(0|[1-9][0-9]{0,19})$`, at most 2^64 − 1. Another form is refused as `form` in a record, and closes the connection in a message (that message's reason).
- **A run counter at 2^64 − 1** cannot begin another run. The agent stops, and only a new enrolment with a new key, which restarts the counter (CH-12), lets it run again.
- **Meets:** SL-19 (a closed set in each direction; SL-T12's contract test).
- **Test:** M-1, M-3.

### 3.2 `node-hello`

**CH-6. The node's first frame on every connection.**

```
{ "schema": "otsec.netobs/0.2", "type": "node-hello",
  "sensor_id": "<uuid>", "generation": "<decimal from 1>",
  "taken": { "run_counter": "<decimal from 1>", "run_id": "<uuid>", "seq": "<decimal from 0>" } }
```

- `sensor_id` and `generation` are the live enrolment's.
- `taken` is the node's saved position for this sensor (CH-18): the highest run it has accepted, and its taken position T in that run (CH-17), 0 when nothing of the run is taken yet. `taken` is absent when the node holds no position that carries over to this generation: none saved, or **a saved position whose generation is below the generation at which the node's position began**, which reads as none (CH-12, CH-18; SL-R6; D5's B4 on #634).
- **With the sensor database lost** (CH-18; SL-31; D1's ruling, comment 6837755868 on #644): when `sensorrun.json` holds a copy of the run, and the copy's generation is not below the generation at which the position began, `taken` names that copy's `run_counter` and `run_id` with `seq` 0, the form for a run with nothing taken. Otherwise `taken` is absent. *Why:* with the copy kept as the node's saved run and no `taken` sent, the agent would offer that run as a new run with `prior`, and CH-13 row 5 would close it as `hello` at every dial; dropping the copy would let a replayed older run in as new. The agent treats this `taken` as any other (below): a run it no longer holds is not applied, and its true hello is judged.
- The node sends it only after it has finished every record it read on its previous connection to this sensor, or left it untaken. So `taken` is exact when it is sent. Its read loop is synchronous (#628 §1.15, D5-12).
- **At the agent:**
  - A `sensor_id` or `generation` other than its own enrolment's closes the connection (`binding`).
  - A `taken` that names a run the agent does not hold, by counter and `run_id` together, is not applied.
  - A `taken.seq` above the newest `seq` of the named run is not applied either, and is counted under `taken_ahead` (D3 B2).
  - In every case the agent then sends its true hello, and the node judges it (CH-13). That is how a node that saw a copy, or a restored snapshot, learns of it.
- **Meets:** SL-13, SL-16, SL-19, SL-31, SL-R6.
- **Test:** M-3, H-4, H-8, H-9.

### 3.3 `sensor-hello`

**CH-7. The sensor's first frame, after it reads `node-hello`.**

```
{ "schema": "otsec.netobs/0.2", "type": "sensor-hello",
  "sensor_id": "<uuid>", "generation": "<decimal from 1>",
  "run_counter": "<decimal from 1>", "run_id": "<uuid>",
  "current": true|false,
  "first_seq": "<decimal from 1>", "newest_seq": "<decimal from 0>",
  "drops_channel": "<decimal from 0>",
  "lost": [ { "from_utc": "<RFC 3339 UTC>", "to_utc": "<RFC 3339 UTC>" } ],
  "prior": { "runs_skipped": "<decimal from 0>", "records_lost": "<decimal from 0>",
             "lost": [ { "from_utc": "...", "to_utc": "..." } ],
             "previous_end": "clean|unclean", "started_by": "agent|capture|engine|enrolment" },
  "pinned_by": "signature|console",
  "config_digest": "sha256:<hex>",
  "buffer_bytes": "<decimal from 1>",
  "sensor_utc": "<RFC 3339 UTC>" }
```

- `schema` names the minor of this connection's records (CH-36).
- `run_counter` and `run_id` name **the one run this connection carries** (§4.4).
- `current` is true exactly when that run is the agent's current run, and false when it is an older run being flushed. The node uses it to find where a backlog ends (CH-39; asked by #628 §1.6).
- `first_seq` is the `seq` of the first record the agent will send on this connection. On a resume it may be at or below the node's taken `seq`. The node then drops those records as duplicates (CH-14).
- `newest_seq` is the newest `seq` of this run that the agent has numbered **and synced** when it sends the hello (CH-19). It is at least `first_seq` − 1, and equals it when the agent has nothing of this run to send yet.
- `drops_channel` and `lost` declare this run's losses so far: the count of numbered records the agent evicted unacknowledged (CH-15), and their capture spans (CH-40). The agent states only values it has synced (CH-19).
- `prior` declares what came before this run (CH-16, CH-42). It is present exactly when the hello opens a run the node has not accepted.
- `pinned_by`: how the agent's end was pinned (CH-33).
- `config_digest`: the run's digest (CH-32), so that the node checks it at each hello (D5's note on #627).
- `buffer_bytes`: the agent's buffer bound (CH-20), from 16 MiB to 64 GiB on the wire. A value below the site floor (256 MiB) raises `sensor-buffer-small` (CH-20).
- `sensor_utc`: the sensor host's clock when it sent the hello (CH-22).
- **The node's checks** are in CH-13, in order. Any field outside its form or range closes the connection (`hello`).
- **D3's SL-13 listed "the oldest `seq` its buffer still holds".** It is replaced by `newest_seq` and `drops_channel`. `first_seq` carries the same fact, and D3 accepts the change (D3's note 5).
- **Meets:** SL-5, SL-13, SL-14, SL-16, SL-17.
- **Test:** M-3, H-1.

### 3.4 `tick`

**CH-8. A live message from the sensor every `SensorTickInterval` (10 s), never buffered.**

`SensorTickInterval` is the sensor's 10 s. It is not the node's periodic pass, which `service.go` calls `TickInterval` (60 s on `main`).

```
{ "schema": "otsec.netobs/0.2", "type": "tick",
  "sensor_id": "<uuid>", "run_id": "<uuid>",
  "sensor_utc": "<RFC 3339 UTC>",
  "newest_seq": "<decimal from 0>", "sent_seq": "<decimal from 0>",
  "drops_channel": "<decimal from 0>",
  "lost": [ { "from_utc": "...", "to_utc": "..." } ],
  "buffered_records": "<decimal from 0>", "buffered_bytes": "<decimal from 0>" }
```

- **When it is sent.** The agent makes a `tick` at the moment it sends it: once straight after its hello, then every `SensorTickInterval`. It is never written to the buffer and never numbered.
- **Its fields.**
  - `sent_seq` is the highest `seq` the agent has sent on this connection, **or skipped on it as unreadable (CH-19)**, or `first_seq` − 1 when it has done neither (D6 B5; D5's B3 on #634). A skipped `seq` is never sent later, so counting it as sent makes it a counted gap at the node (CH-15), and T can pass it. Without that, an unreadable last entry of a flushed run would be above every `sent_seq`, T would stop below the run's `newest_seq`, no `ack` could cover it (CH-9), and the connection would carry that run until either end restarted. The agent sends only synced records (CH-19), so `sent_seq` is never above the synced `newest_seq`.
  - `newest_seq`, `drops_channel` and `lost` are the connection's run's (CH-15, CH-40), as synced values only.
  - `buffered_records` and `buffered_bytes` are the agent's whole buffer, every run, for status and for `sensor-buffer-filling` (CH-45).
- **Why a new message, and not the heartbeat.**
  - A heartbeat is a numbered record. During an outage it waits in the buffer, and after the outage it arrives behind the backlog, so the node cannot tell an outage from a skew.
  - A `tick` is made when it is sent. So the node's received time minus its `sensor_utc` is the skew plus the network delay plus any queueing behind records written before it on the same stream. That queueing grows while a backlog drains. CH-22 takes the least offset of several ticks for that reason, and §16 states it.
- **The node's checks, at each tick.** A failure closes the connection (`tick`):
  - `sensor_id` and `run_id` must be the hello's. A tick under another `sensor_id` also counts once under `sensor-id`, and writes `sensor.link_refused` (`sensor-id`) under the cap (CH-11, C8-4; SL-10).
  - `newest_seq`, `drops_channel` and `sent_seq` must not fall below their earlier values on this connection.
  - `sent_seq` must be at most `newest_seq`.
  - Each span in `lost` must have `from_utc` at or before `to_utc`. A new or wider span must come with a rise in `drops_channel` (CH-40). A span that ends after `sensor_utc` is not a fault: CH-40 cuts and counts it.
  - A tick that fails its strict decode also closes as `tick`.
- **The rate rule** (difference 10). A tick that arrives less than `TickMinSpacing` (5 s) after the previous accepted tick on this connection, other than the first tick after the hello, is counted under `tick_early` and does nothing more. It gives no skew sample, runs no gap check and resets no timer.
- **What an accepted tick moves at the node:**
  - the skew estimate (CH-22);
  - the gap check (CH-15);
  - the never-received count up to `sent_seq` (CH-15);
  - `sensor-unreachable`'s timer (CH-44);
  - status.
- **D3 accepts `tick` as a fourth type** from the sensor (D3's note 1, difference 10). D3 amends SL-19's list once 0.2 is approved (ruling 6).
- **Meets:** SL-14, SL-17, SL-19, SL-20.
- **Test:** T-5, S-2, S-5.

### 3.5 `ack`

**CH-9. The node's acknowledgement.**

```
{ "schema": "otsec.netobs/0.2", "type": "ack",
  "run_counter": "<decimal from 1>", "run_id": "<uuid>", "seq": "<decimal from 0>" }
```

- It names the connection's run and the node's saved taken position T in it (CH-17).
- The node sends one within `AckMaxDelay` (1 s) of its saved T moving, and at least once every 10 s while the connection is open, as a keepalive (CH-4).
- **At the agent** (D3 B2, D6 B6):
  - the run must be the connection's;
  - `seq` must be at least the last `ack` on this connection;
  - `seq` must be at most the larger of `first_seq` − 1 and the highest `seq` the agent has sent, or skipped as unreadable, on this connection: its latest `sent_seq` (CH-8).

  Otherwise the connection closes (`ack`). There is no `taken.seq` term: an `ack` of `first_seq` − 1 on a resumed run that has nothing to send is valid. So is the node's keepalive of the T it holds, which CH-17 lets cover `seq`s never received.
- **Its only effect** is to move the agent's trim cursor for that run (CH-19). An equal `ack` changes nothing.
- **Counted:** `ack` under `agent.closes`.
- **Meets:** SL-15, SL-19.
- **Test:** A-1.

### 3.6 The order of a connection

**CH-10. The order, after the handshake:**

1. The node sends `node-hello`.
2. The agent reads it, chooses the run to offer (CH-16), and sends `sensor-hello`, then a `tick`.
3. The node judges the hello (CH-13). If it accepts it, it reads records, ticks and heartbeats, and sends `ack`s. If it refuses it, it closes the connection.
4. The agent sends the run's records in `seq` order from `first_seq`, a `tick` every `SensorTickInterval`, and new records of the same run as it numbers and syncs them.
5. When the agent has an `ack` that covers the newest record of a run that is not its current run, it closes the connection with TLS `close_notify` (`run-complete`). The node then redials under CH-38.

- **Outcome of a break in this order:**
  - A second `node-hello` closes the agent's connection (`node-hello`).
  - A second `sensor-hello` closes the node's (`hello`).
  - A record or tick before the hello also closes the node's (`hello`).
- **Counted:** those reasons, and `run-complete` under `agent.closes`.
- **Meets:** SL-13, SL-14.
- **Test:** M-3, S-3.

### 3.7 What closes a connection, and what refuses one record

**CH-11. Two kinds of fault, kept apart.**

- **A channel fault closes the connection,** because the state of the exchange can no longer be trusted. Each one is counted by reason at the end that closes.
- **A record fault refuses the one record,** and the connection stays open, as in 0.1. It is counted under `sensor-record-refused` by reason.

**The node's close reasons, a closed set:**

| Reason | When | C8 `sensor.link_refused`? |
| --- | --- | --- |
| `hello` | The first frame is not a valid `sensor-hello` of a minor the node knows (CH-36): a 0.1 peer, another type first, a strict-decode failure, a field outside its form or range; a second hello; `prior` present on a resume or absent on a new run; a `lost` span that breaks CH-40's checks | No |
| `hello-timeout` | No hello within `HelloTimeout` | No |
| `binding` | `sensor_id` or `generation` differ from the enrolment of the key that authenticated; `pinned_by` differs from the value kept for this generation (CH-33) | Yes, `binding` |
| `run-regressed` | CH-13 rows 3 and 5a | Yes |
| `run-forked` | CH-13 row 4 | Yes, and the link is held (SL-16) |
| `run` | A record's `run_id` is not the hello's | No |
| `tick` | CH-8 | Yes, `sensor-id`, when the tick's `sensor_id` differs from the hello's (CH-8, SL-10, C8-4). No for every other `tick` fault |
| `idle` | CH-4 | No |
| `frame-too-large` | CH-2 | No |
| `store` | A store error that is not a final outcome (CH-17; difference 7) | No |
| `position-not-saved` | The node could not save the position before it accepts a hello: the new generation on a `renew`'s first resume (CH-13 row 5b) or a new run (row 6) (D4's note 7 on #633). The name is #644 §1.1's, and the alarm is `sensor-position-not-saved` (#644 §1.4) | No |
| `second-connection` | CH-3 | No |
| `enrolment` | CH-37: a revocation, or **any enrolment of the sensor applied while the connection is open, a `renew` with the pin unchanged included**, or the revocation fast path (#644 §1.3; SL-R6; D4's B1 on #633, D1 in D4-90) | No: the decision's own records are C8 `sensor.revoked` or `sensor.enrolled` (D3's §11.2) |
| `shutdown` | The node is stopping, including a restart to take an edited `network_sensor` entry (CH-37) | No |
| `state-unread` | A record in the node's own sensor-state fold cannot be parsed, so the node's state cannot be read. The node closes every open sensor connection and dials none until the state is read (D1's ruling on #633; #644 §1.3). It is fail-closed, and it implies nothing about the sensor. The alarm is `sensor-state-unread`, cause `fold-record` (CH-45) | No |

**`closed-before-hello`** is a key of `link_closes` and not a node close reason: the agent closed the connection after the handshake and before the node had read a `sensor-hello` (its `binding` after a `renew`, for one). It is not `hello-timeout`, and it is never `run-complete` (CH-38; D4's note 5 on #633; #644 §1.1). M-8's closed set of node reasons does not include it.

**What the sensor sees of a node close.** The node's close reason is its own count and never crosses the link: every close is a TLS close with no C13 message (CH-37). So a new node reason, `state-unread` included, changes nothing at the sensor. The agent keeps its buffer, counts the end under `idle`, `shutdown` or not at all, and resumes from `taken` when the node next dials (CH-16).
- **What a `state-unread` close costs in the field** (D5's N10 on #634; #644 §1.3). If the fold record becomes readable, the link resumes from `taken` with the sensor's buffer intact (M-10). If it does not, the state stays unknown, and only a `rekey` or a `replace` is accepted (C7-4): each needs the sensor's console, starts the node's position again, and has the sensor discard its buffer, declared in `prior` (CH-12). The interval is a coverage gap with cause `held` (CH-45).
- A 0.1 reader never meets a close reason, because none is stored.

**The agent's close reasons, a closed set,** counted in `agent.closes` (CH-43): `handshake`, `node-hello`, `node-hello-timeout`, `binding`, `ack`, `type`, `idle`, `frame-too-large`, `superseded`, `run-complete` and `shutdown`. The last three are not faults.

**A record refused, with the connection left open,** at the node:

- Every 0.1 reason stands: C13's codes (`decode`, `schema`, `form`, `range`, `order`, `conflict`, `hash`, `type`, `missing`), and `platform/sensorlink`'s reasons (`sensor-id`, `seq`, `counter-decrease`, `stored`).
- A record whose `sensor_id` is not the hello's is refused as `sensor-id`, and writes `sensor.link_refused` (`sensor-id`) under D3's cap (SL-10).
- 0.2 adds no reason for a record. The checks on 0.2's fields use the existing codes, each named where it is defined.

**Not audited:** a link opening or closing. Only C8-4's six reasons write `sensor.link_refused` (D3's §11.2, C8-4 and C8-7). The rest are counts in status, under #644 §1.9's caps (CH-45). **The cap is for each sensor, generation and reason** (C8-5; ruling 2 on #631): at most once in a stretch and once an hour for each, and its hour starts again at each succeeded `sensor.enrolled` of that sensor. A stretch ends at the next accepted hello from that sensor, and at a node start (C8-5; CH-1).

- **Meets:** SL-10, SL-14, SL-19, SL-20.
- **Test:** M-1, M-8 (the set in each direction pinned by a contract test), M-10, M-11.

**CH-37. A close for an enrolment decision** (D3 B5).

- **Input:** while a connection is open, the node applies one of these:
  - a revocation of the sensor (SL-R2), or the revocation fast path that a pending revocation file triggers (ruling 3 on #628, #628 §1.3);
  - **any enrolment of its `sensor_id`, whatever its reason, a `renew` with the pin unchanged included** (SL-6, SL-R6; D4's B1 on #633, adopted by D1 in D4-90). One rule with no branch on the reason. Its cost: after a `renew`, the node's redials end at the agent's `binding` until the sensor's end holds the renewal (SL-5 step 6), each counted as `closed-before-hello` (CH-11); the pair keeps its proof (SL-30), and the interval is a coverage gap with cause `held` (CH-45).
- **Outcome, in this order,** which follows SL-R2 and #644 §1.3:
  1. From the decision on, the node takes no further record of the connection, and sends no `ack`.
  2. It closes the connection at once, with TLS `close_notify` and no C13 message (SL-R2, SL-R7).
  3. After its read loop has returned, it commits every record its hold still holds for the sensor, tied or untied, and then takes each stream's `through_seq` (SL-R3).
  4. A revocation then writes `sensor.revoked`, as SL-R2 orders it.
- **An edited `network_sensor` entry** takes effect only at a restart, because the configuration is read at start. So the running connection closes as `shutdown`. After the restart the node does not dial, because the entry no longer equals the enrolment (SL-9). That is not an `enrolment` close (D6's condition).
- **Counted:** `enrolment` and `shutdown` under `link_closes`.
- **Meets:** SL-6, SL-9, SL-R2, SL-R3, SL-R6, SL-R7.
- **Test:** M-9, and the rig's SL-T10.

## 4. Runs, order and resume (brief items 2 and 3)

### 4.1 Generation, run counter, `run_id`, and a new enrolment

**CH-12. At the sensor.**

- **`generation`** is the enrolment's, a decimal from 1 (SL-5). It is carried in both hellos and in no record.
- **`run_counter`** is a decimal from 1. A run begins, and the counter rises by one, **whenever any of the four programs of SL-3 starts**: the socket holder, the frame stage, the engine or the link agent (SL-3, SL-14). "The capture stage" means the socket holder and the frame stage together (SL-3).
  - **One cascade is one new run** (D3's note 6 on #634). A socket holder that restarts ends the frame stage and then the engine. The agent sees that as one end of its streams, and begins one new run once every program has started again, not one for each.
  - **Each stage ends when its input ends** (SL-3). The frame stage ends when the socket holder's pipe ends, and the engine ends when the frame stage's pipe ends.
  - **How the agent learns of a restart.** The frame stage sends its counters, and the socket holder's that crossed the first pipe (CH-26, CH-29, CH-31), to the agent over a one-way local stream. The agent reads the engine's output over another (SL-3, SL-22). The end of either stream means that a program upstream stopped, so a socket holder that restarts alone is seen too. The agent begins a new run before it takes anything from the restarted programs.
  - **[S2]** How the engine's output is read, and so how its end is seen, depends on the engine. If a restart is missed, the node keeps open-flow entries the engine has forgotten (D3's assumption table).
- **`run_id`** is a lowercase UUID the agent draws at the start of each run, as in 0.1.
- **The agent writes the new counter and `run_id` to disk, and syncs them, before it numbers the run's first record,** and so before any hello names the run. A crash after that cannot bring the same counter back under another `run_id`, which the node would read as a fork (SL-14).
- **Each record still carries `sensor_id`, `run_id` and `seq`,** as in 0.1. The generation and the counter are in the hellos alone, and the node maps the `run_id` it accepted to them (SL-13, SL-14).
- **Order** is by (`run_counter`, `seq`) within the position that the node keeps (CH-18).
- **A new enrolment** (ruling 5; D3's note 11). Its outcome depends on the enrolment's signed `reason` **and on whether the sensor's pin is unchanged**, never on the reason alone (D3's condition on ruling 5). D3 adds to C7 0.11 that `renew` needs the same pin, and `rekey` and `replace` a different one, each `denied` otherwise.
  - **`renew` with the pin unchanged:** the generation rises. The run counter, the agent's buffer and the node's saved position all carry over, so the outage's buffered records are flushed under the new generation. Nothing is discarded. An expired enrolment, renewed, therefore loses nothing.
  - **Any other enrolment (`new`, `rekey`, `replace`), or a revocation:** run 1 of the new generation begins, and the node's position for the sensor starts again (SL-16).
    - **How the node makes the position start again** (SL-R6; D5's B4 on #634; #644 §1.3). The node keeps, for each `sensor_id`, **the generation at which its position began**: a `new`, a `rekey` and a `replace` set it to their own generation, and a `renew` with the pin unchanged keeps it. It is kept in `sensors.json` and can be folded from the `sensor.enrolled` records (their `generation`, `sensor_spki`, `reason` and `previous_spki`, C8-2). **A saved position whose generation is below it reads as none:** `node-hello` carries no `taken` (CH-6), and CH-13 row 3 reads the saved counter as 0. *Why:* deciding the carry-over from the live generation's reason and pin alone fails across two enrolments with no accepted hello between them. A `rekey` under which no hello is accepted, then a `renew` of the new pin, would carry the older key's position over; the first hello would close as `run-regressed`, write a false replay record, and never earn SL-30's proof, so the link would stop at the dial limit.
    - **It is never done by writing a reset cursor at the enrolment** (D5's B4 on #634, comment 6835767712): under SL-30 a cursor of the live generation proves the pair, and that pair has not answered.
    - **A position that reads as none, or that row 6's save replaces, does not drop what it owes** (SL-31; #644 §1.3). Before the cursor is replaced, the node writes every `lost` gap still marked owed and the `sensor.run-loss` of a `prior` still marked owed, or carries those marks into the new cursor. A kill in between gives them twice, never not at all. *Test:* H-8's second half; the rig's SL-T24 (e).
    - The agent discards from its buffer every record the node did not acknowledge, and declares them in the first hello of the new generation: `prior.records_lost` with their count, and `prior.lost` with their capture spans (CH-40). It is never silent.
    - The previous key no longer passes the node's handshake, so the records cannot be sent (SL-6).
    - **On `replace`, the old host may never send that hello.** So the node also records its own count of the old generation's unsent tail: the last `newest_seq` that host stated, less T. It goes in a `sensor.run-loss` event (D6's loss table). **That `newest_seq` is kept in the cursor** (CH-18), as the last value stated when the cursor was saved, so the count survives a node restart since the last connection (D5's N8 on #634).
  - D3 confirmed this against SL-R3, with the pin condition above (D3 on #627, comment 6802832834).
- **Counted:** at the node, the records a new-key enrolment discarded, from `prior` and from its own count (CH-16).
- **Meets:** SL-3, SL-5, SL-6, SL-13, SL-14, SL-16, SL-R3, SL-R6.
- **Test:** H-3, H-5, H-6, H-8, H-11.

**CH-42. How the previous run ended** (D6 B3, ruling 4).

- **Input:** a hello that opens a new run carries `prior.previous_end` and `prior.started_by`.
- **The fields:**
  - `previous_end` is `clean` only when every program whose stop ended the previous run left a clean-stop marker that the agent read before it began this run. Otherwise it is `unclean`.
  - `started_by` names which program's start began this run: `agent`, `capture` or `engine`, or `enrolment` for run 1 of a new key's generation. **`capture` covers either half of the capture stage,** the socket holder or the frame stage, because the agent sees both stop as the end of one stream and cannot tell which half it was.
  - The socket holder, the frame stage and the agent each write their own marker at a clean stop.
  - **[S2]** How the engine's clean stop leaves a marker depends on how the engine is run under its service manager (assumption A8).
- **Outcome at the node:**
  - On `unclean`, the node records a possible loss in its `sensor.run-loss` event, under #628 §1.9 item 5's cap (CH-45). The loss is the numbered records written since the previous run's last sync, up to `buffer_sync_ms` (CH-19), and, when `started_by` is `capture` or `engine`, whatever that program held and had not written, which the sensor cannot count.
  - A crash therefore never reads as a clean restart.
- **Counted:** unclean run ends, in status.
- **Meets:** SL-14 ("a loss nobody owns"); SL-22's "a crash is counted".
- **Test:** S-6.

### 4.2 Judging a hello

**CH-13. At the node.**

- **Input:** the node's saved position for the sensor (CH-18): `run_counter`, read as 0 when there is none or when the position reads as none (its generation below the generation at which the position began, CH-12), `run_id`, and taken `seq`; and the hello. With the sensor database lost, the saved run is the run file's copy at `seq` 0 when CH-6 sends it, and none otherwise (CH-18).
- **The checks,** in this order. The first failure decides:

| # | Check | Outcome |
| --- | --- | --- |
| 1 | A `sensor-hello` of a minor the node knows (CH-36), strictly decoded, every field in its form and range: `buffer_bytes` from 16 MiB to 64 GiB; `newest_seq` at least `first_seq` − 1; `pinned_by` and `prior.*` in their sets; every span in `lost` and `prior.lost` passing CH-40's checks | Else close, `hello` |
| 2 | `sensor_id` and `generation` equal the enrolment of the key that authenticated | Else close, `binding` |
| 3 | `run_counter` is not below the saved one | Else close, `run-regressed` |
| 4 | Equal `run_counter`, another `run_id` | Close, `run-forked`. The node keeps the sensor `fork-held` (CH-18) and stops dialling it until an administrator enrols it again with a new key, or revokes it (SL-16) |
| 5 | Equal `run_counter` and `run_id`: **a resume** | `prior` must be absent, and `drops_channel` must not be below the D the node holds for the run (CH-15); else close, `hello`. **5b: a resume under a higher generation than the saved position's**, which is how a `renew` with the pin unchanged carries its run over (CH-12). **Row 5b applies only when the node carried the position over to the live enrolment's generation, which it does for a `renew` with the pin unchanged and for nothing else** (CH-12; D3's note 3 on #634; ruling 1 on #634). Any other resume under a higher generation closes, `hello`. Before it accepts the hello, the node saves the new generation in the cursor (CH-18), and a save that fails closes, `position-not-saved`. That save also serves as SL-30's proof for the renewed pair, which otherwise reads as unproven until the agent next starts a run (D4 on #631 at `1889d929`). **5a:** `newest_seq` below the saved taken `seq` closes, `run-regressed`. The agent sends only synced records (CH-19), so the node can hold more of a run than the sensor's disk only when that disk went back: a restored snapshot, a copy, or a file system that lost synced data (A5) (D3 B2) |
| 6 | A higher `run_counter`: **a new run** | `prior` must be present, else close, `hello`. **First, the node runs CH-15's check of G against D for the run the cursor still holds,** because the save below overwrites G and D (D5's N9 on #634). Before it accepts the hello, the node saves in the cursor, in one `SaveSourceCursor` (CH-18): the new counter and `run_id`, with taken `seq` 0; `prior`'s counts, spans, `previous_end` and `started_by`, with its owed mark (CH-16); the spans of the hello's own `lost`, with their cut ends and owed marks (CH-40); and the run's `config_digest` (CH-32). It writes the second copy of the run, with its generation, to `sensorrun.json` (CH-18). A save that fails closes, `position-not-saved` (#644 §1.4) |
| 7 | `pinned_by` equals the value kept for this generation, or is the first one seen in it | Else close, `binding` (CH-33) |
| 8 | `config_digest` against the expected digest (CH-32) | A difference raises `sensor-coverage-mismatch`, and does not close |
| 9 | `buffer_bytes` at least the site floor, 256 MiB (CH-20) | Below it raises `sensor-buffer-small`, and does not close |

- **On a new run,** `prior.runs_skipped` must equal the hello's `run_counter` − the saved `run_counter` − 1. A difference does not close, because closing would blind the node. It raises `sensor-gap-undeclared` (reason `runs`) under CH-45's cap.
- **A new run clears** the node's open-flow table, as any new `run_id` does today (`hold.go`, D1 on #576). A run's `config_digest` is kept with it (CH-18), and a record whose digest differs from it is refused as `conflict` (CH-32).
- **Counted:** each close reason, under `link_closes`.
- **Meets:** SL-5, SL-10, SL-13, SL-14, SL-16, SL-19, SL-31, SL-R6.
- **Test:** H-1, H-2, H-4, H-7, H-8, H-9.

### 4.3 Within a run: duplicates, re-ordering, gaps and their declaration

**CH-14. Each record on a connection.**

- **Input:**
  - Let P be the run's saved taken position T (CH-17) **at the moment the record is read**, not its value at the hello. At the hello P is `taken.seq`, or 0 on a new run. It can rise during the connection when a release commits held records **of the same run** (CH-17). A release of an earlier run's held record never moves it.
  - Let L be the highest `seq` the node has read on this connection, which starts at `first_seq` − 1.
- **A record that decodes strictly takes its `seq`,** whatever later check refuses it, `sensor-id` included, so that L moves and no false gap is counted. This changes `platform/sensorlink`'s order today, which refuses `sensor-id` before it reads a `seq`. **D5 builds this.**

| A record whose... | Outcome | Counted |
| --- | --- | --- |
| `run_id` is not the hello's | Close, `run` | `link_closes` |
| `sensor_id` is not the hello's | Refused; C8 under D3's cap; the connection stays open (SL-10); it moves L | `sensor-id` |
| `seq` is at or below L | Refused (a re-ordered or repeated record); the connection stays open | `seq` |
| `seq` is above L and at or below P | Dropped as a **duplicate**: never stored twice, no alarm; it moves L | `duplicate` |
| `seq` is above L and above P | Read as in 0.1. Above L + 1, the `seq`s between that are above P are this run's gap (CH-15) | — |

- A record refused before a `seq` can be read (`decode`, `schema`, `type`) takes no `seq`. The tick's `sent_seq` covers it (CH-15).
- **A resend of a record that the node's restored hold has, or has already released** (#628 §1.4):
  - **Already released:** the release moved the saved T past it (CH-17), so the resend is at or below P and is a duplicate by position.
  - **Still held:** the hold drops the resend, matched by `run_id` and `seq`, and counts it under `duplicate`.
  - Either way the resend is counted under `duplicate`, T moves past it, only the held copy commits, and nothing is stored twice or lost.
- **Meets:** SL-10, SL-14.
- **Test:** S-1.

**CH-15. A gap must be declared, and is checked whenever the run's state can change.**

- **G**, the run's gap at the node, is the count of the run's `seq`s above P that the node never read. It grows in three ways:
  - when a record arrives above L + 1 (CH-14);
  - on a resume whose `first_seq` is above P + 1 (by `first_seq` − P − 1), or on a new run (by `first_seq` − 1);
  - **at each accepted tick, by every `seq` at or below its `sent_seq` that the node has not read** (D6 B5). So a record refused before its `seq` could be read, even the last of a run, is a counted gap, and T can pass it (CH-17).
- **D**, the run's declaration, is the largest `drops_channel` the sensor has stated for the run, in a hello, tick or heartbeat. It counts the run's numbered records that the agent evicted, or could not read back, before the node acknowledged them (CH-19, CH-20).
- **The check: G at most D.** D may exceed G, because a record the node took, but whose `ack` reached the agent after the eviction, counts in D and not in G.
- **When it runs** (D6 B4): at each accepted tick; when a connection of the run ends; and when the hello of a later run of the same sensor is judged, **before CH-13 row 6's save overwrites G and D** (D5's N9 on #634), so that a crash between that save and the hello's acceptance cannot lose the check.
- **Outcome:** if G is above D, the node raises `sensor-gap-undeclared` (reason `seq`), with the excess. Its status alarm rises once for each rise of the excess in a run (#628 §1.4), and its health events stay under CH-45's cap, at most 4 an hour for each sensor (#628 §1.9 item 5).
- **A falling `drops_channel`** closes the connection in a tick (`tick`) or a hello (`hello`), and is refused as `order` in a heartbeat (`Follows`). The agent states only synced values (CH-19), so a crash does not make it fall.
- **G and D are kept with the position** (CH-18), so the check holds across a node restart (D5-3).
- **A rise of D,** whichever message carries it, feeds the node's `sensor.counters` health event (CH-45; D3's note 4), so a declared loss leaves a durable trace.
- **Meets:** SL-14, SL-15.
- **Test:** S-2, S-5 (with its leg for the check before row 6's save).

**CH-40. A loss carries its capture spans, and the node marks them** (difference 3, ruling).

- **Input:** the agent keeps, for each run, the capture spans of the records it evicted or could not read before the node acknowledged them. A span runs from the earliest `first_utc` (or heartbeat `at_utc`) to the latest `last_utc` (or `at_utc`) of a series of such records.
- **The declaration.** The run's spans are carried as `lost` in `sensor-hello` and `tick`, and for whole runs and discarded generations as `prior.lost`. Each list is the run's full set, at most `MaxLostSpans` (8) disjoint spans, oldest first. When a ninth would be needed, the two spans with the shortest time between them are merged, so a list may cover more time than was lost, and never less.
- **The checks** (D3's change 4). A declared loss switches off the node's one independent check, own-session, for its span, so the node checks it and shows it:
  - **An impossible span closes the connection.** A span whose `from_utc` is after its `to_utc` closes it as `tick`, or as `hello` for `lost` and `prior.lost` in a hello.
  - **A span that widens with no rise closes the connection the same way.** A span that is new, or wider than the spans the node holds for the run, must come with a `drops_channel` **above Ds, the D at which the run's spans were last accepted**, or, for `prior.lost`, with a `prior.records_lost` above 0 (#644 §1.6; D5's N8 on #641). Ds is 0 for a run with no span accepted. When the node accepts a new or wider span it sets Ds to the message's `drops_channel`.
    - *Why Ds and not D:* a heartbeat carries `drops_channel` and no spans (CH-15), so a heartbeat made after an eviction and read before the tick that declares its span raises D first. Judged against D, that tick would show no rise and close an honest sensor. Ds moves only when spans are accepted, so the rise that pays for a span is counted once.
  - **The node keeps the run's spans in the cursor, in the transaction that admits them** (SL-31, D3's ruling (b),; D5's B2 on #634 and D4's B2 on #633). The spans the node holds for a run, those of `prior.lost` included, each as stated and with its cut end and owed mark (below), and Ds, are saved in the sensor database's cursor (CH-18) **in the same `SaveSourceCursor` that admits them,** or in CH-13 row 6's save for `prior.lost`, before the message that carried them is acted on. They are never kept apart from D, so they cannot fall behind it, and a rename lost at a power cut cannot touch them. `sensorrun.json` holds no span. After a node restart, a resume's unchanged `lost` list is therefore not new, and passes. *Why not the sensor's word after a loss of the node's own* (SL-31's reasons against options (a) and (c)): a span the node never saw rise would go unchecked, and a span it had cut would be cut again at the restart, keeping `own-session-unseen` off on the node's own sessions for that time.
  - **A save that fails** leaves the message unacted on and closes the connection as `store` (CH-17): nothing is admitted that is not saved with its D.
  - **With the sensor database lost** (CH-18), the node holds no D, no Ds and no spans. The hello's spans, in `lost` or `prior.lost`, are then new against a D of 0, admitted only with the count the sensor states, and each opens a `lost` gap with its cut end fixed at its receipt. That is loud, and it trusts nothing the node still held (SL-31).
  - **Each span's gap is owed from the save that admits it** (SL-31; #644 §1.6). The span is saved with a mark that its `lost` gap is owed. The mark is cleared only by a later cursor save made after the gap's `sensor.coverage-gap` event has committed; until then the marked span is the event's hold. After a restart the node writes the gap of every span still marked, and raises `sensor-records-lost`. A kill between the two writes gives the gap twice, never not at all.
  - **A span that reaches past the present is cut, not refused.** A span may end after the message's `sensor_utc`, because the sensor's clock may have been stepped back since (CH-21). That is not a channel fault. The node still opens the `lost` gap and raises the alarm below. The cut follows these rules, so that a span neither closes an honest sensor later nor keeps the own-session check off for good (D6 and D3 on round three).
  - **The node keeps two things for each span: the span as stated, and a cut end.**
    - The cut end is fixed once, when the node accepts the message that first carries the span. It is the earliest of three times: the span's `to_utc`; the message's `sensor_utc`; and the node's receipt time plus `max_skew_ms`.
    - Example: the node receives the message at 12:00:10 on its own clock, and `max_skew_ms` is 2,000 ms, so the third term is 12:00:12. A span stated to end at 12:05:00, in a message whose `sensor_utc` is 12:03:00, is cut at 12:00:12.
    - `sensor_utc` is the sensor's own word, and so is E, which is built from it. So the third term uses neither, and rests on the node's clock alone (D3 on round three). A sensor that states its clock and a span in 2100 is cut at the node's receipt time plus the bound.
    - A later message never moves the cut end. The node counts each cut once, under `spans_cut`, when the cut end is below the stated `to_utc`.
  - **Later messages are compared with the span as stated, not with the cut one.** The same span stated again is neither new nor wider. It passes D3's widening check, is not cut again, and is not counted again. A span stated wider than the stated span needs a rise above Ds, as any widening does.
  - **One cut end for each span, so the cursor has a fixed size** (#644 §1.6; D5's note on #641). The node keeps one window for each span, from its stated `from_utc` to its cut end, and replaces this proposal's earlier "its new part gets its own cut end":
    - A part added before the stated `from_utc` extends the window back.
    - A part added after the stated `to_utc` extends the window to that part's own cut end, fixed once in the same way, **only when the window was not cut** (its cut end equals the stated `to_utc`), so that the two are contiguous.
    - **When the window was cut, the added part's window is not kept.** Its gap and `sensor-records-lost` are raised as for any widening.
    - So the window is never wider than the two pieces the earlier rule gave, and a part left out can only make the own-session check judge more, which fails loud. The cut end never moves forward otherwise, so a span cannot follow time and keep `own-session-unseen` off for good.
  - **The unjudged window is the span up to its fixed cut end.** It is what `node.lost` carries and what the detector uses (below), and it does not move as later ticks arrive. A window cut to nothing (a cut end at or before its `from_utc`) writes no `node.lost` entry.
  - **A span is not brought to the node's clock by E in 0.2** (D3's item 9 for #645, asked and not required; D6's N7 on #641). A `lost` gap's start is the sensor's stated time, and only its end is bounded by the node's clock. Within `max_skew_ms` the span sits within 2,000 ms of where it fell. With the sensor's clock outside that bound it can be displaced by up to the offset, so the own-session check is off for a shifted interval: a session in the shifted part that the sensor missed raises nothing, and one in the unshifted part of the true loss raises `own-session-unseen`. D3 asks that the span take `+ E` as a backlog record's `made_utc` does (CH-39), which would narrow the shift to E's own error. **Not taken, for these reasons:**
    - The shift above `max_skew_ms` exists only while no tie is made for skew, for either of CH-22's two causes: `sensor-clock-skew` stands, or the latest o is outside `max_skew_ms` (D5's N1 on #645 at `1c454cb6`). Every observation committed in that time carries `node.skewed`, with its own-session alerts under the `clock-skew` key, whichever cause holds (CH-41, CH-47). So the interval is already marked as one whose times are not to be trusted.
    - E would have to be fixed at admission and kept with each span in the cursor, so that a restart, the owed gap's write and the widening check all use one value. That is a field per span in both documents' cursor, and #644 is at its form now.
    - E at a hello rests on one sample. A hello's `prior.lost`, and every span after a lost sensor database (above), are admitted when E is the hello's o alone (CH-22), with its network delay and queueing, before any tick's lower sample can correct it. A span moved by that E would keep one sample's error in the cursor for good. (This reason replaces "E is often unknown when a span is admitted", which contradicted CH-22; D5's N1 on #645 at `1c454cb6`.)
    - E is built from `sensor_utc`, the sensor's own word (CH-24), and the cut end was kept off it for that reason (D3 on round three). A span moved by E moves the window that switches off the node's only independent check by an amount the sensor states.
    - **The residual** is stated in §16. A later minor can take D3's request with the cursor change it needs. `from_utc` after `to_utc` closes; a span stated new or wider with no rise above Ds closes.
  - Every new or widened span opens a **coverage gap with cause `lost`**, under the `lost` gaps' own budget (CH-45), and raises **`sensor-records-lost`**, a status alarm for the stretch (CH-45). The gap's times are the stated `from_utc` and the cut end.
- **The mark.** When a `lost` list shows a span the node has not marked, or a span widened, the node sets `node.lost` on the next observation of that run that it stores. `node.lost` is a list of at most 8 `{from_utc, to_utc}`. A new run's `prior.lost` goes on the first observation of the new run.
- **What the detector does with it** (D4's code, third part): it adds each span to its degraded intervals, so `covers` keeps `own-session-unseen` from judging a session inside a declared loss (`own.go`), as 0.1 already treats degraded coverage. `sensor-gap-undeclared` and the node's coverage gap still make the loss loud.
- **Outcome when no observation follows** (the run ends first): the mark is not placed, and a session in that span may raise `own-session-unseen`. That fails loud (§16).
- **Counted:** spans marked, spans refused, `spans_cut`, and lost gaps, in status.
- **Meets:** SL-14, SL-17, SL-31, AP-36 (2), P5.
- **Test:** S-7, S-9, S-10.

### 4.4 Records left from an earlier run

**CH-16. Flushed before the next run's hello, or declared lost in it.**

- **Input:** the agent's buffer and `node-hello`'s `taken`.
- **Each connection carries one run.** The agent offers the oldest run that still holds records the node has not acknowledged, and its current run when none does. It never sends a record of a later run on that connection.
- **Applying `taken`.** The agent applies `taken` only under CH-6's conditions, and then drops that run's records up to `taken.seq` from its buffer.
- **A resume** offers the run named in `taken`. `first_seq` is `taken.seq` + 1, or the run's oldest record still held if that is higher. The records in between were evicted, and the run's `drops_channel` and `lost` cover them (CH-15, CH-40).
- **When the agent has an `ack` that covers the newest record of a run that is not its current run,** it closes (`run-complete`), and the next connection offers the next run (CH-10, CH-38). No record of an older run follows a newer run's hello (SL-14).
- **A new run's hello declares what came before it,** in `prior`:
  - `runs_skipped`: this `run_counter` − `taken.run_counter` − 1, with `taken.run_counter` read as 0 when `taken` is absent;
  - `records_lost`: the records of those runs, and of the `taken` run above `taken.seq`, that the agent evicted or discarded without the node's acknowledgement; and, when a new key's enrolment discarded them, the previous generation's (CH-12);
  - `lost`: their capture spans (CH-40);
  - `previous_end` and `started_by` (CH-42).
- **Outcome at the node:**
  - It checks `runs_skipped` (CH-13) and `prior.lost` (CH-40). It cannot check `records_lost`, which is the sensor's word (AP-36).
  - It records both in one `sensor.run-loss` health event for each new run that declares a loss, at most 4 an hour for each sensor, merged past that (#628 §1.9 item 5, §1.15 D5-9).
  - **`prior` is durable at the node before the event** (D6's condition), **in the cursor** (SL-31; D3's preference, taken by #644 §1.4). `prior`'s counts, spans, `previous_end` and `started_by` are saved with the new run, with an owed mark, in CH-13 row 6's one `SaveSourceCursor`, before the hello is accepted. They stay there until the `sensor.run-loss` event that carries them has committed to the health stream, and only a later cursor save clears the mark. So a node crash, an event held past the ceiling, and a `sensorrun.json` that is lost, unreadable or behind do not lose the sensor's declaration. **D5 builds this.**
  - **Only a lost sensor database can lose it.** Status then names a `prior` possibly lost (CH-18).
  - **Twice, never not at all.** The cursor and the health stream are in two databases, so a kill between the event's commit and the clearing of its mark gives the event twice. **`sensor.run-loss` carries the run's generation, counter and `run_id`,** so an upstream reader, who sees no status, can tell one declaration sent twice, and status counts the owed events written at a start as possibly second copies (SL-31; #644 §1.4). These are details of a health event, and need no C4 change.
- **A run's tail cannot wedge the connection** (D6 B5). The tick's `sent_seq` makes every `seq` the agent sent either read or a counted gap (CH-15), so T reaches `newest_seq` and the agent's `run-complete` follows.
- **Meets:** SL-14, SL-16.
- **Test:** S-3, S-4, H-10.

**CH-36. The minor of a connection** (D6 B5).

- **Input:** the `schema` of `sensor-hello`.
- **The rule:** all records of one run carry one minor, and the hello that offers the run names it. The node accepts a hello of any channel minor it knows, and then requires every record of the connection to carry that minor. A record of another minor is refused as `schema`, and the connection stays open.
- **For 0.2,** the only channel minor with a hello is 0.2, so a 0.1 peer's first frame closes as `hello` (CH-35).
- **For a later minor,** a node of that minor that also knows 0.2 can flush a 0.2 sensor's buffered runs, run by run, instead of refusing them record by record.
- **Counted:** `schema` under `sensor-record-refused`; `hello` under `link_closes`.
- **Meets:** no SL rule. It answers the brief's acceptance (a 0.1 reader is kept) and D6 B5.
- **Test:** R-1, R-6.

### 4.5 Acknowledgement

**CH-17. An `ack` names the node's taken position, and nothing less durable.**

- **The node acknowledges what it has *taken*,** as SL-15 now says too (amended in #631): committed, held durably, refused or dropped with its count durable, a duplicate, or never received and counted. D1 ruled the counts' durability a clause (ruling 2). The brief's words were "committed sequence number". The reason for "taken": a record refused for good must not block the stream, and the hold's checkpoint is durable.
- **Taken position T** of a run is the highest `seq` such that every record of the run at or below T is one of these **final outcomes** (D5-1 and D5-2, as #628 §1.4 and §1.15 answer them):
  - committed to the store;
  - saved in the intake hold's checkpoint (`netcheckpoint.intake`), with the save returned (#628 §1.4);
  - refused by C13 or by `platform/sensorlink` (CH-11), or dropped by the unresolved budget, at a full class, or at the record cap, **with the run's refused and dropped totals saved durably** (ruling 2);
  - a duplicate (CH-14);
  - a `seq` the node never read, counted in G (CH-15).
- **Not final:** any other store error (drain-only, a closed database, an I/O fault). The node takes nothing further, closes the connection (`store`), leaves T where it is, and redials with back-off. The sensor's buffer holds the records, and the resume starts from `taken.seq` + 1 (D6 B2, difference 7).
- **Durable before acknowledged.** The node saves T with the run's refused and dropped totals in the observation stream's source cursor (CH-18). It does so in the same commit as the record that moves it, or on its own when no record commits (`SaveSourceCursor`): after a hold save, a refusal, a drop, a duplicate or a gap, at most once a second. #628 §1.4 puts the totals there (at `a50ee61c` it used a minute event instead).
  - **The cursor's other saves on its own** (#644 §1.4; its §1.11 row 22), each a `SaveSourceCursor` when no record commits: **before every hold save** (below); **before a message that changes the spans, `prior`, the run's digest or a heartbeat baseline is acted on** (CH-13 rows 5b and 6, a hello or tick that raises D with a span, CH-40; a heartbeat that changes a baseline, CH-26); **after each write of `sensorrun.json`**, to commit its `write_no` (CH-1); and **for W at most once a minute** (CH-45). The value written is never below the position already saved, and later record commits carry the same values, so nothing the cursor holds is saved apart from D.
  - It never sends an `ack` above the T it has saved.
  - It never moves T past a refused or dropped record before the totals that count it are saved, whichever database the write that moves T is in.
  - So no committed record is ever above the `taken` sent in `node-hello` (D4's B1 on #628), and a node crash never erases the only trace of a record that the sensor has trimmed.
  - **T and the hold** (#628 §1.4; D6's finding on `9a6dac52`, fixed by D1's ruling). The cursor is saved after a hold save at most once a second, so a held record can be above `taken`. Two rules close that gap, with no new state:
    - **Before it holds record n, the node saves T through n − 1.**
    - **Every commit that releases held records of the saved position's run moves T past them in that same transaction,** with that run's totals.
  - **A release moves T only for the run the saved position belongs to** (#628 §1.4; D6's finding on `ceb1ddaa`). A held record of an earlier run, released after a newer run's hello, leaves T unchanged:
    - **If the release commits it,** it is stored as that earlier run's record, and nothing is counted in the totals. A committed record is neither refused nor dropped.
    - **If the release refuses or drops it,** that refusal or drop is counted in the refused or dropped total of the run the cursor now holds, the newer run. That is the only run whose totals the cursor carries (CH-18). The count is therefore saved, but under the newer run's totals and not the earlier run's.
    - D5's wording, "its drop counted in the newer run's totals", means the second case only.
  - **No `ack` names a `seq` above both the highest `seq` read on this connection and the latest tick's `sent_seq`,** even when T is higher. T can be higher after a restored hold's release in mid-connection. The `ack` names T, or the higher of the two figures (read and `sent_seq`) when T is above both. So the `ack` stays within the agent's bound of CH-9.
  - **What a node killed between a hold save and the next cursor save does with a resend.** The node restarts with record n in its hold and `taken` at n − 1. The sensor resends n:
    - If the restored hold has already released n, by `TickHold` past its deadline or by `RecoverHold`, the release moved the saved T past n, so the resend is at or below CH-14's P and is a duplicate by position.
    - If n is still held, the hold drops the resend, matched by `run_id` and `seq`.
    - Either way the resend is counted under `duplicate` and T moves past it. Only the held copy commits, so nothing is stored twice and nothing is lost.
- **At the agent,** an `ack` lets it drop the run's records at or below `seq`, and nothing else (SL-19).
- **A record the node read and had not finished when a connection ended** has no outcome. It is sent again on the next connection, from `taken.seq` + 1 (CH-6).
- **Counted:** `store` under `link_closes`; the refused and dropped totals.
- **Meets:** SL-15 and SL-19.
- **Test:** A-2, A-3, A-4, S-10, H-10.

### 4.6 What the node keeps

**CH-18. For each sensor, the node keeps durably:**

**The rule of P4-4-L6: what changes with a run is kept in the sensor database's cursor, with D, and never apart from it** (SL-31, D3's ruling (b); #644 §1.4, and its §1.11 row 2). One fact is never held in two stores of different durability.

- **in the observation stream's source cursor,** committed with each record or saved on its own (CH-17; #644 §1.4):
  - the position: the generation, the run counter, the `run_id`, the taken `seq` T, G and D (CH-15), and the run's refused and dropped totals (CH-17);
  - `write_no`, SL-30's write number (CH-1). A first cursor of 0 is a number; only a database with no cursor holds none (SL-30; SL-T23 (r));
  - the run's `config_digest`, saved at CH-13 row 6 (CH-32);
  - Ds, the D at which the run's spans were last accepted (CH-40);
  - the last `newest_seq` the sensor stated for the run (CH-12, `replace`);
  - the run's heartbeat baselines: the last `frames_outgoing`, `drops_holder`, `frames_overlong` and `drops_driver` taken, and whether `egress_check` was carried, or none (CH-26, CH-27; `drops_driver` by D1's rulings 6839936385 and 6840188059 on #645: with no baseline held, the run total is the loss for all three counters);
  - W, the moment accounted through, with the `seq` and `at_utc` of the current heartbeat it came from, and the gap causes seen since (CH-45);
  - the run's spans, at most 8, each as stated, with its cut end and its owed mark (CH-40);
  - `prior`, when present, with its owed mark and its spans, at most 8, each as above (CH-16).

  **Its bound, `MaxLinkCursorBytes`, is 2,048 bytes,** for a text form of at most 1,575 (#644 §1.4 itemises 1,554 at its head `4a606518`, 1,560 with `unclean` in full; the `drops_driver` baseline adds one decimal of at most 20 digits and its separator, 21 bytes, so 1,575, or 1,581 with `unclean` in full, which D5 itemises when #644 states the same; 2,048 holds either way). It was 192 for a text form of 187 before P4-4-L6. It is the node's constant and not C13's (difference 11), and C13 states it so that both documents give one figure (SL-31). No C5 change: the cursor is a BLOB that C5 bounds only through the record's bytes (`contracts/store/commit.go`; D5 on #641). **What it costs:** every stored observation carries the cursor in its row and its class's quota, at most 479 bytes with no span or `prior` held and up to 1,575 while they are held (#644 §1.4, with the `drops_driver` baseline added).
- **in the node's run record** (`sensorrun.json`, #644 §1.3), written to a temporary file, synced and renamed, under `write_no` (CH-1): a second copy of the run's counter and `run_id`, **with its generation**, written at each new run accepted, not at each resume; SL-30's counts and proofs (CH-1); the cap's last record times (C8-5); the re-arm's spent request hashes; the held events of the pool (CH-45); the poison record (#644 §1.9 item 9); the standing `sensor-transmitted` (CH-26); and a copy of W, written only with the file's own writes, so never later than the cursor's W (CH-45). **It holds no span, no `prior` and no digest** (SL-31);
- **in the node's sensor state** (`sensors.json`, #644 §1.3): the state `live`, `revoked` or `fork-held` (D3 B4); the first `pinned_by` of each generation (CH-33); **the generation at which the node's position began** (CH-12; SL-R6); and the live enrolment's record time, which #644 names `enrolled_at`, the earliest bound for a coverage gap (CH-45).

**Outcome:**

- A new run's counter and `run_id` are saved before its hello is accepted (CH-13 row 6). T, G, D and the totals are saved with each commit that moves them (CH-17).
- At start the node takes the higher of the two copies of the run. Two copies with one counter and two `run_id`s are a fork, and the sensor is `fork-held` (#628 §1.4). A copy read from a file that is behind can only be lower, so taking the higher stays safe.
- **A `fork-held` sensor is still not dialled after a node restart** (D3 B4).
- **A position that cannot be read** means no dial, and `sensor-state-unread` with cause `position`, never a failed start (CH-4; #644 §1.3). The node's start and SER and Syslog collection never wait on any of this. The caps and the store set that keep a sensor's work from reaching collection are #628 §1.9 items 1 to 7 (D6, OT safety).
- **A run file that cannot be compared with a sensor's database reads as lost for that sensor** (D3's item 7 for #645; D1's alarm half, checked, and §11.3 in #641; D6's B4 on #641). Under a live enrolment, when that sensor's database is lost, absent, unread or without a cursor, "behind" could be judged only against the other databases, and on a node with one sensor against none, so a stale file would read as current. **So the file then reads as lost for every value it holds for that sensor, and for every pair that sensor's enrolments name, `sensor-transmitted` included,** as it already does for SL-30's counts (CH-1). **Two exceptions,** each of which only moves something earlier or is checked again: the copy of W, which a stale copy only moves earlier (CH-45); and the copy of the run that `node-hello` names after a lost database, whose cost SL-31 states and D1 accepted (below). Wherever this proposal says a run file "lost", for a sensor, this case is included. *Test:* H-10's fourth run, which is SL-T24 (g)'s third case. *Control:* a node that applies the lost-database rule to SL-30's counts only, which clears `sensor-transmitted`.
- **A run file that is lost, unreadable or behind** (CH-1), or that cannot be compared (above), raises `sensor-state-unread` with cause `run-file`. It touches no span, no `prior` and no digest, because none is in it. **D1's alarm half** (D4-90), the same rule as #644's (§1.4, §1.8, §1.9 item 5): **a node-side loss or rollback of `sensorrun.json` never silently clears a standing alarm, never rolls back or re-arms SL-30's dial count, and never loses or doubles a `prior` or the run's `config_digest` without a status that names it.** Value by value:
  - `sensor-transmitted` stays raised, or is raised, until an administrator clears it, while an enrolment is live (CH-26);
  - SL-30's counts read as spent unless a cursor of the live generation proves the pair, and the spent re-arm hashes are rebuilt, so a request file put back is refused (CH-1);
  - `prior` and the digest are the cursor's, so the file cannot touch them; a `sensor.run-loss` written twice is named in status and carries its run (CH-16);
  - the cap's record times are lost, so the cap holds from the start (C8-5);
  - the held pool events are named in status as possibly lost. **A coverage gap is never held only in the file:** a `lost` gap's hold is its marked span, and every other gap is held by W, which does not move past it (CH-45);
  - the poison record can be lost, which costs at most one more contained panic at that observation, loud as `sensor-failed`.
- **A sensor database lost where a position existed** (SL-31; D4's B5 on #633; CH-1: under a live enrolment a missing database is lost). The node creates it again after marking the pairs spent (CH-1), and holds no D, no Ds, no spans, no `prior`, no digest, no baselines and no W. Status names the lost position, says that the position is taken from the run file, and names a `prior` possibly lost.
  - **The hello** (D1's ruling, comment 6837755868 on #644; *test:* H-9, SL-T24 (f)): when `sensorrun.json` holds a copy of the run whose generation is not below the generation at which the position began, `node-hello` names that copy with `taken.seq` 0; otherwise it carries no `taken` (CH-6). The copy may be behind, because with the database gone its `write_no` cannot be checked.
  - **What a stale copy costs** (D3's bound in SL-31, adopted by D1): a copy of the sensor or a restored snapshot whose counter lies between the stale copy's and the true one is accepted where it should be refused as `run-regressed`, for that window only and only after two faults on the node. A compromised sensor gains nothing it could not already do (SL-16's residual).
  - **SL-30's counts read as spent,** so the dial that would send this hello waits for an administrator's re-arm, and `sensor-dial-limit` stands. That fails closed.
  - The hello's spans are new against a D of 0, admitted only with the count the sensor states, and each opens a `lost` gap (CH-40). The run's digest is learned again from the hello, and status says so (CH-32). The records the agent trimmed after the lost acknowledgements count in G at the first resume, so `sensor-gap-undeclared` is raised once, with the lost position named in status as its likely cause.
  - The gap at the node's start reaches back to the run file's copy of W, or else to `enrolled_at` (CH-45).

**Counted:** saves that failed (`position-not-saved`, CH-11); `sensor-state-unread` by cause (CH-45).

**Meets:** SL-6, SL-14, SL-16, SL-20, SL-30, SL-31. **Test:** H-3, H-4, H-7, H-9, H-10, A-2, S-10; the rig's SL-T23 (o) to (r) and SL-T24 (a) to (h); the node's `TestRunFileFirstWriteKill` for a cursor of 0 (#644 §1.1).

## 5. The sensor's buffer (brief item 4)

**CH-19. What the buffer holds, and where.**

- **Input:** each heartbeat and observation the agent makes.
- **What it holds.** The link agent keeps an append-only buffer on the sensor host's disk, in its own data directory. Each entry is a C13 record exactly as it will be sent. It holds heartbeats and observations only, so it holds redacted frames and allow-listed fields only (SL-22). Ticks and hellos are made when they are sent and are never in it.
- **A record is numbered when it is written to the buffer. It is sent only after the sync that covers it** (D3's change 1, D6's item 1).
  - So the node can never hold more of a run than the sensor's disk holds, unless the disk went back (CH-13 row 5a, A5).
  - The cost is up to `buffer_sync_ms` added to every record's path. That changes the value R6.4 will report, not its measure (D6).
- **Syncing.** The buffer, and beside it each run's counter, `run_id`, newest `seq`, `drops_channel` and `lost` spans, are synced at least every `buffer_sync_ms` (100 ms). The agent states in hellos and ticks only values it has synced (D6 B5).
  - A sync that takes longer than `buffer_sync_ms` is counted under `sync_late` (CH-43), and numbering goes on.
  - A crash of the agent or the host loses at most the records written since the last sync. CH-42 makes that a declared possible loss.
- **A record the agent cannot write** (a full or failing disk) is never sent. The agent stops, its service manager starts it again, and that begins a new run with `previous_end: unclean` (CH-42).
- **An entry the agent cannot read back** is skipped. It counts in its run's `drops_channel` and `entries_unreadable` (CH-43), and its run's `lost` span is widened to the capture times of its readable neighbours.
- **Run entries.** The agent keeps a run's entry until the node has sent an `ack` for a later run, or named one in `node-hello`, so that it can still declare the run's tail (CH-16). CH-46 bounds how many.
- **Meets:** SL-14, SL-15, SL-22.
- **Test:** B-2, B-3, B-5.

**CH-20. How much, for how long, and what an overflow counts.**

- **The bound is in bytes:** `buffer_bytes`, 2 GiB by default, up to 64 GiB. It is a sensor setting, in the configuration digest (CH-32), and stated in the hello.
- **The floor differs by build** (D6's condition; D1 confirms), as SL-22 does for the redaction switch:
  - **A site build** refuses at start a `buffer_bytes` below **256 MiB**.
  - **A test build** takes **16 MiB**, so that the rig can fill a buffer (B-1).
  - **The node** raises **`sensor-buffer-small`**, a standing alarm, while a sensor's hello states a `buffer_bytes` below 256 MiB (CH-13 row 9).
  - A small buffer cannot be caught by `sensor-buffer-filling`, because no tick arrives during the outage that fills it (D6). The floor is the guard.
- **It is never bounded by age.** This proposal's rule is that the agent evicts nothing by its own clock.
- **Eviction.** When a new record would take the buffer over its bound, the agent evicts the oldest records first, whatever their run, until it fits. Each evicted record that the node had not acknowledged counts in its run's `drops_channel`, and its capture time joins its run's `lost` spans (CH-40). A record already acknowledged is simply trimmed.
- **Why the oldest.**
  - A buffer that kept the oldest would stop recording when it filled, so whatever happened afterwards, an attack for example, would never reach the node.
  - Evicting the oldest keeps the newest. An attacker who floods to push an event out must keep flooding after it, and `drops_channel` shows the loss either way.
  - A node that holds its key can also empty the buffer by acknowledging. That is inherent, and the buffer is not a second evidence store (§16, D3's note 10).
- **The sizing rule** (difference 9, ruling). For each site, `buffer_bytes` must hold at least the site's record rate times the node's `outage_hours`, the planned outage that also sizes the unresolved budget. No station's rate has been measured, so **this rule cannot be checked yet**. The node raises `sensor-buffer-filling` when a tick's `buffered_bytes` passes three quarters of the hello's `buffer_bytes` (CH-45).
- **How long 2 GiB lasts** is the bytes over the record rate. This is `desk` arithmetic, not evidence:
  - A heartbeat is at most about 3 KiB with the 2 KiB coverage statement, so heartbeats alone take at most 3 KiB × 8,640 = 25,920 KiB, or 25.3 MiB, a day.
  - An observation without frame bytes is at most about 5 KiB; a first-sight one at most 64 KiB.
  - At an assumed one observation of 5 KiB a second, 2 GiB (2,097,152 KiB) lasts 419,430 s, which is 4.85 days. At ten a second, 11.65 hours.
  - GT-PCAP's captures are short and are not a station's rate. A station's rate is measured only by H-06's 24 h run on hardware.
- **Counted:** `drops_channel`, per run.
- **Meets:** SL-14, SL-15.
- **Test:** B-1, B-4, B-6.

**CH-46. The agent keeps at most `MaxAgentRuns` (64) run entries** (D6's bounds note).

- **Input:** a 65th run begins while 64 run entries are held. A decoder that crashes every 60 s through a day's outage would otherwise leave 1,440 runs, each needing a connection and a durable save at the node.
- **Outcome:** the agent discards the oldest run that still holds unacknowledged records, and declares it in the next new-run hello's `prior`: in `runs_skipped` (the run is never offered), in `records_lost` with its count, and in `lost` with its spans. Nothing is silent. Those spans open a `lost` coverage gap and raise `sensor-records-lost` at the node (CH-40).
- **The lever** (D3). Someone who can crash the engine (AP-30) while the link is cut can make the agent discard the oldest run after 64 restarts, far sooner than the byte bound. What limits that is the service manager's restart delay, so the sensor's image must set one (assumption A8's image; D3 adds it to AP-30).
- **Counted:** at the node, through `prior` (CH-16).
- **Meets:** SL-14, SL-20.
- **Test:** S-8.

## 6. Time (brief items 2 and 5)

### 6.1 Clock fields

**CH-21. The sensor host's clock appears in four places.**

| Field | On | What it is |
| --- | --- | --- |
| `made_utc` (new, required in 0.2 records) | Every observation | The sensor's clock when the agent numbered the record and wrote it to the buffer |
| `at_utc` (0.1) | Every heartbeat | Unchanged. In 0.2 it is also the heartbeat's made time, because the agent makes and numbers a heartbeat at once |
| `sensor_utc` (new) | `sensor-hello`, `tick` | The sensor's clock when it sent the message |
| Capture times (0.1) | `first_utc`, `last_utc`, frame `ts` | Unchanged: the capture timestamps |

- **A capture time is the kernel's receive timestamp** that crosses the first pipe with each frame (SL-3 item 1), never the time a later stage read the frame. A stage that stamped frames when it read a pipe would add the pipe's queueing to every capture time, to CH-28's PRP window and to R6.4's comparison.
- **Form:** each is RFC 3339 UTC with `Z` and at most nine fractional digits, the form 0.1 checks (`utcForm`). Another form is refused as `form` in a record, and closes the connection in a message.
- The node checks no order between these fields, because the sensor's clock may step.
- `made_utc` − `last_utc` is the sensor's own pipeline time: capture to engine to agent. **[S2]** Its size depends on when the engine writes a line (§14).
- **Not compared:** a relay's own event time against a frame's time. They differ by the relay's reporting delay, its clock error, and possibly its local-time offset. A later correlation must never read that difference as skew, and must never take a relay's time as UTC without the relay's time settings (D2 on #627, N-5).
- **Meets:** SL-17.
- **Test:** T-1, P-4.

### 6.2 The skew check

**CH-22. The node's estimate, from live messages only** (difference 5, ruling).

- **Input:** at each `sensor-hello` and each accepted `tick` (CH-8), the node takes **o** = its own wall time when it received the message − the message's `sensor_utc`. A positive o means that the sensor's clock is behind.
- **The sign, stated once here, for every clause that uses E.** A sensor time is brought to the node's clock by **adding E**: sensor time + E. Worked example (D3): the node reads 12:00:10 when a tick stating 12:00:00 arrives, so o = +10 s. With E = +10 s, a `made_utc` of 12:00:00 is 12:00:10 on the node's clock. CH-23 and CH-39 use this step.
- **What o includes.** The one-way network delay, plus any queueing behind records written earlier on the stream, which grows while a backlog drains (D3's assumption table). Both make o larger, so they can hide a sensor clock that is ahead.
- **The estimate E** is the smallest o of the connection's last 6 ticks: one minute, the least delayed sample (#628 §1.5). On a new connection it is the hello's o until the first tick.
- **Heartbeats and observations are never used,** because a buffered one is late by the outage (CH-8).
- **Outcome:** the node raises **`sensor-clock-skew`** when |E| is above `max_skew_ms` (2,000 ms), and clears it when |E| is at or below 1,500 ms (#628 §1.5).
- **The bound's basis, unmeasured:** an order below `tie_grace_s` (30 s by default), so a sensor within it cannot move a flow out of a session's window. That a site's time client keeps well inside 2 s is not measured, and it assumes a working time source, which is the owner's O-10. A free-running host would pass 2 s within days (D6, inference; D2 gives a free-running SEL-751 as 2 minutes a year, a relay and not a sensor host). `max_skew_ms`, `AckMaxDelay` and `buffer_sync_ms` all rest on figures nobody has measured (D6's bounds note; §12).
- **The tie uses the latest sample too** (D3's change 2; #628 §1.5). The least of six ticks is for the alarm only. **No tie is made while the alarm stands, or while the latest o is outside `max_skew_ms`**, even before E catches up. **One rule for both causes** (D4's B3 on #633; #644 §1.5): the node marks the observations it commits then, and their alerts are aggregated, whichever cause holds (CH-41).
  - A clock stepped back for less than a minute then ties nothing from its first tick.
  - **A sample read after the node's own read loop was held** (D4's B3 on #633; #644 §1.5 item 6). o is taken at the node's read, and the read loop takes the next frame only after each commit (F4), so a commit held 3 s, F-016's figure on the hosted Windows runner, can put an honest sensor's latest sample above 2,000 ms. **Such a sample still gates the tie,** which fails closed: no tie, the observations marked and aggregated. It is **counted** under `skew_samples_after_hold` when the read-loop step before it lasted longer than `AckMaxDelay` (1 s), so a slow node shows as the cause in status. It still enters E, whose least of six is not raised by one late sample.
  - What stays is a step made and undone between two ticks. That is D3's residual for AP-35, with O-10.
  - Skew never suppresses (SL-17).
- **Nothing stored is re-timed.** The node's own comparisons bring a sensor time to the node's clock by the step above. Capture times stay as the sensor wrote them. D3 confirmed the sign on round three, and #628 §1.5 now adds E as well (`t_node = t_sensor + E`).
- **The node serves no time to the sensor** (SL-17). No field of `node-hello` or `ack` carries a time.
- **Counted:** stretches of `sensor-clock-skew`, under CH-45's cap; `skew_alarm_windows`, `skew_latest_windows` and `skew_samples_after_hold` in status (CH-41).
- **Meets:** SL-17, SL-29.
- **Test:** T-2, T-10.

**CH-41. The skew mark and the `clock-skew` key** (difference 4, ruling).

- **Input:** an observation committed **while no tie is made for skew,** for either of CH-22's two causes: `sensor-clock-skew` stands, or the latest o is outside `max_skew_ms` while E is not (a clock stepped back, or a tick read late). Also a `collection.run` that the node marks `skewed` because its session ended then (D5's record, #644 §1.5). **One rule for both causes** (D4's B3 on #633; #644 §1.5 and its §1.11 row 10): the input named the alarm only, while CH-22 marked for both.
- **Outcome:**
  - The node sets `node.skewed: true` on the stored observation. Only the node sets it, as with `node.late`; a sensor record that carries `node` is refused (0.1 §14 item 5).
  - **`node.skewed` and the key `clock-skew` mean "no tie was made for skew"**, the alarm or the latest sample, and not that the alarm stood. So an aggregated alert can stand with no `sensor-clock-skew` raised. Status counts the windows of each cause apart, `skew_alarm_windows` and `skew_latest_windows`, and the samples after a held read loop, `skew_samples_after_hold` (CH-22), so such an alert is explained there (#644 §1.5 item 5).
  - The detector (D4's code, third part) puts every `own-session-unseen` and `own-session-outside-record` alert that comes from such an observation, or from such a session, under one window key for each rule: `asset_id` `clock-skew`, beside the `asset-unresolved` bucket (0.1 §7.3).
  - The aggregated alert names the assets it covers, up to 8, and counts the rest (CH-47; ruling 13 on #628).
  - With 0.1's coalescing, that is at most 2 records a window for each of the two rules.
  - A flow that would match no session even at |E| plus `g` keeps its asset's own key, so a spoofed session that matches no run still alerts on its own (#628 §1.5 item 4).
- **Counted:** alerts under the key, as 0.1 counts a window's `hits`.
- **Meets:** SL-17 (the alerts aggregated, with the skew alarm or status's counts naming the cause).
- **Test:** T-6, T-10.

**CH-47. The aggregate keys, and the assets an aggregated alert names** (ruling 13 on #628; difference 4; #628 §1.5, §1.6, §1.9 item 4).

- **Input:** an `own-session-unseen` or `own-session-outside-record` alert that the detector puts under an aggregate key instead of an asset's.
- **The keys:** three new values of an alert's `asset_id`, each allowed only for those two rules:
  - `clock-skew`: no tie was made for skew, for either of its causes (CH-41);
  - `sensor-records-late`: a backlog record untied after a break (CH-39). **The key shares its name with the alarm `sensor-records-late` (CH-23), and not its meaning** (D4's note on #633; #644 §1.6). The alarm is raised by a record later than `late_bound_s` (180 s); the key is used after a break longer than `backlog_tie_s` (60 s), or for a short break's record outside its `made_utc` window. So after a break of 61 to 180 s the alerts come under the key while the alarm does not stand. The name is kept, because both say "records the outage made late", and status shows the break's length beside the key's windows;
  - `hold-timeout`: a session whose tie the node could not make because the scheduler's wait on the link's lock timed out, **or because a recovered panic in a scheduler call was taken as a timeout** (#644 §1.9 items 4 and 9; D4's note on #633). The second cause is new in P4-4-L6. **Such a panic raises no `sensor-failed`, does not stop the sensor's work and opens no `sensor-failed` gap** (D1's ruling to D4 on #645's pass after `d2362d7c`): the node's own bug should not cost the site its coverage, and `network-session-not-tied` keeps it visible. *Test:* T-12.
- **The names:** an aggregated alert carries two new details:
  - `assets`: the asset IDs it covers, space-separated, at most 8, enrolled assets first;
  - `assets_total`: how many it covers in all.

  An alert that loses its asset is not accepted (ruling 13 on #628). #628 §1.5 and §1.6 say that the alert "names the assets it covers, up to 8, and counts the rest". `assets` and `assets_total` are the field names for both documents, and they are C13's. `assets` is present exactly when `asset_id` is one of the three keys, and `assets_total` is at least the number listed.
- **Outcome:** an alert with an aggregate key and no `assets`, with `assets` under another `asset_id`, or with an aggregate key under another rule is refused as `conflict` by `Alert.Validate`.
- **Counted:** as 0.1 counts a window's `hits`.
- **Meets:** SL-17, SL-20 (a cap that protects collection does not switch off the independent check; D3's condition on #628).
- **Test:** T-6, T-9, T-12.

### 6.3 Late records, and ties on a backlog

**CH-23. A late record is stored, flagged and counted, and never dropped by the sensor's clock.**

- **Input:** a record's **lateness** = the node's wall time when it received the record − the record's made time (`made_utc`, or a heartbeat's `at_utc`) − E (CH-22).
- **The bound** is `late_bound_s`: 180 s by default, from 30 s to 3,600 s, a node setting. That is the figure in both documents, by D1's ruling on round two. The basis:
  - `sensor-unreachable` is due after 60 s of quiet, and is raised at the node's first periodic pass after that (D4-74, D1 on #581). On `main` the pass is `Runtime.Tick` every `TickInterval`, 60 s (`service.go`), so the alarm comes by 120 s. `records-auditor` reads the record as allowing a pass of up to 120 s, which gives 180 s.
  - 180 s holds under either reading, so "late" means "held by an outage the node has already alarmed on".
  - With #628's sensor manager driving its own checks about once a second (#628 §1.9 item 3), the alarm comes sooner. The bound does not depend on that.
- **Past the bound:**
  - an observation is stored as any other, with `node.late: true`, and counted under `late`;
  - a heartbeat is taken for its counters and counted under `late`, and the node's live checks (skew, blind) do not use it (CH-31, CH-44);
  - the node raises `sensor-records-late` once for each connection that carries one, under CH-45's cap;
  - the detector judges a late observation by its capture time, as any other.
- **`late` is the sensor's own word.** It rests on the sensor's `made_utc` and on E, which a clock moved during the break can defeat. The node's own measure of a break is CH-39's (D3 B3).
- **Never:** a record is not refused, dropped or re-timed for lateness. The node never orders, prunes or expires anything by the sensor's clock (SL-17).
- **Counted:** `late`.
- **Meets:** SL-17.
- **Test:** T-3, T-4.

**CH-39. A backlog record takes a tie only on the node's own measure of the break** (D3 B3, ruling 1; D3's change 3 as D1 ruled it; the break per outage from #628 §1.6, D6's item 2). **[S2]**

C13 defines "break" and "backlog record" here, and #628 cites this definition (D1's ruling on round two).

- **Input:**
  - A **break** runs, on the node's monotonic clock, from the last accepted frame of a sensor's connection (CH-44) to the accepted hello of the next. After a node start, the first break is unknown, and counts as longer than `backlog_tie_s`.
  - **The backlog of a break is per outage, not per connection.** It is every record the node reads from the break's end until it has read through the `newest_seq` of the first hello after the break whose `current` is true (CH-7). So every old run flushed after an outage, on however many connections, belongs to the same backlog and is judged by the same break. A connection that follows a `run-complete` takes on that break.
  - Records numbered after the break ended, but read before the backlog is through, count as backlog too. That errs towards untied.
  - **A second break that begins before a backlog is through** extends that backlog. Its records are judged by the **longest** break of the unfinished backlog, not by the latest one. So a short second break never gives ties to records that a long first break left untied (D6 on round three).
- **Outcome after a break longer than `backlog_tie_s`:**
  - Each backlog record takes no tie: the intake hold and the late index (#628 §1.6) make none for it. It is committed untied, with `node.backlog: true`.
  - The node marks each `collection.run` whose window overlaps the break (D5's record).
  - The detector puts the `own-session-outside-record` alerts of marked observations, and the `own-session-unseen` alerts of marked sessions, under one window key for each rule, `asset_id` `sensor-records-late`, naming up to 8 assets and counting the rest (CH-47). So an outage raises one alert a window for each rule, not one for each session.
  - A flow that matches no session keeps its own key, as in CH-41.
- **Outcome after a break at or below `backlog_tie_s`** (D3's change 3, ruled by D1):
  - A backlog record takes a tie only when its `made_utc`, brought to the node's clock, falls between the start and the end of the break on the node's clock, within `max_skew_ms`.
  - "Brought to the node's clock" is `made_utc` + E, CH-22's step. With o as the node's time minus the sensor's, and E = +10 s, a `made_utc` of 12:00:00 is 12:00:10 on the node's clock. D3 confirmed this sign; D1's ruling and D3's earlier text said "less E".
  - Otherwise it is committed untied with `node.backlog: true`, and alerts as above.
  - So the bound limits how far a capture time can be displaced, and not only how long an attacker has.
- **[S2]** A flow that began in the break, but whose first record the engine writes only at its end, is numbered after the hello and is not a backlog record. If E-D4-03 shows that the engine writes so, this rule also needs the capture time (D3).
- **`backlog_tie_s`** is 60 s by default, at most 120 s (D3), the name and figure in both documents (D1's ruling on round two). Its basis:
  - 60 s is the quiet after which `sensor-unreachable` is due (CH-23 gives when the node raises it). So a break past the bound is one the node is already alarming on.
  - Above about 60 s, a spoofed session can reach a neighbouring scheduled run's window (D3), hence the 120 s ceiling.
- **The residual** is a clock moved and restored inside a break at or below the bound, within `max_skew_ms` of the node's own measure. D3 records it in AP-35.
- **The heartbeat's cadence in 0.2** (brief P4-4-L6; SL-16 asks C13 to state it). The agent makes a heartbeat every `SensorTickInterval` (10 s) by its own monotonic clock, **whether or not a connection is open**, numbers it, and writes it to the buffer as any record (CH-19). Its `at_utc` is its made time (CH-21). So an outage's heartbeats arrive in the backlog, about 10 s apart by `at_utc`, and 0.1's interval is unchanged. A heartbeat is never skipped because the link is down; one evicted from the buffer counts in `drops_channel` as any record.
- **A coverage gap closed as covered** (D4-90's gap rule; SL-16 and D3's condition 2; #644 §1.9 item 5). The backlog that covers a gap is through once the node has read through the `newest_seq` of the first hello after the break whose `current` is true, as above. **A gap of any cause but `lost`, `blind` and `revoked`** (CH-45), other than a sensor's never watched (below), is then closed as covered, whole, only by **a chain of heartbeats in one run, from the heartbeat that set W (CH-45) to a current heartbeat after the gap,** whose two ends the node placed by its own receipt, and only if all four of these hold:
  1. every `seq` of the run between the two ends is read, with no declared loss among them (no rise of D);
  2. **the chain shows capture, by CH-31's blind rule, flat counts included, and never by the carrier alone** (D3's item 3 for #645; SL-16; D6's B2 on #641): no stretch of the chain as long as `blind_after_s`, measured by the heartbeats' `at_utc`, has every interface blind under CH-31. For each such stretch, some interface's `packets` rose within it and its `carrier` was not `down`. **A stretch that began before the chain's first heartbeat counts from the last rise the node holds for that interface in the run,** and where it holds none, from the chain's first heartbeat. So a stretch flat for four minutes before W and two after fails, as it would live. A chain that fails leaves the whole gap open, unwatched, and agrees with `sensor.past-blind` (CH-44). *Test:* V-17, whose control is a chain that checks the carrier alone and closes a flat ten-minute cut as covered;
  3. **no two consecutive heartbeats are more than `HeartbeatGapMax` apart by their `at_utc`.** The two ends count, so a silence just before the reconnect fails too. A live heartbeat is placed by its receipt, and only its `at_utc` enters this check;
  4. **there are at least as many heartbeats as the gap's length on the node's clock divided by `HeartbeatGapMax`:** 20 for a ten-minute gap. This ties the sensor's spacing to the node's clock, so that a sensor clock running slow cannot pass the third part with too few heartbeats.

  **Unbroken `seq`s alone do not show capture:** an engine that stops its heartbeats for eight minutes without a new run leaves them unbroken (D5's N5 on #641). Observations arriving are not the test either, so a quiet interval that was watched is closed.
  - **`HeartbeatGapMax` is 30 s,** three `SensorTickInterval`s at the cadence above. It is the one value that C13, the node's design and D3's note use (SL-16; #644 §1.10). It tolerates one late or missing heartbeat on a loaded sensor, so an honest stall does not record watched time as unwatched.
  - **There is no partial cover** (#644 §1.9 item 5; SL-16). Whatever the chain does not show leaves the whole gap open, written as unwatched from its start to the first current heartbeat after its cause ends that shows capture (CH-45). So a sensor restart inside a gap leaves the whole gap open, with cause `restart`. **For a break longer than `backlog_tie_s` this is D3's condition, adopted by D1 as a refinement of D4-90** (comment 6837169700 on #641): "covered" must be shown, and across a restart inside such a break it cannot be. **Applying it to shorter breaks too is #644's proposal,** which fails closed and which D3 accepts in SL-16; C13 states the same. Where the chain shows coverage, D4-90's sentence holds unchanged: the gap opened at the link drop or the node's start is closed as covered once the backlog that covers it is through.
  - The spacing and the count rest on the sensor's word, as every heartbeat does. They stop an honest fault from closing a gap; they do not stop a compromised sensor from claiming capture it did not make (AP-36).
  - **The gap of a sensor never watched since its enrolment is never closed as covered** (SL-16 and gap leg 15; D5's B1 on #645; CH-45). No heartbeat ever set W, so no chain can start, and a backlog the sensor made before its first current heartbeat is its word, placed on no clock of the node's. That gap closes at the first current heartbeat that shows capture, always with `covered: false`, however long the backlog before it.
- **Counted:** `backlog` (records), and breaks longer than the bound, in status.
- **Meets:** SL-16, SL-17 (skew and backlog never suppress), AP-35.
- **Test:** T-7, T-8, T-11; V-2, V-3, V-4, V-5, V-7, V-8, V-9, V-15, V-16, V-17.

Heartbeats are never stored, and a resume sends nothing at or below `taken`, so the node keeps, for the cursor's run, **the last `frames_outgoing`, `drops_holder`, `frames_overlong` and `drops_driver` taken, and whether `egress_check` was carried,** in the cursor (CH-18), saved before a heartbeat that changes them is acted on (CH-17). `drops_driver` joined them by D1's ruling on D5's N3 (comment 6839936385 on #645), because `capture_loss` names it (CH-45; C4 0.4) and its difference across a node restart needs a durable baseline like the others, under the same rule as the other two (D1's ruling 6840188059 on #645); #644 §1.8 states the same.
  - **A new run starts with no baseline,** and a lost sensor database, or a cursor that cannot be read, leaves the node with none. The counters' baselines are then set by the first heartbeat of the run that the node takes. **The `egress_check` baseline is set only by the run's first heartbeat seen from its start** (CH-27); a run taken without that heartbeat holds no egress baseline, and CH-27's rule for that case applies (#644 §1.8).

  - **With no baseline held, any non-zero `frames_outgoing` raises `sensor-transmitted`.** That covers the first heartbeat of a run that the node takes (D4's note 7 on #633: the run's first heartbeat can be evicted, CH-20, or refused), a run whose first heartbeats fall in a declared loss or a gap, and a node restart with the sensor database lost. **With a baseline, any rise raises it.** So a transmit is never missed for want of a comparison, and is at worst raised again for one already raised, which fails loud.
  - **One rule for the three capture-loss counters, `drops_driver`, `drops_holder` and `frames_overlong`** (D1's ruling 6840188059 on #645, which withdraws the special form for `drops_driver` in 6839936385). **A rise of any of them against its baseline is a capture loss** in `sensor.counters` (CH-45). **With no baseline held, the run total taken is the loss,** for each of the three alike, and a run total of 0 is no loss. That can count a loss twice after a lost database or a node restart with the cursor unread. That is an over-count, stated, never a loss: frames dropped before a node restart are always counted. *Test:* W-8 (f) and (g).
  - **`sensor-transmitted` stays raised across a loss of the node's own** (D1's alarm half; CH-18). Its standing state is in `sensorrun.json`, so with that file lost, unreadable or behind while an enrolment is live, **or unable to be compared with the sensor's database because that database is lost, absent, unread or without a cursor** (CH-18; D3's item 7 for #645), the node raises it until an administrator clears it. A loss never clears it silently. *Test:* H-10; the rig's SL-T24 (g).
- **[S2] The engine's timers through a quiet spell** (0.1 §4.3). Inference, not measured: an engine that reads a capture stream may advance its own clock only by packet times. During a quiet spell its timers would then not fire, and `flow_idle_s`, `sa_reply_timeout_ms` and a flow's `end: idle` would wait for the next frame. Either the agent applies those two bounds on its own clock, or the pipe case of E-D4-03 shows that the engine keeps them.
- **Outcome:** every counter is a run total that never decreases. A decrease is refused as `order` by `Follows` (C13), which `platform/sensorlink` counts as `counter-decrease`.
- **Meets:** SL-3, SL-26.
- **Test:** W-1, W-3, W-5, W-7, W-8, H-10.

**CH-27. `interface_check` on Linux** (D2 B-1, D6 B7).

- 0.1 makes it "D5 §7 step 4's binding read", a Windows read of the NIC's protocol bindings. On the Linux sensor host it is **the link agent's** read of each monitoring interface, at its start and at each heartbeat. Neither capture program can make it: the frame stage has an empty network namespace, and the socket holder may make no call beyond its allow-list (SL-3). The agent runs in the host's network namespace and reads through sysfs and rtnetlink. Its three values keep their sense.
- **`ok`** when, for every monitoring interface, all of these hold:
  - it has no IPv4 or IPv6 address, link-local included;
  - ARP is off (`IFF_NOARP`), and IPv6 is disabled on it;
  - **it has no master of any kind** (a bridge, a bond, a team, an Open vSwitch datapath, a VRF or any other);
  - **it is the lower device of no other interface** (no VLAN sub-interface, macvlan or ipvlan sits on it);
  - and the host forwards no IP traffic (SL-28).
- **`bound`** when any of these fails, because the interface, or something stacked on it, could transmit. `interface-bound` is then in `coverage.degraded`, as in 0.1.
- **`unknown`** when the agent cannot read one of them (assumption A3).
- **The egress rule is not in `interface_check`.** It has a field of its own in the heartbeat, `egress_check`, whose values are `ok` (the rule of SL-26 is loaded on every monitoring interface) and `absent` (it is not, on at least one).
  - **The agent gains no capability to read it** (D3's condition on #631). Reading nftables rules is taken to need `CAP_NET_ADMIN` (**assumption**, not read from a source), which the agent must not hold.
  - **If it cannot be read without one, the field is left out of every heartbeat,** and not carried as a constant `unknown`.
  - **That is a visibility limit, stated here and in §16:** the sensor then does not report whether its egress rule is loaded. The controls are SL-T21 on the rig and the digest's `file` line for the rule set (CH-32).
  - A rig leg decides whether the rule can be read without a capability (SL-3, "What the rig still owes"; W-6).
  - **`egress_check` is in every heartbeat of a run, or in none** (D3's note 5 on #634). A field that was carried earlier in the run and is then left out means the agent's reading changed, and is read as `absent`, not as "unreadable".
  - At the node, `absent`, or a field dropped within a run, raises `sensor-egress-absent` and refuses nothing, because it is the sensor's own word (CH-45; D5 on #631; ruling 4 on #634).
  - **Whether the field was carried earlier in the run is a baseline in the cursor** (CH-26's baseline rule; D5's B1 on #634; SL-26's §11.3 as #641 amends it). A heartbeat that is **the run's first seen from its start** (the node accepted the run as a new run, CH-13 row 6, and has read every `seq` of it below that heartbeat with no declared loss) sets the baseline: carried or not. An omitted field there raises nothing, and status shows the egress state as **`unknown`**, D3's word (#644's §1.11 row 20; D5's N4 on #634).
  - **When the node holds no baseline for the run and the heartbeat is not the run's first seen from its start** (after a lost sensor database, or when the run's first heartbeats were evicted, refused or in a gap), a heartbeat that omits the field raises `sensor-egress-absent`, until a new run shows from its start whether the field is carried. The node then cannot tell a field dropped within the run from one never carried, so it fails loud (D1's alarm half in D4-90; SL-26 §11.3). *Test:* W-8 (e); the rig's SL-T24 (h).
- **Counted:** heartbeats whose `interface_check` is not `ok`, and heartbeats with `egress_check` `absent`, in status.
- **Not in it** (each invisible to a kernel read; D2's N-4, inference). Each is for the test named:
  - an LLDP or DCBX agent in the NIC's firmware;
  - a board management controller that shares the port through NC-SI (SL-27, an H-row);
  - Ethernet PAUSE frames sent when transmit flow control is on (the image test, SL-T16);
  - IPv6 duplicate address detection, router solicitations and MLD reports sent at link-up before `disable_ipv6` is applied, because the check reads state after the fact (the image test);
  - the socket holder's socket, under its call filter. It can send after `CAP_NET_RAW` is dropped (SL-26, AP-31 (3); measured on the rig, run 43077596916, one kernel, on a veth pair), so what stands against it is the call filter, the egress rule and the attachment (SL-3; SL-T21, SL-T22);
  - a user-space LLDP agent, and STP, which needs a bridge that the master rule already catches;
  - a DHCP or time client (SL-T16, SL-T18);
  - whether the engine's namespace is empty (SL-T2).

  C-11's zero-frames test stays the control for all of it.
- **Meets:** SL-3, SL-26, SL-28.
- **Test:** W-2, W-4, W-6, W-8.

## 8. PRP (brief item 7)

**CH-28. `prp_window_ms`, and what a duplicate is.**

- **Input:** `coverage.settings.prp_window_ms`, an integer, required in 0.2 records. A value outside 10 to 2,000 is refused as `range`; an absent one as `missing`.
- **Where it runs:** the frame stage, before the engine sees a frame (SL-3). The capture clock is the kernel's receive timestamp that each pipe record carries (CH-21), never the time the frame stage read the record.
- **A duplicate** is a frame whose source MAC and RCT sequence number equal those of a frame seen within `prp_window_ms` on the capture clock, and whose RCT LAN ID differs from that frame's. It is judged by the LAN ID in the RCT, not by the interface it arrived on (D2's N-2).
- **A repeat with the same LAN ID** is passed to the engine and not counted (D6, on 0.1 §4.4's "seen").
- **The comparison** (D2's VLAN answer, adopted by D1) is made after the frame stage has put a tag that the kernel stripped back into the frame (SL-3 item 2). It covers the frame from the destination MAC through the RCT. It leaves out the whole 802.1Q tag (TPID and TCI, so the VID, PCP and DEI), masks the RCT's LAN ID, and ignores any bytes after the RCT, which a bridge that stripped a tag from a short frame adds as padding. The RCT is found from its suffix and its LSDU size field. Only a copy identical under this comparison is discarded (D4-69).
- **Which copy is kept.** The first to arrive is passed, with its own tag. With differing tags the kept VID can change from frame to frame, so a discarded duplicate whose tag differed is counted (`prp_tag_differs`, CH-29). A flow may then show under two VLANs, and the count says why (D2's condition 2).
- **The window's purpose** is to cover the difference in delay between the two LANs. It is not a receiver's entry ageing (D2's N-1).
- **Bound: 400 ms by default, from 10 ms to 2,000 ms.** The basis:
  - SEL devices on a PRP network set `PRPTOUT`: SEL-751 and SEL-787-4 from 400 to 10,000 ms, default 500; the SEL-400 series from 100 to 10,000 ms, default 500. The SEL-400 series uses a fixed 44 ms at 1 Gbps for 87L and SV, so short windows exist (D2 on #627, citing the manuals). The default sits in what these devices use.
  - That IEC 62439-3 gives 400 ms is assumption A4. The project does not hold the standard.
  - The window must stay well below the time one source takes to wrap its RCT sequence number. **That the number is 16 bits is assumption A4**, so the wrap figure (above 160,000 frames a second at 400 ms) is an assumption too.
- It is a sensor setting, in the configuration digest (CH-32), and in an alert's flattened coverage.
- **Not counted:** a duplicate that arrives after the window passes as a new frame, and is decoded twice. That doubling is silent (§16).
- **Meets:** SL-3 (the discard runs in the frame stage).
- **Test:** P-1, P-2, P-4.

**CH-29. The discard stage's counters and its table.**

- **Input:** the discard step of the frame stage (SL-3).
- **Counters:** four heartbeat counters, run totals that never decrease, required in 0.2:
  - **`prp_mismatched`:** frames that meet a duplicate's MAC, sequence number and LAN ID condition but differ under CH-28's comparison. Neither copy is discarded, as D4-69 rules. A rise is a signal: a frame changed on one LAN, two senders that share a MAC, or a benign per-LAN difference, such as a PTP event message whose correction field differs per LAN if a device puts an RCT on PTP (D2's N-2, inference; whether a SEL device does is unknown).
  - **`prp_table_full`:** frames passed without a duplicate check, because the table was full. A frame that cannot be checked is passed, never discarded unchecked: a duplicate then doubles a count, which shows, where an unchecked discard could lose a frame, which would not.
  - **`prp_tag_differs`:** discarded duplicates whose 802.1Q tag differed from the kept copy's (D2's condition 1). The node's status shows it beside `prp_table_full` while it is above 0, as a reason why that sensor's flow counts and VLAN sets are unreliable. That is D2's note on round two, for D5 to build.
  - **`prp_wrong_lan`:** frames whose RCT LAN ID is not the configured `lan` of the interface they arrived on, the interface being the slot that the frame's pipe record carries (SL-3). They are handled as any other frame. The SEL-751 counts such "WRONG LAN" frames too (D2 on #627).
- **The table.** `prp_table_entries` is the number of (MAC, sequence number) entries kept: 65,536 by default, from 4 to 1,048,576 (D6's bounds note).
  - An entry lives for the window only, so the table holds the doubly attached sources' frame rate times `prp_window_ms` (D2). At 400 ms, 65,536 entries hold about 163,000 frames a second.
  - D2's figures: one SV stream at 80 samples a cycle is 4,800 frames a second at 60 Hz (inference, IEC 61850-9-2LE not held), so sixteen streams fill under a third of the table. A line-rate flood of minimum-size frames can fill it, and `prp_table_full` then counts. It is a `setting` line in the manifest (CH-32), so the rig can set 4 (P-3).
- **Not in `coverage.degraded`.** `prp_table_full` can double counts while `coverage.degraded` is empty (D6). A new degraded value would make every 0.1 reader refuse the stored 0.2 records that carry it, because the reader checks the degraded list against its own closed set at every minor (`citation.go`). So the counter, the node's status and its `sensor.counters` event carry it instead (§16).
- **Meets:** SL-3. **Test:** P-2, P-3.

**CH-30. More than one sensor host on a PRP network: what C13 would need, as options** (D2's N-3).

D3's O-12 lists one host with two monitoring ports, two hosts, or one LAN only. **This is not a decision:** O-12 is the owner's. The node's design holds two sensors in its shape, a database each, and the third part builds one (#644 §1.2, `MaxSensors`; D5-10; D4's note 7 on #633). Its shape for two is option (ii).

| Option | C13 change | Cost |
| --- | --- | --- |
| (i) One host, two monitoring ports | None. The discard runs in the frame stage (SL-3) | One machine touches both LANs (SL-28, O-12). On the SEL-2730M and RSTP-mode switches the mirror target is documented as taking no ingress during a monitoring session (D2 on #627); O-1's rule still counts a mirror port as accepting ingress until an H-row shows otherwise for that model |
| (ii) Two hosts, two streams, no merge | None. Each sensor reports its LAN (`interfaces[].lan`, `prp.lans_seen` with one LAN), so `duplicates_discarded: false` is not a mismatch (0.1 §4.4) | Each event on both LANs can alert twice. The two streams also differ by design: a singly attached node's frames are on one LAN only (D2). Which sensor ties the node's own sessions is D5's |
| (iii) Two hosts, merged at the node | For each cited frame, its RCT sequence number and a hash with the LAN ID, tag and padding masked. For flow counts, either each flow's set of RCT sequence numbers, which is unbounded, or a rule that one LAN's sensor is primary | A merge stage in the node. The two clocks must agree well within the time a source takes to wrap its sequence number (A4), not within `prp_window_ms` (D2 corrects `674ce453`). Both backlogs must drain before a merge |
| (iv) One LAN only | None | One host and one port. Every doubly attached node's traffic is seen, because it sends each frame on both LANs (D2, inference). Singly attached nodes on the other LAN are not seen, and the coverage statement says one LAN |

**D4's view:** (iii) costs a merge stage for the gain of one alert instead of two. Use (i) where one host may touch both LANs, otherwise (ii) or (iv).

**Meets:** no SL rule. Brief item 7 and O-12.

**Test:** nothing to test. These are options, not requirements.

## 9. A blind sensor (brief item 8)

**CH-31. Per-interface counts and carrier in every heartbeat, and the node's rule.**

```
"interfaces": [ { "name": "<token>", "carrier": "up|down|unknown", "packets": <uint64> } ]
```

- **Input:** required in 0.2 heartbeats, at most `MaxInterfaces` (8), one entry for each interface in `coverage.interfaces`, by name.
- **The node's checks:**
  - A set of names that differs from the coverage statement's is refused as `conflict`, and so is a sum of `packets` that differs from `counters.packets`.
  - A falling `interfaces[].packets` within a run is refused as `order` by `Follows` (counted `counter-decrease`).
  - A `carrier` outside its set is refused as `form`.
- `packets` is the frames the frame stage read from the first pipe for that interface since the run began, before the PRP discard. The interface is the slot that each pipe record carries (SL-3). `carrier` is its link state; `unknown` when it cannot be read (assumption A2).
- **The node's rule** (difference 6, ruling; #628 §1.8):
  - An interface is **blind** when its `packets` has not risen across the heartbeats of the last `blind_after_s` of the node's monotonic time, or when its `carrier` is `down`.
  - Only heartbeats that are not late (CH-23) count.
  - `sensor-blind` is raised when **any** interface is blind, and names it. A coverage gap opens only when **every** interface is blind.
  - The comparison starts again at a new run's first heartbeat.
- **`blind_after_s`:** a node setting, 300 s by default, from 60 s to 3,600 s.
- **The basis (assumption A7):** a mirrored station LAN carries periodic traffic. D2 cites a device-side source per device (D2 on #627, from the manuals): a SEL device on PRP sends supervision frames every `PRPINTV` (1 to 10 s, default 2); GOOSE repeats at its maximum time; C37.238 PTP messages go every second. So 60 s of silence on a port that mirrors such a device is not normal. Whether a site's mirror carries those frames is per site, and is unshown, so the default is the wider one.
- **What this cannot see:** a sensor that lies about its counts (AP-36). The node's own-session check is the independent one.
- **Counted:** stretches of `sensor-blind`, under CH-45's cap.
- **Meets:** SL-20.
- **Test:** K-1, K-2, K-3.

**CH-44. What resets `sensor-unreachable`, and coverage that is unknown** (D3's note 2, ruling 3).

- **Input:** frames on a connection whose hello was accepted.
- **Outcome:**
  - Only an **accepted** frame resets `sensor-unreachable`'s timer: a tick accepted and not early (CH-8), or a heartbeat or record taken (CH-17). A refused record, a failed hello, an early tick or an unknown type does not reset it (AP-36 (2); D4-73's rule that a reconnect never resets it).
  - A stretch of 60 s with no heartbeat that is not late, while accepted ticks arrive, shows as **coverage unknown**. Status shows `coverage: unknown`, and the node raises **`sensor-no-heartbeat`** once a stretch. The name and the 60 s are #628 §1.8's.
  - **The interval of such a silence is a coverage gap, and the alarm is unchanged** (D3's item 6 for #645; SL-16's ninth cause; D6's B1 on #641). The alarm says the heartbeats stopped. The interval is carried by a `silent` gap, opened from W once no current heartbeat has come for `HeartbeatGapMax` while the link is current and no gap is open (CH-45). *Test:* V-16.
  - A flat interface count seen only in late heartbeats is recorded, once the backlog drains, as a past blind stretch in one health event, `sensor.past-blind`, under CH-45's cap.
- **Counted:** each alarm's stretches, under CH-45's cap.
- **Meets:** SL-20, AP-36.
- **Test:** K-4; V-16 for the gap.

## 10. What the sensor states about itself

### 10.1 The configuration digest

**CH-32. `coverage.config_digest`, and in `sensor-hello`.** Required in 0.2: `sha256:` and 64 lowercase hex digits.

- **What it covers.** At the start of each run, the agent builds a manifest M: UTF-8 lines, each ended by `\n`, sorted by their bytes, with no duplicate:
  - `program <name> sha256:<hex>`, one for each of the four programs of SL-3: `socket-holder`, `frame-stage`, `engine` and `agent`. **[S2]** Which files make up the engine's executable and its plugins depends on the engine;
  - `file <path> sha256:<hex>` for every configuration file any of the four reads at start, and for the files that confine them. That includes:
    - the engine's scripts and packages (**[S2]**);
    - the allow-list (**[S2]** for its form);
    - the redaction configuration;
    - the capture configuration and the agent's configuration;
    - **the socket holder's call-filter profile** (SL-3);
    - **the egress rule set** of SL-26.
    - `<path>` is relative to the sensor's configuration root, matches `^[A-Za-z0-9._-]+(/[A-Za-z0-9._-]+)*$`, is at most 255 bytes, and has no `..` segment.
    - The agent's key and its enrolment are not in M. They are not configuration, and a renewed enrolment must not read as an edit;
  - `setting <name> <decimal>` for `prp_window_ms`, `prp_table_entries`, `sa_reply_timeout_ms`, `max_pending_dnp3`, `flow_idle_s`, `buffer_bytes`, `buffer_sync_ms` and `ring_bytes`. `ring_bytes` is the capture ring's size in bytes, 0 allowed (O-11);
  - `redaction <slot> on|off` for each slot of D4-67 and D4-68, under these closed names: `telnet-password`, `ftp-pass`, `snmp-community`, `http-basic`, `http-cookie`, `http-set-cookie`, `http-form-body`. A server's echo of a slot is part of its slot.
- `config_digest` is `sha256:` and the hex SHA-256 of M.
- **It is constant within a run.** Each program reads its configuration only at its start, and any start begins a new run (CH-12). The node keeps the run's digest from its hello **in the cursor, saved at CH-13 row 6** (CH-18; SL-31; D3's preference, taken by #644 §1.4), so a `sensorrun.json` that is lost or behind cannot lose it or bring back an earlier run's. A record whose `config_digest` differs from it is refused as `conflict`, across a node restart too (D5's note on #627). **With the sensor database lost,** the digest is learned again from the next hello, and status says so. It is the sensor's word either way, and row 8 still compares it with the configured digest.
- **A site build has no `off`.** The site's frame stage, the program that redacts (SL-3), refuses at start a configuration that names the switch (SL-22, D1's ruling on #624). So `redaction <slot> off` appears only in a test build.
- **The agent hashes the files on disk at the run's start,** not what each program loaded. It shows an edit made through the files. A program that loaded something else is not shown (D3's note 12).
- **For the egress rule set this limit is stronger.** The digest hashes the rule file on disk, not the rules the kernel holds. Root loads those rules, and can change them without touching the file. So the digest shows an edit of the file and nothing else. `egress_check` (CH-27), where it can be read, and SL-T21 are what speak to the kernel's rules.
- **The agent shows M at its console,** so that a person can compare it with the digest the node shows.
- **The expected digest** is `network_sensor.sensors[].config_digest` in the node's configuration, read from the sensor's console at commissioning, as the pins are (D5-4, #628 §1.15). A hello or record whose digest is not the expected one raises `sensor-coverage-mismatch`. It never refuses a hello and never fails a start (CH-13 row 8). Each patch of the sensor therefore needs an edit of the node's configuration, and until then the alarm stands.
- **What it shows, and what it does not.** It is the sensor's own word (AP-36). It shows an edit made through the sensor's own programs, such as a redaction slot switched off or an allow-list widened. It does not show a compromise.
- **Counted:** `conflict` refusals; stretches of the mismatch alarm.
- **Meets:** SL-3, SL-19, SL-22, SL-26.
- **Test:** G-1, G-2, G-3.

## 11. The 0.1 reader, and every new field

**CH-35. Every change bumps the minor and keeps a 0.1 reader.**

- **The channel stays strict.** A 0.2 node reads 0.2 on the channel only (CH-36). A 0.1 peer cannot pass the hello (`hello`), which is right: 0.1 has no binding, no resume and no acknowledgement.
- **The reader for stored records accepts both identifiers.** It reads any 0.x minor already: strictly for its own and earlier minors, and forward for a later one (`DecodeStored`, `storedSchema`).
  - A field that 0.2 requires in a channel record is optional in the Go type, required in a 0.2 channel record, and may be absent in a stored record of any minor.
  - **An alert's two new coverage fields are optional at every minor** (D6), because a 0.2 node can raise an alert from a stored 0.1 observation, whose coverage lacks them.

| New in 0.2 | Where | A 0.1 reader | The 0.2 reader on a 0.1 record |
| --- | --- | --- | --- |
| The four messages | The channel only, never stored | Never meets them | — |

**The rollback** (D5's finding, D6 B1; D4 confirmed the reading of the code; ruling on the 0.1 rollback):

- **What `main` does.** `Runtime.detectorCheckpoints` (`platform/node/netdetector.go`) keeps only documents whose `schema` equals `otsec.netcheckpoint/0.1`. So a 0.1 node does not see a 0.2 checkpoint at all. It starts as a first start, with no `network-detector-not-restored`. It judges the retained observations again and stores their alerts a second time. It never removes the 0.2 document, which can be up to 1,354,752 bytes in the configuration class.
- **Required: a bridge build, released before the first build that writes 0.2.** Its node, still writing 0.1:
  1. recognises any `otsec.netcheckpoint/0.x` detector document;
  2. for a minor it cannot read, raises `network-detector-not-restored`, starts its detector from the oldest retained observation, and removes that document once its own first checkpoint has committed. **It raises the retained observations' alerts again, and says so with the alarm.** That is a stated limit (D6; #628 §1.15 item 3, where D5 keeps it rather than read an unverified `last_alert_seq`);
  3. accepts an alert of a later minor whose `asset_id` is `clock-skew`, `sensor-records-late` or `hold-timeout`;
  4. reads an unknown `coverage.degraded` value of a later minor as degraded, not as a refusal, so that a later minor can add one (D6's note on round two);
  5. ties a held observation by patching its raw JSON rather than re-encoding it with 0.1's type, so that a held 0.2 body keeps `made_utc` and its `node` marks (#628 §1.15 item 2).
- **It is a release rule** (ruling 14 on #628): D7 records the bridge build in `docs/release.md` as a release floor, with the configuration shape that rolls back with it (#628 §1.15 item 4).
- **Rollback from 0.2 is supported only to the bridge build.** A rollback to an older build gets the silent restart above: duplicate alerts, and an orphaned checkpoint. The third part's brief carries the build order.
- **The learner's checkpoint** has no coverage statement, and its form does not change. It takes the new identifier because both halves share one (0.1 §8), and the bridge build's reader accepts both.
- **The intake hold's checkpoint** keeps `otsec.netcheckpoint.intake/0.1`. A held body is raw JSON decoded with `json.Unmarshal`, so a 0.2 body passes (D5-9).
- **Sizes.**
  - The two coverage fields take about 110 bytes, inside `MaxCoverageBytes` (2 KiB), which does not change.
  - `made_utc` and the node marks add up to about 60 bytes to a stored observation, plus `node.lost` at most 8 spans of about 70 bytes.
  - The two flattened coverage details add about 130 bytes to an alert, and `assets` and `assets_total` at most about 330.
  - The source cursor adds up to the node's 2,048 bytes to `Record.Bytes`: at most 479 with no span or `prior` held, and up to 1,575 while they are held (CH-18, with the `drops_driver` baseline; 192 before P4-4-L6).
  - **The worst stored body is pinned against 0.1's `MaxNetobsBytes` (24 KiB),** because a 0.1 `DecodeStored` checks that first (D6). If the worst-case tests fail with the new fields, the bound goes to D1, and is not changed silently. No test was run for this proposal; the one local render behind CH-43's and C4 0.4's octet figures is not reproducible and is not evidence of any class (C4 0.4 §4).
- **Meets:** no SL rule. The brief's acceptance.
- **Test:** R-1 to R-6. R-3's fixture and test land on `main` before the 0.2 code, while the 0.1 code is there to run them (D6).

A step of the wall clock while a gap is open changes neither the count the chain's fourth part asks for (CH-39) nor whether the gap closes. A step back that puts the written end before the start is handled as across a restart (below): the gap is written with `clock_stepped: true`, and **a gap is never dropped for its times.** *Test:* V-9's third case. *Control:* a node that takes the length from the wall-clock times asks the chain for no heartbeats and closes the slow-source cut as covered.
- **The gap at the node's start reaches back** (D4-90): to W, the last moment the node holds durably as watched. **When the cursor holds no W,** whatever the reason (the cursor unread, the sensor database lost, or a sensor never watched since its enrolment), it reaches back to **an earlier moment the node still holds durably, never a later one** (SL-16; gap leg 9): the copy of W in `sensorrun.json` when the file holds one, whatever its `write_no`, since a file that is behind only moves the start earlier; and otherwise the time of the live enrolment's `sensor.enrolled` record (`enrolled_at` in `sensors.json`, which the fold can also read from the chain). **A sensor never watched since its enrolment has been unwatched since it,** so its gap, opened at a node start or while the node runs, begins no later than `enrolled_at` (SL-16), and it stands from the enrolment, not from a connection's end: the `link` row above holds it while the node holds no W, so through a long first backlog, or a first dial that never comes, it is `open` in the stream (gap leg 15). The event then carries `from_bound: true`, and status says that the start is a bound and not the moment watching stopped. So a station power loss that also takes the sensor database leaves no interval in no gap.
- **Across a node restart the reach-back compares wall-clock times,** the saved moment and the time after the start, because nothing else survives a restart (as for C8-5's cap). A clock stepped forward during the outage lengthens the gap, which fails closed. **A clock stepped back** can put the gap's end before its start: the gap is still written from the saved moment, never dropped, with `clock_stepped: true`, and the node writes C4's `time.node-stepped` health event once for that step. C4 0.3 defines `time.node-stepped` (`contracts/event/event.go`), and nothing on `main` writes it, so this adds a writer and changes no contract (#644 §1.9 item 5; SL-16).
- **How a gap closes.**
  - **As covered,** whole, only by the chain of CH-39, in the run of W's heartbeat, with its four parts and `HeartbeatGapMax`. There is no partial cover (CH-39).
  - **Otherwise unwatched,** at the first current heartbeat after its cause ends **that shows capture** (as for W above: not every interface blind under CH-31, flat counts included), written as unwatched (`covered: false`) from its start to that heartbeat's receipt (D3's item 4 for #645; SL-16). A sensor whose counts are still flat at the reconnect keeps the gap open until an interface's `packets` rise. *Test:* V-17.
  - **Three causes are not closed by a chain** (SL-16): a **`lost`** gap is its span, from the stated `from_utc` to the fixed cut end (CH-40), written once with those times; a **`blind`** gap closes unwatched at the first current heartbeat in which an interface's `packets` rose (CH-31; V-17's second case); a **`revoked`** gap is closed only by the first current heartbeat, showing capture, of a run under a later enrolment's generation, which is a new key, since a revoked pin is never enrolled again. It closes unwatched, never as covered: no chain runs across a new generation's run 1, and nothing the revoked key sent is trusted for that interval. Nothing else closes it: not a restart, a change of configuration or time. With no later enrolment it stays open (D3's rule 1 on #641, comment 6838033945).
  - A `held` gap after a new key's enrolment closes the same way, unwatched at that key's first current heartbeat, because no chain runs across a generation (gap leg 11).
- **What is written:** the health event `sensor.coverage-gap` on `platform/health`, with the details `cause` (the cause at the open), `causes` (every cause seen while it stood, space-separated), `state` (`open` or `closed`), `from_utc`, and when closed `to_utc` and `covered` (`true` or `false`); the times are on the node's clock, except a `lost` gap's, which are its span's. Also `merged`, the number of gaps a merged record carries; `from_bound: true` when `from_utc` is an earlier bound and not W; and `clock_stepped: true` when the node's clock was stepped back across the gap. **The names `from_bound`, `clock_stepped` and `enrolled_at` are D5's** (#644 §1.9 item 5 and §1.3; SL-16 states only what each must carry), and C13 states them so that both documents give one name. They are details of a health event, which C4 0.3 accepts as free keys; C4 0.4 does not change that.
- **When it is written** (#644 §1.9 item 5): a `lost` gap is written once, `closed` with `covered: false` and its span's times, from the save that admits its span (CH-40; SL-16: "written once with those times"); a `blind`, `held`, `revoked` or `sensor-failed` gap is written `open` when it opens; a `link`, `node-start` or `silent` gap is written `open` only once it has stood 60 s from its start, as `sensor-unreachable` is due. Every gap written `open` is written again when it closes, covered or not. One closed before it was written `open` is written once: as `closed` with `covered: false` if unwatched, and not at all if covered. So a link drop whose backlog covers it within a minute writes nothing, a longer one is forwarded as open and then as covered, and nothing watched is forwarded as unwatched. **A gap that never closes is in the stream as `open`** (gap legs 10 to 13), so an outage that does not end is never a quiet stream.
- **Budgets and merging.** `lost` gaps have their own 4 an hour, and every other cause another 4 (the budget table above). Past a budget, gaps of that budget are merged into one record: first start, last end, number and causes. **A `lost` gap merges only with `lost` gaps,** so it is never merged away without its cause, whatever the other budget does. A gap waiting for its budget or the ceiling is held in the cursor, as above.
- **At a start,** the node opens `node-start` from W for each configured sensor, and writes the `lost` gap of every span still marked owed (CH-40).
- **What it rests on.** A heartbeat is the sensor's word (AP-36). These rules stop an honest fault from closing a gap, not a compromised sensor from claiming capture it did not make.

**Limits:**

- **Everything is `desk`, and nothing is built.** No row of §15 has run.
- **A compromised sensor can still lie** in every field it states: counts, `drops_channel`, `lost`, `prior`, `previous_end`, `config_digest`, `pinned_by`, `made_utc` (and so `late`), and every observation (AP-34 (b), AP-36). 0.2 makes a lie by another sensor, a replay, a copy and an undeclared loss visible. It does not make a sensor honest.
- **`late` is the sensor's own word** (CH-23). The node's own measure is CH-39's break. Its residual, a clock moved and restored within a break at or below `backlog_tie_s` and within `max_skew_ms` of the node's measure, goes to AP-35 (ruling 1, D3). So does a step made and undone between two ticks (CH-22).
- **The current run can wait behind an outage's old runs:** up to 64 runs drain at one connection every 10 s, about 11 minutes, or longer under back-off (CH-38, CH-46). `sensor-no-heartbeat` shows it (D6).
- **A node that holds its key can empty the sensor's buffer** by acknowledging. The buffer is not a second evidence store (D3's note 10). A flood while the link is cut evicts earlier records, declared (CH-20); D3 adds it to AP-36.
- **A crash** loses up to `buffer_sync_ms` of numbered records, and an engine or capture-stage crash whatever that program held. Each is declared as a possible loss (CH-42), not counted exactly.
- **Two node kills can over-count one drop.** If a release of an earlier run's held records stores nothing, it moves no T and only raises the newer run's totals (CH-17), so two kills in that window can raise a dropped total twice. That is an over-count, never a loss (D6 on `0f4f19f3`).
- **A tick's offset includes queueing** behind records on the same stream (CH-22). The least of 6 ticks reduces this, and does not remove it while a long backlog drains. CH-39 covers ties during that time.
- **A `lost` span is on the sensor's clock** (CH-40; D3's item 9 for #645, not taken in 0.2). While no tie is made for skew (CH-22's two causes: `sensor-clock-skew` stands, or the latest o is outside `max_skew_ms`; D5's N1 on #645), the span, its gap and the interval in which `own-session-unseen` is off can be shifted by up to the offset from the interval actually lost; the cut end keeps it from reaching past the node's receipt plus `max_skew_ms`.
- **A loss's mark** reaches the detector only on a later observation of the same run (CH-40). If none follows, a session in the span may raise `own-session-unseen`, which fails loud.
- **A PRP duplicate later than the window,** and a full table, double counts with `coverage.degraded` empty (CH-28, CH-29). The counters show the second, and nothing shows the first.
- **How long the buffer lasts** is not known, because no station's record rate has been measured (CH-20).
- **The sensor may not report whether its egress rule is loaded.** If the link agent cannot read the rule without a capability (A9), `egress_check` is left out of every heartbeat (CH-27). That is a visibility limit: the node then learns of the rule only through the digest's `file` line, which shows the file and not the kernel's rules (CH-32), and the rule is shown only by SL-T21 on the rig.
- **The only measurement behind SL-3's shape is one kernel, on a veth pair** (run 43077596916, with a stand-in and no sensor). Nothing in this proposal about the four programs, the first pipe or the egress rule is built, and no sensor image exists.
- **The gap rule reports watched time as unwatched when it cannot show otherwise** (CH-39, CH-45). A sensor restart inside any break, a declared loss, an unread `seq`, a silent stretch or too few heartbeats leaves the whole gap open. That is the direction D4-90 requires, and it costs false "unwatched" intervals, never false "watched" ones. A compromised sensor can still state heartbeats that close a gap (AP-36).
- **After a lost sensor database** (CH-18): a stale run-file copy can let one narrow window of copied or restored runs in (D3's bound); every held span is taken again as a new `lost` gap; `sensor-gap-undeclared` is raised once for the trimmed records; a `prior` owed may be lost, named in status; a capture loss can be counted twice; and the next dial waits for an administrator's re-arm.
- **A `sensor.run-loss` or a `lost` gap can be written twice** after a kill between its commit and the clearing of its mark (CH-16, CH-40). Never not at all; the run's identity in the event lets a reader see it.
- **The agent's counts are in status only** (CH-43), not in a forwarded event, because the event would not fit a 2,048-octet Syslog target with them (C4 0.4, §4).
