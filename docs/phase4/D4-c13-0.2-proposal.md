## 2. The transport (brief item 1)

**CH-1. The link is TCP, then TLS 1.3, then C13's framing.** The node dials the address and port that the live enrolment names (SL-5, SL-9). The rules for the handshake are D3's, and C13 relies on them: TLS 1.3 only; both ends present a certificate; each end checks the other's key against the pin in the enrolment in force at that moment, at every handshake; no session resumption, no early data and no pre-shared key; no system roots and no trust by name (SL-2, SL-12). The certificate's own dates are not checked: the node enforces the enrolment's `not_after` (SL-8). C13 sets no default port; the enrolment names it.

- *Meets:* SL-2, SL-12, SL-18 (the node opens the link and listens for nothing).
- *Refused:* a handshake that fails any of these never reaches C13. The node counts it and writes `sensor.link_refused` with D3's reasons `peer-key` or `expired` (SL-T3, SL-T8). That count and record are D5's and D3's, and are named here only so that the sets meet.

**CH-2. Framing runs in both directions, with a small cap from the node.** Every message in either direction is one frame: the 4-byte big-endian length, then one JSON document in UTF-8.

- Sensor to node: at most `MaxChannelFrame` (64 KiB), as in 0.1. A longer length closes the connection (`frame-too-large`), as today (`FramesTooLarge`).
- Node to sensor: at most `MaxNodeMessage` (1 KiB). A longer length closes the connection at the agent (`frame-too-large`). The node's two messages are under 300 bytes, so 1 KiB holds them with room and no more (SL-19: "small and bounded, and carry no text").
- *Meets:* SL-19, SL-20 (a bounded read at each end).

**CH-3. One connection for each sensor.** The node opens at most one connection, and has at most one dial in progress, for each `sensor_id`. If the link agent completes a handshake with the node's key while it holds an older connection, it closes the older one (`superseded`) and keeps the newer: the node holds one key, so the newer connection is the node's current one, after a restart for example.

- *Meets:* SL-12 ("at most one connection for each sensor").
- *Counted:* `superseded` at the agent, which the next `tick` does not carry (the agent's counts are its own, and are shown at its console).

**CH-4. Timeouts.** Both ends use the same three:

| Name | Value | What it does |
| --- | --- | --- |
| `HandshakeTimeout` | 10 s | The TLS handshake must complete within it, at both ends (SL-12) |
| `HelloTimeout` | 10 s | The first frame from the other end must arrive within it after the handshake: `node-hello` at the agent, `sensor-hello` at the node. Otherwise the connection closes: `node-hello-timeout` or `hello-timeout` |
| `IdleTimeout` | 30 s | A connection that carries no frame in a direction for 30 s is closed by the receiving end (`idle`). The sensor sends a `tick` every 10 s and the node an `ack` at least every 10 s (CH-8, CH-9), so 30 s is three missed messages |

- *Meets:* SL-12 (a slow handshake cannot hold the dialer), SL-20 (a read deadline for each link).

## 3. The channel's messages

### 3.1 Closed sets

**CH-5. Each direction has a closed set of message types.**

| From | Types | Stored? | Numbered (`seq`)? |
| --- | --- | --- | --- |
| Node | `node-hello`, `ack` | No | No |
| Sensor | `sensor-hello`, `tick` | No | No |
| Sensor | `heartbeat`, `observation` (0.1's records, 0.2's fields) | The observation, and health events from the heartbeat, as in 0.1 | Yes, as in 0.1 |

- **At the agent,** a frame from the node whose type is not in its set, that fails a strict decode, or that carries a field not listed here, closes the connection (`type`, or `node-hello` or `ack` for a malformed one of those). The agent has no code path from a node message to anything but its trim cursor (SL-19).
- **At the node,** an unknown type from the sensor is refused with `CodeType` and counted, and does not close the connection, as in 0.1. An alert-shaped record is still refused this way (0.1 §1, AP-34).
- *Meets:* SL-19, and SL-T12's "a contract test pins the closed set of message types in each direction".

### 3.2 `node-hello`

**CH-6. The node's first frame on every connection.**

```
{ "schema": "otsec.netobs/0.2", "type": "node-hello",
  "sensor_id": "<uuid>", "generation": "<decimal from 1>",
  "taken": { "run_counter": "<decimal from 1>", "run_id": "<uuid>", "seq": "<decimal from 0>" } }
```

- `sensor_id` and `generation` are the live enrolment's.
- `taken` is the node's saved position for this `sensor_id` and generation (§4.6): the highest run it has accepted, and the highest `seq` of that run that it has taken (§4.5). `seq` is 0 when the run is accepted and nothing of it is taken yet. `taken` is absent when the node has accepted no run of this generation.
- The node sends it only after it has finished with, or abandoned, every record of its previous connection to this sensor. So `taken` is exact when it is sent. **D5 builds this.**
- **At the agent:** a `sensor_id` or `generation` other than its own enrolment's closes the connection (`binding`). A `taken` that names a run the agent does not hold, by counter and `run_id` together, is not applied to its buffer, and the agent still sends its hello: the node then judges it (§4.2). That is how a node that saw a copy learns of it.
- *Meets:* SL-13 (node to sensor: `sensor_id`, generation and the last committed position), SL-19 (no text, no setting).

### 3.3 `sensor-hello`

**CH-7. The sensor's first frame, after it reads `node-hello`.**

```
{ "schema": "otsec.netobs/0.2", "type": "sensor-hello",
  "sensor_id": "<uuid>", "generation": "<decimal from 1>",
  "run_counter": "<decimal from 1>", "run_id": "<uuid>",
  "first_seq": "<decimal from 1>", "newest_seq": "<decimal from 0>",
  "drops_channel": "<decimal from 0>",
  "prior": { "runs_skipped": "<decimal from 0>", "records_lost": "<decimal from 0>" },
  "pinned_by": "signature|console",
  "buffer_bytes": "<decimal>",
  "sensor_utc": "<RFC 3339 UTC>" }
```

- `run_counter` and `run_id` name **the one run this connection carries** (§4.4).
- `first_seq` is the `seq` of the first record the agent will send on this connection. `newest_seq` is the newest `seq` of this run that the agent has numbered when it sends the hello. It is at least `first_seq` − 1, and equals it when the agent has nothing of this run to send yet; a lower value closes the connection (`hello`). Records up to `newest_seq` are this connection's **backlog**, which the node's hold can wait for by number and not by clock (§13, D5-7).
- `drops_channel` is this run's `drops_channel` so far: its numbered records that the agent evicted before the node acknowledged them (§5, §7). It declares losses (§4.3).
- `prior` is present exactly when the hello opens a run the node has not accepted (its `run_counter` is above `taken.run_counter`, or `taken` was absent). It declares what was lost before this run (§4.4).
- `pinned_by` says how the agent's end was pinned (§10.2).
- `buffer_bytes` is the agent's buffer bound (§5), so that status can show how full it is.
- `sensor_utc` is the sensor host's clock when it sent the hello (§6).
- **D3's SL-13 listed "the oldest `seq` its buffer still holds".** It is replaced by `newest_seq` and `drops_channel`: what the node will receive, and what the sensor declares lost. Under the resume rule (§4.3), records the agent holds below `first_seq` are at or below the node's taken position, so the node could do nothing with the oldest one.
- *Meets:* SL-13, SL-14, SL-5 (how the end was pinned), SL-17 (the clock).

### 3.4 `tick`

**CH-8. A live message from the sensor every 10 s, never buffered.**

```
{ "schema": "otsec.netobs/0.2", "type": "tick",
  "sensor_id": "<uuid>", "run_id": "<uuid>",
  "sensor_utc": "<RFC 3339 UTC>",
  "newest_seq": "<decimal from 0>", "drops_channel": "<decimal from 0>",
  "buffered_records": "<decimal from 0>", "buffered_bytes": "<decimal from 0>" }
```

- The agent makes a `tick` at the moment it sends it, every `TickInterval` (10 s) and once straight after its hello. It is never written to the buffer and never numbered.
- **Why a new message, and not the heartbeat.** A heartbeat is a numbered record: during a link outage it waits in the buffer, and after the outage it arrives behind the backlog. Its `at_utc` then differs from the node's clock by the outage plus the skew, and the node cannot tell the two apart. A `tick` is made when it is sent, so the node's received time minus its `sensor_utc` is the skew plus the network delay alone (§6.2). It also tells the node, while a backlog drains, how far the backlog goes and what has been lost from it.
- `sensor_id` and `run_id` must be the hello's. `newest_seq` and `drops_channel` are the connection's run's, and neither may fall below its value in the hello or an earlier tick on this connection. A tick that breaks any of this closes the connection (`tick`).
- `buffered_records` and `buffered_bytes` are the agent's whole buffer, every run, for status.
- This is a fourth message type from the sensor, beyond SL-19's list of three. It carries no device text and no frame bytes, and it moves nothing on the node except the skew check, the gap check and status. **D3 reviews it against SL-19.**
- *Meets:* SL-17 (skew), SL-14 (declaring a gap without waiting for a heartbeat).

### 3.5 `ack`

**CH-9. The node's acknowledgement.**

```
{ "schema": "otsec.netobs/0.2", "type": "ack",
  "run_counter": "<decimal from 1>", "run_id": "<uuid>", "seq": "<decimal from 0>" }
```

- It names the connection's run and the node's taken position in it (§4.5).
- The node sends one within `AckMaxDelay` (1 s) of its taken position moving, and at least once every 10 s while the connection is open, as a keepalive (CH-4).
- **At the agent:** the run must be the connection's; `seq` must be at least the last `ack` on this connection; and `seq` must be at most the larger of the highest `seq` the agent has sent on this connection and, when the `node-hello`'s `taken` names this run, `taken.seq`. Otherwise the connection closes (`ack`) and the agent counts it. Before any record is taken on a new run, the node's keepalive `ack` names `seq` 0.
- **Its only effect** is to move the agent's trim cursor for that run (§5). An equal `ack` changes nothing.
- *Meets:* SL-15, SL-19 ("an acknowledgement for another run, or above the highest `seq` sent, is counted and closes the connection").

### 3.6 The order of a connection

**CH-10.** After the handshake:

1. The node sends `node-hello`.
2. The agent reads it, chooses the run to offer (§4.4), and sends `sensor-hello`, then a `tick`.
3. The node judges the hello (§4.2). If it accepts it, it reads records, ticks and heartbeats, and sends `ack`s. If it refuses it, it closes the connection.
4. The agent sends the run's records in `seq` order from `first_seq`, a `tick` every 10 s, and new records of the same run as it numbers them.
5. When the node acknowledges the newest record of a run that is not the agent's current run, the agent closes the connection with TLS `close_notify` (`run-complete`), and the node dials again for the next run (§4.4).

A second `node-hello` or `sensor-hello` on one connection closes it (`node-hello` at the agent, `hello` at the node).

### 3.7 What closes a connection, and what refuses one record

**CH-11.** Two kinds of fault, kept apart:

- **A channel fault closes the connection,** because the state of the exchange can no longer be trusted. Each is counted by reason at the end that closes.
- **A record fault refuses the one record** and the connection stays open, as in 0.1. It is counted under `sensor-record-refused` by reason.

**Closed at the node**, a closed set:

| Reason | When | C8 `sensor.link_refused`? |
| --- | --- | --- |
| `hello` | The first frame is not a valid 0.2 `sensor-hello` (a 0.1 peer, another type first, a strict-decode failure, a field outside its form); a second hello; `prior` present on a resume or absent on a new run (§4.2) | No |
| `hello-timeout` | No hello within `HelloTimeout` | No |
| `binding` | `sensor_id` or `generation` differ from the enrolment of the key that authenticated (§4.2); `pinned_by` differs from the one first seen in this generation (§10.2) | Yes, `binding` |
| `run-regressed` | §4.2 | Yes |
| `run-forked` | §4.2 | Yes, and the link is held (SL-16) |
| `run` | A record's `run_id` is not the hello's | No |
| `tick` | §3.4 | No |
| `idle` | CH-4 | No |
| `frame-too-large` | CH-2 | No |

**Closed at the agent**, a closed set: `node-hello`, `node-hello-timeout`, `binding`, `ack`, `type`, `idle`, `frame-too-large`, `superseded` and `run-complete`. The last two are not faults.

**A record refused, connection open**, at the node: every 0.1 reason stands (`decode`, `schema`, `form`, `range`, `order`, `conflict`, `hash`, `type`, `missing`, `sensor-id`, `seq`, `counter-decrease`, `stored`). A record whose `sensor_id` is not the hello's is refused as `sensor-id` and writes `sensor.link_refused` (`sensor-id`) under D3's cap (SL-10). 0.2 adds no record reason; the new checks on 0.2's fields use the existing codes (`conflict`, `order`, `form`), each named where it is defined.

- **A link opening or closing is not an audit record.** Only D3's six reasons write `sensor.link_refused` (D3's §11.2). The rest are counts in health and status, for D5 to bound (SL-20).
- *Meets:* SL-10, SL-14, SL-19, SL-20.

## 4. Runs, order and resume (brief items 2 and 3)

### 4.1 Generation, run counter and `run_id`

**CH-12. At the sensor.**

- **`generation`** is the enrolment's, a decimal from 1 (SL-5). It is carried in both hellos and in no record.
- **`run_counter`** is a decimal from 1 for each generation. A run begins, and the counter rises by one, **whenever any of the three programs starts**: the capture stage, the engine or the link agent (SL-3, SL-14). The agent learns that the capture stage or the engine restarted from the end of the stream it reads from it, and begins a new run before it takes anything from the restarted program. Taking a new enrolment begins run 1 of the new generation.
- **`run_id`** is a lowercase UUID the agent draws at the start of each run, as in 0.1.
- **The agent writes the new counter and `run_id` to disk, and syncs them, before it numbers the run's first record,** and so before any hello names the run. A crash at any point after that cannot bring the same counter back under another `run_id`, which the node would read as a fork (SL-14, D5 on #624).
- **Each record still carries `sensor_id`, `run_id` and `seq`,** as in 0.1. The generation and the counter are in the hello alone, and the node maps the `run_id` it accepted to them (D3 and D5 on #624).
- **Order** is by (generation, `run_counter`, `seq`).
- **At a new enrolment** the agent discards from its buffer every record of the previous generation that the node did not acknowledge, and declares them in `prior.records_lost` of the new generation's first hello (§4.4). They cannot be sent: the previous generation's key no longer passes the node's handshake (SL-6).
- *Meets:* SL-14, SL-16. *Test:* SL-T9 (j) and (k).

### 4.2 Judging a hello

**CH-13. At the node.** The node holds, for each `sensor_id` and generation, the saved position of §4.6: `run_counter` (0 when none), `run_id` and taken `seq`. It checks a hello in this order, and the first failure decides:

| # | Check | Outcome |
| --- | --- | --- |
| 1 | A valid 0.2 `sensor-hello` (CH-7) | Else close, `hello` |
| 2 | `sensor_id` and `generation` equal the enrolment of the key that authenticated | Else close, `binding` |
| 3 | `run_counter` is not below the saved one | Else close, `run-regressed` |
| 4 | Equal `run_counter` with another `run_id` | Close, `run-forked`, and the node stops dialling this sensor until an administrator enrols it again with a new key, or revokes it (SL-16) |
| 5 | Equal `run_counter` and `run_id`: **a resume** | `prior` must be absent, else close, `hello` |
| 6 | A higher `run_counter`: **a new run** | `prior` must be present, else close, `hello`. The node saves the new counter and `run_id`, with taken `seq` 0, **before it takes the run's first record** |

- **On a new run,** the node checks `prior.runs_skipped` against its own count: it must equal the hello's `run_counter` minus the saved `run_counter` minus 1. A difference does not refuse the hello, because refusing would blind the node. It raises `sensor-gap-undeclared` with reason `runs` and counts it.
- **A new run ends the previous run's state at the node:** the open-flow table is cleared, as on any new `run_id` today (`hold.go`, D1 on #576).
- *Meets:* SL-10, SL-13, SL-14, SL-16. *Test:* SL-T9 (b), (e), (g), (i).

### 4.3 Within a run: duplicates, re-ordering and gaps

**CH-14. Each record on a connection.** Let P be the taken `seq` of the connection's run when the hello was accepted (0 on a new run), and L the highest `seq` the node has read on this connection, which starts at `first_seq` − 1.

| A record whose... | Outcome |
| --- | --- |
| `sensor_id` is not the hello's | Refused, `sensor-id`; C8 under D3's cap; the connection stays open (SL-10) |
| `run_id` is not the hello's | Close, `run` |
| `seq` is at or below L | Refused, `seq` (a re-ordered or repeated record); the connection stays open |
| `seq` is above L and at or below P | Dropped as a **duplicate**: counted under `duplicate`, never stored twice, no alarm, and it moves L |
| `seq` is above L and above P | Read as in 0.1. If it is above L + 1, the `seq`s between that are above P are counted as this run's gap |

- A record that decodes strictly takes its `seq`, even when a later check refuses it, as in 0.1 (`link.go`), so a gap counts only records the node never received.
- *Meets:* SL-14. *Test:* SL-T9 (a), (c), (d).

**CH-15. A gap must be declared.**

- **G**, the run's gap at the node, is the sum of the gaps of CH-14 over every connection of the run, plus the resume gap: `first_seq` − P − 1 when that is above 0. On a new run P is 0, so the run's first `first_seq` − 1 records count.
- **D**, the run's declaration, is the largest `drops_channel` the sensor has stated for the run: in its hello, its ticks or its heartbeats. It counts the run's numbered records that the agent evicted before the node acknowledged them (§5).
- At each `tick`, if G is above D, the node raises **`sensor-gap-undeclared`** (reason `seq`) with the excess, once for each rise of the excess in the run, and counts it.
- D may exceed G: a record that the node took, but whose `ack` reached the agent after the record was evicted, counts in D and not in G. So the check is "G is at most D", never equality.
- A `drops_channel` in a tick or a hello below the run's earlier value closes the connection (`tick` or `hello`). In a heartbeat it is refused as `counter-decrease`, as every counter is in 0.1.
- *Meets:* SL-14 ("a gap the sensor does not declare raises an alarm"; "a loss nobody owns is how a record is made to vanish", P5). *Test:* SL-T9 (f).

### 4.4 Records left from an earlier run

**CH-16. Flushed before the next run's hello, or declared lost in it.**

- **Each connection carries one run.** The agent offers the oldest run of its generation that still holds records the node has not acknowledged, and its current run when none does. It never sends a record of a later run on that connection.
- It applies `node-hello`'s `taken` only when the counter and `run_id` name a run it holds, and then drops that run's records up to `taken.seq` from its buffer.
- **A resume** offers the run named in `taken`. `first_seq` is `taken.seq` + 1, or the run's oldest record still held if that is higher. The records in between were evicted, and the run's `drops_channel` covers them (CH-15).
- **When the node acknowledges the newest record of a run that is not the current one,** the agent closes the connection (`run-complete`, CH-10 step 5). The next connection offers the next run. So no record of an older run ever follows a newer run's hello (SL-14).
- **A new run's hello declares what came before it,** in `prior`:
  - `runs_skipped`: the runs between the node's `taken` run and this one, which the node will never receive: this `run_counter` − `taken.run_counter` − 1, with `taken.run_counter` read as 0 when `taken` is absent;
  - `records_lost`: the records of those runs, and of the `taken` run above `taken.seq`, that the agent evicted or discarded without the node's acknowledgement; and, when `taken` is absent, the previous generation's records discarded at enrolment (CH-12).
- The node checks `runs_skipped` (CH-13). It cannot check `records_lost`, which is the sensor's word (AP-36), and it records it in health and status. **D5 builds the health event.**
- *Meets:* SL-14 ("records left from the previous run"), SL-16. *Test:* SL-T9 (a) with an engine restart during the outage, (j), (k); new rows in §15.

### 4.5 Acknowledgement

**CH-17. An `ack` names the node's taken position, and nothing less durable.**

- **Taken position T** of a run: the highest `seq` such that every record of the run at or below T is one of these:
  - committed to the store;
  - saved in the intake hold's checkpoint (`netcheckpoint.intake`, `hold.go`): "held durably by the node's intake hold" (D5);
  - refused or dropped by the node under a counted reason, where D5's decision D5-1 (§13) makes that outcome final;
  - a duplicate (CH-14);
  - a `seq` the node never received, counted in the run's gap (CH-15).
- **The node never acknowledges past a record whose outcome a node crash could undo.** The node saves T durably, with the commit that moves it where there is one, and sends no `ack` above the T it has saved (SL-15, the lesson of C-04 and E-01).
- **At the agent,** an `ack` lets it drop the run's records at or below `seq` from its buffer, and nothing else (SL-19).
- **A record the node received and had not finished when a connection ended** has no outcome. It is sent again on the next connection, from `taken.seq` + 1, and taken then (CH-6: the node finishes or abandons the old connection's records before it sends `node-hello`).
- *Meets:* SL-15. *Test:* SL-T9 (a), (g), and the kill rows of §15.

### 4.6 What the node keeps

**CH-18. For each `sensor_id` and generation, the node keeps:** the highest `run_counter` accepted, its `run_id`, and the taken `seq` in it. It saves the new run's counter and `run_id` before it takes the run's first record (CH-13), and the taken `seq` with each commit that moves it (CH-17). So every check of §4.2 holds across a node restart (SL-14, SL-T9 (g)). **D5 builds this.**

- **D5 decides** whether G and D of CH-15 are kept too. Without them, a node restart forgets the current run's gap count, and an undeclared gap that straddles the restart is not alarmed. D4's view: keep them, because they are two numbers beside the taken position.

## 5. The sensor's buffer (brief item 4)

**CH-19. What the buffer holds, and where.**

- The link agent keeps an append-only buffer on the sensor host's disk, in its own data directory. Each entry is a C13 record exactly as it will be sent: its frame and its bytes. It holds heartbeats and observations only, so it holds redacted frames and allow-listed fields only (SL-22). Ticks and hellos are made when they are sent and are never in it.
- **A record is numbered when it is written to the buffer,** and it is sent from the buffer. It is never sent without being written first.
- **The buffer is synced at least every `buffer_sync_ms` (100 ms).** A crash of the agent or the host loses at most the records written since the last sync. They were numbered under a run that has now ended, and the agent no longer knows them, so no hello can declare them. That is a stated limit (§16), and the run's end is itself visible as a new run.
- **A record the agent cannot write** (a full or failing disk) is never sent. The agent stops, its service manager starts it again, and that begins a new run (CH-12). The loss shows as a new run, not as a silent gap.
- **The agent keeps, beside the buffer and synced with it,** each run's counter, `run_id`, newest `seq` and `drops_channel`, so that it can make a true hello after a restart. It keeps a run's entry until the node has sent an `ack` for a later run, or named one in `node-hello`, so that it can still declare the run's evicted tail in `prior` (CH-16).
- *Meets:* SL-14, SL-15, SL-22.

**CH-20. How much, for how long, and what an overflow counts.**

- **The bound is in bytes:** `buffer_bytes`, 2 GiB by default, configurable from 256 MiB to 64 GiB, a sensor setting that is in the configuration digest (§10.1). The bytes are the frames as stored.
- **It is never bounded by age.** The agent evicts nothing by its own clock (D1's rule for late records: "never dropped by the sensor's clock").
- **When a new record would take the buffer over its bound,** the agent evicts the oldest records first, whatever their run, until it fits. Each evicted record that the node had not acknowledged is counted in its run's `drops_channel` (§7). A record already acknowledged is simply trimmed.
- **Why the oldest.** A buffer that kept the oldest would stop recording at the moment it filled, so whatever happened after that, an attack for example, would never reach the node. Evicting the oldest keeps the newest, which is what the node's current coverage needs, and an attacker who floods to push an event out must keep flooding after it, while `drops_channel` shows the loss either way. The node's coverage gap for the outage is bracketed by its own `sensor.coverage-gap` records (D5's note §1) and by the declared `drops_channel`.
- **How long 2 GiB lasts** is the bytes over the record rate, and no rate has been measured (`desk`, arithmetic, not evidence). A heartbeat is at most about 3 KiB with the 2 KiB coverage statement, so heartbeats alone take at most about 26 MiB a day. An observation without frame bytes is at most about 5 KiB, and a first-sight one at most 64 KiB. At an assumed one observation a second of 5 KiB, 2 GiB lasts about four days. At ten a second, about 11 hours. GT-PCAP's captures are short and are not a station's rate. A station's rate is measured only by H-06's 24 h run on hardware.
- *Meets:* SL-14 (the counter of numbered records evicted, so a gap can be declared), SL-15 ("records that fell out of the buffer are lost, declared and counted").
- *Test:* §15, rows B-1 to B-4.

## 6. Time (brief items 2 and 5)

### 6.1 Clock fields

**CH-21. The sensor host's clock appears in four places.**

| Field | On | What it is |
| --- | --- | --- |
| `made_utc` (new, required in 0.2) | every observation | The sensor's clock when the agent numbered the record and wrote it to the buffer |
| `at_utc` (0.1) | every heartbeat | Unchanged. In 0.2 it is also the heartbeat's made time, because the agent makes and numbers a heartbeat at once |
| `sensor_utc` (new) | `sensor-hello`, `tick` | The sensor's clock when it sent the message |
| capture times (0.1) | `first_utc`, `last_utc`, frame `ts` | Unchanged: the capture timestamps |

- All are RFC 3339 UTC with `Z`, at most nine fractional digits, the form 0.1 already checks (`utcForm`).
- `made_utc` minus `last_utc` is the sensor's own pipeline time for a record: capture to engine to agent. It is reported, and it is not R6.4 (§6.4).
- The node checks no order between these fields, because the sensor's clock may step. It checks the form only (`form`).
- *Meets:* the brief's item 5 ("the sensor host's clock in each record and heartbeat").

### 6.2 The skew check

**CH-22. Measured on live messages only.**

- On each `sensor-hello` and each `tick`, the node takes **offset** = its own wall time when it received the message − the message's `sensor_utc`. A positive offset means that the sensor's clock is behind. The offset includes the one-way network delay, which on a site LAN is far below the bound.
- **Heartbeats and observations are never used for it,** because a buffered one is late by the outage, and the node cannot tell an outage from a skew (CH-8).
- The node raises its skew alarm when |offset| is above `max_skew_ms`. **D5 sets the bound and names the alarm** (P4-4-L3 item 4). D4 proposes 2,000 ms: an order below `tie_grace_s`, 30 s by default, so a sensor within it cannot move a flow out of a session's window, and well above what a LAN time client keeps.
- **While the skew is outside the bound,** the node makes no tie between an observation and one of its own sessions: the flow is judged untied, which alerts, and the alerts are aggregated with the skew alarm naming the cause (SL-17, D5 on #624). Skew never suppresses.
- The node serves no time to the sensor (SL-17). No field of `node-hello` or `ack` carries a time.
- *Meets:* SL-17, SL-29 (the check that does not depend on the time source).

### 6.3 Late records

**CH-23. A late record is stored, flagged and counted, and never dropped by the sensor's clock.**

- **Lateness** of a record = the node's wall time when it received the record − the record's made time (`made_utc`, or a heartbeat's `at_utc`) − the latest offset of CH-22 on this connection.
- **The bound** is `late_bound_s`, 120 s by default, from 30 s to 3,600 s, set on the node. **D4's choice:** a record later than 120 s came through an outage long enough for `sensor-unreachable`, which is raised after 60 s of quiet (D5's note §1), plus a tick. So "late" means "held by an outage the node has already alarmed on", and records of a short stall are not flagged.
- **Past the bound:**
  - an observation is stored as any other, with `node.late: true`, and counted under `late` in status;
  - a heartbeat is taken as any other for its counters, and counted under `late`; its values are history, and the node's live checks (skew, blind) do not use them;
  - the node raises `sensor-records-late` once for each connection that carries one;
  - the detector judges a late observation as it judges any other, by its capture time. An alert from it is never suppressed (SL-17).
- **Never:** a record is not refused, dropped or re-timed for its lateness, and the node never orders, prunes or expires anything by the sensor's clock (SL-17).
- **The bound is not how the node's hold waits for a backlog.** That uses `newest_seq` from the hello (CH-7), by number, so it does not depend on either clock (§13, D5-7).
- *Meets:* SL-17, the brief's item 2 ("a bound on how late a record may arrive, with what the node does past it"). *Test:* §15, rows T-3 and T-4.

### 6.4 R6.4 is not changed

**CH-24.** R6.4's latency stays D6's measure: the alert's time minus the triggering frame's send time, on one host clock under the timed replay (GT-PCAP plan §5, `docs/verification.md`). 0.2 adds `made_utc` and the offset, which let a reader split a latency into the sensor's part and the node's, but neither defines it. On the rig, the sensor's and the node's namespaces share the runner's clock. On two machines, a latency across them needs the offset, and the report says which clock it was measured against (the exit gate's line).

## 7. The wording left from an on-node sensor (brief item 6)

**CH-25. The channel's transport.** 0.1's opening says that under options (a) and (c) the channel is "a local pipe or Unix socket bound to the sensor's account", and D5's note §2 describes the named pipe and `SO_PEERCRED`. Under option (b) (D4-85), the channel is the TLS link of §2, and that text is history. The node's intake still reads any byte stream with C13's framing (`ServeSensor`), so a test can feed it from a pipe. In 0.2 it also writes `node-hello` and `ack`, so it needs a stream in both directions (**D5 builds this**).

**CH-26. The heartbeat's counters on the Linux sensor of SL-3.** Their meaning as 0.1 states it stands; this is what each one counts on the three-process sensor.

| Counter | 0.1's meaning | On the Linux sensor |
| --- | --- | --- |
| `packets`, `bytes` | Not defined in 0.1 beyond the name | The frames the capture stage read from its `AF_PACKET` sockets, before the PRP discard, and the sum of their wire lengths. Equal to the sum of `interfaces[].packets` (§9) |
| `drops_driver` | "what the capture driver reports"; `pktmon`'s lost-event count under (a′) and (c′) | The kernel's count of frames it dropped because the socket's buffer was full: `tp_drops` from `PACKET_STATISTICS`, summed over the capture stage's sockets and accumulated since the run began. **Assumption A1:** that reading `PACKET_STATISTICS` returns `tp_packets` and `tp_drops` and resets them, so the capture stage must add them up. Absent still means unknown, never zero. It does not count frames the NIC or its driver dropped before the socket (§16) |
| `drops_decoder` | "drops in the decoder queue" | Frames the capture stage could not write into the pipe to the engine because the pipe was full: the engine fell behind |
| `drops_channel` | Records lost because the channel did not take them | The numbered records the link agent evicted from its buffer before the node acknowledged them (§5). In 0.1 they were dropped before numbering. In 0.2 they are numbered, so they also show as gaps in `seq`, and that is how the node matches a gap to its declaration (CH-15) |

**CH-27. `interface_check` on Linux.** 0.1 makes it "D5 §7 step 4's binding read", a Windows read of the NIC's protocol bindings. On the Linux sensor host it is the capture stage's read of each monitoring interface, at its start and at each heartbeat. Its three values keep their sense:

- **`ok`** when every monitoring interface has no IPv4 or IPv6 address (link-local included), has ARP off (`IFF_NOARP`), has IPv6 disabled on it, and is not a port of a bridge or a bond; and the host forwards no IP traffic (SL-28).
- **`bound`** when any of these fails: the interface has something that could transmit. `interface-bound` is then in `coverage.degraded`, as in 0.1.
- **`unknown`** when the capture stage cannot read one of them.
- **Not in it:** whether a DHCP or time client runs, which the image's own test shows (SL-T16, SL-T18), and whether the engine's namespace is empty, which SL-T2 shows. C-11's zero-frames test stays the control for all of it.
- **Assumption A3:** that these properties can be read from the kernel by an unprivileged process after `CAP_NET_RAW` is dropped. The C-11 rig's negative control, an interface given an address, must read `bound`.
- *Meets:* SL-26, SL-28. *Test:* §15, row W-2.

**`interfaces[].name`** stays a token (0.1 §2). A Linux interface name outside the token form is renamed in the sensor's configuration, never sent raw.

## 8. PRP (brief item 7)

**CH-28. `prp_window_ms` in the coverage settings.**

- `coverage.settings.prp_window_ms`: the time, on the capture clock, within which a frame with the same source MAC and RCT sequence number as one already seen on the other LAN is a duplicate (0.1 §4.4). Required in 0.2, an integer.
- **Bound:** 400 ms by default, from 10 ms to 2,000 ms. A value outside the bound is refused as `range`.
- **Basis: D4's choice, on an assumption (A4):** that IEC 62439-3 gives its duplicate-discard `EntryForgetTime` as 400 ms. The project holds no copy of IEC 62439-3. The window must cover the difference in delay between the two LANs, and stay well below the time one source takes to wrap its 16-bit RCT sequence number, which at 400 ms is above 160,000 frames a second from one source.
- It is one sensor setting, so it is in the configuration digest (§10.1) and in the alert's flattened coverage (`coverage.settings.prp_window_ms`).
- *Meets:* the brief's item 7.

**CH-29. Two new counters for the discard stage.** Both are heartbeat counters, run totals that never decrease, required in 0.2.

- **`prp_mismatched`:** frames whose source MAC and RCT sequence number match a frame seen on the other LAN within `prp_window_ms`, but whose bytes differ anywhere other than the RCT's LAN ID. **Neither copy is discarded,** so both reach the engine, as D4-69 rules ("discards only a copy that is byte-identical apart from the LAN ID"). A rise is a signal: a frame changed on one LAN, or two senders that share a MAC.
- **`prp_table_full`:** frames passed to the engine without a duplicate check, because the discard stage's table of recent (MAC, sequence number) entries was full. The table is bounded (D4-69, D3). A frame that cannot be checked is passed, never discarded unchecked: a duplicate then doubles a count, which shows, where an unchecked discard could lose a frame, which would not.
- **For D2 and D1:** D4-69's rule compares the whole frame, 802.1Q tag included. If the two LANs' mirror ports tag differently, every duplicate mismatches, `prp_discards` stays flat and `prp_mismatched` rises. That shows in the counters, but it would leave every count doubled. Whether the tag is left out of the comparison needs the sites' switch settings, which the owner has yet to give (D4-86).
- *Meets:* SL-3 (the discard runs in the capture stage), the brief's item 7. *Test:* §15, rows P-1 to P-3.

**CH-30. Two sensor hosts on a PRP network: what C13 would need, as options.** D3's O-12 lists one host with two monitoring ports, two hosts, or one LAN only. With two hosts, no stage sees both copies, so the discard cannot run, and C13 carries nothing that would let the node merge two streams. **This is not a decision:** O-12 is the owner's, and what the node does with several sensors is D5's (P4-4-L3 item 2).

| Option | C13 change | Cost |
| --- | --- | --- |
| (i) One host, two monitoring ports | None. The discard runs in the capture stage | One machine touches both LANs (SL-28, O-12) |
| (ii) Two hosts, two streams, no merge | None. Each sensor reports its LAN (`interfaces[].lan`, `prp.lans_seen` with one LAN), so `duplicates_discarded: false` is not a mismatch (0.1 §4.4). Each stream counts its own LAN once | Each event can alert twice, once per sensor. A frame lost on one LAN shows in that stream only. Two baselines and two detectors, as D5 decides |
| (iii) Two hosts, merged at the node | For each cited frame, its RCT sequence number and a hash with the LAN ID masked, so the node can see that two sensors cite one frame. For flow counts, either the set of RCT sequence numbers of each flow, which is unbounded, or a rule that one LAN's sensor is primary and the other fills its gaps | A merge stage in the node; the two sensors' clocks agreeing within `prp_window_ms`, which is milliseconds and far below any skew bound here; and both backlogs drained before a merge |

**D4's view:** (iii) costs a new merge stage and a dependence on sub-second agreement between two machines' clocks, to turn two alerts into one. Where one host may touch both LANs, (i); otherwise (ii).

## 9. A blind sensor (brief item 8)

**CH-31. Per-interface counts and carrier in every heartbeat.**

```
"interfaces": [ { "name": "<token>", "carrier": "up|down|unknown", "packets": "<decimal from 0>" } ]
```

- Required in 0.2, at most `MaxInterfaces` (8), one entry for each interface in `coverage.interfaces`, by name. A set of names that differs from the coverage statement's is refused as `conflict`. So is a sum of `packets` that differs from `counters.packets`.
- `packets` is the frames the capture stage read from that interface since the run began, before the PRP discard. It never decreases within a run; a decrease is refused as `counter-decrease`, as for every counter (`Follows`).
- `carrier` is the interface's link state. **Assumption A2:** that the kernel reports it to an unprivileged reader. `unknown` when it cannot be read.
- **Why per interface.** A PRP sensor with one port on each LAN whose LAN-B port goes dark still shows a rising total. Only the per-interface count shows the half that is blind.
- **The node's rule is D5's** (`sensor-blind`, P4-4-L3 item 7). D4 proposes: an interface is blind when its `packets` has not risen across the heartbeats of the last `blind_after_s` (60 s by default), or its `carrier` is `down`, using only heartbeats that are not late (CH-23); the sensor is blind when every interface is. **Assumption A7:** that a mirrored station LAN carries periodic traffic, such as GOOSE retransmissions, PTP and the masters' polling, so that a minute with none is a fault or a gap in the mirror. No site's traffic has been seen. A segment that is quiet for longer by design gets a longer bound in the node's configuration.
- **What this cannot see:** a sensor that lies about its counts (AP-36). The node's own-session check (`own-session-unseen`) is the independent one.
- *Meets:* the brief's item 8, SL-20 ("a sensor that is cut, blind or flooding"). *Test:* §15, rows K-1 to K-3.

## 10. What the sensor states about itself

### 10.1 The configuration digest

**CH-32. `coverage.config_digest`.** Required in 0.2: `sha256:` and 64 lowercase hex digits.

- **What it covers.** The agent builds a manifest M at the start of each run: UTF-8 lines, each ended by `\n`, sorted by their bytes, with no duplicate:
  - `program <name> sha256:<hex>` for each of the three programs' executables: `capture`, `engine` and `agent` **[S2: which files make up the engine's executable and its plugins]**;
  - `file <path> sha256:<hex>` for every configuration file any of the three reads at start: the engine's scripts and packages **[S2]**, the allow-list of the engine's output (SL-22) **[S2: its form]**, the redaction configuration, the capture configuration and the agent's configuration. `<path>` is relative to the sensor's configuration root, matches `^[A-Za-z0-9._-]+(/[A-Za-z0-9._-]+)*$`, at most 255 bytes, and has no `..` segment. The agent's key and its enrolment are not in M: they are not configuration, and a renewed enrolment must not read as an edit;
  - `setting <name> <decimal>` for `prp_window_ms`, `sa_reply_timeout_ms`, `max_pending_dnp3`, `flow_idle_s`, `buffer_bytes` and the ring's size in bytes (O-11);
  - `redaction <slot> on|off` for each slot of D4-67 and D4-68, under these closed names: `telnet-password`, `ftp-pass`, `snmp-community`, `http-basic`, `http-cookie`, `http-set-cookie`, `http-form-body`. A server's echo of a slot is part of its slot.
- `config_digest` is `sha256:` and the hex SHA-256 of M.
- **It is constant within a run,** because each program reads its configuration only at its start, and any start begins a new run (CH-12). A record whose `config_digest` differs from that of the run's first record taken is refused as `conflict`, and counted.
- **A site build has no `off`.** The site's capture stage refuses at start a configuration that names the switch (SL-22, D1's ruling on #624). So `redaction <slot> off` appears only in a test build, and the digest of a test build differs from a site build's in that line and in the `program` lines.
- **The agent shows M at its console,** so that a person can compare the digest the node shows with the files on the sensor.
- **The node's expected digest is D5's to source** (§13, D5-4). A digest other than the expected one raises `sensor-coverage-mismatch`.
- **What it shows, and what it does not.** It is the sensor's own word, like the rest of the coverage statement (AP-36). It shows an edit made through the sensor's own programs, such as a redaction slot switched off or an allow-list widened. It does not show a compromise, because a compromised agent can state any digest.
- *Meets:* SL-19 ("a local edit that switches redaction off then shows at the node"), SL-22. *Test:* SL-T12's digest leg; §15, rows G-1 to G-3.

### 10.2 How the sensor's end was pinned

**CH-33. `pinned_by` in `sensor-hello`.** Closed: `signature` when the agent verified the enrolment's admin signature (SL-5 step 6), `console` when an installer typed the node's pin at the sensor's console (SL-5's fallback).

- Another value closes the connection (`hello`).
- The node keeps the first value it accepts for each generation. A different value later in the same generation closes the connection (`binding`), because the way the end was pinned changes only with a new enrolment.
- The node shows it in status, so a deployment pinned by hand is never mistaken for one pinned by signature (SL-5). Whether a node may refuse `console` is D5's and D1's to decide (§13, D5-5).
- *Meets:* SL-5. *Test:* §15, row G-4.

### 10.3 The allow-list's count

**CH-34. `engine_lines_refused`,** a heartbeat counter, a run total that never decreases, required in 0.2: the lines the link agent took from the engine and refused, because they came from a stream that is not on the allow-list or failed the agent's strict parse. A refused line is wiped, and is never buffered or sent (SL-22). A field that is not on the list is not taken, and is not counted, because the line it came in is still used.

- **[S2]** What a "line" is depends on the engine's output form: one log line, or one JSON object.
- *Meets:* SL-22 ("refuses and wipes any stream that is not listed"), and it is what SL-T15's allow-list control can watch at the node. *Test:* §15, row G-5.

## 11. The 0.1 reader, and every new field

**CH-35. Every change bumps the minor and keeps a 0.1 reader.**

Alert: two unknown details, accepted because the alert's schema is a later minor (`AlertFromHealth`) | Absent: not known. A 0.1 observation's coverage stays valid |
| `node.late` | Stored observation | Ignored | Absent: not late |

## 14. Clauses the engine's result could change [S2]

E-D4-03 (P4-4-S2, PR #625) has not run. These clauses depend on what the engine is and what it writes:

1. **The manifest's `program` and `file` lines** (CH-32): which files make up the engine and its packages (Zeek with ICSNPP, or Suricata with its rules), and so what a digest covers.
2. **The allow-list's form and its count** (CH-32, CH-34): what a line of the engine's output is, which streams and fields are listed, and whether any listed field can hold a secret (SL-22; D3's assumption that E-D4-03 decides).
3. **`made_utc` − `last_utc`** (CH-21): the engine's own delay before it writes a line. **Assumption A6:** that Zeek writes a connection's record when the connection ends unless a script writes one at its start. Whether an engine can give a `flow` `start` and a first sight at the first packet is what E-D4-03 shows. This changes no field, but it changes what R6.4 will measure.
4. **What feeds `decoder_errors` and `sessions_unparsed`:** the engine's own statistics, whose names and meanings depend on the engine.
5. **`drops_decoder`** (CH-26) assumes that the engine reads its input from the capture stage through a pipe, under SL-3. E-D4-03 shows whether the engine reads a pipe offline under `unshare -n`.

Nothing in §2 to §6, §8 or §9 depends on the engine.

## 16. Not in 0.2, assumptions and limits

**Not in 0.2:**

- A count of frames the NIC or its driver dropped before the packet socket (the interface's own receive counters). `drops_driver` does not include them (CH-26). A candidate for a later minor.
- The "MAC changed within a flow" signal (D4-73's candidate list). Not asked by the brief.
- HSR, which stays `not-decoded`.
- A merge of two PRP sensors' streams (CH-30, option (iii)).
- Any time, setting or command from the node to the sensor (SL-17, SL-19).

**Assumptions,** each `unknown` until what is named settles it:

| | Assumption | Settled by |
| --- | --- | --- |
| A1 | `PACKET_STATISTICS` returns `tp_packets` and `tp_drops` and resets them on read (CH-26) | Reading packet(7), and W-1 on the rig |
| A2 | The interface's carrier can be read by an unprivileged process (CH-31) | K-3 on the rig |
| A3 | An interface's addresses, ARP flag, IPv6 state and bridge membership can be read by an unprivileged process (CH-27) | W-2 and C-11's negative control |
| A4 | IEC 62439-3 gives `EntryForgetTime` as 400 ms (CH-28) | The standard's text, which the project does not hold; the inter-LAN delay in a site's PRP capture, if the owner authorizes one |
| A5 | The sensor host's file system keeps what was synced across a power cut (CH-12, CH-19) | An H-row on the sensor host |
| A6 | Zeek writes a connection's record at its end unless a script writes one at its start (§14) | E-D4-03 |
| A7 | A mirrored station LAN carries periodic traffic, so a minute with none on a port is a fault (CH-31) | A site's traffic, which needs the owner's authorization; until then `blind_after_s` is a setting, not a fact |

**Limits:**

- **Everything is `desk`, and nothing is built.** No row of §15 has run.
- **A compromised sensor can still lie** in every field it states: counts, `drops_channel`, `prior`, `config_digest`, `pinned_by` and every observation (AP-34 (b), AP-36). 0.2 makes a lie by another sensor, a replay, a copy and an undeclared loss visible. It does not make a sensor honest.
- **A crash of the agent or its host** loses the records written since the last sync, at most `buffer_sync_ms`, with no declaration (CH-19). The crash itself shows as a new run.
- **How long the buffer lasts** is not known, because no station's record rate has been measured (CH-20).
- **On two machines,** a latency across the sensor and the node rests on the measured offset, which includes the network delay (CH-22, CH-24).
