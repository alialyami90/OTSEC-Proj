# C5 0.8: four document series for item 3, one more removable series, and the floor terms (P4-3-C5)

C5, 2026-11-05. This is a proposal for `otsec.store/0.8`, deliverable 1 of brief P4-3-C5 (`docs/agent-handoffs.md`, item 3 implementation briefs, D4-53). It takes the list "What C5 0.8 would need" from the approved node note, `docs/phase4/C5-asset-node.md`. Nothing here is built yet. Every result it promises will be `simulated` or `desk`.

The store's part and the node's part are kept apart below, as in 0.7. The store can enforce only what it can see: class, holds, commit order and a document's series. The node enforces the rest.

**Two places where this proposal departs from the note's wording** are set out for C1's ruling (Questions 1 and 2). The note asked for holds on sets and identity records. This proposal adds none, because none of the three evidence series can be removed at all. The note's floor counted two sets. This proposal keeps that floor, and it also keeps every installed set, as D4-20 keeps superseded baselines.

## 1. The series (`DocumentInfo`'s closed table)

0.8 adds four series to the pairing that `DocumentInfo.Validate` enforces:

| Kind | Series | Document | Stream | Validator |
| --- | --- | --- | --- | --- |
| `evidence` | `identity` | the node's identity record, `otsec.identity/0.1` | `config/<asset>` | the node's |
| `evidence` | `finding` | a C12 finding, `otsec.finding/0.1` | `config/<asset>` | C12's `Validate`, in the bytes the node hashed |
| `evidence` | `advisory.set` | a C11 envelope, `otsec.advisory/0.1`, signature included | `advisory` | C11's strict decode, bounded at `MaxEnvelopeBytes` |
| `working-state` | `identity.read` | the node's latest-read record, `otsec.identityread/0.1` | `config/<asset>` | the node's |

The five 0.7 pairs are unchanged. With nine series in all, `Validate` passes the nine pairs and refuses every other pair of kind and series, as it does today.

**Why `identity.read` is working state.** It holds only an invocation ID and a time (C12's `identity.latest_read`). It is not in the audit chain, and its value is copied into every finding that relies on it, so the finding is what keeps it as evidence. It is the same kind of record as a checkpoint: only the newest one matters, and an older one is useless once a newer one has committed.

**The two node documents.** Both are defined in `platform/node`, as `otsec.eventcheckpoint/0.1` is. Their schemas are written as the first field, so the readers that skip by schema prefix (`storedBaselines`, `checkpoints`) skip them.
- **`otsec.identity/0.1`** holds the asset ID, the C1 0.3 attributes with their sources, the first-read invocation ID and time, and the hash of the asset's previous identity record, if any. Its capture holds the bytes the attributes' spans cover. The validator decodes it strictly. It checks that each attribute's bytes lie inside the capture, and that the whole record, document and capture together, is at most `MaxIdentityRecordBytes`, 64 KiB (Question 3).
- **`otsec.identityread/0.1`** holds the asset ID, an invocation ID and a time. It has no capture and is at most 4 KiB.

**The validator cannot see the stream**, as 0.7 already says. The node's writer puts each series only on its own stream, and a node test checks this. Each document names its asset, and the set names no asset.

## 2. What can be removed

`RemovableSeries` gains one series, `identity.read`. It becomes `config.snapshot`, `eventcheckpoint.learner`, `eventcheckpoint.detector` and `identity.read`.

- **The store's rule is unchanged.** `RemoveConfig` refuses the newest record of the series in the stream, a held record, and a record of any other series.
- **The node's rule.** After each `identity.read` commits, the node removes the asset's older `identity.read` records in one step. So the stream keeps one of them, and two for the moment between the commit and the removal. A removal writes no C8 record, as for a checkpoint (D4-32), because the record is not in the audit chain. A removal that fails raises the alarm once and is retried after the next commit. Removals are counted in status, as checkpoint removals are.
- **`identity`, `finding` and `advisory.set` are not removable**, as `config.difference` and `baseline.event` are not. They are evidence of a change, and D4-20's ruling applies to them unchanged: nothing removes them by time or space, and a release is the D4-20 rule 4 export and release, which is not built. Their growth is bounded by events that each raise an alarm or need a signature:
  - a new identity record only on a changed value, which raises `identity-changed`;
  - a new finding revision only on a C12 §7 change, which needs a set replacement, an identity change, or a configuration change retrieved, and each of those is signed or alarmed. The revision itself raises `finding-changed`;
  - a new set only on a signed install.

## 3. Holds

**0.8 adds no hold code** (Question 1). A hold exists to stop a removal. Since the store refuses every removal of `identity`, `finding` and `advisory.set` by series, a hold on them would add holds-table rows and a start-up reconcile path that change nothing. It would also need a C8 record as its `Ref`, and no C8 0.11 record names a finding.

If a later version makes one of these series removable, that version adds the hold codes in the same change. That is the guard the note asked for: a set and the identity records named by a finding that is the newest for its (asset, advisory) stay stored.

## 4. The `advisory` stream

- **Node layout only.** It is a node-level stream in the configuration database, of class `configuration`, and it exists only when `applicability` is on. `Layout.Validate` already allows it: one class, one database. The stream's name is the node's layout, not a contract matter.
- **The class rules for it** are the configuration class's: the record cap, strict validation, no forwarding, and `stop-collecting` at the quota. The class text in `class.go` is extended to name identity records, latest-read records, findings and advisory sets. No `StreamClass`, `FullAction` or quota rule changes.

## 5. The quota floor terms (node, `platform/node/layout.go`)

The floor stays a check that catches a quota too small to work. It is not a sizing recommendation (D4-20 rule 5). 0.8's terms are added to today's floor:

| Term | Per | Bytes |
| --- | --- | --- |
| The newest identity record, one change, and two `identity.read` | asset with `asset` on | 2 × 64 KiB + 2 × 4 KiB = 136 KiB |
| Findings | asset with `applicability` on | 1 × `ConfigRecordBytes` (1.5 MiB) |
| Two sets: the one in use and the one being installed | node with `applicability` on | 2 × `ConfigRecordBytes` (3 MiB), since `MaxEnvelopeBytes` is below the record cap (C11 §1.4) |

- **The findings term is a fixed allowance**, because the number of findings depends on the set, which is not known at load. C12 bounds the counts in a finding but not its bytes. 1.5 MiB holds several hundred findings of a few KiB each. A set with many entries naming an asset's product can need more, and the quota is the owner's to size.
- **Sets are kept, so each install adds up to 1.4 MB** (Question 2). An SEL-only set is estimated at about 100 KB (C11 §1.4, estimate only, no set measured). So the sets term holds two sets at the bound, and a third fills the class unless other terms have room. At the estimated size, it holds about thirty.
- **When the class is full,** the store stops the class's writes, as today (`store-quota-reached`, D4-19). That stops configuration reads, identity records, findings and set installs together. A set that cannot be stored is not installed, and the set in use stays in use. The file stays in `admin_dir`, and the alarm says why.

The load error names each term and the count behind it, as the D4-20 and event-baseline terms do (B3 on #319).

## 6. Compatibility

- **The store format stays `otsec.platform-store/2`.** There are no new columns, no index and no migration. `doc_kind` and `doc_series` hold the new names.
- **A 0.7 binary on a 0.8 store:**
  - It opens the store.
  - It removes no `identity.read`, because its `RemovableSeries` refuses that series. The records stay until 0.8 returns. At about 200 bytes each (an estimate) and one read a minute, that is about 300 KB per asset per day.
  - Its readers of `config/<asset>` either skip the new documents or pass over them. `storedBaselines` and `checkpoints` skip anything without their schema prefix. `locate` and `locateAll` match by digest, and a digest is unique to its bytes. C6's cross-version test pins this.
  - It has no asset module or R9, so it writes none of the four series.
- **A 0.8 binary on a 0.7 store:** nothing to migrate. The four series simply have no records yet.
- **The release note.** A rollback below 0.8 loses nothing stored. While rolled back, no identity record, finding or set is written, and status has no `identity` or `applicability` lines. When 0.8 returns, its start evaluates every asset under the newest installed set that verifies (the note §3).

## 7. Tests

- **`contracts/store`:**
  - `DocumentInfo` over every kind and series pair: the nine in sections 1 and 0.7 pass, and every other pair is refused, including `working-state` with `identity`, `finding` or `advisory.set`, and `evidence` with `identity.read`;
  - `RemovableSeries` is exactly the four series;
  - `CheckRemoveConfig` takes `identity.read` and still refuses `identity`, `finding` and `advisory.set`.
- **`platform/store`:**
  - `RemoveConfig` refuses the newest `identity.read`, and removes an older one;
  - it refuses a record of each of the three evidence series, even unheld and not the newest.
- **`platform/node`** (in the node PR):
  - `ConfigDocuments` classifies each new document into its series, and refuses an identity record over 64 KiB, a capture that does not cover an attribute's span, a finding that fails C12's `Validate`, and an envelope over `MaxEnvelopeBytes`;
  - each series is written only on its own stream;
  - one `identity.read` stays after each run, and a failed removal is retried;
  - the floor terms, each refused at one byte below;
  - a set install that does not fit the quota leaves the set in use and the file in place.
- **C6's contract tests and the cross-version case** in section 6.

## Questions

1. **C1: no hold codes in 0.8 (section 3).** Is "not removable by series" enough, with the holds added by whichever later version makes these series removable? The note said the set and identity records "stay held while a finding that is the newest for its (asset, advisory) names them". This proposal meets that by never removing them.
2. **C1, and C3 for retention: are installed sets kept for good (section 5)?** The other choice is to make `advisory.set` removable once a newer set is in use and every asset has been evaluated under it. The chain's `advisory.set_installed` keeps each removed set's digest, so a finding still names it, but the set's bytes would be gone. I propose keeping them, for the same reason D4-20 keeps superseded baselines: each install is a signature that only people make, and a realistic set is small.
3. **C2: is 64 KiB enough for one identity record?** It is the document plus the bytes its spans cover: on the SEL-751, the FID, CID and serial number; on an SEL-2731 or SEL-2741, the C3 0.4 operations' values, including `sysDescr` (at most 255 octets) and the engine ID. If any one value can be larger, tell me the bound.
4. **C4: a finding whose advisory is no longer in the set.** Under a newer set, does the node write a revision for it, and in which class? Section 2's bound assumes such a finding is revised once, or not at all. It must not be revised at every evaluation.
