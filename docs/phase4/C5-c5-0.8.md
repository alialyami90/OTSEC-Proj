# C5 0.8: four document series for item 3, one more removable series, and the floor terms (P4-3-C5)

C5, 2026-11-05. This is a proposal for `otsec.store/0.8`, deliverable 1 of brief P4-3-C5 (`docs/agent-handoffs.md`, item 3 implementation briefs, D4-53). It takes the list "What C5 0.8 would need" from the approved node note, `docs/phase4/C5-asset-node.md`. Nothing here is built yet. Every result it promises will be `simulated` or `desk`.

The store's part and the node's part are kept apart below, as in 0.7. The store can enforce only what it can see: class, holds, commit order and a document's series. The node enforces the rest.

**Two places where this proposal departs from the note's wording** are set out for C1's ruling (Questions 1 and 2). The note asked for holds on sets and identity records. This proposal adds none, because none of the three evidence series can be removed at all. The note's floor counted two sets. This proposal keeps that floor, and it also keeps every installed set, as D4-20 keeps superseded baselines.

## 1. The series (`DocumentInfo`'s closed table)

0.8 adds four series to the pairing that `DocumentInfo.Validate` enforces:

| Kind | Series | Document | Stream | Validator |
| --- | --- | --- | --- | --- |
| `evidence` | `identity` | the node's identity record, `otsec.identity/0.1` | `config/<asset>` | the node's |
| `evidence` | `finding` | a C12 finding, `otsec.finding/0.1` | `config/<asset>` | C12's `Validate`, in the bytes the node hashed |
| `evidence` | `advisory.set` | a C11 envelope, `otsec.advisory/0.1`, signature included | `advisory` | C11's strict decode, bounded at `MaxEnvelopeBytes` |
| `working-state` | `identity.read` | the node's latest-read record, `otsec.identityread/0.1` | `config/<asset>` | the node's |

The five 0.7 pairs are unchanged. With nine series in all, `Validate` passes the nine pairs and refuses every other pair of kind and series, as it does today.

**Why `identity.read` is working state.** It holds only an invocation ID and a time (C12's `identity.latest_read`). It is not in the audit chain, and its value is copied into every finding that relies on it, so the finding is what keeps it as evidence. It is the same kind of record as a checkpoint: only the newest one matters, and an older one is useless once a newer one has committed.

**The two node documents.** Both are defined in `platform/node`, as `otsec.eventcheckpoint/0.1` is. Their schemas are written as the first field, so the readers that skip by schema prefix (`storedBaselines`, `checkpoints`) skip them.
- **`otsec.identity/0.1`** holds the asset ID, the C1 0.3 attributes with their sources, the first-read invocation ID and time, and the hash of the asset's previous identity record, if any. Its capture holds the bytes the attributes' spans cover. The validator decodes it strictly. It checks that each attribute's bytes lie inside the capture, and that the whole record, document and capture together, is at most `MaxIdentityRecordBytes`, 64 KiB (Question 3, answered).
- **`otsec.identityread/0.1`** holds the asset ID, an invocation ID and a time. It has no capture and is at most 4 KiB.

**The validator cannot see the stream**, as 0.7 already says. The node's writer puts each series only on its own stream, and a node test checks this. Each document names its asset, and the set names no asset.

## 2. What can be removed

`RemovableSeries` gains one series, `identity.read`. It becomes `config.snapshot`, `eventcheckpoint.learner`, `eventcheckpoint.detector` and `identity.read`.

- **The store's rule is unchanged.** `RemoveConfig` refuses the newest record of the series in the stream, a held record, and a record of any other series.
- **The node's rule.** After each `identity.read` commits, the node removes the asset's older `identity.read` records in one step. So the stream keeps one of them, and two for the moment between the commit and the removal. A removal writes no C8 record, as for a checkpoint (D4-32), because the record is not in the audit chain. A removal that fails raises the alarm once and is retried after the next commit. Removals are counted in status, as checkpoint removals are.
- **`identity`, `finding` and `advisory.set` are not removable**, as `config.difference` and `baseline.event` are not. They are evidence of a change, and D4-20's ruling applies to them unchanged: nothing removes them by time or space, and a release is the D4-20 rule 4 export and release, which is not built. They grow only on events that each raise an alarm or need a signature. An alarm reports growth but does not bound it (C6 on #444), so the item 3 ceiling in section 5 is what bounds them:
  - a new identity record only on a changed value, which raises `identity-changed`;
  - a new finding revision only on a C12 §7 change, which needs a set replacement, an identity change, or a configuration change retrieved, and each of those is signed or alarmed. The revision itself raises `finding-changed`;
  - a new set only on a signed install.

  Because the set is a §7 field, each install revises once every finding whose advisory is still in the set, so findings grow by about findings × installs per asset (C4). A finding whose advisory has left the set is never revised again (Question 4).

## 3. Holds

**0.8 adds no hold code** (Question 1). A hold exists to stop a removal. Since the store refuses every removal of `identity`, `finding` and `advisory.set` by series, a hold on them would add holds-table rows and a start-up reconcile path that change nothing. It would also need a C8 record as its `Ref`, and no C8 0.11 record names a finding.

If a later version makes one of these series removable, that version adds the hold codes in the same change. That is the guard the note asked for: a set and the identity records named by a finding that is the newest for its (asset, advisory) stay stored.

## 4. The `advisory` stream

- **Node layout only.** It is a node-level stream in the configuration database, of class `configuration`, and it exists only when `applicability` is on. `Layout.Validate` already allows it: one class, one database. The stream's name is the node's layout, not a contract matter.
- **The class rules for it** are the configuration class's: the record cap, strict validation, no forwarding, and `stop-collecting` at the quota. The class text in `class.go` is extended to name identity records, latest-read records, findings and advisory sets. No `StreamClass`, `FullAction` or quota rule changes.

## 5. The quota floor terms (node, `platform/node/layout.go`)

The floor stays a check that catches a quota too small to work. It is not a sizing recommendation (D4-20 rule 5). 0.8's terms are added to today's floor:

| Term | Per | Bytes |
| --- | --- | --- |
| The newest identity record, one change, and two `identity.read` | asset with `asset` on | 2 × 64 KiB + 2 × 4 KiB = 136 KiB |
| Findings | asset with `applicability` on | 1 × `ConfigRecordBytes` (1.5 MiB) |
| Two sets: the one in use and the one being installed | node with `applicability` on | 2 × `ConfigRecordBytes` (3 MiB), since `MaxEnvelopeBytes` is below the record cap (C11 §1.4) |

- **The findings term is a fixed allowance**, because the number of findings depends on the set, which is not known at load. C12 bounds the counts in a finding but not its bytes. 1.5 MiB holds several hundred findings of a few KiB each. A set with many entries naming an asset's product can need more, and the quota is the owner's to size.
- **Sets are kept, so each install adds up to 1.4 MB** (Question 2). An SEL-only set is estimated at about 100 KB (C11 §1.4, estimate only, no set measured). So the sets term holds two sets at the bound. At the estimated size, it holds about thirty.
- **The item 3 ceiling** (C6's FAIL on #444, C1's ruling there). An optional module must never stop configuration monitoring, least of all on input an on-path sender can drive, such as an identity that changes on every run. So the configuration class has a ceiling for the item 3 series: the quota less the configuration module's own floor terms (the D4-20 term for each asset whose configuration is read, and the event-baseline terms). It does not include 0.8's terms.
  - **What it refuses.** The node refuses every write of `identity`, `identity.read`, `finding` and `advisory.set` that would leave the class holding more than the ceiling. That covers writes made with `asset` alone as well as with `applicability`.
  - **What still runs.** Configuration snapshots, differences, baselines and checkpoints keep their path up to the full quota, unchanged. Removing an older `identity.read` still runs, since it frees room.
  - **When it trips.** The node raises `asset-store-full` once per crossing, and clears it when the class falls back below the ceiling, so the next crossing raises it again (C6). One name covers both modules. The matcher pauses. Each refused write is counted by series and shown in status, so nothing is lost silently (P5). When room returns, the next collection run's evaluation catches up, as the restart rule in D4-53 does.
  - **What it never does.** It never removes evidence, never displaces a configuration record, and never stops a configuration read.
  - **Why the floor still holds.** The quota floor is today's terms plus 0.8's, so the ceiling always leaves at least 0.8's terms for item 3.
- **A set install past the ceiling is refused** (C3's condition and C1's ruling on #444). Before it commits a set, the node checks that the class would stay at or below the ceiling after the set. If it would not, the set is not installed. The set in use stays in use, and the file stays in `admin_dir`.
  - **The alarm.** The node raises `advisory-set-no-room` once per file hash, as `advisory-set-refused` is raised, so a file left in place does not re-raise it at every tick. The health line carries the file's SHA-256, the set's ID and version (checked by C11 step 4), the bytes needed and the bytes free (C3).
  - **No audit record.** This is a storage refusal, not one of C11's §1.5 refusals, so no `advisory.set_refused` is written.
- **The floor counts every stored set.** At start, the node compares the configuration quota with the floor plus every stored set beyond the two the floor already counts, each at its stored size. If the quota is below that, the node raises `advisory-sets-over-floor` with both figures. It does not refuse to start, because a node that will not start stops SER collection too, and AP-29 keeps the advisory path apart from collection.
- **When the class is full anyway,** from configuration records up to the full quota, the store stops the class's writes, as today (`store-quota-reached`, D4-19). That stops configuration reads, identity records, findings and set installs together. It does not stop SER collection: the adapter-evidence class has its own quota, and the scheduler checks only that one before a run (`cannotKeep`). An identity or `identity.read` commit that fails raises its alarm, and the SER run's own records still commit.

The load error names each term and the count behind it, as the D4-20 and event-baseline terms do (B3 on #319).

## 6. Compatibility

- **The store format stays `otsec.platform-store/2`.** There are no new columns, no index and no migration. `doc_kind` and `doc_series` hold the new names.
- **A 0.7 binary on a 0.8 store:**
  - It opens the store.
  - It removes no `identity.read`, because its `RemovableSeries` refuses that series. It also writes none, having no asset module. So the one or two `identity.read` records per asset that 0.8 left behind stay as they are, and nothing grows while rolled back (C6's correction on #444).
  - Its readers of `config/<asset>` either skip the new documents or pass over them. `storedBaselines` and `checkpoints` skip anything without their schema prefix. `locate` and `locateAll` match by digest, and a digest is unique to its bytes. C6's cross-version test pins this.
  - It has no asset module or R9, so it writes none of the four series.
- **A 0.8 binary on a 0.7 store:** nothing to migrate. The four series simply have no records yet.
- **The release note.** A rollback below 0.8 loses nothing stored. While rolled back, no identity record, finding or set is written, and status has no `identity` or `applicability` lines. When 0.8 returns, its start evaluates every asset under the newest installed set that verifies (the note §3).

- **`contracts/store`:**

- **`platform/store`:**
  - `RemoveConfig` refuses the newest `identity.read`, and removes an older one;
  - it refuses a record of each of the three evidence series, even unheld and not the newest.
- **`platform/node`** (in the node PR):
  - `ConfigDocuments` classifies each new document into its series, and refuses an identity record over 64 KiB, a capture that does not cover an attribute's span, a finding that fails C12's `Validate`, and an envelope over `MaxEnvelopeBytes`;
  - each series is written only on its own stream;
  - one `identity.read` stays after each run, and a failed removal is retried;
  - the floor terms, each refused at one byte below;
  - the ceiling (C6's test, C1's ruling): an identity that changes on every run fills the class to the ceiling, then `asset-store-full` is raised once, the matcher pauses and the refusals are counted by series, and configuration reads, stores and differences continue for every asset up to the full quota;
  - a set install past the ceiling is refused with `advisory-set-no-room`, raised once per file hash and carrying the file's SHA-256 and the set's ID and version. The set in use and the file stay where they are, and no `advisory.set_refused` is written;
  - when room returns, the next run's evaluation catches up;
  - stored sets beyond the floor raise `advisory-sets-over-floor` at start, and the node still starts;
  - with the configuration class full, an SER run still commits its records, and the identity commit's alarm is raised.

## Questions

1. **Ruled by C1 on #444: no new hold codes.** `identity`, `finding` and `advisory.set` are never removable, which is the stronger rule, and satisfies the note's "stay held". A later minor that makes any of them removable adds the hold in the same minor.
2. **Ruled by C1 on #444: installed sets are kept for good, for item 3** (D4-20). C3 accepts under its condition, which section 5 meets: the floor counts every stored set, and an install past the ceiling is refused with a health line. A retention rule can be sized once the owner says how often sets are published (HR-18). C3's alternative, keeping a set while a finding names it, keeps every set anyway, since findings are never removed.
3. **Answered by C2: 64 KiB is enough.** C1 caps every attribute value at `MaxValueBytes` (256 bytes), and a span covers exactly its value. An identity holds at most five values: on the SEL-751, `firmware_id`, `model`, `firmware_version`, `sel.cid` and `serial_number`; on the SEL-2731/2741, `firmware_id`, `model`, `firmware_version`, `hostname` and `snmp_engine_id`. The model and firmware version spans lie inside the FID's. So the captured bytes are under 1.3 KiB, and the rest of the 64 KiB is for the document's sources and read paths. `sysDescr` is not an attribute; it is only searched for the FID.
4. **Answered by C4: a finding whose advisory has left the set gets no revision.** The matcher produces output only for entries in the set in use, so the node has nothing to compare and writes nothing, at every evaluation. The last stored finding stays as evidence and names its set. Status counts only findings whose advisory is in the set in use. If the advisory returns, the first evaluation records one revision. C4 also notes that each install revises once every finding whose entry is still in the set, so growth is about findings × installs per asset, bounded because each install is signed (section 2). A per-finding byte cap in C12 0.2 is not needed for the floor, which is a fixed allowance.
