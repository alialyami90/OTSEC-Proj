# C5 0.4 proposal: configuration snapshots, held records, and unknown senders (P4-A5)

Owner: B5. Date: 2026-10-27. Status: **proposal, for review.** B1 approves it. B4, B2, B3 and B6 review it as consumers, and B6 writes the contract tests before the code merges. Every number here is `desk` (Linux, modernc SQLite) unless it says otherwise.

C5 0.4 is one minor that carries everything Phase 4 needs from the store, so that two C5 minors are never open at once (A1 on #209, P4-A5):

1. a **configuration** stream class for C9 snapshots and C10 baselines, with a per-record cap;
2. **held records**, which pruning never removes while the node holds them: the acknowledged baseline, and any snapshot with an unacknowledged difference;
3. HR-11's **`syslog-unknown`** class, the absolute bound on what unknown senders can store;
4. the **faster unknown count**, which follows from 3 with no contract change of its own.

The scope was agreed in the project threads with B4 (items 3 and 4, and how C10 is stored) and B2 (transcript retention, D4-8) on 2026-10-27.

## 1. The configuration class

- **`ClassConfiguration` (`"configuration"`)**, with the full action `StopCollecting`. At its quota, configuration reads stop, and the store raises `store-quota-warning` first, at the class's `WarnFraction`. A configuration record never displaces an event, because a class only ever uses its own quota.
- **Its own database.** A configuration class sits in a database with no event class (a new `Layout` rule, like audit's). So a full configuration store cannot stop event collection, and an event flood cannot stop configuration reads.
- **`Record.Event` holds a typed document, not a C4 event.** This applies to a C9 snapshot (`otsec.config/…`) and a C10 baseline (`otsec.baseline/…`). The writer gives the `Log` a validator for the class, as audit does with C8's `ValidatePending`, so C5 imports neither C9 nor C10. The store keeps the document's bytes exactly, with no seq written in. C10 hashes those stored bytes with SHA-256 for `node.baseline_ack` (D4-4 item 5), and C9 does the same.
- **The transcript is the record's `Capture`.** It is one `config.read` session's native bytes. The snapshot names it by `sha256:<hex>` and points into it by section span and SHA-256, with no second copy of the bytes (D4-8). The snapshot and its capture commit together, and the existing rule prunes the capture once no retained record refers to it.
- **`Quota.MaxRecordBytes`** (new; 0 means no cap, and the configuration class requires a value above 0). A record whose event plus capture exceeds it is refused before it is queued, with `CodeTooLarge`. The node keeps the read's bytes in quarantine, so there is never a partial snapshot (C9). The default is **512 KiB**, B2's estimate of a full SEL-751 read (24 `SHO` forms, about 150 to 250 KB of transcript). It is a parameter, and is later derived from register revision 5's counted per-form byte caps.

### The recovery reserve must cover one capped commit

One commit cannot checkpoint partway, so its whole WAL growth must fit in the reserve. Measured (one record, `wal_autocheckpoint=0` after a `TRUNCATE` checkpoint, 4 KiB pages):

| Capture | WAL written | Ratio |
| --- | --- | --- |
| 128 KiB | 164,832 B | 1.26 |
| 256 KiB | 296,672 B | 1.13 |
| 512 KiB | 560,352 B | 1.07 |
| 768 KiB | 824,032 B | 1.05 |

A 512 KiB commit (560 KB of WAL) already exceeds `WALBoundBytes` (512 KiB). With today's 1 MiB recovery reserve, it would leave about half the reserve for everything else.

**New rule** (`Params.Validate`, given the layout): `RecoveryReserveBytes` ≥ 2 × (WAL bound + 1.25 × the largest `MaxRecordBytes` in the layout). The 1.25 covers the measured ratio with margin. At 512 KiB that is about 2.3 MiB. The reserve is a preallocated file on the store's volume, so the extra space costs little, and the cap need not shrink to fit the old reserve.

## 2. Held records

- **`Holder`** (new interface, implemented by the store):
  - `Hold(ctx, stream, seq, reason)` and `Release(ctx, stream, seq)` are each committed at `SyncFull`;
  - `Held(ctx, stream)` lists the holds.
  
  A hold is kept in the database beside the record, so it survives a restart without the node having to rebuild it first.
- **Pruning skips held seqs.** `PruneStep` deletes the oldest at most `max` events at or below the boundary that are **not held**. A held record keeps its capture by the existing rule (a capture goes only when no retained record refers to it), so a held snapshot keeps its transcript (B2).
- **Allowed classes.** Only configuration-class streams take holds. A hold on any other class is refused, so a hold can never pin events or audit.
- **What the node holds** (P4-A5, not C5):
  - the acknowledged baseline of each asset, configuration and event;
  - every snapshot whose difference from the baseline is not yet approved or acknowledged.
  
  The node releases a hold only after the C8 record that ends it has committed (audit before act).
- **A full class with holds.** If held records fill the configuration quota, configuration reads stop with the alarm, as for any full class. The class never evicts a held record, and the node never releases a hold to make room.

## 3. The `syslog-unknown` class (HR-11)

- **`ClassSyslogUnknown` (`"syslog-unknown"`)**, with the full action `DropAndCount` for every transport, TCP and TLS included. A full class therefore never refuses a connection that also carries a known sender. At the quota, the store raises **`syslog-unknown-full`** (health type `store.syslog-unknown-full`); unknown senders' messages are dropped and counted. A known sender's messages keep storing in its listener's class.
- **The bound is the stored bytes in the class**, so it does not depend on any clock. Neither a forward or backward clock step nor a restart refills it. This is the absolute bound HR-11 asks for, and A3's condition before any `device-observed` listener.
- **Layout (node, P4-A5):** each listener gets a second stream, `syslog-unknown/<listener>`, in the listener's database, where every `asset-unresolved` record goes. A stream keeps one class for life, so known and unknown records cannot share a stream. Forwarding treats it as another stream of the listener's database.

## 4. The faster unknown count

- `UnknownSpent` and the per-window budget stay as they are in 0.4 (B4). They are the per-listener share, and this minor removes no behaviour.
- At start the node counts only the `syslog-unknown/<listener>` stream. The count's cost is then bounded by that class's quota, not by the whole listener stream, which is what made it slow.
- #196's rule is kept: an unknown sender is charged as it is read and counted by received time, never by commit time (#178).
- A later minor may drop the window count if B6 agrees the class quota is enough on its own.

## Compatibility and rollback

- **The 0.3 reader.** A 0.3 store opens unchanged under 0.4. The new classes and the holds table appear only when a layout declares them, and nothing in a 0.3 database changes meaning.
- **Rolling back to a 0.3 node** after a 0.4 node has run. The 0.3 node refuses a layout that names an unknown class, so it does not start (fail closed). An operator who rolls back removes the configuration database and the `syslog-unknown/*` streams from the layout, after exporting them if needed. The release note says so.
- **`Identifier`** becomes `otsec.store/0.4`.

## Tests

**Contract tests (B6, independent, before merge):**
- a configuration record over `MaxRecordBytes` is refused and nothing is stored;
- a layout that mixes configuration with an event class is refused;
- a reserve below the new bound is refused;
- `PruneStep` never removes a held seq at any step size, and removes the rest in order;
- a held record keeps its capture;
- a hold outside the configuration class is refused;
- holds survive a kill at each commit point;
- `syslog-unknown` at its quota drops and counts while a known sender's stream keeps storing;
- the class bound holds across a restart and across forward and backward clock steps.

**The store's own tests** cover the same cases on SQLite, plus the WAL measurement above as a regression bound.

## Open points for reviewers

1. **B2:** is 512 KiB the right default until revision 5's counted caps exist?
2. **B4:** with the class quota as the absolute bound, is `syslog-unknown-full` (once per fill, cleared when below `WarnFraction`) the health signal you want beside `syslog.unknown-budget`?
3. **B3:** holds are written by the node, which is the trust boundary. A compromised node could hold or release records. It could already discard its own store (#181's principle), so a hold adds no new power. What matters is that the C8 record of the acknowledgement or approval is the authority, and a hold only follows it. Is that enough?
4. **B6:** which of the tests above do you want as contract tests in `tests/contract`, and which in the store package?
