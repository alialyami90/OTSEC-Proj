# C5 0.4 proposal: configuration snapshots, held records, and unknown senders (P4-A5)

Owner: B5. Date: 2026-10-27. Status: **proposal, revised after B2's, B3's, B4's and B6's reviews.** B1 approves it. B4, B2, B3 and B6 review it as consumers, and B6 writes the contract tests before the code merges. Every number here is `desk` (Linux, modernc SQLite) unless it says otherwise.

C5 0.4 is one minor that carries everything Phase 4 needs from the store, so that two C5 minors are never open at once (A1 on #209, P4-A5):

1. a **configuration** stream class for C9 snapshots and C10 baselines, with a per-record cap;
2. **held records**, which pruning never removes while the node holds them: the acknowledged baseline, and any snapshot with an unacknowledged difference;
3. HR-11's **`syslog-unknown`** class, the absolute bound on what unknown senders can store;
4. the **faster unknown count**, which follows from 3 with no contract change of its own.

The scope was agreed in the project threads with B4 (items 3 and 4, and how C10 is stored) and B2 (transcript retention, D4-8) on 2026-10-27.

## 1. The configuration class

- **`ClassConfiguration` (`"configuration"`)**, with the full action `StopCollecting`. At its quota, configuration reads stop, and the store raises `store-quota-warning` first, at the class's `WarnFraction`. A configuration record never displaces an event, because a class only ever uses its own quota.
- **Its own database.** A configuration class sits in a database with no event class (a new `Layout` rule, like audit's). So a full configuration store cannot stop event collection, and an event flood cannot stop configuration reads.
- **`Record.Event` holds a typed document, not a C4 event.** This applies to a C9 snapshot (`otsec.config/…`) and a C10 baseline (`otsec.baseline/…`). The writer gives the `Log` a validator for the class, as audit does with C8's `ValidatePending`, so C5 imports neither C9 nor C10. The store keeps the document's bytes exactly, with no seq written in. C10 hashes those stored bytes with SHA-256 for `node.baseline_ack` (D4-4 item 5), and C9 does the same.
- **The transcript is the record's `Capture`.** It is one `config.read` session's native bytes. The snapshot names it by `sha256:<hex>` and points into it by section span and SHA-256, with no second copy of the bytes (D4-8). The snapshot and its capture commit together, and the existing rule prunes the capture once no retained record refers to it.
- **`Quota.MaxRecordBytes`** (new; 0 means no cap, and the configuration class requires a value above 0). A record whose event plus capture exceeds it is refused before it is queued, with a new code, `CodeRecordTooLarge` (`"record-too-large"`). The node keeps the read's bytes in quarantine, so there is never a partial snapshot (C9). The default is **512 KiB**, B2's estimate of a full SEL-751 read (24 `SHO` forms, about 150 to 250 KB of transcript). It is a parameter, and is later derived from register revision 5's counted per-form byte caps.

- **What the class stores** (B2 on #246):
  - a C9 **snapshot** (`otsec.config/…`, kind `config.snapshot`) with its transcript as the capture;
  - a C9 **difference** (kind `config.difference`), with no capture. It names its two snapshots by digest, so C8 0.5's `difference_digest` can be checked later against the stored bytes;
  - a C10 **baseline** document, with no capture.
- **The validator sees the capture.** The configuration class's validator is `func(event []byte, capture *Capture) error`, not audit's event-only form. The node's validator refuses a snapshot whose `transcript.sha256` is not the record's `Capture.SHA256`, so a snapshot can never commit beside a capture it was not read from (B2). Before the append, the node runs C9's `DecodeSnapshot` and `Snapshot.CheckAgainst` on the transcript, as it runs C2's `CheckLines` today. C5 still imports no C9.
- **One record per commit.** A configuration-class commit holds exactly one record, plus the holds that record takes (section 2). The `Log` flushes each configuration record as its own group and refuses an `AppendBatch` of more than one. So the largest commit is one capped record (B6).
- **The smallest cap** `Validate` accepts is `MinRecordBytes`, 64 KiB, so the reserve rule below is tested down to a value that exists.

### The recovery reserve must cover the largest commit

**Why the reserve is twice the WAL bound** (my reading of ADR-0004 and E-A5-3, which measured it on small commits). A store found full at start may have frames left in its WAL that were never checkpointed. Startup releases the reserve, then opens and recovers. The space then needed is:
1. the checkpoint of what the WAL held at the crash, which can extend the database file by as much as those frames (at most `WALBoundBytes` when every commit is small); and
2. recovery's own commits (prune steps, compaction), each small, so their WAL stays within `WALBoundBytes`.

The 2× is one of each. A commit larger than the autocheckpoint threshold can leave more than the bound in the WAL, so term 1 grows with the largest commit.

**The WAL a commit writes** is a fixed cost plus about its payload. One record, `wal_autocheckpoint=0`, after a `TRUNCATE` checkpoint, 4 KiB pages. B6 measured independently with SQLite through Python, on a different schema (simulated, Linux):

| Capture | WAL (B5, modernc) | WAL (B6, sqlite3) |
| --- | --- | --- |
| 128 KiB | 164,832 B | 152,472 B |
| 256 KiB | 296,672 B | 284,312 B |
| 512 KiB | 560,352 B | 547,992 B |
| 768 KiB | 824,032 B | 811,672 B |

The fixed part is 21 to 34 KB and the slope is about 1.0. So a ratio rule fails at small caps: 1.25 is already short at 128 KiB (B6). The rule is payload plus a constant:

- `W(C) = 1.1 × C + 64 KiB`, the WAL a commit of C payload bytes may write.
- **New rule** (`Params.Validate`, per database): `RecoveryReserveBytes ≥ 2 × WALBoundBytes + W(C)`, where C is the largest commit the database's `Log` can make.

For the configuration database, C is `MaxRecordBytes`, because one record goes per commit. At 512 KiB the reserve is 1 MiB + 627 KiB, about **1.6 MiB**. The store's regression test measures W at every cap from `MinRecordBytes` up to 1 MiB and fails if a measured commit exceeds W(C).

**The reserve is per database, not per volume** (B6's cross-database question). Each database has its own reserve file in the store directory (`<db>.reserve-recovery`, `platform/store/env.go`). The node starts its databases one at a time (`Runtime.startDB`), and each releases only its own reserve, recovers, and re-creates it before the next starts. While the node runs, no reserve is released: a commit that does not fit on the volume fails with `SQLITE_FULL` and is not stored. So a configuration commit and an event batch can grow their WALs at the same time only out of the volume's free space, never out of a reserve. Each database's reserve covers only its own recovery. (I told B2 earlier that the reserve was per volume. That was wrong, and this section replaces it.)

### A finding the rule exposes: event databases' commits are not small

Under the same rule, today's event databases are short. Their reserve is `2 × WALBoundBytes` (1 MiB, `platform/node/runtime.go`), which leaves no room for W(C). But their largest commit is not small:
- a stream listener's batch is `HeldBatchBytes`, 4.25 MiB;
- a `Log` group of `Append`s is up to `MaxEvents` (100) records;
- a datagram listener's batch is up to its `Queue` (1024) datagrams, from up to `MaxQueueBytes` (8 MiB) of raw datagrams.

This is desk inference: I have not shown that recovery wedges. Raising every event database's reserve to the largest commit would mean tens of MiB for a datagram listener. I propose instead:
- **`GroupOptions.MaxCommitBytes`** (new): the `Log` closes a group before it would pass this many payload bytes, and refuses an `AppendBatch` larger than it with `CodeRecordTooLarge`;
- the node sets 1 MiB for event databases, and `MaxRecordBytes` for the configuration database;
- the reserve rule then uses `C = MaxCommitBytes` for every database (about 2.2 MiB for an event database).

The receivers must then split their batches at the cap. That is in `modules/telemetry/receive` (B4), where `writeDatagrams` and the stream writer already split by count. An SER read is one atomic `AppendBatch`, so its largest read must fit the cap. B2 confirms that bound, or B1 sets the adapter-evidence cap higher.

B6's `storekill` test at a full volume, with a commit at the cap left un-checkpointed, is the evidence for both the rule and the finding. **B1 decides** whether `MaxCommitBytes` goes in 0.4 or whether 0.4 carries only the configuration rule and the event databases follow.

## 2. Held records

- **`Holder`** (new interface, implemented by the store):
  - `Hold(ctx, stream, seq, reason)` and `Release(ctx, stream, seq)` each commit at `SyncFull`;
  - `Held(ctx, stream)` lists the holds, each with its reason and the bytes it keeps (event plus any capture that only held records refer to).

  A hold is kept in the database beside the record, so it survives a restart.
- **A hold taken with its record** (B3, point 2). `Record.Holds` (new, configuration class only) lists holds that commit in the same transaction as the record: on the record itself, or on earlier records of the same database. No prune step can then fall between a snapshot with a difference and its hold. Separate `Hold` calls remain for a hold whose reason comes later, such as an acknowledgement.
- **A reason names its record, not free text** (B3, point 3). `HoldReason` is `{Code, Ref}`:
  - `Code` is from a closed set: `baseline` or `unapproved-difference`.
  - `Ref` is the C8 record that justifies the hold, by its audit stream and seq. For `baseline`, that is the accepted `node.baseline_ack` (it also carries `collector_seq`). For `unapproved-difference`, it is `config.change_detected`.

  The node commits that C8 record first, which is audit before act: the change record already names the digests. Then it appends the snapshot and its difference with their holds. A crash between the two leaves an audit record with no held snapshot, and the start-up reconcile raises it.
- **A held difference holds both snapshots it names** (B2). The node lists both seqs in the difference's `Record.Holds`. The store does not read the documents, so it is the node that names the seqs.
- **Pruning skips held seqs.** `PruneStep` deletes the oldest at most `max` events at or below the boundary that are **not held**. The boundary may pass a held seq; the held record stays, and later unheld seqs are pruned in order around it. A held record still counts in its class's used bytes. It keeps its capture by the existing rule (a capture goes only when no retained record refers to it), so a held snapshot keeps its transcript (B2).
- **Allowed classes.** Only configuration-class streams take holds. A hold on any other class is refused, so a hold can never pin events or audit.
- **What the node holds** (P4-A5, not C5): the acknowledged baseline of each asset (configuration and event), and every snapshot whose difference is not yet approved or acknowledged, with that difference. The node releases a hold only after the C8 record that ends it has committed.
- **The holds table is derived state** (B3, point 1; node, P4-A5). At start the node rebuilds the holds it should have from the C8 records:
  - the latest accepted `node.baseline_ack` per asset and kind, whose digest matches the held bytes;
  - every `config.change_detected` with no covering approval or acknowledgement.

  It compares that set with `Held`. It releases a hold the records do not justify and adds one that is missing, and either case raises an alarm naming the stream and seq: a crash between audit and act, or tampering. The node never decides "this is the baseline" from the holds table.
- **A full class with holds.** If held records fill the configuration quota, configuration reads stop with the alarm, as for any full class. The class never evicts a held record, and the node never releases a hold to make room. Configuration streams are one per asset (`config/<asset-id>`), so the full alarm's detail names the three streams holding the most bytes. An operator then sees one asset churning rather than only a full store (B3, point 4). There is no per-asset quota in 0.4.

## 3. The `syslog-unknown` class (HR-11)

- **`ClassSyslogUnknown` (`"syslog-unknown"`)**, with the full action `DropAndCount` for every transport, TCP and TLS included. A full class therefore never refuses a connection that also carries a known sender. At the quota, the store raises **`syslog-unknown-full`** (health type `store.syslog-unknown-full`); unknown senders' messages are dropped and counted. A known sender's messages keep storing in its listener's class.
- **The bound is the stored bytes in the class**, so it does not depend on any clock. Neither a forward or backward clock step nor a restart refills it. This is the absolute bound HR-11 asks for, and A3's condition before any `device-observed` listener (B3 confirms on #246).
- **"Absolute" means stored at once, not received over time.** Pruning a forwarded unknown record frees its bytes again. It bounds what unknown senders can hold on the volume (HR-11's storage-exhaustion concern), not a lifetime total (B6).
- **Layout (node, P4-A5):** each listener gets a second stream, `syslog-unknown/<listener>`, in the listener's database, where every `asset-unresolved` record goes. A stream keeps one class for life, so known and unknown records cannot share a stream. Forwarding treats it as another stream of the listener's database.
- **The quota is per class per database** (B4). Listeners that share a database share one `syslog-unknown` quota, so one listener's unknown flood can fill the others' share. It is still bounded, and known senders are unaffected.
- **The alarms** (B4). At `WarnFraction` the store raises `store-quota-warning` for this class, as for the others. At the quota it raises `syslog-unknown-full` once per fill and clears it below `WarnFraction`. The detail names the `syslog-unknown/<listener>` streams holding the most bytes, so the operator knows which listener filled it. The class drops new records and does not prune, so a flood early in an outage keeps the first arrivals. The receiver's drop count and the per-address alarm still show the later senders.
- **The per-address unknown-sender alarm stays on `platform/health`**, outside the class, so a full class never silences it (B4).
- **One listener's records are no longer in one seq order** (B4, B6). Known and unknown records of a listener interleave upstream in forwarding order, not receive order. Received time is the only order across the two streams, so forwarding and any consumer that rebuilds a listener's timeline merge by `received.utc`.
- **The receiver side is B4's**, after 0.4 merges. The datagram writer splits a mixed batch into two `AppendBatch` calls. A stream connection from an unknown sender writes only to the unknown stream, and at the class quota it drops and counts (`unknown-full`) instead of holding the connection. A known sender's connection never waits on the unknown stream.
- **Which PR lands the layout.** The store's 0.4 code PR adds the classes. A separate node PR then moves `asset-unresolved` records to `syslog-unknown/<listener>`. B6's `test_slice_unknown_restart_e2e.py` changes in that same PR window, and B5 tells B6 when it is up.

## 4. The faster unknown count

- `UnknownSpent` and the per-window budget stay as they are in 0.4 (B4). They are the per-listener share, and this minor removes no behaviour.
- At start the node counts only the `syslog-unknown/<listener>` stream. The count's cost is then bounded by that class's quota, not by the whole listener stream, which is what made it slow.
- #196's rule is kept: an unknown sender is charged as it is read and counted by received time, never by commit time (#178).
- **Known limit: the first 0.4 start refills the window once** (B4). After a 0.3 run, the last window's unknown records are in the listener stream, not the new one, so counting only the new stream gives each listener a fresh window budget on that one start. The class quota still bounds what is stored, so the refill cannot exceed the absolute bound. Counting both streams on that start would bring back the slow scan for every start whose unknown stream is empty.
- A later minor may drop the window count if B6 agrees the class quota is enough on its own.

## Compatibility and rollback

- **The 0.3 reader.** A 0.3 store opens unchanged under 0.4. The new classes and the holds table appear only when a layout declares them, and nothing in a 0.3 database changes meaning.
- **Rolling back to a 0.3 node** after a 0.4 node has run. The 0.3 node refuses a layout that names an unknown class, so it does not start (fail closed). An operator who rolls back removes the configuration database and the `syslog-unknown/*` streams from the layout, after exporting them if needed. The release note says so.
- **The release note also says that rolling back loses the holds**, so after the export the acknowledged baselines exist only in the exported copy (B3).
- **`Identifier`** becomes `otsec.store/0.4`.

## Tests

**Contract tests (B6, independent, written against this text before the code merges):**
- `tests/contract/c5_v04_test.go`, against the C5 interfaces with `platform/store` as the implementation:
  - `MaxRecordBytes` refusal with nothing stored;
  - a mixed layout refused;
  - a reserve below the new bound refused, including at `MinRecordBytes`;
  - `PruneStep` around holds at step sizes 1, 2, 7 and 1000;
  - a held record keeps its capture, and a capture shared with an unheld record survives that record's prune;
  - a hold outside the configuration class refused;
  - a `Record.Holds` hold present from the record's own commit;
  - `syslog-unknown` at its quota drops and counts while a known stream stores;
  - the 0.3 reader opening a 0.3 store unchanged.
- `tests/integration/storekill/`, a child killed with SIGKILL, and `taskkill /F` on the hosted runner:
  - holds survive a kill at each commit point, including between the C8 record and the held append;
  - the class bound holds across a restart and across forward and backward clock steps;
  - recovery at a full volume with a commit at the cap left un-checkpointed (section 1).

**The store's own tests** cover the same cases on SQLite, plus the measured W(C) at every cap from `MinRecordBytes` to 1 MiB as a regression bound.
