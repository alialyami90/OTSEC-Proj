# C4 `otsec.event/0.4`: what C13 0.2 requires of `sensor.counters` (P4-4-L6)

D4, 2026-11-13. This is the C4 0.4 proposal that brief P4-4-L6 asks of D4 (`docs/agent-handoffs.md`, "After D4-90"; D4-90; D5's B6 on #634, comment 6835767712). It is Markdown only. D1 approves it together with C13 0.2 (`docs/phase4/D4-c13-0.2-proposal.md`), the node's design, C7 0.11 and C8 0.13. The code in `contracts/event` changes only after that approval, under the third part's brief.

**Nothing here is built.** Every clause is a requirement. Evidence class: `desk`, read on `main` at `e20a594f`. The size figures of §4 are an **unreproduced estimate**: they come from a throwaway test run once on the owner's PC against `contracts/syslog` at `e20a594f`, which was deleted and never committed, so it cannot be re-run and carries none of the evidence classes (`desk`, `simulated`, `CI-Linux`, `CI-Windows`). E4-6 pins them in CI when the code lands (D1's ruling of 2026-11-13 on #645).

## 1. Why a minor is needed

C4 0.3, an approved contract, accepts in a `sensor.counters` health event only `reported_by`, `sensor_id`, `run_id` and `diff.<name>` for the 13 names of `SensorCounters` (`contracts/event/event.go`). Any other detail of an event stamped 0.3 is refused (`checkSensorCounters`, `contracts/event/validate.go`: "not a detail of sensor.counters in 0.3").

C13 0.2 requires `sensor.counters` to carry the rises of eight heartbeat counters that 0.3 does not name, and to mark a capture loss (C13 0.2, CH-26, CH-29, CH-45; ruling 5 on #634). A node built to C13 0.2 would therefore write an event that C4 0.3 refuses, and the event that carries a declared loss's durable trace would be lost (D5's B6 on #634).

## 2. What 0.4 changes, and nothing else

**The identifier** becomes `otsec.event/0.4`. D1's brief limits the minor's rules to `sensor.counters` (D4-90: "what C13 0.2 requires of `sensor.counters` (its counters, and the detail that marks a capture loss) and nothing else"). The identifier itself is stamped on every event the node writes, because the code has one constant for all of them (§3); no rule of any other event type changes.

**C4-0.4-1. Eight more counters.** In an event of minor 0.4 or later, `diff.<name>` is also accepted for these names, C13 0.2's new heartbeat counters:

| Name | C13 0.2 clause | What it counts |
| --- | --- | --- |
| `drops_holder` | CH-26 | Frames the socket holder could not write into the first pipe. A capture loss |
| `frames_overlong` | CH-26 | Frames longer than the holder's buffer, not passed. A capture loss |
| `frames_outgoing` | CH-26 | Frames sent on a monitoring interface; its alarm is `sensor-transmitted` |
| `prp_mismatched` | CH-29 | Frames that met a PRP duplicate's keys and differed |
| `prp_table_full` | CH-29 | Frames passed without a duplicate check |
| `prp_tag_differs` | CH-29 | Discarded duplicates whose 802.1Q tag differed |
| `prp_wrong_lan` | CH-29 | Frames whose RCT LAN ID is not the interface's |
| `engine_lines_refused` | CH-34 | Engine output lines refused by the agent's allow-list |

The same rules as 0.3 apply to each: a decimal difference since the sensor's previous report, `^(0|[1-9][0-9]{0,19})$` and at most 2^64 − 1; never a total, so a detail named for a counter without `diff.`, or with `total.`, is refused. In an event stamped 0.3, the eight names stay refused as 0.3 refuses them.

**C4-0.4-2. `capture_loss`.** A detail, present exactly when the event's `diff.drops_driver`, `diff.drops_holder` or `diff.frames_overlong` is above 0. Its value lists those of the three names whose difference is above 0, space-separated, in that order. Any other value is refused (`enum`), and so is the detail when none of the three rose, or its absence when one did (`missing`).
- *Why a detail, and why these three:* a capture loss is a frame the sensor never passed to the engine, so nothing about it can reach the node. Ruling 5 on #634 (comment 6805936000) names `frames_overlong` a capture loss in CH-45 beside `drops_holder`. **`drops_driver`, the kernel's own drop count, is in the set by D1's ruling of 2026-11-13 on #645:** more loss counted fails closed, and D5 confirmed the reading; the node's design (#644 §1.8) is to name it too. One detail names all three, so a reader upstream, who sees no status, can find a capture loss without knowing the counters' meanings.
- *Not a capture loss:* `drops_decoder` (frames that reached the frame stage and that the engine fell behind on) and `drops_channel` (records numbered and evicted, which C13 0.2 declares with their spans). Both keep their 0.3 meaning.

**C4-0.4-3. `diff.packets` is required in 0.4.** Every 0.4 `sensor.counters` event carries `diff.packets`, as `0` when no frame was read.
- *Why:* a 0.3 reader accepts an unknown detail of a later minor (`later` in `checkSensorCounters`), but it still refuses an event with no `diff.<name>` of its own 13 ("no diff.<counter>", `contracts/event/validate.go` l.340 on `main`; D5 read the same on #645). An event that carried only, say, `diff.frames_outgoing` would be refused by a node rolled back to 0.3 code, and by an upstream 0.3 validator. With `diff.packets` always present, a 0.3 reader reads every 0.4 event. So **0.4 needs no reader floor.**
- *Why this is within "nothing else":* no C13 clause requires `diff.packets`. It is required here only because a 0.3 reader must be able to accept every 0.4 `sensor.counters` event, which the minor's own compatibility needs (`contracts/README.md`: a reader of an earlier minor reads a later one). It changes no meaning: `diff.packets` keeps its 0.3 meaning, and `0` is a value 0.3 already accepts. Without it, C4-0.4-1 would make a 0.4 event that a 0.3 reader refuses, and 0.4 would need a reader floor instead.

**Unchanged:** `reported_by`, `sensor_id`, `run_id`; the 13 names of 0.3 and their meaning; `HealthSensorCounters`; every other event type and detail. **Not added, though asked about:**
- **The link agent's counts** (`agent.closes.*`, `taken_ahead`, `sync_late`, `entries_unreadable`, C13 0.2 CH-43) are not in `sensor.counters`. C13 0.2 changes CH-43 so that their rises are shown in status only. §4 gives the reason.
- **`sensor.coverage-gap`'s details** (`cause`, `causes`, `state`, `covered`, `merged`, `from_bound`, `clock_stepped`) and **`sensor.run-loss`'s run identity** need no C4 change: those types have no closed detail set in 0.3, and C4 accepts their details as free keys (`contracts/event/validate.go`; D5 on #644 §1.11). `time.node-stepped` is already a 0.3 type (`contracts/event/event.go`), and the node's design adds a writer of it, not a change.

## 3. Readers and writers

| | Reads a 0.3 `sensor.counters` | Reads a 0.4 `sensor.counters` |
| --- | --- | --- |
| C4 0.3 code (`main`) | Yes | Yes: the new details are accepted from a later minor, and `diff.packets` satisfies its one required counter (C4-0.4-3) |
| C4 0.4 code | Yes: none of the 0.4 details is required at 0.3 | Yes, with C4-0.4-1 to C4-0.4-3 checked |

- **The writer** of `sensor.counters` is the node (#644 §1.9 item 5).
- **What the code will stamp: every event, of every type, 0.4** (D1's ruling on D5's N4, comment 6839936385 on #645). `event.Identifier` (`contracts/event/event.go` l.15) is one constant, stamped by every producer on `main`: `modules/telemetry/normalize/ser.go` l.477 and l.519, `modules/telemetry/normalize/syslog.go` l.152, `platform/node/runtime.go` l.521 and `platform/sensorlink/link.go` l.357. The store reads its own minor from the same constant (`eventVersion`, `platform/store/commit.go` l.332) and refuses a pending event of a later minor (`assignSeq`, l.353). So 0.4 changes `Identifier` to `otsec.event/0.4`, and `self` in `contracts/event/validate.go` (l.75) to minor 4, and every event the node writes from then on says 0.4. A separate constant for `sensor.counters` alone was weighed and is not proposed: the store's check would then have to read the higher constant, so the binary would carry two minors of one contract for no reader's gain.
  - *What that means for readers:* nothing changes in meaning. An event of any other type stamped 0.4 is checked as before, and a 0.3 reader reads it with `strictjson.Forward` (`contracts/event/decode.go`), which ignores what a later minor adds. Forwarded Syslog carries the new identifier.
  - **The rollback consequence, for D7's floors.** A node rolled back from 0.4 code to 0.3 code reads every stored 0.4 event (above, and §3's table), so stored data sets no floor. Its store refuses any **pending** event stamped 0.4 (`commit.go` l.353). On `main` no pending event outlives the process that built it: the link's hold keeps observations and builds the event at commit (`HeldRecord`, `platform/sensorlink/link.go` l.342–357), and SER and Syslog events are built by the node at commit time. **So a rollback loses nothing as long as that stays true.** The node's design must keep it true for what it adds: a pool event held in `sensorrun.json` (C13 CH-45) is held as its counts and built at its write, never held as built event bytes, or a rolled-back binary refuses it and the held event is lost. D5 to confirm on #644. The same holds between two binaries: a collector or a second node writing pending events into this store would need a floor, and none does on `main` (`cmd/otsec-collector` stamps no C4 event).
  - *Test:* E4-7.
- **Syslog** (C6) renders details as they are, one `hd` parameter each (`contracts/syslog/render.go`). No C6 change.

## 4. Size

The node builds each sensor event to render in at most 2,048 octets, a default Syslog target's limit (`syslog.DefaultMaxOctets`; #644 §1.9 item 5), with up to 4,096 bytes stored.

The worst 0.4 event was built with every difference at 2^64 − 1 (20 digits), the 21 counters of 0.3 and 0.4, `capture_loss` naming all three, a 63-character node ID, a lowercase UUID for the sensor and the run, and the default target of `TestSensorDropEventFits` (`platform/node/sensor_test.go`). It was rendered with `contracts/syslog`'s own assembly at `e20a594f`, in a throwaway test run once on the owner's PC and then deleted. **What follows is an unreproduced estimate,** not evidence of any class: the test is not committed and cannot be re-run, and E4-6 pins the figures in CI when the code lands:

| Event | Details | Octets | Fits 2,048? |
| --- | --- | --- | --- |
| 0.4, without the agent's counts | 25 | **1,569** | Yes, with 479 to spare |
| 0.4, with the agent's 14 counts as `diff.agent.<name>` | 39 | **2,316** | No: `Render` refuses it as too large, and drops no detail to fit |

So the agent's counts stay out of `sensor.counters` (§2). C4-0.4-3's reason rests on reading `validate.go`, not on that run; E4-3 and E4-4 test it.

**Owed, with the code:** the node's size test for `sensor.counters` at its worst case, beside `TestSensorDropEventFits` (D5's, #644 §1.9 item 5), and C4's own tests below.

## 6. Limits

- The figures of §4 are an unreproduced estimate from one local run of the render, not CI and not committed. E4-6 pins them when the code lands.
- A rollback loses no event only while no pending event outlives the process that built it (§3). That is true on `main`, and the node's design must keep it true for its held pool events.
- A capture loss is the sensor's own word (AP-36), like every counter.
- `sensor.counters` is under the pool's caps (C13 0.2 CH-45): a rise can be merged into a later event, never dropped.
