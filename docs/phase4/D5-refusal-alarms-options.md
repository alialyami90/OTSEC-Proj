## 1. What `main` does today

- **A refused stored observation.** `observeTo` calls `observationOf` (`event.Decode`, then `ObservationFromEvent`, which calls `DecodeStored`). On any error it passes `nil` to `Detector.Observe`, which refuses it and still takes its seq. `Observe` also refuses a decoded record of another sensor or with no readable `first_utc`. Each refusal adds 1 to `DetectorStatus.Refused` (`observations_refused`), in process memory only. No alarm is raised, no reason is kept, and nothing is written to the health stream. `Through` moves past the record, and the next checkpoint lets the stream be pruned past it.
- **No reason is classifiable yet.** `DecodeStored` returns plain `*netobs.Error` values. `netobs.ErrLaterMinor` does not exist on `main`; it comes with (b)'s code (condition 2). `ObservationFromEvent` can return a decoded observation together with a `conflict` error; `observeTo` drops it to `nil`.
- **A refused baseline cannot happen yet.** `detectorConfig` sets no `DetectorConfig.Baseline`, so `NewDetector` takes the no-baseline branch.
- **`network-detector-not-restored` repeats.** While `r.detector` is nil, `tickSensor` calls `startDetector` at every tick. When the restore fails, `startDetector` raises not-restored through `Status.Raise` before it tries `NewDetector`. If anything after that fails, the start fails and the next tick raises not-restored again. `Status.add` does not deduplicate, so each repeat takes a slot of the `MaxStatusAlarms` (200) ring. The text "starts again from the oldest retained observation" is false whenever the fresh start then fails. `tickSensor` raises `network-detector-not-started` once per down stretch (`detectorDown`).
- **A transient store read fails the restore (a live defect on `main`, D6's F4 on #766).** `alertsAfter` returns a failed `db.Read` of the alert stream as an error, and `startDetector` treats it as a restore failure: it raises not-restored and starts fresh. That fresh start's first checkpoint lets `saveDetectorCursor` remove the restorable checkpoint, and every retained observation is replayed with no committed alert held back, so the alerts already committed for them are stored a second time. A failed `detectorCheckpoints` read, by contrast, fails the start, and the next tick tries again. Section 4 fixes it; D1 may record it as an open item until then.
- **Node alarms write no health event.** `Status.Alarm` and `Status.Raise` write the status file and the OS log only. Health events come from the store's own alarms (`storeAlarm`, as `store.<code>`) and from the writers that call `health` or `sensorHealth`.
- **The ceiling drop.** The observation stream is pruned only through consumer cursors; `netretain` prunes the alert stream only. When the detector is off its cursor holds, the class fills, and at its quota the store refuses new observations with `CodeQuotaReached`. The link then drops them under `class-full`, counted by reason and asset, written as `intake.drop-counted` by `reportDrops`, and the store raises `network-full` once per fill (#602, D4-76). D3's third condition therefore needs no new code, only a test that shows it with the detector held off (section 6, T9).

## 2. `network-observation-refused`

### 2.1 Reasons

The reason is taken from the first refusal on the record's path, in this order:

| Reason | Where | How the node tells it |
|---|---|---|
| `later-minor` | `observationOf` | `errors.Is(err, netobs.ErrLaterMinor)` (exists only once (b)'s code has merged), for a later C4 stamp on the envelope or a later C13 stamp on the stored observation; the node tells the two apart by the error's `Field`, `schema` for C4 and `netobs.schema` for C13, as #765's section 2 (b) states them, never by `Detail` |
| `later-minor` | `observationOf`, `event.Decode` | a later-C4 `network-observation` event that `Validate` refuses inside `event.Decode` (a new `binding.method`, the body moved out of `netobs`): under D4's option 1 on #765 (D5's F1 there), (b)'s code also runs the later-C4 check on the event `Decode` returns with a `Validate` error, and a later stamp refuses it with `ErrLaterMinor` (`Field: "schema"`) ahead of the `Validate` error |
| `malformed` | `observationOf` | any other error: `event.Decode`, `ObservationFromEvent`'s kind or conflict check, or `DecodeStored` |
| `detector-refused` | `Detector.Observe` | `observationOf` succeeded and `Observe` returned an error |

**Where `Code` and `Field` come from (a dependency on (b)'s code).** On `main` the split by `Field` does not exist: `DecodeStored`'s errors carry fields relative to the body, so a later C13 stamp would fail as `Field: "schema"`, the same value as the C4 envelope's, and `validateStored` returns a join, so `errors.As` can hand the node a sibling's `Field` (D4's F1 on #766). D4 owes two things in (b)'s code: `ObservationFromEvent` prefixes the body's `Field` with `netobs.`, and a later-minor refusal is returned alone, not joined. The node depends on both, and T1's legs are the check that the split holds. The node then reads:

- **`later-minor`:** `Code` and `Field` from the typed error that `errors.Is(err, netobs.ErrLaterMinor)` matched, found by walking the error tree, never from a sibling of a join.
- **`malformed`:** the error is a `*event.Error` or a `*netobs.Error`, possibly a join; the node takes `Code` and `Field` from the first typed one in the tree. An untyped error carries neither, and both are shown as `-`.
- **`detector-refused`:** `Observe`'s errors are untyped `fmt` errors, so they carry no `Code` or `Field`. The node picks the alarm's wording by comparing `o.SensorID` with its own sensor ("another sensor's"), else "no readable time", and never parses the error string.
- **A map key is not node-held (D3's F4 on #766).** `netobs` fields are node-held paths (`record`, `baseline`, `checkpoint`; `refuseNulls` runs on keys strict decoding has already read), but C4's validator builds `health.details.<k>` from the record's own map keys. A `Field` that names a map key is cut to the map's name (`health.details`) before it reaches the alarm or the event.

A record whose seq is at or below `Through` is not a refusal (`Observe` returns nothing). The counts are kept on `observeTo`'s path only: `rebuildFrameIndex` reads records at or below `Through`, which were judged or refused before the restart, so its skip of a refused record is not counted again; an alert that cites a skipped first sight's frames counts them under `frames_missing`, as now (D5's 7010817086 on #765).

**What the detail may carry.** A `netobs.Error`'s `Detail` can quote values from the record, and the alarm goes to the OS log, which never holds device or packet text (`Status.Raise`'s rule). So the alarm and the health event carry the reason, the error's `Code` and `Field`, and seq numbers, never `Detail` or the error string.

### 2.2 When it is raised (a real choice)

"Once per run" cannot mean the sensor's `run_id`: a refused record did not decode, so its run is unknown. So "run" here is the node's process run.

- **R1. Once per process run and reason.** An in-memory set of the reasons raised, as `tickSensor` keeps for `sensor-record-refused` (`in.refused`). Every later refusal of that reason only raises the counts. A restart raises it again at the first new refusal. At most three raises per process.
- **R2. Once per stretch.** Raised at the first refusal of a reason, cleared at a checkpoint whose interval saw none of that reason, raised again at the next. It shows a second occurrence weeks later in the same process, but a source that refuses one record every other minute raises up to 30 an hour per reason, up to 90 an hour in all, and fills the 200-slot ring in a few hours.

**Recommendation: R1.** A rollback, the cause of `later-minor`, always restarts the process, so R2 adds nothing for it. For the other two reasons the counts and their health event (section 2.4) show every later occurrence, so R1 loses no information and cannot fill the ring.

### 2.3 What it says

Raised with `Status.Alarm` on the network database, stream the observation stream, as `raiseDetector` does now. One text per reason:

- `later-minor`: "a stored observation was written by a later build (`<a C4 minor above this build's event.Identifier | a C13 minor above this build's netobs self>`, chosen by `Field`), so this build refused it at judging: the detector did not judge it and raised no network alert for it. Every such record is counted in status (`observations_refused_by`) and on the health stream. First at seq `<n>`. Remedy: move this node forward to a build that reads it; records already passed are not judged again."
- `malformed`: "a stored observation did not decode (`<code>` at `<field>`), so the detector did not judge it and raised no network alert for it. Every such record is counted. First at seq `<n>`."
- `detector-refused`: "the detector refused a stored observation (`<another sensor's | no readable time>`, chosen as section 2.1 states), so it raised no network alert for it. Every such record is counted. First at seq `<n>`."

### 2.4 The durable counts (a real choice)

All three options keep the counts by reason in memory, show them in status, and write them as one health event. They differ in when the event is written and how a start reads it back.

- **A. The B3 drop-count pattern (#597), as first proposed in 7009772447.** Written when the counts change, at most once every `SensorDropReportEvery` (1 minute) unless final, by the `reportDrops` path, and read back at start by the `lastDropCounts` scan. Errors: a crash loses the refusals after the last write that sit before the last checkpoint (they are not replayed), and counts twice those that sit after the last checkpoint and were already written (the replay refuses them again). A start whose checkpoint did not restore replays every retained observation, so it recounts every retained refused record unless that start also begins the counts again.
- **B. Written with the checkpoint, carrying `through` (recommended).** At each detector checkpoint (`checkpointDetector`, from `tickDetector` at the steps Tick asks for, at most once a `TickInterval` (60 s), and at the stop) whose interval refused any record, the node writes the counts event **before** it stores the checkpoint, with `through` set to the `Through` about to be checkpointed. A checkpoint whose interval refused nothing writes no event. Two rules make the counts exact without an event at every checkpoint:
  - **No checkpoint passes an unwritten count.** While a counts event is owed (its write failed, or the ceiling or its own budget holds it), the checkpoint waits, up to the bound below, and is tried again at the next step; the detector goes on judging in memory, so only pruning and the replay window wait. So every refusal at or below a stored checkpoint's `Through` is in a written event, and a restored T with a newest event whose `through` is below T means no refusal in between: the counts are exact, quiet checkpoints included, unless a checkpoint was forced past the bound (below).
  - **A replay does not count twice.** If the event was written and the checkpoint was not (a crash between them, or a failed checkpoint), the event's `through` is above the restored T. During the replay the node counts a refusal only when its seq is above the restored event's `through`, since the event already holds every refusal at or below it.
  - **A bound on the wait.** The wait is measured from when the event first became owed, not from each checkpoint. A checkpoint is not held back past `RefusedCountsWait` (proposed 1 hour, four times the counts event's own spacing, section 5) from that instant. Past it the checkpoint is stored, and from then on, while the event is still owed, every checkpoint is stored at its step as D4-74's cadence has it, so a store fault cannot turn pruning into one step an hour. Status marks the counts a lower bound with the seq range not yet in an event (`observations_refused_exact: false`, `observations_refused_unsure: "<a>-<b>"`) until the event is written. So a full platform class never holds pruning, and through it the observation class, for long.
  - **Its own alarm.** The forced checkpoint is not a failed checkpoint, so `network-detector-checkpoint-failed`'s text on `main` ("the detector's checkpoint was not stored, so its cursor stays") would be false there (D4's F4 on #766). The node raises its own alarm, `network-refused-counts-unwritten`: "the counts of refused observations at seqs `<a>-<b>` were not written to the health stream within `RefusedCountsWait` (`<cause>`), so the detector's checkpoint was stored without them. Status shows the counts as a lower bound until they are written. A restart before then shows them as exact, and this alarm is then the only record of that range." It is raised at the first forced checkpoint, again at most once an hour while the event is still owed, and at the stop if the final write is held, each with the range as of then, so the OS log keeps the range outside the store (D3's F2 (a) on #766).
  - **The limit: a restart before the owed event is written shows the counts as exact** (D4's F3, D3's F2 (b) on #766). The flag and the range live in memory only. A crash, or a stop whose final write is also held, restarts with a restored T above the newest event's `through`, and the start reads that as no refusal in between, so status shows `observations_refused_exact: true` while the range was never counted. The OS log alarm above is then the only record of the range; after a crash, the refusals since its last raise, up to an hour of them, are in no record. A durable marker the start could read would close this, but while the platform class is held the only durable writes left are in the network database, where a node-held marker would be a new record kind (a C5 or C13 change, which the brief excludes). Not proposed.
  - **How far the start reads back** (D6's F2 on #766). The start reads the newest `detector.observation-refused` event for the stream, with its type and `stream` pinned as `parseDropCounts` pins them, at most `sensorDropScanRecords` (2,000) records back, as `lastDropCounts` reads. When it finds none (a quiet stretch left the event past the scan, or `Runtime.Prune` removed it behind its consumers), the counts begin again, with `since` set to now and the seq rule's `through` set to 0, and status shows the new `since`, as the drop counts do now. The counts are never reported under the old `since` once its event is not found.
  - **A start whose checkpoint did not restore** starts the detector at the oldest retained observation, and the counts begin again (`since` = now, `through` = 0). The earlier event stays on the health stream as the record of the earlier counts, and the replay counts each retained refused record once.
  It writes no more events than A, and fewer when refusals are rare.
- **C. Counts in the detector checkpoint.** Exact and atomic, but it is a new `otsec.netcheckpoint` key: a C13 minor, with CH-35's bridge items 1 and 2 on a rollback (7009772447). The brief excludes a C13 change. Not proposed.

**Recommendation: B.** Its counts are exact since `since`, while that `since`'s event is retained and within the start's scan: on a clean stop, on a crash at any point, and across quiet checkpoints, as long as no owed event has waited past `RefusedCountsWait` and the build does not change between an event and its checkpoint (section 8). Past the bound they are a stated lower bound, with the seq range, while the process lives, and a restart before the event is written shows them as exact (the limit above). A errs in both directions after a crash and needs B's fresh-start rule anyway. D1 accepted two departures from the forward-read note's condition 1 (counts written with the checkpoint, not on B3's timer; "run" is the node's process run), to be recorded in D4-120. **B adds a third, from D4-74** (D4's F4 on #766): D4-74's cadence writes the checkpoint at each `Tick` where `through` moved, and only a failed write keeps the cursor; B holds back a checkpoint that could be written, for up to `RefusedCountsWait`, while the detector goes on reading (unlike `network-alert-not-stored`, which also stops reading). D1 records it in D4-120 if accepted.

**The health event.** No existing type fits. `intake.drop-counted` is for records that were not stored; a refused observation is stored and not judged, and reading refusals as drops would change what every reader of that type sums. So the event needs a new C4 health type (section 7). Proposed name `detector.observation-refused` (D4 names it). Details, every value a decimal or a node-held name: `stream`, `since`, `through`, `count`, `reason.<r>` for each reason above 0, and `first_seq.<r>` and `last_seq.<r>`, the lowest and highest seq refused for that reason since `since`. The two seq keys are the durable answer to "which ones" once the records are pruned past; they are cheap (six keys at most) and can be struck if the reviewers find them unnecessary. Like every sensor health event it is written by `sensorHealth`, under the platform class's ceiling, and a held write is counted in `health_held`; it has a budget of its own, outside the pool (section 5).

**Status.** `observations_refused` stays the total, so a reader of `otsec.nodestatus/0.1` keeps working. Added: `observations_refused_by` (by reason), `observations_refused_since`, `observations_refused_exact` and `observations_refused_unsure`.

## 3. `network-baseline-refused`

### 3.1 The design

- **The cause.** `NewDetector` (D4's code, the D4 row with condition 3 in the forward-read note's section 4) returns an error the node tests with `errors.As` (or `errors.Is` on a sentinel), carrying the baseline's hash, its stamped `schema`, and the cause: `later-minor` (stamped above `baselineSelf`), `not-canonical`, or `malformed`. `RestoreDetector` calls `NewDetector`, so the same error reaches the node from a restore too.
- **Raised once per down stretch.** In `startDetector`'s caller, `tickSensor`: when the start fails with that error, the node raises `network-baseline-refused` once, keeps it raised while the start keeps failing for that cause, and clears it when the detector starts. `network-detector-not-started` is not raised for that cause, and `network-detector-not-restored` is not raised (section 4 places that raise after a successful start). One cause, one alarm.
- **The detector stays off** (D1's 7010372954): `r.detector` stays nil, `Through` does not move, and the observation stream is not pruned. The baseline-free rules do not run.
- **A standing entry while it is off** (D3's F3 on #766, against D3's condition 1, "stays raised until it clears"). `Status.add` is a ring of 200 with no clear, so one raise per stretch can be pushed out by 200 later alarms, and while the detector is off the sensor section has no `detector`. So while the start keeps failing for this cause, the sensor section of the status file carries a standing `detector_off: {cause, hash, since}`, kept until the detector starts and then removed. The alarm and the health event are still raised once per stretch.
- **`<schema>` only when it parses.** The value comes from a document refused as malformed or not canonical. It is shown, in the alarm, the health event and `detector_off`, only when it parses as a `netbaseline` identifier, and otherwise as `unreadable`, so no document text reaches the OS log.
- **What it says:** "the approved network baseline `<hash>` (`<schema> | unreadable`) was refused by this build (`<written by a later netbaseline minor | not canonical | malformed>`), so the network detector is off and no network alert is raised. The observation stream is kept for judging and grows until its class quota, past which new observations are dropped and counted (`class-full`, `network-full`). Remedy: approve a baseline this build reads, or move this node forward to a build that reads this one."
- **Its health event.** One event at the raise, type `detector.baseline-refused` (D4 names it), details `hash`, `schema`, `cause`. Written by `sensorHealth`; a held or failed write is tried again at each tick step while the alarm stands, and not after it clears.
- **D3's third condition** (the ceiling drop is the existing counted, alarmed drop): it holds on `main` today (section 1); T9 shows it.

### 3.2 When it lands (a real choice)

- **L1. With condition 1's change, before any baseline is wired.** The tests need a baseline in `detectorConfig`, so this adds a test-only way to set one, and D4's classified error has to exist first.
- **L2. In the change that wires the approved baseline into `detectorConfig` (recommended).** That change brings the baseline, D4's classification and the alarm together, and its tests use the real path. It meets condition 3's "no later than". Nothing reaches the refusal before it.

**Recommendation: L2,** with the not-restored fix of section 4 moved forward into condition 1's change, since that defect is live on `main` for any start that fails after a failed restore.

## 4. `network-detector-not-restored`: the repeat and the text

**Fix:** keep the restore's error in `startDetector` and raise not-restored only after the start has succeeded, after its last step that can fail, as `AlarmAlertUnreadable` is raised now (D6's N4 on #682). Then:

- a start that fails raises nothing from `startDetector`; `tickSensor` raises not-started once, and its text adds "the stored checkpoint did not restore either: `<error>`" when the restore failed too;
- the start that succeeds raises not-restored once, and its text is then true: "the detector's checkpoint did not restore, so the detector started again from the oldest retained observation: `<error>`";
- a start that fails for the baseline raises only `network-baseline-refused` (section 3).

The `<error>` here is a restore error (`RestoreDetector`'s, or an alert that does not decode), which names checkpoint fields and seqs, not record text; the change checks that before it keeps the error in the alarm.

**A failed store read is not a restore failure** (D6's F4 on #766; the defect is live on `main`, section 1). A failed store read during the restore, `alertsAfter`'s `db.Read` of the alert stream as well as `detectorCheckpoints`, fails the start, under not-started, and the next tick tries again. Only a checkpoint that does not decode or restore starts fresh. Alerts that do not decode are already skipped and counted (`AlarmAlertUnreadable`). So a transient read no longer discards a good checkpoint, stores committed alerts a second time, or, under B, begins the counts again. This lands with condition 1's change.

## 5. The health stream's budget

On `main` both new events go through `sensorHealth`, under the platform class's ceiling, as `reportDrops` does. `detector.observation-refused` is written at most once per checkpoint and only when the counts changed; `detector.baseline-refused` once per down stretch.

**The counts event has a budget of its own, 4 an hour, outside the CH-45 pool** (D3's F1 on #766), as `sensor.coverage-gap` has its own two budgets. Under B this event holds back the checkpoint, and the pool is spendable by the sensor whose output it measures: a sensor can spend all 24 of `PoolPerHour` through the alarm names it triggers (clock skew, records late, buffer filling and others, 4 each), and `rank` only orders what waits. In the pool, a sensor sending later-minor records could drive every checkpoint that carries refusals to `RefusedCountsWait` and the counts into the lower bound. With its own budget it cannot. `detector.baseline-refused`, once per down stretch and holding nothing back, joins the pool's list in `D5-sensor-node.md` section 1.9 item 5 when the pool is wired (`platform/sensorlink/health.go`, not wired under F-027's gate).

**The effect on S.** The sensor's caps rise from 45 to 49 records an hour, so `S = (49 x sensors + 3 x retired) x 4,096 x H` bytes; section 1.9 item 5's list and S change with the code.

**Under its own cap, steady refusals space the counts events to 4 an hour,** so under B the checkpoints that carry refusals wait for them: pruning and the replay window lag by up to 15 minutes while refusals continue, and the counts stay exact. Only if the ceiling holds an event past `RefusedCountsWait` do the counts become a stated lower bound with the range (section 2.4) until it is written. Under A the same cap would leave them a lower bound for up to 15 minutes at every step.

## 6. Tests

Each test names its control; the mutant is the change that must make it fail. All in `platform/node` unless stated.

- **T1 (with (b)'s code).** Three legs: a replayed stored observation whose C13 stamp is one minor above netobs `self`; one whose C4 envelope is stamped one minor above `event.Identifier` (each computed from the build's own, self-check item 11); and a later-C4 event with an unknown `binding.method`, which `Validate` refuses inside `event.Decode` (D4's F2 on #766). Each is refused under `later-minor`, its alarm text names the right stamp (by the `Field` of the error `ErrLaterMinor` matched: `netobs.schema` for the first, `schema` for the other two), raises `network-observation-refused` once, writes its counts event, and its count is exact after a clean restart. The first two legs are the check that (b)'s `Field` split holds. *Mutant:* the alarm removed. *Controls:* the same record at `self` is judged and not counted; the third leg's event at `event.Identifier` is counted `malformed`.
- **T2.** A stored record whose `netobs` does not decode is refused under `malformed`. A marker string placed in the record's offending field appears in neither the status file nor the OS log. A second leg places the marker in a map key (`health.details`), and the alarm's `Field` is the map's name (D3's F4 on #766). *Positive control, first, for each leg* (D6's F5 on #766): the marker is in `observationOf`'s error string, so the mutant can show it. *Control:* the valid record is judged. *Mutant:* the error string put in the detail, which shows the marker.
- **T3.** A stored observation of another sensor is refused under `detector-refused`. *Control:* the node's sensor's record is judged.
- **T4.** Five refusals of one reason raise one alarm; three reasons raise three. *Mutant:* a raise per record, which raises five.
- **T5 (B's exactness).** (a) Refusals, then several quiet checkpoints, then a restart: the counts are exact and not flagged. *Mutant:* the start that flags any event whose `through` is below T, which flags them. (b) A seam that fails the counts write: the checkpoint waits, and the detector's `Through` moves while the stored checkpoint does not; when the write succeeds the checkpoint follows; a restart in between gives exact counts. *Mutant:* the checkpoint not held back, which loses the interval's refusals. (c) A crash after the event and before the checkpoint: the replay refuses those records again and the counts do not rise. *Mutant:* the seq rule removed, which counts them twice. (d) A write held past `RefusedCountsWait` (a seam clock): the checkpoint is stored, `network-refused-counts-unwritten` raised once with the range, `network-detector-checkpoint-failed` not raised, and the counts flagged with the range; later checkpoints while the event is still owed are stored at their steps, not held another hour. A restart leg: a restart before the owed event is written shows the counts as exact, as section 2.4's limit states, and the alarm's range is in the OS log (D3's F2 (c), D4's F3 on #766). *Control:* the write succeeds within the bound, and nothing is flagged. (e) The newest counts event pruned, and in another leg past the 2,000-record scan: the start begins the counts again with a new `since`, and does not report them exact under the old one (D6's F2 on #766). *Control:* the event retained and within the scan, and the counts kept.
- **T6.** A checkpoint that does not restore starts the counts again, and each retained refused record is counted once. *Control:* the same store with a restorable checkpoint keeps the earlier counts.
- **T7 (section 4).** A restore failure followed by a failing fresh start for three ticks raises no not-restored and one not-started; the start that then succeeds raises exactly one not-restored. *Mutant:* the raise put back before `NewDetector`, which raises three. A second leg (D6's F4 on #766): the alert-stream read fails once; the next tick restores, raises no not-restored, and stores no alert twice. *Control:* `main`'s path, which raises not-restored, starts fresh and stores the committed alerts again.

## 8. Limits

- A refused record is not judged again. Moving forward to a build that reads it does not replay records the detector has passed, and they are pruned at the next checkpoint. The count and the seq range are what remains. Holding them from pruning would be a new store mechanism and is not proposed.
- While a counts event is held by its own budget or the platform ceiling, the checkpoints that carry refusals wait, so pruning and the replay window lag, by up to 15 minutes under its budget. Past `RefusedCountsWait`, measured from when the event first became owed, the counts are a stated lower bound until the event is written.
- **A restart before an owed event is written shows the counts as exact** while the range was never counted (section 2.4). The OS log's `network-refused-counts-unwritten` alarm is then the only record of the range, and after a crash the refusals since its last raise, up to an hour of them, are in no record.
- **The counts are exact only since `since`,** while that event is retained and within the start's 2,000-record scan; otherwise they begin again with a new `since` (section 2.4).
- **A build change between an event and its checkpoint breaks the seq rule** (D6's F3 on #766). The rule assumes the replay refuses the same records the event counted. If the build changes while (T, U] is open (a crash, or a stop whose final checkpoint fails), a forward build judges records the event counted as refused, so the count is too high and `later-minor`'s "records already passed are not judged again" is false for them; a back build refuses records the event did not count, so the count is too low. Neither is flagged. Carrying the writer's netobs and C4 self in the event, so that a start whose own differs marks (T, U] unsure, would close it; not proposed in this note.
- `later-minor` and T1 need (b)'s `ErrLaterMinor`, its `netobs.` prefix on `Field`, and its later-minor error returned alone (section 2.1).
