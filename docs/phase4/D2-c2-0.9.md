# C2 0.9: the session's connection, a Get or GetNext reply that doesn't match its request, and bounded times (D2, 2026-11-07)

D2's proposal for `otsec.adapter/0.9`, under brief P4-4-B2 (`docs/agent-handoffs.md`) and D4-68's carry to C2. It asks D5 and D3 to review, and D1 to approve. No code is written until D1 approves it. Evidence class: `desk`. The RFC text cited is RFC 3416 in `/mnt/project-files/rfc/`, which the owner allowed (D4-58). The code cited is `main` at `765f936`.

0.9 adds four things:

1. `session.local_addr` and `session.connected_at`, so the node can tie a flow the sensor sees to one of its own sessions (AP-35, C13 §5, the baseline note §5);
2. a code for a Get or GetNext reply whose binding list doesn't match the request (D4-60, and D1 on #541);
3. a nine-digit bound on the fraction of every C2 time (D4-61);
4. the collector refusing to load when two enrolled assets share one outbound endpoint (D4-68).

Items 1 to 3 change the contract text. Item 4 is collector behaviour, and is listed here because D4-68 carries it with this revision.

## 1. `session.local_addr` and `session.connected_at`

### 1.1 The gap

C13 §5 ties a flow from the node's address to one of the collector's sessions. Today the session record gives only the destination and the window `[started_at, ended_at]`. So the node can tie any flow from its own address to that destination inside the window (the `window` tie). The baseline note §5 narrows that to the first established connection. The residual is an attacker's connection that starts inside the window before the platform's own, which is then tied in its place. With the session's own local address and connect time, the node ties exactly one connection, and any other connection alerts (`own-session-outside-record`).

### 1.2 The fields

```json
"session": {
  "connected": true, "wake_sent": false, "language_probe": "accepted",
  "password_prompt": true, "credential_sent": true, "echo_scan": "performed",
  "access_level": "1", "quit_sent": true,
  "local_addr": "127.0.0.1:53114",
  "connected_at": "2026-11-07T20:15:02.418230115Z"
}
```

- **`local_addr`** is the collector's end of the session's one connection: the local address of the socket the collector opened, as `host:port` in `net.JoinHostPort` form. The host is an IP literal in the canonical form `netip.Addr.String` gives, so IPv6 is compressed, and `net.JoinHostPort` puts it in brackets. The collector writes it with `netip.Addr.Unmap()` and no zone. So an IPv4-mapped IPv6 address (`::ffff:a.b.c.d`), which a dual-stack socket can report, is written as plain IPv4. The sensor sees the IPv4 header, so a mapped form would never match its port (D4, D6 and D3 on #541, one fix). The port is 1 to 65535.
- **`connected_at`** is when that connection was established, on the clock that stamps `started_at` and every segment's `at` (the adapter's `now` seam). It is RFC 3339 UTC with `Z`, under the bound in §3.
  - **For a TCP session (SEL Telnet),** it is when the dial returned a connected socket. The SEL-751 adapter dials at most once successfully per run. It retries only when the dial fails, before any byte is sent (`modules/ied/sel751/run.go` `connect`). So a failed attempt, which never completed a handshake, has no fields, and the node doesn't tie it (baseline note §5).
  - **For an SNMPv3 session,** "connected" already means a datagram was sent (0.7, `SNMPFacts`). So `connected_at` is the `at` of the first segment the collector sent. The collector opens one connected UDP socket per run and closes it at the run's end (`modules/security/collector/snmp.go`, `plan.Dial` and `defer nc.Close()`). So the run's datagrams share `local_addr`, and the sensor sees them as one conversation.

### 1.3 Rules (`Result.Validate`)

For a 0.9 result or later:

1. `connected` true ⇔ both fields are present. With `connected` false, neither is. The fields are `omitempty`, so a result that never connected looks as it does in 0.8.
2. `local_addr` parses as above. Each of these fails: a hostname, a zone, port 0, an unspecified address (`0.0.0.0` or `::`), an IPv4-mapped IPv6 address, or any other non-canonical form.
3. `started_at` ≤ `connected_at` ≤ `ended_at`.
4. `connected_at` is no later than the `at` of the transcript's first segment. For an SNMPv3 result, it equals that segment's `at`, and that segment is sent.

A 0.8 result carries neither field, and a 0.8 result that does fails ("new in 0.9"), as `session.snmp` does before 0.7. A 0.8 reader reads a 0.9 result forward and ignores both (`strictjson.Forward`), so older nodes keep working with a newer collector.

### 1.4 Who fills them

- **SEL-751 adapter (`modules/ied/sel751`):** from the `net.Conn` its `Dial` seam returns (`LocalAddr()`) and the clock reading when `Dial` returns. The `Dial` seam itself doesn't change.
- **SNMPv3 (`modules/ied/snmpv3` and the collector):** the `snmpv3.Conn` interface gains `LocalAddr() string`, and the session sets `local_addr` from it when it sends its first datagram. The collector's `udpConn` implements it from the connected socket (`nc.LocalAddr()`). This is the collector change B2 allows in `modules/security/collector/` (D1 on #539). I chose to pass the address through the interface, not have the collector patch the result afterwards, so the result is built in one place, as it is today (`modules/ied/snmpv3/result.go`).

### 1.5 How the node uses them (C13 §5, for D5 and D4)

The node ties a C13 flow to a session when:

- the flow's client (address, port) equals `local_addr`;
- its server (address, port) is the run's endpoint;
- its `l4` is the endpoint's transport;
- its time agrees with `connected_at` under the baseline note §5's time rule. A flat "first sight within `tie_grace_s`" would miss a TCP flow the sensor joins midstream, and an SNMPv3 run whose UDP conversation the sensor already holds open from an earlier run with the same 5-tuple (D5, D4 on #541). So the time rule stays in the note, which D4 widens for these cases once 0.9 is approved.

That is C13's `tie: connection`. A 0.8 result, or one not connected, keeps the `window` tie. The clocks differ: `connected_at` is the collector host's, and the flow's time is the sensor's. So the grace stays. The port match is what makes the tie exact.

**Limit:** the tie needs the sensor to see the collector's own address. A NAT between the collector and the monitored segment rewrites the source port. The node then never ties the session, and `own-session-unseen` and `own-session-outside-record` fire. That failure is visible, not silent. Where the sensor sits is ADR-0009's open choice, so this goes into the sensor brief's placement rules.

## 2. `failed.snmp_varbinds_mismatch`

### 2.1 The gap (D4-60)

RFC 3416 §4.2.1 (GetRequest) and §4.2.2 (GetNextRequest) both say: "All fields of the Response-PDU have the same values as the corresponding fields of the received request except as indicated below". Each binding is then processed in place: for Get, given its value or an exception; for GetNext, replaced by its successor or by `endOfMibView`. So a `noError` Response to either request has exactly as many bindings as the request. The client (`modules/ied/snmpv3/session.go`) names neither violation:

- `walk` ends a GetNext walk as complete when the Response has no bindings, and keeps every binding when it has more than one. So D4-60 barred `GETNEXT` walks from signed registers until a code exists.
- `get` keeps whatever bindings come back. So a short Get Response silently drops an attribute today.

### 2.2 The code

- **`failed.snmp_varbinds_mismatch`**: an authenticated `noError` Response to a GetRequest or a GetNextRequest whose binding count differs from the request's. The name covers both requests, so the one code means one thing: the reply's binding list doesn't match the request it answers (D1 on #541). The session ends, the bytes are kept, and nothing is suspended, as with the other SNMP protocol codes (D4-54). Stage after-auth, SNMP only, new in 0.9. The count is checked as soon as the Response is decoded, before any of its bindings is kept, so no binding from that Response gives a value (D6 on #541). Bindings from earlier valid Responses in the same run still give values. They were valid replies, and the failed code already marks the run. That is how the other failed SNMP codes treat them today: values from authenticated answers read before the failure are reported, while the FID, model and firmware version never are, because they need a FID that was compared and matched (`fidRead` in `modules/ied/snmpv3/result.go`).
- **GetBulk is out of scope.** RFC 3416 §4.2.3 lets a GetBulk Response carry fewer bindings. The empty case is already `failed.response_too_large` (`walk`).
- **GetRequest is in (D1 on #541).** D1 ruled that the code covers Get too, because silently keeping a shorter list drops data.
- **The rule is the count only.** The binding names are already checked where it matters: a walk refuses a name that isn't greater than the one before (`failed.snmp_walk_not_increasing`). A Get binding's name that differs from the request's isn't checked in 0.9. That stays a recorded limit, as it is today.

**D4-60's bar on `GETNEXT` walks lifts when the 0.9 code merges, not when this proposal does** (D1 on #541). That is when the client returns `failed.snmp_varbinds_mismatch`, with D6's test 3 (§6) green at that head. Until then, every SNMP operation in a signed register stays a `GET` or a `GETBULK` walk.

## 3. Every C2 time has at most nine fractional digits (D4-61)

`asset.ValidTime` accepts any fraction length. Go's `time.Parse` reads `2026-11-07T20:00:00.1234567891Z` and drops the tenth digit (checked with `go run` on Go 1.27.3: the value parses, and formats back with nine digits). C12 0.2's `identity.mismatch.at_utc` is a C2 `ended_at` as stored, and C12's form allows at most nine digits (D4-61, `docs/phase4/D4-c12-0.2.md` rule 1). So 0.9 bounds the fraction to 1 to 9 digits, or none, on every C2 time:

- `started_at` and `ended_at`;
- `connected_at`;
- each transcript segment's `at`.

The check is a C2 helper (`validTime`), not a change to C1's `asset.ValidTime`, so C1 doesn't move. It applies to results of every minor. No result this code writes changes, because Go's `time.RFC3339Nano` never writes more than nine digits, and none in the repository has more. A hand-written result with ten digits now fails, which is the point.

## 4. The collector refuses two assets on one outbound endpoint (D4-68)

The tie in §1.5 resolves a flow's server to one asset. C13 §5 already resolves two assets on one address to neither (`ip-ambiguous`). The collector is where enrollment is checked, so it refuses the case at load. `NewPipeline` (`modules/security/collector/pipeline.go`) returns an error when two enrolled assets have outbound endpoints with:

- the same transport layer (TCP for `telnet` and `ssh`, UDP for `snmpv3`);
- the same host, compared as `netip.ParseAddr(host).Unmap().WithZone("")`. C1 already refuses an endpoint host that isn't an IP address (`contracts/asset`), so there is no other branch. `Unmap` makes `10.0.0.5` and `::ffff:10.0.0.5` the same host, as C1's inbound-sender check does (D3 on #541). The zone is dropped because the sensor sees no zone, so two assets that differ only by zone would be indistinguishable on the wire. Refusing them is the closed side. Refusing a zoned host at enrollment is a later C1 change, not part of 0.9 (D1 on #541);
- the same port.

The collector then doesn't start. That fails closed, and the error names both asset IDs and the shared endpoint. One asset with two endpoints on its own host is unaffected. Two assets on one host with different ports, or one on TCP and one on UDP, are unaffected, because the sensor tells them apart by port and `l4`.

## 5. Contract mechanics

- `Contract` becomes `otsec.adapter/0.9`. Readers still accept any minor of major 0, as `version.Accepts` does today: an earlier one strictly, a later one forward. The goldens gain 0.9 examples: a connected SEL result and a connected SNMPv3 result with both fields, and a `failed.snmp_varbinds_mismatch` result for `TestEveryCodeHasAnExample`. The 0.8 goldens stay as they are, and must still validate.
- Nothing else in C1, C3 or C7 changes. C8's run records don't carry the fields: the node reads them from the result, as it reads `started_at` today.

## 6. Tests D6 is asked for (B2 deliverable 2)

1. The four §1.3 rules, each with a failing case, including `connected` true with one field missing, an IPv4-mapped `local_addr`, a zoned one, an unspecified one (`0.0.0.0:40000`, `[::]:40000`), and a 0.8 result that carries the fields.
2. An SEL simulator run and an SNMPv3 simulator run in which `local_addr` equals the address the far end saw. The simulator reports it, so the value is checked from outside the adapter.
3. A walk against an agent that answers a GetNext with zero bindings, and one that answers with two. Both end `failed.snmp_varbinds_mismatch` with the bytes kept. Also a Get of two OIDs answered with one binding, which ends the same way.
4. A ten-digit fraction refused in each of the four time fields.
5. The collector refusing to load two assets on one host:port, including one written `10.0.0.5` and one `::ffff:10.0.0.5`, and two that differ only by zone. Loading two on one host with different ports, or with TCP and UDP.
