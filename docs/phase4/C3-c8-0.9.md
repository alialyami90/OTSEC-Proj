# C8 0.9: config.checkpoint_not_restored (C3)

Status: proposal for review, C3, 2026-11-04 (D4-40 items 6 and 8). C5 and C4 review as the writers and as the callers of `VerifyConfigFrom`, and C6 writes the contract tests. This is a contract change only. It adds one action, two fields and one function, and changes no rule of 0.8: `VerifyConfig` is `VerifyConfigFrom` from seq 1. Everything here is `desk`: the tests use fixtures, and no device has been contacted.

## Why

D4-32 item 2 says that when the newest checkpoint of one half of an asset's event baseline does not restore, the node raises an alarm and writes an audit record. A learner then starts the audited re-learn of D4-26. A detector is rebuilt from the acknowledged baseline. The node never falls back to an older checkpoint (D4-36 item 2). Until 0.9, no C8 action could carry that record. Until this merges, slice 1c raises the alarm and the health event only (D4-40 item 6).

## The record

`config.checkpoint_not_restored` is written from contract minor 9. It is written by the node (actor type `node`) with outcome `warning`, and its target is the asset. Its reason code is the error class, from a closed set:

| `reason_code` | When |
| --- | --- |
| `corrupt` | The stored record does not decode or check. The document is not one the node's encoder writes, the capture is not the snapshot the document names, or the snapshot fails its own checks. |
| `version` | The document's schema, or the snapshot's format, is one this node does not read. |
| `mismatch` | It decodes and checks, but it is not this asset's current state. This covers another asset, a learner whose version or previous baseline is not the asset's next re-learn, and a detector whose baseline is not the acknowledged one. |
| `refused` | The checkpoint was read in full and decodes, and the node's own check of its content refused it: the half would not take the snapshot it holds. |

A read that did not complete is not a restore outcome, so it is not a reason for this record (C5's question on #387, ruled by C1). That covers a database that is not open, a busy open, and a read error. The node keeps that half unstarted, raises an alarm, retries, and writes no record. So a fault that clears on retry never throws away a learner's progress.

The `config` group:

| Field | Learner | Detector |
| --- | --- | --- |
| `kind` | `event` | `event` |
| `checkpoint_half` (new) | `learner` | `detector` |
| `checkpoint_seq` (new) | the checkpoint record's seq in `config/<asset>` | the same |
| `baseline_version` | the version the re-learn will record | absent |
| `previous_digest` | the baseline the re-learn will replace, from version 2; absent at version 1 | absent |
| `baseline_digest` | absent: the re-learn has recorded nothing | the acknowledged event baseline it is rebuilt from |

`correlation_id` is `eventcheckpoint.<half>:<checkpoint_seq>` (`CheckpointCorrelationID`). That is the C5 series (D4-39 item 3) and the seq of the record, so it names one stored record. It is the same when a restart finds the same checkpoint again, and it needs no invented ID. A node that restarts before its re-learn commits a new checkpoint writes a second record with the same ID. Nothing refuses that, because it failed again.

The detector's `baseline_digest` goes beyond C1's list. C1 accepted it in D4-40 item 6. It is not read from the failed checkpoint, which may not decode. It names the baseline the node rebuilds the detector from, so the chain shows what the detector now runs against.

## What `Validate` checks

- The actor is the node, the outcome is warning, and the reason code is one of the four.
- `kind` is event, the half is one of the two, `checkpoint_seq` is at least 1, and `correlation_id` is exactly `eventcheckpoint.<half>:<seq>`.
- No approval, read, change or removal field is present.
- For a learner: no `baseline_digest`, a version of 1 or more, and a version of 1 exactly when `previous_digest` is absent.
- For a detector: a `baseline_digest`, and no version and no previous digest.
- `checkpoint_half` and `checkpoint_seq` are refused on every other action. A record stamped 0.8 or earlier cannot carry the action.

## What `VerifyConfig` checks

1. **A learner** follows the latest `config.baseline_recorded` of its asset before it in `recs`. Its version is one more than that record's, and its `previous_digest` is that record's digest. With no recording before it, it is held to version 1 only when `recs` holds the asset's version-1 recording, after it (the same `firstIn` reading as 0.8). Otherwise `recs` may start after the asset's first recording, and nothing is checked.
2. **A detector** names the event baseline that the latest succeeded `config.baseline_acknowledged` of its asset before it in `recs` set. A denied acknowledgement sets nothing. A baseline recorded but not yet acknowledged is refused. With no acknowledgement in `recs`, nothing is checked.

## `VerifyConfigFrom`: a chain pruned at the node (D4-40 item 8)

The node prunes its audit stream once records are forwarded. `VerifyConfig` assumes that `recs` starts at the chain's first record, or before everything the records in it name. A retained view nearly always cuts through such a reference. Every one of the 14 later cuts of C8's `readsChain` failed. So a node that verifies its chain at start, as #384 does, would stop every observed asset after the first prune (C3 on #384, B1). C1 chose a check that tolerates the cut, with four conditions.

`VerifyConfigFrom(recs, first)` checks the view from seq `first`: the configuration and collector records retained after the node's recorded prune point. Any record before `first` is refused. A reference to something before the view is unknown, not broken. Every other reference resolves as in `VerifyConfig`. "Before the view" means:

| Reference | Unknown when |
| --- | --- |
| A chain seq (`change_seq`) | below `first` |
| A decision (`decision_seq`, `read_seq`, `unchanged_read_seq`, `approval_seq`) | below the lowest `collector_seq` that a `collector.request` in the view records before its first `collector.seq_reset`. If there is none, every decision of that epoch is unknown. After a reset in the view, nothing is unknown. |
| The reset that bounds a detection with no earlier run | in the view's first epoch |
| The asset's active configuration baseline | not yet shown. It is taken from the asset's first record in the view that names one, and is checked from then on. |
| Open alarms and changes | not yet shown |
| The compared reads that a removal takes | for the asset's first `config.reads_removed` in the view only, and only when it takes reads from before the view. Its digest is then not checked. Its range must end at the last read it takes from the view, and its `kept_digest` must be the view's newest compared read when the view holds one. A removal whose reads are all in the view is checked in full. |

A record whose decision is unknown is still checked for everything that does not need that decision.

**C1's conditions, and where each one lives:**
1. The view starts at the node's recorded prune point, and its hash chain is checked in full. That is the caller's job: `VerifyChain` from the prune point's checkpoint, which C5 keeps across pruning, then `VerifyConfigFrom` with `first` one past it. Inside the function, any record before `first` is refused.
2. Only a reference to something before the prune point is unknown. This is the table above.
3. The full chain stays verifiable upstream. This does not change: forwarding sends every record before it is pruned.
4. Status shows that start-up verification ran from the prune point. That is the node's (C4 on #384, C5).

**A condition on the node (C5, from the code).** The node has one collector request in flight at a time: every request comes from the one scheduler goroutine, and each `Do` returns only after its decision record is appended. So the chain holds decisions in `collector_seq` order, and "below the lowest decision in the view" means "before the view". C5 keeps this true when wiring the signed kinds. A node that broke it could write a decision after a higher one. A prune point between them would then make a reference to the pruned one broken, not unknown, and the check would fail closed.

## For the writers

- **C5 (the node).**
  - Write the record after the alarm, and before the learner commits the first checkpoint of its re-learn or the detector its first rebuilt checkpoint. A crash before the record is written leaves the same newest checkpoint, which fails again at the next start, so the record is written then.
  - Take the learner's version and previous from what the node would record next (C10's `Version` and `Previous`). Do not take them from the failed checkpoint.
  - `checkpoint_seq` is the newest committed record of the series, chosen by commit order without decoding it (D4-36 item 2).
- **C4 (the halves).** Please confirm the four classes against what restore can return. In particular, does the learner or the detector have a refusal of a decoded snapshot that is not covered by `refused`?
