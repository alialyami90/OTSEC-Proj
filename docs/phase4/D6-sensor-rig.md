# D6: the rig for the sensor's tests (P4-4-R1)

D6, 2026-11-11. Brief P4-4-R1 (`docs/agent-handoffs.md`, "Phase 4 item 4, second part", D4-86) asks for the rigs that V-M6, R6.4 and C-11 need, built before the sensor exists, so that the sensor is tested by something that was not shaped by it. This note says what was built, what each rig's self-test showed, what is planned and not built, and why.

- **No sensor exists.** Nothing here is V-M6, R6.4 or C-11 evidence. Each result is a result about the rig: it shows that the rig can tell a pass from a fail.
- **Evidence classes.** `CI-Linux` for what ran on the hosted runner, which is `simulated`: every interface is a virtual one in a network namespace made for the test, and `standin_sensor.py` stands in for the sensor and decodes nothing. `desk` for what ran on the owner's PC.
- **Safety.** Nothing captures a real network, nothing scans or probes, and no device or lab machine is contacted. The runner's own NIC is never a monitoring interface. What needs a lab machine is an H-row that nobody runs without the owner's authorization (section 6).
- The code is `tests/integration/sensor_rig/`. Deliverable 0, the GT-PCAP cases and the engine run's pass conditions, is on `main` as `96c35ef8` (#623), and this branch holds `main` from there.

### What a process with no capability can still do with its open socket

D3's link note takes as an assumption that an open packet socket can still send after its capability is dropped, and leaves it to this rig (SL-3, SL-26; D3 on #626). **The rig measured it, and the assumption holds: dropping every capability does not stop a process from sending on the packet socket it already holds, and does not stop it from switching the bypass option on.** On this kernel, on a veth pair:

| The stand-in | On the quiet `mon0`, no rule | Behind the nftables egress chain | Behind the `tc` egress filter |
| --- | --- | --- | --- |
| **Kept its capabilities** (root: the control) | Send: accepted, arrived. Set `PACKET_QDISC_BYPASS`: accepted. Send with it: accepted, arrived | Send: `ENOBUFS`, did not arrive. Set the option: accepted. Send with it: `ENOBUFS`, did not arrive | Send: `ENOBUFS`, did not arrive. Set the option: accepted. Send with it: **accepted, arrived** |
| **Dropped everything** (no capability in any set, `NoNewPrivs` 1, an unprivileged user) | Send: **accepted, arrived.** Set the option: **accepted.** Send with it: **accepted, arrived** | Send: `ENOBUFS`, did not arrive. Set the option: accepted. Send with it: `ENOBUFS`, did not arrive | Send: `ENOBUFS`, did not arrive. Set the option: accepted. Send with it: **accepted, arrived** |
| **Set the option, then dropped everything** | Send with it: **accepted, arrived** | Send with it: `ENOBUFS`, did not arrive | Send with it: **accepted, arrived** |

- **A process with no capability sent frames from `mon0`.** With no rule, every one of its sends arrived at `tap0`. The same process could not open a second packet socket: the drop stops a new socket, and it does not stop the one that is open.
- **It could set `PACKET_QDISC_BYPASS` after the drop.** The kernel accepted the option from a process with no capability, in all three arrangements. Setting it before the drop made no difference.
- **Behind the `tc` filter, the process with no capability got a frame out,** by the bypass option, exactly as root did.
- **Behind the nftables `netdev` egress chain, nothing it sent arrived,** with or without the option.
- In every column the process without capabilities did what the control did. On this kernel, the capability made no difference to a send on an open socket.

So "`CAP_NET_RAW` dropped after the socket opens" keeps a capture stage from opening more packet sockets, which was measured. It does not make that stage unable to transmit. Whether such a stage can change or remove the rule was not measured here. What that means for the design is D3's (SL-3, SL-26, AP-32), and the limits below hold for these rows too: one kernel, a veth pair.

### Limits

- **A veth pair says nothing about a real NIC's driver.** It has no hardware queue, no offload and no firmware, and a real driver may have a send path of its own. Every result above is one kernel, 7.0.0-1017-azure, on a veth pair. It says nothing of another kernel, of an XDP socket, or of a process that removes the rule. H-18 repeats the zero-frames run and both senders on a real NIC, and nobody runs it without the owner's authorization.
- **What the three send-path rows show, and no more.** On this kernel and this pair: a queue that drops everything did not stop a `PACKET_QDISC_BYPASS` sender; a `tc` clsact egress filter stopped the host's stack and an ordinary packet socket and did not stop it either; an nftables `netdev` egress chain stopped all three. These are measurements. What they mean for the sensor host is D3's to say, and the next three points are D3's reading from its review of #626, given as D3's and not as D6's.
  - **(D3) "An egress filter" is too loose a requirement.** A `tc` clsact filter and a queue both sit at the queueing layer, and the bypass option skips that layer by design. The requirement is named by its test, not by its kind: a rule on each monitoring interface that the rig's bypass sender does not pass, shown on the sensor image's own kernel. One mechanism has met that so far, an nftables `netdev` chain on the `egress` hook with policy drop. A `tc` rule or a queue does not count: it stays a second measure and never the only one.
  - **(D3) What the nftables row shows, and does not.** It shows that on kernel 7.0.0-1017-azure, on a veth pair, the chain stopped the host's stack, an ordinary packet socket and a packet socket with the bypass option. It does not show another kernel, or one built without the hook; a real NIC's driver, offload or firmware (H-18); any other send path, such as an XDP socket, an XDP program that transmits, or the kernel's packet generator, none of which was sent here; or anything against root, who removes the rule.
  - **(D3) The TAP statement stands.** One host rule was in force and still let a frame out, and only a second sender showed it. A host rule is software on the machine that is assumed compromised. Against a compromised sensor host, only a TAP holds, and a mirror port counts as accepting ingress until an H-row shows otherwise for that switch model.
- **A bridge and a VLAN device stand for the other masters and upper devices.** D2's point on #627 names more of each: a bond, a team, Open vSwitch and a VRF as masters, and macvlan and ipvlan as upper devices. One of each kind is built. The check that a sensor's capture interface has no master of any kind and nothing stacked on it belongs to C13 0.2, which is not approved. It is planned for the C-11 run on the real sensor and is not built.
- **The source writes C13 0.1.** `c13_source.py` emits `otsec.netobs/0.1` and nothing else. When C13 0.2 is coded, the source, its committed stream and the contract test change with it.
- **The stand-in is not a sensor.** The C-11 pass says that the arrangement is quiet and the rig can see. It says nothing about an engine, which may send: Zeek and Suricata link libpcap, which can, and Suricata transmits by design in `reject` and IPS modes (ADR-0009).
- **The replay in the C-11 self-test is the 19 DNP3 cases with gaps cut to 2 ms,** not the whole GT-PCAP set at its recorded pace: the two R6.2 series are an hour each. The gate's run replays the whole set, and says what pace it used.
- **Latency is measured on one host's clock.** Under option (b) the alert's time is the node's and the sensor is another machine. In CI both are on the runner. On two machines the measure needs both clocks compared first, which C13 0.2's skew fields are for (P4-4-L2).
- **The checker covers `flow`, `service`, `function` and `insecure` rows.** The derived Modbus capture's label on `main` holds an `insecure` row (`reason=modbus-tcp`), which is V-M6's "every insecure use flagged", and the checker judges it. An earlier head of this note said that no label held one, which was false once #623 merged (D4 on #626). It does not judge `dnp3_no_sa`, alerts against `case` rows or redactions, and `encrypted`, `identity` and `undecoded` records have no label rows on `main` to be compared with.
- **The Modbus label is judged with records built by hand in the test.** Its frames come from a public capture and are not in the repository, so the source cannot make its records. The source's stream and the contract test are DNP3 only.
- **Some of the source's records claim what a sensor could not know yet** (D4 on #626). They are right for decoding and wrong in time, which matters before the source feeds the node's intake, its hold logic or a latency test: the flow's `start`, with `protocol: dnp3`, and the `service`, with `basis: content`, are both sent at the SYN and cite it, before any DNP3 byte; a function whose `sa` is absent is sent at its request, where a sensor learns that only at the reuse or after `sa_reply_timeout_ms`; a UDP flow's `end: idle` is sent at its last datagram and not `flow_idle_s` later; and two heartbeats a run meet "every 10 s" only because every streamed capture is shorter than that. Its heartbeats say `interface_check: unknown`, since it reads a file and no interface.
- **The replay checks catch only an error above the tolerance.** The timed frames are 100 ms apart and the tolerance is 50 ms. A replayer that mishandles the millisecond gaps of a real exchange, or is off by less than 50 ms, is not caught, and the latency check accepts up to 50 ms of error (D4 on #626).
- **The capability check reads capabilities and nothing else.** It does not read the process's user or groups, its threads, or which descriptors it holds, and it cannot show that a process calls no send function. A real capture stage has all of those to show (D3 on #626). The stand-in shows none of them.
- **The authorized writers.** `gt_checker.writers()` resolves every name in `authorized_writers` through `masters`, `outstation` and `outstations`, and stops on a name that none of them holds (D4 on #623: `dnp3-cases.json` names outstations in two places). Nothing judges `unauthorized-write` with it yet.
- **The source reads labels, so it cannot be wrong where the labels are wrong.** It is a way to run the node's side before a sensor exists, and a known-good input for the checker's self-test. It is not a second opinion on the labels: the stream is pinned to its generator, and its content to the labels only through the checker, which reads the same label columns, so a misreading that both share is not caught (D4 on #626).

## 4. Cases that had no plan (deliverable 5)

Each case says what it must show, how it will be tested, and whether it is built.

1. **`CAP_NET_RAW` dropped after the socket opens. Built, with its send leg.** The measured result is in section 2: a process with no capability still sends on its open socket and still sets the bypass option. The rule the check applies: the process's permitted, effective, inheritable and ambient sets are all empty, and either `NoNewPrivs` is 1 or its bounding set is empty, read from `/proc/<pid>/status` while it is receiving frames. The self-test also shows that such a process cannot open a second packet socket. On the sensor it is read after the first heartbeat and again at the end of the replay, for every process and thread of the sensor's service.
2. **A link cut and resumed. Planned, not built.** A third namespace holds the node, joined to the sensor's by a second veth pair, the link. Mid-replay the link goes down for longer than the sensor's send timeout and comes back. Pass: the node's stored observations equal the uninterrupted run's, compared by key and cited hashes; nothing is stored twice; `sensor-unreachable` is raised once and cleared; a buffer overflow on the sensor is counted and shows as a gap, never as silence; SER and Syslog collection lose nothing meanwhile. **Not built because** acknowledgement and resume are C13 0.2's (P4-4-L2), and the node has no dialer (P4-4-L3). The GT-PCAP plan's §5 has the node-side half, a kill and restart at intake level.
3. **A revoked sensor credential refused and alarmed. Planned, not built.** Enrol a test key, run, revoke it with the admin-signed request, and reconnect. Pass: the link closes at once; the next connection is refused and alarmed; records already stored are kept and marked; a record sent after the revocation is in no store class; the network baseline needs acknowledging again. The same rig runs the two refusals beside it: a sensor with no enrolled credential, and a record under another `sensor_id`. **Not built because** the credential, the C7 kind and the C8 actions are P4-4-L1's proposals and are not approved.
4. **No inbound port on the node. Planned, not built.** In the node's namespace, list every listening socket (from `/proc/net`, read inside the namespace) before the sensor is configured and while the link is up. Pass: the set is the same, and the link's connection was opened by the node, which the capture on the link shows by the SYN's sender. It reads the node's own socket table and scans nothing. **Not built because** the node has no dialer and no `network_sensor` link settings yet.
5. **The spoofing flood. Planned in the GT-PCAP plan §5, not built.** Under option (b) it runs through the link, so it also shows that a flood from the sensor never stops SER or Syslog collection (D5, D3 on #618). **Not built because** it needs a flood generator on the source, the node with its quotas, and GT-INJ's feed in one run, which is a leg of its own. The source here sends label-derived records only.
6. **AP-33's key search over the sensor's disk and the link's bytes. Planned, not built.** Every test secret is unique to its capture (plan §2D). After the replay, search for each one, raw, as hex in either case and as base64 (the forms V-M1's M3 searches), in: every file under the sensor's state, log, temporary and core-dump directories, and its swap if it has any; the bytes of the link as captured on the link's veth, and the C13 stream inside the TLS session as the node reads it; the node's store; and everything forwarded. A control secret planted in each place must be found, so an empty result means something. **Not built because** no labelled capture holds a secret yet (plan §2D's cases are not built), and there is no sensor disk to search.

### What the rig can host as built, and what it cannot (D3 on #626)

The rig has one monitoring interface, one sensor namespace, and no file system of its own for the sensor. So of the tests in D3's link note (`docs/phase4/D3-sensor-link.md`):

- **It can host** the tests that need one monitoring interface and a process on it: the zero-frames run, the egress rule against the bypass sender from the capture stage's own account, and the capability reading.
- **It cannot host, as built:** SL-T19, which needs two monitoring interfaces and a management interface in three namespaces; and SL-T1, SL-T14, SL-T15 and SL-T16, which need the sensor's own root file system.

### What the planned legs need from the node (D5 on #626)

From D5's review, against the node's link design in #628, which is not approved. None of it is built.

- **The source must become a C13 0.2 peer.** It writes 0.1 one way. To feed the real node through its dialer it has to be a TLS server with a pinned key that checks the node's client certificate, answers the node's hello, sends ticks, reads acknowledgements and resends from where the node says. Until then the committed stream can feed `ServeSensor` in-process only, and that function's shape changes with 0.2.
- **A third namespace with the real node binary,** the collector, the simulator and Syslog senders, as the `vm8_paired` leg builds them, because the pass conditions are about SER and Syslog collection. A leg that checks forwarding needs rsyslog, and then the leg's `apt` condition is revisited. The controls need test-build seams in the node: a slow network commit and an unfair lock.
- **Time.** One leg for each rig leg, as the slice suite has: the flood leg runs for twice the observation quota's fill time, the cut-and-resume leg for 10 minutes, and the clock leg across 20 scheduled runs.
- **No inbound port:** the node reads its configuration at start only, so "before the sensor is configured" means a start with no `network_sensor` section compared with a start that has one.
- **Platform.** The rig runs the node's Linux build. The node's Windows-only parts stay with the dispatched Windows workflow.
