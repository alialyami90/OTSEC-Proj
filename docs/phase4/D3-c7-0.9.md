# C7 0.9: refuse an all-zero or all-`ff` engine ID at install

D3, 2026-11-06. This is a proposal and its code in one PR, approved by D1 on 2026-11-06 (relayed by the coordinator) as an item 3 contract fix, which D4-34 allows. It merges after V-M1's counted run. D6's contract tests come once the V-M1 PR is up.

## Why

RFC 3411 §5 (`SnmpEngineID`, `/mnt/project-files/rfc/rfc3411.txt`) says an engine ID is never all zeros or all `'ff'H`. D2's client now refuses such a pinned ID before it sends anything (#495, `TestPinnedEngineIDForm`). But C7 0.8's `USM.Validate` still accepts one. So the credential installs, and then every run on it fails at start. The defect should be refused where the administrator signs it, not found at the first run. Found in D3's review of #495.

## The change

- `contracts/authz/usm.go`: `USM.Validate` refuses an `engine_id` that is all `00` or all `ff` octets, at any length from 5 to 32. The pattern rule is unchanged.
- `ContractID` is `otsec.authz/0.9`. Nothing new goes on the wire. The minor marks the stricter rule. The refusal applies whatever the request is stamped, because no valid 0.8 message can carry such an ID.
- `schema/credential-ref.json` (`$id` 0.9): `engine_id` gains `"not": {"pattern": "^(?:(?:00)+|(?:ff)+)$"}`.
- The two admin-signed goldens are stamped 0.9, regenerated with `OTSEC_UPDATE_GOLDEN=1`. Only their `contract` line changes.
- `contracts/README.md`: C7's row, at D1's request for the change.

## Compatibility

Readers accept every minor of their major, so a 0.8 node and a 0.9 collector interoperate.

**A stored credential is re-validated.** The collector runs `Ref.Validate` on every credential store entry when it opens the store (`modules/security/collector/credstore.go`, `checkEntries`). A store that already holds such a credential therefore fails to open after the upgrade, and the collector does not start. That fails closed (P5). Such a credential could exist only in a test store, because no real credential exists (D2-5). It could never have run, under #495. No fixture in the repository has such an ID (checked with `grep` across `*.go` and `*.json`). The remedy is to revoke it before upgrading. Applying the rule at install only would need a second validation path, which is not worth its code for a credential that cannot run.

## Tests

- `TestSNMPv3Credential`: the new rows "engine id all zeros" (5 octets) and "engine id all ff" (32 octets) failed on `main` ("accepted") before the change. `00000000ff` stays valid.
- D6 adds the contract tests after V-M1's PR is up.

## Open, for D2

Whether C1 0.3's declared `snmp_engine_id` carries the same rule. D1 asked D2. The collector already requires the credential's engine ID to equal the asset's declared one (`endpointMatches`), so with this change such an asset gets no credential.
