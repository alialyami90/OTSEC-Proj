# C8 0.8: config.baseline_recorded (B3)

Status: proposal for review by C4, C5 and C6 (B4, B5 and B6 when it was opened), at B1's request. Updated by C3 on 2026-10-28 for the D4-26 amendment (the acknowledgement window) and D4-29 (`correlation_id`). It is a contract change only: it adds one action and one field, and changes no rule of 0.7. Everything here is `desk`: tests use fixtures, and no device has been contacted.

## Why

A configuration baseline starts as a person's acknowledgement of a snapshot that is already stored, and `config.baseline_acknowledged` records it with the digest and the one it replaces. An **event baseline** (C10, R4.8) is different: the node's learner writes it when an observation period ends and no person is involved until one acknowledges it. Before this change the chain did not show that such a baseline had been written, or that a re-learn had replaced one. A node that lost or never wrote a baseline left no trace, and the succession of event baselines could be read only from C10 records that pruning can remove.

## The record

`config.baseline_recorded`: written by the node (actor type `node`), outcome `info`, no reason code, a target asset and a `correlation_id`, from contract minor 8. Event baselines only: 0.8 refuses `kind: configuration` here, because nothing writes it (B1, on #346). A later minor adds it with its first writer. Its `config` group has:

| Field | Meaning |
| --- | --- |
| `kind` | `event` |
| `baseline_digest` | the stored record's hash, C10 `Hash` |
| `baseline_version` | new in 0.8; C10's `Version`: 1 exactly when nothing is replaced, otherwise one more than the replaced record's |
| `previous_digest` | the baseline of that asset that this one replaces (C10 `Previous`); absent for the asset's first |

The names reuse the group's existing fields (`kind`, `baseline_digest`, `previous_digest`) so that one reader handles acknowledgements and records alike. B1's list had "digest" and "previous"; they are `baseline_digest` and `previous_digest` here.

## What `Validate` checks

Node actor; info; no reason code; kind `event`; a digest; `previous_digest` is a digest and not the record's own; none of the detection, approval, read or removal fields; a version of 1 or more that is 1 if and only if `previous_digest` is absent. `baseline_version` is refused on every other action.

## What `VerifyConfig` checks

1. **Succession.** Each record names as `previous_digest` the baseline the last one before it in `recs` recorded for the asset, and its version is one more than that record's. With none before it in `recs`, nothing is checked, as for acknowledgements: `recs` may start after the asset's first.
2. **Recorded, then acknowledged (B1, D4-26 item 4 and its amendment).** A succeeded `config.baseline_acknowledged` of kind `event`, stamped 0.8 or later, names the digest that the latest `config.baseline_recorded` of its asset before it in `recs` recorded. `recs` may start partway through the chain, so:
   - with a recording of the asset before the acknowledgement in `recs`, the acknowledgement must name that latest recording's digest. A digest replaced inside the window, one replaced before it, and one the window never recorded are each refused, with a test each;
   - with none before it, the acknowledgement is refused only when `recs` holds the asset's version-1 recording (after it), which shows nothing was recorded before. Otherwise the window starts after the recording and the acknowledgement is accepted, with a test.

   This is a little stricter than the amendment's wording ("refuse only a digest that a recording inside `recs` has replaced"). After any recording of the asset in `recs`, an acknowledgement of a digest that recording did not record is refused even when no recording in `recs` names that digest. That case is provably wrong: the recording in the window replaced the asset's then-current baseline, so the digest acknowledged cannot be current. The test is "not the window's latest recording". C1 rules if the literal wording should stand. An acknowledgement stamped 0.7 or earlier is not held to it (no record existed), a denied one names whatever it was asked to, and a configuration-kind one keeps the 0.6 rule.

**Upgrade consequence for B5.** A node that already holds an event baseline when it upgrades to 0.8 must record it before an acknowledgement of it can be accepted by the chain. B5's start-up repair (below) does that.

## Writing the record (B5)

The baseline lives in the configuration database and the record in the audit database, so one commit step cannot cover both. The node stores the baseline first and then writes the record; every field of the record can be re-derived from the stored baseline. A crash between the two leaves a baseline whose record is missing, and the node writes it at its next start, after folding the chain so that a digest already recorded is not recorded again (a repeat digest breaks the chain). A record without a baseline does not occur. Until the repair, the baseline is not acknowledgeable and health shows "baseline stored, not yet recorded". The node tests both crash points. C8 cannot see the store: this is C5's and B5's.

## `correlation_id` (D4-29)

The recording's `correlation_id` is the 64 hex digits of its `baseline_digest`, without the `sha256:` prefix: C8's ID pattern allows at most 64 characters, and a C10 hash is 71. It is stable across a replay and a restart, and the start-up repair needs no invented ID (B5's proposal). The acknowledgement keeps the signed request's ID, which also joins it to the collector's acceptance. The recording and its acknowledgement join on `baseline_digest`, which both carry. `Validate` refuses any other value, and the schema requires 64 lowercase hex digits (it cannot compare two fields).

## Effects on other work

- **B5 / C5.** As above. A 0.7 reader sees the action as unrecognized (`Normalize`) and keeps the new field as it keeps any field of a later minor (C8-A6-2).
- **B4 / C10.** `baseline_digest` is `baseline.Hash` of the stored bytes, `baseline_version` is `Baseline.Version`, `previous_digest` is `Baseline.Previous`. Nothing in C10 changes.
- **B6.** Fixtures: two valid and ten invalid records under `contracts/audit/testdata`, checked against the schema with an independent validator as well as `Validate`.

## Evidence

Unit tests for every field rule, the succession and the acknowledgement rule (`config_recorded_test.go`). Mutants of the new code, all killed. The schema was checked against all valid fixtures and the new invalid ones with `jsonschema` 4.26. The older invalid fixtures the schema accepts are cross-field rules that JSON Schema cannot state, as before.
