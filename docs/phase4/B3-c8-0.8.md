# C8 0.8: config.baseline_recorded (B3)

Status: proposal for review by B4, B5 and B6, at B1's request. It is a contract change only: it adds one action and one field, and changes no rule of 0.7. Everything here is `desk`: tests use fixtures, and no device has been contacted.

## Why

A configuration baseline starts as a person's acknowledgement of a snapshot that is already stored, and `config.baseline_acknowledged` records it with the digest and the one it replaces. An **event baseline** (C10, R4.8) is different: the node's learner writes it when an observation period ends and no person is involved until one acknowledges it. Before this change the chain did not show that such a baseline had been written, or that a re-learn had replaced one. A node that lost or never wrote a baseline left no trace, and the succession of event baselines could be read only from C10 records that pruning can remove.

## The record

`config.baseline_recorded`: written by the node (actor type `node`), outcome `info`, no reason code, a target asset and a `correlation_id`, from contract minor 8. Its `config` group has:

| Field | Meaning |
| --- | --- |
| `kind` | `event`, or `configuration` for a configuration baseline the node stores as a record of its own |
| `baseline_digest` | the stored baseline record's hash: C10 `Hash`, or C9's digest for a snapshot |
| `previous_digest` | the baseline of that asset and kind that this one replaces (C10 `Previous`); absent for the asset's first |
| `baseline_version` | new in 0.8; `event` only: C10's `Version`, 1 exactly when nothing is replaced, otherwise one more than the replaced record's |

The names reuse the group's existing fields (`kind`, `baseline_digest`, `previous_digest`) so that one reader handles acknowledgements and records alike. B1's list had "digest" and "previous"; they are `baseline_digest` and `previous_digest` here.

A configuration snapshot has no version, so `baseline_version` is refused for `kind: configuration`. It is refused on every other action.

## What `Validate` checks

Node actor; info; no reason code; kind is `event` or `configuration`; a digest; `previous_digest` is a digest and not the record's own; none of the detection, approval, read or removal fields; and for `event`, a version of 1 or more that is 1 if and only if `previous_digest` is absent.

## What `VerifyConfig` checks

Per asset and kind, each record names as `previous_digest` the baseline the last one before it in `recs` recorded, and an event baseline's version is one more than that record's. With none before it in `recs`, nothing is checked, as for acknowledgements: `recs` may start after the asset's first. Two kinds and two assets do not disturb each other.

## Written with the baseline record: both or neither

The node writes the C8 record and the baseline record in one commit step. C8 cannot see the store, so this is C5's and B5's to test. A crash may not leave a stored baseline with no record, or a record with no baseline. The contract helps one way: a repeat of the same digest is refused by `Validate`, so a replay after a crash shows as a broken chain and not as a second baseline.

## Not decided here (for B1, B4, B6)

- **Acknowledgement against a recorded baseline.** I did not add a rule that a `config.baseline_acknowledged` of kind `event` must name a digest the chain recorded. It would turn the D4-20 race (an acknowledgement naming a digest the store no longer has) into a chain break, and it would fail every chain from before 0.8. If B6 wants it, it can apply to acknowledgements stamped 0.8 or later.
- **`kind: configuration`.** Nothing writes it today, because the acknowledgement is the configuration baseline's record. B1's text said "where it applies"; I allowed it, with the same succession rule and no version, so that a later C9 baseline record needs no contract change. If B5 prefers, 0.8 can accept `event` only and add `configuration` when something writes it.
- **`correlation_id`.** Required, as for every configuration action. What it holds for a learner's record (the learning run's ID, or the baseline's own) is B4's and B5's to say.

## Effects on other work

- **B5 / C5.** The node writes this record with the C10 baseline, in the same step, and C5 holds the baseline as before. A 0.7 reader ignores the action (`Normalize` gives `unrecognized`) and the field is inside the group it already reads strictly only for a 0.8 record.
- **B4 / C10.** `baseline_digest` is `baseline.Hash` of the stored bytes, `baseline_version` is `Baseline.Version`, `previous_digest` is `Baseline.Previous`. Nothing in C10 changes.
- **B6.** Fixtures: three valid and nine invalid records under `contracts/audit/testdata`, checked against the schema with an independent validator as well as `Validate`.

## Evidence

Unit tests for every field rule and for the succession (`config_recorded_test.go`). Twelve one-line mutants of the new code, all killed after one test was added. The schema was checked against all valid and invalid fixtures with `jsonschema` 4.26: every valid fixture passes, and every new invalid fixture fails. The six older invalid fixtures the schema accepts are cross-field rules that JSON Schema cannot state, as before.
