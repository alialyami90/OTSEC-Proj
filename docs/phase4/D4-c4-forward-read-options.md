## 1. What the network path judges, and what a forward read can drop

### 1.1 Which C4 kinds the network path judges

The product code calls `event.Decode` in twelve places (`git grep -n "event.Decode(" -- platform modules cmd ':!*_test.go'`). Five are in the network and intake files (`netdetector.go`, `netintake.go`), and two of them lead to a judgement on the network path (D6's F1 on #765 corrected the first version of this table, which named one):

| Reader | C4 kind and type | What it does with the event | Judged? |
| --- | --- | --- | --- |
| `observationOf` (`netdetector.go`), called by `observeTo` and `rebuildFrameIndex` (whose loop keeps a first sight with `node.stored_capture`) | `network-observation` | `event.Decode`, then `netobs.ObservationFromEvent`, then the detector's rules | **Yes** |
| `alertsAfter` (`netdetector.go`) | `telemetry-health`, type `netobs.alert` | `event.Decode`, then `AlertFromEvent`, to hold back alerts a replay raises again | No: an alert records a judgement already made (as in the C13 note, §1) |
| none in the node | `telemetry-health`, type `sensor.counters` | Written by `sensorlink` (`health.go`) and forwarded; no product code reads one back | No |
| `runSessionOf` (`netintake.go`), called by `newSessions` (`netdetector.go`), whose sessions `handOver` gives to `netdetect.Detector.Session` | `telemetry-health`, type `collection.run` | `event.Decode`, then the session is built from `health.type` and `health.details`; `Session` judges it through `judge`, which raises `own-session-unseen` when no tied flow is seen, and `connected` and `open_flow` decide whether it is judged at all | **Yes.** For this record the envelope *is* the session: there is no separate body, so no C13 stamp guards it |
| the two run lookups of the intake's repair (`netintake.go`): `healthNames` and `committedEvents` | `healthNames`: the health stream's `collection.run` and `collection.outcome-unknown`; `committedEvents`: the run's SER events on its SER stream (`collection.invocation_id`) | Find whether a run's record or its SER rows were committed, for the repair | No |

The window of the second reader is the observations' window: a restored detector reads the health stream again from `SessionThrough` (`nd.health`), and from 0 when it was not restored. D6's probe on #765 (`desk`, scratch, not committed): a `collection.run` stamped one C4 minor above `event.Identifier`, with an unknown top-level key and an unknown `health` key, goes through `runSessionOf` with the session built and no error; *control:* the same at 0.5 is refused as `decode`. A `runSessionOf` error is counted as a missing session and not judged (`newSessions` marks the entry `bad`), in memory only, like `observations_refused`.

**Outside the network path, one more reader judges C4 envelopes** (D3's F1 on #765), and the grep above misses it because it does not call `event.Decode`: `eventFeed.read` (`platform/node/eventbaselines_feed.go`) decodes SER, Syslog and health events with plain `json.Unmarshal`, and `take` routes each by `source.asset.id` and `kind` to the event baseline, which judges it and raises departure alarms. After a rollback the restored feed reads again the events after `RestartAfter`, including those a newer build stamped. `json.Unmarshal` drops an unknown key as a forward read does, so the latent fail-open of §1.4 exists for SER and Syslog judgements too. It is safe today for the same reason as §1.4: no C4 minor after 0.2 changed a SER or Syslog envelope field (0.3 added the new kind; 0.4 and 0.5 changed `sensor.counters`). This note does not propose (b) for these kinds ("Not an option" gives the cost of making them strict); §3 condition 3 gives them option (a)'s rule with (d)'s floor clause. That the feed uses `json.Unmarshal` rather than `event.Decode` is D5's code; the store validates every record at commit with `event.Decode`, so it is not a finding here.

So **the network path judges two C4 kinds: `network-observation`**, through `ObservationFromEvent`, **and `collection.run`**, through `runSessionOf` and `Detector.Session`. §1.2 to §1.4 are about `network-observation`; `collection.run` is in §1.5. The options in §2 cover both.

### 1.2 What `ObservationFromEvent` reads from the envelope

`ObservationFromEvent` reads three envelope fields, and the rules read none:

- `kind`: anything but `network-observation` is refused as `type`.
- `source.asset.id` and `flags`: checked against the body's `node.dst_asset` (C13 §5). An unresolved destination needs no asset and the flag `asset-unresolved`; a resolved one needs the asset to equal `dst_asset`. Either mismatch is refused as `conflict`.
- `netobs`: handed to `DecodeStored`.

`observationOf` returns only the `*netobs.Observation`. The detector's rules, the frame index and the learner see the body, never the envelope. `Link.record` builds the envelope from the body (`source.asset` from `node.dst_asset`, the flag from `AssetUnresolved`), so today the envelope repeats the body and adds nothing a rule depends on.

### 1.3 What a forward read of a later C4 minor drops

`event.Decode` reads an event of a later 0.x minor with `strictjson.Forward`, which ignores a key that is not a field name and still refuses duplicates and case variants (`Decode`'s comment; D1-10). Read from the code:

- **Inside `netobs`, nothing is dropped.** `Event.Netobs` is a `json.RawMessage`. In `checker.check` it is neither a struct nor a map, so its object's keys are walked as `any` and none is refused or dropped, and `encoding/json` copies the raw bytes. The body therefore reaches `DecodeStored` whole, where C13's (b) decides it.
- **In the envelope, any key the reader's `Event` type lacks is dropped:** a new top-level key, or a new key in `source`, `source.asset`, `source.asset.binding` or `received`.
- **A new value in an open set is kept but not understood.** `flags` is open (`KnownFlags`; `checkFlag` checks only the token form), and `kind` is open. A later minor's flag value passes any reader's `Validate`, and `ObservationFromEvent` ignores every flag but `asset-unresolved`.
- **What fails closed already.** A new `binding.method` or `binding.confidence` value is refused by `checkAsset` and `checkObservedAddress` (closed sets). A later minor that moved the body out of `netobs` would fail `checkNetobs` (`missing`). A new kind for observations would fail `ObservationFromEvent` (`type`). Each of these is refused at judging, and the replay counts it under `observations_refused`. The first two fail inside `event.Decode` (its `Validate`), so they never reach `ObservationFromEvent`, and on `main` they read as a decode error (D5's F1 on #765); §2 (b) makes them read as a later minor.
- **A held record's `received` fails closed at the sensor's start** (D6's F5 on #765). Each held record keeps a C4 `event.Received` (`HeldRecord.Received`) inside the `otsec.netcheckpoint.intake/0.1` record, and `decodeIntake` reads that record with `decodeExact`, which refuses an unknown field. D6's probe (`desk`, scratch): a held record whose `received` has one added key makes `decodeIntake` fail with "unknown field", `loadIntake` returns the error, and `startSensor` fails. So while the stream holds an intake record a newer build wrote, a C4 minor that adds a key to `received` (or `clock`) stops an older build's sensor start. That fails closed and loud, it is outside every option here, and no option changes it; §3 condition 3 makes each later minor state it.

### 1.4 Whether a dropped key can change a judgement

- **Today, no.** C4 0.4 and 0.5 changed only `sensor.counters` (C4-0.4-1 to -3, C4-0.5-1 to -3, `contracts/event/doc.go`); no rule of `network-observation` changed after 0.3. Nothing in §1.2 depends on a key that 0.4 or 0.5 added. So every build on `main` reads a stored 0.5 network-observation event the way it would read the same event at its own minor (`TestCCD2ForwardE47` and `TestCCD0E47StoredEvents` show the decode, not the judgement).
- **Later, yes.** The fail-open is latent: it opens the first time a C4 minor puts something a rule should respect into the envelope of a `network-observation` event, rather than into the C13 body. Two forms of that change read less restrictively to an older build:
  1. **A dropped key**, for example an envelope key saying the body is partial, redacted or superseded, or a second asset reference that the asset check must also match.
  2. **An ignored flag value** with the same meaning, for example a flag that marks the observation as not to be judged as complete.

  In both, the older build judges the observation as if the qualifier were not there. C13's (b) does not stop it, because the body's own `schema` is still within the reader's C13 minor.
- **Which records.** A narrower window than C13's §1. C13's window has two parts: the stored observations after the detector's restored `Through`, which `observeTo` replays after a rollback (and which `rebuildFrameIndex` reads for first sights at or below `Through`), and the held records, which the older build commits and then judges. C4's window is the first part only. **Held records are not in it:** `Link.record` builds the envelope when it commits, with `event.Identifier`, so a held record released by an older build carries the older build's C4 minor, and only its body can be of a later minor (C13 (b) then decides).
- **The reading that 0.4 and 0.5 left the envelope unchanged is `desk`** (D7's N2 on #765): it is read from `doc.go` and from D6's diff of `contracts/event` from `c9d4d6c8` (the last 0.3 commit) to `5938aec8`, which touches only `checkSensorCounters`, the counter constants and `self`/`Identifier`. It is a per-minor judgement of option (a)'s kind, and no test checks it.
- **Why C4 moves separately.** `Identifier` is one constant (`doc.go`, 0.4 and 0.5 entries), so every C4 minor restamps every event the node writes, `network-observation` included, even when it changes only `sensor.counters`. `network-observation` entered at C4 0.3, beside C13 0.1. Since then each has moved two minors, not in step: C4 0.4 came with C13 0.2 (D4-92), C13 0.3 came without a C4 minor (D4-102), and C4 0.5 came without a C13 minor (#755).

### 1.5 `collection.run` on the network path

What §1.3 says of the envelope holds for a `collection.run` event, with one difference: its judged content is in the envelope (`health.type`, `health.details`), so a forward read that drops a key drops it from the judged record itself, and no C13 stamp stands behind it. Today nothing changes: no C4 minor after 0.2 changed the `health` envelope's fields. Later, a C4 minor that adds a `health` key or an envelope qualifier that `Session` should respect would read less restrictively to an older build, as in §1.4. The window is the replay of the health stream after `SessionThrough`; a run whose record the older build writes itself is stamped with its own minor.

`health.details` is an open map whose keys the node defines (`sessionDetails`, D5's), not C4. A detail key that a later node build adds is kept but not understood whatever the C4 minor, the same class as §1.3's flags (D6's F1 on #765). No C4 option reaches it; §3 names it as a residual.

## 2. The options

Each option answers the same points: whether it closes the fail-open; its cost to readers; the sensor; its tests with controls and mutants; its effect on the `docs/release.md` §7.1 floors and AP-10; and when it must land. "The hand install" (a build installed by hand below the mechanism) is the residual of every option, as in the C13 note, and AP-10 does not stop it either.

### (a) A per-key statement in each later C4 minor

Each C4 minor states, for the `network-observation` envelope and the `collection.run` record (§1.5), each key and flag value it adds and what a forward-reading build does with it. One that reads less restrictively is not added as an ignorable key: it goes into the C13 body (where C13's (b) refuses it), or into a closed set an older reader already checks, or the minor takes a §7.1 floor at its first reader.

- **Closes it?** Only by review, minor by minor. Nothing checks the statement. The C13 note rejected this for C13 because §15.8 (b)'s "would refuse" was wrong for seven builds and was found by a probe, not by review (D6's finding 1 on #762).
- **Readers.** No code change; a harmless C4 minor costs nothing after a rollback. That matters more for C4 than for C13, since C4 restamps every event (§1.4).
- **The sensor.** None. The sensor writes the C13 body; the node writes the C4 envelope.
- **Tests.** Per minor, D6's old-reader leg with the previous release as reader: `ObservationFromEvent` over each new envelope key's event, asserting refusal or a stated harmless drop. *Control:* a key stated as refused, read by a reader patched to drop it, fails the leg. It proves each minor's statement, not that the next minor has one.
- **Floors and AP-10.** None of its own; a minor that cannot be made harmless takes a floor held by `docs/release.md` until AP-10 exists.
- **When.** A text rule in C4 and a line in `docs/release.md` §7.2's "Rules that will add rows", before the next C4 minor is approved.

### (b) The network path refuses a later C4 minor's `network-observation` and `collection.run`

`ObservationFromEvent` refuses a `network-observation` event whose `schema` is a later C4 minor than the reader's own, after its `kind` check and before `DecodeStored`. `runSessionOf` refuses a `collection.run` event of a later C4 minor in the same way, before it builds the session (D6's F1 on #765). `event.Decode` is unchanged, so SER, Syslog, other health and alert events keep their forward read (`docs/release.md` §7.2, the C4 0.4 row).

- **The check.** One exported function in `contracts/netobs` (D4's), which takes an event and returns the refusal below or nil, and an unexported helper under it that takes the event's `schema` and the reader's C4 minor as arguments (D6's F3). The exported function passes C4's own minor, taken from `event.Identifier`, never C13's `self`. Its callers:
  - `ObservationFromEvent` (D4), after its `kind` check and before `DecodeStored`.
  - `observationOf` (D5), on the path where `event.Decode` returns an error **and** a non-nil event: `Decode` reads a later minor forward and then returns `&e, e.Validate()`, so a later-C4 event that `Validate` refuses (a new `binding.method` or `binding.confidence`, a body moved out of `netobs`, §1.3) is checked for its stamp, and a later stamp is refused with `ErrLaterMinor` ahead of the `Validate` error (D5's F1 on #765, option 1). An event that `Decode` refuses before `Validate` (a duplicate key or a case variant, refused by `strictjson.Forward` itself) returns no event and stays a decode error.
  - `runSessionOf` (D5), after `event.Decode` and on the same non-nil-event error path, before the session is built. A refusal there is an error, so `newSessions` marks the entry `bad` and the session is counted missing and not judged, as any `runSessionOf` error is today. **Its order** (D5's N1 on #765, 7011296411), on both decode paths (no error, and an error with a non-nil event):
    1. `health.type == collection.run` first. A record of another type is no session (`ok` false, no error), whatever its stamp, so a later-minor `sensor.counters` or other health record is not counted as a missing session. An error with no event stays an error, as today.
    2. Then the stamp check. A later-C4 run is refused here, before the `after_seq` test, so a later run whose minor renamed or moved `after_seq` is counted as a refused session, not read as "no session".
    3. Then the `after_seq` test and the session's fields, as today.
- **The refusal.** A `*netobs.Error` with `Code: CodeSchema` and `Field: "schema"` (the event's), for which `errors.Is(err, netobs.ErrLaterMinor)` holds: the same sentinel as C13's (b), so D5's `later-minor` reason counts both. The node tells the two stamps apart by `Field`, never by the detail (D5's 7010817086; the OS-log rule): `schema` for C4, `netobs.schema` for C13. That split does not exist on `main` (D4's F1 on #766): `DecodeStored` reports the body's own stamp as `Field: "schema"`. So in (b)'s code `ObservationFromEvent` prefixes every `Field` that `DecodeStored` returns with `netobs.`, and returns a later-minor refusal alone, never inside an `errors.Join`, so the error the node matches with `errors.Is(ErrLaterMinor)` is the one whose `Field` it reads. A later C4 event with an unknown envelope key is refused as `schema` too, because `event.Decode` has already read it forward.
- **A schema the check cannot read** (D6's F4 on #765): an empty or unparseable `schema`, another name or another major is refused as `schema` (`CodeSchema`, not `ErrLaterMinor`). It fails closed. A product event reaches the check only through `event.Decode`, which already refuses each of these, so the choice changes no product path; it changes one test, listed below.
- **Closes it?** Yes, in code, for every build that carries it and every later C4 minor, with no per-key review: a later `network-observation` envelope or `collection.run` record is never judged with a key dropped or a flag misunderstood. It does not reach a node-defined detail key in `collection.run` (§1.5) or the event baseline's feed (§1.1); §3 names both.
- **Readers.** After a rollback across any C4 minor, every network observation and every `collection.run` session of the newer C4 minor still to be judged is refused, even when that minor changed only `sensor.counters`, as 0.4 and 0.5 did. That is the cost of `Identifier` being one constant. It falls on the same replay window as the fail-open and as C13's (b) (§1.4, and §1.5 for the health stream); held records are outside it. A refused first sight drops out of `rebuildFrameIndex`, and an alert citing its frames counts them under `frames_missing`, as under C13's (b). A refused session raises no `own-session-unseen` for its run.
- **The loss outlasts the rollback** (D7's N1 on #765). `observeTo` counts a refused observation under `Refused` and `Detector.Observe` still takes its seq, so `Through` passes it and the next checkpoint stores that `Through`; `nd.health` passes a `bad` session entry the same way. A node moved forward again restores past those records and never judges them. So the cost of a rollback across any C4 minor is: the replay window's network observations and sessions are refused and alarmed while rolled back, **and never judged afterwards**. `docs/release.md` §7.1 already records the same for the C13 §15 floor (D3's F1 on #762). **D5's condition 1 does not change this:** #766 at `e87cf561` makes the refusal durable and alarmed (a count and a seq range per reason on the health stream), and states that a refused record is not judged again and is pruned at the next checkpoint. It makes the loss visible after a restart; it does not recover it. Holding refused records for a later judgement would be a new store mechanism, which neither note proposes.
- **Its condition.** Refused is still unjudged, so (b) needs the same condition as C13's (b): D5's durable, alarmed refusal (`network-observation-refused`, D1's 7001264083 item 4) lands with it or before it. For `collection.run` the refusal is counted today only as a missing session, in memory; the same condition covers it, so #766's counts must include a session refused as a later minor, or D1 records it as an open item.
- **The sensor.** None.
- **Tests.**
  - Contract (`contracts/netobs`, D4): a `network-observation` event stamped one C4 minor above `event.Identifier`'s, computed from it and not written as `0.6` (self-check item 11), with a body at C13's `self` and no unknown key, is refused as `schema` with `ErrLaterMinor`. *Mutant:* the refusal removed, which accepts it. The same event with an unknown key at the top level and in `source.asset` is refused as `schema`, not `decode`. *Control:* the same event at `event.Identifier` is accepted. *Mutant:* the comparison made `>=`, which refuses the control. *Mutant:* the comparison made against C13's `self` instead of C4's.
  - That last mutant is killed only while the two minors differ (D6's F3 on #765): when C4's minor equals C13's `self`, both comparisons agree on the refusal case and on the control, and the mutant survives without notice. So (b) tests the comparison twice. The helper is tested with a reader minor passed in that differs from both C4's and C13's current minors, over below, equal and above; *mutant:* `>=`, and an off-by-one on the minor, each killed. And a guard test fails, with a message naming this mutant, when `event.Identifier`'s minor equals C13's `self`, so the exported function's test is never silently vacuous (0.5 against 0.3 today).
  - Contract, the `Validate` path (D4; D5's F1 on #765): a `network-observation` event one C4 minor later with an unknown `binding.method`: `event.Decode` returns a non-nil event and an error, and the exported check on that event returns `ErrLaterMinor` with `Field: "schema"`. *Control:* the same event at `event.Identifier`: `Decode` returns its error, and the check returns nil, so the node keeps the decode error. *Mutant:* `Decode` returning nil on a `Validate` error, which fails the test (it pins the behaviour the node's call relies on).
  - Contract, the schema the check cannot read (D4; D6's F4): an event with no `schema`, with an unparseable one, with another name and with another major is refused as `schema`, without `ErrLaterMinor`. *Mutant:* an unparseable schema accepted.
  - Contract, the `Field` split (D4; D4's F1 on #766): a later-C13 body in a current-C4 envelope is refused with `Field: "netobs.schema"`, and the error is not a join. *Mutant:* the prefix removed.
  - Placement controls (D4): a SER, a Syslog and a `netobs.alert` event one C4 minor later still pass `event.Decode`, and the alert still passes `AlertFromEvent`. *Mutant:* the refusal moved into `event.Decode` or `Event.Validate`, which refuses them; `TestCCD2ForwardE47` and `TestCCD0E47StoredEvents` (`tests/contract`, D6's) would fail too.

A third leg (D5's F1): a replayed later-C4 observation with an unknown `binding.method` is counted under `later-minor`; *control:* the same event at `event.Identifier` is counted under `malformed`. A `collection.run` leg (D6's F1): a replayed later-C4 run is not handed to `Detector.Session`, raises no `own-session-unseen`, and is counted; *control:* the same run at the node's own minor is judged.
