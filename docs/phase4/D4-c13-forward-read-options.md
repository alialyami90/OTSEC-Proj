# C13: how a build reads a later minor's stored record (options)

**Status: approved, option (b), by D1 (D4-120 item 2.2; 7010466389 on #763).** Owner D4. This is the open item of D1's ruling 7001264083 on #760, item 3 (D4-120 item 2.1): options before the next C13 minor and before P4-4-DE, under D4-99 (a new mechanism is settled as options first). No code is changed here.

**Evidence class: `desk`.** First read at `main` `2dde13b6`; revised to the four reviews on #763 (D7's 7009756281, D5's 7009772447, D3's 7009793907, D6's 7010191380) and re-read at `main` `1d49f54a`, where `DecodeStored`, `DecodeBaseline`, `storedSchema` and `validateStored` are as at `2dde13b6`. The forward-read results cited are D4's probe (7001201557 on #760) and D6's (7001254947 on #760, 7001107395 on #762, 7010191380 on #763), all scratch tests on the owner's PC that were not committed. Nothing in this note was run.

## 1. The problem

- **What reads forward.**
  - **Stored observations,** by `DecodeStored` (`contracts/netobs/observation.go`; `storedSchema` sets `c.later`). It uses `strictjson.Forward`, which drops a key the reader does not know. That is by design: contracts/README.md ("Readers accept every minor of their own major and ignore fields they do not know", under "Identifiers and compatibility") and D1-10 (`strictjson.Forward`), and C13 0.2's CH-35 ("forward for a later one").
  - **Held records,** by the link's release of a held observation (`Link.record`, `platform/sensorlink/link.go`; CH-35 bridge item 5). It decodes with `encoding/json`, checks no schema, takes the event's asset from the record's `node`, and commits the raw body; `tieBody` keeps every key. D6's probe (7010191380 finding 2): a held end restamped and given `x_later_key` at the top level and in `node` is committed with the key kept, at 0.4, at 1.0 and with the schema `not-a-schema`. The link judges nothing: the record is judged later through `DecodeStored`, which reads the 0.4 record forward and refuses the other two.
- **What does not.**
  - **Network baselines.** `DecodeBaseline` (`contracts/netobs/baseline.go`) reads a later `otsec.netbaseline/` minor forward, but every caller that judges or adopts a baseline pairs it with `IsCanonical`, which decodes strictly: `NewDetector`, `LearnerCheckpoint.Validate` (and so `RestoreLearner`), netack's `Adopt` and `BuildAccepted`, and `OnlyWritersAdded` (D6's finding 1 on #763). D6's probe, netbaseline 0.2: with a key this build does not know, at the top level or inside `period`, `NewDetector` refuses it ("the baseline is not in canonical encoding") and so does the learner's restore; with no new key it is accepted with nothing dropped. The only forward reader left is netack's `DraftFill`, which has no caller outside netack on `main`, and a draft it shows still fails `Adopt`. So **there is no baseline fail-open today.** What a later baseline costs is in "Where it bites".
  - **Checkpoints.** Both network checkpoints decode strictly at every minor (`DecodeLearnerCheckpoint`, `DecodeDetectorCheckpoint`), and a detector checkpoint of a minor the node cannot read goes through CH-35's bridge items 1 and 2.
  - **Alerts.** A stored alert of a later minor is read forward through bridge items 3 and 4 (`AlertFromHealth`); an alert records a judgement already made and is not judged again, so it is outside this note.
  - **The channel.** `DecodeChannel` and `DecodeFromSensorIn` read only the schema with `Forward`, then decode strictly; `DecodeFromNode` is strict (D6 on #763, "What held").
- **The fail-open.** A later minor that adds a key whose absence reads less restrictively (a key a rule, the learner or a coverage check depends on) is dropped without a word by every build below it, and the stored observation is judged as if the key were not there. §15 of the C13 0.3 proposal showed the case: at `26545062`, a 0.3 record's `objects_unread` and `inner_vlans` are dropped (D6's finding 1 on #762). The same probe shows a record stamped **0.4** read forward with both keys dropped at `2dde13b6` and at `26545062` (D4's 7001201557). At #760's head `57048382` both keys are 0.3 keys that #760 reads; there D6's probe dropped `x_later_key` in `function`, a key #760 does not know (D6's 7001254947). So #760 and every build after it does the same to the next minor's keys (D3's 7001225871 condition 2; D6's 7001254947 point 4).
- **Where it bites (read from code, not measured).**
  - **Stored observations:** those after the detector's restored `Through`, replayed by `observeTo` (`platform/node/netdetector.go`), and the stored-capture lookup that also calls `observationOf`. Records the newer build judged before it stopped are not judged again. How many a real rollback leaves unjudged depends on how the newer build stopped, and is not measured.
  - **Held records:** the newer build never judged them. After a rollback, the older build commits every held record of the newer minor and judges it, so each one is in the window above.
  - **Baselines (a cost, not a fail-open, on every build):** after a rollback across a `netbaseline` minor that adds a key, `NewDetector` refuses the approved baseline as not canonical and detection stops until a baseline the older build reads is approved. It is latent today: `detectorConfig` sets no `DetectorConfig.Baseline`, so `NewDetector` always takes the no-baseline branch (D5's 7009772447 point 1). Once a baseline is wired, the trace is D5's: `startDetector` raises `network-detector-not-restored` (whose text, "starts again from the oldest retained observation", is then false) at every tick, `tickSensor` raises `network-detector-not-started` once per stretch, neither has a health event or names the cause, and the observation stream is not pruned while the detector is down. That is §3's condition 3, owed whichever option is chosen.
- **Which builds.** Every build on `main` today reads a later stored observation forward. None has been released (`docs/release.md` §7.3, §7.4), so no released build carries the fail-open yet. Any mechanism in a build protects only from that build on: a build cannot refuse on a check it does not carry (D3's 7001225871). So whichever option is chosen must be in **every released build**, which means it lands before the first release, and every build below it leaves the rollback set by a `docs/release.md` §7.1 floor (§3, condition 6).
- **What no option here stops.** A hand install of an old commit, which AP-10's signed floor does not stop either (D3's 7001225871; D6's 7001254947 point 3). That residual is named in each option's row as "the hand install".
- **C4, owed separately (D3's F4 on #763).** Every stored observation reaches `DecodeStored` only through `observationOf`, which calls `event.Decode` first, and `event.Decode` reads a later C4 minor forward (`contracts/event/decode.go`). `ObservationFromEvent` judges from the envelope: `kind`, `source.asset` and `flags`. C4 and C13 move separately (C4 0.5 merged in #755 while C13 stayed at 0.3), so nothing here stops a later C4 minor from changing what that envelope says to an older build. Making all of C4 strict is too broad: SER and Syslog depend on C4's forward read (`docs/release.md` §7.2, the C4 0.4 row). §7.2's per-key rule for C4 is option (a), which this note rejects for C13 because nothing checks it. So this is **an open item, owner D4**: options before the next C4 minor that adds or changes a field read on the network-observation or sensor-health paths, and before P4-4-DE. The narrow candidate is (b)'s rule on those kinds only: `ObservationFromEvent` refuses an event stamped above C4's `self`. D1 records it in D4-120.

## 2. The options

Each option is answered on the same five points: does it close the fail-open for records written by a newer build; what it costs readers; what it costs the sensor; which tests prove it; when it must land. Each option's tests include D6's old-reader leg (D1's 7001264083 item 7); under every option, its readers R1 (#760's first parent) and R2 (`26545062`) keep their §15 cases, which predate every option (D6's 7010191380).

### (a) A per-key statement in each later minor

Each C13 minor states, key by key and value by value, what a forward-reading build does with it (drops the key; refuses a new value in a closed set, as it refused `sa: unknown`) and whether the record then reads less restrictively. A key that does is not added as an ignorable key: it is carried in a form every reader in the rollback set refuses (a new value of a closed set the older reader already checks, or a new major), or the minor takes a `docs/release.md` §7.1 floor at its first strict reader.

- **Closes it?** Only by review, minor by minor. Nothing in code checks the statement. §15.8 (b)'s "would refuse" was wrong for seven builds and was found by D6's probe, not by review (D6's finding 1 on #762), so this is exactly the mistake the option relies on people not making. A floor taken under it holds only by the release record until AP-10 is built (`docs/release.md` §7.3).
- **Readers.** No code change. A harmless key stays harmless after a rollback (CH-35's purpose).
- **The sensor.** None. Which keys the sensor emits is fixed by the minor.
- **Tests.** Per minor, the old-reader leg with the previous release as the reader: `DecodeStored` over each new key's record, asserting refusal or a stated harmless drop. *Controls:* for a "refused" key, a reader patched to read that key forward fails the leg; for a "harmless drop", the same key at the reader's own minor is refused as `decode`. It proves each minor's statement, not that the next minor will have one.
- **When.** A text rule in C13, before the next minor is approved. It costs every later minor a review that `docs/release.md` §7.2's "Rules that will add rows" already partly asks for.

### (b) `DecodeStored` refuses any later minor

C13's stored observation declares itself strict, as contracts/README.md allows ("A contract may declare itself strict"; C7's requests are). A stored observation of a minor above the reader's own is refused as `schema`; earlier minors are read strictly, as now. The precedent is D4-61: the node refuses an `otsec.finding/` minor that `finding.Known` does not name, per asset, with an alarm.

- **Where the refusal goes.** In `validateStored`, after `storedSchema`, on the stored observation's path only. Not in `storedSchema`, which `Alert.Validate` shares: there it would refuse every later-minor alert too (D6's finding 3 on #763; V3 failed `TestAlertFromHealthStrict`, `TestBridgeAggregateKeys`, `TestMismatchRule` and `TestC13v02T9Aggregate`, and would fail `TestDetectorBridgeLaterRecords`'s alert leg). Stored alerts stay read forward, bridge items 3 and 4 unchanged. `DecodeStored`'s first decode stays `strictjson.Forward`, so a later record is refused as `schema` whether or not it carries a key this build does not know, not as `decode`; its strict decode of a record at or below `self` is unchanged.
- **A checkable refusal (D5's point 3).** The refusal is a `*netobs.Error` with `Code: CodeSchema` for which `errors.Is(err, netobs.ErrLaterMinor)` holds, so the node can count it by reason. The closed `Code` set is unchanged; the contract test pins the sentinel.
- **Baselines are not part of (b) (D6's finding 1 on #763).** `IsCanonical` already refuses, on every path that judges or adopts a baseline, every later baseline a forward read would lose a key from (§1). Refusing in `DecodeBaseline` too would add only a `schema` code in place of "not canonical", and the refusal of a later baseline with no new key, which is read safely today; that refusal would turn the detector off after a rollback where today it judges correctly. D6's V2a (the refusal in `DecodeBaseline`) failed no test. So `DecodeBaseline` stays as it is. The cause of a refused baseline is named by condition 3's alarm, not by a contract sentinel.
- **Closes it?** Yes, for every build that carries it and every later minor, with no per-key review: a later stored observation is refused, never judged with keys missing. A held record is still committed by `Link.record` as held, with its raw body, and refused at judging, so the evidence is kept and the refusal is counted (condition 1). Refused is still unjudged (D3's F1 on #762, 7000973154): without D5's open item (D1's 7001264083 item 4, a durable, alarmed refusal) a refusal shows only as the in-memory `observations_refused`, which breaks P5. **So (b) needs that item to land with it or before it.**
- **Readers.**
  - After a rollback across a C13 minor, every stored observation of the newer minor still to be judged is refused, harmless keys or not. It is the same set the fail-open reaches (§1), held records included, so the loss is bounded by the same window.
  - `rebuildFrameIndex` also skips a refused first sight; an alert that cites its frames counts them under `frames_missing`, so that loss is visible (D3 on #763).
  - The link's own check is not affected: `Link.observe` calls `ValidateStored` on each record it builds from the channel, and the channel admits only minors the node lists (`channelIdentifiers`), none above `self`.
  - It reverses CH-35's "forward for a later one" for the stored observation. Bridge item 4 (an unknown `coverage.degraded` value read as degraded) then no longer reaches a stored observation; it stays for alerts.
- **The learner (D7's N1; D3's F3).** A build that carries (b) cannot learn from a forward-read record, provided the network learner is fed stored observations only through `DecodeStored`: the record is refused before the learner sees it. No build below (b) runs the network learner in the node (no `netdetect.NewLearner` or `RestoreLearner` in `platform/` or `cmd/` at `1d49f54a`; D4's 7001396105). So a learner checkpoint needs no stamp of the build that wrote it, if the learner is wired after (b) merges (condition 5).
- **The sensor.** None. The channel is strict already: a sensor whose minor the node does not list fails the hello (`channelIdentifiers`), and its records wait in its buffer (CH-20). The upgrade order in `docs/release.md` §7.2 (node first, sensor second) is unchanged.
- **Tests.**
  - Contract (`contracts/netobs`, D4): a stored observation stamped one minor above `self`, with no unknown key, is refused as `schema` with `ErrLaterMinor`; the minor is computed from `self`, not written as `0.4`, so the test does not break at the next minor (self-check item 11). *Mutant:* the later-minor refusal removed, which accepts it. The same record with an unknown key is refused as `schema` with `ErrLaterMinor`, not as `decode`. *Mutant:* `DecodeStored`'s first decode made strict, which refuses it as `decode`. *Control:* the same record at `self` is accepted. A stored alert one minor above `self` is still read. *Mutant:* the refusal placed in `storedSchema`, which refuses it. Restoring "the forward branch" is not a separate mutant: after the change a later record still takes the forward decode, only to reach the refusal; reading it forward without refusal is the first mutant.
  - Node (D5): a replayed later-minor observation is refused, counted under reason `later-minor`, raises `network-observation-refused` once, and the count survives a restart. *Mutant:* the alarm removed. *Control:* the same record at `self` is judged and not counted.
  - Link (D5): a held record of a later minor is committed as held and then refused at judging under `later-minor`. *Control:* a held record at `self` is judged.
  - Tests that assert the forward read today change, each reviewed by its owner: `TestStoredRoundTrip`, `TestFlowEnd03Minors` and `TestBridgeUnknownDegraded`'s stored leg (`contracts/netobs`); `TestDetectorBridgeLaterRecords`'s observation leg (D5's, `platform/node/netbridge_test.go`; its `AlertsUnreadable == 0` alert leg stays); `TestC13v02R2StoredReader` (D6's, `tests/contract`). D6 ran the placement (V1, the refusal in `validateStored`) and exactly the three in `contracts/netobs` and `TestC13v02R2StoredReader` failed; `TestDetectorBridgeLaterRecords` is read from code (`platform/node` not run); nothing in `netdetect` or `netack` failed, nor in `sensorlink` run filtered to `Later|Bridge|HoldTie`. Not affected: `TestCCD3N12StoredEnd03` (it runs the 0.3 reader, its own minor) and `TestAcceptedDiffersOnlyInWriters`'s "another minor" case (`reminor`), which reads `IsCanonical`; it would fail only if a refusal went into `Baseline.Validate` (D6's V2b), which (b) does not do. D4 changing another role's test needs D1's authorization under CLAUDE.md §5.3, as for #755 (D4-119 item 2.7).
  - Old-reader leg (D6): add R3, the commit that lands (b). It reads the head's record restamped to R3's minor + 1, with and without an unknown key; each is refused as `schema`. *Control:* the same record at R3's own minor, accepted. The leg's own control: R3 with the refusal removed, which must fail. From the next C13 minor on, R3 reads the producer's bytes without a restamp.
- **When.** Before the next C13 minor is approved, so its §7.1 row states "refused, alarmed" as the rollback cost, and before P4-4-DE (D1's item 3). In any case before the first release.

### (c) A node-side floor stamped in the store

The node writes a key in the store's `meta` table (for example the lowest C13 minor a reader needs), in the same transaction as the first record that needs it. At start, the network detector compares the stamp with its own `self`, and if the stamp is higher it does not restore or judge, and raises an alarm; collection and SER forwarding go on, as under D4-61.

- **Closes it?** Yes, for builds that carry the check. An older build ignores an unknown `meta` key: the store compares only `format`, `node_id` and `database` (`platform/store/db.go`; D6 confirmed on #763). Bumping the store's `format` instead would refuse the whole store, SER included, which is too broad.
- **How it relates to AP-10.** AP-10 is checked by the newer build, against an update package, before the downgrade is installed. Its anti-rollback floor is not designed, and its three refusals have no code and no test (`docs/release.md` §5 item 4); nothing on a node enforces a floor yet, and no OTSEC build has been released (`docs/release.md` §7.3). (c) is checked by the older build, from the data, after the downgrade, and also covers a hand install of any build that carries it. They complement each other. Neither binds a build that predates it.
- **Readers.** Coarser than (b): a stamp turns off all judging on the node, not only the later records. A stamp has to be cleared when no record needing it remains, which needs retention to be tracked, or it stays until an operator acts. It adds a writer duty and a transactional ordering in `platform/` (D5's code).
- **The sensor.** None.
- **Tests.** Store and node (D5's): a stamp above `self` leaves the detector off with the alarm while SER continues; *control:* an equal stamp starts it. A crash test between the stamp and the first record shows that neither commits without the other. D6's old-reader leg cannot test it, because the leg runs `DecodeStored` at contract level and (c) is checked at node start; the proof is D5's node tests, or a node-level leg.
- **When.** Before the first release, and before the first writer that needs the stamp.

### (d) A per-record reader floor

The writer marks only the records that need it: a stored key, for example the lowest minor that may read the record forward, set by the node when the record carries a key whose absence reads less restrictively. A reader that carries the check refuses a record whose floor is above its own minor and reads every other later record forward.

- **Closes it?** Yes, for builds that carry the check, and only for keys the writer is told to mark. Which keys need marking is (a)'s per-key judgement, made once in code instead of once in text, with the same chance of being wrong.
- **Readers.** Refuses only what matters, so harmless keys survive a rollback. That precision saves records only inside the same small window (b) refuses (§1).
- **The sensor.** None, if the node sets the floor at intake.
- **Tests.** Contract: a later record with a floor above `self` is refused, the same record without the floor is read forward; *mutant:* the floor ignored. Old-reader leg: R3 is the commit that lands (d); the head's record with its floor above R3 is refused, without the floor it is read forward. Plus (a)'s per-minor rows for each marked key.
- **When.** Before the first release, and the reader check before the first minor that sets the floor.

### (e) A new major for each such change

A change that adds a key the detector depends on is a new major (C13 1.0). Every build on `main` refuses another major already at `DecodeStored` (`self.Accepts` in `storedSchema`), so this binds today's builds too, the seven forward-reading ones included (D4's probe: a 1.0 record is refused at `2dde13b6` and `26545062`). It does not bind at the link: `Link.record` commits a held 1.0 record, which is then refused at judging (D6's finding 2 on #763).

- **Closes it?** Yes, by refusal, for every build. Refused is still unjudged (D3's F1 on #762, 7000973154), so it needs D5's open item as (b) does.
- **Readers.** A major across every netobs reader: alerts, checkpoints, the bridge, the 0.2 alert stamp and C4's `netobs` path, with a migration note and every consumer's review (contracts/README.md). D4's option (c) in 7001201557 costed it as the largest change.
- **The sensor.** A new major on the channel and a new hello.
- **Tests.** Every netobs test at the new major. Old-reader leg: R1 and R2 each read a restamped 1.0 record and refuse it. *Control:* the same record at 0.x is accepted by the same reader. The leg does not cover the link committing a held 1.0 record.
- **When.** At each such change. Its only advantage over (b) is binding builds that were never released.

## 3. Recommendation: (b), with its conditions

D7 and D3 accept (b) (7009756281, 7009793907); D5 finds it buildable on the node (7009772447); D6 agrees with its direction for stored observations (7010191380). No review changes the recommendation. The one change from the first head is that baselines leave (b) (§2 (b), D6's finding 1).

- **Why (b).** It is the only option that closes the fail-open in code, for every later minor, without relying on a per-key judgement that has already been wrong once (§15.8 (b)). The change is small: `validateStored` refuses a later minor with `ErrLaterMinor`, on the stored observation's path only. The project already chose refusal over forward reading for a form whose loss misjudges (D4-61). Its cost, refusing harmless keys after a rollback, falls on the same replay window as the fail-open (§1).
- **Its conditions.**
  1. **D5's open item (7001264083 item 4) lands with it or before it,** so a refused stored record is durable and alarmed, not only an in-memory count (P5). D5's design, settled as options first in a D5 note (D4-99): an alarm `network-observation-refused`, raised once per run and reason, with the count, in status and as a health event; reasons at least `later-minor`, `malformed` and `detector-refused`; counts by reason on the health stream in the B3 drop-count pattern (#597), restored at start, in preference to a detector-checkpoint key, which would cost a C13 minor.
  2. **C13's text declares the stored observation strict,** with `ErrLaterMinor`, and states that CH-35's forward read is superseded for the stored observation (not for alerts or baselines); the change goes through D1 as a contract change, reviewed by D5, D6 and D3.
  3. **A refused baseline is alarmed (owed today, whichever option).** D5's alarm `network-baseline-refused`, raised once until it clears, naming the baseline's hash and its stamped `schema`, and whether it was refused as written by a later `netbaseline` minor (stamped above `baselineSelf`) or as malformed, with a health event; `network-detector-not-restored` is not raised when the cause is the baseline. `NewDetector` (D4's code) classifies the refusal for it. It lands no later than the first change that puts a baseline into `detectorConfig`. **D1's ruling (7010372954, to be recorded in D4-120): the detector stays off while the baseline is refused**, and the stream stays unpruned; it does not run the baseline-free rules, which would move `Through` past records never judged against the approved baseline while alerts keep flowing and the node looks covered (D5's 7010354192, D3's 7010365557). D3's three conditions hold: `network-baseline-refused` stays raised until it clears, with its health event; its text says that no network alert is raised and names the remedy (approve a baseline this build reads, or move forward again); and when the unpruned stream reaches its class ceiling, intake's refusal is the existing counted and alarmed drop, never a silent one, which D5 confirms in this condition's change.
  4. **Each later minor's `docs/release.md` §7.1 row states its rollback cost** (`docs/release.md` §7.2, "Rules that will add rows"). For a C13 minor, at or above (b) the cost is "refused, alarmed"; below (b) it stays "read forward", and those builds are out of the rollback set by condition 6. For a `netbaseline` minor, on every build: one that adds a key costs "detector off and alarmed, observation stream unpruned, until a baseline the older build reads is approved"; one that adds no key is read safely. D4 recommends, as D7 does, that a `netbaseline` minor that adds a key takes a §7.1 floor at its first reader rather than accept that cost; D7 and D1 decide at that minor.
  5. **Timing:** before the next C13 minor is approved, before P4-4-DE (D1's item 3), before the network learner is wired in the node (§2 (b), "The learner"), and in every case before the first release.
  6. **(b)'s merge commit is a `docs/release.md` §7.1 floor** (D3's F1, D7's point 1). Every build from `26545062` up to (b)'s parent reads a later minor forward, #760 and today's `main` included. The row: for a node that has stored an observation of any C13 minor later than the one current at (b), the floor is (b)'s merge commit. AP-10's floor must be at least that commit (D1's 7001264083 item 2). The §15 row's exclusion of the seven builds stays for its own scope; the new floor is above it.
- **Not (a)** alone: nothing checks it. **Not (c):** coarser, more machinery in `platform/`, and no record here lacks its own schema stamp, which is what a store stamp would add. **Not (d):** its precision saves records only inside the window (b) refuses, at the cost of (a)'s judgement in code. **Not (e):** a major at each such change, to bind builds that were never released, and not at the link.
- **Residual under (b):** the hand install of a build below it, as under every option; AP-10 is still owed before the first release, and (b) does not replace it (AP-10 is checked by the newer build before the downgrade, (b) by the older build after it); and C4's envelope (§1, owed separately).
