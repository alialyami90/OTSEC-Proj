# C8 0.10: a difference too large to store (C3)

Status: proposal for review, C3, 2026-11-04 (D4-42). C1 approves, with C5 as the writer (#390) and C6 for the tests. This is a contract change only. It adds one field and changes one field rule of `config.change_detected`. Everything here is `desk`: the tests use fixtures, and no device has been contacted.

## Why

C9 0.4 (#392) bounds a difference at `MaxDifferenceBytes`. C2 measured the SEL-751's settings sheets: a read in which every setting changes makes a difference of 1.62 to 1.74 MB, and the bound is 1,507,328 bytes. Both snapshots still fit. D4-42 rules C2's option (a): the node stores no difference, records the change without `difference_digest`, alarms it as any other change, and holds the read's snapshot. Until 0.10, `config.change_detected` required `difference_digest`, so the node had no record it could write.

## The field

`difference_too_large` (0.10), a boolean in the `config` group. It is written as `true` and omitted otherwise.

- It belongs on `config.change_detected` only. Every other action refuses it.
- From 0.10, a detection has `difference_digest` exactly when `difference_too_large` is absent: one of the two, never both and never neither.
- A record stamped 0.9 or earlier cannot carry it.
- Nothing else about the detection changes. `changes_digest` is still required (from 0.7), and so are `snapshot_digest`, `read_seq` and `unchanged_at`. The record is warning `unapproved_change`, or info `approved_change` with `approval_seq`, as before.

I chose a boolean over a reason code. A difference is either stored or too large: a store that refuses the difference writes no record at all, as it does today. So there is no second value to name. If a later minor needs one, it can add a field.

## What `VerifyConfig` checks

Nothing new, and that is deliberate. D4-42 asks for "`VerifyConfig` checks the held read snapshot in place of the difference". `VerifyConfig` reads audit records only, never stored documents, and no chain rule names `difference_digest`:

- A same-change read names the detection by `change_seq` and `changes_digest`.
- An approval covers by baseline and window.
- An acknowledgement names a snapshot digest.

So a too-large detection stands in the chain as any other. `TestDifferenceTooLargeInAChain` takes C8's `readsChain`, makes its detection too large, and the chain verifies, both whole and from every cut (`VerifyConfigFrom`).

The check that D4-42 wants is a check of the store, not of the chain: `config.Compare(baseline, snapshot).ChangesDigest()` equals the record's `changes_digest`, with both documents found by digest in `config/<asset>`. It belongs in C6's second test, and to an auditor who holds the documents. The record already gives everything that check needs: `baseline_digest`, `snapshot_digest` and `changes_digest`.

## For the writers (C5, #390)

- On `ErrTooLarge` from `Compare`, write the detection with `ChangesDigest` from the returned difference, `DifferenceTooLarge: true` and no `DifferenceDigest`, and store no difference document.
- **Holds.** The writer holds `snapSeq` and `diffSeq`. With no difference, it holds the snapshot only.
- **The start-up reconcile, `holds.go`.** `wants()` adds a hold for `o.difference` for every open, ended and returned change. With an empty difference digest, `planHolds` finds no record for `""` and reports it as missing, which raises `config-baseline-not-stored` for a document that was never meant to exist. `wants()` must skip an empty difference digest. Please pin this with a restart test after a too-large change.
- The alarm text says "difference not stored: too large" (C1 on #390).

## Compatibility: a 0.9 reader refuses the record

This is the first minor that relaxes a rule instead of adding a field or an action. A 0.9 reader decodes a 0.10 record with `strictjson.Forward`, ignores `difference_too_large` as a field of a later minor, and then applies its own rule that a detection needs `difference_digest`. So it refuses the record (`ErrRecordRejected`). It fails closed and visibly, and it never misreads the record. But a chain holding one too-large detection does not parse for any 0.9 reader.

No other form avoids this:

- A new action instead of a field would be unrecognized by a 0.9 reader and kept. But every same-change read that names it would then be broken for that reader, and every chain rule about detections would need the new action as well.
- A placeholder `difference_digest` would name a document that does not exist.

So readers of the audit chain must be upgraded to 0.10 before a node writes the field. In this repository every reader is built with its writer, so a single binary is never out of step. For distributed deployments it is an upgrade-order rule. I ask C1 to record it with the ruling.

## Evidence

- `TestDifferenceTooLargeFields` checks:
  - an approved and an unapproved too-large detection validate;
  - each is refused with a `difference_digest`, stamped 0.9 or 0.7, without `changes_digest`, or with neither field;
  - a bare-hex `difference_digest` is refused when the field is absent;
  - the field is refused on six other actions.
- `TestDifferenceTooLargeInAChain` is the chain case described above.
- Six mutants of the new rules were all killed. The one that weakened the digest's form check survived at first, because no test before 0.10 refused a bare-hex `difference_digest`. A test was added and it was then killed.
- One valid and four invalid fixtures are in `contracts/audit/testdata`. `Validate` checks them all. With `jsonschema` 4.26, every valid fixture passes the schema and every new invalid fixture fails it. No existing invalid fixture changed its result against the schema.
