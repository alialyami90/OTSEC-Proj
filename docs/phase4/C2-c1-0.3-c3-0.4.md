## 1. C1 0.3 (`otsec.asset/0.3`): identity attributes with their source

C1 0.3 is a minor bump. Everything in 0.2 stays as it is, and 0.3 adds four things.

### 1.1 Every observation says its kind

`Source` gains a required `kind`: `device-read`, `passive` or `operator` (D4-49 Q4). As with `IdentityBinding.Strength`, the kind follows from the method and is stored so that every reader, the matcher included, can use it without knowing methods.

| Method | Kind | Why |
| --- | --- | --- |
| `adapter-session` | `device-read` | A C2 invocation read it from the device. |
| `simulator-session` | `device-read` | The same read, against a simulator. The evidence class `simulated` still says so, and nothing about simulation changes. |
| `syslog-received` | `passive` | The device sent it unasked, and nothing authenticated it. |
| `passive-network` | `passive` | |
| `operator-entry` | `operator` | |
| `document` | `operator` | A person chose the document and typed in the value. |
| `derived` | any of the three, under the rule below | |

**A derived observation may be `device-read` only when every attribute its `ref` names carries a `device-read` observation, not itself `derived`, equal to that attribute's value.** So a derived value backs neither itself nor another derived value, and a reader that lowers an input to its fallback kind lowers what is derived from it (C6's review of #445). Otherwise it takes `passive` or `operator`, whichever its inputs warrant, and `Validate` refuses `device-read`. A rule therefore cannot raise its inputs to `device-read`, so V-M7's "an operator-entered or passively inferred identity never yields `confirmed`" holds through derivation too.

**A value cut from device bytes is not derived.** The model and the firmware version are parts of the FID. The adapter reports each as its own `adapter-session` observation, whose span covers only that part of the FID's bytes, with the same `ref` (section 1.5). So they are `device-read`, and the span shows exactly which bytes they are.

A 0.3 reader that meets a kind it does not know reads it as `operator`, which never yields `confirmed` (the fallback rule: the least trusted reading).

### 1.2 A device read says its read path

`Source` gains `read`, which is required when the kind is `device-read` and the method is `adapter-session` or `simulator-session`. It is absent otherwise.

```json
"source": {
  "method": "adapter-session",
  "kind": "device-read",
  "ref": "<C2 invocation ID>",
  "span": { "offset": 1844, "length": 39 },
  "read": {
    "transport": "snmpv3",
    "operation": "sel27x1.snmp.entity",
    "oid": "1.3.6.1.2.1.47.1.1.1.1.10.1"
  },
  "observed_at": "2026-11-05T04:20:00Z"
}
```

- **`transport`** is the C1 transport of the endpoint the invocation used: `snmpv3`, `telnet`, `ssh` or `serial`. V-M1 (e) checks this field.
- **`operation`** is the C3 operation that read the bytes: the run's step, not the run. For the SEL-751 it is `sel.id` or the SER read that holds the serial number. For SNMP it is one of section 2's operations.
- **`oid`** is the varbind OID whose value holds the bytes. The FID's column is undocumented (the family note), so this records where the agent actually put it.
- **`header`** names the SNMPv3 header field that holds the bytes, when the value is not in a varbind. 0.3 has one value, `msgAuthoritativeEngineID`, for `snmp_engine_id`.
- An `snmpv3` read has exactly one of `oid` and `header`. Any other transport has neither.

**The evidence ID is `ref`, the C2 invocation ID.** Together with the span, it says which bytes of which transcript hold the value. C5's identity record keeps the bytes the spans cover, under that invocation ID (C5's note, "An identity record carries its own evidence"). So the evidence ID still resolves after `ser/<asset>` is pruned. C12 lists these IDs.

**The first read, not the latest.** C1 keeps the latest observation per (evidence class, method), so an observation's `ref` moves to each newer run that reads the same value. C5 writes an identity record only when a value changes, so only the first read's bytes are held. The result, agreed with C5 (#438 at fd6ffdf, §2):

- A finding cites the identity record's first-read invocation ID.
- It carries the latest confirming invocation ID and time as a separate field. C5 writes these after every successful identity read, as a small `identity.read` record (#438 at 4be03fe).
- `modules/asset` builds the identity record from the observation that first carried each value, never from a `ref` that has moved.

C4's C12 takes this (#440 at c10d835): `identity.latest_read` is required on `confirmed`.

### 1.3 The `snmpv3` transport

`snmpv3` is added to `Transports`.

- An `snmpv3` endpoint names `host` and `port`. The port is required, normally 161 (S29 p. 76), and never defaulted.
- Its path is `direct`. `CheckPath` applies unchanged.
- It is not inbound. The platform receives no traps (the family note).
- It is not in `AlwaysPlaintext`.

**v1 and v2c are not added** (D4-49 Q3). An endpoint naming `snmpv2c` or `snmpv1` fails `Validate` as an unknown transport, so the whole record is refused. That refusal is what V-M1 (d) is shown with in item 3. C3's #437 adds `snmpv2c` and `snmpv1` to C7 0.8 for the approval record. They have nothing to bind to until a later C1 minor adds the transports, and that minor needs the owner's decision HR-17 asks for.

**Downstream security.** An `snmpv3` endpoint is `encrypted-authenticated` only with the binding in section 1.4. That follows the 0.2 rule ("only pinned-key makes a link encrypted-authenticated"), and C3's §2.1 mapping in #437 agrees: the algorithms are strong-only, so there is no weak branch.

### 1.4 The engine ID is what a pinned-key binding pins for SNMPv3

- **A new attribute, `snmp_engine_id`.** Its value is the engine ID in lowercase hex: 10 to 64 hex digits, because RFC 3411's `SnmpEngineID` is 5 to 32 octets. For this family it is 22 digits, `80007c4f03` followed by the MAC (S29 p. 42). It is not operator-only. The device reports it in discovery and in every authenticated response.
- **`pinned-key` gains its SNMPv3 meaning.** Today the package says pinned-key compares "a host key or certificate pinned at commissioning". 0.3 adds: *or, for an `snmpv3` endpoint, the authoritative engine ID that the device's USM keys are localized to. The proof is that the device's responses verify under a key localized to that engine ID (RFC 3414 §2.6).*
- **Validation.** An asset with an `snmpv3` endpoint has a pinned-key binding whose `pre_credential` is exactly `["snmp_engine_id"]`, and `snmp_engine_id` is in `attributes` with an operator-declared value. An `snmpv3` endpoint on any other binding is invalid, so the record is refused and the device gets no session. There is no SNMPv3 link below `encrypted-authenticated` to acknowledge.
- **`firmware_id` may be in `attributes` but not in `pre_credential`.** It is compared after authentication, because the FID comes back only in authenticated responses. That is how the SEL-751 already compares its serial number.

**Why pinned-key is honest here.** Discovery's engine ID is unauthenticated. The client compares it with the pinned value before it sends any authenticated message (C3's §4 rule 2). After that, a response verifies only if the responder holds a key localized to the pinned engine ID, and a responder without the key gets nothing usable. Two limits, both for the commissioning instructions:

- **The key is per device only if the password is.** One USM password per device is C3's commissioning rule (#437). With a password shared across devices, the holder of one device's password can localize keys for any other pinned engine ID and impersonate that device.
- **Offline guessing.** Authenticated messages captured on the LAN let an attacker test guesses at a password offline (RFC 3414 §11.2). The commissioning instructions should ask for long random USM passwords. Whether the device accepts them, and how long it allows, is `unknown` (S29 does not say). Hardware has to show it.

**Where the declared engine ID comes from.** Commissioning takes it from the device itself, from its settings or from its MAC label in the form above, never from a network discovery (C3's review of #439). A discovered value is unauthenticated, so pinning it would trust whatever answered first.

**The collector holds the pinned engine ID too.** The C7 credential pins it (D4-49 Q1, #437 §2.1). Before a session, the collector checks that the credential's engine ID equals the asset's declared `snmp_engine_id`. If they differ, the session is refused with `refused.credential_unavailable`, because that is a configuration fault and not the device's behaviour, and nothing is sent.

### 1.5 Which attributes each family reads

Both families read nothing new for identity.

| Attribute | SEL-751 (`sel.id`, today's `Result.Observations`) | SEL-2731/2741 (section 2's run) |
| --- | --- | --- |
| `firmware_id` | the ID reply (S22 Figure 7.38) | the one value in `entPhysicalTable` or `sysDescr.0` that matches the FID grammar (the family note) |
| `model` | the FID's product part, `SEL-751`, as printed | the FID's product part, for example `SEL-2731M`, as printed |
| `firmware_version` | the FID's R (or X) and V parts, for example `R301-V2`, as printed | the same, for example `R102-V1` |
| `serial_number` | the SER header, at Level 1 (today) | not read. Whether the Entity MIB serves it is `unknown` (the family note) |
| `sel.cid` | the ID reply (today) | n/a |
| `hostname` | n/a | `sysName.0` |
| `snmp_engine_id` | n/a | the `msgAuthoritativeEngineID` of the first authenticated response |

- **Values are kept as printed, and nothing is mapped.** The model is `SEL-2731M`, with the RSTP letter, not `sel-2731`. Mapping a model string to C11's `product` is the matcher's job (C4's note). The same holds for `R301-V2` against a version range.
- **`vendor` and `product_family` stay operator-only** (0.2's `OperatorOnlyAttributes`). The device prints `SEL-` as part of its FID, not as a vendor field, and reading "SEL" out of it would be an inference.
- **The product match uses the device-read `model`, never the declared fields** (C6's review of #439, C4's matcher note §3 on #440).
  - C11's `product` is compared with `model` as a whole string, and `vendor` decides no class. So no operator entry can lower a finding on a device-read identity (D4-49 Q5).
  - **A declared `product_family` that disagrees with the read `model` is an identity conflict.** The family's capability profile lists the models its `product_family` covers (`SEL-751`; `SEL-2731M` and `SEL-2741M`). `modules/asset` compares the read `model` with that list. A model outside it is shown in health (`identity.family_conflict`) and settled by an administrator, and it is never a match input.
  - With no device-read `model`, the match uses the declared fields, and the class is the operator one (C12).
- **The SEL-751 change is in its adapter, not its register.** That answers C5's question 5. The adapter reports `model` and `firmware_version` as two more observations, with sub-spans of the FID it already reads. That is a C2 change in Stage C, with tests, and needs no register revision.

### 1.6 Versions

- **0.3 adds:**
  - `Source.kind` and `Source.read`;
  - the `snmpv3` transport;
  - the `snmp_engine_id` attribute;
  - the SNMPv3 meaning of pinned-key.
- **A 0.2 record is still read.** Its observations have no kind, and a 0.3 reader gives them the kind of their method, from the table in 1.1. A 0.2 `derived` observation reads as `operator`, the fallback.
- **A 0.2 record that carries `kind`, `read` or an `snmpv3` endpoint is invalid.** That is the same rule as D4-16's for register keys.
- **A 0.2 node that reads a 0.3 record with an `snmpv3` endpoint refuses the whole record** (an unknown transport), and with it the asset. That fails closed. It means a node is upgraded before an SNMP endpoint is added to any asset it collects from.

## 2. C3 0.4 (`otsec.register/0.4`): SNMP read operations, never SET

C3 0.4 is a minor bump. Line operations, runs, the deny rules and the signing domain do not change.

### 2.1 An SNMP operation

0.4 adds the package key `snmp_operations`. It is refused in any package below 0.4 (D4-16). A package must now hold at least one operation of either kind; today's check is `len(p.Operations) == 0`.

```json
"snmp_operations": [
  {
    "id": "sel27x1.snmp.system",
    "pdu": "get",
    "oids": ["1.3.6.1.2.1.1.1.0", "1.3.6.1.2.1.1.5.0"],
    "limits": { "max_reply_bytes": 1472, "timeout_ms": 3000 },
    "citations": [ { "source": "S29", "ref": "pp. 46 to 47" } ],
    "evidence": { "class": "documented-untested" },
    "side_effects": "none: reads two system-group scalars"
  },
  {
    "id": "sel27x1.snmp.entity",
    "pdu": "getbulk",
    "subtree": "1.3.6.1.2.1.47.1.1.1",
    "max_repetitions": 16,
    "walk": { "max_varbinds": 512, "max_requests": 32 },
    "limits": { "max_reply_bytes": 1472, "timeout_ms": 3000 },
    "citations": [ { "source": "S29", "ref": "pp. 46 and 75" } ],
    "evidence": { "class": "documented-untested" },
    "side_effects": "none: walks entPhysicalTable within the bounds"
  }
]
```

- **`pdu`** is a closed enum: `get`, `getnext` or `getbulk`. There is no value for SET, Inform, Trap or Report, and an unknown value makes the package invalid. A SET cannot be written in the format, which is the same idea as the line grammar (V-M1 (b)). C3's independent egress check (#437 §4 rule 4) is the second line.
- **`get`** names 1 to 16 instance OIDs in `oids`. One request is sent, carrying exactly those varbinds. It has no `subtree` and no `walk`.
- **`getnext` and `getbulk`** name one `subtree` and a `walk`, and have no `oids`.
  - The first request starts at the subtree. Each later request starts at the last OID returned, so every requested OID lies inside the subtree.
  - The walk ends when a returned OID falls outside the subtree, or on `endOfMibView`. Either one ends the walk normally.
  - If the walk reaches `max_varbinds` or `max_requests` first, the run fails with `failed.response_too_large`, and every byte read is kept. A walk cut short is never presented as complete.
  - **Every returned OID must be greater than the one before it**: the request's start OID for the first, and the previous varbind after that (RFC 3416's lexicographic order). A returned OID that is equal or smaller ends the run at once with `failed.snmp_walk_not_increasing`, and the bytes are kept (C6's review of #439). A looping or backward-stepping agent therefore costs one request, not `max_requests`, and health names it.
  - `getbulk` sets `max_repetitions` (1 to 32) and has `non_repeaters` 0. `getnext` has no `max_repetitions`.
- **Every OID is literal dotted decimal.** It starts with `1.3.6.1.`, has 2 to 128 arcs, each below 2^32, and has no leading zeros. The format has no parameters, so 0.4 has no template.
- **`limits`** (0.3's type) is required for every SNMP operation. `max_reply_bytes` bounds each response message, and `timeout_ms` bounds the wait for each response.
- **Every request advertises `msgMaxSize` equal to the operation's `max_reply_bytes`** (C6's review of #439). An agent sizes its response to the requester's `msgMaxSize` (RFC 3412; RFC 3416 §4.2.3 for GetBulk), so a larger advertised size would make a working switch fail every walk. For an SNMP operation, `Validate` refuses a `max_reply_bytes` below 484, which is RFC 3412's minimum `msgMaxSize`. A reply larger than the advertised size is the agent's fault, and still `failed.response_too_large`. The run's `max_total_bytes` and `deadline_ms` bound the whole session, as in 0.3.
- **The ceilings are 0.3's,** plus `max_varbinds` at most `MaxReadRowsCeiling` (2048) and `max_requests` at most 64.
- **`citations`, `evidence` and `side_effects`** are required, as for a line operation. Every SNMP operation is read-only. Its classification is implied, with no field to set it otherwise.
- **Operation IDs share the package's namespace** with line operations and runs.

### 2.2 Runs

- **A 0.4 run's steps may name SNMP operations.** The steps of one run are all SNMP operations or all line operations, never mixed, because one run is one session on one transport.
- **An SNMP run has no precondition, warning or context steps.** This family's package has none, because the SNMP agent has no `LANG`-style setting that changes its replies.
- **The family's identity run:**

```json
{ "id": "sel27x1.snmp.identity",
  "steps": ["sel27x1.snmp.system", "sel27x1.snmp.entity"],
  "max_total_bytes": 65536, "deadline_ms": 30000, ... }
```

  The engine ID needs no operation, because it comes with discovery and with every authenticated response (section 1.5). The bound numbers above are placeholders for C6 to test on GT-MIB. They are not derived from a real table's size, which is `unknown` (the family note).

### 2.3 What the collector does with an SNMP run

The USM rules are C3's, in #437 §4. In order, for one run:

1. **Before anything is sent:**
   - the declared FID is checked against the family's allowlist (`refused.firmware_not_allowlisted`), as for the SEL-751;
   - the endpoint and binding must be section 1.4's;
   - the C7 credential is resolved, and its engine ID must equal the declared `snmp_engine_id`.
2. **Discovery** (the transcript phase `probe`):
   - The one non-authPriv message is sent: C3's discovery probe.
   - The `msgAuthoritativeEngineID` in the answer is compared with the pinned value. A mismatch ends the run with `refused.engine_id_mismatch`, before any authenticated message, and the keys are never localized to the new value (D4-49 Q1).
3. **Time synchronization** (phase `auth`):
   - At most one authenticated `usmStatsNotInTimeWindows` Report, which carries boots and time. The request is then sent again with the corrected boots and time and a fresh `msgID`. That resend is not the request's retransmission (5).
   - A time-window Report that does not authenticate is never used to set boots or time. It ends the run with `failed.usm_not_in_time_window`.
   - The failure Reports (`usmStatsUnsupportedSecLevels`, `usmStatsUnknownUserNames`, `usmStatsWrongDigests`, `usmStatsDecryptionErrors`) end the run with their code even when they do not authenticate. An agent cannot authenticate them, because it has no key that fits, and a forged one can only stop a run, never steer it.
   - **A Report counts only if it matches the outstanding `msgID` and comes from the endpoint's address and port.** Anything else is discarded, as #437 says for responses below authPriv (C1's ruling, D4-53; GT-MIB U16).
   - **Nothing an unauthenticated message can cause suspends anything** (C1's ruling, D4-53; GT-MIB U15). The four failure codes and `refused.engine_id_mismatch` fail the run and show in health, where repeats are visible. They never suspend the asset or the credential, unlike C1's `identity-mismatch` suspension for the SEL-751, because the message that caused them is not authenticated.
4. **The steps** (phase `operate`):
   - Every request is authPriv, with the configured algorithms only (D4-49 Q2).
   - A response that does not authenticate or decrypt is discarded, not parsed. If no good response arrives, the request times out.
   - A response with a non-zero `error-status` ends the run with `failed.snmp_error_status`, and the bytes are kept.
   - A varbind exception (`noSuchObject`, `noSuchInstance`) is not an error. That OID gives no attribute, and the transcript shows why.
5. **Retransmission:** each request is sent at most twice, the original and one retransmission, each with a fresh `msgID`. Both count against the run's bounds.

### 2.4 C2 0.7 additions this needs (C2's own contract, `contracts/adapter`)

**New codes.** They are distinct so that health shows which failure it was (V-M1 (c), C5's note, "SNMP run failures"):

| Code | When |
| --- | --- |
| `refused.engine_id_mismatch` | Discovery's engine ID differs from the pinned one. Nothing authenticated was sent. |
| `failed.usm_unsupported_sec_level` | A `usmStatsUnsupportedSecLevels` Report |
| `failed.usm_unknown_user` | A `usmStatsUnknownUserNames` Report |
| `failed.usm_wrong_digest` | A `usmStatsWrongDigests` Report |
| `failed.usm_decryption_error` | A `usmStatsDecryptionErrors` Report |
| `failed.usm_not_in_time_window` | A second `usmStatsNotInTimeWindows` Report in one session |
| `failed.snmp_error_status` | A Response with a non-zero `error-status`, for example `authorizationError` |
| `failed.snmp_walk_not_increasing` | A walk returned an OID not greater than the one before it |

None of these is retried at a lower level, as another user, or over another version (#437 §4 rule 1).

**What the transcript holds for SNMP.** One segment for each message sent or received, with its phase, holding the BER of the whole SNMPv3 message.

- For an authPriv message, `msgData` is stored as RFC 3412's `plaintext` choice of `ScopedPduData`, the decrypted `ScopedPDU`, instead of the `encryptedPDU` octets.
- So the stored message is valid SNMPv3 BER. It keeps the header (engine ID, boots, time, user name, the authentication and privacy parameters), and spans can point at varbind values.
- **`msgAuthenticationParameters` is stored as zero octets of the same length, in every segment** (C3's review of #439). The HMAC could not be checked over the stored form anyway. Kept, it would let anyone holding a transcript test password guesses offline: against the authenticated time-sync Report directly, and against an authPriv message by re-encoding its stored plaintext. Zeroing in place keeps every span's offset. It is recorded as a `Redaction` with a new reason, `usm-digest`.
- The ciphertext is not kept, because only the collector's key could read it. The result states both limits.
- **No key is in the transcript.** The keys never appear in a message, and the user name is not secret.

## 3. The asset module's boundary (`modules/asset/`)

This section is design only. The package is created in Stage C, once the contracts are approved.

**What `modules/asset/` is.** It is a node-side package, owned by C2. It turns the observations of a collector `Result` into C1 0.3 attributes:

- it sets each observation's kind, read path and evidence ID;
- it merges the observations into the asset record under C1's confidence rules;
- it reports which attributes changed value or source.

C5's node stores what it returns as an identity record (C5's note) and gives the matcher read access to it.

**What it is not.**

- **It opens no socket**, and it imports no network, `syscall` or `os/exec` package and no `modules/ied/...` package (AP-28, D4-50). Stage C adds a test that checks the package's imports and fails on any of them.
- **It is not a client.** The SNMP client is collector code: `modules/ied/snmpv3/`, owned by C2, linked only into `otsec-collector`. That package holds the USM session, the decoder, and each family's identity parse (the FID-by-form rule). C3's egress check is linked there too, as a separate package from the encoder (#437, AP-5).
- **It does not schedule.** The node's scheduler runs SNMP polls as ordinary schedule entries (C5's note §5).
- **It does not match.** The matcher is C4's.

**Enabled and disabled** (R1.8, V-M1 (a), D4-50). The switch is C5's node configuration `asset`.

- **When it is off:**
  - the node refuses, at load, a schedule entry that names an SNMP operation (C5);
  - `modules/asset` is not called, and no identity record is written;
  - a configuration with `applicability` on is refused (D4-50).
- **The SEL-751 path is unchanged by it.** The SER run's own identity check (AP-27, `refused.identity_mismatch`) is part of the SEL-751 adapter, and stays on either way.
- **The collector's second line.** It runs an SNMP operation only when the node's signed invocation names one, so with the node's entries refused, no SNMP message is built.
- **What V-M1 (a) observes:** zero PDUs at GT-MIB with `asset` off.

**What it depends on.** C1 0.3 (this note), C2 0.7 (2.4), C3 0.4 (2), C7 0.8's SNMPv3 credential (C3), and C5's identity record and switch.

## 5. Changes after approval (C1 on #445, 2026-11-05)

Coding the approved text showed five gaps. C1 ruled on each in #445, and the code follows the rulings. This note is otherwise unchanged from 92026c9.

1. **C1 0.3: `CapabilityProfile.models`** (§1.5 relied on it, and the approved text did not define it). It is optional, and its values are as printed. When it is absent, no `identity.family_conflict` check is made. The applicability match does not use it: it compares the device-read `model` (D4-53).
2. **C3 0.4: an SNMP operation's `max_reply_bytes` is 484 to 65,507** (§2.1; C3's note on #445). 65,507 is the largest UDP payload over IPv4, so a larger `msgMaxSize` could never arrive. 0.3's 1 MiB ceiling still holds for line operations and for a run's `max_total_bytes`.
3. **C2 0.7: what an SNMP result says** (§2.4 named the codes, the transcript form and the redaction, but `Result.Validate` could not carry an SNMP result). The additions are `session.snmp`, the engine ID as the first identity item under AP-27, and `observations[].read`, as proposed in `docs/phase4/C2-adapter-0.7-snmp-results.md`. A sent `usm-digest` is 24 or 48 octets, and a received one may be any length, zeroed.
4. **An authenticated FID mismatch over SNMPv3 suspends the asset, not the credential.** The keys never cross the wire, so suspending them protects nothing (C3 and C1 on #445). `Result.SuspendsCredential` carries this: the collector reads the credential suspension from the result, not from the code alone. The SEL-751 rule is unchanged.
5. **C2 0.7: `failed.snmp_fid_unreadable`, a ninth SNMP code** (C1 on #445, recorded with D4-54). The identity walk authenticated from the pinned engine ID but found no FID, or two different ones. It is after-auth and SNMP-only, and it suspends nothing, because an authenticated answer from the pinned engine ID is not evidence of another device. The transcript is kept. The identity holds only the matching engine-ID item, and no FID, model or firmware version is reported. The run is not a confirming read, so it refreshes no finding's evidence. The goldens cover both cases.
