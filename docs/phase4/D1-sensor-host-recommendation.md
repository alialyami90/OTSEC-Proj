# D1: the sensor host, a recommendation to the owner

D4-86 owes the owner one recommendation on the sensor's host under option (b): the hardware, the operating system, and who builds and patches it. D3's note (`docs/phase4/D3-sensor-link.md` §10) lists twelve choices, O-1 to O-12, with what each costs in risk. This file gives D1's recommendation for each, in one place, for the owner to accept, change or refuse.

**Status: a recommendation.** Nothing here is decided, bought or built. The owner decides every row. Evidence class: `desk`, from D3's note, ADR-0009, and the measurements cited. No hardware, TAP, switch or distribution named or described here has been run by this project.

## What the owner is asked first

Five facts about the sites decide several rows. The first two are already owed (`HANDOFF.md`, "Waiting on the owner", item 2); the other three are new with this file.

1. **Can each site take a network TAP on the links to be monitored,** or only a switch's mirror (SPAN) port?
2. **Is the station network PRP,** with two LANs?
3. **Where would the sensor sit:** in the node's cabinet, in the network cabinet, or in a relay room, and on what power?
4. **What does the site's management network reach,** and where does the site's time server sit? If the time server is only on the station LAN, reaching it would give the sensor a route toward OT assets (D3 on #640).
5. **Which of the links to be monitored carry protection or control traffic,** time-synchronization traffic such as PTP included, and how long an interruption can each of them tolerate? The owner sets that figure, with D2 (D6 on #640). It decides which links may take a TAP at all (O-1). A link with no answer counts as carrying protection traffic with no tolerance for an interruption. For a link that carries time synchronization, and for an optical link, also say how much added delay or lost light it can take: a working TAP adds delay, and a passive optical TAP takes light from the link (D6's understanding on #640, no source read).

Where a row depends on one of them, it says so. A statement marked "D1's judgment" has no source in the records; it is D1's reading, for the owner to weigh.

Where D1 recommends one of D3's options, the others remain open to the owner as D3's note states them.

## The machine this describes

From the rows above, not from a product. **No model is named, and none has been tried.**

- 64-bit x86, small and fanless (D1's judgment), rated for where it sits (question 3): an industrial or substation rating if it goes in a relay room (D1's judgment).
- TPM 2.0 (O-2, O-3); a firmware password and a verified start-up chain (SL-24).
- No out-of-band management controller, or one that can be switched off and has no shared port (O-8).
- Network ports: one monitoring port (two on PRP), one for the link to the node, one for management. Three or four ports. The monitoring ports are chosen with D4 for capture. The rig test of the egress rule (SL-T21) is run again on the chosen image's kernel, and the NIC and its driver need their H-row (H-18).
- Disk sized for the sensor's buffer during an outage, once C13 0.2 sets that figure.

## The operating system

**A long-term-support Linux distribution whose kernel has the nftables `netdev` egress hook.** D1 briefs D4 and D7 to choose it once the owner answers O-7, with SL-T21 run on that image's own kernel before it is relied on. The one measurement so far ran on one kernel on a veth pair (run 43077596916; D3 §9), so it shows nothing yet for the chosen kernel or NIC. The engine is approved as Zeek 9.0.1 with the project's script (D4-90), tested in a container image pinned by digest (run 43092601088), not on a sensor host.

## What stays unproven, whatever the owner chooses

- That the chosen TAP model is receive-only (an H-row not yet written, named in AP-32's test column; needs the owner's authorization).
- How the chosen TAP fails when it loses power or breaks: link-down time and frames lost at power loss, at power return and with a failed TAP (an H-row not yet written). On PRP, that the two LANs' TAPs share no common failure: a check at each site's fitting, kept in the site's commissioning record, not an H-row.
- That the enclosure, firmware password and start-up chain hold (SL-24), that out-of-band management is absent or off (SL-27), and, where a mirror port is used, that it refuses ingress for that switch model: each an H-row.
- That the management network admits only what O-5 says: a commissioning check that the project writes and the site's staff run, as for AP-24. The project runs nothing on a site network without the owner's authorization.
- That a TPM-sealed disk key is released to the verified start-up chain only, and survives a patch's re-seal (O-3; D3's understanding).
- That the egress rule stops every send path on the chosen kernel and NIC: SL-T21 on the image's kernel, which a virtual machine in CI may run (D6's view), and H-18 for the NIC and its driver.
- That the sensor host refuses a tampered, rolled-back or unsigned package (SL-25, SL-T17): no signed release and no updater exist.
- Anything about a real site's traffic: nothing has captured a site network (D4-66).

Nobody runs any of these H-rows without the owner's authorization.

## What the owner is asked to decide

1. Answer questions 1 to 5 above.
2. Accept, change or refuse each row of the table. O-7 changes what the product is and needs the release key's holder (TB9).
3. Authorize, when the time comes, buying for the lab what D6's H-rows need: two TAPs of the chosen model (one for each LAN of a PRP test link), one machine, the two ends of a test link for the TAPs to sit in, where a mirror port is to be used, a switch of each model in use for the ingress H-row, and whatever else each H-row names when D6 writes it. Nothing is bought before that word.
4. Before any TAP is fitted at a site, authorize the outage window it needs, and before any mirror port is set up, the switch's configuration change (O-1).

D1 records the owner's answers in the decision log, and D3's note and ADR-0009 follow them.
