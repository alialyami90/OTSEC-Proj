## 0. The problem in one paragraph

A `flow` that intake ties to one of the node's own collector runs (`node.platform_session`) skips every base rule (`modules/detection/netdetect/detector.go` l.262: `if r.base && (d.base == nil || o.Node.PlatformSession != nil)`). Only `node-address-spoofed` still looks at it, and only at the flow's first frame on the node's own segments (`own.go` l.177 to l.183). So a spoofed session that ties is hidden whole, writes included (HR-24). Today nothing compares a tied flow with the run it is tied to. This note proposes that comparison: one new rule that judges each tied flow against the profile of the run it tied to, taken from the collector's own result. The rule reads no session content.

## 1. Every route by which a spoofed flow can tie

The routes come from HR-24's row, AP-35 (`docs/threat-model.md`), SL-17 (`docs/phase4/D3-sensor-link.md`), D5's node design §1.6 and the baseline note §5. D3 checked them against `hold.go` (l.520 to l.539, l.857): a tie needs a connected result, so a failed dial or a never-connected run ties nothing, and there is no seventh route.

| # | Route | Source | What the detector sees for that invocation |
| --- | --- | --- | --- |

**What the routes share:** the traffic tied to an invocation is either more than the run produced (T1 live, T3, T5, T6, T2 when the run's own flow survives), different from it (T1 through the late index, T2 with the run's records evicted, T4), or, on a shared key, the same amounts with different content (T5's same-length substitution). The rule tests the first two. The third needs the signal in §3, M6.

## 2. What is known about a collector run's session, and when

**Before the run** (the C3 register and the collector's limits) the node knows the protocol, the endpoint, the approved commands, and the bounds (deadline, step timeout, maximum received bytes, `max_reply_bytes`). That gives limits, not a profile: what the device sends back is not known until it arrives. **So the rule judges after the run's result, never before.**

**After the run**, the collector's C2 result (`contracts/adapter/result.go`) gives the node the following. The node already reads it in `configread.go`, `snmp.go` and `identity.go`.

| Item | Field | Telnet | SNMPv3 |
| --- | --- | --- | --- |
| The session's local end and connect time | `session.local_addr`, `session.connected_at` (C2 0.9) | yes | yes |
| Start, end and outcome | `started_at`, `ended_at`, the outcome | yes | yes |
| Whether it connected | `session.connected` | yes | yes |
| Every chunk the client sent or **read**, with direction, phase, time and length | `transcript.segments[]` | the NVT data stream the adapter read. Telnet commands are removed (`modules/ied/telnet` package doc). The client's 3-octet refusals are not in it; `Stats` counts them, and the C2 result does not carry `Stats` | one segment per datagram the client sent or read inside an await, every retry included (`snmpv3/session.go` `record`, l.285 to l.305), in its stored form: the scoped PDU in plaintext in place of `encryptedPDU`, the digest zeroed |
| Credential sent | `session.credential_sent` | once per session; stored as `[REDACTED]\r\n`, 12 octets (`sel751/transcript.go`) | n/a (USM) |
| The agent's engine ID | `session.snmp.engine_id` | n/a | yes, pinned |

**The transcript is exact for what the client sent, and for what it read. It is not a record of everything the device sent** (D2's finding 1):

- **Telnet:** `await` (`sel751/run.go` l.1196 to l.1255) stops reading at the step timeout, the deadline or the response budget, and `commit` records only `s.reply`. Data already decoded but not returned, data the collector's kernel acknowledged but the adapter never read, and data in flight at close never reach the transcript. That happens on every run that ends `failed.timeout` or `failed.response_too_large`, and on every run that ends without QUI (`quitAfter`, l.1094).
- **SNMPv3:** `await` (l.321 to l.361) records only datagrams that arrive while it runs. The late answer to a request that timed out at the last step or at the deadline, and the answer to a first send that arrives after the retry's answer was accepted, are on the wire and not in the transcript.

**What the collector does** (D2, `sel751/run.go` l.446 to l.475, `snmpv3/session.go` l.34 to l.36): the SEL-751 adapter keeps at most one established connection per run and retries the dial only when the dial fails. An SNMPv3 request goes out at most twice, each time with a fresh msgID. The collector never runs two sessions to one asset at once. **So each invocation owns exactly one established flow.** The project's SNMPv3 target is the SEL-2731/2741 switch family (S29, `docs/phase4/C2-snmp-family.md`), all `documented-untested`; the SEL-751 manual never mentions SNMP.

**What the sensor's records show of a flow** (C13 0.2 §4.1 and §4.3):

- `flow` `start` and `end`, with `packets` and `bytes` **over both directions combined**. `bytes` is link-layer octets with any 802.1Q tag and the PRP RCT, without the FCS (C13 l.187), TCP retransmissions included.
- `first_utc` and `last_utc` on the sensor's clock, the `end` reason, and `syn_only`.
- For Telnet, an `insecure` record with `login.user` and `login.attempts`. On a SEL-751 the login has no user name: `ACC`, then `Password: ?` (S22 p. 7.32).
- For SNMPv3, an `encrypted` record emitted once per flow, at the first message, which is the run's noAuthNoPriv discovery.

**What the engine already computes and C13 does not carry** (Zeek `v9.0.1`, read from source):

- `conn`'s `orig_bytes` and `resp_bytes` are `c$orig$size` and `c$resp$size` (`base/protocols/conn/main.zeek` l.275, l.276). For TCP, `TCP_Endpoint::Size()` (`TCP_Endpoint.cc` l.131 to l.163) is the sequence span: the larger of the highest sequence sent and the highest acknowledged, less the start, less the SYN octet and a FIN octet, in a 64-bit space that counts wraps. A retransmission does not extend it. For UDP, `size` is the sum of the payload lengths sent in that direction (`UDPSessionAdapter.cc` l.40 to l.71).
- `orig_pkts`, `resp_pkts`, `orig_ip_bytes` and `resp_ip_bytes` (`main.zeek` l.278 to l.285), from the conn-size analyzer.
- Zeek documents that these counts can be stale inside early events (`init-bare.zeek` l.946 to l.951). The sensor reads them at the connection's end. Whether `num_pkts` counts a fragmented datagram once, after Zeek's reassembly, is inference and a stage 2 check.

## 3. What the detector compares, from sizes, counts and timing

The rule is one new rule, working name **`own-session-mismatch`** (§7 item 1). It judges each `(invocation_id, flow key)` that intake tied, once the invocation's result is known and the flow has ended or its open-flow entry has expired.

**Direction (D1's ruling 2).** Every byte and packet test is per direction. **To the device, the test is strict**: that is where a write shows. **From the device, the bound depends on the run's outcome**, because data that arrives after the adapter stops reading never reaches the transcript.

**Every comparison alerts only on more than the bound.** None is a lower bound, so loss cannot make an own run fail one, and none is switched off under loss or degraded coverage (§4).

| # | Comparison | Telnet | SNMPv3 | Routes it catches |
| --- | --- | --- | --- | --- |

A flow counts as a session if it carried payload in either direction (§7.1 item 2 (a)) or ended `fin`. **Not proposed:** the SNMPv3 `encrypted` record's `level` and `user` (they show only the discovery), `engine_id` (a spoofer talking to the real device gets the real one), and Telnet's `login.user` (a spoofer with the credentials types the same name, and a SEL-751 login has none). None of them separates a spoofer who holds the credentials, which HR-24 assumes.

**T1 through the late index, T2 with the run's records evicted, and T4:** only the spoofed flow is tied, so M1 is silent. M2 to M6 then compare the spoofed flow with a run it did not carry, and they catch it unless it was shaped to the run's profile (§5 item 1). T4, and T1 through the late index when the run's own flow is seen, also raise `own-session-outside-record` on the run's own flow.

### 3.1 M6: the same-length substitution, and what the engine gives

**The attack (D3's B3).** An attacker who sees the session's sequence numbers injects N octets at the relay's `rcv_nxt` just before the collector sends its own N-octet command. The relay executes the attacker's bytes and drops the collector's segment as a retransmission. The collector receives the ACK it expected, and the relay's reply lands in its transcript. Per direction, the sequence span equals the run's, the duration and the single login are unchanged, and M1 to M5 are silent. That is a write, for example `2AC` against an approved command of the same length, hidden whole on the shared key. The transcript is not an independent profile of the received direction on a shared key, because the attacker's induced replies land in it.

**What Zeek gives (checked against its source at `v9.0.1`; not run):**

- **There is no weird named `retransmission_inconsistency`.** The signal is the event `rexmit_inconsistency(c, t1, t2, tcp_flags)` (`src/event.bif` l.325 to l.346). `TCP_Reassembler::Overlap` (`TCP_Reassembler.cc` l.397 to l.411) raises it when an overlapping segment's bytes differ from the bytes the reassembler holds for that range (`memcmp`), except a one-octet overlap on a connection whose peer has done nothing (keep-alives).
- **It compares only against data the reassembler still holds.** That is data not yet acknowledged, plus at most `tcp_max_old_segments` older segments, which is 0 by default (`init-bare.zeek` l.1918 to l.1921). Worse, `TCP_Reassembler::DataSent` (l.420 to l.437) drops a segment that lies wholly below the receiver's acknowledgement before any comparison ("We've already delivered this and it's been acked"). So, in the attack's order, if the sensor sees the relay's ACK of the injected octets before the collector's segment, **no event is raised, whatever `tcp_max_old_segments` is.** It is raised only when the collector's segment arrives before that ACK, which depends on timing the attacker controls.
- **The event hands both payloads to the script.** The stock handler, `policy/protocols/conn/weirds.zeek`, writes them into a Notice, so it must never be loaded. The project's script would count the event per direction and discard `t1` and `t2`.
- **A content-free retransmission count exists, for whole overlaps only** (corrected for D6's B1). Zeek raises `tcp_rexmit(c, is_orig, seq, len, data_in_flight, window)` (`src/analyzer/protocol/tcp/events.bif` l.303 to l.318), which carries no payload, from `TCPStats_Endpoint::DataSent` (`src/analyzer/protocol/tcp/TCP.cc` l.158 to l.181), not from `update_last_seq`. It raises it, and adds `len` to `num_rxmit_bytes`, only when the segment's end does not pass the highest end seen so far (`top_seq - max_top_seq <= 0`), leaving out a segment of at most one octet with no data in flight when `ignore_keep_alive_rexmit` is set. `update_last_seq`'s `DidRxmit` (`TCPSessionAdapter.cc` l.470 to l.502) uses the same test. **A segment that overlaps sent data and ends past the highest end is not counted at all.**
- **Zeek exposes no count of overlapping octets without content** (D1's ruling on B1). I found none in `v9.0.1`'s TCP analyzer: `tcp_rexmit` counts whole overlaps only (above); the reassembler measures a partial overlap in `CheckOverlap` (`src/Reassem.cc` l.306 to l.349), but passes it on only as `rexmit_inconsistency`, only when the bytes differ and are still held; and the one event that gives every segment's `seq` and `len`, `tcp_packet` (`events.bif` l.240), also hands its handler the `payload`. A handler on `tcp_packet` would be a handler that receives payload, which comes back to D1 first, as M6a did. **So the count is the project's own, adopted by D1:** the frame stage, ahead of the engine, counts overlapping octets from headers alone (§3.3).

**So M6 has two forms, both adopted by D1: M6a in ruling 1 of 6854205907, M6b in 6854297364:**

- **M6a, inconsistent retransmissions to the device: `rexmit_inconsistency` count > 0.** The engine makes the comparison; only the count leaves the sensor. **Adopted** (D1's ruling 1, 6854205907). It catches the substitution **only when the collector's segment reaches the sensor before the relay's ACK**, so an attacker who times the injection evades it. It is also the one form that survives PRP duplicates (§4), because an identical duplicate raises nothing. D1 ruled that it stays inside D4-95: the project's handler counts the events and drops both payloads, and logs, stores and forwards neither. The engine already holds the bytes for reassembly, and the rule reads nothing from them.
- **M6b, adopted: overlapping octets to the device above the collector's own** (D1's ruling on B1). The sensor's measure is the frame stage's header-only overlap count (§3.3), one definition, which replaces `tcp_rexmit` as M6b's source. The collector reports the octets its own socket retransmitted to the device. A to-device excess means the sensor saw to-device sequence space covered again that the collector sent once. That catches the substitution, whole or partial, **in both orders**, with the residuals of §5 item 2. No content is read anywhere. It needs a C13 field (§7.1 item 2 (c)), a C2 field (§7.2 item 7), and a new output from the frame stage (§3.3).
  - **How the collector reads it (D3, 6854286062; D1's ruling):** `WSAIoctl` with `SIO_TCP_INFO` and version 0 on the session's own socket, reading `TCP_INFO_v0.BytesRetrans`, from Windows 10 1703, with no elevation. It is read after the peer's EOF with `BytesInFlight` = 0. On a timeout, deadline or abort path it is read and the socket then closed abortively (`SO_LINGER` 0), so nothing is sent after the read. `GetPerTcpConnectionEStats` is not used, since enabling it needs administrator rights. On Linux CI, `TCP_INFO`'s `tcpi_bytes_retrans` (kernel 4.19 and later) serves the same test.
  - **`unknown` fails closed.** If `BytesInFlight` ≠ 0 at the read, the call fails, or the build predates 1703 (LTSB 2016), the result carries `unknown`, and M6b raises `own-session-mismatch` with the reason `no-profile`. The node bounds the value (0 ≤ value ≤ k × sent octets) and reads anything outside it as `unknown`. Under-reporting gives noise, not misses.
  - **`unknown` until measured:** whether `BytesRetrans` counts tail-loss probes (RACK-TLP), and how it counts a repacketized retransmission. Linux is measured on CI-Linux with `netem`. A Windows measurement needs a packet-dropping driver on the owner's PC and the owner's word, which D1 asks for when stage 2 needs it. Until then the Windows half is `desk`.
- **What stage 3 shows for M6a** (D1's ruling 1; D3's note 4):
  - a test that the handler drops `t1` and `t2`: fed an inconsistent retransmission with a known marker payload, the engine's every log, the sensor's C13 records and its channel carry the count and nowhere the marker's bytes;
  - a check that no log field carries payload: every field of every log the engine writes is listed against its type and source, and none is a string or byte field filled from session content;
  - a check that the engine's loaded scripts exclude `policy/protocols/conn/weirds.zeek`, pinned in the sensor's build check.

### 3.2 Evidence, alert text and what the node keeps

**The profile carries numbers and times only** (D3's N1). The node computes it where it receives the C2 result, from segment lengths, directions and times, the outcome, and the counts above. No segment byte reaches `sensorlink` or `netdetect`. A stage 2 test pins the profile's Go type to numeric and time fields, so a field that could hold a byte slice or a string fails to compile the test.

**The alert states the excess only, never the run's own totals.** The client-to-relay total of an own Telnet run, less the lengths of the approved commands, gives the length of the password. So an alert reads, for example, "flow from 192.0.2.x:p to the relay's 23/tcp tied to run R: 2 established flows, 1 expected", "… 1,594 octets to the relay above the run's bound", or "… 3 retransmitted octets to the relay with different content". It never says "spoofed" (D4-68 ruling 10). It cites the tied flow's `start` and `end` (C13 §7.1), and the reason it was judged as it was (§4: `prp-table-full`, `prp-mismatched`, `no-profile`).

**The alert names its comparison in a fixed form** (D6's B3). Each alert's `observation` text begins with a fixed phrase for its comparison, `comparison M1` to `comparison M5`, `comparison M6a` or `comparison M6b`, then, where one applies, `reason prp-table-full`, `reason prp-mismatched`, `reason no-profile` or `reason incomplete` (§3.3). The phrases are pinned in the C13 minor change (§7.1 item 1), so a test attributes an alert to its comparison without parsing free text.

**One judgement is one hit, and its phrase lists every comparison it exceeds** (D6's F2), in the fixed order M1, M2, M3, M4, M5, M6a, M6b, for example `comparison M3 M6b`. A later hit overwrites a window's `Observation` (`detector.go` l.322 to l.325), so a summary keeps only the latest judgement's phrase. A checker therefore attributes from each first alert as raised, and from each summary's latest text, which is the latest judgement's. Every spoofed case runs in a fresh window, and in the variant after four earlier hits the spoofed judgement is the latest, so its phrase is the summary's. Under the mutant of Mx, Mx leaves the phrase and nothing else changes.

**What "cites the spoofed flow" means** (D6's N7). Alerts coalesce by (rule, asset) (`detector.go` l.307 to l.342): the first hit in a window is raised at once and later hits come in its summary, with `Cites` at most `MaxAlertFlows` = 4 flows and `Related` at most 32 seqs (`contracts/netobs/netobs.go` l.50 to l.52). An alert cites a flow when that flow's `start` or `end` record is in `Cites`, or its seq is in `Related`, in the alert or in its window's summary. What each judgement path cites:
- **The flow's `end` seen:** its `start` and its last `end`.
- **The open-flow entry expired with the `end` lost:** its `start` only.
- **`no-profile`:** the tied record that arrived without a profile.

**When the rule judges, and its latency** (D6's N9). On the first path, once both the run's result and the flow's last `end` have committed, and the first heartbeat after that `end` has been read, which closes the PRP stretch (D6's F1); on the second, at the open-flow entry's expiry (`flow_idle_s` + *g* after its last record); on `no-profile`, at the tie. The detection latency of each path is measured from the spoofed flow's last frame to the alert's commit. I propose bounds of one tick and one detector pass after the later of the two commits on the first path, and `flow_idle_s` + 2*g* + one tick on the second; D6 pins the numbers.

**What the node keeps with the run's tie state,** in the hold and in the late index entry until it is spent or expires: the profile and the count of established flows tied so far (D3's N3). T1 and T2 tie after the result has committed, so the profile outlives the result in memory. That is D5's node state, not a contract (§7 item 5).

**A tied flow with no profile fails closed** (D3's N2). Across a node start, a recovered hold or an open-table entry may tie a flow whose run's profile is not held. Such a flow is never skipped: it raises `own-session-mismatch` with the reason `no-profile`, and the base rules judge it as if it were untied.

### 3.3 The header-only overlap count (adopted; D3's and D6's conditions)

- **One definition (D6's O1, choice (A)).** For each tracked TCP flow, in the direction to the device: the overlap count is the sum, over every segment, of its payload octets at or below the highest sequence end seen in that direction before it. A segment starting exactly at the highest end adds nothing; one starting one octet below adds one. So a reordered pair counts, and a loss upstream of the sensor that is not a tail loss counts on both sides (the collector retransmits it), which nets to zero and leaves no credit. Only a tail loss upstream leaves the credit of §5 item 2. The from-device direction is not counted.
- **The keep-alive exclusion is narrow (D6's O4).** Only a one-octet segment at the highest end − 1 is left out. Every other short segment counts.
- **Flow boundaries match the engine's (D6's O2).** A flow starts on a SYN, or at its first frame for a midstream join. Its state resets on a new SYN after `fin` or `rst` on the key. An idle cut falls at `flow_idle_s`. Sequence numbers are unwrapped to 64 bits from the first one seen. Each `end` carries the delta since the previous `end` of the connection. Payload length is the IPv4 total length less the IPv4 header (options included), or the IPv6 payload length less any extension headers, less the TCP data offset. A header whose lengths are inconsistent with each other or with the frame marks the flow `incomplete`.
- **What it reads.** The TCP `seq`, the IP and TCP lengths and data offset, the flags, and the direction. A stage 3 test pins the counter's input type to those header fields, and a metamorphic test replaces every payload byte at random and shows the count unchanged (D6). D3 found it needs no new privilege, file, socket or system call (6854983767, item 1).
- **Which flows, and the table (D3's condition 2).** The frame stage tracks TCP flows to the sensor's listed collector endpoints (each relay's address and Telnet port). **It creates an entry only for a flow whose source is the node's address and whose handshake it saw complete:** the node's SYN, the relay's SYN-ACK, and an ACK of that ISN + 1 (D3, 6855245694). A blind spoof cannot complete a handshake, so only real connections hold entries; a handshake carries no payload, so nothing is counted before the entry exists. A flow with no entry, a midstream join included, has no count and is `incomplete`, as before. The table has a fixed size, `MaxOverlapFlows` = 4,096 entries (about 80 octets each: the key, and per direction a 64-bit highest end with its wrap epoch and a 64-bit count). An entry is freed when its flow ends (`fin` both ways, or `rst`), or after 2 × `flow_idle_s` with no frame. An `idle` cut writes the record and keeps the entry, so a flow that resumes after its cut is not a midstream join. An entry whose flow has carried no payload is freed after `MaxConnectTimeoutMS` (30 s), so that a SYN flood holds the table only while it is repeated (D3, 6855169107). **On overflow a new entry is refused, never a live one evicted,** and every refusal is counted as `overlap_table_full`, on the heartbeat path the CH-29 counters already use. A SYN flood or a stream of spoofed payload segments to a relay's Telnet port creates no entry, so it cannot hold the table.
- **`incomplete` fails closed (D3's condition 2; D6's O3).** A flow's `end` record carries `incomplete` when its entry was refused, when its entry began after the flow's first segment (after a refusal, or as a midstream join with no SYN seen, a sensor restart's included; D3, 6855169107), when any run portion of the key has a `start` and no `end`, after an unclean sensor stop or a lost `end` (D6, 6855188278), when a header in it was malformed, or when the link agent could not join a count to it. **Each frame-stage record joins exactly one engine flow on its key** (D6, 6855275755, B1): a frame-stage record that joins no engine flow, or an entry freed or begun inside one engine flow's span (for example after a spoofed out-of-window `rst`, or `fin`s both ways, followed by a SYN, which the endpoints drop and the engine may not split on), marks that engine flow `incomplete`. A tied flow with `incomplete`, or with no count at all because its endpoint is not on the sensor's list, alerts as `own-session-mismatch` with `reason incomplete` or `reason no-profile`, as `no-profile` does (§3.2). It never reads as zero.
- **A sensor restart** starts a new sensor run, and the new run's entry is a midstream join, so it is `incomplete`. The attacker's highest end from the old run is lost and an overlap that spans the restart is not counted, but the flow alerts with `reason incomplete` instead of passing (D6's O5, now fail-closed). The cost is one such alert for each own run open across a sensor restart, which the restart explains. A key whose old run ended with no `end` is `incomplete` too, so a count that never arrived never makes the sum read low.
- **The channel (D3's condition 4).** The frame stage writes only the ring and the engine's pipe today (SL-3), and its counters reach the heartbeat on the CH-29 path. No existing channel carries a value per flow. The count needs **a new one-way output from the frame stage to the link agent**: fixed-size records of the flow key, its start, the overlap count and the `incomplete` flag, with no frame bytes, which the link agent joins to the engine's `flow` `end` by key and start. **That is an SL-3 change, and it comes back to D3** before stage 2 pins.

## 5. What an attacker who knows the rule can still hide

1. **A session shaped to the run's profile, on a route where the run's own flow is not tied:** T1 through the late index or T2, each with the run's own records lost, or T4 (noisy anyway). The attacker matches every per-direction bound.
   - **Telnet:** the run's approved reads are replaced by commands of the same total length, in a session with one login. A write needs `2AC` and the level-2 password, so the attacker must drop some of the run's reads to make room, and must predict the relay's reply sizes. That is feasible for someone who has seen earlier runs.
   - **SNMPv3:** a `SET` at authPriv of the same encrypted size as the run's `GET` is invisible to any size measure. The collector never sends `SET` (`snmpv3` package doc), but the attacker can.
2. **The same-length substitution on a shared key** (§3.1; D3's B3). Preconditions: the attacker sees the session's sequence numbers, which the node's MAC on its segment allows, injects as the node at `rcv_nxt` before the collector's command of the same length, and holds the relay's level-2 password. M6b, adopted, catches a whole-overlap substitution in both orders, with three residuals:
   - **The partial overlap is caught** by §3.3's count, adopted by D1 (D6's B1). Just before the collector's N-octet command, the attacker injects N − k octets at `rcv_nxt`, for example `2AC` CR for k = 1. The collector's segment then counts N − k overlapping octets that the collector did not retransmit. Zeek's own counts miss it (§3.1), and in the ACK-first order so does M6a, so M6b is its sole witness there.
   - **A sensor restart or an unclean stop between the attacker's segment and the collector's is no longer a miss** (D6's O5; D3 and D6 on `135f68e6`). The overlap is not counted, but the new run's midstream join, or the old run's missing `end`, makes the key `incomplete`, and it alerts with `reason incomplete`.
   - **The credit residual** (D3's note 1). When a collector segment is lost upstream of the sensor and the collector retransmits it, the collector counts the retransmission and the sensor sees the first copy, so the loss credits its octets against a later injection. A Telnet command is one segment, so each such loss is a tail loss. Natural loss gives a random credit. An attacker who can drop one collector frame upstream of the sensor gains a credit of one command's length, then substitutes a command of the same length unseen in the ACK-first order. §6.4 item 7 measures it.
   - **A filled PRP table** suspends M6b on that stretch (item 5), and M6a catches only the collector-first order.
   - Where any of these residuals holds, **this is a write a holder of the credentials can make unseen**, so under D1's ruling 5 HR-24 goes back to the owner with the measurement.
3. **Anything within the tolerance.** Telnet to the relay: the bound is the stored sent octets + 3 × `refusals` + 2, and an own run whose password has p characters sends 12 − p octets fewer than that bound (D6's N3). So the margin is 12 − p octets, up to 11 at p = 1. One added line (at least 8 octets) is caught only for p ≥ 5. Each redacted echo from the relay has the same 12 − p margin; without `refusals` in the C2 result, 194 octets, enough for several short commands. Across each sensor restart in the flow's stretch, the bound to the relay also adds the run's longest approved line + 2 octets (§4), slack an attacker who can restart the sensor gets (D6's F3). SNMPv3 to the agent: none. From the device, the tolerance is wider (*U* + *R* replies of up to `max_reply_bytes`, `command_octets_received`), but a write shows in the direction to the device.
4. **The from-relay direction of a Telnet run that did not read to the relay's EOF, or whose stretch holds a sensor restart,** is not judged. An attacker who makes the run time out (by delaying the relay's replies) loses nothing to M3 from the relay, but the to-relay direction, where the write is, stays strict.
5. **A filled PRP table** doubles the SNMPv3 bound for that stretch, which hides an injection of up to the run's own size in each direction, and suspends M6b. The fill shows in coverage (CH-29); it does not alert on this flow.
6. **Telnet duration (M4) is not judged**, so a Telnet flow kept alive past the run without payload to the relay is not caught by this rule; with payload to the relay, M3 catches it.
7. **The sensor host** (AP-36, one of HR-24's preconditions). Every comparison reads the sensor's records. An attacker who holds the sensor host defeats all of them and needs no tie to do it. This branch is **not narrowed** by the rule and stays with HR-21 and AP-36 (D3's N4).
8. **A move of the sensor's clock during the spoofed flow:** a move back shortens its apparent duration, and a measured move forward widens M4's bound by its size. Both help against M4 only.
9. **The route preconditions stay as HR-24 states them:** spoofing the node's IP and MAC, control of the clock, and the relay's credentials. The rule removes no precondition.

So HR-24 would narrow, outside the sensor-host branch, from "hidden whole on every route" to: hidden when shaped to the run's profile on a route where the run's own flow is not tied (T1 through the late index or T2, with the run's records lost); hidden within the tolerances of item 3 and on a filled PRP table (item 5); and the same-length substitution on a shared key: where M6b is credited or suspended on a filled PRP table (item 2); a sensor restart or unclean stop across the substitution alerts `incomplete`. Whether that closes HR-24 is D1's call at stage 3, on the measurement, and item 2 brings it back to the owner as ruling 5 says.

### 6.6 Own runs (D6's N1, B4)

- **Each cell's expected outcome, labelled before the run,** is one of:
  - **no alert;**
  - **a designed fail-closed alert** (`no-profile`: a recovered hold, `unknown` retransmitted octets; `incomplete`: the overlap table full, a sensor restart mid-run, and every cell whose `end` is lost, by a declared loss covering it or an unclean stop), counted, with its rate reported;
  - **a known false-positive source**, reported and not counted in the no-alert condition, with its commissioning check or H-row: duplicate capture, reordered own segments (M6b, by O1's choice), and an agent whose length forms exceed M3's + 4 (inference).
- **Runs per cell: *n* = 12,000 seeded, distinct runs** (D6's N1; accepted by D1). In-process cases are deterministic, so each run is a distinct construction from a seeded generator that varies p from 1 to 12, the command and row counts, the reply sizes, the timings, the ports, and where loss and retransmissions fall. The generator and its seeds are pinned by hash before the run.
- **The ceiling it gives.** The target is at most one false `own-session-mismatch` a day, as a 95 % ceiling, at a site of 20 assets polled every 15 minutes over both protocols: 3,840 runs a day, so a per-run rate below 1/3,840 ≈ 2.6 × 10⁻⁴, and by the rule of three *n* ≥ 11,520. At *n* = 12,000 the ceiling is 0.024 false alerts a day for each asset and protocol. It holds only for the simulated distribution; the device behaviours marked `unknown` are outside it. If a rig cell cannot reach *n* in CI time, D4 and D6 propose a smaller *n* with its stated ceiling, and D1 rules.
- **Commissioning checks** (D3's note 3; D6's B4), at each site before M6 is relied on: an own Telnet run with no loss shows zero retransmitted octets to the device, and an own SNMPv3 run shows the sensor's datagrams to the agent equal to the run's sent datagrams. Either failing shows duplicate capture, and the sensor's placement is fixed before the rule is enabled.

## 7. What this needs from contracts and from other roles (for D1)

### 7.1 Proposal sketch: the C13 minor change (D1's ruling 3, approved in principle)

Drafted with the stage 2 work and reviewed by the affected roles. No contract file changes in this PR.

1. **The rule token `own-session-mismatch`.** `Rules` is a closed set (`contracts/netobs/alert.go` l.43), so this is a C13 minor change. **An earlier reader** refuses a stored alert carrying the token, as CH-29 records for a new `degraded` value. The proposal states what follows on the node: on `main`, one stored alert that `AlertFromEvent` cannot read, after the checkpoint's `last_alert_seq`, fails the detector's whole restore (`alertsAfter` in `platform/node/netdetector.go`), and nothing counts it. So the brief "The approved contracts in code" makes the restore skip such an alert, count it under `detector_alerts_unreadable` and raise `network-alert-unreadable` (D1's ruling 2 on #673, 6861593265; `docs/phase4/D4-c13-0.3-proposal.md` §1.2). The store is append-only and loses none, so a later upgrade reads them again. This sentence was corrected on 2026-11-13 in #673; it had said that a rolled-back node counts each refused alert under the refusal count, which `main` does not do; D7's record of versions that roll back together lists the change. The C4 `netobs.alert` event forwarded upstream carries the token as text, and no upstream reader parses `Rules`. The reasons `prp-table-full`, `prp-mismatched` and `no-profile` are in the alert's text, not new tokens. **The minor pins the fixed phrases of §3.2,** `comparison M1` to `comparison M6b` and `reason …`, at the start of `observation`.
2. **Per-direction counts on the `flow` `end` record.**
   - **(a) Payload octets per direction, `orig_payload` and `resp_payload`.** D1 asked me first to check whether the engine's per-direction byte counts already give them. **They do** (§2): Zeek's `orig_bytes` and `resp_bytes` are the sequence span for TCP, without the SYN and FIN octets, wrap-safe, and the summed payload lengths for UDP. So the sensor computes nothing new; it copies them. What C13 still needs is the field, because 0.2 carries `bytes` over both directions only. Its definition: the TCP sequence span per direction, without the SYN and FIN, over 64 bits with wraps; for a midstream join, from the first sequence number seen; for UDP, the sum of payload lengths. Each `end` carries the difference since the previous `end` of the same connection, so a checker's sum by key holds. **What inflates it:** a segment far ahead in sequence, and an ACK beyond the data sent (the span takes the larger of the two); both are noisy, not hiding. **What does not:** keep-alives (`snd.nxt` − 1, at most one octet), the PRP RCT (outside the IP datagram), retransmissions, zero-window probes, VLAN tags and padding. Zeek's `missed_bytes` beside it shows the holes inside the span.
   - **(b) Packets per direction, `orig_pkts` and `resp_pkts`,** from Zeek's conn-size analyzer, for SNMPv3's M2. Whether a fragmented datagram counts once is a stage 2 check (§2).
   - **(c) For M6b, adopted: `orig_overlap_octets`,** §3.3's count, in its one definition: the to-device payload octets of each segment at or below the highest sequence end seen in that direction before it, less a one-octet segment at the highest end − 1; the delta since the previous `end`. **And `incomplete`,** true when §3.3's conditions hold; a tied flow with `incomplete` or without the field alerts and never reads as zero. **For M6a, adopted: `orig_rexmit_inconsistent`,** the count of `rexmit_inconsistency` events to the device.
   - **Who reads them** (D3's N1): the same readers, the same forwarding and the same retention as `login.user`. On an own Telnet flow, `orig_payload` less the approved commands' lengths gives the password's length. A stolen node already learns each secret's length from the redaction marker (C13 §3.2, D4-67), so the field adds no new reader at the site; it never reaches an alert, since the alert states the excess only. The residual is recorded when HR-24 closes.
3. **`login.attempts`** counts password lines the client sent, not prompts (D2's note 4); C13 0.2 says only "the number of attempts".
