## C7 0.6

- **Two admin-signed node kinds.** Both are verified like the 0.5 node kinds: the collector checks the signature, spends the nonce, numbers the decision and changes nothing of its own. The node acts only on an accepted reply (`AdminAcceptance`).
  - **`node.change_approval`:** the asset, `baseline_digest`, `window_start`, `window_end` and `reason` (D4-2 item 1).
  - **`node.baseline_ack`:** the asset, the kind (`configuration` or `event`) and `baseline_digest`.
- **The approver comes from the envelope.** The approver is the envelope's signed principal, and the nonce and expiry are the payload's own, so neither body repeats them.
- **`AdminKey.Kinds`** (D4-2 item 2):
  - A key pinned without a list (`nil`) may sign exactly `DefaultAdminKinds`, the six 0.5 kinds. So every key installed today fails closed for the new kinds.
  - An empty list allows nothing.
  - `ValidateAdminKinds` refuses a kind that is not an admin kind, and a kind listed twice. The collector refuses to start on either.
- **The `authority` check** (D4-2 item 3):
  - It runs after `binding` and before `window` and the collector's `replay`, so a refused approval does not spend its nonce.
  - The refusal stays `admin_unverified`. Only an authenticated signer reaches it, so naming the check gives away nothing about signatures.
  - The decision still takes a `collector_seq`, and the node records it as denied (V-M2, "refused and recorded").
  - A request stamped before 0.6 sees `key` in its place (`Refusal.ForRequest`).
- **The approval's window.**
  - Payload rules: it is canonical RFC 3339 UTC, ends after it starts, and is at most 24 hours long.
  - Window rules: at the collector's clock it has not ended, and it starts at most 7 days ahead.
  - The client default is 4 hours. The collector never fills one in.
  - A3 proposed the 24-hour cap on #209. The 7-day lead is new here: it keeps an approval from lying in wait for months.
- **The reason** is printable UTF-8 of 1 to 256 bytes, with no control character and no line or paragraph separator, so it prints on one line in an alarm.
- **The asset check** (the collector, in the verifier PR after approval): after spending the nonce, the collector refuses an asset it does not collect from with `asset_not_enrolled`. A node therefore learns whether an asset exists only from a request signed by a key allowed the kind.

## C8 0.5

The node writes four actions. Each carries a target asset, a `correlation_id`, and a `config` group with exactly that action's fields.

| Action | Actor | Outcome | Fields |
| --- | --- | --- | --- |
| `config.change_approved` | the verified person | `succeeded`, or `denied` when the node refuses to act on it | `decision_seq`, `payload_sha256`, `baseline_digest`, the window, `reason` |
| `config.baseline_acknowledged` | the verified person | `succeeded`, or `denied` (for example `baseline_not_held`, or B4's `baseline_not_next`) | `decision_seq`, `payload_sha256`, `kind`, `baseline_digest`, and `previous_digest` unless it is the asset's first |
| `config.change_detected` | the node | `warning unapproved_change` (the alarm), or `info approved_change` | `baseline_digest`, `snapshot_digest`, `difference_digest`, `read_seq`, `unchanged_at`, `unchanged_read_seq` (absent when the epoch has no earlier run), and `approval_seq` when covered |
| `config.baseline_restored` | the node | `info` | `baseline_digest`, `snapshot_digest`, `read_seq` of the first read equal to the baseline after a recorded difference |

`decision_seq` is the `collector_seq` of the collector's first acceptance. For a repeat answer, that is its `repeat_of`.

`Admin` (`claimed`, `verified`) gains `kind` in 0.5, so a verifier can tell which kind the collector accepted.

### When an approval covers a difference (`ApprovalCovers`)

1. The approval succeeded, and is for the same node, asset and baseline.
2. **Order, not time:** `decision_seq < read_seq`. `read_seq` is the collector's decision on the read that **first** found the difference. Both numbers must come from one collector epoch.
3. The window overlaps the time the change happened in: it starts before the detection and ends after `unchanged_at`. `unchanged_read_seq` is the asset's last run of the same operation before the read that found the change, and `unchanged_at` is that run's record time. With no earlier run in the collector epoch, `unchanged_read_seq` is absent and `unchanged_at` is the time of the `collector.seq_reset` that began it. Both name a record already in the chain, so the node cannot choose how early the change happened (B6 on #250). A run that found nothing, or found the last recorded state, still counts: naming a later run than the last equal read only narrows what an approval covers.
   - The platform cannot place a change more finely than between two reads. A window that ended between them covers a change made after it ended; reading more often narrows that (B6's note on #250).

### What `VerifyConfig` checks over the chain

- Each approval and acknowledgement follows a real acceptance:
  - an allowed `collector.request`, earlier in its epoch;
  - of the matching `verified.kind`;
  - verified for the record's actor;
  - for the same `payload_sha256`.
- Each detection names a real read: an allowed run on the same asset, earlier in its epoch.
- Each detection's `unchanged_read_seq` and `unchanged_at` name the asset's last run of that operation before the read, or the epoch's reset (rule 3).
- **Acknowledged baseline.** Each detection, restore and succeeded approval names the configuration baseline that the asset's last succeeded configuration-kind acknowledgement set. A node cannot compare against, or approve changes to, a baseline no person acknowledged (R4.8; B6 on #250). A run of records must therefore start before the acknowledgement of each baseline it names.
- Each `approval_seq` names an earlier, succeeded approval in the epoch that covers the detection.
- **No late approval.** The node writes `config.change_detected` when a read finds a configuration state it has not yet recorded against the baseline, not on every read. Once a difference from a baseline is recorded as unapproved, no later detection against that baseline may be approved until a `config.baseline_restored` follows the alarm. So an approval accepted after a change was found never silences that change, even when a later read records it again. Ending the alarm takes a signed baseline acknowledgement, or a recorded return to the baseline.
  - The return is a C8 record, not a hold or an `unchanged_at` the node states. That puts it in the chain, where pruning cannot remove it and an auditor sees it. A change made and reverted before anyone acknowledged it is itself worth seeing (B5's option 2 on #250).
- **Succession.** Each succeeded acknowledgement names, as `previous_digest`, the baseline of its asset and kind that the last one in the run set (B4 on #250). C8 alone then shows the chain of baselines after the baseline records are pruned.
  - An earlier draft keyed this on `difference_digest`. That fails, because a C9 Difference names its snapshots by digest, and each read's snapshot has its own invocation ID and time. The same change therefore gets a new `difference_digest` on every read.
- **A `collector.seq_reset` starts a new epoch.** An approval does not survive a collector reinstall.

The mutants I ran against these rules: drop the order check, the epoch increment, the late-approval rule, the restore's clearing or its read check, the succession check, the window, the window's start edge, the kind check, the person check, the read's asset, or the baseline match. Each fails a test. A mutant that lets a denied approval into the approvals map survives, because `ApprovalCovers` refuses a denied approval on its own. That layer is redundant on purpose.

## The enrolment step (adds to `docs/phase3/A3-admin-keys.md`, procedure 1)

This takes effect with the collector change that follows B1's approval of C7 0.6. Until then, the collector's config loader does not read `kinds`.

5a. **Decide which kinds the key may sign, and list them.** A key entry without `kinds` signs only the credential, asset-clear, quarantine-clear and reset-acknowledgement kinds. To let a person approve configuration changes or acknowledge baselines, list every kind they may sign:
```json
{"key_id": "ed25519-…", "public_key": "<base64>", "principal": "<person>@<site>", "status": "active",
 "kinds": ["credential.install", "credential.revoke", "credential.clear_suspension", "asset.clear_suspension",
           "node.quarantine_clear", "node.seq_reset_ack", "node.change_approval", "node.baseline_ack"]}
```
- The list replaces the default. It does not add to it, so a key listed only for `node.change_approval` can no longer sign credential requests.
- The start log names each key's kinds.
- Record the list in the site's change record with the fingerprint.
- Changing the list is a `collector.json` edit by the host's local administrator, the same trust as pinning the key.

## Limits

- **The approver may be the person who changed the relay.** Nothing observes who changed a relay until engineering access (R2) exists. So this is a recorded limitation that R2 can close (D4-2 item 4).
- **An approval is broad.** It covers any difference from its baseline within its window, not named settings. The 24-hour cap bounds this, and the alarm text must show which approval silenced a difference (P4-A3's risk).
- **A node can still forge records.** A node that forges records can forge all of them, as for any collector event. `VerifyConfig` stops a node from silencing an alarm by citing:
  - an acceptance numbered after the read;
  - one of another kind or another person;
  - one from before a reinstall.
- **`VerifyConfig` needs the referenced records.** The acceptances and reads it checks must be in the run of records it is given: the chain from its start, or from a checkpoint before them. It keeps no state between windows, unlike `VerifyCollectorSeqFrom`.
