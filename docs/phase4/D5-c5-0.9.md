# C5 0.9: two stream classes for the passive network sensor (P4-4-A5)

D5, 2026-11-07. This is a proposal for `otsec.store/0.9`, the C5 draft that brief P4-4-A5 allows (`docs/agent-handoffs.md`, item 4 Stage A). It takes section 3 of the approved node note, `docs/phase4/D5-sensor-node.md` (#525), and turns it into contract text. D1 approves it together with D4's C13 `otsec.netobs/0.1` (D4-68). Nothing here is built yet. Every result it promises will be `simulated` or `desk`.

As in 0.7 and 0.8, the store's part and the node's part are kept apart. The store can enforce only what it can see: a record's class, its size, its database and its consumers. The node enforces the rest: what is resolved, what is coalesced, and the floors.

**C13's records are C4 events** (Question 1, answered by D4). Alerts are C4 `telemetry-health` events of type `netobs.alert`, in C10's departure-alarm form, which needs no C4 change. Observations are a new C4 kind, `network-observation`, with an optional `netobs` field: an additive C4 0.3, which D4 owns. So both use the store's event path, and section 2 says what that means.

| class text | | each class says what it holds and why it drops |

Nothing else in the contract changes: no new `FullAction`, document kind, hold code or error code, and no new store table or format.

**`network-observation`** holds C13 observations: what the sensor observed (C13 §4). **A first-sight observation carries its cited frames as its C5 `Capture`**, at most 8 frames of at most 2,048 bytes each (C13's `MaxFrameBytes`), so at most 16,536 bytes as a classic pcap with its headers, about 17 KiB (D4). A repeat observation carries its citation only. This changes the node note §4, where every observation carried only its citation. The reason is D4's: the node's detector raises the alerts, and it can't read the sensor's capture ring, which may rotate first under a flood. **`network-alert`** holds C13 alerts. An alert's capture holds the frames it cites (up to 4 flows, 2 frames each, C13 §7.1), taken from the first-sight captures. Where it is byte for byte one first-sight capture, it has the same SHA-256 and the store keeps the bytes once. Where it combines frames from several, it is a capture of its own. Either way it is charged to the alert class (section 2). **The alert record carries the capture's bytes, not a bare reference** (D3). The detector reads them from the `network` database, through the first-sight observation it consumed, and never takes a reference or bytes from the sensor. So `Capture.Validate` checks the hash against the bytes, and the store dedups it, as for any record. Captures are per database, so an alert can never reach a SER or transcript capture in another one. Under C13 0.1 only the node raises alerts, and the node refuses an alert-shaped record from the sensor.

**Why `drop-and-count` for both.** The sender is the monitored network, which can't be slowed or asked to resend, as for Syslog over UDP. `stop-collecting` would blind the sensor. `refuse-new` would back up into the sensor's memory, and from there into the same drops. `fail-closed` is for operations that need a record, and nothing waits on an observation. So at the quota a new record is dropped and counted, and the alarm says so.

**Why two classes.** A quota is per class. An attacker can make observations at will, from new flows or spoofed addresses. With one class, a flood of observations would take the room the alerts it triggers need. This is the HR-11 lesson that made `syslog-unknown` a class of its own in 0.4.

**Why a record cap for both.** Only the node writes the store, but the bytes come from the sensor, which parses hostile input (AP-33). A cap bounds what one record can take, whatever the sensor sends:
- **The alert cap** bounds an alert with the capture it cites, which is counted against the alert class (section 2). C13 sets how many frames an alert may cite and the sample size of a coalesced alert. The cap must hold the largest alert C13 allows, and the node checks that at load.
- **The observation cap** bounds an observation with its capture, if it carries one. A first-sight observation's capture is at most about 17 KiB (16,536 bytes, D4), so the smallest cap C5 allows, `MinRecordBytes` (64 KiB), holds it with room to spare. The node can set that, and checks at load that the cap holds C13's largest first-sight observation.
- A record over its cap is refused with `CodeRecordTooLarge` before it is queued, as for configuration today.

**Why a database of their own** (`Layout.Validate`). A database has one writer lock. The note puts the network classes in their own `network` database, so a flood can't hold the lock of the SER, Syslog, audit or configuration databases. Today that is the node's layout. 0.9 makes it a contract rule, as it already is for audit and configuration, so a later layout can't put a network class beside SER by mistake. The two network classes may share a database, because each still has its own quota. (`network-observation` floods are the reason for the rule, and sharing a lock with alerts is accepted: an alert waits at most one commit.)

**Why a new alarm.** At the quota, `store-quota-reached` means "the store stopped this class". For the adapter-evidence class that means a read stopped and the device keeps its records. For a network class it means the sensor's records are being lost, which is a blind spot in detection, not a storage fault the device will cover. An operator and the C6 views need to tell the two apart, as `syslog-unknown-full` does for unknown senders. `network-full` is raised once per fill, with `Class` set and `Detail` naming the streams holding the most bytes. It is re-armed by a prune, as every full alarm is. D1 ruled for it (Question 2).

## 2. How the records are stored

**On the C4 event path, unchanged** (Question 1). A record of any class other than audit and configuration must be a pending C4 event of a schema this binary reads exactly. The store writes the assigned seq into its ID (`assignSeq` in `platform/store/commit.go`). Everything the network classes need already works on that path for any class:
- one capture kept once per SHA-256, and deleted only when the last record citing it is pruned (EP-6). So the packets an alert cites live as long as the alert, even after the detector has folded and pruned the observation that first carried them;
- required and best-effort consumers, cursors and prune steps (`ComputeBoundary`);
- forwarding: the forwarder reads C4 events, so an alert can be forwarded and an observation is not, by the node's choice of consumers (section 3).

So 0.9 needs C13's records to be C4 events, and they are (Question 1). One ordering rule follows: the store accepts only a C4 schema this binary reads exactly (`assignSeq`), so C4 0.3 ships in the same release as the node that writes observations.

Typed documents would have needed the document path, which is the configuration class's alone, widened to the network classes, and still a C4 event for each forwarded alert. D4 chose C4 events.

**Capture accounting: each class that cites a capture pays for it** (a 0.9 store change). Today a capture is charged to the class of the record that stored it first. A later record of another class that cites the same SHA-256 adds nothing to its own class, and the capture stays charged to the first class until the last record citing it, of any class, is pruned. With D4's reuse that is a hole:
- an alert reuses a first-sight observation's capture, so the capture is charged to the observation class;
- the detector folds the observation, and it is pruned, but the alert still cites the capture, so the capture stays, still charged to the observation class;
- alerts can therefore hold observation quota for as long as they are kept, and an alert flood would starve observations, which is what the two classes are there to prevent.

So 0.9 charges a network capture, one whose first class (`captures.class`) is `network-observation` or `network-alert`, once to each network class that holds a record citing it:
- **at commit,** a record's capture is added to its class's bytes unless a record of the same class already cites it. That is what `batchBytes` already does within one class;
- **at a prune, discard or removal,** a class's charge for a capture ends when its last record citing it goes, and the capture's row is deleted when no record of any class cites it, as today. The "still cited by this class?" query runs once per capture in a step, so the node PR shows it is indexed by stream and bounded per step (D4);
- **the store format is unchanged** (`otsec.platform-store/2`). The `captures.class` column keeps the first class, and whether a class still cites a capture is a query on `events` by the class's streams.
- **every other capture keeps 0.8's rule exactly** (D6's R1 on #544, D1): charged once, to its first class, until its row is deleted. Only the `network` database has captures of a network class, since a database that holds a network class holds no other (section 1), and a 0.8 binary never opens it (section 5). So no database ever holds captures charged by both rules, and a rollback can't mix them.
- **a class's count never goes below zero.** An update that would take it there fails its transaction instead of being stored, so an accounting drift shows rather than letting a class past its quota (D6's S2 on #544).

Each network class's quota then bounds what that class keeps alive, whatever the other does. A shared network capture is counted twice, which overstates the database's size, never understates it, so the volume rule stays safe. Outside the `network` database nothing changes: a collection run's transcript (platform class) that matches one already stored by SER records (adapter evidence) byte for byte is still charged once, to adapter evidence.

## 3. Pruning: who consumes each stream (node)

C5 never prunes a stream with no consumer, and never evicts an unconfirmed record (ADR-0004 item 9). Without a consumer, a network stream would fill once and then drop everything new, for good.

- **Observations: a required local consumer.** The node's detection module (the network baseline and its detector, D4's note) is a required consumer of the observation stream. Its cursor moves once an observation is folded into a checkpoint that has committed, as `node-suspensions` and `node-holds` do for the audit stream. What is folded becomes prunable. The node never names an observation stream as a forward target's stream, and a node test checks that.
- **Alerts: the forward targets.** An alert stream is consumed by the node's forward targets, as an event stream is today. A required target holds back pruning until it confirms. A best-effort one does so for its replay window.
- **An alert stream with no target: a retention consumer** (D1's ruling, D4-68, Question 3). With no target, nothing would ever prune the alert stream. Benign alerts alone would fill it in time, and from then on every new alert would be dropped (D3). So when the node's configuration names no forward target for the alert stream, the node runs a **required local retention consumer** on it:
  - **How it moves.** At most once an hour, the node moves the consumer's cursor to the last alert committed before the cutoff (`LastCommittedBy`, the existing `CommitIndex` query). It never moves backwards. The alerts it passes become prunable at the next prune step, with their captures (EP-6).
  - **The cutoff advances no faster than twice the monotonic clock** (D3; the factor from D1 in D4-71). The site's time often comes from unauthenticated NTP (AP-22). A spoofed forward step past the retention would otherwise let the next move pass, and the next prune delete, every stored alert, including the alert for what the attacker just did. So each move sets the cutoff to the earlier of two times: now less the retention, by the wall clock; or the previous cutoff plus twice the monotonic time since the previous move. After a start, the bound is the persisted previous cutoff plus a flat hour plus twice the monotonic time since the start, so a forward step gains an attacker at most an hour per restart beyond the doubled rate, and each restart is an audited `service.start`. A backward step only stalls pruning, which is the safe direction: at worst it reaches drop-newest, which is counted and alarmed. The previous cutoff is kept in the move's C8 record. The factor of two lets a lag behind the wall-clock cutoff, from downtime or the other causes below, close at the monotonic rate instead of lasting for good. Status shows both cutoffs and the lag.
  - **Each move is audited.** The node writes a C8 `store.retention_moved` record (C8 0.12, #534 §2.2) of each move before the cursor commits. It names the stream, the old and new seq, the retention, the wall time used, the cutoff, the previous cutoff, and which bound applied. A move after a clock step therefore sits beside the step's `clock.change` record.
  - **The first record is written when the consumer is created** (#534 §2.2). It has `bound: created`, `from_seq` = `to_seq` = the consumer's starting cursor, and no previous cutoff. Its cutoff is the commit time of the oldest stored alert, or wall time less the retention when the stream is empty. Nothing is pruned at creation, so a clock stepped before the consumer's first move can't prune anything, and every later move is bounded from a recorded cutoff. A consumer created again later, after a forward target is removed, starts again with another `created` record.
  - **A move is written only when it advances** (#534 §2.2). The node records a move only when the new cutoff is later than the previous recorded one and the move passes at least one alert. Otherwise it writes and persists nothing, which covers every tick while a backward step stalls the cutoff. "The previous cutoff" and "the previous move" above therefore mean the previous recorded one.
  - **Drop-newest stays, but only within retention.** If alerts fill the quota faster than retention frees it, new alerts are dropped and counted, with `network-full`, until the next move frees room. The alarm is re-armed by the prune that follows a move. Sizing the quota for the retention is still the owner's.
  - **Single-server sites stay allowed** (R1.8). A site with a target doesn't run the consumer: its targets confirm as they do today.
  - **As coded** (`platform/netretain`, `platform/node/netretention.go`; D1 in D4-70):
    - **The setting.** The retention is `network_sensor.alert_retention_days`, from 1 to 3650. It is required with no forwarding target and refused with one. The consumer is `node-retention`, a required consumer of `network-alert/<sensor_id>`.
    - **The start bound.** After a start, the monotonic bound is the persisted cutoff plus one hour plus twice the monotonic time since the start. The hour is flat, not doubled. So the first move after a restart goes at most one hour past the persisted cutoff, and its record says `start`. The consumer evaluates at once after a start, and then at most once an hour. A failed evaluation is retried at the next tick, not an hour later.
    - **Catch-up (D1 in D4-71; D6's F3 and D3 on #559).** A move may advance the cutoff by up to twice the monotonic time since the previous recorded move, and never past the wall time less the retention. A lag behind the wall cutoff, from downtime, a forward clock correction, a cut to the retention, or a consumer created over old alerts, then closes at the monotonic rate. D6's probe (created 60 days after the oldest alert, with a 7-day retention) closes its 53-day lag in 53 days of test clock (`TestCatchUp`). A forward step of the wall clock prunes no faster than twice the monotonic rate. While there is no lag, the bound is held at the wall cutoff, or at the recorded cutoff while a backward step has put the wall cutoff behind it. So an idle stream can't build a lead that a later forward step would spend at once.
    - **Commit times can't go below a used wall time (D3's F1 on #559, D4-71).** The network database, and only it, keeps a wall-clock high-water mark in its `meta` table. It opts in when it is opened (`store.Options.WallMark`, D1 in D4-71), so every other database keeps its commit times as before. Every commit and every cursor save raises the mark to the time it used, in the same transaction. The consumer also raises it at every evaluation (`RaiseWallMark`, D3's F2), so the mark is no staler than the last evaluation even when the whole database is idle. A commit time is the latest of the clock, the stream's last commit time and the mark. Without the mark, an alert committed while the clock is stepped back, on a stream idle for longer than the retention, would land below the recorded cutoff and be passed at the first move after the clock is restored. With the mark, it survives at least half its retention by monotonic time (`TestBackwardStepIdleStream` and `TestBackwardStepIdleDatabase`, D3). A store created before the mark existed starts it at 0, and an older binary ignores the key.
    - **A record that commits and still reports an error (D6's R1 on #559).** C5's `Append` may commit and return the context's error. So after any record error, the next tick first reads the latest record back, and takes the move as made if that record continues the chain from the consumer's cursor.
    - **Status and alarms.** `net_retention` in status shows:
      - the cursor, and whether it is saved;
      - both cutoffs;
      - `lag_s`, how far the monotonic bound is behind the wall cutoff, and `lagging` when that is over one retention period;
      - `unrecorded_to`;
      - `error`, while the consumer is stalled.

      The lag is not the wall cutoff less the recorded cutoff, which would also grow on a stream with no alert old enough to pass. The alarms are:
      - `network-retention-stalled`: raised once while steps keep failing.
      - `network-retention-lagging`: raised when the lag passes one retention period. `network-retention-lag-cleared` follows when it falls back.
      - `network-retention-unrecorded`: at start the store's cursor was past the latest record, so alerts were passed with no record. The consumer is created again at the store's cursor, and its `created` record shows the jump (D3's S1).
    - **The start's audit read.** The latest record is found by reading the audit stream newest page first (500 records a page). The cost was measured on the desk (Linux, 3000 audit records):
      - about 40 ms when the latest page's 500 records are all retention records, so all are parsed;
      - about 7 ms for 3000 records of other actions behind the retention record, which is about 2 µs a record and so about 0.2 s for 100,000.
    - **A lost record.** If the audit stream has been pruned past the consumer's latest record, the consumer is created again with a new `created` record. That passes nothing, so it only keeps more.
    - **The stamp.** `store.retention_moved` exists only in C8 0.12, so its records are stamped `otsec.audit/0.12`. Every other node record keeps `audit.ContractID` (0.11) until item 7 writes 0.12's `keys_digest` and `admin_keys` and moves the stamp for all records. C8's checks read each record's minor on its own, and minors needn't rise along a chain, so the mixed chain verifies.
    - **Release note (rollback).** A node that has written a `store.retention_moved` record can't be rolled back to a binary without the 0.12 readers (#545). That binary refuses the record, and start-up chain verification fails closed.

  **No C5 change is needed for this** (D1 asked me to confirm). The retention consumer is a `Required` consumer under the existing cursor rules, like `node-suspensions` and `node-holds`. It is local, so its confirmation can't be forged from outside. `ComputeBoundary` takes it as it takes any required consumer, and C5 still never evicts a record no consumer has passed (ADR-0004 item 9). C5's best-effort `ReplayWindow` would also make old alerts prunable without a contract change, but its window moves silently with the clock. The required consumer moves only by an audited step, which is why D1 chose it.

## 4. The node's part (`platform/node`, in the node PR)

None of this is contract. It is listed so that reviewers can check the whole bound in one place.

- **The layout.** A `network` database, writer `detection`, exists only when the configuration has a `network_sensor` section (note §5). It holds two streams per sensor, `network-observation/<sensor>` and `network-alert/<sensor>`. Under options (a) and (c) there is one sensor. Under (b) there is one per enrolled sensor host. Each class needs a quota in `store.quotas`, and each quota needs its record cap.
- **The unresolved budget** (D1's ruling for 0.1). Observations whose addresses resolve to no asset may take at most a quarter of the observation quota over the section's planned outage hours. Those over the budget are dropped before they reach the store, counted, and shown in status with their share. It is a rate bound, not an absolute one. To make it exact enough to test (D6):
  - **It is a byte bucket.** It holds at most `B = Q / 4` bytes, where `Q` is the observation quota, and refills at `B / H` bytes per second, where `H` is the outage hours in seconds. An unresolved observation commits only if the bucket holds its bytes (`Record.Bytes`), which are then taken out. So in any span of `t` seconds, unresolved observations take at most `B + t × B / H` bytes.
  - **It runs on the node's monotonic clock,** which the test clock replaces. A wall-clock step neither refills nor empties it.
  - **It starts empty at every start,** so a restart never refills it. Unresolved observations wait for the refill after a restart. The first unresolved address is still reported, because that alert goes to the alert class.
  - Resolved observations never draw on it.
- **Every refused network record is counted by its reason** (D6). The node keeps a separate count for each, in status and in the `intake.drop-counted` event below:
  - **over the unresolved budget:** the node's refusal, before the store;
  - **class full:** the store's `CodeQuotaReached`;
  - **over the cap:** the store's `CodeRecordTooLarge`;

  Each refused record is counted under exactly one reason. The node checks the budget first, so a record it refuses never reaches the store. Coalescing never refuses an alert, so there is no fourth count (D1).
- **Coalescing in C13 uses the drop count's key** (D1, D4-68, D4's to write). Within a window, C13 coalesces alerts per (rule, destination asset, or the unresolved bucket): the key's first alert commits at once, so R6.4's latency isn't held to the window, and if there were repeats a summary with the hit count, the distinct sources and the first flows' citations commits at the window's end. That caps alert records per window at **C13's per-window cap**, which D1 ruled is 2 × rules × (enrolled assets + 1): the first record per key, and the summary if the key had repeats (D4-68), whatever the flows. The bound is for sizing only: coalescing never refuses an alert (D1). Under C13 0.1 only the node raises alerts, and an alert-shaped record from the sensor is refused outright. This replaces an earlier rule of one alert per kind per window, which D4 showed conflicts with the key: a decoy of one kind to an unresolved address would take the slot, and a real alert of that kind to an enrolled relay in the same window would be refused.
- **Dropped alerts, counted per rule and destination asset** (D1's condition, Question 3, keyed as D3 proposed). The store refuses a commit at the quota with `CodeQuotaReached`, but it sees only the class and the stream, not C13's rule or asset. So the node counts each refused alert under the pair (its C13 rule, the asset its destination resolves to):
  - **Why the asset is in the key** (D3's path). An attacker fills the alert quota with alerts of one rule, aimed at an address with no device behind it, each from a new port or spoofed source so that C13's coalescing never merges them. They then send the real write to a real relay. Counted per rule only, its one drop is lost among thousands. Counted per (rule, asset), the decoys all land in one bucket for unresolved destinations, and the real write shows as one drop against the relay. To hide that line, the attacker would have to send traffic matching the rule to the real relay many times, which the operator and the device's own logs would see.
  - **Bounded by configuration.** Every unresolved destination shares one bucket per rule, so there are at most rules × (enrolled assets + 1) counters, the same bound as C13's coalescing. The attacker can't add one.
  - **In status:** beside `network-full`, the class shows the dropped alerts by (rule, asset) since the fill began, and their total. The observation class shows its total, and the unresolved share's drops apart.
  - **Kept across a restart:** while a class is full, the node writes the counts as one C4 `intake.drop-counted` health event on `platform/health`, at most once a minute and only when they changed, once more when a prune re-arms the class, and at a clean stop when they changed since the last write (D6). A crash loses at most the last minute's counts, and status says the counts are since the last write.
  - **Bounded:** the rule is C13's own identifier and the asset is the node's own asset ID, never device text, and the counters are fixed by configuration, so the record stays small whatever the sensor sends.
  - **The observation counts' event is capped** (D1, D4-72, D4's low row on #568). It names the `SensorDropDetailAssets` (8) assets with the most drops and sums the rest in one `asset.other` detail, so the asset details still sum to `count`. With every value at its widest it renders in under three quarters of a default Syslog target's 2048 octets: a health event a target cannot render would stop the health stream's forwarding. A write that fails for any other reason raises `store-commit-failed` on the health stream's database and is tried again a minute later. After a restart, an asset that was summed into `asset.other` starts again from 0 in `dropped_by_asset`, and its earlier drops stay in `other`, so the total stays exact (D6).
- **The floors,** checked at load as the configuration floor is (D4-20 rule 5). The load error names each term and the count behind it:
  - **alerts:** C13's per-window cap × the alert cap, so one window of coalesced alerts always fits. A floor over the whole retention was considered and dropped: at real values it comes to hundreds of GB and would refuse every real configuration (D3). Instead, status shows beside the class's fill **the shortest time in which coalesced alerts could fill it**: the quota ÷ (C13's per-window cap × the alert cap) windows (D3). It is an operator figure, not a load check. If it is shorter than the retention, drop-newest is possible within the retention, and the operator can see that before it happens;
  - **observations:** at least two of the detector's largest fold batches at the observation cap: one batch being folded and one arriving. D4's baseline note bounds a batch at 256 observations (`fold_batch`, its §3).

  The window and the number of rules wait for C13. The per-window cap's form is ruled: 2 × rules × (enrolled assets + 1). They are set in the node PR, and this proposal fixes only the rule.
- **The volume rule** (`platform/node/README.md`, D4-14) gains the two network quotas × `DiskBytesPerQuotaByte` (2.5), plus the `network` database's recovery and last-resort reserves, which follow from its commit cap as for every database.
- **The sensor's alarms** (`sensor-unreachable`, `sensor-record-refused`, `sensor-coverage-mismatch`, `sensor-interface-bound`) are node alarms, not C5 codes (note §6).

**If D6's spoofing-flood test shows starvation from its unresolved legs** (note §9, D1's condition), the unresolved observations become a third class, `network-unresolved`, before the gate. That is one more class constant and its `ActionFor` case in a later C5 minor, one more quota in the layout and the volume rule, and nothing else. I haven't reserved it in 0.9, because the class set is closed and a class nobody uses would be dead code.

## 5. Compatibility

- **The store format stays `otsec.platform-store/2`.** The `network` database is a new file, with the same tables as every database. There is no migration.
- **A 0.8 binary on a store a 0.9 node used** never opens the `network` database, since its layout doesn't name it. The database stays on disk unopened, as a disabled sensor leaves it (note §5). The other databases hold no network class, so nothing in them changes.
- **A 0.8 binary refuses a configuration with a `network_sensor` section,** because the node's configuration decodes strictly. So a node that is rolled back below 0.9 must have the section removed first, or it won't start, and SER collection stops with it. The release note says so. I chose that over making the 0.8 decoder lenient, because a section ignored in silence would leave the operator believing that the sensor runs.
- **Capture accounting across a rollback and a re-upgrade: no drift** (D6's R1 on #544, D1). Per-class charging applies only to captures of a network class, which live only in the `network` database. A 0.8 binary refuses a layout that names a network class (its `ActionFor` knows neither), so it never opens that database. Every other database is charged by 0.8's rule under both binaries, so a rollback, and an upgrade after it, leave every class's count as it was. Nothing marks which binary stored a capture, and no meta key is added.
- **A 0.9 binary on a 0.8 store:** nothing to migrate. With the section, the `network` database is created at the next start.
- **The release note.** A rollback below 0.9 needs the `network_sensor` section removed first. Capture accounting needs nothing.

## 6. Tests

- **`contracts/store`** (with D6's contract tests):
  - `Classes` has nine classes, and `ActionFor` gives `drop-and-count` for both network classes;
  - `FullAlarm` gives `network-full` for both, and `HealthType` gives `store.network-full`;
  - `Quota.Validate` refuses either network class with no record cap, or a cap outside `[MinRecordBytes, Bytes]`;
  - `Layout.Validate` refuses a database that holds a network class with any non-network class, and accepts one that holds both network classes.
- **`platform/store`:**
  - a network record over its cap is refused with `CodeRecordTooLarge`, and one at the cap commits;
  - at the quota a network commit is refused with `CodeQuotaReached`, and `network-full` is raised once, with the top streams, and re-armed by a prune;
  - an alert's capture is kept while any alert cites it, and removed in the step that prunes the last one;
  - capture accounting: an observation stores a capture, and an alert cites it, so both classes are charged its bytes. Pruning the observation ends the observation class's charge only, and the alert class's bytes are unchanged. Pruning the alert deletes the capture and ends the last charge. Two records of one class citing one capture charge that class once. Outside the network classes a capture shared by two classes is charged once, to its first class, and pruning in either order leaves both at their payload bytes; discard does the same; a capture inserted as 0.8 inserts it, with any ID, stays charged once; and an update that would take a class's count below zero fails its transaction (D6's R1, S1 and S2 on #544).
- **`platform/node`** (in the node PR):
  - with no `network_sensor` section, the layout is byte for byte today's;
  - with it, the layout has the `network` database, and a missing quota or cap is refused at load;
  - each floor is refused at one byte below, the alert floor with each of its terms named, and status shows the shortest fill time for the alert class from the quota, the coalescing cap and the alert cap;
  - a first-sight observation's capture over the observation cap is refused with `CodeRecordTooLarge`, and an alert-shaped record from the sensor is refused and counted;
  - the detector's cursor moves only after its checkpoint commits, and folded observations are pruned;
  - an observation stream is never a forward target's stream;
  - the unresolved budget on the test clock (D6), with every count exact. With `Q`, `H` and record sizes chosen so the numbers are whole: the bucket starts empty; after `H` seconds exactly `B / r` unresolved records of `r` bytes commit and the next is refused; after `n` more seconds exactly `n × B / (H × r)` more commit; a wall-clock step changes nothing; a restart empties the bucket; and resolved records commit throughout, unaffected;
  - the refusal counts by reason (D6): records refused over the budget, by a full class and over the cap give three counts, each exactly the number refused for that reason, readable apart in status and in the `intake.drop-counted` event, and no record is counted twice;
  - with the observation class full, SER and Syslog still commit, and an alert still commits on its own quota;
  - D6's count test (D1's condition): with the alert class full and no forward target, `network-full` is raised; K alerts of one rule and J of another are refused; status shows K and J by (rule, asset) beside `network-full`; the `intake.drop-counted` event carries them; and after a restart status shows the same counts;
  - D3's hiding case, worded as AP-36's test on #533: on the test clock with no forward target and a small alert quota, raise distinct-flow alerts of rule R to an unresolved destination in each window, which coalesce to two records per window (the first and the summary), and advance the clock window by window until `network-full` is raised. Then raise one alert of rule R to an enrolled asset A. Status and the `intake.drop-counted` event show a drop of exactly 1 against that (rule, asset) pair, apart from the unresolved bucket;
  - the counts across a stop (D6): after a clean stop and start, status shows exactly the counts before the stop; after a crash on the test clock, at most the last minute's counts are lost;
  - the retention consumer, on the test clock: with no alert target, it exists, and with a target it doesn't; at creation it writes its `created` record and prunes nothing, and so does a consumer created again after a target is removed; a tick that wouldn't advance the cutoff and pass an alert writes nothing; it moves at most once an hour, never backwards, and only past alerts older than the retention; each move writes its C8 record before the cursor commits, and a failed audit write leaves the cursor where it was; the passed alerts and their captures are pruned and `network-full` is re-armed; and alerts filling the quota within the retention are dropped and counted as before;
  - the retention consumer across a forward clock step (D6, D3): with alerts committed over one retention, step the wall clock forward by twice the retention, then let a move run. The `clock.change` record and then the move's C8 record are in the audit stream, the move's record says the monotonic bound applied, and the move passes no alert younger than the retention by monotonic time. After a restart the cutoff advances at most one hour past the persisted one. A backward step stalls the cutoff and passes nothing new, and its stalled ticks write no record (D3, #534 §3). So an early prune is prevented, and the step is recorded.
- **D6's spoofing-flood test** (note §9) is the one that decides whether the third class is needed. It also checks that every labelled resolved observation is stored during the flood. Its unresolved legs decide `network-unresolved`. Its leg that mimics a known pair has a resolved end and isn't budgeted, so a drop there decides a budget per destination asset instead (note §8, D6).

## 8. The network baseline's series (D1's ask and ruling, D4-68; the intake hold from D4-72)

D4's learner builds a baseline of who talks to whom and with which function codes, which a person accepts by a signed digest (AP-36 (1)). The detector judges traffic against the accepted one. Each keeps a checkpoint of its own state. All three are typed documents, not C4 events, so they go on the configuration class's document path, as the event baseline and its checkpoints did in 0.7. D4's baseline note defines the documents, and this section only places them in C5.

**Four series in `DocumentInfo`'s closed table:**

| Kind | Series | Document | Removable |
| --- | --- | --- | --- |
| `evidence` | `baseline.network` | a network baseline, as learned and as accepted | no |
| `working-state` | `netcheckpoint.learner` | the learner's checkpoint, holding the draft baseline | yes: it joins `RemovableSeries` |
| `working-state` | `netcheckpoint.detector` | the detector's checkpoint, holding its folded state and open windows | yes: it joins `RemovableSeries` |
| `working-state` | `netcheckpoint.intake` | the node's intake hold for one run (D4-72, below) | yes: it joins `RemovableSeries` |

- **`Validate` passes thirteen pairs** and refuses every other one, including `working-state` with `baseline.network` and `evidence` with any of the three working-state series.
- **`baseline.network` is never removed,** as `baseline.event` is not (D4-20). A new one is written only when learning completes or a person accepts one, so it grows by signed or alarmed events.
- **Both checkpoints are removed as `eventcheckpoint.detector` is.** After a checkpoint commits, the node removes the older ones of its series on the stream in one step, so one stays, or two for a moment. A removal writes no C8 record (D4-32).
- **Two series, not one** (D1). The learner and the detector are separate required consumers with different lives, and each one's cursor holds back only its own pruning. One combined checkpoint would rewrite the draft baseline at every detector commit.
- **The documents' schemas are their first field** (`otsec.netbaseline/0.1` and `otsec.netcheckpoint/0.1`, names D4's; the checkpoint's half is a field inside it, as in `otsec.eventcheckpoint/0.1`). So the readers that skip by schema prefix (`storedBaselines`, `checkpoints`) skip them, and a 0.8 binary passes over them.

**The learner's consumer** (D1's ruling):
- **Its cursor moves when its checkpoint commits.** The learner folds observations into the draft, commits a `netcheckpoint.learner` holding the draft, and only then moves its cursor on the observation stream. So the class keeps draining through the 7 days of learning, and a restart resumes the draft from the checkpoint.
- **It is retired when the baseline is acknowledged,** with a C8 record (D3's C8 minor, section 7), and from then on it is not among the stream's consumers, so it never holds pruning again. Its last cursor row stays in the store and counts for nothing, because `ComputeBoundary` counts only the consumers the node passes it.
- **Between the end of learning and the acknowledgement,** the learner folds nothing more, and its cursor follows the detector's, so a draft that waits weeks for a person never holds pruning. D1 confirmed this (D4-68), and C13 §8 says the same.
- **Relearning starts a new learner consumer,** with a new ID per learning run, whose cursor starts at the stream's last committed seq. A stopped run is retired, with its C8 record, as at acknowledgement.

**Where they live (node layout).** One stream per sensor, `netbaseline/<sensor>`, of class `configuration` in the configuration database, present only when the `network_sensor` section is. A `network_sensor` section therefore needs `store.quotas.configuration`, and the load error says so, as item 3's does.

**They never stop configuration monitoring** (C6's rule on #444). The network series join item 3's ceiling. The node refuses a write of any of the four that would leave the class above the quota less the configuration module's own floor terms. A refusal raises the node alarm `network-baseline-no-room` once per crossing, is counted by series in status, and never displaces a configuration record. A refused learner checkpoint leaves the learner's cursor where it was, so the class fills toward the observation quota's drop rather than losing the draft. The configuration floor gains the network terms: two of each of the other three series at `ConfigRecordBytes` (1.5 MiB), 9 MiB in all (D6), plus the intake hold's term below, checked at load as the other terms are. The record cap is the class's, `ConfigRecordBytes`, and D4's note must keep each document under it.

**The intake hold, `netcheckpoint.intake`** (D4-72, within 0.9 because nothing wrote it before). The node sets `platform_session` when it commits an observation, but a run's `local_addr` and `connected_at` reach it only in the run's result. So intake holds the flows from the node's own address to the endpoint of a run it has dispatched and has no result for, and commits them, tied or not, when the result commits or at the hold's deadline. The hold is node state, not detector state, and the detector never reads the series.
- **One record per run,** holding the run's request ID (the invocation ID reaches the node only with the reply), the hold's deadline in node wall time, and the held C13 records in arrival order. A release is the same run's record with no flows.
- **Two bounds, and neither evicts** (D3's I1, D1). The run holds at most `connect_retries` + 1 **flows**, counted as distinct flow keys, not records. A record that starts a new flow past that bound commits untied at once and is counted; it never evicts a held flow, so a spoofer can't push the platform's own flow out of the hold. A held flow's later records (its functions and its `end`) wait with it, so the run also holds at most `floor(ConfigRecordBytes / 64 KiB)` − 1 **records** (23), each at most C13's 64 KiB worst stored size, which keeps the run's record under `ConfigRecordBytes` with room for its envelope. A record that would pass that cap releases the run's whole hold untied at once, the record with it, and the release is counted.
- **Its deadlines** (D1). The node can't see a run's own `deadline_ms`, so a run's hold gives way untied at dispatch + C2's `MaxDeadlineMS` + `tie_grace_s`, and at once when the run ends with no result. A failed dial still open when the result commits waits for its `end` until its arrival + `MaxConnectTimeoutMS` + `flow_idle_s` + `tie_grace_s`, and gives way at once on a new sensor `run_id` or degraded coverage.
- **The open table** (part (d) of the baseline note's section 5, D1). A tied flow that is still open after its run's release keeps its key, at most 64 keys, in the newest record, so its later records tie to the same session until its `end`, across a restart. A `start` on an open key never ties through the table: the sensor saw the old flow end, so the entry leaves, written first and counted, and the `start` is judged as a new flow. An entry expires at its latest record + `flow_idle_s` + `tie_grace_s`, in node wall time, saved so that it survives a restart and clamped as the deadlines are (D1 on #576). A run whose session is an unexpired open entry's 5-tuple (an SNMPv3 run reusing its conversation) re-points the entry to its own invocation at its result, and the node writes `open_flow` on its `collection.run` (D1 on #576). A new sensor `run_id` clears the table; a seq gap or degraded coverage does not. Past 64 keys the oldest gives way and is counted, and its later records commit untied.
- **Written before it takes effect.** A hold or release takes effect only once its record commits. A failed write commits the flow untied at once and counts it under the checkpoint-failure counter, with its own alarm. A write the ceiling above refuses is handled the same way: the flow commits untied and is counted (D3's I3).
- **Rebuilt at start** from the newest record of each run, which after the removal below means only the in-flight runs' records and at most one release. A backward clock step can't stretch a hold: on start and at each check, the deadline is the earlier of the stored one and now plus the run's limits plus `tie_grace_s` (D1).
- **Removed after each release** (D3's I2, D1). After a release commits, the node removes every record of that run except one that is the series' newest record on the stream, which C5 keeps. So the series holds only the in-flight runs' records and at most one release, whatever the number of runs ever dispatched, and the start rebuild reads only those.
- **Its floor term** joins the configuration floor: in-flight runs × the per-run record cap (23) × 64 KiB, so each in-flight run is under `ConfigRecordBytes`. The collector runs at most one session per asset, so in-flight runs are at most the scheduled assets.

**Compatibility.** A 0.8 binary never writes or removes the four series, and its readers skip them by schema prefix. Under 0.8, older checkpoints left behind stay, and nothing grows, as for `identity.read` in 0.8.

**Tests:**
- `contracts/store`: `DocumentInfo` over every pair, so thirteen pass and every other is refused; `RemovableSeries` is exactly the seven series; `CheckRemoveConfig` takes both checkpoints and the intake hold, and refuses `baseline.network`.
- `platform/store`: `RemoveConfig` refuses the newest checkpoint of either series and any `baseline.network`, and removes an older checkpoint.
- `platform/node`:
  - with the section and no configuration quota, the load is refused;
  - the floor's network terms are refused at one byte below;
  - one checkpoint of each series stays after each commit;
  - each consumer's cursor moves only after its own checkpoint commits;
  - during learning, on the test clock, observations become prunable as the learner's checkpoints commit, and a restart resumes the draft;
  - after acknowledgement, the learner is retired with its C8 record, and observations become prunable with no learner cursor counted (D1);
  - between the end of learning and the acknowledgement, the learner holds no pruning;
  - relearning starts a new learner consumer at the stream's head;
  - a network write past the ceiling raises `network-baseline-no-room` once, while configuration reads and stores continue to the full quota;
  - a refused learner checkpoint, followed on the test clock: the learner's cursor stays, `network-baseline-no-room` is raised first, then `network-full` once observations reach their quota, and each dropped observation is counted (D6).

## Questions

1. **Answered by D4: C13's records are C4 events.** Alerts are `telemetry-health` events of type `netobs.alert`, with no C4 change. Observations are a new C4 kind in an additive C4 0.3. A first-sight observation carries its frames as its capture, and an alert stores its own capture of the frames it cites, kept once when the bytes are the same, which is why 0.9 changes capture accounting (section 2).
2. **Ruled by D1: `network-full`** (D4-68). A detection blind spot mustn't read as a storage fault, and `syslog-unknown-full` is the precedent. The question was: a dedicated alarm, or `store-quota-reached`? I proposed `network-full`, so that a detection blind spot doesn't read as a storage fault (section 1). The cost is one code and one C6 view row. Using `store-quota-reached` with its `Class` would add nothing to the contract.
3. **Ruled by D1: a retention consumer when there is no alert target** (D4-68, section 3). Drop-newest applies only if the quota fills within the retention. The drop count is keyed by (rule, destination asset), with one bucket for unresolved destinations (section 4), and C13's coalescing uses the same key. D3 records the residual. The question was what an alert stream with no forward target should do. My first draft kept every alert until full and then dropped the newest. D3 showed how a decoy flood could hide a real alert behind that, and the stream would stay blind for good. No C5 change follows, and section 3 says why.
