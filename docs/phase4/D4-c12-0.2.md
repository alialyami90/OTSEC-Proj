# C12 0.2 proposal: cite a mismatch on an operator or passive identity

Author: D4 (role 4, C12's author). Date: 2026-11-06. Status: **proposal, for D1's approval. No code is written until D1 approves it** (D4-59). It is based on `main` at `dbde057`. Evidence class: `desk`. Every statement about the code was read from `main` at that SHA, and nothing was run for this note except where it says so.

It fixes item 3's one accepted C12 limitation (D4-55; [phase-4-item3-exit.md](../phase-4-item3-exit.md), "A mismatch on an operator identity is not cited in the finding", and its next task 3).

## 1. The gap

A device read can refuse an asset's identity: SEL `refused.identity_mismatch`, or SNMP authenticated `failed.identity_mismatch` (D4-54). Under D4-55, an operator-only asset under such a mismatch is treated as a device-read one is. The version reads as unread, each entry naming either model is `applicable-by-version` with `firmware-version` unread, and the declaration's evidence is marked `stale`.

C12 0.1 lets an identity cite only evidence of its own source (`finding.go`, "`%s evidence for a %s identity`"). So the finding marks the operator declaration stale but cannot say **what** made it stale. `markStale` in `modules/applicability/applicability.go` says this in its comment. The mismatch is visible in `identity.read`, in status and in the chain's `asset.suspend` record, but not in the finding. A reader of the finding alone sees a stale operator identity with no cause. On a device-read identity, the same finding cites the mismatch read beside the stale evidence.

A passive identity (R6.7, not built) would have the same gap.

## 2. What must not change

- **An operator's entry never stands as a device read**, and a device read never stands as the identity's own evidence on an operator or passive identity. #440's probe "operator evidence citing a device read" (`contracts/finding/finding_test.go`) must still fail. So must `TestC12EvidenceIsItsSourcesForm` in role 6's `tests/contract/c12_c6_test.go`.
- **D4-57's forms:** a device read is a v1 to v8 RFC-variant UUID, and passive evidence is never `audit:`.
- **No new class or reason.** A mismatch still never makes a finding `confirmed`, and it never makes one `not-applicable` (D4-55).
- **Device-read identities keep their 0.1 shape.** They already cite each read that made them stale (a mismatch or a configuration change) as extra `device-read` entries in `identity.evidence`. Moving them would revise every stale device-read finding at upgrade, for no gain in meaning.

## 3. Options

**A (proposed): a separate field, `identity.mismatch`.** It is a `Read` (`{"id", "at_utc"}`, the type 0.1 already uses for `latest_read`). It names the device read that contradicts an operator or passive identity. `identity.evidence` keeps its 0.1 rule, every entry of the identity's own source, so nothing an operator entered can be read as a device read. The mismatch sits in a field whose meaning is only "this read contradicts the identity".

**B (not proposed): allow `device-read` entries in an operator identity's `evidence` after a stale first entry.** This needs no new field, and it matches the device-read shape. But it makes the meaning of `identity.evidence` depend on position: the first entry is the identity's record, and the rest are contradictions. A reader that takes "any device-read evidence" as support would read a contradiction as support, which is the confusion #440's probe exists to prevent.

**A' (not proposed): A, with device-read identities moved to the new field too.** It is more uniform, but it rewrites every stale device-read finding at upgrade (§2, last point). The device-read list also holds configuration changes, which are not mismatches.

## 4. The contract change (C12 0.1 to 0.2)

`Identifier` becomes `otsec.finding/0.2`. The change is additive, a minor bump, and a 0.1 reader is kept (§6).

```go
type Identity struct {
	Product    string     `json:"product"`
	Version    string     `json:"version"`
	Source     Source     `json:"source"`
	Evidence   []Evidence `json:"evidence"`
	LatestRead *Read      `json:"latest_read,omitempty"`
	// Mismatch is the device read that refused this operator or passive
	// identity (0.2): its C2 invocation ID and when the run ended, as the
	// node's identity.read mismatch object holds them (D4-55).
	Mismatch *Read `json:"mismatch,omitempty"`
}
```

New `Validate` rules. Each is a `conflict` unless it says otherwise:

1. **Form.** `identity.mismatch.id` is an invocation ID (the D4-57 UUID form), a `form` failure otherwise. `identity.mismatch.at_utc` is RFC 3339 UTC with `Z`.
2. **Only on an operator or passive identity.** A device-read identity cites its contradicting reads in `identity.evidence`, as in 0.1.
3. **It means what the matcher does with it.** If present, every `identity.evidence` entry is `stale`, and the class is `applicable-by-version`. That is the only class `entry()` gives under a mismatch to an entry naming either model. An entry naming neither model is `product-not-named` and carries neither the mark nor the field, as on a device-read identity.
4. **A stale operator or passive identity says why** (0.2 records only). Any `stale` entry in such an identity's `evidence` requires `identity.mismatch`. Today a mismatch is the only thing that makes such evidence stale (`markStale`). The rule is skipped for 0.1 records, which were written without the field.
5. **Not in a 0.1 record.** A record whose schema is `otsec.finding/0.1` and that carries `identity.mismatch` is refused (`schema`). The field does not exist in 0.1.

Rules 2 and 3 never let a device read support an operator or passive identity. The read can only appear as the reason that identity is stale.

`doc.go` gains one paragraph under "What a finding holds", saying the same. The "What Validate checks" paragraph lists rules 2 to 4.

## 5. The matcher change (`modules/applicability`, D4)

- `markStale`, non-device-read branch: when `e.mismatched`, set `f.Identity.Mismatch` to a copy of `in.LatestMismatch`, besides the stale mark it already sets. Its comment changes to match.
- `same()` leaves `Schema` out, as it already leaves out the revision fields, the time, the matcher and `latest_read`. Without that, the first evaluation after the upgrade would record a revision of every stored finding only because the schema string changed. With it, a stored 0.1 finding is revised only when its content changes. The one real change at upgrade is an operator finding under a standing mismatch, which gains `identity.mismatch`. It is recorded as one revision, with `from` unchanged (`applicable-by-version`).
- `Version` (the matcher's) is bumped.

## 6. What the node needs (D5), and compatibility

- **The node reads both minors.** Two places compare the schema exactly today: `configdocs.go` (`head.Schema == finding.Identifier`) and the `fold` prefix in `platform/node/findings.go`. Both must accept `otsec.finding/0.1` and `0.2`. I propose a `finding.Known(schema string) bool` in C12, so the node does not hard-code the list. `decodeExact` needs no change: the new field is `omitempty`, so a 0.1 record still decodes and re-encodes to its own bytes, and its `Hash` is unchanged.
- **Rollback is the open point.** On a node built before 0.2, `fold` does not match a 0.2 record's prefix and skips it without an error. The newest finding it then sees for that entry is an older one, so its next evaluation would write a revision whose `previous` names that older hash, forking the chain. `configdocs.go` would refuse the record on a read check. Two ways to close it, for D5 and D1:
  - (a) **Ship forward only, as D4-55 did for C5 0.8 parts 2 and 3**, and say so in the release record.
  - (b) **Before 0.2 merges, a small D5 change** makes `fold` fail closed on any `otsec.finding/` schema it does not know. A rollback then stops with an error instead of forking.

  I recommend (b), because it also covers every later minor. It needs D5's own PR and D1's ruling.
- **Status and V-M7.** `last_evaluation.identity_evidence_id` is unchanged (D4-55). Role 6's V-M7 checker (`tests/integration/vm7/vm7.py`) collects cited IDs from `identity.evidence`, preconditions and mitigations. It must also collect `identity.mismatch.id` before any V-M7 cell expects an operator finding to cite a mismatch.

## 7. Acceptance and proving tests

All are `simulated`, run in GitHub Actions on Linux and Windows (both workflows green on the head).

- `TestGTADV` still passes 128 of 128 cells, and `TestOperatorMismatch` and `TestRevisions` still pass.
- **A new matcher case.** An operator identity under a mismatch gives `applicable-by-version`, the declaration `stale`, and `identity.mismatch` equal to `LatestMismatch`. With no mismatch, the field is absent. When the mismatch names neither model, the finding is `product-not-named` without the field.
- **New `Validate` cases**, each refused: the field on a device-read identity; a bad invocation ID (`form`); the field with a current (not stale) identity; the field on a not-applicable class; a stale operator identity in a 0.2 record without the field; the field in a 0.1 record (`schema`).
  - Each accepted: a 0.1 record with a stale operator identity and no field (the reader is kept); a passive identity with the field.
  - #440's "operator evidence citing a device read" still fails.
- **The upgrade.** Evaluating a stored 0.1 finding with no content change records nothing (`same()`). Under a standing mismatch, exactly one revision is recorded.
- **Role 6's contract tests.** `tests/contract/c12_c6_test.go` is extended: the matrix in `TestC12EvidenceIsItsSourcesForm` is unchanged, plus cases for rules 1 to 5. Every contract change needs role 6's contract tests.
- **The node (D5).** A 0.1 and a 0.2 finding in one stream fold in order. Under (b), an unknown minor fails closed.
