# C4 `otsec.event/0.5`: a `sensor.counters` event that carries several runs

D4, 2026-11-19. **Approved by D1 (D4-119 item 2.5); coded in #755.** This is the C4 0.5 proposal that D1's ruling 6996137498 on #747 asks of D4 (to be recorded as D4-119), after D3's B1 on #747 (comment 6996063511), D5's options (6996107756) and D4's reading of C4 (6996131387). It is Markdown only. D1 approves it, and the code in `contracts/event` changes only after that. **#747 merges after the 0.5 code has merged, or carries it under D1's brief** (D5's N2 on #753): the store checks every event it commits against C4, and the 0.4 code refuses `runs_folded`, so #747's fold cannot pass E5-5 before the 0.5 code, its stamp (E5-7) and E5-3's fixture are on `main`. No build of `main` writes a folded event under 0.4 (ruling 6996137498, item 3).

**Nothing here is built.** Every clause is a requirement. Evidence class: `desk`, read on `main` at `37a82fab`. The size figure in §4 is arithmetic on 0.4's unreproduced estimate, not a measurement.

## 1. Why a minor is needed

C4 0.4 checks `sensor.counters` in `checkSensorCounters` (`contracts/event/validate.go`). Its words are "the sensor's and run's IDs" and "a decimal difference since the previous report", and D4-72 says the differences are "since the last event in the run". So a 0.4 event covers one run.

D1's ruling 6996137498 takes D5's option 1: one waiting `sensor.counters` for each sensor, with the rises of a new run added into it. That bounds the pool and `sensorrun.json` under run churn (D3's B1). The event then carries the rises of several runs under the latest `run_id`. A reader of 0.4 would attribute every rise, a capture loss included, to that run. The event has to say that it is folded. In 0.4, an event refuses any detail its own minor does not define, so the event needs a new detail and a new minor.

## 2. What 0.5 changes, and nothing else

**The identifier** becomes `otsec.event/0.5`, stamped on every event the node writes. As in 0.4 §3, `event.Identifier` is one constant, and `self` in `contracts/event/validate.go` moves to minor 5. No rule of any other event type changes.

**C4-0.5-1. `runs_folded`.** A detail of `sensor.counters`, accepted in an event of minor 0.5 or later:
- Its value is the number of **earlier runs** whose rises are in the event, beside the run that `run_id` names. It is a decimal, at least 1, with no leading zero, and at most 2^64 − 1 (`^[1-9][0-9]{0,19}$`, then parsed). `0`, a leading zero, a sign, a non-decimal value and a value above 2^64 − 1 are refused (`enum`).
- **Which runs count** (D6's B1 on #753). A run counts in an event when at least one heartbeat of that run, taken by the node, added a rise above 0 to the event's waiting entry. Two kinds of run are not counted, and `run_id` never names them:
  - a run that ends before any of its heartbeats is taken;
  - a run whose every heartbeat taken added no rise.

  A run whose rises are split over two events counts in each of them. **"Added a rise" means the rise in the heartbeat, counted before any saturation of the entry** (D6's B3 on #753). A run whose only rise lands on a counter already held at the maximum still counts, and `run_id` names it.
- **It is present exactly when the event carries rises of more than one run.** An event without it means one run, exactly as in 0.4. The validator can check only its form. Whether it is present when it should be, and what count it carries, is the writer's rule, and D5's node test checks it (E5-5).
- It is not a counter. `diff.runs_folded` and `total.runs_folded` are refused as details that the minor does not define.
- In an event stamped 0.4 or earlier, `runs_folded` is refused, as the code on `main` already refuses any detail its minor does not define ("not a detail of sensor.counters in otsec.event/0.4", `checkSensorCounters`).

**C4-0.5-2. What `run_id` and `diff.<name>` mean in a folded event.**
- `run_id` names **the latest run** whose rises the event carries.
- Each `diff.<name>` is the sum of the rises that the node took for this sensor **since the previous `sensor.counters` written for this sensor in the same position generation**, across runs.
- **The runs folded into one event share one position generation** (D3's B1 on #753). A `new`, `rekey` or `replace` enrolment begins a generation, and a `renew` with the pin unchanged keeps it (`docs/phase4/D5-sensor-node.md`, enrolment).
  - At an enrolment that begins a generation, the waiting `sensor.counters` is never folded into the new generation's runs. It is written first, or kept as its own entry until its budget allows.
  - Only an administrator-signed, audited enrolment creates that extra entry, at most one per enrolment, so the bound of D3's B1 on #747 still holds against the sensor.
  - *Why:* `sensor.counters` carries no generation or key. A fold across a `replace` would put the replaced host's capture loss and `diff.frames_outgoing` under the replacement's `run_id`.
- In an event without `runs_folded`, both keep their 0.4 meaning: one run, and the difference since that run's previous report.
- C4-0.4-2 is unchanged, applied to the summed values: `capture_loss` names, in order, the capture-loss counters whose summed `diff.` is above 0. C4-0.4-3 is unchanged: `diff.packets` is always present.
- *Why a count and not the folded runs' IDs:* the event stays bounded (§4). **The cost is that a folded event cannot be split back into its runs** (D3's N1 on #753).
  - Accepting a run on the link writes no event, and a run with a clean `prior` writes none at all (D5-9).
  - Only a run with a declared loss, or one that did not end cleanly, has its own `sensor.run-loss`, which stays keyed by its run.
  - §6 states the limit.

**C4-0.5-3. A value at the maximum is a lower bound, and the writer never wraps.** A `diff.<name>` or `runs_folded` of 18446744073709551615 (2^64 − 1) means **at least** that many. This is reader-visible text. The validator does not change: it already accepts that value and refuses anything above it (0.4's E4-8).

The writer's rule (ruling 6996137498, item 4; D5's N1 and D3's B2 on #753):
- **A sum is never wrapped.**
- **Holding the maximum is always the fallback.** A single rise can be 2^64 − 1, since the counts are the sensor's own report (AP-36). So two runs inside one spacing window can pass the maximum while no write is allowed.
- **Any early write stays within the name's budget** (CH-45). A write outside it would hand the write rate to the sensor.
- **While a value is held at the maximum,** the sensor's status names the saturation until the entry is written. Later runs still raise `runs_folded` and move `run_id`. `capture_loss` still names every capture counter that rose.
- So the clause can apply under any design. D5 chooses to hold the maximum, with no write-first path (D5's 6996234057 on #753), and E5-8 tests it.

**Unchanged:** `reported_by`, `sensor_id`, the 21 counter names and their meaning, `capture_loss`, the required `diff.packets`, `HealthSensorCounters`, and every other event type and detail. `sensor.run-loss` stays keyed by its run.

## 3. Readers and writers

| | Reads a 0.4 `sensor.counters` | Reads a 0.5 `sensor.counters` (folded or not) |
| --- | --- | --- |
| C4 0.3 code | Yes (0.4 §3) | Yes. `runs_folded` is a detail of a later minor, which `checkSensorCounters` accepts (`later`), and `diff.packets` meets its one required counter (C4-0.4-3) |
| C4 0.4 code (`main`) | Yes | Yes, for the same reason. It checks 0.4's rules, and it reads a folded event as one run. That is the misreading this minor exists to remove, and a reader stays exposed to it only until it is upgraded |
| C4 0.5 code | Yes. `runs_folded` is absent, so the event reads as one run | Yes, with C4-0.5-1 checked |

- **No reader floor:** every earlier reader accepts every 0.5 event (E5-3).
- **The writer** is the node (#644 §1.9 item 5; #747).
- **Receivers upgrade first** (C6, `contracts/syslog/doc.go`, "Versions"): every forwarded event's `ev` becomes `otsec.event/0.5`, as with 0.4 (0.4 §3). Syslog renders `runs_folded` as one more `hd` parameter (`contracts/syslog/render.go`). C6 does not change.
- **Rollback, for D5 and D7** (D3's N2 and D6's N2 on #753).
  - **No binary on `main` reads `sensorrun.json`.** At `37a82fab` its name appears in Go only in comments. Its reader arrives with #747, which merges only with the fold, so the first merged form of the waiting entry already carries the fold count.
  - **A rollback past #747** goes to a binary that never reads the file. That binary writes no held entry, marked or unmarked, and the case of 0.4 §3 is unchanged. **D7 has no floor to record from 0.5.**
  - **The rule for any later binary that reads the file:** the run file carries a form version from its first merged form, and the reader checks it. A later version is refused as unreadable (`sensor-state-unread`, cause `run-file`), which is a stated loss and never an unmarked fold. Any later change to what the waiting entry means bumps that version. A reader that decodes the file and ignores the version (plain `json.Unmarshal` ignores fields it does not know) does not meet this rule. E5-9 tests it.
  - A held pool event is still kept as counts and built when it is written (0.4 §3).

## 4. Size

0.4 §4's worst `sensor.counters` rendered in an estimated 1,569 octets against a default target's 2,048, as an unreproduced estimate. `runs_folded` at its 20-digit maximum adds one `hd` parameter, `hd="runs_folded=18446744073709551615"`. That is 37 octets, and 38 with the space that `sd()` writes before each parameter, for about 1,607 octets. That is arithmetic on an estimate, not a measurement. E4-6, the node's size test owed under 0.4, takes `runs_folded` at its maximum into its worst case (E5-6).

## 6. Limits

- The validator checks the form of `runs_folded`, not its truth. That a fold is always marked and the count is right rests on the writer and on E5-5.
- **A folded event does not say in which of its runs a counter rose.** Only runs with a declared loss, or that did not end cleanly, have their own `sensor.run-loss` (D5-9; D3's N1 on #753).
- A 0.3 or 0.4 reader reads a folded event as one run until it is upgraded (§3). Receivers are upgraded first, so this matters only for a receiver that is not.
- A value of 2^64 − 1 is a lower bound (C4-0.5-3). A sensor in a restart loop, or a compromised one, can reach it on purpose (E5-8). No real sensor is known to have reached it.
- The size figure in §4 is arithmetic on 0.4's unreproduced estimate. E5-6 pins it.
- The counts are the sensor's own report (AP-36). A fold sums them and adds nothing to them.
