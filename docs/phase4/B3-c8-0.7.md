# C8 0.7: compared reads and their removal (B3)

Status: proposal for review by B1, B2, B5 and B6. It implements D4-20 rule 3 (reads with no difference, or the same change, are removable; the newest stays) in the audit contract. It changes no rule of 0.6. Everything here is `desk`: tests use fixtures, and no device has been contacted.

## What D4-20 needs from the audit chain

Rule 3 lets the node remove stored configuration reads that show nothing new, but only if the chain can show afterwards that each removed read was one of those, and what it was compared with. Three things follow:

1. Each such read needs a **positive result record** in the chain, written by the node before anything is removed. Without it the remover could not tell, from the chain alone, a read that showed no difference from a read the node simply never recorded a result for.
2. A read that shows **the same change again** needs to name the change, so that a persistent change is held once and not on every read (D4-20 amendment).
3. A removal needs its **own record, written before the removal**, so that a crash leaves the audit naming at least what was removed.

## New records

Both are written by the node (actor type `node`), outcome `info`, with a target asset and a `correlation_id`, from contract minor 7.

| Action | Reason | Config fields |
| --- | --- | --- |
| `config.read_compared` | `no_difference` | `baseline_digest`, `snapshot_digest`, `read_seq` |
| `config.read_compared` | `same_change` | the same, and `change_seq`, `changes_digest` |
| `config.reads_removed` | none | `removed_count`, `removed_first_seq`, `removed_last_seq`, `removed_digest`, `kept_digest` |

`config.change_detected` gains `changes_digest` (C9's digest over the difference's ordered changes), required from 0.7 and refused before. `baseline_digest` becomes optional in the shared `Config` group and is required on every action but `config.reads_removed`.

`removed_digest` is `RemovedReadsDigest` over the removed reads' snapshot digests: `sha256:` and the SHA-256 of each digest as written (`sha256:<hex>`) followed by a line feed, in stream order. The test pins one value so the node's remover and the contract cannot drift.

## What `VerifyConfig` checks

- A `config.read_compared` names a run on the same asset in the same epoch, compares against the asset's acknowledged configuration baseline, and gives that read its only result. A detection or restore for a read that already has a `config.read_compared` breaks the chain, and so does the reverse.
- `no_difference` is refused while a change recorded against that baseline is still open. A restore or a succeeded configuration-kind acknowledgement of the asset ends it (the same event that ends alarms in 0.6), so re-acknowledging a baseline starts it afresh.
- `same_change` names the newest recorded change against the baseline by `change_seq`, and its `changes_digest` equals that change's.
- A `config.reads_removed` takes fewer reads than the chain shows as compared and not yet removed (the newest stays), oldest first. `removed_digest` must match those reads and `kept_digest` must be one that stays.

The remover therefore can take only reads whose result is already in the chain and shows no difference or the same change. A read held as `approved-difference`, `superseded-baseline` or `restored-difference` (D4-19, D4-20 rules 1 and 2) has a detection or restore record, never a `config.read_compared`, so it is outside what any removal record can name.

## Crash behaviour

The node writes `config.reads_removed`, receives the receipt, then removes. If it stops between the two, the chain names reads that are still stored. On restart the node completes the removal the last `config.reads_removed` names, by seq range, without a new record. The audit may name more than was removed, never less (D4-20 rule 3). `VerifyConfig` cannot see the store, so this rule is C5's and B5's to test.

## Effects on other work

- **Cost.** One extra audit record per compared read. This is the price of rule 3; the alternative, inferring "no difference" from the absence of a detection, cannot be told apart from a lost record.
- **Upgrade.** A node upgraded with an open 0.5 or 0.6 alarm has no `changes_digest` on that detection, so it cannot record `same_change` against it. It re-alarms once (a new detection with a digest) and then holds the change once.
- **B2 / C9.** `changes_digest` needs C9 to supply a digest over the ordered changes of a difference. C9 0.1 has none (`Digest` is over stored bytes). **Assumption, not yet confirmed with B2:** C9 0.2 adds it. If B2 prefers another definition, only the field's description changes here.
- **B5 / C5 0.7 and the remover.** The remover reads the chain for the pending list and the newest kept read, and writes `config.reads_removed` through the store before it removes. A 0.6 binary that opens a 0.7 store ignores unknown actions and prunes nothing held (C5 0.7).
- **B6.** Tests for the existing chains use fixtures at the current contract and now carry `changes_digest` on detections. Older fixtures stamped 0.5 still validate without it.

## Not in this change

- Rule 4 (signed release and export of held evidence). It is not owed by Phase 4; its design is separate.
- Any rule about space pressure. Removal is by seq range only, never by time or space (D4-20 rule 3).
- Any change to C7. The removal is the node's own act and takes no signed request.

## Evidence

`go test ./contracts/audit/` (new file `config_reads_test.go`): a full chain (baseline acknowledged, a no-difference read, an approved detection, two same-change reads, a removal leaving the newest) verifies; 17 broken variants each fail with the named reason (2 more variants are accepted), a re-acknowledged baseline accepts and a replaced one is refused, and 61 single-record field cases are refused and 8 accepted. Fifteen one-line mutants of `VerifyConfig` and the validators were applied to check the tests catch them; the one that survived (the acknowledgement not ending an open change) led to the A to B to A acknowledgement test, which now kills it. The JSON schema is cross-checked against the fixtures with `jsonschema` (all valid fixtures validate; the invalid ones that the schema cannot express, the cross-field rules, are the same kind as the existing ones).
