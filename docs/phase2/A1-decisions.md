## D2-9: RELP/TLS peer check is by name, not by CA alone

**Evidence:** A6, `desk`/`simulated`, rsyslogd 8.2312.0 with librelp 1.11.0. With `tls.authmode="certvalid"`, imrelp accepted a self-signed client certificate that the CA never signed. With `tls.authmode="name"` and `tls.permittedPeer` set to the node's name, imrelp refused that certificate, a missing certificate, and a stranger's certificate.

**Rules:**
- C6 commissioning requires the receiver to use name mode with `permittedPeer`, never `certvalid`.
- A durable acknowledgement needs `queue.type="Direct"` and `omfile sync="on"` in the receiving ruleset. Without them, `200 OK` can arrive before the write.
- The forwarder checks the receiver's name in the same way, so neither side relies on the CA alone.
- A4 writes both rules into C6 as a minor revision, reviewed by A3 and A6.
- The slice harness configures rsyslog this way.

**Amendment (2026-10-24, A6, `desk`/`simulated`, librelp 1.11.0):** name mode accepted a CA-signed client certificate whose subject CN was the permitted peer while its SAN named another node. The peer check therefore holds only if the CA never puts a node's name in a certificate held by anything other than that node. Commissioning rule: the node CA issues a certificate carrying a node's name, as CN or as a SAN entry, only to that node, and issues no certificate whose CN differs from its SAN dNSName. A4 adds this rule to C6's commissioning text in the next C6 revision. A6's receiver is stricter than librelp (SAN first, CN only when there is no SAN), so tests against it do not depend on this rule.

## D2-10: A third lock: collection endpoints and listeners are loopback only

**Reason (A6, review of #84):** both D2-4 locks read the same `target` label, which an administrator sets. An endpoint with a real relay's address labelled `simulated` passes both. In Phase 2 the only device is the simulator on the same host (D2-3), so a lock that ignores the label costs little and stops a typo from pointing a credentialed session at real equipment.

**Rules:**
- The node's loader refuses a configuration in which a collection endpoint's host, or a Syslog listener's bind address, is not a loopback IP literal (127.0.0.0/8 or `::1`) (A5).
- The collector refuses a run whose endpoint host is not a loopback IP literal (A3).
- Host names are refused, `localhost` included, so the check never depends on name resolution.
- Forwarding targets are not covered, because the upstream collector is not a device.
- Each lock gets its own negative test (A6). Lifting either lock follows D2-4: the owner authorizes a named lab device, and the authorization is recorded in a decision.

## D2-11: The credential install path is a guessing oracle for a compromised node

**Finding (A3, #90):** the node service holds the public half of the collector's install key. It can therefore seal any guess and install it under a new reference whose plaintext scope differs from the target's. The reuse rule replies `secret_rejected` exactly when the guess equals a stored secret, and SEL default passwords are well known. Any refusal that depends on equality leaks equality, however it is worded. The oracle goes away only when the node cannot originate an install.

**Ruling:**
- **Phase 2:** A3's durable install budget (10 installs per hour per node, refused with `rate_limited`, and no shared count in any reply) is accepted as an interim control. It is acceptable because every Phase 2 credential is a lab-only test value (D2-5), no secret of another scope exists, and D2-4 and D2-10 keep every endpoint on the simulator. The budget bounds broad guessing, but it does not stop the attack the finding describes. At 10 per hour, a compromised node can test every published SEL factory password within the first hour (A6 review of #91). So the interim ruling holds only under this condition: no credential installed in Phase 2 is a vendor default password, or a password used on any real device. A6 tests the budget once it lands: the 11th install in an hour is refused with `rate_limited`, the refusal survives a collector restart, and the reply carries no count.
- **Before any `device-observed` endpoint** (that is, before D2-4 or D2-10 is lifted), installs must be authenticated independently of the node. An administrator signs the request with a key whose public half is pinned in the collector, out of band. The signature binds:
  - the reference and the scope;
  - the sealed secret itself, so that a node cannot swap its own guess under a genuine signature;
  - the node ID and the install key ID;
  - the operation (install, revoke or clear-suspension) and the contract version, as a fixed domain-separation prefix, so that a signature for one operation is never valid for another;
  - the admin key's ID, so that rotation and revocation of that key can be audited;
  - an expiry, which the collector refuses if it lies further ahead than a fixed maximum lifetime;
  - a single-use nonce, which the collector spends durably before it makes any decision.

  The node can relay an install but cannot originate one, so only someone who already holds administrative authority can reach the reuse result. Revoke and clear-suspension carry the same requirement (A3 review of #91). A revoke stops collection, and a clear lifts a safety floor, so neither may be originated by the node. A3's design, [A3-signed-credential-requests.md](A3-signed-credential-requests.md), is the C7 0.2 candidate.
- This stays an open high risk in the Phase 2 exit report until that control is merged. A6 may challenge the interim ruling with a test or evidence. A safety or security objection from A6 is not overruled by this decision (brief §5.7).

## D2-12: TLS references resolve from files in Phase 2 (lab only)

**Context (A5):** the node must resolve C6 `trust_anchor_ref` and `client_credential_ref` before it can forward. A3's design (credential design §9) uses `nodekey_` references, a node key register, and a non-exportable key in the `NT SERVICE\otsec-node` certificate store, created from a CSR the node generates. That is C7 0.2 work. It needs a Windows certificate store implementation, which will not be ready for the slice.

**Ruling:** for Phase 2 only, the node resolves these references from files. This resolver is labelled lab-only.
- The node configuration gains `tls_dir`. On Windows this is `OTSEC\config\tls`.
- `<ref>.pem` holds a trust anchor. `<ref>.crt` and `<ref>.key` hold a client credential.
- References match `^[a-z0-9_-]+$`, so a reference cannot name another path.
- `tls_dir` itself must pass the store's directory rule, which also refuses junctions.
- Each file must be a regular file. Symbolic links, reparse points and Windows device names (such as `con.pem`) are refused. The checks run on the opened handle, not on the path, and each file has a size limit.
- Every file must pass the same owner and ACE rule, not only the key: mode 0600 on Linux, or the store's owner and ACE rule on Windows (A3's #84 notes apply). The node itself has no write access to any of them. A trust anchor the node could write would let an attacker sit in the middle of the required audit path (A3 review of #95).
- No file content appears in any log or error.
- `forward.ClientTLS` resolves and checks everything before the node starts. A missing or bad reference stops the node; it never falls back to another reference.
- The certificates and keys are test material only (D2-5). No key used here is used anywhere else. The key is stored unencrypted, which is part of the gate limitation below.

A3's §9 design remains the target. Until it lands, the file resolver is a gate limitation, and a `device-observed` deployment (lifting D2-4 or D2-10) needs §9 first. A3 reviews this resolver.

## D2-14: C2 0.2 closes two gaps in the QUI rule

**Context (A2, #99):** A2's `FuzzRun` found two sessions where no result could both follow the safety rule and pass `Validate`. The adapter followed the safety rule. The collector would then quarantine the result (#82) rather than use it. Neither state has been seen on a device. The manual does not describe either reply.

1. **A reply at Level 1 ends in `Password: ?`.** Anything sent now is a password attempt, so QUI would be a second attempt (C-19). D18 wanted QUI because Level 1 was reached.
2. **A rejected probe reply prints `=>` or `=>>`.** D16 sends nothing after a rejected probe, not even QUI. D18 wanted QUI because a prompt above 0 was seen.

**Ruling:** both are closed in C2 `otsec.adapter/0.2`. A1 applied the change, and A2 (C2 owner), A3, A4 and A6 review it.

- **Gap 1 gets a new code, `failed.unexpected_password_prompt`.**
  - It is `failed`, not `refused`, because the session was already under way when the device state appeared. It is a distinct code, not `failed.unexpected_access_level`, so that this credential-relevant state is not hidden behind a code that means something else.
  - It is exempt from the QUI rule. QUI is refused for it.
  - The bytes must back it: Level 1 was reached, an operate-phase line was the last sent, and the last prompt received is `Password: ?`.
  - The asset is suspended with `unexpected-access-level`. Repeating the invocation would send ACC and the password again into the same state, which is the code table's rule for suspension. The credential is not suspended, because the relay accepted the password and nothing was sent at the prompt.
  - The session ends without QUI, so the C7 failed-auth floor applies to the next session (A3's PR 3 sets it again after an exit without QUI).
- **Gap 2 adds `refused.language_probe_rejected` to the codes exempt from the QUI rule.** D16 already requires the QUI probe to be the last line sent, so the bytes are still bound. No new code is needed.
- **Versioning.**
  - `Contract` becomes `otsec.adapter/0.2`, and writers stamp 0.2.
  - Every code records the minor that added it. A result of an earlier minor that carries a newer code is refused, so a 0.1 result can never carry the new code.
  - Results of 0.1 still validate unchanged.
  - The `failed.unknown` example moves to 0.3, because 0.2 now knows every code it defines.

Both states are simulated (fuzz-found). A capture that shows either one (H-13, H-15) is evidence for or against the ruling.

## D2-15: After a collector_seq reset, collection is held until an admin acknowledges; the node keeps asset suspensions

**Context (A5, A3):**
- A reinstall that loses both collector stores starts a fresh state, so `collector_seq` starts again at 1. `audit.VerifyCollectorSeq` then reports the chain as broken, and nothing records the reinstall or raises an alarm.
- A5 proposed a C8 record for the reset. A3 drafted it as C8 0.2: [A3-c8-seq-reset.md](A3-c8-seq-reset.md), in the project files.
- While reviewing #100, A3 found that #97 records no asset suspension from `Code.Suspends`, and that a fresh collector state held no failed-auth floor. Both are fixed in A3's PR 4.
- The node keeps no C1 suspensions (A5).

**Rulings:**
- **The C8 0.2 draft is approved in direction.** A6 still reviews it. A3 writes it into `contracts/audit`, because C8 is A3's.
  - The record is `collector.seq_reset`, with `previous_high`, `first_seen` and `install_key_id`. The admin's acknowledgement is `collector.seq_reset_ack`.
  - `VerifyCollectorSeq` treats each reset as an epoch boundary. A restart without the record still breaks the chain.
- **The node also detects a reset by the install key, not only by the number.**
  - A reinstalled collector whose first reply the node sees can carry a number above the old high mark, for example after replies were lost while the node was down.
  - A changed `install_key_id` is therefore a reset too. The chain still breaks on any gap, which is correct.
  - The node checks the install key before it sends each request, not when a reply arrives. A changed key holds collection before anything reaches the new collector (A6 on #101).
  - From its first start, the node records in the audit chain the install key it trusts. A number that goes back while the key stays the same is not a reinstall. It is a restore of old collector stores, for example `credentials.json` and `state.json` restored together, and it is never acknowledged: collection stays held until the collector is reinstalled with a new key (A6 on #101).
  - Record names, from A3's C8 0.2:
    - The trusted key is `collector.install_key`, written at the node's first start before its first request. Each `collector.seq_reset_ack` makes its key the trusted one.
    - `first_seen` is optional, because a reset found by the key before a request has no reply yet. When it is present, it is checked.
    - The chain breaks on a reset to any key trusted or reset before (a restore, never a reinstall; A3, #110), and on a key change without an acknowledged reset.
  - `collector_epoch` in C7 0.2 replies remains the stronger fix.
- **Collection is held after a reset until an admin acknowledges.**
  - Alarm-only collection was allowed only if a reset could not weaken a safety control.
  - The floor holds from PR 4.
  - Asset suspensions do not survive in the collector, and the node keeps none yet. The condition is not met.
  - The admin acknowledges by confirming the new install key (T-12) and writing `OTSEC\config\admin\seq-reset-ack.json`, which the node and the collector can read but not write (#119). The node refuses an acknowledgement that names the key it already trusted. Before acknowledging, the admin also checks the active register revisions: a fresh state loses the collector's family floors, and node-side suspensions do not carry them (A3 on #101).
- **The node keeps asset suspensions (A5, `platform/node`).**
  - The node records a suspension from `Code.Suspends` on every outcome, even one that fails validation. It audits it as `asset.suspend` (C8 0.2, because collector records do not carry the C2 code reliably) and writes it durably before the next schedule decision.
  - If the `asset.suspend` audit record cannot be written, the node holds all collection on every asset, not only the suspended one, until it can, whatever happens to the file. A hold kept only in memory would be lost on a restart (A5 and A6 on #101).
  - The file is a checkpoint with `through_seq`, and the node always replays the audit tail after it. Suspensions and clears apply in chain order.
  - The rebuild fails if:
    - the stream was pruned past what the rebuild needs;
    - a record does not parse;
    - the file claims more than the stream holds.

    Then the node holds collection on every asset and raises an alarm.
  - Audit pruning never passes the checkpoint's `through_seq`, so the tail the rebuild needs always exists (A6 on #101).
  - An admin clears a suspension by writing `OTSEC\config\admin\clear-suspension.json` (#119), which names the asset and the exact invocation reference. The node clears only an exact match and audits `asset.suspension_clear` (C8 0.2) before scheduling again. It never clears on its own. `asset.suspension_clear` is keyed by asset, C1 reason and reference, and the node takes the reason from the suspension it matched. The collector holds its own suspension of the asset. It lifts that suspension only on the node's C7 0.2 `asset.clear_suspension` request, and only when the request names the same asset and reference as the file the collector reads itself (#117).
  - Once node-side suspensions land, the manual suspension review before a reset acknowledgement is no longer needed. The register revision check stays.
- **Interim only.** The acknowledgement and clear files are the Phase 2 interim. Before any `device-observed` endpoint, both become admin-signed C7 requests, as D2-11 requires for install, revoke and clear-suspension. C7 0.2 is A3's `asset.clear_suspension`, the collector side of the clear, so the signed requests come in the minor after it (A1 on A3's collector-clear design).
- **Gate item.** A3's PR 4 must carry the asset suspension and the fresh-state floor before any adapter is hosted. On main, `hostedRunner` is nil, so no run reaches a device.
- **Reviews.** A6 reviews the node work for reliability and fault injection. A3 reviews it for the trust boundary on the clear path.

## D2-16: A relay's TIDLE bounds the floor only on a direct Ethernet Telnet path

**Context (A6 on #114, A2):**
- `sel751` can now report the TIDLE it parsed from `SHO P 1` (`Config.TIDLE`). The collector could use it in place of the 31-minute fallback for the floor after an exit without QUI.
- TIDLE is the time-out of the relay's own Ethernet Telnet. Through a port server to a serial port, Level 1 lasts as long as that port's `T_OUT`, which can be longer than TIDLE, or 0 (no time-out at all).
- C1 cannot say which path an endpoint takes.

**Rulings:**
- **The collector does not wire `Config.TIDLE` in Phase 2.** The floor after an exit without QUI stays the 31-minute fallback. `sel751` may report the value, but it does not shorten a floor. Under D2-10 every endpoint is loopback, so nothing is lost.
- **C1 gains an endpoint path before any `device-observed` endpoint** (A2's proposal): for example `path: "direct"` or `"port-server"`. A reported TIDLE may set the floor only on `direct`.
- **A port-server path is refused until it has its own rule.** With `T_OUT` unknown or 0, no floor bounds Level 1 after an exit without QUI, so the fallback is not safe there either. The same holds for the failed-auth floor, because a pending `Password: ?` also times out by TIDLE on the direct path only (A3). The rule needs evidence of the port's `T_OUT` (a hardware or configuration check, H-13).
- **An endpoint with no path, or an unknown one, is refused like a port server** once the field exists (A2).
- **A reported TIDLE counts only from an `ok` or `partial` run**, because the serial check comes after `SHO P 1` (A2, A3 on #114).
- **Gate item:** the C1 path field and the port-server rule are owed before the first `device-observed` endpoint, together with the admin-signed C7 requests (D2-15).

## D2-17: An ID reply the adapter cannot read suspends nothing (C2 0.3)

**Context (A6 on #118, A2 #122):** A6's end-to-end run fed the simulator's `ID` reply without its STX and ETX frame. `sel751` reported `refused.identity_mismatch`, and the asset was suspended until an administrator cleared it. A reply the adapter cannot read is not evidence of another device.

**Ruling:** C2 becomes `otsec.adapter/0.3` with `failed.identity_unreadable`. A2 owns C2, A1 approves the change, and A3 (the suspension path) and A6 (safety) review it.
- **When it applies.** The ID reply has no STX and ETX frame, prints a key twice, has no FID line, or has an empty FID. A FID visible in unframed text is neither accepted nor called a mismatch: the adapter does not read unframed text.
- **What it does.**
  - It is decided before auth. ACC is never sent and no credential is used. C2 binds it to the bytes: `ID` is the last line sent, in the probe phase, after an accepted probe.
  - Identity is `not-checked`, and the reply bytes stay in the transcript.
  - It suspends neither the asset nor the credential. A repeat sends only the Level 0 wake, `QUI` and `ID`, which are read-only register lines, at the schedule's rate.
  - The floor and QUI behaviour are unchanged.
- **`refused.identity_mismatch` keeps its suspension** and now covers only a FID that was read and differs.
- **Not silent.** Every run reports the failure. The node's `otsec health` is to show each asset's last code and consecutive failures, so a relay that never frames `ID` is visible (A5).
- **`refused.language_probe_rejected` keeps its suspension** on an unreadable QUI reply. A port that may not be English risks commands meaning something else, as with register rev 3's Spanish state-changing mnemonics (ADR-0005).
- **Versioning.** Results of 0.1 and 0.2 validate unchanged. A 0.2 result cannot carry the new code. The `failed.unknown` example moves to 0.4.

**Evidence: simulated.** Whether a relay or a port server ever strips the `ID` frame is for H-12 and H-13. If one does, the frame rule changes, and this ruling changes with it.

## D2-18: The collector names the suspension it holds, and the node adopts it (C7 0.3)

**Context (A6 on #120):** Suppose the reply to the run that suspends an asset is lost, or the node stops before it records the outcome. Then the collector holds the suspension and the node holds nothing:
- every run was refused `asset_not_enrolled`, which names no cause;
- the administrator's clear file was refused by the node, which held no such suspension;
- `asset.clear_suspension` comes only from the node.

The only way out was a collector reinstall. That fails closed, but the cause was hidden and the recovery costly.

**Ruling:** C7 becomes `otsec.authz/0.3`. A3 owns C7 and the collector side (#125), A5 the node side (#127), and A1 approved the contract.
- **The collector names the suspension it holds.** It refuses a run of a suspended asset with the new code `asset_suspended`. The refusal carries `suspension: {reason, ref, code}`: the C1 reason, the invocation that set it, and the C2 code. The same field rides on `suspension_mismatch` when the collector holds a suspension other than the one a clear names. That covers the identity-mismatch case, where the collector's ref is replaced.
- **The node adopts a suspension only the collector holds.** It records an ordinary C8 0.2 `asset.suspend` with the collector's reason, ref and code, with the detail "adopted from the collector's refusal". The administrator's normal clear file then clears both sides. Adopting only adds a restriction the collector already enforces, so a compromised collector gains nothing.
- **The node checks before it adopts.** C7 checks only the code's shape, because C2 imports C7. The node adopts only when the code is a known C2 code whose `Suspends()` equals the reason. It adopts nothing, and raises `asset-suspension-not-adopted`, when:
  - the code is missing, which is what a collector state written before codes were kept gives;
  - the code and reason disagree;
  - the node already holds another suspension of the asset;
  - the ref is the one whose clear the node is sending;
  - the field fails C7's check, such as a suspension on another refusal code or a malformed ref.

  Each of these alarms is raised once and never quotes the reply.
- **`operator` is never a held suspension.** The collector suspends only from run outcomes. An operator suspension has a principal ID as its ref and no C2 code.
- **Versioning.** A request stamped before 0.3 gets the 0.2 reply, because replies decode strictly: a run gets `asset_not_enrolled`, and a clear keeps `suspension_mismatch`, in both cases without the field. The seal labels are unchanged. The admin-signed requests (D2-11, D2-15) move to the 0.4 candidate.

**Evidence: simulated.** A6 ran it end to end on the real binaries with the node killed mid-run: the node adopted the suspension, and one administrator file cleared both sides.

## D2-19: A probe with no reply suspends nothing (C2 0.4)

**Context (A6 V-S12, A2 #133):** A6's end-to-end run delayed every reply by 20 s against a 15 s step timeout. Up to C2 0.3 the adapter reported a probe with no reply as `refused.language_probe_rejected`. That suspended the asset as `language-not-english` until an administrator cleared it. The same delay later in the session gives `failed.timeout`, which suspends nothing. A slow link is not evidence of a Spanish port.

**Ruling:** C2 becomes `otsec.adapter/0.4`, with a fourth probe outcome, `unanswered`. A2 owns C2, A1 approved the change, and A3 (suspension path) and A6 (safety) reviewed it.
- **When it applies.** No prompt follows `QUI` before the step times out or the connection closes. Part of a reply with no prompt counts too, because the grammar needs the whole reply and a prompt ends one.
- **What it does.** The code is `failed.timeout` or `failed.transport_closed`, and neither suspends anything. `QUI` is the last line sent (D16), and C2 checks that. The floor is untouched, because this happens before `ACC`.
- **Unchanged.** A reply that ends in a prompt is judged by the grammar, and one outside it still gives `refused.language_probe_rejected` and suspends (D2-17). A reply past the response budget is still a rejected probe (A6's requested test, which kills the mutant that would change this).
- **A repeat** sends only the wake and `QUI` at Level 0, at the schedule's rate. ADR-0005 found no Spanish command that begins with `QUI`. A port that really is Spanish gives its full reply on a later run, and the grammar rejects it. The cost is some failed runs before the suspension, and no line is ever sent outside the register (A6). `collection-repeated-failure` after 3 failures makes the repeats visible.
- **Versioning.** A 0.3 reader rejects `language_probe: "unanswered"`, because the enum is closed. A node or collector rolled back on its own would quarantine such a run. The first release that carries this says so, beside D2-20's rollback note.
- **Open for V-S12 (A6 with A5):** health shows `failed.timeout` for both a late device and a hung `SER`. The result's detail tells them apart, but health does not show it.

**Evidence: simulated.** A6 ran the late-device case on the PR's binaries: `failed.timeout`, no suspension, no `asset-suspended` alarm. 6 of 8 mutants were killed, one survivor was equivalent, and the other was killed by the added test (A1 re-ran it). Whether a real relay's QUI reply matches the grammar remains H-12.

## D2-20: The failed-auth floor holds from ACC until QUI (amends D1-20)

**Context (A6 on D2-16, A3 #131):** D1-20 cleared the floor on `=>`. A6 killed the collector after `=>` and before QUI. Nothing was left in the state, but the relay may hold Level 1 until `TIDLE` after the last line. On main the next session landed on the open level 61 s later, and only the adapter's `refused.session_elevated` stopped it.

**Ruling (A3 owns the collector, A1 approved, A6 reviewed):**
- **`=>` no longer clears the floor.** It stamps the floor again and marks the level open (`level_open`). Only a session that sent QUI clears it (`EndAuth`). An exit without QUI sets the floor again from that moment, as before.
- **A process that dies with the level open leaves the floor behind.** The next process counts the floor from when it opened the state, because the level lasted no later than the death. A state with an open level and no floor time is unavailable, which fails closed.
- **Rollback.** A collector built before this change refuses a state file that holds `level_open`, which fails closed. The first release that carries this tells operators so (A6), from `docs/phase2/A3-collector.md`.
- `docs/phase1/A3-credential-design.md` and D1-20 describe the floor as cleared on `=>`; this ruling supersedes that sentence. The start of the floor at `ACC` is unchanged.

**Evidence: simulated.** A6 killed 10 of 10 mutants and ran the kill after `=>` on the PR's binaries: the next two runs were refused `rate_limited`, and no second session reached the device. Whether a real relay holds Level 1 after a dropped connection is for H-13.
