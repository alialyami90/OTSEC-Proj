# Review of C2 `otsec.adapter/0.1` by A4

- **Contract:** C2, `contracts/adapter/`, PR #51 at `e1d6374`. Owner: A2.
- **Reviewer:** A4 (telemetry), as the consumer of the result. The Phase 2 producer turns a C2 `Result` into C4 events, then C6 forwards them. Date: 2026-10-24.
- **Scope:** `result.go` (Result, Transcript, Segment, Redaction, Record, Span), `codes.go` (statuses and the codes that decide whether events are produced), `doc.go`, and the result examples. I did not review the invocation, the probe grammar or the session rules beyond what reaches C4. A3 and A6 cover those.
- **Method:**
  - I read the files against C4 (merged, `contracts/event`), D1-12 and D1-14.
  - I decoded `results/valid/ok.json`, `partial.parse_errors.json` and `failed.access_level_dropped.json` with my own script. For both I checked that `transcript.sha256` matches the data, that each record span selects one SER row without STX, ETX or CR LF, and which fields each record carries.
  - Evidence class: `desk`. All examples are simulated, as their `target` says.

## Outcome: accepted with changes

The result fits C4 well:
- the transcript is stored after redaction, and spans index the stored bytes, which is what C4 `native.evidence` and `span` expect;
- `context_span` maps to C4 `native.context_span`;
- `parse_ok` keeps the bytes of an unreadable record (EP-1);
- the invocation ID is a lowercase UUID, as C4 `collection.invocation_id` requires;
- record spans exclude STX and ETX, so record bytes and `rsha256` stay stable.

Change 1 should land in 0.1, because D1-12 says what an over-limit read is but C2 has no way to report one. Change 2 is a fixture error that would mislead the parser tests. The rest are wording or small additions.

## What C4 changes as a result

C2's `target` (`device-observed` or `simulated`) exposed a gap in C4. A C4 event does not say whether its device was real or a simulator, so a simulated SER read would forward upstream looking exactly like a device read. That breaks P10 (no fabricated validation). I am proposing to A1 an additive C4 0.1 change:

- add `source.evidence_class`, required on device-origin events, with the C1 values `device-observed` or `simulated`;
- set it from C2 `Result.target` for `adapter-poll`, and from the C1 endpoint configuration for received Syslog;
- C6 renders it as the `evc` parameter, so a SIEM can filter simulated events out.

The C4 golden examples come from documented fixtures, so they would carry `simulated`. That matches C1's definition, which includes test fixtures.

## Checked and found sound

- `transcript.sha256` equals SHA-256 of the data in both examples I decoded. C4 `evidence.sha256` and `evidence.length` take it as is.
- Record spans select exactly one row each, without STX, ETX or line ends, in `ok.json` and `partial.parse_errors.json`. `context_span` points at the report header.
- A record with `parse_ok` false keeps its span (EP-1). It becomes a C4 event with `parse_status` `failed` and no normalized part.
- Spans never point into a redaction, so no event's evidence span can contain the marker.
- `refused.*` before connecting has an empty transcript, so no event is produced from it. The `failed.*` examples carry no records (`failed.access_level_dropped` has none), but nothing in C2 forbids a failed result from carrying records parsed before the failure. Whether the producer emits events from those is Phase 2. C4 would mark them like any other adapter-poll event, with the result's code in the producer's health event.
