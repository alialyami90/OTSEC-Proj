# C4 `otsec.event/0.1`: A3 rating of A6 item 5

Reviewer: A3. Date: 2026-10-24. Scope: only the item A6 asked A3 to rate in [C4-A6.md](C4-A6.md), item 5: nothing checks that `source.origin_auth` fits `collection.method`. Reviewed against PR #29 at 3e271a5. This is not a full A3 review of C4.

## Rating: medium, needed before C4 merges

`origin_auth` is the only field that tells a consumer how far it can trust an event's content (AP-22). Today a producer bug can turn UDP Syslog, which anyone on the station LAN can forge, into an event that claims it came from a session the platform opened itself. Nothing downstream can tell the difference. That raises trust in content an attacker controls, which no device claim or producer path is allowed to do.

The rating is not high, because no external input sets `origin_auth`: only platform code does. But the fix is a closed table and a few negative tests, so it should land with the contract rather than after it.

## The allowed pairs

| `collection.method` | Allowed `origin_auth` | Why |
| --- | --- | --- |
| `adapter-poll` | `session` | The platform opened the session to a configured target. How well that link authenticates the device (Telnet, SSH with or without a pinned key) is the endpoint's `downstream_security` label in C1, and C8 records it on every device record. Allowing the TLS values here as well would give two ways to say the same thing, and a reader could take `tls-mutual` on a Telnet poll at face value. |
| `syslog-receive` | `none`, `tls-server-only`, `tls-mutual` | The sender opened the connection. `none` is for UDP and TCP, and the TLS values follow the listener's handshake. |
| `host-push` | `none`, `tls-server-only`, `tls-mutual` | The sender opened the connection, as with Syslog. |
| (platform events) | `platform` | Already enforced. |

Every other pair is rejected. Each pair that is not allowed gets a negative test, including A6's three: `syslog-receive` with `session`, `adapter-poll` with `none`, and `adapter-poll` with `tls-mutual`.

This differs from A6's example in one place: A6 would also allow the TLS values for `adapter-poll`. A3 proposes `session` alone, for the reason given in the table. If A4 later needs the adapter link's strength inside the event, it should be a separate field copied from C1, not a second meaning of `origin_auth`.

## Note, no change needed now

`tls-mutual` says the client certificate verified. It does not say that the certificate belongs to the asset the event is bound to. Until certificates are pinned to assets (C1 `pinned-key`), the asset binding of a `tls-mutual` event is still by sender address, and its confidence should say so.
