## Outcome: accepted

The field gives D1-23 the source it lacked. An adapter-poll event's class now comes from `Result.target`, which `CheckAgainst` ties to the endpoint, which an admin set. Nothing in the chain takes the label from the far end. Nothing here blocks the merge.

## Checked and agreed

- **Strict in C1, open in C4.** C1 refuses a missing or unknown target in every minor. C4 keeps an event with an unknown class from a later minor and reads it as simulated. The two rules differ, but both fail toward the weaker claim, so both are right:
  - a C1 record is configuration, and refusing it stops collection before anything is labelled;
  - a C4 event is already-collected evidence, and dropping it would lose data (EP-1).
- **`CheckAgainst`** checks the invocation, the operation, the asset, the endpoint, and target equality. The producer copies `Result.target` only after this check passes.
- **One endpoint per sender.** `CheckSenders` keeps each (transport, host) pair to one asset per node, so a received message arrives on exactly one endpoint, and its class has one answer.

## Notes for C4 and Phase 2 (no change to this PR)

1. **A relayed message takes the class of the endpoint it arrived on, not the subject's.** A message relayed by an RTAC arrives on the RTAC's Syslog endpoint, and its subject is bound by a content field to another asset (AP-22). Its `evidence_class` is the arrival endpoint's target: the far end the node heard is the relay. I will state this in C4's `EvidenceClass` doc.
2. **A message from an unknown sender has no endpoint.** This is an `asset-unresolved` Syslog event. C4 still requires a class, and none of the D1-23 or D1-24 sources applies. Both defaults are wrong:
   - `device-observed` claims what nobody configured;
   - `simulated` would let a SIEM filter on `evc` hide traffic from an unknown sender, which is exactly the traffic a security analyst wants to see.

   **Proposal for A1:** the node's Syslog listener carries its own admin-set target, and an unresolved event takes it. A lab listener fed by a simulator or replay is `simulated`, and a production listener is `device-observed`. The listener contract (R4.1, Phase 2) defines it. Until then, C4 says the class of an unresolved event is the listener's.
3. **The cross-check is per asset, not per observation (a limitation).** `Validate` accepts a `device-observed` adapter-session value when *any* endpoint of the asset is `device-observed`. An asset with one real and one simulated endpoint would accept a device-labelled value read through the simulator. `CheckAgainst` already stops this on the result path. An observation names its invocation (`source.ref`) but not its endpoint, so the asset record alone cannot catch it. Adding `source.endpoint_id` to adapter-session and syslog-received observations would close the gap. A2's call; it is not needed for Phase 2's simulator-only slice.
