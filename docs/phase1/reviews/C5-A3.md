# C5 `otsec.store/0.1`: A3 security review

Reviewer: A3. Date: 2026-10-24. Reviewed: PR #33 at 2ef46a2 (first read at 63308b3) (`contracts/store/`, `docs/phase1/A5-store-semantics.md`, `docs/phase1/A5-node-posture.md`). The review covers trust boundaries: who can open the store, how audit records are kept and protected, the storage-full actions, and the HR-9 posture condition. A6 owns reliability and fault injection.

**Outcome: accepted with changes C5-A3-1 to C5-A3-3, needed before merge. C5-A3-4 is a decision for A1.** C5-A3-5 to C5-A3-8 are notes.

## What holds as drafted

- **Audit has its own database.** `Layout.Validate` refuses audit mixed with any other class. So a Syslog flood cannot fill the audit quota, and a full audit store does not stop evidence intake.
- **Storage-full actions are fixed in code.** `ActionFor` is a closed switch with no configuration path. No class evicts unconfirmed records. Audit is `fail-closed`.
- **A failed commit stops the Log.** `commit-failed`, `commit-not-durable` and `commit-mismatch` stop it, and every later `Append` returns `log-stopped` until a restart. For audit, that means fail closed until restart, which is the right behaviour.
- **Receipts are sealed** and exist only after a commit at `FULL`. The prune boundary comes only from persisted cursors. Both are needed for audit: a record that has no receipt was never written.
- **Only `relp-tls` targets may be required consumers** (2ef46a2). Plain RELP acknowledgements can be forged by anyone on the path. A forged acknowledgement would let an attacker on the station LAN make the node prune records that were never received, so this rule is a security rule as well as a delivery rule. Agreed.
- **A best-effort cursor never makes anything prunable** (2ef46a2), and there is no forced prune in 0.1. Agreed. This does not settle C5-A3-2(b), because the replay window alone still makes records prunable.
- **Mode changes are audited** (section 4a). C8 now has the action `store.mode_change`, with the new mode as `reason_code` and the causing alarms in `detail`. That fills the `TODO(C8)`. When the audit database itself is the one that failed, see C5-A3-5.

## C5-A3-4: does a full audit store stop device collection? (A1 decision)

Every collector run sends a Level 1 password to a device, and the brief requires credential use to be audited (C8 `collector.request`, `credential.use`). Under C5-A3-3, a run request needs an audit receipt first, so **a full or failed audit store stops credential-bearing collection.** Passive intake (Syslog, `adapter-evidence` already received) keeps going. This narrows the claim in A5 §1 that a full audit store does not stop evidence collection.

- **A3 recommends audit before act for collection too.** Unaudited credential use is what AP-2 and AP-14 are about, and on Telnet the password is already in clear text. Audit volume is small next to evidence: about nine records of under 1 KiB per session. The quota warning gives early notice, and the SER buffer outlasts a short stop.
- **The alternative** is to let scheduled collection continue unaudited while the audit store is full, and to record a single gap record once audit is back. That keeps evidence flowing, but leaves credential use with no record for the length of the gap.

## Section 4: "nothing else opens the store" (A1's question)

**A3 accepts the ACL plus an exclusive lock file for 0.1.** A3 looked for a way around it for an account that is not an administrator and found none. That holds provided the three conditions below are met. All three are Phase 2 implementation rules, not contract changes.

1. **The ACL goes on the store directory, as a protected DACL** (inheritance off), and not only on the files. SQLite creates `-wal`, `-shm` and journal files while it runs, and they inherit the directory's ACL. The default ACL on `C:\ProgramData` lets Users read and create files, and a subdirectory inherits it unless inheritance is turned off. The DACL names the node's service SID only, plus SYSTEM and Administrators, which cannot be excluded on Windows anyway.
2. **SQLite temporary files stay inside that directory, or in memory.** Set `temp_store=MEMORY`, or point SQLite's temp directory at the store directory. Otherwise a large sort writes record content to the service profile's `Temp` folder, under a different ACL.
3. **The collector's SID is not in the store's ACL, and the node's SID is not in the credential store's ACL.** The two processes are separated in both directions (A3 credential design). The collector hands results to the node over IPC and never writes the store.

**Residual, accepted and recorded:** a local administrator or SYSTEM can take ownership, or use backup privilege, and read or change the files whatever the ACL and share mode say. C5 cannot prevent that. Tampering with audit records is detected by the C8 chain, and against the newest records only by a checkpoint held off the node (AP-17). On Linux, the equivalents are a `0700` directory owned by the service user, with `0600` files. `flock` is advisory there, so the lock file only stops cooperating instances, and the file mode is the real barrier.

## Notes, no change needed

- **C5-A3-5, alarms when the store cannot open.** `RunStartup` returns its alarms in the result. If the database that holds `platform/health` is the one that failed, those alarms have nowhere to be stored. Phase 2 needs a channel outside the store, such as the Windows Event Log and node status, so that a storage failure stays observable (principle 5).
- **C5-A3-6, captures are content-addressed.** A capture is kept once per SHA-256 and deleted with the last record that refers to it. A capture is raw device output, so it may contain the echo of whatever the transport sent. HR-3 redaction must happen before the capture is built (C2/C6), never in the store.
- **C5-A3-7, the lifecycle table and the H-11 record should both be signed.** `A5-node-posture.md` ships the H-11 record signed in the release package. The OS lifecycle table should be shipped the same way, so that an operator cannot mark an edition as supported by editing configuration. The label also depends on the node clock. A clock stepped backwards hides an expired edition, but clock changes are audited (C8 `clock.change`), so the change is visible.
- **C5-A3-8, sizing.** The sizing rule in section 5 should include the audit quota with headroom for the longest expected outage of its required consumer, given C5-A3-2(b).

- **C5-A3-9, one collecting node per asset (A1 D1-3).** This is consistent with C7, where a `CredentialRef` is bound to one asset and one node, and its secret is sealed to that node's collector key. Moving collection to another node is therefore also a credential re-install on the new node and a revocation on the old one. C8 records the move as `asset.collector_assign`.

## HR-9: node posture matches what A3 asked

Confirmed. `A5-node-posture.md` section 3 is what HR-9 asked for. The condition `node-os-unsupported` is a standing state: it is shown continuously, raised once, and cleared when the label returns to supported. It is also raised for `OS support unknown`. Raising and clearing are audited (C8 `node.posture_change`). The migration date is recorded at commissioning as an audited admin action (C8 `node.migration_date`), and the condition says when none is recorded. Collection is unaffected. Low severity, rising to medium once the migration date passes, is acceptable.

For the record, two editions in the table are already past their end: Windows 10 Pro 22H2 (2025-10-15) and Windows 11 Pro 24H2 (2026-10-14). A node on either raises the condition at commissioning. That is the owner-accepted Windows 10 Pro case under HR-9.

## Re-check at 24db070 (2026-10-24)

A3 read the diff and ran the package tests, which pass. A3 also ran its own interop probe: an adapter over the real C8 `audit.ValidatePending` and `audit.Seal` (PR #38), with two `SealAudit` batches. The four sealed records pass `audit.VerifyChain` against a head checkpoint built from the returned `ChainLink`. The probe was not committed.

- **C5-A3-1: closed.**
  - `SealAudit` validates every pending record before sealing any, seals in order after the stored head, and returns the new head for the same transaction.
  - `Record.Event` and `CommitBatch` document the audit path.
  - `Layout.Validate` and the startup policy allow at most one audit stream.
  - The `AuditChain` mirror maps directly onto C8: the hex encoding of `[32]byte` is `prev_hash`, and `Genesis()` as all zeros is `audit.GenesisPrevHash`. That makes `TODO(C8)` an adapter, not a change in meaning.
- **C5-A3-2: closed.** The audit prune persists the last removed `ChainLink` in the same transaction, and `Outbox.ChainAnchor` exposes it read-only. For class audit, `ComputeBoundary` counts only required consumers, and a stream with no required audit consumer is never pruned (`TestAuditBoundaryIgnoresBestEffort`, `TestAuditPruneKeepsAnchor`).
- **C5-A3-3: closed.** `AuditBeforeAct` runs the action only with a receipt. Each of these returns `audit-unavailable` and the action does not run (`TestAuditBeforeAct`):
  - a stopped Log;
  - quota reached;
  - an audit database that is not open;
  - a cancelled context.

  A quota refusal no longer stops the Log (`TestQuotaRefusalDoesNotStopTheLog`). That is correct, because nothing was written.
- **C5-A3-4: D1-11** is recorded in C5, C7 and C8.

### One note, no change needed

**C5-A3-10: one bad pending record refuses its whole group.** `SealAudit` refuses the batch, so the other appends in the same group commit also get `CodeInvalid`, and their privileged operations are refused too. That is fail-closed, so it is safe. But a single faulty producer could deny unrelated privileged operations for the length of a group window. Phase 2 can call `ValidatePending` in `Append` for class audit, so a bad record is refused on its own before it joins a group.

**Outcome now: accepted.**
