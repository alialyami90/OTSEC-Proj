# Review of C8 `otsec.audit/0.1` by A4

- Contract: C8, `contracts/audit/`, PR #38, commit 6142ed0. Owner: A3.
- Reviewer: A4 (telemetry), as the owner of C4 (shared node ID, platform timestamp and health events) and C6 (the forwarder that would carry audit records upstream).
- Date: 2026-10-24.
- Scope: `audit.go` (Record, Time, Action, patterns), `seal.go`, `chain.go`, `doc.go`. I checked two things A1 asked for: that C4 health and mode-change events line up with C8 actions, and whether C6 can forward sealed audit records without re-encoding them. I did not review C7, the credential design, or the chain algorithm beyond what forwarding needs. A6 covers those.
- Method: I read the files above against C4 (PR #29 at b157ff8), C5 (`store.mode-changed`, audit read-back as sealed bytes) and the local C6 draft.

## Outcome: accepted with changes

The record and the chain fit what C4 and C6 need. The rule that sealed bytes are never re-encoded (`seal.go`) is what lets a forwarder carry them unchanged. Change 1 blocks, because the node ID is a shared identifier under D1-1. Change 3 should land in 0.1, because a second timestamp model is costly to merge later. The rest are wording and can follow.

## Health and mode-change events against C8 actions

A1 asked whether these line up. They do, with the gap noted in change 5:

| Fact | C8 action | C4 platform event | Source |
| --- | --- | --- | --- |
| Store changes mode (collecting, drain-only, blocked, failed) | `store.mode_change`, reason_code = new mode | health `store.mode-changed` | C5 (D1-4) |
| Storage alarm raised or cleared | `storage.alarm` | health `store.*` (names final in C5) | C5 |
| Node clock stepped | `clock.change` | none today (see change 5) | node runtime |
| A source's clock reported unsynchronized | none, and none is needed: it is telemetry, not a security action | health `time.unsynchronized` | C4 producer |
| Audit cannot be written, so collection is refused | the refusal itself cannot be audited; it goes to node status (D1-11) | health `store.mode-changed` (blocked) | C5 |
| Forward target unreachable or text omitted | none | health `forward.*` | C6 |

The last row is correct as it is: a forwarding fault is telemetry. If it ever needs an audit trail, the action would be `service.*`, not a new C8 action.

## Forwarding audit records (C6)

This is in scope for C6. ADR-0004 lists audit as a forwarded stream, and C5 returns audit records from `Read` as sealed C8 bytes for the forwarder to pass on unchanged. C8 already does its part: `seal.go` makes `Seal` the only encoder and forbids re-encoding. What C6 will do (recorded in the C6 PR, not here):

- An audit record is never rendered from fields. The sealed bytes go into the RFC 5424 MSG part as they are (MSG-ANY, no BOM). They are preceded by a structured element with `node`, `seq` and `hash`, so a receiver can index records without parsing them. The receiver hashes the MSG bytes, not a re-encoding.
- An audit record is never truncated, split or summarised. C6's text-omission steps apply only to event device text. A target with the `audit` stream must have `max_message_octets` at least `audit.MaxRecordBytes` plus header room. Validation rejects a smaller target, so an oversized record cannot occur at runtime. A record that still does not fit is a contract violation and is reported, never dropped.
- Audit goes only on octet-counted or RELP framing. Non-transparent (LF) framing is safe for compact JSON with no raw LF, but RFC 6587 says receivers may also split on other characters, so C6 does not offer it for audit.
- Whether audit must go to a required (`relp-tls`) target is A1's call under ADR-0004 item 6. I recommend it, at least for checkpoints (change 7).

Until C8 merges, C6 refers to `audit.MaxRecordBytes` as TODO(C8).

## Checked and fine

- The pending-then-seal split matches C5 (ValidatePending, then Seal in the commit transaction) and C4's `ValidatePending` pattern.
- Strict decoding via `contracts/internal/strictjson` follows D1-10.
- Secret-named fields are rejected, and digests replace parameters and sent bytes, so a forwarded audit record carries no secret and no raw device output. This matters because a Syslog collector is a weaker trust zone than the node.
- `ActionUnrecognized` as a reader fallback, keeping the record in the chain, matches the open-set rule C4 uses for `kind` and health types.
