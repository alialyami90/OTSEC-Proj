## Outcome: accepted with changes

The model fits the SEL-751 slice well:

- The run request carries no line, no limits and no secret.
- The credential is bound to asset, node, transport and level.
- The prompt-gated slot and one attempt per session are right.
- The probe-only operations are refused for schedules.

Changes 1 to 3 come from what the manual says happens around a wrong password and an unclosed session. They are needed before a credential is used against a relay, simulated or not, because the simulator must reproduce them (A6). Changes 4 to 6 are needed for C2 to build an invocation from a run. Changes 7 and 8 are wording.

## What the manual says, and why it matters here

**A. A wrong password leaves the relay inside the password prompt.**
- S22 p. 7.33: "If the entered password is incorrect, the relay prompts you for the password again (Password: ?). The relay prompts for the password as many as three times. If the requested password is incorrectly entered three times, the relay pulses the SALARM Relay Word bit for one second and remains at Access Level 0."
- So the transport detects a rejected password as a second `Password: ?`, not as an error line.
- C-19 is right that nothing more may be sent, because any next line, `QUI` included, is the second password attempt.

**B. Closing the connection does not reset the access level.**
- S22 p. 7.16, note beside the Telnet server text: "Use the QUIT command prior to closing the Telnet-to-Host session to set the relay to Access Level 0. Otherwise, the relay remains at an elevated access level until TIDLE expires."
- `TIDLE` (TELNET TIME-OUT) is 1 to 30 minutes, with a default of 15 (Table 4.104, Ethernet Port Settings, sheet 2).
- The manual does not say whether a new TCP connection inherits the old session's state. It does say the state outlives the close. That covers both an elevated level and, by A, a pending password prompt.
- Until a lab capture shows otherwise, a new session must assume it can land in either state. This is `unknown` evidence, and A6 should add it to the simulator and to H-12.

**C. The valid password characters are printable ASCII except space, at most 12 characters** (Table 7.54, p. 7.70; Appendix N, p. N.2). The 0 to 32 characters in Appendix C are the RTAC's own Port 1 setting, not the SEL-751's.

| 1 | **The failed-auth floor must outlast `TIDLE`.** After `auth-failed` (and after any session where the credential was sent and Level 1 was not confirmed, such as a timeout or close in the auth phase), refuse runs for that asset for longer than the port's `TIDLE`. Use the value read by `SHO P 1` on the last good session, or 31 minutes when it is not known (the range maximum is 30). The proposed 15 minutes equals the default and is shorter than the maximum. | By A and B, a session opened within `TIDLE` may land in the pending `Password: ?`. Its first byte would then be password attempt 2, and the `QUI` probe would be attempt 3, which pulses `SALARM`, the relay's alarm contact. The floor exists to stop that, so it has to cover the case. | yes |
| 2 | **Split `unexpected-access-level` by when it is found.** (a) If the first prompt is already `=>` or `=>>` before any line is sent (D18, a session left open by B), nothing is sent and no password left the node. That suspends nothing on the credential. C2 adds a before-auth refusal for it (see C2 below). The asset is not suspended either, because `TIDLE` clears the state. The run is refused, recorded, and retried no sooner than `TIDLE`. (b) If `ACC` and the password give a prompt other than `=>` (`=>>`, or `=` without `Password: ?`), the password was sent, and the credential is suspended as today. The design table (section 7) says "The first prompt was already elevated", which is case (a), where no password was sent. That contradicts its own rule ("limited to cases where the password was sent or may have been"). | By the manual, `ACC` only ever reaches Level 1 (p. 7.33: `2AC` goes to Level 2, `CAL` to Level C). An elevated first prompt is therefore left-over session state, not a credential problem. Suspending the credential for it would stop collection over a condition that clears itself. | yes |
| 3 | **`password-prompt-absent` suspends the asset, not the credential**, or say why it should also suspend the credential. `ACC` reached `=>` without asking, so no secret was sent (C2 `refused.password_prompt_absent` requires `credential_sent` false). | Section 7's own rule, as in 2. It matters less than 2, because the relay is in a bad state either way (Level 1 with no password, AP-23). If A3 wants the credential stopped too as defence in depth, that is fine, but the table should say so. | no |
| 4 | **The credential's `access_level` uses the register's token.** The field comment gives `"ACC"` as an example, and the design says "the reference's level is 1". C3 operations carry `access_level` `"0"`, `"1"`, `"2"` or `"C"`. Make the comment and the check use that token, and make bound use a contract function (for example `CheckRun(ref, op, endpoint)`): the reference's level must equal the operation's level. | `ACC` is the command, not the level. Two vocabularies for one value would let a `"1"` operation and an `"ACC"` reference never match, or always match if someone "fixes" the comparison loosely. | yes |

Make `credential_ref` optional, and in `ValidateAgainst` require it exactly when the operation's level is above `0`. | Otherwise every `sel.id` run must name a credential, and a collector that sees a credential may send `ACC` for a read that never needed it. Sending no `ACC` for Level 0 keeps the password off the wire (AP-2). | yes |
| 6 | **Bind the credential to a C1 endpoint, not only a transport.** Add `endpoint_id` to `CredentialRef` (and to `SealAAD`), or to `RunBody`. | C2 needs an endpoint ID, and a C1 asset may have two endpoints of one transport, for example two Ethernet ports, each with its own acknowledgement. Binding the transport alone leaves the collector to guess. The endpoint also carries the downstream security label and acknowledgement scope that C7 already compares. | yes (for C2) |

Either C3 0.2 adds it, or the policy lives in the C1 capability profile (A2 can add `secret_policy` to the profile). A1 to choose. | Rejecting a password the relay cannot hold, at install time, is better than an `auth-failed` suspension later. | no |

## For C2 (my contract), from this review

These are A2 changes, listed here so A3 and A6 can check them against C7:

- **New code `refused.session_elevated`** (before auth, suspends nothing). The first prompt after connect is `=>` or `=>>`. Nothing is sent, the connection is closed, and the result carries the observed prompt.
- **The wake line is withdrawn.** By A and B, a bare line end sent before the first prompt can be a password attempt if the previous session left `Password: ?` pending. The transport waits for unsolicited output first. If it sees none, it sends one line end only when the floor in change 1 has passed since the last session that ended without `QUI`. C2 records which case applied.
- **A rejected password is a second `Password: ?`**, not an error line. My example transcript showed "Invalid Password". I will correct it.
- **Results carry `register_version`** (the run's `register_version`), so every transcript names the package that permitted its lines (EP-4).
- **`Code.SuspendsCredential()`** returns the C7 suspend reason, separate from the C1 asset reason. The credential is suspended only when `credential_sent` is true: `failed.auth_rejected` → `auth-failed`, `failed.unexpected_access_level` → `unexpected-access-level`, `failed.identity_mismatch` → `identity-mismatch`. `refused.password_prompt_absent` follows A3's answer to change 3.
- **Who builds the invocation.** The collector builds the C2 invocation from the accepted run, the C1 asset (endpoint, binding, `pre_credential`) and the profile. It is never received from the main process. A C7 refusal means no invocation exists. A C2 `refused.*` means the run was accepted and the collector then refused it before connecting.
- **Limits have no home yet.** C7 says limits come "from the verified register and the asset's capability profile". Neither C3 nor the C1 profile has them today. I propose `session_limits` on the C1 capability profile, under C2's ceilings. A1 to confirm.

## Checked and agreed

- **The run request is closed.** There is no line, no limits and no secret. Params are bounded printable ASCII and are rendered through `Matcher.Render`, which applies the deny rules. A probe-only operation is refused (`ValidateAgainst`). This matches C3, and with the transport's `Permit` check it closes C-A2-1 twice over.
- **The probe phase stays inside the transport.** `QUI` and `ID` before `ACC` are not requested by any run. They are allowed only by `Permit(probe, line)`. C7 has nothing to add there, which is right.
- **The prompt-gated slot** opens only after `Password: ?` following `ACC` (p. 7.33 shows that exact prompt). One `ACC` and one password per session. No `QUI` after a rejected password. All three match the manual and C2.
- **Plaintext binding.** Telnet and serial are labelled `plaintext-unauthenticated` with scope `lab-only`, the same token as the C1 acknowledgement scope, and the transport tokens match C1's.
- **`identity-mismatch` is not clearable in place.** This matches C1-A3-5 and C2's `failed.identity_mismatch`. A pre-authentication FID mismatch (`refused.identity_mismatch`) sends no password and does not suspend the credential. C7's reason list agrees.
- **Secret write-time check.** A secret equal to any register line, allowed or denied, is rejected. That covers `ACC`, `QUI`, `SER` and the denied `SER C`, so the credential slot cannot carry a command.
- **SALARM.** By p. 7.33, a successful Level 1 access does not pulse `SALARM` (only Level 2, Level C and three failures do). So routine collection does not touch the alarm contact.

## Open, not blocking

- **Serial transport.** C7 allows `serial`. By B, a serial port's session state persists, and nothing closes it. The slice is Telnet (ADR-0005), and C1 already labels serial as plaintext. I would leave serial runs out of 0.1 until a lab capture shows the port behaviour. A3 and A1 to decide.
- **Concurrent sessions.** Table 7.5 limits concurrent sessions, and R106 had a Telnet multiple-session fix (Appendix A). C7's `busy` refusal covers the platform's own sessions, but not a person's QuickSet session on the same port. C2 will report that as `failed.transport_closed` or a timeout. Worth a line in the design's residuals.
