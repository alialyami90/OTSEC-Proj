# Review: C7 `otsec.authz/0.1` by A5

Reviewer: A5 (Windows node runtime and C5). Reviewed: PR #38, branch `claude/project-thread-qj1j9d` at `48b73ba`, `contracts/authz/` and `docs/phase1/A3-credential-design.md`. Date: 2026-10-24.

Scope, as A1 asked: the trust boundary between the node service and the collector service on a Windows node. That covers:

- service SIDs and privileges;
- where credentials and collector state are stored;
- the IPC between the two processes;
- the lock and DACL assumptions C7 shares with C5.

The role matrix, the register signature check and the device-side behaviour are for A6 and A2.

Evidence: everything below is `[doc]` (Microsoft documentation) or `[inferred]`. Nothing has run on a Windows site image. Each Phase 2 rule names the test that would confirm it, in the style of A3's T-1 to T-9.

## Re-check at `0e311a7` (2026-10-24): accepted

- **C7-A5-1, closed.** `CredentialRef.NodeID` and the C8 `node_id` use `node.IDPattern` from `contracts/node`, and the schema says so.
- **C7-A5-2, closed.** C8 records carry `collector_seq` on every collector-reported event, and `audit.VerifyCollectorSeq` finds a missing, duplicated or short number (`TestVerifyCollectorSeq`). A reply without it is not accepted (`TestReplyFailsClosed`). The residual in section 9 now says that auditing depends on the node writing the records, and that `collector_seq` exposes an omission once a later event is reported.
- **C7-A5-3, closed, with one wording item.** The failed-auth time and the counter are flushed before the collector replies, a future failure time counts as inside the floor, and `collector_state_unavailable` refuses every run when the state cannot be read or flushed. The rule names those two values only. It should also name the credential state changes (install, suspension, clearing, revocation), so that a crash cannot lose an `auth-failed` suspension and let the same wrong password be tried again once the floor has passed. This does not block the merge.
- **W-1 to W-4** are in section 2 of the design, with test T-13.

## Outcome at `48b73ba`: accepted with changes

Changes C7-A5-1 to C7-A5-3 are needed before merge. W-1 to W-4 are Phase 2 rules for the credential design document, and they do not change the contract. Notes 5 to 8 need no change.

The split itself is sound:

- the node holds no secret and the collector holds no store;
- the IPC cannot carry a raw line, a limit or a secret;
- a credential is bound to one asset, node, transport and level;
- the sealed install means the node relays ciphertext it cannot open.

What follows is about the places where the boundary depends on something C7 does not yet say.

## Phase 2 rules for the credential design (Windows)

**W-1. The IPC is a local named pipe, and each end checks the other.** `[doc]` The default security descriptor of a named pipe gives read access to Everyone and to the anonymous account. And whichever process creates a pipe name first owns it.

- The collector creates the pipe with `FILE_FLAG_FIRST_PIPE_INSTANCE` and `PIPE_REJECT_REMOTE_CLIENTS`. Its explicit DACL grants read and write to `NT SERVICE\otsec-node` only, plus SYSTEM.
- The collector checks the client's token at identification level (`ImpersonateNamedPipeClient` at `SecurityIdentification`, then `RevertToSelf`), and refuses any SID other than the node's. This needs no impersonation privilege (W-2).
- **The node checks the server.** It gets the server process with `GetNamedPipeServerProcessId`, checks that the process token holds `NT SERVICE\otsec-collector`, and otherwise sends nothing.

This last check matters for the store. If the collector is stopped, any local process can create the pipe name. It cannot get a secret, because installs are sealed to the collector's key. But it can answer `run` requests with forged C2 results, and the node would commit those to C5 as evidence.

- Test: start a second process that creates the pipe name first. The node refuses to talk to it, and nothing is committed.

**W-2. Neither service keeps `SeImpersonatePrivilege`.** `[doc]` Windows grants "Impersonate a client after authentication" to the SERVICE group, so every service, virtual accounts included, has it by default. A service holding it has a known route to SYSTEM, the "potato" family of local privilege escalations. SYSTEM can read every credential (residual in section 9). If the node service kept the privilege, a compromise of the internet-facing process would be one step away from the credential store, and the two-account split would buy little.

- Both services set a required-privileges list (`SERVICE_CONFIG_REQUIRED_PRIVILEGES_INFO`, `sc privs`) that does not include `SeImpersonatePrivilege`. The SCM then removes it from the process token.
- Test: `whoami /priv` run as each service, or the token read in the service's self-test, lists no `SeImpersonatePrivilege`. `[inferred]` that this is enough for the identification-level check in W-1. The test confirms that too.

**W-3. Only the collector can reach devices.** `[doc]` Windows Firewall rules can match a service by its service SID (`New-NetFirewallRule -Service`).

- Outbound to the device subnets and device ports (Telnet 23 for the slice) is allowed for `otsec-collector` only.
- The same traffic is blocked for `otsec-node` and for every other program.

The design already says the node does not talk to devices. W-3 makes that a property of the host, not of the node's code, so a compromised node cannot open a Telnet session to a relay itself. Syslog intake on the node is inbound and is not affected.

- Test: from the node service, a TCP connect to a simulator's port 23 fails. From the collector service, it succeeds.

**W-4. The installer creates the directory tree, and does not inherit it.** `[inferred]`, from the default `%ProgramData%` ACL: Users may create folders, and CREATOR OWNER gets full control of what it creates. The credential design puts a protected DACL on `credentials\`, and C5 puts one on the store directory. But a non-admin user who pre-creates `%ProgramData%\OTSEC\…` before the install owns those folders. An owner can rewrite the DACL whatever the installer sets.

- The installer creates `%ProgramData%\OTSEC`, `…\store` and `…\collector\credentials` itself, with protected DACLs and owner Administrators.
- If any of them already exists with another owner, or with an unexpected ACE, the installer stops.
- The service binaries live under `%ProgramFiles%`, never under `%ProgramData%`.
- Test: the T-3 ACL listing also checks the owner and the parent `OTSEC` directory. A pre-created directory makes the installer stop.

## Consistent with C5, no change

5. **The store ACL and the collector SID.** C7 says the collector's SID is not in the store's ACL, and the node's SID is not in the credential store's ACL. This matches C5-A3 condition 3, which C5 now records in A5-store-semantics.md section 4. W-4 is the same rule for the directories' owners.
6. **Audit before act.** The C7 `doc.go` rule, that no request is sent before the `collector.request` record holds a C5 receipt, is what C5's `AuditBeforeAct` implements on the node side (D1-11). The collector cannot check that the node did this, which is part of C7-A5-2's residual.
7. **The collector needs no durable outbox for SER.** If the node crashes after an accepted `run`, the result is lost before commit. The SER rows are still on the relay, and the next run re-reads them; C4 alignment drops the duplicates. So the collector's durable state is only the state in C7-A5-3, not a second event store. A full C5 store does not stop the collector from refusing or revoking, because its state lives in its own directory.
8. **The fingerprint in the Event Log is not authoritative.** Any local service can write an Application log event under any registered source name, the node included. A reader who checks the install key's fingerprint there should check the event's user SID, which Windows records and the writer cannot choose. The commissioning record stays the reference, as section 4 of the design says.
