Two observations:

- The digest is the C2 `transcript.sha256`, the same lowercase hex. The C5 evidence ref is `"sha256:" + transcript.sha256` (`store.EvidenceRef`). So the chain now names the stored evidence object, which closes the gap A6 raised in A6-chain.md (finding 1).
- A pre-connect refusal has an empty transcript (C2 doc.go), so its session close carries the SHA-256 of zero bytes. That is correct, and a verifier should expect it.

## Should

**1. Say what an open without a close means.** The session-close record is a collector action, and its digest is known only once the session ends. If the collector crashes between `device.session.open` and the close, no close record is written, and after D1-25 none can be written later without the transcript. That was already true before D1-25, but the doc now promises that "every session-close record carries" the digest, and it is silent on the missing case. Change: state in doc.go that an open with no matching close (same `correlation_id`) means the session ended without the collector recording it, and that a verifier reports it rather than treating the chain as broken. This links to V-S13 (every session ends with `QUI`), which A6 checks from the stored transcripts.

## Nit (no change asked)

`ParseRecord` exempts `transcript_sha256` at any depth, not only at the top level. In a later-minor record, a nested `{"ext":{"transcript_sha256":"<text>"}}` is accepted and ignored. That adds nothing new: a nested unknown key with any other harmless name (`output`, for example) is accepted the same way. So A6 does not ask for code.
