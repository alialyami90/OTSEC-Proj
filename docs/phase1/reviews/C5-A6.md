# C5 `otsec.store/0.1`: A6 review

- **Reviewed:** PR #33 at `0ae019c` (`contracts/store/`, `docs/phase1/A5-store-semantics.md`, `docs/phase1/A5-node-posture.md`), A5. A6's probes were first written against `2ef46a2` and re-run at `0ae019c`.
- **Reviewer:** A6, 2026-10-24. A6 reviewed reliability and fault injection; A3 reviewed trust boundaries (`C5-A3.md`).
- **Outcome:** **accepted with changes.** Changes 1 and 2 are required. Changes 3 to 6 should be made. Section "For A6" lists what moves into V-S9 and H-14.

A6 drove `RunStartup`, `Resume`, `Log` and `AuditBeforeAct` from a test outside the package. It used its own fakes of `StartupEnv`, `RecoveryStore` and `Committer`, not A5's `fake_test.go`. The fakes can fail any call, log every call in order, release a reserve without freeing its space, need free space at `Open`, and shrink or not shrink usage on prune. The expected behaviour comes from the contract's own prose (section 4 table, section 4a, section 5), from D1-4 and D1-11, and from F-011, F-013 and F-014.

## Required changes

**1. A record carries its own class, so an audit record can go to an evidence stream and evidence can enter the audit chain.**

`Record` has both `Stream` and `Class`. `CommitBatch` seals "for class audit", and `AuditBeforeAct` checks only `rec.Class`. Nothing ties the class to the stream's class in `Layout`. A6's probe used a committer that does what the `CommitBatch` doc asks and nothing more:

| Call | Result |
| --- | --- |
| `AuditBeforeAct` with `Stream: sel751-feeder1/ser`, `Class: audit` | receipt `node-a:sel751-feeder1/ser:1`, and **`act` ran** |
| `Append` of an `adapter-evidence` record and an `audit` record on `node/audit` | both accepted, and committed as one batch `[adapter-evidence audit]` |

In the first case the privileged operation runs on a receipt from the evidence database. That breaks D1-11's audit before act, and the audit record is outside the C8 chain. In the second case, an unsealed record lands in the audit stream. Depending on how a Phase 2 committer reads "for class audit", the chain breaks or an unsealed record sits inside it.

Change: make class a property of the stream. `NewLog` takes the `Layout`, or a stream-to-class map built from it. `Append` and `AppendBatch` refuse, with `invalid`, a record whose `Class` is not its stream's class, or drop `Record.Class` altogether. `AuditBeforeAct` checks that the receipt's stream is the node's one audit stream. Add both rows above as tests.

**2. `Usage` must count live pages. If it counts the file size, startup prunes every confirmed event.**

Step 6 prunes "while usage is above `PruneTarget`". `RecoveryStore.Usage` is "the space the database uses". After a delete, SQLite keeps the freed pages in the file until compaction (step 7). If an implementation reports the file size, usage does not fall during step 6, so the loop runs until the boundary stops it. A6's probe used 1,000 events at quota, a required cursor at 900 and a target of 80%:

| `Usage` reports | First retained event after startup |
| --- | --- |
| live pages | 201: pruned to the target |
| file size, free pages included | 901: **every confirmed event pruned** |

Confirmed events are not lost upstream, so this is not V-S9's "un-forwarded record evicted". But the site is the system of record (Q6), and the second store keeps a tenth of what the first does after every recovery.

Change: define `Usage` as live pages times the page size, that is (`page_count` − `freelist_count`) × `page_size`, against the class quotas. Add a test with a store that does not shrink on prune.

## Should

**3. From `blocked`, the way out is the last-resort reserve, not space from outside.** The probe set the recovery reserve to 64 KiB, below the 96 KiB headroom, with 0 bytes free. Startup released the recovery reserve, found 64 KiB free and stopped in `blocked`. `Resume`, with nothing freed outside, saw "recovery reserve missing on an existing store", released the last-resort reserve, opened, and ended in `drain-only`. A restart does the same. So section 4a's "an open attempt is never the way out" holds, but "free space comes from outside the store" does not. The node only waits 60 s for the next `Resume`.

Change: when step 4 finds less than the headroom after releasing the recovery reserve, release the last-resort reserve in the same run. Add `RecoveryReserveBytes ≥ OpenHeadroomBytes` to `StartupPolicy.Validate`, alongside the existing last-resort check. With the proposed numbers (twice the WAL bound against the WAL bound plus 64 KiB), this holds whenever the WAL bound is at least 64 KiB, but nothing enforces it.

**4. A store at quota with nothing prunable starts in `collecting` with no alarm.** The probe set 1,000 of 1,000 used and a required consumer that never confirmed. Startup returned `collecting`, `AcceptsEvents` true, and no alarm. The first `Append` will be refused at quota, so nothing is lost. But the startup report says the node is healthy when it cannot store one event. Change: when usage is still at or above the limit after step 6, raise `store-quota-reached`, plus `required-consumer-stalled` for each required consumer whose cursor held the boundary.

**5. The startup loops do not check the context.** The compaction loop ends only when `CompactStep` returns `more=false`. With a `CompactStep` that always returns `more=true`, `RunStartup` was still running 2 s after its context expired, after 5.3 million calls. The prune loop ends when a pass prunes nothing, so it is bounded by the store's contents. Change: check `ctx.Err()` in both loops, and bound compaction by the free-page count at the start of step 7. Either way, end in `drain-only` with an alarm rather than hang. A startup that never returns raises nothing, which goes against principle 5.

**6. Inspect and `FreeBytes` failures reuse `store-open-blocked`.** Both end in `failed`, but `store-open-blocked` is also the alarm for the recoverable `blocked` mode. An operator who sees it waits for space that will not help. Change: give step 2 and the `FreeBytes` call their own alarm, such as `store-inspect-failed`.

## Checked and found sound

- **Every failure point in section 7** ends where the section 4 table says. Every failure before step 5 ends in `failed`, and `Open` is never called. `Open`, `CheckSettings` and `QuickCheck` end in `failed`, and the store is closed. `Usage`, `LoadCursors`, `LastCommitted`, `PruneStep` and `CompactStep` end in `drain-only`. A failed re-creation of the recovery reserve also ends in `drain-only`. The lock is released on every exit except a failed `Lock`.
- **A failed release of either reserve stops startup** before any open, with `reserve-release-failed` (D1-4).
- **A release that reports success but frees nothing** is caught by the headroom check, which gives `blocked`. The check measures free space; it does not trust the call.
- **The headroom against the F-013 model**, where an open fails below 32 KiB free: startup does not open at 28,672, 65,536 or 98,303 bytes free (`blocked`), and opens at 98,304. Whether 96 KiB prevents F-013 on NTFS is untested (below).
- **`AuditBeforeAct`** does not run `act` with no Log, and it refuses a record whose class is not audit. A stopped Log and a cancelled context return no receipt, by reading `Append`. Change 1 is the remaining gap.
- **One audit stream per node.** `StartupPolicy.Validate` refuses two (C5-A3-1).
- **No forced prune.** `PruneStep` accepts only a sealed `Boundary`. A stream with no consumer is never pruned.
- **`A5-node-posture.md` lifecycle table against V-S20.** Every UTC instant matches the Pacific time converted with that date's offset (Python `zoneinfo`, 10 of 10). A6 re-fetched the Windows 11 Home and Pro page on 2026-10-24. It lists 24H2 to 26H2 exactly as the table does, including 26H2 ending 10/10/2028 6:59:59 AM. That date falls on a Tuesday, where the other rows end on a Wednesday, but it is what the page says. The `EditionID` values are still `[inferred]` until the site image is read (H-14).

## For A6: what moves into V-S9 and H-14

**V-S9 gains these cases**, all runnable in simulation:
- `blocked`: no reserves and free space below the headroom; the store is not opened, the lock is held, and `Resume` opens only at the headroom;
- `drain-only`: a prune, compaction or re-creation failure; no new events, forwarding continues, and `Resume` returns to `collecting`;
- a failed release of each reserve stops startup;
- nothing prunable at quota (change 4);
- D1-11: with the audit store full, no `ACC` is sent and Syslog is still received;
- D1-7, carried from C4: a cleared SER buffer raises exactly one gap (V-S4).

**H-14 part 3**, on the Windows site image, needs:
- **headroom on NTFS:** a full store with no reserves and exactly the headroom free; the store must open and drain (the F-013 condition);
- **lock layers:** with the protected DACL on the store directory, a non-administrator account cannot open the files. A second instance under the service SID fails at `Lock` while the share-mode-0 lock file is held;
- **a failed release:** another process holds the reserve open without `FILE_SHARE_DELETE` (WinError 32), or an ACL denies delete. Startup must end in `failed` with `reserve-release-failed` and never open. On Linux, a read-only directory gives the same case.

**A5's question on the H-11 key:** recording the drive firmware with an H-11 result, without making it part of the key, is acceptable to A6. A firmware change is then visible, and it does not invalidate the result on its own. C-24 stays open until H-11 runs per hardware model.
