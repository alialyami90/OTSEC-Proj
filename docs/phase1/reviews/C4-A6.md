# C4 `otsec.event/0.1`: A6 review

- **Reviewed:** PR #29 at `32722fe` (`contracts/event/`), A4.
- **Reviewer:** A6, 2026-10-24.
- **Outcome:** **accepted with changes.** Changes 1 to 3 are required. Question 4 is for A4 and A1. Change 5 is security-relevant and is for A3 to rate. Change 6 is optional.

A6 tested the PR's `Validate`, `Codes` and `Align` from a test outside the package that does not use A4's helpers. Expected values come from A6's own transcription of Figure 10.16 (`tests/safety/recording_simulator/documented/sel-751/ser-fig-10-16.txt`), from V-S4, and from an independent JSON Schema validator.

## Required changes

**1. When `Align` finds a gap, it re-stores records that were already stored, and they carry no duplicate flag. V-S4 fails on its "records removed" case.**

When no offset leaves an overlap, every record of the new read is added with `gap-before`. A6's probes:

| Previous read | New read | `Align` result | Already stored and added again |
| --- | --- | --- | --- |
| `a b c d` | `a c d e` (b removed) | `gap`, added `[0 1 2 3]` | `a`, `c`, `d` |
| `a b c` | `a B c d` (b changed in place) | `gap`, added `[0 1 2 3]` | `a`, `c` |

The records that were already stored get new sequence numbers, so they get new event IDs. They carry `gap-before`, not `possible-duplicate`. V-S4 requires all of the following:
- zero duplicate stored events after overlap;
- forwarded duplicates share one stable event ID;
- on SEL-751, where no sequence number or counter is documented, removed records are reported as "gap detection unsupported" (C-06).

Both of the probe cases above also look like tampering with the device's buffer. The contract should make them visible, not bury them in new copies.

Change: when there is no overlap, the records of the new read that already appear in the previous read must not be stored as new events. If identical records make it unclear which ones are already stored, they are added with `possible-duplicate` and the result is `ambiguous`, as the existing rule already does for overlaps. A4 designs the rule. One approach is to align the previous read with the new read on their longest common ordered run, rather than only on a suffix of the previous read. Add the two cases above to `align_test.go`, with the stored set they must produce.

**2. The precision rule rejects honest records from any device whose time resolution is coarser than the digits it prints.**

`checkDigits` fails a time when the step of its last printed digit is finer than `resolution_ns`. A6's probes on row 1:
- with `resolution_ns` 4,166,667 (a quarter cycle at 60 Hz), `13:54:10.511` is rejected with code `precision`;
- with `resolution_ns` 2,000,000, it is rejected the same way.

SEL-751 is not affected, because the manual gives its Sequential Events Recorder a 1 ms time-stamp resolution (Specifications, p. 1.22) and it prints milliseconds. But a device that processes in quarter cycles and prints milliseconds is common. For such a device, a parser that states the true resolution produces an invalid event. A parser that states the print step instead gets past the rule, but then `resolution_ns` no longer means resolution. Either way the field is misleading, and the contract does not say what happens to an event that fails `Validate`. Under EP-1, a native record must never be discarded silently.

Change, in two parts:
- Define the rule's input as the step of the printed value, for example `print_step_ns`, or define `resolution_ns` as exactly that and say so in `doc.go`. Then state the device's real timing granularity through `accuracy_ns` or the quality fields.
- State in `doc.go` that a record which cannot be represented as a valid event is still kept, with its native bytes and `parse_status` `partial` or `failed`. It is never dropped. Change 3 depends on this too.

**3. A native time that cannot be converted has no valid representation, so the `invalid-time` flag cannot be used.**

`wall_clock` must be present and must parse. A6's probes on row 1:
- `native` set to `02/30/2007 13:54:10.511`, `wall_clock` empty and the `invalid-time` flag added: rejected, `time-format`;
- `wall_clock` set to `2007-02-28T23:59:60.511` (a leap second): rejected, `time-format` ("second out of range").

`invalid-time` is in the closed flag list (`event.go`), but no event that carries it can validate. The only other option is to leave out `device_time` entirely. That loses the device's native time string as a time, and the record's own clock-quality fields go with it.

Change: allow `wall_clock` to be absent when `device_time.flags` holds `invalid-time`, with `native` kept verbatim. Also decide how to represent second 60. Two options: accept `:60` in `wall_clock`, with UTC conversion refused unless `leap_seconds_known`, or carry it as `invalid-time`. Then add both cases to the valid examples.

## Question for A4 and A1

**4. An empty previous read is treated as a gap, so clearing the buffer raises `ser.gap` twice.**

| Previous read | New read | Result |
| --- | --- | --- |
| `a b` | (empty: the buffer was cleared) | `gap`, nothing added |
| (empty) | `x` | `gap`, `x` added with `gap-before` |

The first gap is correct. The second is not: when the previous read was empty, nothing can have been dropped from it.

The second read can still hide a loss. If the buffer wrapped completely between the two reads, records were lost without trace. That loss cannot be detected from the reads alone, and the same is true after any read.

A6 recommends returning `ok` with every record added when the previous read is empty and not nil, and noting the undetectable case in `doc.go`. A4 and A1 decide.

## For A3 to rate

**5. Nothing checks that `origin_auth` fits `collection.method`.**

`Validate` accepts each of these combinations on row 1:
- `syslog-receive` with `origin_auth` `session`;
- `adapter-poll` with `none`;
- `adapter-poll` with `tls-mutual`.

`origin_auth` is what AP-22 relies on to decide how far an event's content can be trusted. A producer bug could therefore label UDP Syslog as coming from an authenticated session, and the contract would not notice.

Change: add a closed table of the pairs that are allowed, and reject every other pair. For example, `adapter-poll` would allow `session` and the TLS values, and `syslog-receive` would allow `none` and the TLS values. Add a rejection test for each pair that is not allowed.

## Optional

**6. Decoding is not strict.** Go's `encoding/json` matches keys to fields case-insensitively, lets a duplicate key overwrite the first, and ignores unknown fields.

A6's probe added `"ORIGIN": "platform"` beside `"origin": "device"`, and the result depended on the order of the keys. C3 made its decoding strict because a signed document must be read the same way by every reader. Stored events are evidence, and the same argument applies. A4 can add a strict `Decode`, or C7 can cover it at the IPC boundary. A1 decides where it belongs.

### `Decode` and `strictjson.Forward`

A 0.1 event goes through `strictjson.Decode` and a later-minor event through `Forward`. Probes at the top level and nested (`source`, `source.asset.binding`):

| Probe | 0.1 | 0.2 |
| --- | --- | --- |
| `"ORIGIN"` before or after `"origin"`; `"Origin"` in place | rejected | rejected |
| Duplicate `"origin"`, nested duplicate `"origin_auth"` | rejected | rejected |
| `"ORIGIN_AUTH"` beside `"origin_auth"`; `"Method"` in `binding` | rejected | rejected |
| Kelvin sign `K` beside `"kind"`; long s `"ſource"` | rejected | rejected |
| `"SCHEMA": "otsec.event/0.1"` beside a 0.2 `"schema"` | rejected | rejected |
| Unknown exact key (`zz_new`, top level or in `binding`) | rejected | **ignored**, as D1-10 intends |
| Unknown key twice | rejected | rejected |
| `{}` after the event | rejected | rejected |

An unknown key that folds to no field, such as `Zz_new`, is ignored in 0.2. That is consistent with `Forward`.

A later-minor event that carries an enum value 0.1 does not know (`origin_auth` `tpm-attested`, `collection.method` `network-tap`, binding confidence `verified`, origin `sensor`) fails `Validate`. Unlike C1 (C1-A6 change 2), C4 never reads an unknown value as something more trusted. **For A1:** a newer site node's events will fail validation at an older central node until both run the same minor. That is safe, but the upgrade order belongs in C6 or the deployment notes.

### R-1: bound the size of a read before `Align` (required before a producer uses it)

`realign` builds a table of (n+1)·(m+1) 32-bit entries. A6 measured reads with no overlap:

| Records per read | Time | Allocated |
| --- | --- | --- |
| 1,024 | 6 ms | 4 MB |
| 4,096 | 0.41 s | 64 MB |
| 8,192 | 1.26 s | 256 MB |

SEL-751 returns at most 1,024 SER rows (S22, `SER` command: "as many as 1024 rows"), so a correct device is cheap. C1's SEL-751 example is a Telnet endpoint, labelled `plaintext-unauthenticated`. On such a link, a device fault or anyone on the path can return a much longer response. Two such reads of 50,000 lines need about 10 GB, which stops the collector and every other asset on the node. Question 7 of the brief applies: the platform must not be crashed through a device it monitors.

Change: state a maximum read length, and treat a longer read as a failed parse with its native bytes kept (EP-1) and a health event, never as input to `Align`. The bound can be per profile (1,024 for SEL-751) in C2, or a constant in C4 that `Align` enforces. A1 decides where. Add a test with a read one row over the bound.

### Should

**S-1. With repeated keys, a gap can hide a new record.** A ring buffer only appends, so in a new read the surviving old records come first and every new record follows them. `realign` can still match a record that comes after an added record to an old one. Example: previous read `1 3 0`, buffer cleared, then `4 0′ 5` is written, where `0′` has the same key as `0`. `Align` returns gap, adds `4` and `5`, and treats `0′` as already stored, so it is lost without a flag.

The same randomized test with keys from 6 values lost new records in 4,638 gap results out of 20,000 rounds. A6 tried one rule: on a gap, every record from the first added one onwards is added, and those that `realign` had matched are marked possible duplicates. That cut the gap losses to 1,349. The cases left are ambiguous from keys alone, for example `5 0 2 → 0′`, where a removal and a clear look the same.

SEL-751 keys include the date, the millisecond and the row text, so a repeat needs the same millisecond and the same text. A clock reset is the plausible route. Change: adopt the rule above or a better one, and say in `Align`'s doc that it assumes keys do not repeat within a pair of reads. Then add `1 3 0 → 4 0′ 5` to `align_test.go`.

**S-2. Second 60 is accepted only at 23:59 local time.** A leap second happens at 23:59:60 UTC. `wall_clock` is the device's local time. On a `-08:00` clock it prints `15:59:60`, and on a `+05:30` clock `05:29:60`. Both are rejected with `time-format`. EP-1 still holds, because the record can carry `invalid-time`. Change: accept second 60 at any minute and give it no UTC, as for 23:59. Alternatively, accept it only where the stated offset puts it at 23:59 UTC, and accept it at any minute when the offset is unknown.

**S-3. `invalid-time` with a `wall_clock` present validates.** A4's note says `wall_clock` is absent exactly when the flag is set. Only one direction is enforced. Change: reject a `wall_clock` when `invalid-time` is set, and add that as an invalid example.

Evidence class: `desk` (Go 1.26.0 on Linux). The ring-buffer model is A6's own and is labelled `simulated`. Nothing here was run against a device.
