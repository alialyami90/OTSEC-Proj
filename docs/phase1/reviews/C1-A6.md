## A1's question: does C1 claim more than the FID before the password?

**The prose does not, but the data model cannot say it, and a record that gates on nothing before the password validates.**

`doc.go` is accurate against Figure 7.38 (`gtID`). The `ID` response has the FID, BFID, CID, DEVID, DEVCODE, PARTNO, CONFIG, SPECIAL and the two display-package versions, and no serial number. `doc.go` says the FID is compared at Level 0 and the serial number only after authentication, where it "can detect a substitution, but cannot protect the credential". A6 found no sentence that claims more.

The record format has no way to carry that difference. `IdentityBinding.Attributes` is one list "compared on every session", with no statement of which entries are compared before a credential is sent. A6's probes on `sel-751-simulated.json`, a Telnet endpoint with a `device-reported` binding:

| `identity_binding.attributes` | `Validate` |
| --- | --- |
| `["firmware_id", "serial_number"]` (the golden example) | valid |
| `["serial_number"]` | **valid**: nothing is compared before the password is sent |
| `["ip_address"]` | **valid**: a `device-reported` binding on a value the device does not report |

## Required changes

**1. The binding must say which attributes are compared before a credential is released, and a `device-reported` binding must have at least one.**

AP-27 and V-S19 depend on the FID check running before `ACC`, so that firmware outside the allowlist never receives a password. C2 needs to read that order from the record, not from prose. As it stands, an asset bound on `serial_number` alone passes validation and would send the password with no prior check.

Change:
- Mark the pre-credential attributes in the binding, for example `pre_credential: ["firmware_id"]` as a subset of `attributes`.
- Reject a `device-reported` binding with an empty pre-credential set.
- For a `device-reported` binding, reject attributes the device does not report (`ip_address`, `location`, `device_name` as entered by an operator). A `device-reported` binding should compare only what the device reports.
- Add `["serial_number"]` alone and `["ip_address"]` to the invalid examples.

Which attribute a family can report before authentication is content. For SEL-751 it is what Figure 7.38 shows, so the profile is the natural place for it, through the `sel.id` operation that already runs in `probe` at access level 0 (C3, `6a776bc`).

**2. A later-minor record can carry trust that 0.1 never grants. The fallbacks that `asset.go` promises are not applied.**

The enum comment says a value from a later minor is read "as the enum's fallback (Effective), never as anything more trusted". No `Effective` function exists, and `Validate` accepts any well-formed token in a later-minor record. A6's probes on `sel-751-simulated.json` restamped as `otsec.asset/0.2`:

| Change | `Validate` | What a 0.1 reader is left with |
| --- | --- | --- |
| `identity_binding` `{method: "tpm-attested", strength: "cryptographic"}` | **valid** | A binding a UI shows as cryptographic. `FallbackStrength` is `spoofable`, but nothing applies it. |
| A FID observation with `method: "simulator-replay"` and class `device-observed` | **valid** | A simulator value shown as a device observation. The simulated pairing rule only knows `simulator-session` (P10). |
| `confidence: "verified"` on `firmware_id` | **valid** | A confidence the rules cannot check. |
| Evidence class `hardware-verified` on `serial_number` | rejected, but only because the binding then has no operator-declared value | In any attribute outside the binding, an evidence class 0.1 cannot interpret. |

The forward-compatibility rule is sound. These values only need reading down.

Change:
- Define a fallback for every enum that carries trust, and apply it wherever 0.1 code reads the value. Either add the `Effective` accessors the comment names, or normalize in `Decode`. The fallbacks, from least to most specific:
  - strength: `spoofable` unless the method is known to be `pinned-key`;
  - evidence class: the least trusted class;
  - a source method 0.1 does not know: never paired with `device-observed`;
  - confidence: recomputed from the observations.
- Add one valid example per row above, with the value a 0.1 reader must report.

**3. Decoding is not strict, so a key in a different case silently replaces the identity binding.**

C1 says it is not strict: unknown fields are ignored. Go's `encoding/json` also matches keys case-insensitively, and the last match wins. A6 appended `"IDENTITY_BINDING": {"method": "address-only", "strength": "spoofable", "attributes": []}` after the real `identity_binding` in `sel-751-simulated.json`. `Decode` accepted the record, and the binding Go read was `address-only` with no attributes. The FID check was gone. A person or a schema-based tool reading the same file sees the `device-reported` binding.

Asset records are configuration that operators and import tools write. A record whose binding means one thing to its reviewer and another to the node defeats B-05.

Change: decode strictly, as C3 does since `6b93659` and as A1 decided for C4 (D1-9). Reject a key that is not an exact field name, and reject duplicate keys. Unknown exact-case fields can still be accepted for forward compatibility, since that rule is about field names, not spellings. Add a case-variant key and a duplicate key to the invalid examples.

## Should

**4. The transcript spans in the golden examples cannot both come from one Figure 7.38-shaped response.**

`sel-751-simulated.json` puts the FID value at offset 42 (33 bytes) and the CID value at offset 98 (4 bytes) of the same simulator transcript. In Figure 7.38, `BFID` comes between `FID` and `CID`. With the figure's lines and CRLF endings, a FID value at 42 puts the CID value at 139, or at 136 with LF endings. Offset 98 falls inside the BFID value. No transcript is checked in, so the spans cannot be checked, and the README does not list spans among the invented values.

Change: check in the synthetic transcript the spans point into, and test that each span selects its value. Otherwise, say in the README that the spans are invented. A6's chain test will derive its own synthetic `ID` response from Figure 7.38 (C3-A6, decision (a)) and will check C1's spans against it.

It will run each pattern on the same corpus of valid and invalid node IDs. D1-3, a second node's request for an asset assigned to another node being refused, belongs to C7's request check. A6 will write it as a negative test when C7 opens.

## Checked and found sound

- **The invalid examples:** all 24 are rejected (the PR description says 20). A6 checked rejection only; A2's own tests check the reason for each.
- **Confidence rules.**
  - Two device claims do not corroborate each other.
  - A `conflicting` attribute keeps the operator-declared value.
  - `single-source` needs exactly one observation equal to the value.
- **The `simulated` class and the `simulator-session` method go together** in a 0.1 record. A session observation needs its transcript span (EP-2).
- **Asset IDs** must be assigned lowercase UUIDs. An ID derived from the FID is rejected.
- **Binding strength in 0.1 records.**
  - `device-reported` and `address-only` are `spoofable`.
  - A `pinned-key` binding cannot sit on a plaintext endpoint.
  - `encrypted-authenticated` requires `pinned-key`.
- **Profiles.**
  - A profile that sends adapter operations needs a firmware allowlist.
  - Every status except `unknown` needs a citation.
  - Mechanism `none` goes only with `unsupported` or `unknown`.
- **The golden FID** `SEL-751-R501-V0-Z104101-D20260910` is a Table A.1 row, on an allowed branch (R501).
- **`WeakestDownstreamSecurity`** reports nothing for an asset with no endpoints, and reports `plaintext-unauthenticated` for an unknown level.

### R-1: an asset with no pre-credential check can still receive a credential (required)

C1 says "a device-reported binding without one is invalid, so ACC is never sent ungated". The record format does not enforce the "so". A6's probes:

| Record | `Decode` |
| --- | --- |
| `sel-751-simulated.json` with its binding replaced by `address-only`, no attributes, Telnet endpoint unchanged (0.1) | **valid** |
| The same record as 0.2, binding method `tpm-attested`, `pre_credential` empty | **valid**. `Effective` keeps the unknown method, with strength `spoofable`. |

In both cases, nothing in C1 or C7 stops a credential being installed for the asset and sent. C7's run check compares the asset, node, transport and plaintext scope, and never the binding. So `ACC` and the Level 1 password go to whatever answers at the address, with no FID check first (AP-27, V-S19).

Change: state the rule where it is enforced, and test it. Either C1 or C7, as A1 decides, says that the collector uses a credential only for an asset whose `Effective` binding is `pinned-key`, or is `device-reported` with a non-empty `pre_credential` that passed `CheckProfile`. Any other binding, including a method from a later minor, is refused before connecting. `Effective` should read an unknown binding method as `address-only`. Add both records above as cases. A C7 refusal (`credential_mismatch`, or a new code) needs a test too.

### Should

**S-1. A 0.1 record with an unknown field decodes.** `Decode` uses `Forward` for every minor, so `"zz_new": 1` in a 0.1 record is ignored. C4 uses `strictjson.Decode` for records of its own minor or earlier. C1 should do the same, so that a typo in a hand-written 0.1 record fails instead of being dropped.

**Outcome: accepted once R-1 is resolved.**
